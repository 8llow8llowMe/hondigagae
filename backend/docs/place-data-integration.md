# 장소 데이터 통합 설계

> 관광 API만으로는 제주 반려견 동반 장소가 29곳뿐이고 식당·카페가 0곳이라 서비스가 성립하지 않는다.
> 부족분을 어떤 소스로 어떻게 메울지 정한 문서다. 실측 근거는 `data-api-analysis.md`, 엔티티는 `entity-design.md`.

## 1. 소스별 성격

| 소스 | 제주 규모 | 인증키 | 갱신 | 쓰는 곳 |
|------|----------|--------|------|---------|
| 관광정보 GW (TourAPI) | 반려견 동반 29곳 / 전체 1,027곳 | 필요 | 주 1회 배치 | 장소 마스터 |
| 반려동물 동반여행 API | 29곳 (동반 정보 9필드) | 필요 | 주 1회 배치 | 장소 마스터의 동반 조건 |
| **한국문화정보원 문화시설** | 1,191행 (여행 228 + 긴급 214 + 기타) | 불필요 (파일) | 파일 갱신 시 | 장소 마스터 확장, 긴급 시설 |
| **식약처 반려동물 동반출입 음식점** | 102곳 | 불필요 (파일) | 주 1회 배치 | 식당·카페 |
| VWorld 지오코더 | — | 필요 | 배치 중 호출 | 식약처 주소 → 좌표 |

**서버는 카카오 API 를 호출하지 않는다.** 지도는 클라이언트가 JS SDK 로 그리고, 서버가 다루는
장소 데이터는 전부 공공데이터다. 카카오 로컬을 한때 검토했다가 걷어낸 경위는 §6 에 남긴다.

## 2. 문화정보원 데이터

[data.go.kr/data/15111389](https://www.data.go.kr/data/15111389/fileData.do) — 파일데이터(CSV, 약 30MB, 전국 70,650행).
**활용신청 없이 다운로드**되므로 인증키가 필요 없다.

### 제주 1,191행의 구성

이름·주소가 통째로 같은 중복이 많은 원천이다. 중복 제거는 `sourceKey`(시설명+주소 해시) upsert 가
자동으로 처리하므로, 설계에 쓰는 숫자는 항상 **중복 제거 후** 값이어야 한다.

| 카테고리3 | 원본 행 | 중복 제거 | 쓰는 곳 |
|---------|-----:|-----:|---------|
| 동물약국 | 616 | **128** | `emergency_facility` |
| 동물병원 | 225 | **86** | `emergency_facility` |
| 반려동물용품 | 76 | 74 | 미사용 |
| 펜션 | 64 | 64 | `place` |
| 여행지 | 64 | 62 | `place` |
| 박물관 | 57 | 57 | `place` |
| 미용 | 44 | 36 | 미사용 |
| 카페 | 24 | 24 | `place` |
| 미술관 | 18 | 18 | `place` |
| 문예회관 | 3 | 3 | `place` |

- 여행 카테고리(의료·용품·미용 제외)는 중복 제거 후 **228곳**. 그중 동반 가능(Y)이 **169곳**,
  동반 불가(N) 59곳도 함께 적재해 검색에서 "동반 불가"로 보여준다
- 좌표는 1,191행 **전부** 보유. 실내/실외 컬럼도 빈값이 하나도 없다
- **카페 24곳이 이 원천의 숨은 값어치다.** 관광 API 에 제주 반려견 동반 카페가 0곳이라
  여행 일정의 휴식 슬롯을 채울 유일한 소스였다. 크기 제한(`12kg 미만`), 제한사항
  (`불독 견종 입장 제한`), 추가요금(`9,000원`)까지 들어 있어 place 의 반려동물 컬럼이 실제로 채워진다

## 3. place 엔티티 확장

원천이 둘이 되므로 식별자 체계를 바꾼다.

```text
place  (추가/변경)
├─ source            VARCHAR(20)  NOT NULL   신규. TOUR_API / CULTURE_PORTAL
├─ source_key        VARCHAR(64)  NOT NULL   신규. 원천 식별자
│                                             TourAPI = contentId 문자열
│                                             문화정보원 = SHA256(시설명|도로명주소) 앞 32자
├─ content_id        BIGINT       NULL       변경. TourAPI 전용이라 nullable 로
├─ indoor            BOOLEAN      NOT NULL   신규. default false
├─ outdoor           BOOLEAN      NOT NULL   신규. default false
├─ pet_only          BOOLEAN      NOT NULL   신규. default false
├─ allowed_pet_size  VARCHAR(20)  NOT NULL   신규. enum AllowedPetSize (기존 place_pet_info 와 동일 enum)
├─ pet_restriction   VARCHAR(500) NULL       신규
├─ pet_extra_fee     VARCHAR(200) NULL       신규
└─ merged_into_id    BIGINT       NULL       신규. 중복 판정 시 살아남은 행을 가리킨다

uk_place_source_source_key   (source, source_key)     ← 새 원천키
idx_place_content_id         (contentId)              ← uk 에서 일반 인덱스로 강등
idx_place_indoor_pet_available (indoor, petAvailable) ← 실내 대안 추천용
```

`merged_into_id`가 채워진 행은 조회에서 제외한다. 물리 삭제하지 않는 이유는 원천 재적재 시 되살아나기 때문이다.

## 4. 중복 판정 규칙

실측(문화정보원 여행용 171곳 × 관광 API 29곳)으로 검증한 결과다.

| 규칙 | 결과 | 처리 |
|------|-----:|------|
| 정규화 이름 완전일치 + 좌표 1km 이내 | 7건 | **자동 병합** |
| 정규화 이름 부분일치 + 좌표 300m 이내 | 7건 | **자동 병합** (실측 당시엔 수동 확인 후보였으나 구현은 자동 병합이다) |
| 좌표만 150m 이내 (이름 다름) | 2건 | **병합하지 않는다** |

- 정규화 = 괄호·대괄호 안 제거 → 공백·기호 제거 → 소문자
- 좌표만 근접한 건은 실제로 별개다. `녹차미로공원`과 `쉼한모금`이 93m 거리에 따로 있다.
  반대로 `도치돌목장`과 `도치돌 알파카목장`(99m)은 같은 곳이라, 이름 부분일치가 좌표보다 신뢰도가 높다.
  **단, 지금의 부분일치(`PlaceNameMatcher.isPartialMatch`, 한쪽이 다른 쪽을 품는 관계)로는 이 쌍이
  걸리지 않는다** — `도치돌목장 ⊄ 도치돌알파카목장`. 현재 동작을 `PlaceIdentityPolicyTest` 가 고정해 두었고,
  토큰 단위 부분일치로 넓히는 것은 오탐 실측이 필요한 후속 이슈다.
- 이름은 같은데 좌표가 먼 경우(`서우봉` vs `서우봉둘레길`)는 원천마다 기준점이 달라서다(정상 vs 입구).
  그래서 완전일치 규칙의 반경을 1km로 넉넉히 잡았다.
- 병합 시 **관광 API 행을 살리고** 문화정보원 행에 `merged_into_id`를 채운다.
  관광 API가 이미지·개요·동반 정보 9필드를 갖고 있어 정보량이 많다.
- 판정 상수(병합 1,000m·300m, 이미지 백필 500m)의 정본은 `PlaceIdentityPolicy` 한곳이다(#363) —
  값을 조정할 때 병합과 백필 중 한쪽만 바뀌는 어긋남을 막는다.
- 이미지 백필 반경 500m 가 병합 1,000m 보다 좁은 이유는 틀렸을 때 값이 다르기 때문이다 —
  병합은 두 행이 하나로 보이는 정도이고 재적재 때 다시 판정하지만, 백필은 **틀린 사진이 장소에 붙어**
  사용자가 곧바로 오해한다. 그래서 백필은 완전일치만 받는다.

## 5. 배치 잡

### CultureFacilityImportJob (신규)

```bash
# CSV 경로는 프로퍼티(culture-facility.file-path)로 준다. 기본값은 backend/data/pet_culture.csv 다.
./gradlew :service:batch-service:bootRun --args="--spring.batch.job.enabled=true --spring.batch.job.name=cultureFacilityImportJob sido=제주특별자치도"

# 다른 경로에 두었다면
CULTURE_FACILITY_CSV_PATH=/path/to/pet_culture.csv ./gradlew :service:batch-service:bootRun --args="..."
```

- 입력은 로컬 CSV 경로. API가 아니라 파일이라 읽기는 `adapter/out/file` 에 두고 `adapter/out/persistence` 로 upsert 한다
- CSV 원본은 30MB라 저장소에 커밋하지 않는다 (`.gitignore` 의 `backend/data/`). 재다운로드 주소는 §2
- `sido` 파라미터로 제주만 필터 (전국 70,650행 중 1,191행)
- upsert 키는 `(source, source_key)`. 재실행해도 같은 행을 갱신한다
- **적재가 채우는 컬럼을 추가·변경했으면 배포 뒤 잡을 1회 재실행한다.** 컬럼은 tour-service 의
  `ddl-auto` 가 만들지만 값은 이 잡만 채운다. 재실행을 빠뜨리면 API 는 필드를 정상적으로 내려주면서
  값만 기본값(`weekly_hours_spec` null · `open24` false)으로 남는다 — #301 이 그랬다.
  적재 로그의 `withWeeklyHoursSpec` 이 0 이거나 없으면 이 상태다
- 적재 후 별도 스텝에서 §4 규칙으로 중복 판정 → `merged_into_id` 갱신
- CSV는 UTF-8 BOM. `utf-8-sig` 로 읽어야 첫 컬럼명이 깨지지 않는다

## 6. 식당·카페 — 식약처 등록 업소

관광 API 에 제주 반려견 동반 식당이 0곳이라 "점심 → 숙소 → 카페 → 산책" 동선의 밥 먹는 칸이 비었다.
그 칸을 메우는 소스다.

### 6-1. 원천

[식품안전나라 반려동물 동반 가능 업소 현황](https://www.foodsafetykorea.go.kr/portal/petKorea.do).
`POST /portal/petKorea/downloadExcel.do` 에 인증키 없이 xlsx 가 온다.
컬럼은 연번·업소명·업종·지역·업소주소 다섯뿐이다.

```
전국 2,610곳 · 제주 102곳 (경기 707, 서울 486 다음 8위)
  일반음식점 56 · 휴게음식점 38 · 제과점영업 8
  제주시 51 · 서귀포시 51
```

이 원천을 고른 이유는 **영업자가 지자체에 등록을 신청해 수리된 업소**라는 점이다. 동반 가능 여부가
행정적으로 확정이라 추측이 섞이지 않는다. 식품위생법 시행규칙 개정(2026-01-02 공포, 2026-03-01 시행)으로
생긴 제도이고, 시행 다섯 달 만에 제주 102곳이 등록됐다. 등록이 계속 느는 원천이라 주기 실행이 전제다.

**공개된 오픈 API 가 아니라 화면이 쓰는 경로다.** 규격이 바뀌면 끊기므로
`mfds.pet-restaurant.file-path` 에 내려받아 둔 파일을 대신 읽는 우회로를 열어 둔다.

### 6-2. 좌표 — VWorld 지오코더

원천에 좌표가 없어 주소로 채운다. [국토교통부 지오코더(VWorld)](https://www.vworld.kr) 무료, 일 40,000건.

제주 102건을 실제로 돌려 검증한 결과다.

| 항목 | 결과 |
|------|------|
| 성공률 | **102 / 102** |
| 성공 방식 | 원본 주소 + 도로명 102건 — **정제 불필요** |
| 좌표 중복 | 0건 — 도로 중심점으로 뭉개지지 않고 건물 단위로 떨어진다 |
| 교차검증 | 두 원천에 다 있는 `애월더선셋` 기준 문화정보원 자체 좌표와 **38m** 차이 |

주소는 **정제하지 않고 원문 그대로** 넘긴다. `(1층)`, `(B동)`, `(2층 색달동)` 같은 꼬리를 떼지
않아도 전부 통과하고, 섣불리 괄호를 지우면 동을 구분하는 정보까지 날아가 오히려 정확도가 떨어진다.

### 6-3. 모르는 값은 넣지 않는다

이 원천은 "동반 가능하다"는 사실만 알려준다. 실내인지, 크기 제한이 있는지는 말해 주지 않는다.

| 컬럼 | 값 | 이유 |
|------|-----|------|
| `pet_available` | true | 등록 사실 자체가 근거 |
| `pet_allowance_type` | ALLOWED | 등록 제도가 전구역/일부구역을 나누지 않는다 |
| `source_category` | 일반음식점 / 휴게음식점 / 제과점영업 | 원본 업종 보존 |
| `content_type_id` | 39 | 세 업종 모두 관광 API 음식점으로 모은다 |
| `indoor` / `outdoor` | **NULL** | 원천에 없다. "실외"와 "정보 없음"은 다르다 |
| `allowed_pet_size` | UNKNOWN | 원천에 없다 |

INSERT 의 컬럼 목록에서 `indoor`/`outdoor` 를 아예 빼고, UPDATE 절에서도 건드리지 않는다.
병합 잡이 다른 원천에서 옮겨 채운 값을 재실행 때마다 도로 지우면 안 되기 때문이다.

좌표를 못 얻은 업소는 **적재하지 않는다**. 목록에는 보이는데 지도에는 없는 장소가 생기는 편이 더 나쁘다.
버린 건수와 업소명은 로그로 남긴다.

### 6-4. 문화정보원 카페와의 관계

이름 대조로 확인한 결과 두 소스가 겹치는 곳은 `애월더선셋` **1곳뿐**이다. 여행시설 228곳과는 0곳.
사실상 상호 보완이라 합치면 제주 식음료 **125곳**이 된다.

### 6-5. 카카오 로컬을 걷어낸 경위

한때 카카오 로컬 실시간 검색으로 이 칸을 메우려 했다. 실제로 붙여 재보고 접었다.

| | 카카오 로컬 | 공공데이터 |
|---|---|---|
| 제주 식음료 | 카페 257 + 식당 37 (`애견동반` 키워드) | 카페 24 + 식당·제과 102 |
| 동반 가능 여부 | **추측** — 리뷰 등에 그 단어가 있다는 뜻 | **확정** — 지자체 등록 / 원천 Y 플래그 |
| 크기 제한·제한사항·추가요금 | 없음 | 있음 (문화정보원) |
| 실내/실외 | 없음 | 있음 |
| 저장 | **금지** (DB·캐시 모두) | 가능 |

숫자는 카카오가 많지만 검증되지 않은 숫자다. 실제로 `애견동반` 검색 결과에 프랜차이즈 디저트
체인이 올라왔다. 응답에 `petPolicyVerified=false` 를 달아 "단정하지 말라"고 안내해야 하는 데이터였다.

걷어내서 얻은 것:

- 저장 금지 예외 규칙이 사라진다. 좌표를 일정에 남길 수 있어 AI 플래너가 식사 슬롯을 DB 에서 채운다
- 반려견 필터·실내외·크기 필터가 식당에도 그대로 적용된다 (같은 `place` 테이블이므로)
- 실시간 외부 호출과 서킷브레이커 폴백 경로가 하나 줄어든다

잃은 것은 커버리지다. 제주 음식점 7,704곳 중 102곳만 다룬다. "근처 아무 밥집" 폴백은 없어졌다.
반려견 여행 서비스에서는 맞는 교환이라고 본다.

**카카오는 로그인에만 쓴다.** 지도는 클라이언트에서 JS SDK 로 그리고 서버는 관여하지 않는다.

## 7. AI 플래너의 식사 슬롯

식음료 장소가 `place` 테이블에 있으므로 일정에 미리 넣을 수 있다.

- AI 가 만드는 일정의 식사 항목은 `PlanItemType.MEAL` + `targetId = place.id` 로 확정해 둔다
- 동선 좌표가 바뀌면 `GET /api/v1/places/nearby?contentType=RESTAURANT` 로 대안을 제시한다
- 좌표를 저장할 수 있으므로 지도에 동선을 그대로 그릴 수 있다

다만 제주 전역 102곳이라 동선에 따라 반경 안에 한 곳도 없을 수 있다. 그때는 "이 근처에는 확인된
동반 가능 식당이 없다"고 정직하게 말해야 한다 — 검증되지 않은 후보로 칸을 채우지 않는다.

1. `place` 엔티티 확장 + 마이그레이션 (§3) — 완료
2. `PlaceImportJob` 에 `source`/`source_key` 추가 (§5) — 완료
3. `CultureFacilityImportJob` 신규 + 중복 판정 스텝 (§5, §4) — 완료

그중 식음료가 125곳이다.

## 9. 긴급 시설 (동물병원·동물약국)

같은 CSV 안에 동물병원과 동물약국이 섞여 있어 한 번 읽는 김에 같이 적재한다. 다만 여행 장소가
아니라 **급할 때 찾는 곳**이므로 `place` 가 아닌 `emergency_facility` 테이블로 분리했다.
여행 일정 후보에 동물병원이 섞여 들어가는 것을 막기 위해서다.

**두 종류를 한 테이블에 담는다.** 급할 때 필요한 것은 "가장 가까운 도움"이지 "가장 가까운 병원"이
아니다. 종류를 컬럼(`facility_type`)으로 나눠 두면 거리로 함께 정렬해 그 질문에 답할 수 있고,
필요하면 종류로 좁힐 수도 있다.

### 9-1. 실측한 데이터 품질

| 항목 | 동물병원 | 동물약국 |
|------|---------|---------|
| 원본 행 | 225 | 616 |
| **실제 시설 수** | **86** | **128** |
| 좌표 보유 | 225 / 225 | 128 / 128 |
| 전화번호 보유 | 224 / 225 | **128 / 128** |
| 운영시간 보유 | **114 / 225 (51%)** | **125 / 128 (98%)** |
| 24시간 운영 | **3곳** | 사실상 없음 |

중복은 `source_key`(시설명+주소 해시) UK 로 upsert 하면 자동 정리된다. 이름이 겹치는 병원·약국은
0건이라 두 종류를 한 테이블에 넣어도 서로 흡수하지 않는다.

**품질이 종류마다 다르다는 점이 응답 설계를 갈랐다.** 약국은 운영시간이 98% 채워지는데 병원은
절반뿐이다. null 을 "휴무"로 오해하면 안 되므로 응답에 `operatingHoursKnown` 플래그를 따로 내려
화면이 "영업시간 정보 없음"으로 표시하게 한다.

`open24` 판정에서 **"연중무휴"를 24시간으로 보지 않는다.** 연중무휴는 매일 연다는 뜻이지
하루 24시간 연다는 뜻이 아니다 — 실제로 "연중무휴 / 14:00~20:00" 인 병원이 있다.
상호에 `24시` 가 있거나 운영시간이 `00:00~24:00` 인 경우만 true 다 (`OperatingHoursParser`).
첫 정규식이 "연중무휴"에 오탐해 24시간 병원을 부풀렸던 자리라 규칙을 여기 남긴다.

### 9-2. 반경 검색

```
GET /api/v1/emergencies/facilities?lat=&lng=&radius=&type=&open24Only=&size=
```

`type` 을 비우면 병원과 약국이 거리 순으로 섞여 나온다.

DB 는 좌표 **사각 범위**로만 1차 필터하고(`EmergencyFacilityRepository.findWithinBox`),
정확한 원형 반경과 거리 정렬은 애플리케이션에서 계산한다. 제주 전체가 214곳뿐이라 메모리 정렬
비용이 무시할 수준이고, DB 에 삼각함수를 넣는 것보다 이식성이 좋다.
**규모가 커지면 공간 인덱스로 옮겨야 하는 지점**이라 Processor 주석에 표시해 두었다.

거리 계산은 `common-core` 의 `GeoDistance`(하버사인)를 쓴다. 같은 계산을 장소 주변 검색·긴급
시설 검색·배치 중복 판정 세 곳이 따로 하면 "300m 안"의 뜻이 갈라지므로 한곳에 모았다.

`type`·`open24` 필터는 파라미터가 `null` 이면 조건 자체를 끄는 방식이다
(`:facilityType is null or h.facilityType = :facilityType`).

### 9-3. 검증

JPQL 은 컴파일로 검증되지 않아 `EmergencyFacilityRepositoryTest` 에서 H2 로 실제 스키마를 만들고
질의한다. 이 테스트가 잡아낸 실제 결함이 하나 있다 — `@Comment` 안의 작은따옴표를 Hibernate 가
이스케이프하지 않아 `comment on column` DDL 이 깨졌다. 엔티티 코멘트에는 작은따옴표를 쓰지 않는다.

`place` 쪽 반경 검색도 같은 방식으로 `PlaceRepositoryNearbyTest` 가 검증한다. 병합된 행이 빠지는지,
좌표 없는 행이 걸러지는지, `indoor` 가 null 인 장소가 true/false 어느 필터에도 잡히지 않는지를 확인한다.
마지막 항목이 특히 중요하다 — 식약처 원천이 실내 여부를 주지 않아 그 상태가 실제로 존재한다.

## 10. 이후 확장 — 매칭·영업시간 컬럼

적재 이후 두 기능이 컬럼을 더했다. 원천 데이터의 어떤 성질에서 나왔는지만 여기 남긴다.

### 10-1. `place.max_pet_weight_kg`

크기 원문에 kg 숫자가 있는 곳(제주 28곳, "5kg 이하"~"30kg 미만")의 숫자를 보존한다.
enum(`allowed_pet_size`)은 10kg 경계로 뭉개므로 "12kg 미만"인 곳이 SMALL_MEDIUM(중형까지)이
되어 20kg 중형견도 통과해 버린다. 검색의 `petWeightKg` 필터가 이 컬럼으로 정확히 거른다.
미만/이하는 구분하지 않는다 — 1kg 오차는 enum 의 오차보다 작다.

### 10-2. `emergency_facility.weekly_hours_spec`

운영시간 자유 텍스트를 `WeeklySchedule` spec("12345:0900-2100;6:1000-2200")으로 구조화해
저장한다. 실측 기준 여행 장소 93%, 동물약국 98%, 동물병원 64% 가 풀린다.
"법정공휴일 …" 같은 조건부 구간은 공휴일 달력 없이 판정할 수 없어 버리되 나머지는 살리고,
원문을 아예 풀 수 없으면 null — 조회의 `openNow` 가 "모름"이 된다. 모름을 닫힘으로 표시하지
않는 것이 규칙이다.

여행 장소도 같은 규칙으로 구조화한다 — `place_intro.weekly_hours_spec` + `open24` 를 문화정보원
적재가 채우고, 장소 상세 응답(`intro.openNow`)이 이를 판정한다. 원문(`use_time`)은 그대로
보존한다. 단, TourAPI 는 `detailIntro2` 를 아직 수집하지 않아 spec 이 채워지는 것은 문화정보원
출처 장소(약 230곳)뿐이다. TourAPI 운영시간 수집과 목록 `openNowOnly` 필터는 후속 과제다.

두 컬럼의 값은 `cultureFacilityImportJob` 재실행으로만 채워진다 — 컬럼이 생긴 시점의 기존 행은
비어 있다(§5 재실행 규칙, #301).
