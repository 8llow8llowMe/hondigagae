# [BE] feat: TourAPI `detailIntro2` 운영시간 수집 — 여행 장소 `openNow` 커버리지 확대

> 이슈: [#361](https://github.com/8llow8llowMe/hondigagae/issues/361)
> 상태: 구현 완료
> 대상: batch-service `placeimport` 컨텍스트 (조회 쪽은 손대지 않았다)

## 무엇이 문제였나 — 판정되는 장소가 15% 미만

장소 상세의 `intro.openNow` / `open24` 는 #267 에서 이미 구현됐다. 그런데 값을 만들어 주는
원천이 문화정보원 하나뿐이라, **TourAPI 출처 장소는 `place_intro` 행이 아예 없어 판정이 전부
"모름"(null)으로 내려갔다.**

2026-09-08 dev 재적재(#301) 뒤 실측으로 커버리지가 드러났다.

| 출처 | 곳 | `place_intro` | `openNow` 판정 |
| --- | ---: | --- | --- |
| 문화정보원 | 228 → **174** (54곳은 중복 병합으로 흡수) | 있음 | 가능 |
| TourAPI | **964** | 없음 | 전부 모름 |
| 식약처 | 102 | 없음 (원천에 운영시간이 없다) | 전부 모름 |

기능은 "구현"이었지만 **화면에서 영업 상태가 실제로 보이는 장소는 전체의 15% 미만**이었다.
`openNow` 는 판정 로직의 문제가 아니라 데이터 커버리지의 문제였다.

## 왜 TourAPI 는 행이 없었나

`place` 마스터는 목록 API(`areaBasedList2`)로 채웠고, **운영시간은 목록에 없다.** 상세
API(`detailIntro2`)를 장소당 한 번 불러야 나온다. #267 시점에는 그 호출을 붙이지 않았고
(`267-place-open-hours.md` 설계 판단표의 마지막 줄이 그 기록이다), `place_intro` 를 쓰는 경로는
`JdbcPlaceBulkAdapter.CULTURE_INTRO_UPSERT_SQL` 하나였다.

덤으로 `place_intro` 의 `info_center` / `chk_pet` / `chk_baby_carriage` / `chk_credit_card` /
`raw_json` 은 **설계상 `detailIntro2` 전용 컬럼**이라(`entity-design.md` §2) 채우는 코드가
아무 곳에도 없었다. 상세 응답의 해당 필드도 늘 null 이었다. 이번에 같이 채워진다.

## 판단 1 — 요일 표기 없는 원문을 "매일"로 볼 것인가

`OperatingHoursParser` 는 세그먼트에 **요일부를 필수로** 요구했다. 문화정보원 CSV 가
`"매일 09:00~21:00"` / `"월~금 09:00~21:00, 토 10:00~22:00"` 처럼 요일부를 붙여 주기 때문이다.
TourAPI 는 그렇지 않다 — `"09:00~18:00"` 만 주는 경우가 흔하다.

그대로 두면 그 원문이 전부 null 로 남아 **수집의 값어치 자체가 사라진다.** 실은 더 나빴다:
정규식 `^(.+?)\s*(\d{1,2}):(\d{2})~…$` 는 `"09:00~18:00"` 을 요일부 `"0"` + 시각 `"9:00~18:00"`
으로 매칭해 버려, 못 푸는 이유조차 엉뚱한 자리에 있었다.

**요일부를 선택으로 바꾸고, 비면 전 요일로 본다.** 근거는 이렇다 — 요일 정보가 없는 원문에서
운영시간을 매일로 보는 것은 추론이지만, **휴무일(`rest_date`)은 spec 이 원래 반영하지 않으므로
새로운 오차 유형이 아니다.** 문화정보원의 `"매일 09:00~21:00"` + `"매주 화요일 휴무"` 조합이
이미 화요일에 "영업 중"이라고 말하고 있고, 그 절충은 #267 에서 받아들인 것이다. 여기서
요일부 없는 원문만 따로 "모름"으로 남길 이유가 없다.

나머지 규칙은 건드리지 않았다 — 조건부 구간(`"법정공휴일 …"`, `"7~9월 …"`)은 여전히 버리고,
못 풀면 null 로 남기며, `"연중무휴"` 는 여전히 24시간이 아니다.

**그러나 이 추론을 기본값으로 두면 안 된다.** 같은 파서를 긴급 시설 적재도 쓰고, 그쪽 소비처는
표시가 아니라 **하드 필터**다 — `openNowOnly` 는 "지금 확실히 열린 곳"만 남기며 모름도 뺀다
(`NearbyFacilityQueryProcessor`, #37). 여기서 모름을 추론값 `true` 로 승격시키면, 운영시간이
`"09:00~18:00"` 이고 휴무일이 `"일요일"` 인 동물병원이 **일요일 오후에 "지금 진료 중"으로 올라온다.**
화면에 잘못 표시하는 것과, 급할 때 닫힌 병원을 골라 주는 것은 성격이 다르다.

그래서 추론은 호출부가 고른다 — `parseWeekly` 는 종전대로 엄격하고(문화정보원·긴급 시설 경로가
그대로 쓴다), TourAPI 수집만 `parseWeeklyAssumingEveryDay` 를 쓴다. **기존 두 경로의 해석 결과는
한 건도 바뀌지 않는다** — 그래서 문화정보원 실측 수치(여행 장소 93% 등)도 다시 재지 않았다.

## 판단 2 — 964콜을 어떻게 쓸 것인가

개발계정 쿼터는 **일 1,000건**이고, `placeImportJob` 의 이미지 단계가 **이미 실행당 964콜**
(장소당 `detailImage2` 1회)을 쓰고 있었다. 운영시간 964콜을 그대로 더하면 확실히 초과하고,
초과분은 조용히 실패해 **뒷부분 장소만 커버리지가 비는** 형태가 된다 — 가장 발견하기 어려운
고장이다.

세 안을 놓고 골랐다.

1. 상한 없이 전량 964콜 — 커버리지를 즉시 채우지만 한도를 확실히 넘는다
2. **실행당 상한 + 증분 대상 선정** ← 채택
3. 이미지 단계까지 함께 증분화해 총 호출을 1,000 밑으로 맞춘다 — 쿼터는 실제로 지켜지지만
   이슈 범위를 넘어 멱등하게 돌던 기존 단계를 함께 고친다

**2번을 골랐다.** 대상은 `place_intro` 가 **없는 곳 먼저 → 그다음 `synced_at` 오래된 순 → id**
이고, 실행당 상한은 `place-intro-import.max-calls-per-run`(기본 300)이다. 이 "며칠 분할"은
`entity-design.md` §11 이 처음부터 적어 둔 적재 전략과 같은 규칙이다.

**그리고 상한 300 이 실제로 300 이 되도록 스텝 순서를 바꿨다.** 처음에는 intro 를 이미지 스텝
뒤에 두었는데, 그러면 intro 가 시작될 때 남은 하루 예산이 목록(약 17콜)과 이미지(964콜)를 빼고
**수십 건**밖에 없다 — 상한 300 은 조회할 대상 수의 뚜껑일 뿐이고 진도는 남은 예산이 정한다.
그 배치로는 전량 커버가 4주가 아니라 10개월 규모였다.

**순서가 곧 예산 우선순위**이므로 intro 를 이미지 앞으로 옮겼다. 근거는 두 데이터의 성격 차이다 —
intro 는 **아직 없는** 데이터이고, 이미지는 **이미 적재된** 데이터를 매 실행 전량 다시 받는
갱신이다. 이미지가 한도에 닿아 멈추면 기존 `place_image` 행이 그대로 남으므로 잃는 것은 "이번 주
갱신"뿐이지만, intro 가 못 돌면 그 장소의 영업 상태는 계속 "모름"이다. 그래서 이미지 스텝은
한도 초과를 만나면 남은 장소를 건너뛰고 **조용히** 끝낸다(스텝을 실패로 만들지 않는다) —
이 순서에서 한도에 닿는 것은 예외가 아니라 정상이기 때문이다.

매 실행 이미지까지 전량 갱신해야 하면 이미지 대상 쿼리에도 같은 증분 규칙이 필요하다. 그것은
이 이슈 범위 밖으로 남긴다.

**한도 초과는 "한 곳 실패"가 아니다.** 포털은 한도 초과를 HTTP 200 + 오류 본문으로 답하므로
서킷이 세지 않는다. 이것을 장소 단위 실패로 접으면 남은 대상 전부가 실패로 기록되고, 아래
"뒤로 밀기" 규칙까지 겹쳐 **그 장소들이 다음 실행에서도 채워지지 않는다.** 그래서 한도 초과를
전용 코드(`TOUR_API_QUOTA_EXCEEDED`)로 분리해 스텝을 즉시 끝낸다 — 진도는 예산만큼만 나가고,
채우지 못한 장소는 순환 앞자리에 그대로 남는다.

**원천이 내용을 주지 않은 곳도 `synced_at` 은 민다.** 정렬이 "intro 없는 곳 먼저"라,
`detailIntro2` 가 빈 응답(`items=""`)을 주는 장소는 행이 생기지 않아 **매 실행 다시 앞자리를
차지한다.** 그대로 두면 그 장소들이 희소한 예산을 계속 먹고 나머지는 한 번도 차례가 오지
않는다. 그렇다고 빈 행으로 덮으면 다른 경로가 채워 둔 값을 지우므로, 내용 컬럼은 건드리지 않고
`synced_at` 만 밀어 순환에 넣는다 — 지오코딩 실패 업소의 `touchPetRestaurantsSyncedAt` 와 같은 규칙이다.

**호출이 실패한 곳도 같은 이유로 뒤로 민다.** 영영 실패하는 장소(원천에서 사라진 `contentId`
등)가 NULL 머리에 고착하면 매 실행 그만큼의 예산이 아무것도 채우지 않고 사라진다. 한 바퀴 뒤에
자연히 재시도되므로 일시적 실패도 잃지 않는다.

**서킷 오픈과 키 누락은 한 곳 실패로 넘기지 않고 단계를 즉시 끝낸다.** 둘 다 남은 대상을 다
돌아도 결과가 같은 상태다 — 원천이 죽었거나 키가 없다. 특히 키 누락은 호출 전에 터지므로 서킷이
막아 주지 못한다: 그대로 두면 상한만큼의 장소가 전부 "실패"로 기록되며 `synced_at` 이 밀려
대상 순환까지 헝클어진다. 그 밖의 한 곳 실패는 기록하고 계속 간다 — 운영시간은 보강 데이터라
한 곳의 오류가 나머지를 막으면 손해가 더 크다.

## 판단 3 — 운영시간이 없는 타입은 부르지 않는다

`detailIntro2` 는 contentTypeId 마다 응답 필드가 전부 갈린다. 그런데 **숙박(32)·여행코스(25)·
축제(15)에는 운영시간 필드가 아예 없다.** 숙박은 `checkintime` / `checkouttime` 을 주지만
그것은 영업시간이 아니다 — 호텔의 `openNow` 를 체크인 시각으로 판정하면 틀린 말을 하게 된다.

예산이 희소한 자원이므로 **판정에 쓸 수 없는 호출로 예산을 태우지 않는다.** 대상은
관광지(12)·문화시설(14)·레포츠(28)·쇼핑(38)·음식점(39)이고, 이 목록은
`PlaceContentType.INTRO_HOURS_TARGETS` 한곳에 있다.

대가는 있다 — 숙박·여행코스 장소는 `info_center` / `parking` 도 못 받는다. 쿼터에 여유가
생기면(운영계정 키) 그때 넓히는 것이 맞는 순서다.

## 판단 4 — HTML 과 컬럼 길이는 어댑터가 흡수한다

TourAPI 상세 텍스트에는 `<br>` 과 HTML 엔티티가 섞여 오고, 길이도 `place_intro` 컬럼
(`use_time` 300자 등)을 넘는다. 둘 다 원천 형식의 문제라 도메인 파서가 아니라 어댑터
(`TourApiIntroFieldMapper`)가 흡수한다 — `mapx`/`mapy` 를 `lat`/`lng` 로 바로잡는 것과 같은 자리다.

- `<br>` 은 **세그먼트 구분자(`,`)로** 바꾼다. 그래야 `"09:00~18:00<br>입장마감 17:30"` 에서 앞
  구간이 살고 뒤 구간만 버려진다. 단순 제거였다면 한 줄로 붙어 전체가 "모름"이 된다
- 컬럼 길이로 **자른다.** 자르지 않으면 MySQL strict 모드가 `Data too long` 으로 단계 전체를
  죽인다. 한 장소의 긴 안내문이 964곳의 적재를 무너뜨리게 둘 수는 없다

## 어떻게 만들었나

이미지 수집 경로와 같은 모양으로 맞췄다 — 같은 성격의 일(장소당 1회 상세 호출)이 두 군데에서
다른 모양이면 다음 사람이 둘 중 어느 쪽을 따라야 하는지 알 수 없다.

```text
PlaceIntroImportTasklet            (adapter/in/batch/tasklet)
  → PlaceImportUseCase#importPlaceIntros
    → PlaceImportFacade → PlaceIntroImportProcessor
        ├ PlaceIntroBulkPort#findTourApiTargets(타입 코드, 상한)   ← 증분 대상 선정
        ├ PlaceCatalogPort#fetchDetailIntro(contentId, 타입)       ← detailIntro2 1회
        └ PlaceIntroBulkPort#upsert(placeId, intro)                ← place_intro upsert
```

- 도메인 모델 `ImportedPlaceIntro` 는 `ImportedPlaceImage` 처럼 **`placeId` 를 들지 않는다.**
  place id 는 쓰기 포트가 따로 받는다 — 수집한 것은 "장소의 소개"이고 그것이 어느 행에 꽂히는지는
  적재 쪽 관심사다
- 쓰기 대상은 `source='TOUR_API'` 로 가둬 **문화정보원 행을 덮지 않는다.** 병합·delist 된 행도
  대상에서 뺀다(이미지 대상 쿼리와 같은 규칙)
- `place_intro.id` 는 `place_id` 를 그대로 쓴다(1:1). 문화정보원 경로와 같은 규칙이라 재실행이 멱등이다

## 곁딸린 계약 변화 — `intro` 가 null 이 아니게 되는 장소

`synced_at` 만 미는 경로가 **빈 `place_intro` 행을 만든다.** 조회 쪽
(`PlaceQueryProcessor`)은 행 존재로 `Optional` 을 만들므로, 원천이 내용을 주지 않는 TourAPI
장소는 상세 응답의 `intro` 가 `null` 대신 **모든 필드가 null 인 객체**로 나간다.

판정은 틀어지지 않는다 — `PlaceOpenState.resolve(null, false, now)` 는 그대로 "모름"(null)이다.
화면도 바뀌지 않는다: FE 의 이용 안내 절은 `hasUseGuideValue` 로 값이 하나라도 있을 때만 서고
(`frontend/src/features/place/place-detail-section.tsx`), 운영시간 행은 원래 `intro?.` 로 읽어
`intro` 가 null 이든 비었든 같게 그린다. "intro 객체는 있지만 내부 값이 전부 없으면 섹션을 만들지
않는다"는 FE 테스트가 이 동작을 이미 고정해 두고 있었다.

그래도 **계약이 바뀐 것은 사실이라 여기 적는다.** `intro != null` 을 "소개 정보가 있다"로 읽는
소비자가 새로 생기면 이 전제가 깨진다 — 판단 기준은 객체의 유무가 아니라 필드의 유무다.

## 커버리지는 로그로 본다

`withWeeklyHoursSpec` 이 0 이면 컬럼만 있고 값이 없는 상태 — #301 이 정확히 그랬고, API 를
전수 조회해 보기 전에는 아무도 몰랐다. 그래서 적재 로그에 구조화 커버리지를 남긴다
(문화정보원 적재와 같은 규칙).

```text
place intro import finished. targets=300, upserted=287, withUseTime=241,
withWeeklyHoursSpec=198, open24=6, emptyIntro=13, skipped=0, failedPlaces=0
```
