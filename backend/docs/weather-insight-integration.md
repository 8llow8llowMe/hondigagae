# 날씨 기반 인사이트 통합 설계

> 기상청 단기예보를 붙여 여행 적합도와 산책 위험도를 산출하는 구조를 정리한 문서다.
> 원천 실측 근거는 `data-api-analysis.md` §6-1, 엔티티는 `entity-design.md` §10, §7 참고.

## 1. 왜 이 기능인가

관광 데이터를 예쁘게 보여 주는 서비스는 이미 많다. 반려견 여행 서비스가 다른 지점은
**같은 날씨를 사람이 아니라 반려견 기준으로 읽는 것**이다.

- 한여름 기온 25도 맑은 한낮은 사람에게 산책하기 좋은 날이지만, 아스팔트 표면은 50도를 넘어
  발바닥 화상 구간에 들어간다
- 반려견은 땀이 아니라 헐떡임으로 체온을 내리므로 습도가 높으면 같은 기온이 훨씬 위험하다
- 단두종(불독/퍼그/시츄)은 기도가 짧아 같은 더위에서 먼저 위험해진다

이 셋은 기온만 보는 판정으로는 전부 보이지 않는다. 그래서 적합도(`suitability`)와
산책 위험도(`walk-safety`)를 **일부러 나눴다** — 적합도는 "여기 갈 만한가", 위험도는
"지금 걸어도 되는가"를 묻는다. 하나로 합치면 둘 중 하나가 반드시 희석된다.

## 2. 데이터 원천

| 원천 | 오퍼레이션 | 방식 | 커버리지 |
|------|-----------|------|---------|
| 기상청 단기예보 `VilageFcstInfoService_2.0` | `getVilageFcst` | 실시간 + Redis 격자별 캐시 | 오늘 ~ **오늘+4** (실측) |
| 기상청 중기예보 `MidFcstInfoService` | `getMidLandFcst` + `getMidTa` | 실시간 + Redis 지역별 캐시 | 오늘+4 ~ **오늘+10** (실측) |
| 관광지 집중률 `TatsCnctrRateService` | `tatsCnctrRatedList` | 배치 적재 + DB 조회 | **30일 rolling** |

**원천마다 커버리지가 다르다는 점이 응답 설계를 갈랐다.** 날씨는 없고 혼잡도만 있는 날짜가
있고, 반대로 단기예보만 있고 중기예보는 없는 날짜도 있다. 그래서 적합도 응답은
`weatherApplied` / `congestionApplied` 플래그와 `forecastSource` 를 따로 내려 어떤 근거가
실제로 쓰였는지 드러낸다. 없는 근거를 0으로 채워 점수에 섞지 않는다.

### 2-1. 단기예보와 중기예보를 잇는 규칙

단기예보(오늘~+4)와 중기예보(+4~+10)를 이어 **약 11일**을 덮는다. 겹치는 날짜가 있고 빈 날짜는 없다. 여행 계획 서비스에서는
3일 밖 날짜를 묻는 것이 예외가 아니라 기본 경로라, 중기예보가 없으면 적합도가 대부분의
질문에 답하지 못한다.

| | 단기예보 | 중기예보 |
|---|---|---|
| 위치 지정 | 격자 `nx`, `ny` | **예보구역 `regId`** |
| 발표 | 1일 8회 | **1일 2회 (06, 18시)** |
| 시간 해상도 | 1시간 | **오전/오후** |
| 오퍼레이션 | 하나 | **둘을 날짜로 조인** |
| 습도 / 풍속 | 있음 | **없음** |
| 시각별 데이터 | 있음 | **없음** |

**겹치는 날짜는 단기예보가 온전할 때만 단기예보를 쓴다.** 시각별 데이터가 있어 더 정확하지만,
**단기예보의 마지막 날은 시각이 거의 오지 않는다** — 실측에서 자정 한 시각뿐이었다
(§5-1). 그 날짜는 최고/최저기온을 원천에서 직접 주는 중기예보가 더 정확하다.
합치는 규칙은 `WeatherForecastProcessor` 한곳에만 둔다 — 흩어지면 같은 날짜를 화면마다
다른 예보로 답하게 된다.

**한쪽 실패가 다른 쪽을 막지 않는다.** 3일 밖 날짜를 묻는 사용자에게 단기예보 장애는
상관이 없고, 오늘 날씨를 묻는 사용자에게 중기예보 장애도 그렇다.

**중기예보의 함정 셋.** 예보구역 코드가 두 오퍼레이션에서 서로 다르고(육상은 도 단위,
기온은 지점 단위), 응답이 날짜별 행이 아니라 **한 행에 일차가 필드명으로** 박혀 오며
(`wf3Am`, `taMin3` … 8일차 이후는 오전/오후 구분 없음), 날씨가 코드가 아니라
"흐리고 비" 같은 **문장**이다. 셋 다 어댑터가 흡수한다.

일차는 **발표일 기준**이다. 18시 회차를 다음 날 새벽에 조회할 때 조회일에서 세면 하루가 밀린다.

## 3. 격자 — 이 연동의 첫 관문

기상청 API 는 **위경도를 받지 않는다.** 5km 격자 번호(`nx`, `ny`)만 받으므로 장소 좌표로
날씨를 조회하려면 반드시 DFS 격자 변환을 거쳐야 한다.

변환기는 `common-core` 의 `KmaGrid` 에 뒀다. `GeoDistance`(하버사인)를 한곳에 모은 이유와
같다 — tour-service 의 실시간 조회와 다른 곳의 사전 계산이 서로 다른 격자를 내면 캐시가
갈라지고 같은 장소에 다른 날씨가 붙는다.

**제주를 격자 하나로 볼 수 없다.** 문서에 적혀 있던 고정값(제주시 53/38)만 쓰면 성산일출봉
(60/37)의 날씨가 제주시 날씨로 바뀐다. `KmaGridTest` 가 이 두 점이 다른 격자임을 고정한다.

## 4. 캐시 — 성능이 아니라 쿼터 정책

공공 API 개발계정은 **일 1,000건 제한**이 있어 캐시 적중 여부가 기능의 가용성을 좌우한다.
그래서 캐시를 어댑터 안에 감추지 않고 `WeatherForecastCachePort` 로 꺼내 application 계층이
정책을 눈에 보이게 결정하도록 했다.

### 4-1. 키는 장소가 아니라 격자

```
{prefix}:insight:weather:forecast:{nx}:{ny}
```

장소 315곳이 서로 다른 좌표를 가져도 같은 격자에 모이면 원천 호출은 한 번이고,
그 한 번이 그 격자의 **5일치를 통째로** 준다. 장소별로 캐싱하면 이 계산이 무너진다.

실측 기준 쿼터 계산은 이렇다.

| 방식 | 키 개수 | 일 호출 (발표 8회) | 판정 |
|------|---------|--------------------|------|
| 장소별 캐싱 | 315 | 2,520 | 한도 초과 |
| 격자별 캐싱 | 94 (제주 육지) | **752** | 한도 내, 마진 25% |
| 격자 묶기(factor 2) | 약 25 | 약 200 | 여유. 단 정확도를 내준다 |

중기예보는 예보구역 단위라 제주 전체가 키 두 개로 덮이고 발표도 1일 2회뿐이다 — 하루 8건이
더해질 뿐이라 쿼터에 사실상 영향이 없다.

### 4-2. TTL 은 고정값이 아니라 다음 발표 시각

10분 TTL 을 걸면 발표 간격 3시간 동안 같은 데이터를 18번 다시 받아 쿼터만 태운다.
반대로 3시간 고정 TTL 은 발표 직후 갱신을 놓친다. 그래서 어댑터가 계산한
`nextPublishAt` 을 `WeatherObservationQueryResult` 에 실어 올리고, 캐시는 그 시각까지를
신선한 값으로 본다.

발표 주기를 아는 것은 기상청 프로토콜을 아는 어댑터의 책임이므로 계산은 그쪽에 남긴다.

다만 신선도 만료를 **발표 정각이 아니라 그보다 조금 뒤로** 잡는다 (`cache-grace-minutes`,
기본 30분 / 중기예보 60분). 이유가 두 개다.

- 정각에 만료시키면 그 순간 모든 격자가 동시에 낡아 호출이 한꺼번에 몰린다
- 발표 직후에는 일부 category 가 비어 오는 일이 실제로 있다 (§5) — 그때 부르면 어차피
  부실한 값을 받는다

즉 유예는 쿼터를 아끼면서 응답 품질도 같이 지킨다. 늘릴수록 최신성을 내주는 지렛대다.

### 4-3. 격자 묶기 — 기본은 끔

`grid-coarsen-factor` 로 인접 격자를 묶어 키를 줄일 수 있다 (`KmaGridPoint.coarsenedBy`).
factor 2 면 호출이 대략 1/4 로 준다.

**기본값을 1(끔)로 둔 이유는 제주 지형이다.** 한라산(해발 1,950m)과 해안은 기온이 10도 넘게
차이 나는데, 묶으면 그 둘이 한 격자로 뭉개진다. 반려견 기준 고온 판정이 이 서비스의 핵심이라
함부로 내줄 정확도가 아니다. 쿼터가 실제로 빠듯해졌을 때 켜는 지렛대로만 남긴다.

구현에서 조심할 점 하나 — **조회 격자와 캐시 키가 반드시 같은 값에서 나와야 한다.** 둘이
갈라지면 캐시에 넣은 것과 다른 격자를 조회하게 되어, 기능은 정상으로 보이는 채로 적중률만
0 에 가까워진다. 그래서 `WeatherForecastProcessor.gridAt` 한 곳에서만 만들고, 이 성질을
테스트로 고정해 두었다.

### 4-4. 갱신 락 — 캐시 스탬피드 방어

발표 시각이 지나 캐시가 한꺼번에 낡으면, 그 순간 들어온 요청이 모두 원천으로 몰린다.
dev/prod 는 인스턴스가 여러 대라 인스턴스 3대 × 격자 10개면 한 회차에 30건이 나갈 수 있는데
실제로 필요한 것은 10건이다. `ForecastRefreshLockPort` 가 이것을 막는다.

**Redlock 을 쓰지 않는다.** dev/prod 는 Sentinel 3노드 구성인데, Sentinel 은 여러 마스터에
분산하는 것이 아니라 마스터 하나를 감시하며 페일오버시키는 구조다. 쓰기는 항상 그 마스터
한 곳으로 가므로 단순 `SET NX PX` 로 충분하다. Redlock 은 서로 독립된 마스터가 여러 대일 때
필요한 알고리즘이다.

해제는 Lua 로 토큰 비교 후 삭제한다. GET 후 DEL 로 나누면 그 사이 TTL 이 만료되고 다른
요청이 키를 잡을 수 있어 **남의 락을 지우게 된다.**

락을 못 잡았을 때의 처리가 이 설계의 요점이다.

1. 낡은 캐시라도 있으면 그것을 준다 — 락 주인이 곧 새 값을 채우므로 낡음은 잠깐이다
2. 캐시가 아예 없으면(콜드 스타트) 1.5초까지 짧게 기다리며 캐시를 다시 본다
3. 그래도 없으면 **락 없이 원천을 부른다**

3번이 중요하다. **이 락은 정확성 장치가 아니라 절약 장치다** — 놓쳐도 답이 틀리지 않고 호출이
한 번 더 나갈 뿐이다. 그래서 페일오버 중 락이 유실되는 것도(비동기 복제라 미복제 쓰기가
사라진다) 감당할 수 있다. 중복 호출 한 건이 사용자에게 에러를 내는 것보다 싸다.

### 4-5. 폴백 순서

`external-api-guide.md` §2 의 순서를 `WeatherForecastProcessor` 가 그대로 구현한다.

1. 신선한 캐시가 있으면 그것
2. 없으면 원천 호출 → 성공하면 캐시에 넣고 반환
3. 원천이 실패했는데 **낡은 캐시라도 있으면 그것** (스테일 허용, 기본 6시간)
4. 아무것도 없으면 도메인 예외(503)

3번이 핵심이다. 기상청이 잠깐 흔들렸다고 장소 상세가 500 을 내면 안 된다.
세 시간 전 예보는 없는 것보다 훨씬 낫다.

Redis 장애도 예외로 올리지 않고 캐시 미스로 취급한다 — 락 어댑터도 같은 원칙으로, 실패를
"락을 못 잡음"과 같게 취급한다. 캐시는 쿼터를 아끼는 장치이지 데이터의 원천이 아니다.

## 5. 실측으로 확인한 원천의 함정

`KmaVillageForecastAdapter` 가 아래를 전부 흡수한다. 어느 하나도 adapter 밖으로 새지 않는다.

| 함정 | 증상 | 방어 |
|------|------|------|
| **category 별 1행** | 같은 시각의 기온/강수확률/하늘상태가 서로 다른 행에 흩어져 온다 | 시각 기준 피벗 → `WeatherForecast` |
| **PCP/SNO 는 문자열** | `강수없음`, `1mm 미만`, `30.0~50.0mm` 가 섞여 온다. `Double.parseDouble` 하면 터진다 | `PrecipitationAmount` 가 수치와 원문을 함께 보존 |
| **발표 회차 공백** | 회차 직후 몇 분은 데이터가 아직 없어 빈 응답이 온다 | `KmaBaseTime.previous()` 로 한 단계 물러서 재시도 |
| **키 오류는 XML** | serviceKey 문제일 때 JSON 이 아니라 `OpenAPI_ServiceResponse` XML | 파싱 전 형태 확인 |
| **resultCode 가 다르다** | 기상청은 `"00"`, 관광공사 계열은 `"0000"` | 둘 다 수용 |
| **items 가 빈 문자열** | 0건일 때 객체가 아니라 `""` | 세 형태(배열/객체/빈문자열) 모두 흡수 |
| **numOfRows 로 잘린다** | 한 회차가 1,000행을 넘는다. 잘려도 오류가 아니라 마지막 날이 반쪽으로 온다 | `numOfRows` 여유 + `totalCount` 비교 → 잘리면 마지막 날짜 폐기 |
| **23시 회차에는 오늘이 없다** | 발표일 행을 하나도 주지 않는다. 밤에 "오늘"을 물으면 예보가 비어 온다 | 정상 상태로 다룬다 — `ForecastCoverage.DAY_ENDED` (§5-2) |

### 5-0. numOfRows 잘림 — 조용히 틀리는 쪽

2026-08-28 실측에서 한 회차가 **1,052행**이었다(격자 53:38, 17시 회차). 회차마다 907~1,052행으로
갈리는데 `numOfRows=1000` 이면 **일부 회차만 잘린다.** 잘려도 `resultCode` 는 `00` 이다.

무엇이 틀리는지가 중요하다.

| | 온전한 응답 | `numOfRows=1000` 으로 잘린 응답 |
|---|---|---|
| 09-01 행 수 | 98 | 58 |
| 09-01 예보 시각 | 00시 ~ 21시 | 00시 ~ 12시 |
| TMX(일 최고기온) | **31.0** | 없음 |
| 접었을 때 최고기온 | 31.0 | **30.0** (12시까지의 최대 기온) |

고온 임계값이 **31.0도**라 이 1도가 판정을 정확히 가른다. 게다가 방향이 **"실제보다 안전하다"** 다 —
반려견 고온 위험을 다루는 기능에서 가장 나쁜 방향이다.

`DailyWeather.hasDaySummary` 도 이것을 막지 못한다. 시각이 5개고 12시 예보가 있으니 **온전해 보인다.**
그 가드는 "원천이 마지막 날을 적게 준다"를 막으려고 만든 것이지 "우리가 요청을 적게 했다"를
막지는 못한다.

그래서 두 겹으로 막는다.

1. `numOfRows` 기본값을 1,500 으로 올린다 (실측 최대 1,052 대비 여유)
2. `totalCount` 와 받은 행 수를 비교해 잘렸으면 **WARN 로그 + 마지막 날짜 폐기**

2번이 필요한 이유는 1번이 언젠가 또 부족해질 수 있어서다. 행이 `(fcstDate, fcstTime)` 오름차순으로
오는 것을 실측으로 확인했으므로 잘림은 항상 꼬리만 자르고, **반쪽이 되는 것은 마지막 날짜뿐**이다.
그 날짜를 버려도 커버리지는 비지 않는다 — 중기예보가 덮는다.

`PrecipitationAmount` 에서 **`1mm 미만`을 0 으로 두지 않는 것**이 특히 중요하다.
0 으로 두면 "비가 안 온다"는 뜻이 되어 버리고, 이는 파싱 실패보다 나쁜 버그다.
범위 표기(`30.0~50.0mm`)는 하한을 취하되 원문을 잃지 않는다.

### 5-1. 단기예보 마지막 날은 자정 한 시각뿐이다

실측한 날짜별 시각 수다 (`base_time=1400`).

| 8/27(오늘) | 8/28 | 8/29 | 8/30 | **8/31** |
|---:|---:|---:|---:|---:|
| 9 | 24 | 24 | 8 | **1** |

**이것이 조용한 버그를 만든다.** 8/31 을 하루로 접으면 최고기온이 자정 기온이 되어, 근거가
거의 없는데도 그럴듯한 점수가 나온다. 예외도 경고도 없다.

그래서 `DailyWeather.hasDaySummary` 로 온전함을 따진다. 기준은 **낮 데이터의 존재**다 —
최고기온은 오후에 나오므로 12시 이후 예보가 없으면 하루의 최고기온을 놓친다. 오늘은 예외로
남은 시각만 있어도 쓴다(지나간 시간이 없는 것이 정상이고, "남은 하루"는 그 자체로 답이 된다).

`TMN`/`TMX` 도 전체 798행 중 3행씩만 온다. 뒤쪽 날짜는 시각별 기온으로 최고/최저를 대신한다.

**11일보다 먼 날짜에는 예보가 없다.** 다음 달 여행을 계획하는 사용자에게는 근거가 없으며,
이것이 예외 상황이 아니라 **기본 경로**다. 그래서 판정 결과에 `INSUFFICIENT` 등급을 두었다 (§6-1).

### 5-2. 23시 회차부터 자정까지는 "오늘" 예보가 없다

실측이다 (격자 53:38, 2026-09-03).

| base_time | totalCount | 09/03 | 09/04 | 09/05 | 최초 예보 시각 |
|---|---:|---:|---:|---:|---|
| `2000` | 1,016 | 36 | 290 | 290 | 09/03 21:00 |
| **`2300`** | 980 | **0** | 290 | 290 | **09/04 00:00** |

각 회차의 예보는 발표시각 다음 시간부터 시작한다. 23시 회차의 다음 시간은 이미 다음 날이므로
**발표일 행이 0 건**이다. 즉 `publish-delay` 가 지난 23:10 무렵부터 자정까지, 오늘의 시각별
예보는 **원천에 존재하지 않는다.** 재시도해도 자정 전에는 채워지지 않는다.

이것이 조용히 사고를 만들었다. 골든타임(`/insights/walk-times`)이 "오늘 남은 예보 없음"을
`INSIGHT_003`(503)으로 올려 **밤 11시대에 화면이 사라졌다.** 좌표에 따라 갈리는 것처럼 보인 것도
같은 원인이다 — 23:10 전에 채워진 격자 캐시는 유예(기본 30분) 동안 오늘 행을 계속 들고 있고,
그 사이 캐시 미스가 난 격자만 23시 회차를 받아 비었다. **좌표축이 아니라 시각·캐시축이다.**

#### "예보가 없다"를 셋으로 가른다

`ForecastCoverage` 가 이 구분의 정본이고, 네 화면이 모두 이것을 쓴다.

| 값 | 뜻 | 상태 코드 | 사용자가 할 일 |
|---|---|---|---|
| `AVAILABLE` | 그 날짜 예보가 있다 | 200 | — |
| `DAY_ENDED` | 예보 시간대가 이미 지났다 | **200** | 내일을 본다. 자정이면 저절로 풀린다 |
| `OUT_OF_RANGE` | 예보가 아직 닿지 않는다 | 200 | 날짜가 가까워지면 다시 본다 |
| `UNAVAILABLE` | 목록 자체를 못 받았다 | 200 (`walk-times`·`walk-safety`·`suitability`) / 503 (`regional-weather` 전 권역 실패 시) | 다시 시도한다 |

**정상 상태를 5xx 로 올리지 않는다.** 재시도해도 풀리지 않는 것을 "잠시 후 다시 시도해
주세요"라고 말하면 클라이언트는 풀리지 않을 것을 계속 두드리고, 프론트는 조회 실패로 보고
섹션을 통째로 숨겨 사용자는 이유조차 알 수 없다. "예보를 못 받았다"는 것도 화면이 말할 수
있는 정보다.

**대신 설정 오류(`INSIGHT_004`)는 그대로 올린다.** serviceKey 가 없는 배포는 저절로 낫지
않는데, 200 뒤에 숨기면 "오늘은 예보가 없네"로 읽혀 며칠이고 발견되지 않는다. 그래서
`WeatherForecastProcessor` 의 원천 호출 폴백이 이 코드만 다시 던진다.

## 6. 판정 규칙

점수와 근거는 **LLM 이 아니라 규칙**에서 나온다. 같은 입력에 같은 점수가 나와야 하고,
근거는 실제 수치에서 조립되어야 한다 (`services/tour-service.md`).
ai-service 는 이 결과를 받아 문장을 다듬을 뿐이다.

### 6-1. 적합도 — 근거가 없으면 점수를 만들지 않는다

`SuitabilityScore.score` 는 Wrapper 이고, 날씨를 못 쓰면 **null** 이다. 등급은
`SuitabilityLevel.INSUFFICIENT` 가 된다.

근거 없는 0점이나 50점을 주면 사용자는 그것을 "여기는 별로다"로 읽는다.
**모르는 것과 나쁜 것은 다르고**, 그 구분을 값의 모양으로 강제한다.
동물병원 운영시간에 `operatingHoursKnown` 플래그를 둔 것과 같은 판단이다.

점수를 못 내도 `reasons` 는 비지 않는다. 동반 가능 여부처럼 날씨와 무관하게 아는 사실은
그대로 내려 주고, **왜 점수를 못 냈는지**도 근거로 남긴다. 이때 두 경우를 구분한다.

- `FORECAST_OUT_OF_RANGE` — 예보가 닿지 않는 날짜. 정상이고 기다릴 일이다
- `FORECAST_UNAVAILABLE` — 가져오지 못함. 장애이고 다시 시도할 일이다

감점 방식(100에서 빼기)을 쓰는 이유는 근거를 만들기 쉬워서다. "무엇 때문에 깎였는지"가
그대로 근거 목록이 된다. 가점 방식은 "왜 90점인가"에 답하기 어렵다.

실내 공간이 있으면 날씨 감점을 **절반으로** 줄이되 없애지는 않는다 — 오가는 길은 여전히 밖이다.

#### 고온 판정은 기온과 체감온도 중 큰 값에 건다 (#417)

입력은 **`max(최고기온, 하루 최고 체감온도)`** 하나이고, 임계는 **반려견 기준 28℃ / 31℃**다.
체감온도는 `DailyWeather.maxFeelsLikeTemperature()`(기상청 여름철 체감온도의 시각별 최대)다.

반려견은 헐떡임으로 체온을 내리므로 습도가 높으면 같은 기온도 더 위험하다. 기온만 보면 습한
30도와 건조한 30도의 점수가 같아진다 — 습도가 점수에 한 번도 반영되지 않던 자리였다 (#407).

| 같은 기온 30℃ | 체감 | 감점 |
| --- | --- | --- |
| 습도 40% | 28.5℃ | −15 (기온 규칙) |
| 습도 95% | 33.2℃ | **−30** (체감이 31 을 넘는다) |

**체감온도에 33/35 를 걸지 않는다.** 기상청 여름철 체감온도는 습구온도 기반이라 습도 100%
에서도 기온 대비 상승폭이 기온 30℃ 대에서 약 **+3.6℃** 다(기온 30℃·습도 100% → 33.6℃.
기온이 높을수록 조금 커져 35℃ 에서 +3.9℃). 체감에 33/35 를 걸면 체감이 33 을 넘는 시점의
기온은 이미 29.5 를 넘어 기온 감점이 늘 같고, 35 를 넘는 시점의 기온은 31 을 넘어 기온 감점이
이미 최대다 — 체감 규칙이 한 번도 이기지 못하는 **죽은 규칙**이 된다. 28/31 은 이 서비스가 반려견 기준으로 정한 더위
임계이고 체감온도는 반려견이 실제로 겪는 온도이므로, 그 임계를 체감온도에 거는 것이 일관된다.

산책 위험도(§6-2)가 33/35 를 쓰는 것과 어긋나는 것이 아니다. 그쪽은 **사용자가 아는 폭염특보
척도로 등급을 말하는 화면**이고 여기는 반려견 기준 척도로 점수를 매기는 곳이다 — 척도가 다르니
임계도 다르다.

큰 값 하나만 쓰므로 감점은 한 번이다 — 더하면 같은 더위를 두 번 세게 된다. 체감이 기온보다
높으면 근거 문장이 체감 기준(`"최고 체감온도 33도(기온 30도) 로 ..."`)이 되고, 아니면 기존
`"최고기온 …"` 그대로다. 근거 코드는 어느 쪽이든 `HEAT_RISK` 하나라 응답 스키마는 그대로다.

중기예보에는 시각별 습도가 없어 체감온도가 null 이다. 그때는 기온 규칙으로 **퇴화**한다 —
없는 습도를 평균으로 채워 체감을 지어내지 않는다.

### 6-2. 산책 위험도 — 노면과 호흡을 본다

점수를 내지 않고 등급만 낸다. "산책해도 되는가"는 정도의 문제가 아니라 임계를 넘었는지의
문제이고, 73점 같은 값은 판단에 도움이 되지 않는다.

**노면(아스팔트) 온도 추정 (`PavementHeat`)**

기상청은 노면온도를 주지 않는다. 기온에 일사로 인한 상승분을 더해 추정한다.

```
노면온도 = 기온 + 27도 x 일사계수 x 하늘상태계수 x 바람계수
  일사계수 : 그 날짜·시각·위도의 태양 고도 sin 값 / 기준값(0.9846 = 하지 정오 북위 33.5도).
             0~1 로 자른다. 시각은 열용량 지연 1시간만큼 되돌려 넣는다
  하늘상태 : 맑음 1.0 / 구름많음 0.6 / 흐림 0.3 / 정보없음 0.6 / 젖은 노면 0.1
  바람     : max(0.6, 1 - 0.03 x 풍속m/s). 풍속을 모르면 1.0 (보정하지 않는다)
```

상수 27은 "**한여름** 기온 25도 맑은 날 아스팔트 약 52도"라는 널리 인용되는 수치에 맞춘
값이다. **기준점이 한여름 정오라는 것이 이 설계의 요점이다** — 다른 계절/시각은 일사계수로
그보다 작아진다.

> **왜 바꿨나 (2026-09).** 이전 구현은 시각만 보는 고정표(`12~15시 1.0`)였다. 그래서 한여름
> 정오에 맞춘 `+27도`가 9월 15시에도, 12월 13시에도 그대로 붙었다 — 겨울 정오의 태양은
> 여름의 절반도 안 되는 고도인데 같은 값을 얹은 셈이다. dev 에서 기온 29도인 9월 오후에
> 노면 56도가 찍혀 사용자가 값을 의심했다. 계절이 빠진 것이 근본 원인이라 시각표를 걷어내고
> **태양 고도를 실제로 계산**한다.

**"노면은 14시가 가장 뜨겁다"의 몫은 두 번 세지 않는다.** 그 말의 대부분은 지연이 아니라
**기온 자체가 14~15시에 최고**라서다. 상승분은 기온 대비 초과분이므로 여기에 넣을 것이
아니고, 표면 열용량에서 오는 진짜 지연(약 1시간)만 반영한다. 절대 노면 정점은 `기온 곡선 +
상승분 곡선` 이 만든다.

한국 표준시 자오선(동경 135도)과 실제 경도의 남중 시각 차이(제주 약 34분)는 무시한다.
시간당 계수 차이보다 작아 등급을 바꾸지 않는다.

**추정 입력은 전부 같은 예보 행에서 뽑는다** (`WalkSafetyEvaluator.pavementOf`). 기온만 그
행에서 가져오고 시각은 기준 시각을 쓰면, `nearest` 가 최대 3시간 떨어진 행을 고르는 경우
기온과 일사가 어긋난 채 계산된다.

**이것은 추정치다.** 실측이 아니므로 응답 문구는 단정형을 피하고 위험 안내로 쓴다.
포장 재질, 색, 그늘 여부에 따라 실제 값은 더 달라진다. 응답 필드명도
`estimatedPavementCelsius` 로 추정임을 드러낸다.

**화면에는 기온과 나란히 둔다.** 노면온도만 표시하면 사용자는 그것을 기온으로 읽는다 —
실제로 그렇게 신고가 들어왔다. 그래서 `temperature`(기온)를 같은 응답에 함께 내리고,
Swagger 설명에 "나란히 보여 달라"를 못박아 뒀다. 문구도 "노면 온도"가 아니라
**"노면(아스팔트) 온도"** 로 통일한다 — 무엇의 온도인지가 이 서비스의 핵심 정보다.

**체감온도 (`FeelsLikeTemperature`)** — 판정·표시의 기준값. **기상청이 주는 값이 아니라 기상청
여름철 산식으로 우리가 계산한다** (단기예보에는 체감온도 카테고리가 없다). 기온과 상대습도로
습구온도(Stull, 2011 근사식)를 구해 산출하며, 폭염특보(주의보 33℃·경보 35℃)와 같은 척도라
기상청 앱의 값·특보 기준과 맞는다. 판정 임계도 이 특보 기준을 그대로 쓴다 — 임계의 출처가
우리 감이 아니라 기상청 공식 기준이다. 습도를 모르면 **보정하지 않는다** — 없는 값을 평균으로
채우면 없는 근거를 지어내는 것이 된다.

**열지수 (`HeatIndex`)** — 미국 NOAA Rothfusz 회귀식의 섭씨 계수판. **판정에는 쓰지 않는 참고
병기값**이다. 고온다습에서 기상청 체감온도보다 4~13℃ 높게 나와(예: 33℃/85% → 열지수 48 vs
체감온도 35.5) 사용자가 아는 기상청 값과 어긋났고, 그래서 판정 기준에서 내렸다. 응답에는
`heatIndexCelsius` + 계산 근거 문구(`heatIndexBasis`)로 남는다.

하루 단위로는 `DailyWeather.maxFeelsLikeTemperature()` 가 시각별 체감온도의 **최대**를 낸다 (#88).
"최고기온 + 최고습도" 로 한 번 계산하지 않는 이유는 둘이 같은 시각에 나오지 않기 때문이다 —
제주 여름은 기온이 내려가는 저녁에 습도가 올라 체감이 더 높은 시각이 따로 있다. 적합도 응답의
`weather.maxFeelsLikeTemperature` 로 나가고 plan-service 일정 브리핑이 그대로 전달한다. 중기예보는
시각별 데이터가 없어 null 이다.

**견종 (`BreedHeatRisk`)** — 사용자 자유 입력이라 표기가 제각각이고 못 잡는 경우가 반드시
생긴다. 그래서 판정 결과는 **가중치를 더하는 쪽으로만** 쓰고, 매칭 실패를 "안전하다"로
해석하지 않는다.

**중기예보로는 판정하지 않는다.** 노면온도를 `기온 + 일사(날짜·시각·위도) x 하늘상태 x 바람`
으로 추정하므로 시각별 데이터가 필요한데, 중기예보에는 오전/오후뿐이라 오후 두 시 아스팔트를 계산할 수 없다.
중기예보가 덮는 날짜는 `UNKNOWN` 을 유지한다 — 억지로 값을 내면 없는 근거를 지어내는 것이다.
누락이 아니라 의도한 경계이고, 사유 문구도 "시각별 예보 없음"으로 정확히 적는다.

**안전 시간대 (`saferWindow`)** — 이 응답의 실질적인 값어치다. "위험합니다"만 말하면 사용자는
할 수 있는 것이 없다. "지금은 위험하지만 18시 이후는 괜찮다"고 말해야 일정을 옮길 수 있다.
기준 시각 **이후**만 본다 — 이미 지나간 아침을 제안하는 것은 조언이 아니다.

### 6-3. 임계값은 프로퍼티로

`InsightProperties`(`insight.*`)로 뺐다. 이 숫자들은 확정된 사실이 아니라 **현재의 판단**이고,
반려견 기준 기온 임계값은 견종/체중/계절에 따라 논의가 갈린다. 조정할 때마다 배포하지
않아도 되게 둔다. 기본값은 통용 기준을 보수적으로 잡은 것이며 수의학적 확정치가 아니다.

### 6-4. 기상특보 — 정도의 문제가 아닌 것은 정도로 표현하지 않는다

특보는 다른 감점과 성질이 다르다. **경보는 점수를 0 으로 눌러 버린다.**

감점으로 다루면 다른 조건이 좋을 때 상쇄되어 태풍경보에 "여행 적합 82점"이 나간다.
경보는 기상청이 "나가지 말라"고 말하는 단계라 정도의 문제가 아니고, 그러므로 정도로
표현하지 않는다.

등급을 `INSUFFICIENT` 로 두지 않은 것은 의도한 선택이다. 그것은 "판단 근거가 없다"는 뜻인데
지금은 근거가 **있고**, 그 근거가 나쁘다고 말하고 있다. 모르는 것과 나쁜 것을 구분하는 것이
이 서비스의 규칙이라 여기서도 지킨다 — 점수 0, 등급 `LOW` 다.

| 단계 | 적합도 | 산책 위험도 |
|------|--------|-------------|
| 경보 | 점수 0, 등급 LOW | DANGER. **예보보다 먼저 본다** — 시각별 예보가 없어도 UNKNOWN 이 아니다. **saferWindow 도 주지 않는다** — 곡선에 안전 구간이 있어도 골든타임(`SUPPRESSED_BY_WARNING`)과 같은 축으로 억제한다 (#357) |
| 주의보 | 감점 45 | 최소 CAUTION. 노면·체감온도가 좋아도 "안전"을 단언하지 않는다. saferWindow·골든타임 추천은 막지 않는다 |

"경보인가"의 판정은 `WeatherWarning.suppressesRecommendation` **한 곳**이다. 적합도·산책
위험도·골든타임·권역 추천이 모두 이 메서드를 쓴다 — 호출부마다 조건을 세우면 한쪽만 고쳐져
같은 특보에 "추천하지 않는다"와 시간대 제시가 한 화면에 함께 서는 모순이 생긴다 (#357).

여러 특보가 동시에 뜨면(태풍 + 호우 + 강풍) **가장 무거운 것**으로 판정한다.
단계를 먼저 보고, 같으면 종류 선언 순서를 쓴다 — 그 순서가 곧 심각도다.

**못 알아본 문구는 "특보 없음"이 아니라 `OTHER` 다.** 표기가 바뀌었을 뿐인데 태풍을 놓치는
것이 이 기능의 최악이라, 모르는 쪽을 안전한 쪽으로 접지 않는다.

#### 원천에서 밟은 두 함정 (2026-09-01 실호출)

| 함정 | 증상 | 방어 |
|------|------|------|
| **오퍼레이션을 잘못 고르기 쉽다** | `getWthrWrnList` 는 통보문 이력이라 `"호우주의보 해제"` 도 한 행으로 온다. 발효 중으로 읽으면 이미 풀린 경보로 일정을 취소시킨다 | 현황은 `getPwnStatus` 의 `t6` 다 |
| **`stnId` 가 필터하지 않는다** | 제주(184)와 서울(108)에 같은 전국 문구가 온다. 그대로 읽으면 전라남도 폭염주의보가 제주 특보가 된다 | 특보마다 붙은 지역 목록에서 제주를 직접 확인한다 |

둘 다 **오류가 나지 않고 그럴듯한 값이 나오는** 형태다. 실호출로 확인하지 않았으면 배포 후에도
한동안 몰랐을 종류의 실수라, 그때 받은 응답을 픽스처로 박아 테스트에 고정했다
(`WeatherWarningStatusTextTest`).

실측에서 **열대야주의보**가 나왔다. 밤에도 기온이 안 내려가 "저녁에 나가면 된다"는 회피
수단 자체가 막히는 특보라, 반려견 기준으로는 폭염 못지않다.

## 7. 제주 권역 비교 — 이 섬에서만 성립하는 질문

제주는 가로 70km 남짓인데 해발 1,950m 산이 한가운데 있다. 같은 시각에 북부는 비가 오고
남부는 개어 있는 일이 흔하다. "제주 날씨"를 한 값으로 말하면 그 차이가 통째로 사라진다.

권역은 다섯이다.

| 권역 | 대표 좌표 | 격자 | 근거 |
|------|-----------|------|------|
| 제주시권 | 33.4996, 126.5312 | (53, 38) | 행정 경계 + 중기예보 기온 지점 |
| 서귀포권 | 33.2541, 126.5600 | (53, 33) | 한라산 남쪽. 실측에서 북부와 최고기온 1도 차 |
| 동부권 | 33.4586, 126.9420 | (60, 37) | 격자가 다르고 바람이 가장 세다 |
| 서부권 | 33.3940, 126.2400 | (47, 36) | 격자가 다르다 |
| 한라산권 | 33.3617, 126.4930 | (52, 35) | 해발이 달라 해안과 기온이 크게 벌어진다 |

**대표 격자 하나씩만 본다.** 권역 안을 여러 격자로 훑으면 정확해지지만 호출이 권역 수의 몇
배가 된다. 이 기능이 답하려는 것은 "어디가 더 나은가"이지 "정확히 몇 도인가"가 아니다.
`WeatherForecastProcessor` 를 그대로 쓰므로 기존 격자 캐시에 얹히고, 그 격자에 장소가 있어
이미 받아 둔 예보면 **호출이 0** 이다.

### 다섯을 병렬로 본다

캐시가 다 비어 있으면 순차 조회는 권역당 원천 왕복이 그대로 쌓인다. 어댑터가 빈 응답에 직전
회차로 한 번 더 시도하므로 **권역당 최악 두 번**이고, 다섯이면 응답이 수십 초까지 늘어진다.
발표 직후나 배포 직후에 첫 요청자가 그것을 다 뒤집어쓴다.

`insightRegionalTaskExecutor`(전용 풀, 크기 = 권역 수)로 함께 조회한다.
`parallelStream()` 을 쓰지 않는 이유는 그것이 공용 ForkJoinPool 이기 때문이다 —
여기서 하는 일은 블로킹 HTTP 호출이라 JVM 전체가 공유하는 자원을 오래 잡으면 안 된다.

동시 요청은 **큐로 받는다.** 최대 풀을 키워 요청 수만큼 스레드를 늘리면 기상청으로 나가는
동시 호출이 그만큼 늘어난다 — 쿼터가 일 1,000건인 원천에 그렇게 몰아치면 안 된다.

병렬화로 잃기 쉬운 둘을 테스트로 지킨다(`RegionalWeatherProcessorTest`).

- **순서** — 완료 순서로 모으면 비교표 줄 순서가 매번 달라진다. 사용자가 같은 화면을 두 번
  볼 때 다른 것으로 읽고, 동점 추천의 타이브레이크도 흔들린다. 그래서 권역 선언 순서로 모은다
- **실패 격리** — 한 권역이 실패해도 나머지로 답한다

대표 좌표가 서로 다른 격자에 떨어지는 것을 테스트로 고정했다(`JejuRegionTest`).
겹치면 비교표가 같은 날씨를 두 줄로 보여 주는데, 오류가 나지 않고 그럴듯해 보여 눈으로는
잡히지 않는다.

판정은 `SuitabilityEvaluator.applyWeatherRules` 를 재사용한다. 복사했다면 임계값이 바뀔 때
한쪽만 고쳐져 같은 날씨를 화면마다 다르게 판정하게 된다. 권역 비교는 "밖에 나가기"를
전제하므로 실내 대피처 없음 / 바람 그대로 맞음으로 넣는다.

권역 항목의 수치는 최저·최고기온에 더해 **하루 최고 체감온도**(`maxFeelsLikeTemperature`)를
싣는다. 값은 장소 상세의 `weather.maxFeelsLikeTemperature` 와 같은 규칙 —
`DailyWeather.maxFeelsLikeTemperature()`(기상청 여름철 체감온도의 시각별 최대) — 이다.
홈 카드와 장소 상세가 같은 척도의 숫자를 말해야 사용자가 두 화면을 오가며 비교할 수 있다.
예보를 못 받은 권역은 세 값 모두 null 이다 — 0 이나 최고기온으로 지어내지 않는다
(`RegionalWeatherPresenterTest`).

권역 점수도 같은 고온 규칙(§6-1)을 타므로 **습한 권역은 `weatherScore` 가 내려간다** — 표에
실린 체감온도와 점수가 서로 다른 근거를 말하지 않는다 (#417).

## 8. 산책 골든타임 — saferWindow 와 무엇이 다른가

둘 다 "언제가 나은가"를 다루지만 고르는 기준이 반대다.

| | saferWindow (장소 산책 위험도) | 골든타임 (`/walk-times`) |
|---|---|---|
| 질문 | "지금 위험한데 언제 나가지" | "오늘 언제가 제일 낫지" |
| 고르는 것 | **가장 이른** 괜찮은 구간 | **가장 좋은** 구간 (등급 → 길이 → 이른 시각) |
| 조건 | 지금이 안전하면 주지 않는다 | 항상 곡선을 준다 |

판정은 같은 간이 판정(`WalkSafetyEvaluator.hourlyCurve` → `quickLevel`)을 쓴다.
따로 계산하면 같은 시각을 한쪽은 주의로, 다른 쪽은 안전으로 말하게 된다.

**추천할 게 없으면 추천하지 않는다.** 아무 구간이나 골라 "그나마 이때"를 주면 사용자는
그것을 허락으로 읽는다.

### 8-1. 추천이 없는 이유는 셋이다 — `GoldenWindowStatus`

`goldenStart: null` 하나로 뭉개면 화면이 이유를 고를 수 없고, 결국 셋 중 하나의 문구를
나머지 둘에도 쓰게 된다. **실제로 그렇게 틀렸다** — 풍랑경보가 발효된 날, 곡선에는 저녁
안전 구간이 초록으로 그려져 있는데 화면은 "남은 시간이 모두 위험 등급이에요"라고 단정했다.
곡선과 문장이 서로 다른 말을 하면 사용자는 둘 다 믿지 않는다.

| 값 | 뜻 | 화면이 할 말 |
|---|---|---|
| `AVAILABLE` | 추천 구간이 있다 | 구간을 보여 준다 |
| `SUPPRESSED_BY_WARNING` | 경보라 보류했다. **곡선에 안전 시각이 남아 있어도 이 값이다** | "경보가 발효 중이라 추천하지 않아요" |
| `ALL_HOURS_RISKY` | 남은 시각이 전부 위험이다 | "오늘은 나가지 않는 편이 좋아요" — **이 값일 때만 참인 문장** |
| `NO_FORECAST` | 판정할 예보가 없다 | 위험 톤을 쓰지 않는다. 모르는 것은 모르는 것이다 |

가르는 순서가 곧 규칙이라 `GoldenWindowStatus.of` 한 곳에 둔다 — 예보 없음이 먼저,
그다음이 경보, 마지막이 곡선 판정이다. 호출부마다 `if` 를 세우면 한쪽만 고쳐져 같은 상태에
다른 문구가 나간다.

`ForecastCoverage` 와 겹치지 않는다. 그쪽은 "곡선이 왜 비었나"(장애냐 정상이냐)를 답하고,
이쪽은 "추천을 왜 안 했나"를 답한다.

## 9. 반려견 조건을 어떻게 받는가

**tour-service 는 반려견 프로필의 사본을 갖지 않는다.** 요청 파라미터로 받는다.

- tour-service 는 인증이 없는 공개 조회 서비스다 (`service-inventory.md`)
- 프로필의 원천은 auth-service 이고, 사본을 두면 사용자가 프로필을 고쳐도 옛 값으로 판정한다
- 비회원도 장소를 볼 수 있어야 하고, 같은 장소를 여러 아이 기준으로 비교해 보는 것이
  이 기능의 자연스러운 쓰임이다

일정 브리핑(plan-service)은 회원 컨텍스트가 있으므로 auth-service 내부 API
(`GET /internal/v1/pets/{petId}/condition`)로 특성을 받아 tour-service 에 파라미터로 넘긴다.
그 내부 API 는 이름과 생년월을 내보내지 않는다 — 판정에 필요 없고, 서비스 경계를 넘는
개인정보는 최소로 유지한다.

## 10. 혼잡도 — 명칭 기반 매칭

혼잡 HIGH 감점 위에 반려견 특성 감점이 얹힌다 — 소음 민감(소리가 부담)과 사회성 낮음(다른
개·낯선 사람과의 대면이 부담)은 **이유가 다른 별개 감점**이라 둘 다면 함께 깎인다 (#425).
"언제 덜 붐비나"의 답은 `CongestionSnapshot.leastCrowded` 한 곳이 고른다 — UNKNOWN 은 후보가
아니고(데이터 없음은 한산함이 아니다), 동률이면 가장 이른 날짜다.

집중률 API 는 `contentId` 가 아니라 관광지 **이름**으로 데이터를 준다. 이름은 원천마다
표기가 달라 그대로 비교하면 상당수가 유실되므로 `place_name_link` 를 거쳐 잇는다.

- 정규화/부분일치 판정은 장소 병합에 쓰던 `PlaceNameMatcher` 를 **재사용**한다.
  같은 문제에 다른 규칙을 쓰면 "같은 곳"의 뜻이 두 곳에서 갈라진다
- 좌표로 보정하지 않는다 — **이 원천에 좌표가 없다.** 그래서 완전일치를 우선하고,
  부분일치는 후보가 **정확히 하나일 때만** 받는다. 여럿이면 UNMATCHED 로 남긴다.
  잘못 이은 혼잡도는 없는 혼잡도보다 나쁘다
- `place_name_link.place_id` 는 **nullable** 이고 매칭 실패 행도 저장한다. 실패를 행 없이
  버리면 커버리지가 얼마인지 아무도 모르게 되고, 수동 보정 대상 목록도 사라진다
- 매칭률은 배치 로그로 남긴다. 커버리지가 조용히 떨어지는 것이 이 방식의 가장 큰 위험이다

조회 시 매칭이 없으면 `CongestionLevel.UNKNOWN` 이다. 매칭 실패를 "한산함"으로 바꿔치기하지 않는다.

## 11. 매핑 계층

`insight` 는 저장소 규약(coding-conventions §4, §12-2)을 그대로 따른다.

```
PlaceEntity ──(InsightMapper, MapStruct)──▶ PlaceCondition ──(Processor)──▶ PlaceSuitabilityInfo
                                                                                    │
                                                                     (Presenter)────┘
                                                                                    ▼
                                                                      PlaceSuitabilityResponse
```

| 구간 | 담당 | 이유 |
| --- | --- | --- |
| Entity → Domain | `InsightMapper` (MapStruct) | 손으로 옮겨 적는 코드는 컬럼이 늘 때 빠뜨린다 |
| Domain → Info | Processor | 판정에 필요한 조합은 애플리케이션 로직이다 |
| Info → Response/Item | Presenter | 응답 모양은 Presenter 에서 마무리한다 |

**포트가 `QueryResult` 대신 domain model 을 반환하는 경우가 있다.** `PlaceProfileQueryPort` 가
그렇다 — 필요한 모양(좌표 + 동반 조건 + 실내외)이 그대로 판정 입력이라 중간 타입을 한 겹 더
둘 이유가 없었다. 반대로 `WeatherObservationQueryResult` / `CachedWeatherQueryResult` 는
domain model 에 **메타데이터**(다음 발표 시각, 신선도)를 얹어야 해서 `QueryResult` 로 둔다.
기준은 "포트가 값 말고 더 할 말이 있는가"다.

`InsightMapper` 는 프로퍼티 → 도메인 임계값 변환(`toThresholds`)도 맡는다. 필드명이 그대로
대응하므로 손으로 옮길 이유가 없고, 임계값이 하나 늘 때 옮겨 적는 코드를 고치는 것이
빠뜨리기 쉬운 자리이기 때문이다.
