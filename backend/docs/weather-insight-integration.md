# 날씨 기반 인사이트 통합 설계

> 기상청 단기예보를 붙여 여행 적합도와 산책 위험도를 산출하는 구조를 정리한 문서다.
> 원천 실측 근거는 `data-api-analysis.md` §6-1, 엔티티는 `entity-design.md` §10, §7 참고.

## 1. 왜 이 기능인가

관광 데이터를 예쁘게 보여 주는 서비스는 이미 많다. 반려견 여행 서비스가 다른 지점은
**같은 날씨를 사람이 아니라 반려견 기준으로 읽는 것**이다.

- 기온 25도 맑은 한낮은 사람에게 산책하기 좋은 날이지만, 아스팔트 표면은 50도를 넘어
  발바닥 화상 구간에 들어간다
- 반려견은 땀이 아니라 헐떡임으로 체온을 내리므로 습도가 높으면 같은 기온이 훨씬 위험하다
- 단두종(불독/퍼그/시츄)은 기도가 짧아 같은 더위에서 먼저 위험해진다

이 셋은 기온만 보는 판정으로는 전부 보이지 않는다. 그래서 적합도(`suitability`)와
산책 위험도(`walk-safety`)를 **일부러 나눴다** — 적합도는 "여기 갈 만한가", 위험도는
"지금 걸어도 되는가"를 묻는다. 하나로 합치면 둘 중 하나가 반드시 희석된다.

## 2. 데이터 원천

| 원천 | 오퍼레이션 | 방식 | 커버리지 |
|------|-----------|------|---------|
| 기상청 단기예보 `VilageFcstInfoService_2.0` | `getVilageFcst` | 실시간 + Redis 캐시 | 오늘 포함 **약 3일** |
| 관광지 집중률 `TatsCnctrRateService` | `tatsCnctrRatedList` | 배치 적재 + DB 조회 | **30일 rolling** |

**두 원천의 커버리지가 다르다는 점이 응답 설계를 갈랐다.** 날씨는 없고 혼잡도만 있는 날짜가
흔하다. 그래서 적합도 응답은 `weatherApplied` / `congestionApplied` 플래그를 따로 내려
어떤 근거가 실제로 쓰였는지 드러낸다. 없는 근거를 0으로 채워 점수에 섞지 않는다.

## 3. 격자 — 이 연동의 첫 관문

기상청 API 는 **위경도를 받지 않는다.** 5km 격자 번호(`nx`, `ny`)만 받으므로 장소 좌표로
날씨를 조회하려면 반드시 DFS 격자 변환을 거쳐야 한다.

변환기는 `common-core` 의 `KmaGrid` 에 뒀다. `GeoDistance`(하버사인)를 한곳에 모은 이유와
같다 — tour-service 의 실시간 조회와 다른 곳의 사전 계산이 서로 다른 격자를 내면 캐시가
갈라지고 같은 장소에 다른 날씨가 붙는다.

**제주를 격자 하나로 볼 수 없다.** 문서에 적혀 있던 고정값(제주시 53/38)만 쓰면 성산일출봉
(60/37)의 날씨가 제주시 날씨로 바뀐다. `KmaGridTest` 가 이 두 점이 다른 격자임을 고정한다.

## 4. 캐시 — 성능이 아니라 쿼터 정책

공공 API 개발계정은 **일 1,000건 제한**이 있어 캐시 적중 여부가 기능의 가용성을 좌우한다.
그래서 캐시를 어댑터 안에 감추지 않고 `WeatherForecastCachePort` 로 꺼내 application 계층이
정책을 눈에 보이게 결정하도록 했다.

### 4-1. 키는 장소가 아니라 격자

```
{prefix}:insight:weather:forecast:{nx}:{ny}
```

장소 315곳이 서로 다른 좌표를 가져도 같은 격자에 모이면 원천 호출은 한 번이고,
그 한 번이 그 격자의 **3일치를 통째로** 준다. 장소별로 캐싱하면 이 계산이 무너진다.

### 4-2. TTL 은 고정값이 아니라 다음 발표 시각

10분 TTL 을 걸면 발표 간격 3시간 동안 같은 데이터를 18번 다시 받아 쿼터만 태운다.
반대로 3시간 고정 TTL 은 발표 직후 갱신을 놓친다. 그래서 어댑터가 계산한
`nextPublishAt` 을 `WeatherObservationQueryResult` 에 실어 올리고, 캐시는 그 시각까지를
신선한 값으로 본다.

발표 주기를 아는 것은 기상청 프로토콜을 아는 어댑터의 책임이므로 계산은 그쪽에 남긴다.

### 4-3. 폴백 순서

`external-api-guide.md` §2 의 순서를 `WeatherForecastProcessor` 가 그대로 구현한다.

1. 신선한 캐시가 있으면 그것
2. 없으면 원천 호출 → 성공하면 캐시에 넣고 반환
3. 원천이 실패했는데 **낡은 캐시라도 있으면 그것** (스테일 허용, 기본 6시간)
4. 아무것도 없으면 도메인 예외(503)

3번이 핵심이다. 기상청이 잠깐 흔들렸다고 장소 상세가 500 을 내면 안 된다.
세 시간 전 예보는 없는 것보다 훨씬 낫다.

Redis 장애도 예외로 올리지 않고 캐시 미스로 취급한다. 캐시는 쿼터를 아끼는 장치이지
데이터의 원천이 아니다.

## 5. 실측으로 확인한 원천의 함정

`KmaVillageForecastAdapter` 가 아래를 전부 흡수한다. 어느 하나도 adapter 밖으로 새지 않는다.

| 함정 | 증상 | 방어 |
|------|------|------|
| **category 별 1행** | 같은 시각의 기온/강수확률/하늘상태가 서로 다른 행에 흩어져 온다 | 시각 기준 피벗 → `WeatherForecast` |
| **PCP/SNO 는 문자열** | `강수없음`, `1mm 미만`, `30.0~50.0mm` 가 섞여 온다. `Double.parseDouble` 하면 터진다 | `PrecipitationAmount` 가 수치와 원문을 함께 보존 |
| **발표 회차 공백** | 회차 직후 몇 분은 데이터가 아직 없어 빈 응답이 온다 | `KmaBaseTime.previous()` 로 한 단계 물러서 재시도 |
| **키 오류는 XML** | serviceKey 문제일 때 JSON 이 아니라 `OpenAPI_ServiceResponse` XML | 파싱 전 형태 확인 |
| **resultCode 가 다르다** | 기상청은 `"00"`, 관광공사 계열은 `"0000"` | 둘 다 수용 |
| **items 가 빈 문자열** | 0건일 때 객체가 아니라 `""` | 세 형태(배열/객체/빈문자열) 모두 흡수 |

`PrecipitationAmount` 에서 **`1mm 미만`을 0 으로 두지 않는 것**이 특히 중요하다.
0 으로 두면 "비가 안 온다"는 뜻이 되어 버리고, 이는 파싱 실패보다 나쁜 버그다.
범위 표기(`30.0~50.0mm`)는 하한을 취하되 원문을 잃지 않는다.

**단기예보는 약 3일까지다.** 다음 달 여행을 계획하는 사용자에게는 예보가 아예 없으며,
이것이 예외 상황이 아니라 **기본 경로**다. 그래서 판정 결과에 `INSUFFICIENT` 등급을 두었다
(§6-1). 중기예보(`MidFcstInfoService`, 3~10일)는 아직 붙이지 않았다 — `§10 남은 일` 참고.

## 6. 판정 규칙

점수와 근거는 **LLM 이 아니라 규칙**에서 나온다. 같은 입력에 같은 점수가 나와야 하고,
근거는 실제 수치에서 조립되어야 한다 (`services/tour-service.md`).
ai-service 는 이 결과를 받아 문장을 다듬을 뿐이다.

### 6-1. 적합도 — 근거가 없으면 점수를 만들지 않는다

`SuitabilityScore.score` 는 Wrapper 이고, 날씨를 못 쓰면 **null** 이다. 등급은
`SuitabilityLevel.INSUFFICIENT` 가 된다.

근거 없는 0점이나 50점을 주면 사용자는 그것을 "여기는 별로다"로 읽는다.
**모르는 것과 나쁜 것은 다르고**, 그 구분을 값의 모양으로 강제한다.
동물병원 운영시간에 `operatingHoursKnown` 플래그를 둔 것과 같은 판단이다.

점수를 못 내도 `reasons` 는 비지 않는다. 동반 가능 여부처럼 날씨와 무관하게 아는 사실은
그대로 내려 주고, **왜 점수를 못 냈는지**도 근거로 남긴다. 이때 두 경우를 구분한다.

- `FORECAST_OUT_OF_RANGE` — 예보가 닿지 않는 날짜. 정상이고 기다릴 일이다
- `FORECAST_UNAVAILABLE` — 가져오지 못함. 장애이고 다시 시도할 일이다

감점 방식(100에서 빼기)을 쓰는 이유는 근거를 만들기 쉬워서다. "무엇 때문에 깎였는지"가
그대로 근거 목록이 된다. 가점 방식은 "왜 90점인가"에 답하기 어렵다.

실내 공간이 있으면 날씨 감점을 **절반으로** 줄이되 없애지는 않는다 — 오가는 길은 여전히 밖이다.

### 6-2. 산책 위험도 — 노면과 호흡을 본다

점수를 내지 않고 등급만 낸다. "산책해도 되는가"는 정도의 문제가 아니라 임계를 넘었는지의
문제이고, 73점 같은 값은 판단에 도움이 되지 않는다.

**노면온도 추정 (`PavementHeat`)**

기상청은 노면온도를 주지 않는다. 기온에 일사로 인한 상승분을 더해 추정한다.

```
표면온도 = 기온 + 27도 x 하늘상태계수 x 시간대계수
  하늘상태: 맑음 1.0 / 구름많음 0.6 / 흐림 0.3 / 정보없음 0.6 / 젖은 노면 0.1
  시간대  : 12~15시 1.0 / 11,16시 0.85 / 10,17시 0.6 / 9,18시 0.35 / 7,8,19시 0.15 / 그 외 0
```

상수 27은 "기온 25도 맑은 날 아스팔트 약 52도"라는 널리 인용되는 수치에 맞춘 값이다.
지면은 기온보다 늦게 달아오르므로 정오가 아니라 **14시 전후**에 무게를 뒀다.

**이것은 추정치다.** 실측이 아니므로 응답 문구는 단정형을 피하고 위험 안내로 쓴다.
포장 재질, 색, 그늘 여부에 따라 실제 값은 더 달라진다. 응답 필드명도
`estimatedPavementCelsius` 로 추정임을 드러낸다.

**열지수 (`HeatIndex`)** — Rothfusz 회귀식의 섭씨 계수판. 습도를 모르면 **보정하지 않는다**.
없는 값을 평균으로 채우면 없는 근거를 지어내는 것이 된다.

**견종 (`BreedHeatRisk`)** — 사용자 자유 입력이라 표기가 제각각이고 못 잡는 경우가 반드시
생긴다. 그래서 판정 결과는 **가중치를 더하는 쪽으로만** 쓰고, 매칭 실패를 "안전하다"로
해석하지 않는다.

**안전 시간대 (`saferWindow`)** — 이 응답의 실질적인 값어치다. "위험합니다"만 말하면 사용자는
할 수 있는 것이 없다. "지금은 위험하지만 18시 이후는 괜찮다"고 말해야 일정을 옮길 수 있다.
기준 시각 **이후**만 본다 — 이미 지나간 아침을 제안하는 것은 조언이 아니다.

### 6-3. 임계값은 프로퍼티로

`InsightProperties`(`insight.*`)로 뺐다. 이 숫자들은 확정된 사실이 아니라 **현재의 판단**이고,
반려견 기준 기온 임계값은 견종/체중/계절에 따라 논의가 갈린다. 조정할 때마다 배포하지
않아도 되게 둔다. 기본값은 통용 기준을 보수적으로 잡은 것이며 수의학적 확정치가 아니다.

## 7. 반려견 조건을 어떻게 받는가

**tour-service 는 반려견 프로필의 사본을 갖지 않는다.** 요청 파라미터로 받는다.

- tour-service 는 인증이 없는 공개 조회 서비스다 (`service-inventory.md`)
- 프로필의 원천은 auth-service 이고, 사본을 두면 사용자가 프로필을 고쳐도 옛 값으로 판정한다
- 비회원도 장소를 볼 수 있어야 하고, 같은 장소를 여러 아이 기준으로 비교해 보는 것이
  이 기능의 자연스러운 쓰임이다

일정 브리핑(plan-service)은 회원 컨텍스트가 있으므로 auth-service 내부 API
(`GET /internal/v1/pets/{petId}/condition`)로 특성을 받아 tour-service 에 파라미터로 넘긴다.
그 내부 API 는 이름과 생년월을 내보내지 않는다 — 판정에 필요 없고, 서비스 경계를 넘는
개인정보는 최소로 유지한다.

## 8. 혼잡도 — 명칭 기반 매칭

집중률 API 는 `contentId` 가 아니라 관광지 **이름**으로 데이터를 준다. 이름은 원천마다
표기가 달라 그대로 비교하면 상당수가 유실되므로 `place_name_link` 를 거쳐 잇는다.

- 정규화/부분일치 판정은 장소 병합에 쓰던 `PlaceNameMatcher` 를 **재사용**한다.
  같은 문제에 다른 규칙을 쓰면 "같은 곳"의 뜻이 두 곳에서 갈라진다
- 좌표로 보정하지 않는다 — **이 원천에 좌표가 없다.** 그래서 완전일치를 우선하고,
  부분일치는 후보가 **정확히 하나일 때만** 받는다. 여럿이면 UNMATCHED 로 남긴다.
  잘못 이은 혼잡도는 없는 혼잡도보다 나쁘다
- `place_name_link.place_id` 는 **nullable** 이고 매칭 실패 행도 저장한다. 실패를 행 없이
  버리면 커버리지가 얼마인지 아무도 모르게 되고, 수동 보정 대상 목록도 사라진다
- 매칭률은 배치 로그로 남긴다. 커버리지가 조용히 떨어지는 것이 이 방식의 가장 큰 위험이다

조회 시 매칭이 없으면 `CongestionLevel.UNKNOWN` 이다. 매칭 실패를 "한산함"으로 바꿔치기하지 않는다.

## 9. 매핑 계층

`insight` 는 저장소 규약(coding-conventions §4, §12-2)을 그대로 따른다.

```
PlaceEntity ──(InsightMapper, MapStruct)──▶ PlaceCondition ──(Processor)──▶ PlaceSuitabilityInfo
                                                                                    │
                                                                     (Presenter)────┘
                                                                                    ▼
                                                                      PlaceSuitabilityResponse
```

| 구간 | 담당 | 이유 |
| --- | --- | --- |
| Entity → Domain | `InsightMapper` (MapStruct) | 손으로 옮겨 적는 코드는 컬럼이 늘 때 빠뜨린다 |
| Domain → Info | Processor | 판정에 필요한 조합은 애플리케이션 로직이다 |
| Info → Response/Item | Presenter | 응답 모양은 Presenter 에서 마무리한다 |

**포트가 `QueryResult` 대신 domain model 을 반환하는 경우가 있다.** `PlaceProfileQueryPort` 가
그렇다 — 필요한 모양(좌표 + 동반 조건 + 실내외)이 그대로 판정 입력이라 중간 타입을 한 겹 더
둘 이유가 없었다. 반대로 `WeatherObservationQueryResult` / `CachedWeatherQueryResult` 는
domain model 에 **메타데이터**(다음 발표 시각, 신선도)를 얹어야 해서 `QueryResult` 로 둔다.
기준은 "포트가 값 말고 더 할 말이 있는가"다.

`InsightMapper` 는 프로퍼티 → 도메인 임계값 변환(`toThresholds`)도 맡는다. 필드명이 그대로
대응하므로 손으로 옮길 이유가 없고, 임계값이 하나 늘 때 옮겨 적는 코드를 고치는 것이
빠뜨리기 쉬운 자리이기 때문이다.
