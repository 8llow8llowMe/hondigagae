# AI Service

## 책임

LLM 기반 AI 기능 전담. 선정된 AI 기능의 LLM 호출·프롬프트·결과 조립을 소유한다.

> **기능 선정 전 단계.** 아래 표는 AI 기능 후보 10종 전체의 배치안이다.
> 실제 구현 대상은 루트 `README.md`의 후보 풀에서 의사결정으로 선정된 기능만이며,
> 선정이 확정되면 이 문서를 선정 기능 중심으로 갱신한다.

| 후보 기능 | 컨텍스트 | 방식 |
|------|----------|------|
| AI 여행 플래너 (일정 생성) | `planner` | 비동기 job |
| 일정 수정 AI (자연어 수정) | `planner` | 비동기 job 또는 동기 |
| AI 여행 상담사 / 여행 비서 | `assistant` | 대화 세션 + SSE |
| 여행 적합도 해설 | `analysis` | 동기 (tour-service 점수 기반 해설) |
| 반려견 성향 분석 | `analysis` | 배치성 분석 + 조회 |
| 여행 스타일 학습 (사용자) | `analysis` | 배치성 분석 + 조회 |
| 여행 후기 자동 작성 | `analysis` | 비동기 job |
| XAI 추천 이유 | 공통 | 모든 추천 응답에 `reasons` 포함 |

## 주요 API (후보 기능 전체 기준 초안)

> 선정에서 제외된 기능의 API는 구현하지 않는다.

- `POST /api/v1/ai-plans` — 일정 생성 제출 (`202` + jobId, 멱등)
  - `petIds`(최대 5) / `petId` 선택 — 둘 다 없으면 **대표 반려견**이 기본값
  - `pinnedPlaceIds`(최대 10) — 필수 포함 장소. 검색 후보에 강제 합류, 없으면 AIPLAN_013 실패
  - `sigunguCode` 선택 — 후보를 그 시군구(제주시=4 · 서귀포시=3)로 좁힌다. 생략하면 지역 전체다.
    **좁혀서 후보가 없으면 지역 전체로 넓히지 않고 AIPLAN_012 로 실패한다** — "제주시만" 이라는
    요청에 서귀포 장소를 섞으면 조건을 무시한 일정이 되고 그 사실이 응답에 드러나지도 않는다
  - `planId` + `regenerateDay` — 하루 재생성. 기존 일정을 plan-service 내부 API 로 받아
    지정한 날만 새로 짠다. 일차 범위는 제출 시점에 검증(AIPLAN_014/015)
  - 검증: 시작일은 오늘 이후(AIPLAN_017), 기간은 최대 10일(AIPLAN_018) — 예보 커버리지(약 11일)와 프롬프트 규모에 맞춘 상한
  - `preferFavorites` — 즐겨찾기 우선 반영. 찜한 장소를 후보에 합치고 [선호] 표시로
    우선 배치를 지시한다. 필수가 아니라 조회 실패는 관용 처리(선호 표시만 빠짐)
  - **여행 기간의 기상청 예보**(tour 내부 API, 약 11일)를 프롬프트 "날씨 전망" 절로 싣는다 —
    강수확률 60%↑ 실내 위주, 최고기온 31℃↑ 야외는 아침·저녁 배치 지시. 커버리지 밖/조회 실패는 절 생략
- `POST /api/v1/ai-plans/packing-list/{planId}` — 반려견 여행 준비물 목록 생성 (동기, 수십 초 가능).
  일정 개요(필수)·반려견 특성·날씨 전망(관용)을 근거로 항목마다 이 여행 데이터 기반의 이유를 붙인다. 저장하지 않는 제안이다
- `GET /api/v1/ai-plans/jobs/{jobId}` — 폴링. 상태·초안과 함께 제출 때 쓴 생성 조건(`conditions`)과,
  완료된 작업이면 그 초안을 이미 담은 일정(`committedPlanId`, plan-service 에 물어 온다)을 내린다
- `GET /api/v1/ai-plans/jobs/{jobId}/stream` — SSE. 이벤트 페이로드가 폴링 응답과 같아 `conditions` ·
  `committedPlanId` 도 함께 온다
- `POST /api/v1/ai-plans/jobs/{jobId}/cancel` — 작업 취소. 이미 취소된 잡은 200(멱등),
  완료·실패한 잡은 409(AIPLAN_019)
- `POST /api/v1/ai-plans/{planId}/revisions` — 자연어 일정 수정 ("카페 말고 다른 곳")
- `POST /api/v1/assistant/conversations` / `POST .../conversations/{id}/messages` — 상담사·비서 채팅
- `POST /api/v1/reviews/drafts` — 후기 자동 작성
- `GET /api/v1/members/me/pets/{petId}/preferences` — 반려견 성향 분석 결과
- `GET /api/v1/members/me/travel-styles` — 여행 스타일 학습 결과

## 처리 흐름

```text
Controller → Facade → *JobProcessor → *Worker(@Async("aiPlanTaskExecutor")) → Redis 상태 저장/이벤트
```

- 비동기 패턴 세부는 `api-design-guide.md` §7, 대화형 API는 §8을 따른다.
- 일정 생성 파이프라인: 반려견 프로필(auth) + 장소·적합도 데이터(tour) Feign 조회 → 프롬프트 조립 → LLM 호출 → 일정안 검증 → 결과 반환. 사용자가 확정하면 plan-service에 저장된다.

## 구현 주의점

- LLM 호출은 `AiLlmPort` 뒤에 캡슐화한다. 구현은 `OllamaLlmAdapter`(**Spring AI**,
  공유 인프라의 로컬 LLM) 하나다. on/off 스위치나 스텁 어댑터는 두지 않는다 — BossPickSeoul 과
  같은 구조이고, 프론트 개발자가 백엔드를 로컬에 띄우지 않고 dev 서버에 붙기로 해서 LLM 없는
  환경을 위한 분기가 필요 없다. Spring AI 는 첫 호출 때 연결하므로 Ollama 가 없어도 기동은 된다.
- **모델 교체는 `AI_LLM_MODEL` 값 하나로 끝난다** (gpt-oss:20b / qwen2.5:7b-instruct / llama3.1:8b 등,
  Infra/ollama 참고). provider 교체(예: ANTHROPIC)는 spring-ai-{provider} 의존 + 모델 빈 +
  어댑터를 더하는 것으로 끝난다 — application 계층은 손대지 않는다 (BossPickSeoul 동일 구조).
- 구조화 출력은 `BeanOutputConverter` 가 응답 DTO 에서 JSON 스키마를 유도해 프롬프트에 싣고
  파싱까지 맡는다. Ollama `format=json` 이 "JSON 만"을, 스키마 지시가 "어떤 JSON 인지"를 강제한다.
  마크다운 코드 펜스로 감싼 응답도 관용 처리된다(로컬 모델이 자주 내는 형태).
- gpt-oss 계열 추론 강도는 `AI_LLM_REASONING_EFFORT`(기본 low) — medium 은 추론에 생성 토큰
  대부분을 소모한다. 미지원 모델은 이 값을 무시한다.
- Spring AI 내장 재시도(기본 10회)는 끈다. 타임아웃된 생성은 다시 보내도 똑같이 느려서
  GPU 와 워커 스레드만 점유한다 — 실패 처리는 서킷 + 잡 상태로 일원화한다.
- 서킷 인스턴스 `llm` 단일 인스턴스, `slow-call-duration-threshold` 완화 (`coding-conventions.md` §10).
- **일정을 소유하지 않는다** — 생성 결과는 제안(draft)이며, 저장·확정의 원천은 plan-service다.
  **담긴 사실의 정본도 plan-service 다** — 담기 멱등 키(`plan.source_ai_job_id`)를 plan 이 쥐고,
  잡 조회는 그쪽에 물어 `committedPlanId` 를 싣는다 (#970, 아래 "담은 일정을 함께 내린다").
- **환각은 사후 검증보다 후보를 먼저 주는 방식으로 막는다.** tour-service 에서 동반 가능으로
  확인된 장소 목록을 받아 프롬프트에 싣고 "이 안에서만 고르라"고 한다. 검증은 틀린 답을
  걸러낼 뿐이지만 후보를 주는 방식은 애초에 틀릴 자리를 없앤다. 후보 줄에는 **1부터 시작하는 번호**를
  붙이고 모델은 그 번호만 적는다 — 아이디 · 이름 · 종류는 서버가 그 번호의 후보에서 채운다 (#1128, 아래
  "출력 토큰을 줄인다").
- **실내 · 카페를 명시한 요청은 후보 풀에 반영한다** (#1170). `requestNote` 에 `실내` 또는 `카페` 가
  있으면 그 조건으로 동반 가능 장소를 더 찾아 풀 앞에 둔다. 개수 상한(`place-candidate-size`)은
  그대로라 일반 검색의 꼬리만 빠진다. 숙소는 실내여도 그 요청을 대신하지 않는다. 맞는 후보가
  없으면 생성을 멈추지 않고, 근거 맨 앞에 `REQUEST_UNMET`("요청하신 실내 카페가 이번 후보에 없어요"
  등)을 붙이고 넣었다고 말하는 근거는 뺀다.
  - **권역을 돌아가며 8곳을 고른다 (#1245).** 전에는 `placeId` 순 앞 8곳이었는데 dev 실내 카페 앞 8곳 중 5곳이
    북서부였다 — 남서부 · 남부 일정의 식사가 애월로 오갔다. 이제 50곳을 가져와 `CandidateZonePolicy.acrossZones` 가
    권역(`JejuZone` 선언 순서)을 한 바퀴씩 돌며 고른다. 권역을 모르는 후보는 맨 뒤다.
- **`itemType` 과 `placeId` 는 따로 볼 수 없다 (필수).** `placeId` 는 plan-service 에서
  `targetId` 가 되는데, 그 값이 `place.id` 인지 `walk_course.id` 인지를 `itemType` 이 정한다
  (`shared-travel` 의 `PlanItemType`). 어긋나면 400 도 나지 않고 **틀린 아이디가 조용히 저장된다**
  — `WALK` 는 장소 존재 검증에서 빠지는 유형이기 때문이다 (#89).
  - **ai-service 는 산책 코스를 본 적이 없다.** 후보 목록은 tour-service 의 장소뿐이라
    `walk_course.id` 를 알 방법이 없다. 그래서 초안에는 `WALK` 가 나오지 않는다 —
    산책 일정은 장소 항목으로 내려가고 그 성격은 `note` 에 담긴다.
  - **종류는 모델이 아니라 후보 분류가 정한다** (#1128, `OllamaLlmAdapter#itemTypeOf`). 숙박 → `LODGING`,
    음식점 → `MEAL`, 그 밖 → `PLACE` — 셋 다 `targetId` 가 `place.id` 인 유형이다. 모델이 종류를 고르던 때는
    `WALK` 에 장소를 실어 오거나 `"CAFE"` 같은 모르는 코드를 적는 것을 뒤에서 `PLACE` 로 바로잡아야 했는데,
    이제 모델이 종류를 쓰지 않아 그 보정 자리가 없다(옛 필드를 섞어 써도 무시된다).
- 돌아온 번호를 후보 목록과 다시 대조한다 — 프롬프트 규칙을 어기는 일이 드물게 있다. **번호가 없거나
  목록 밖이면 항목을 버리고** 개수를 경고 로그로 남긴다. 전에는 후보 밖 항목을 장소 연결만 끊고 모델이 적은
  이름으로 남겼지만, 이제 이름을 모델이 쓰지 않아 남길 것이 없다 — 이름도 장소도 없는 줄은 화면에 "이름이
  없는 항목" 으로 그려진다(#487 과 같은 결과). 그래서 **초안의 모든 항목에는 장소가 있다.**
- 프롬프트에 개인정보(회원 식별 정보)는 최소화하고, 반려견 특성·여행 조건 등 필요한 정보만 전달한다.
- **프롬프트의 내부 표기가 사용자 문장에 새지 않게 한다 (필수).** 준비물 `reason`, 초안 `reasons[]` 와
  `items[].note` 는 FE 가 손대지 않고 그대로 그리는 **화면의 본문**이다. 모델은 입력의 표기를
  그대로 흉내 내므로, 프롬프트가 `[1일차]` 라고 쓰면 이유에 `[1일차]~[3일차] 구름많음` 이 그대로
  나갔다 (#233). 두 겹으로 막는다.
  - **입력 표기**: 근거 문장이 가리키게 될 이름(일차 `1일차`, 반려견 `반려견 2`)은 대괄호 없이 쓴다
    (`AiPlanPromptFactory#dayLabel`). 대괄호는 후보 줄의 태그(`[필수 포함]` · `[선호]`)처럼 지시문이
    이름으로 부르는 표시에만 남긴다 — 이것은 문장 안에서 인용될 일이 없다.
  - **출력 지시**: 두 시스템 프롬프트에 "대괄호 같은 기호 표기를 쓰지 말고 `2일차`·`1~3일차` 처럼
    문장으로 적으라"는 규칙을 둔다.
  - **후처리**: 그래도 새는 것은 `LlmTextCleaner` 가 어댑터에서 걷어낸다 — 대괄호 문자 제거와
    `1일차~3일차` → `1~3일차` 접기, 이 둘뿐이다. 문장을 더 다듬기 시작하면 규칙의 끝을 아무도 모른다.
    프롬프트만으로는 완전히 막히지 않아 후처리를 둔 것이고, 후처리만 두면 프롬프트가 계속 새는
    표기를 가르치는 셈이라 둘 다 필요하다.
- **장소명 뒤 조사도 같은 두 겹이다** (#570). 프롬프트 규칙 9번이 "장소명 뒤에 조사를 붙이지
  말라" 고 `애월코스트34은` 을 인용해 지시하는데도 dev 에서 그대로 나왔다 — **규칙이 없어서가
  아니라 모델이 어긴 것**이라 프롬프트를 세게 쓰는 것으로는 확정적으로 못 막는다.
  `KoreanParticleFixer` 가 어댑터에서 바로잡는다.
  - **후보 장소명 바로 뒤에 붙은 조사만** 고친다. 문장 전체를 훑지 않는다 — 모델이 쓴 일반
    문장까지 손대면 고치는 것보다 망가뜨리는 것이 많아진다.
  - **조사 다음 글자가 한글이면 조사로 보지 않는다.** 이 가드가 없으면 `노형` 이 후보일 때
    `노형은하수공원` 이 `노형는하수공원` 이 된다.
  - **숫자를 읽어서 받침을 판정한다.** `34` 는 "삼십사" 라 받침이 없어 `34는` 이다. 프론트의
    `lib/text/korean.ts` 는 숫자 읽기를 일부러 안 하는데(거기는 반려견 이름이라 한글이 압도적),
    여기는 이 버그를 낸 이름이 `애월코스트34` 라 숫자 읽기 없이는 고칠 수가 없다.
  - **받침을 모르면 손대지 않는다.** 프론트는 판정 불가를 "받침 없음" 으로 보는데 **여기서 그러면
    안 된다** — 저쪽은 조사가 *없는* 자리에 새로 붙이므로 빗나가도 본전이지만, 여기는 **이미 붙어
    있는 조사를 덮어쓴다.** 빗나가면 맞던 문장이 틀린 문장이 되고 그건 고치려는 버그와 같은
    종류다. 후보 제목은 tour-service 원문 그대로라 `카페공작소(애월점)` 처럼 괄호로 끝나거나
    `...Pension` 처럼 영문으로 끝나는 것이 실제로 있다 — 앞은 `)` 라 알 수 없고, 뒤는 읽으면
    "펜션"(ㄴ 받침)이라 오히려 받침이 있다.
  - **`으로`/`로` 는 고치지 않는다.** 한국어 도로명이 문자 그대로 `<지명>+로` 라서, 지명이 후보
    제목이면 `노형로 12` 의 `로` 가 조사로 잡혀 `노형으로 12` 가 된다 — 뒤 글자를 보는 가드로는
    막을 수 없는 구조적 충돌이다. 보고된 것도 프롬프트 규칙 9번이 나열한 것도
    `은/는 · 이/가 · 을/를` 뿐이라 애초에 범위 밖이다.
- **같은 장소를 여러 날에 넣지 않는다** (#570). 1일차·2일차가 둘 다 `애월한담공원` 으로 시작한
  초안이 나왔는데 프롬프트에 회피 지시가 **아예 없었다**. 규칙 11번으로 못박고, 어댑터가 같은
  `placeId` 가 여러 날에 걸치면 경고 로그를 남긴다.
  - **숙박(`LODGING`)은 센다는 대상에서 뺀다.** 같은 숙소에 이어 묵는 것이 정상이고, 그것은
    **결과 항목의 `itemType`** 으로 갈린다. 그 `itemType` 은 어댑터가 후보의 `contentTypeName`
    (`숙박`)으로 정한다 (#975 · #1128, 아래).
  - **항목을 지우지 않는다 — 가까운 미사용 후보로 바꾼다 (#1254).** 처음(#570)에는 "지우면 그 일자에 구멍이 나고
    무엇으로 메울지 어댑터가 모른다" 며 경고만 남겼다. dev 에서 재발이 이어졌다 — 10/7 3일 2회 중 1회
    (`곽지해수욕장` 1 · 3일차), 10/8 #1245 배포 뒤 3일 1회차의 3일차가 2일차의 중문색달해수욕장 · 애견카페왈 사계점을
    그대로 되풀이했다(5번 생성 중 2번). 이제는 후보마다 좌표 · 종류를 알고 풀에 권역별 선택지가 있어(#1236 · #1245)
    **메울 것을 안다.** `AiPlanRepeatGuard` 가 사실 대조 다음, 동선 대조 앞에서 앞선 날에 나온 장소(숙박 제외)를
    **같은 종류(식사 자리는 음식점, 장소 자리는 숙박도 음식점도 아닌 것)에서 원래 장소에 가장 가까운, 일정에 없는
    후보**로 바꾼다. 20km 안에 없으면 그대로 두고 경고한다(먼 곳으로 바꾸면 반복보다 나쁜 동선이다). 메모는 서버
    문구다(`AiPlanDraftFactGuard#fallbackNote`) — 모델의 메모는 원래 장소를 두고 쓴 문장이다.
  - **같은 날 안의 되풀이도 바꾼다 (#1257).** 처음에는 "순서를 뜻했을 수 있다" 며 다른 날 반복만 봤는데, 10/8 7일 일정의
    4일차가 `숨비아일랜드 → 숨비아일랜드` 로 같은 카페를 연달아 넣었다. 한 날에 같은 곳을 두 번 들르는 일정은 없다 —
    같은 날 앞 항목에 나온 장소도 같은 규칙으로 바꾼다.
  - **로그 두 가지.** 어댑터의 `LLM placed the same place on multiple days` 는 **모델의 반복을 센다**(가드 앞) —
    재발률을 보는 자리다. `AI plan repeated place replaced day= before= after= km=` · `… kept` 는 가드가 고친 결과다.
    바꿔도 반복이 잦으면 그때 일자별 풀 분할을 본다.
- **초안을 서버가 가진 사실과 대조한다 (필수, #975).** 모델의 자유 서술이 검증 없이 나가서, 같은
  결과에 "각 일정 간 이동 거리가 짧아…" 와 FE 의 `직선 30.1km — 하루 이동이 깁니다` 가 함께 붙었고,
  1박 2일의 마지막 날에 숙박이 들어갔고, 16~23℃ 에 "한낮의 더위를 피할 수 있습니다" 가 나왔고,
  콘도를 "해안가에서 가벼운 산책을 할 수 있는 실외 장소" 로 설명했다. 프롬프트 규칙 11~13 이 1차
  방어고, `AiPlanDraftFactGuard` 가 후보 대조 다음에 마지막 방어를 한다.
  - **숙박 유형은 후보 데이터가 정한다.** `contentTypeName=숙박` 인 장소는 `LODGING` 이다. #1128 부터는 종류
    전체를 모델이 아니라 후보 분류로 정하므로(숙박 → `LODGING`, 음식점 → `MEAL`, 그 밖 → `PLACE`) 바로잡을
    오기가 없다 — 대신 전에 있던 "숙소에서 먹는 `MEAL`(조식)" 예외도 없어졌다. 숙박 후보는 언제나 숙박이다.
    이것이 먼저 정해져야 아래 규칙이 숙박을 가른다.
  - **마지막 날에는 숙박이 없다.** 그날 `LODGING` 항목을 뺀다. 당일치기도 1일차가 마지막 날이다. 어댑터가
    그날의 `lodging` 번호로 붙인 숙박 항목도 여기서 빠진다 — **이 규칙의 주인은 `AiPlanDraftFactGuard` 하나다**
    (어댑터는 마지막 날인지 보지 않고 붙인다).
  - **확인할 수 없는 근거는 버린다.** 모델은 후보 사이 거리와 혼잡도를 본 적이 없다 — 프롬프트에
    없다. `SHORT_DISTANCE` · `LOW_CONGESTION` 근거는 통째로 빼고(스키마의 코드 목록에서도 뺐다),
    다른 근거 · 메모 안의 거리 · 혼잡 문장도 뺀다. 거리는 FE 가 좌표로 재서 행마다 보여 준다.
  - **더위는 최고기온 31℃ 이상인 날에만 말한다.** 프롬프트의 배치 지시와 같은 임계값이다. 메모는
    그날 기온, 근거는 여행 기간 중 가장 더운 날로 가른다. 전망이 없는 날은 "말할 근거가 없다" 로 본다.
  - **메모가 장소 유형 · 실내 여부와 맞아야 한다.** 실내 장소를 `야외 장소` · `야외라` 로, 실외 장소를
    `실내라` 로, 숙소 · 음식점을 `산책하기 좋은 곳` 으로 **서술한** 문장을 뺀다.
  - **지형 · 시설은 이름 · 분류에 있을 때만 말한다 (#1172).** 후보 줄에는 개요가 없다 — 실어도 소용이
    없는 것이, dev 의 여행지 원천은 분류가 `여행지`, 개요가 `관광지` · `공원` 한 낱말이다. 그래서 모델이
    이름에서 짐작해 용두암을 "용암 동굴 탐방하기", 서귀포해양도립공원을 "수영장 주변 산책로 즐기기",
    수월봉을 "산 정상에서 바다 전망 감상" 으로 적었다(2026-10-06 실측). 동굴 · 수영 · 정상/등반/등산 ·
    전망 · 폭포 · 계곡 · 등대 · 해변/백사장 주장은 장소 **이름 · 원천 분류 · 유형**에 근거 낱말
    (`굴` · `수영장`/`해수욕장` · `산`/`오름` · `전망`/`뷰` …)이 있을 때만 남긴다
    (`AiPlanDraftFactGuard.FEATURE_CLAIMS`). 주소는 근거로 보지 않는다 — 지번의 `산 12-1` 이 "산" 이 된다.
    프롬프트 규칙 13 이 1차 방어다. 대가는 메모가 밋밋해지는 것이다 — 문장이 다 빠지면 서버 문구
    ("반려견과 함께 들르는 실외 장소예요.")가 된다. 표에 없는 주장(바위 · 숲 · 전시 등)은 아직 걸러지지
    않는다. 원천 개요가 채워지면 개요를 근거로 넓히는 것이 다음 단계다.
  - **낱말이 아니라 주장을 잡는다.** `야외` · `가까워` · `산책` 한 낱말로 자르면 맞는 문장이 지워진다 —
    실내 카페의 "비가 오면 야외 대신 실내에서 쉬어요", 해변의 "바다와 가까워 걷기 좋아요", 카페의
    "바닷가 산책 뒤에 들러요". 거리는 **장소 사이** 거리를 말할 때만, 실내외 · 산책은 **이 장소가 무엇이다**
    라고 말할 때만 모순이다. 반려견 성향(`더위에 약한`)은 입력으로 받은 사실이라 기온과 무관하게 남긴다.
    한계: 마침표 없이 쉼표로 이은 메모는 한 문장으로 보여 통째로 서버 문구가 될 수 있다.
  - **문장 단위로 걷는다.** 한 줄에 맞는 말과 틀린 말이 섞이는 일이 흔해 통째로 버리면 맞는 말까지
    잃는다. 남는 문장이 없으면 근거는 버리고, 메모는 후보 데이터로 만든 서버 문구
    (`반려견과 함께 묵는 숙소예요.` 등)로 바꾼다. 숙소 문구는 어댑터가 `lodging` 번호로 붙이는 숙박 항목의
    메모로도 쓴다(`AiPlanDraftFactGuard.LODGING_NOTE` 한 상수). 장소가 없는 항목은 메모를 비운다 — 지어 채울
    사실이 없다(#1128 뒤로 어댑터는 그런 항목을 만들지 않지만, 이 클래스는 받은 초안만 보고 판정한다).
  - **이름으로 후보를 거르지 않는다.** 코드처럼 보이는 `N109` 는 원천 데이터에 있는 실제 카페다
    (dev 2,323곳 중 한글 없는 이름은 `5L2F` · `Cafe3535.1` · `N109` 셋, 모두 음식점·카페). 이름 패턴으로
    거르면 실제 장소를 잃는다.
- **동선 — 권역을 싣고, 숙소는 서버가 좌표로 다시 본다 (필수, #1171).** dev 실측(`몽과 제주 2박 3일`)에서
  숙소는 구좌(동쪽)인데 일정은 중문 · 애월 · 한경(서 · 남쪽)이라 직선 33~62km 구간이 여섯이었다. 원인은 둘이다 —
  후보 줄에 주소 문자열만 있고 규칙 12가 "이동 거리는 입력에 없다" 고 해서 **모델에게 지리 신호가 없었고**,
  모델이 고른 `lodging` 을 **서버가 거리로 확인한 적이 없었다.**
  - **권역 (`JejuZone`)** — 한라산을 가운데 둔 6권역(북서부 · 북부 · 북동부 / 남서부 · 남부 · 남동부)을 좌표로
    정해 후보 줄에 `권역: 남서부` 로 싣는다(#1246 부터 전체 주소 대신 `권역: 남서부 · 한경면`). 경계는 위도 33.36(한라산), 경도 126.42 · 126.68 이다.
    제주 범위 밖이거나 좌표가 없으면 싣지 않는다. 규칙 2가 "하루는 한 권역, 많아야 맞닿은 두 권역, 그날 숙소도
    그날 끝 · 다음 날 시작의 권역이나 맞닿은 권역" 을 지시한다. **일자 사이도 잇는다 (#1254)** — "다음 날은 전날
    숙소의 권역이나 맞닿은 권역에서 시작하고, 여러 날이면 맞닿은 권역을 따라 섬을 한 방향으로 돈다". 7일 일정이
    4일차 북동부 숙소 → 5일차 남서부(수월봉) 61.5km 로 섬을 가로질렀다 — 숙소 재배치는 그날 끝과 다음 날 시작
    사이에 숙소를 둘 뿐이라, 두 날이 섬 양 끝이면 고칠 수 없다. **규칙 문장만으로는 모자라 일자별 순서를 제안한다
    (#1257)** — 규칙을 더한 뒤에도 7일 일정이 북부 → 남서부 50.4km, 남동부 → 남서부 56.9km 를 건넜다. 사용자 프롬프트의
    여행 조건에 `- 권역 순서 제안: 1일차 북서부 → 2일차 남서부 → 3일차 남부 …` 를 싣는다(`JejuZone#aroundTheIsland` —
    서쪽 해안을 내려가 동쪽 해안을 올라오는 한 바퀴, 여섯 날을 넘으면 다시 돈다. 이웃한 날은 언제나 맞닿는다). **제안**
    이라 날씨 · 요청에 맞지 않으면 맞닿은 권역으로 바꿔도 된다고 함께 적는다. 하루짜리 · 하루 재생성 · 필수 포함 장소가
    있을 때 · 후보가 6권역을 다 덮지 않을 때(시군구 지정 등)는 싣지 않는다. **덮었다는 것은 권역마다 숙박이 아닌 후보가
    1곳 이상이라는 뜻이다 (#1312)** — 숙박만 있는 권역에 날을 주면 그날 갈 곳이 없어 모델이 다른 권역으로 채운다. 요청마다 다른 조건이라 후보 목록 뒤(#1246 의
    캐시 경계 뒤)에 둔다. **맞닿음은 같은 줄의 옆 칸과 서쪽 · 동쪽 해안의
    위아래(북서부-남서부, 북동부-남동부)뿐이다** — 북부-남부는 한라산을 넘는 길이라 넣지 않았다.
    `JejuZone#adjacentTo` 와 규칙 2 문장이 같은 정의여야 한다. 권역은 거리가 아니라 구역이라 규칙 12와 어긋나지
    않는다. 후보 50곳 기준 프롬프트가 650자 안팎 는다(후보 줄 50 × 10자 + 규칙 2 문장).
  - **숙소 재배치 (`AiPlanRouteGuard`)** — 사실 대조 다음에 돈다(마지막 날 숙박이 빠진 뒤라야 그날을 옮길 밤으로
    보지 않는다). 그날 마지막 항목이 숙박이면, 그날 마지막 장소와 다음 날 첫 장소까지의 직선거리 합으로 숙박
    후보를 비교한다. **모델 숙소가 가장 가까운 숙소보다 10km 이상 멀 때만 옮긴다** — 그 안이면 모델 선택을
    존중한다. 옮길 때 **전날 숙소도 10km 안쪽이면 거기서 이어 묵는다**(밤마다 짐을 옮기지 않게). **필수 포함 ·
    선호 숙소와, 하루 재생성이면 기존 일정의 숙소는 옮기지 않는다** — 사용자가 고른 곳이다. 기준점 좌표를 모르면
    그대로 둔다.
  - **항목 순서는 바꾸지 않는다.** 순서에 시간대가 실려 있다 — 점심 자리의 식당, "오전엔 바다, 오후엔 카페"
    같은 요청. 일자 안의 흩어짐은 권역 지시로 줄이고, 서버는 순서를 고치지 않는다.
  - **구간은 로그로 센다** — `AI plan route legs maxLegKm= longLegs= lodgingRelocated=` (긴 구간 기준 25km,
    0건이어도 한 줄). 옮긴 숙소는 `AI plan stay relocated day= before= beforeKm= after= afterKm=`. 이슈의
    "같은 조건으로 재생성해 구간 거리 비교" 를 dev 에서 이 두 줄로 한다.

    서귀포로 옮겼다(거리 합 79.7 → 19.2km). 남은 긴 구간은 후보 풀에 서쪽 숙소가 없어서다 — 아래 숙박 할당.
- **후보 풀에 숙박 · 음식점을 권역마다 싣는다 (필수, #1236 · #1245).** 후보 풀은 지역 검색 상위 N(`placeId` 순)이라
  숙박 · 음식점이 우연히만 든다 — dev 의 제주 전체 50곳에는 숙박이 3곳(서귀포 2 · 구좌 1), 음식점이 0곳이었다.
  동반 가능 숙박은 56곳(남서부 10 · 북서부 10 · 남부 10 · 북동부 17 · 남동부 6 · 북부 3), 음식점(카페 포함)은
  126곳(북부 36 · 남서부 30 · 북서부 19 · 남부 19 · 북동부 16 · 남동부 6)으로 6권역에 다 있다. 근처에 묵을 곳이나
  식사 자리가 풀에 없으면 모델도 재배치 가드도 고를 수 없다 — 숙박을 싣고 재측정하니(#1236) 25km 넘는 구간 3개 중
  2개가 식사 자리였다.
  - **종류마다 따로 한 번 더 찾는다** — `GET /api/v1/places?contentType=LODGING` · `RESTAURANT`(같은 지역 · 시군구,
    동반 가능, 한 페이지 50곳, `PlaceCandidateQueryPort#findLodgingCandidates` · `#findRestaurantCandidates`). 요청 조건
    후보(#1170) 다음, 숙박 → 음식점 순이고 필수 포함 · 즐겨찾기를 합치기 전이다. 첫 페이지 50곳으로 6권역이 다 잡힌다
    (음식점 남동부만 1곳).
  - **종류마다 권역당 2곳까지** (`CandidateZonePolicy.Kind`). 이미 풀에 있는 같은 종류(요청 조건 카페 포함)도 그 권역
    몫으로 센다. 권역은 프롬프트와 같은 `JejuZone` 이다 — 그래서 `JejuZone` 을 프롬프트 어댑터에서 application 모델로
    옮겼다. 좌표가 없거나 제주 밖이면 어느 몫인지 몰라 싣지 않는다.
  - **상한은 그대로다** — 넘치는 만큼 풀의 뒤에서부터 숙박도 음식점도 아닌 장소(일반 검색의 꼬리)를 뺀다. 종류마다
    많아야 12곳, 합쳐 24곳이라 나머지가 26곳 이상 남고 프롬프트 길이는 늘지 않는다. 실은 숙박 · 음식점은 서로를
    밀어내지 않는다.
  - **못 가져와도 생성은 계속한다.** 동선을 낫게 할 뿐 없다고 일정이 틀리지는 않는다. 종류마다 따로 부르므로 한쪽이
    실패해도 다른 쪽은 싣는다. 장소가 하나도 없으면 싣지 않는다. 로그
    `AI plan candidates spread by zone kind=LODGING|RESTAURANT fetched= before= after=` 로 몇 곳을 실었는지 본다.
- **제주 전체 일정은 후보 풀을 권역마다 대표점에서 가까운 순으로 채운다 (필수, #1312).** 권역 순서 제안(#1257)이
  7일 일정의 4일차를 남동부에 줬는데, 풀에 남동부 방문 후보가 거의 없어 모델이 맞닿지 않은 남서부(중문관광단지)로 그날을
  채웠고, 숙소 재배치 가드가 거리 합을 줄이려 맞게 고른 남동부 숙소(모두올레 애견펜션)를 남부로 옮겼다 — 가드는 결과일
  뿐 원인은 풀이다. dev 실측(2026-10-10): 일반 후보(`placeId` 오름차순 첫 50곳)의 권역 분포가 남동 2 · 남부 9 · 남서 14 ·
  북동 12 · 북부 7 · 북서 6 이었고(남동 2곳은 관광지), 이 꼬리는 숙박 · 음식점을 싣는 만큼 깎여 남동 2곳마저 빠질 수 있었다.
  숙박 · 음식점 추가 검색도 id 순 첫 페이지라 음식점 첫 50곳 중 남동 1곳 · 숙박 남동 6곳이었다. tour-service 목록 API 는
  `lat` · `lng` 를 주면 그 점에서 가까운 순이다 — 남동부 (33.33, 126.80) 기준 상위 12곳에 남동 음식점 6 · 숙박 7곳이 들었다.
  - **언제** — 시군구를 지정하지 않은 제주(`areaCode=39`)의 전체 생성만. 시군구 지정(지정 밖 장소가 섞인다) · 제주 밖(권역이
    없다) · 하루 재생성(기존 일정이 앞뒤 날을 정한다)은 전과 같다.
  - **대표점** (`JejuZone` 의 `anchorLat` · `anchorLng`) — 권역의 기하 중심이 아니라 사람과 관광지가 모인 쪽이다. 중산간을
    기준으로 잡으면 가까운 순 상위가 옆 권역의 해안 장소로 찬다. 점이 제 권역 안에 있음은 `JejuZoneTest` 가 지킨다.

    | 권역 | 대표점 | 근거 |
    |------|--------|------|
    | 북서부 | 33.4300, 126.3000 | 애월(곽지)과 한림(협재) 사이 |
    | 북부 | 33.4996, 126.5312 | 제주시청 — 인구가 가장 많은 시내 |
    | 북동부 | 33.5000, 126.8600 | 구좌(세화 · 월정)와 성산 사이 |
    | 남서부 | 33.2500, 126.3600 | 안덕(산방산 · 카멜리아힐)과 중문 사이 |
    | 남부 | 33.2541, 126.5601 | 서귀포시청 |
    | 남동부 | 33.3300, 126.8000 | 남원과 표선 사이 — dev 실측 기준점 |

  - **조회** — 대표점마다 종류 3가지(전체 · `LODGING` · `RESTAURANT`, 동반 가능, 한 페이지 50곳)를 순차로 부른다. 권역 6 ×
    3 = **18번**이다(`PlaceCandidateQueryPort#findNearbyCandidates` · `#findNearbyLodgingCandidates` ·
    `#findNearbyRestaurantCandidates`). 원천 단위가 "한 점에서 가까운 순" 이라 묶을 수 없고 생성 한 번에 한 번이다 — LLM 이
    수십 초라 수백 ms 는 문제가 아니다. **찾은 것 중 실제 `JejuZone.of(lat, lng)` 가 그 권역인 것만 그 권역 몫이다.**
    일반 후보가 비면(tour-service 장애) 부르지 않는다.
  - **방문 장소(숙박 · 음식점이 아닌 곳) 권역당 3곳 하한** (`CandidateZonePolicy.VISITS_PER_ZONE`) — 하루 2~3곳을 고르므로
    권역의 날 하루를 그 권역 안에서 채울 수 있는 최소다. 3이면 권역 몫이 방문 18 + 숙박 12 + 음식점 12 = 42곳이고 남는
    8칸이 요청 조건 후보 몫(`REQUEST_SLOT`=8)과 같아, 꼬리를 덜어 낼 때 맨 앞의 요청 조건 후보까지 깎이지 않는다(4면 2칸만
    남는다). 이미 풀에 있는 방문 장소도 그 권역 몫으로 센다. 요청 조건 후보 다음, 숙박 · 음식점보다 먼저 싣는다.
  - **숙박 · 음식점은 권역당 2곳 그대로**, 거리순 결과를 먼저 쓰고 id 순 결과를 뒤에 둔다 — 어느 권역의 거리순 조회가
    실패했을 때만 id 순이 그 권역 몫을 채운다.
  - **꼬리 깎기가 권역 몫을 깎지 않는다** — 상한(`AI_LLM_PLACE_CANDIDATE_SIZE`=50)과 프롬프트 길이는 그대로이고, 넘치는
    만큼 뒤에서부터 빼되 숙박 · 음식점과 **권역마다 앞에서부터 3곳의 방문 장소**는 빼지 않는다(`spread(…, visitFloor)`).
    남는 칸은 기존 일반 후보다. 필수 포함 · 즐겨찾기는 이 다음에 합친다(상한과 무관).
  - **실패하면 그 권역 · 종류만 비운 채 이어 간다** — `Zone anchored candidates lookup failed, continuing without them. zone= kind=`.
  - **풀은 한 줄로 센다** — `AI plan candidate pool size= zoneBalanced= zones=NORTH_WEST(visit=,lodging=,restaurant=) … unknown=`
    (모든 요청). 권역 날이 다른 권역으로 새는지 다음 조사에서 이 한 줄로 본다.
- XAI reasons는 LLM 자유 생성이 아니라, 실제 데이터 근거(기온·혼잡도·이동거리·동반 조건)를 코드에서 조립하고 문장화만 LLM에 맡기는 방향을 우선한다.
- 토큰 사용량 카운터를 두어 운영 비용을 추적한다 (어댑터가 호출당·누적 사용량을 로그로 남긴다).
- 거절(`stop_reason=refusal`)은 HTTP 200 으로 온다. content 를 그냥 읽으면 빈 응답을 파싱 실패로
  오해하게 되므로 `stopReason` 을 먼저 본다 — 원인과 사용자에게 할 말이 전혀 다르다.

## 작업 상태 전달 — SSE + 폴링 폴백

- `GET /jobs/{jobId}/stream` (text/event-stream) — 구독 즉시 현재 상태 스냅샷, 이후 **상태나
  세부 단계가 바뀔 때만** 이벤트(PENDING→RUNNING→COMPLETED/FAILED/CANCELED), 종결 시 서버가 연결을 닫는다.
  이벤트 data 는 폴링 응답의 dataBody 와 동일한 JSON 이라 FE 는 처리 코드를 공유한다.
- 전파는 Redis pub/sub(`AiPlanJobEventPort`) — SSE 연결을 잡은 인스턴스와 워커 인스턴스가
  다를 수 있어 저장소 밖 브로드캐스트가 필요하다. 메시지에 상태를 싣지 않고 수신 시 저장소를
  다시 읽는다(발행-저장 순서 역전, 스키마 드리프트 방지).
- 이벤트는 best-effort 다. 유실돼도 25초 하트비트(3회에 1번 상태 재확인)와 폴링 폴백이
  종결을 보장한다. 하트비트의 재확인은 멈춘 잡의 타임아웃 처리(expireIfStuck)도 겸하고,
  **종결만이 아니라 놓친 단계 전이도 전달한다** (#985 — 전에는 종결만 보내 흘린 단계 이벤트를
  다음 이벤트까지 복구하지 못했다).
- **순서: 소유권 확인 → 구독 → 스냅샷 재조회 → 전송** (#985, `AiPlanJobSseStreamer`). 남의 jobId 는
  첫 조회에서 404 `AIPLAN_002` 로 끝나 SSE 시작 전 JSON 봉투로 나가고 구독도 걸리지 않는다. 구독 뒤에
  다시 읽어야 첫 조회와 구독 사이에 발행된 전이(구독 전이라 아무도 못 받는다)가 잡힌다. 재조회가 실패하면
  첫 조회 결과로 대신한다.
- **단조 가드 — 뒤처진 프레임은 보내지 않는다.** 스냅샷 전송·구독 콜백·하트비트가 서로 다른 스레드에서
  각자 읽고 보내므로, 먼저 읽은 옛 상태가 나중에 보내져 마지막 프레임이 될 수 있었다. 연결마다 보낸 프레임의
  진행 순위(PENDING < RUNNING 단계 전 < `stepOrder` 1..n < 종결)를 들고 **그보다 큰 프레임만 보낸다.**
  같은 순위는 다시 보내지 않고, **종결은 단계와 관계없이 항상 보낸다**(가장 높은 순위, 이미 종결을 보낸 뒤만
  제외). 비교·갱신·전송은 emitter 잠금 안에서 한 번에 한다. 테스트: `AiPlanJobSseStreamerTest`.
- 브라우저 기본 EventSource 는 Authorization 헤더를 못 실으므로 fetch 기반 SSE 클라이언트를
  쓴다. 연결이 끊기면 `GET /jobs/{jobId}` 폴링으로 폴백한다. (BossPickSeoul 동일 구조)

### 세부 진행 단계 (필수)

대기 화면이 진행을 그릴 수 있도록 `step` · `stepOrder` · `totalSteps` 를 함께 내린다.
`AiPlanJobStep` 이 정본이고 값은 넷이다 — `CONDITIONS` 조건 확인 → `CANDIDATES` 후보 장소 수집
→ `WEATHER` 날씨 전망 반영 → `DRAFTING` 일정 구성.

- **선언 순서가 곧 워커의 실행 순서다.** 둘이 갈라지면 화면은 정확해 보이는 채로 거짓
  진행률을 그리고, 그것이 이 기능을 미루던 이유다. `AiPlanWorker.toQuery` 의 줄 순서가
  계약이고 테스트가 그 둘을 묶어 둔다 — 단계를 더하거나 순서를 바꿀 때 함께 고친다.
- `order` 와 `total` 은 `ordinal` 과 값의 개수에서 파생한다. 손으로 적으면 값을 추가할 때
  한쪽만 고쳐져 "5 / 4 단계" 가 나간다.
- **PENDING 이면 `step` 이 null 이다.** 0 이나 1 로 채우면 화면이 시작한 것으로 그린다.
- 종결 상태에서는 마지막으로 밟은 단계가 남는다 — 실패 지점을 아는 것이 진단이다.
- 그럴듯한 이름을 늘리지 않는다. 여기 있는 단계는 워커가 실제로 밟는 단계여야 한다.
- **단계 길이는 균등하지 않다.** dev 관측에서 화면이 1/4 에서 4/4 로 튄다는 보고가 있었는데,
  네 단계가 모두 저장·발행된다는 것은 코드로 확인됐고 FE 폴링도 2초다
  (`lib/ai-plan/job.ts` `JOB_POLL_INTERVAL_MS`; SSE 구독 중에는 즉시 push). 남은 가설은
  **2·3단계가 HTTP 조회 한두 번이라 수 초 만에 끝난다**는 것이다.
  `AiPlanWorker.StepTimer` 가 단계별 소요시간을 로그와 지표로 남긴다 — **먼저 재기만 하고 화면은
  손대지 않는다.** 정말 짧은 것이라면 진행 막대는 정직한 것이고, 균등한 4등분처럼 보이게
  만드는 쪽이 오히려 거짓 진행률이다 (#570).
- **단계별 소요는 지표다** (#985). Timer `ai.plan.job.step`(Prometheus `ai_plan_job_step_seconds_*`),
  태그 `step` · `mode`(`full`/`regenerate`) · `outcome`(`completed`/`failed`/`canceled`). jobId 등 잡을 가리키는
  값은 태그에 두지 않는다. 로그 `AI plan job step done` 에도 `mode` · `outcome` 이 실린다. 이름·태그·PromQL 은
  `observability-guide.md` "AI 일정 잡 지표".
- 하루 재생성에서 3/4(WEATHER)에 수십 초 머문다는 보고(#985)는 WEATHER 가 tour 조회 한 번(상한 약 7초)이라
  단계 길이로는 설명되지 않는다. 서버 쪽 원인은 위 SSE 순서 버그였고, 화면 쪽(진행 상태 순서 역전 · 30초 안전
  폴링)은 프론트 이슈로 따로 다룬다.

### 현재 단계 시작 시각 `stepStartedAt` (#985)

작업 조회·SSE 응답에 `stepStartedAt: string | null` 을 싣는다 — **현재 단계에 들어간 서버 시각**이다.
대기 화면이 "이 단계에서 n초째" 를 그릴 때 쓴다. **지어낸 진행률이 아니다** — 단계가 얼마나 남았는지는 말하지 않는다.

- 형식은 ISO-8601 **오프셋 포함**, 서비스 기준 시간대 `Asia/Seoul`, 밀리초까지 (`2026-09-30T14:03:12.345+09:00`).
  밀리초가 0 이면 소수부가 빠진다. 오프셋이 있어 화면이 기기 시간대와 무관하게 뺄셈할 수 있다.
  변환은 `AiPlanPresenter` 한곳이라 폴링과 SSE 가 같다.
- **RUNNING 이고 단계가 있을 때만 채운다.** PENDING 은 단계가 없어 null, 종결(COMPLETED · FAILED · CANCELED)도
  null 이다 — 저장소에는 마지막 단계 시각이 남지만 더 흐르는 시간이 없는데 내리면 끝난 작업 위에 경과 시간이
  계속 늘어난다. 실패 지점은 `step` 이 이미 말한다.
- 저장은 `AiPlanJob.stepStartedAt`(`atStep(step, now)` 가 단계와 함께 적는다). 워커의 전이 저장 시각이라
  `StepTimer` 가 재는 구간보다 Redis 저장·발행 한 번만큼 앞선다.
- **옛 저장 데이터와 호환된다.** 필드가 생기기 전에 저장된 잡은 null 로 읽힌다 — 배포 때 돌던 잡은 다음 단계
  전이 전까지 null 일 수 있다. 테스트: `AiPlanJobJsonCompatibilityTest`, `AiPlanJobStepStartedAtTest`,
  `AiPlanJobStepStartedAtPresenterTest`.

**후속 후보 (#985 범위 밖).** DRAFTING 안의 진행을 알리려면 LLM 스트리밍으로 `draftProgress` 를 내리는 방법이
있다. 지표(단계별 p95 · DRAFTING 비중)를 먼저 본 뒤 판단한다. 하루 재생성이 목표 일자만 출력하게 좁히는 쪽은
#1128 에서 했다(아래 "출력 토큰을 줄인다").

### 생성 조건을 함께 내린다 (필수)

작업 조회·SSE 응답에 `conditions` 블록을 싣는다 — `areaCode` · `sigunguCode` · `startDate` ·
`endDate` · `petIds` · `budget` · `requestNote` ([#488](https://github.com/8llow8llowMe/hondigagae/issues/488)).

**"다시 볼 수 있다" 와 "담을 수 있다" 는 다른 약속이다.** 대기 화면은 주소를 남겨 두면 다시 볼
수 있다고 말하는데, 조건이 응답에 없으면 프론트는 제출 조건을 `sessionStorage` 에 `jobId` 키로
보관하는 수밖에 없다. 그 저장소는 탭·기기·시크릿창을 넘지 못해서, 다른 브라우저로 작업 주소를
열면 **초안은 전부 그려지는데 하단이 "조건을 다시 알려 주세요" 로 바뀐다.** 서버가 조건을 같이
내리면 화면이 저장소 없이 복원한다.

- **새로 저장하는 값이 아니다.** 제출 시점에 이미 `AiPlanJob.requestParams` 로 저장돼 있다
  (멱등 해시의 재료이자 워커의 입력). 조회 시점에 그 문자열 맵을 타입으로 되돌릴 뿐이라
  저장 스키마도 TTL 도 그대로다.
- **키 문자열의 정본은 `AiPlanJobProcessor#toParams` 다.** 워커(`AiPlanWorker#toQuery`)와
  조회(`AiPlanConditionsInfo#from`)가 같은 키를 읽는다. 컴파일러가 잡아 주지 못하는 연결이라
  `AiPlanJobConditionsRoundTripTest` 가 쓰기-읽기를 묶어 둔다.
- **폴링과 SSE 가 같은 모양이다.** 둘 다 `AiPlanPresenter#toJobStatusResponse` 를 지나므로
  갈라질 자리가 없다 — 갈라지면 프론트에 처리 분기가 두 갈래로 생긴다.
- **상태를 가리지 않고 채운다.** 초안(`planDraft`)과 다르다. PENDING 에도 실어야 대기 화면이
  "무엇을 만들고 있는지" 를 말할 수 있다.
- **`petIds` 는 문자열 배열이다.** Snowflake 라 숫자로 내리면 자바스크립트가 조용히 반올림한다
  (`coding-conventions.md` §7-1). 제출 계약(`AiPlanSubmitPayload`)과 같은 모양이라 화면이
  받은 값을 그대로 되돌려 보낼 수 있다.
- **생략 가능한 값(`sigunguCode` · `budget` · `requestNote`)은 null 이다.** 저장은 생략을 빈
  문자열로 적어 두므로 응답 경계에서 접는다 — 그러지 않으면 "메모 없음" 과 "빈 메모" 가 같아진다.
- **반려견을 지정하지 않은 제출은 `petIds` 가 빈 배열이다.** 그때 워커는 대표 반려견으로 대신하는데,
  그 결정은 잡에 기록되지 않으므로 응답도 "지정하지 않았다" 까지만 말한다.
- **노출 범위는 넓어지지 않는다.** 타인의 `jobId` 는 조건이 실리기 전과 똑같이 404 `AIPLAN_002` 다
  (존재 자체를 숨긴다). 조건은 소유권 검증을 통과한 뒤에 조립된다 — 이제 새면 존재 사실만이 아니라
  남의 여행 계획과 메모가 함께 새므로, 그 순서를 `AiPlanJobConditionsExposureTest` 가 고정한다.
- **해석할 수 없는 값은 그 칸만 비운다.** 저장소(`RedisAiPlanJobStoreAdapter#findById`)가 이미
  "해석 못 하면 없는 것으로" 를 택했는데 여기서 던지면 같은 손상 하나가 경로마다 다른 증상을 낸다 —
  폴링은 코드 없는 500 이 되고, SSE 는 구독 콜백이 예외를 삼켜 조용히 멈춘다. 조건은 초안에 덧붙는
  값이지 조회를 성립시키는 값이 아니다.

**담기에 필요한 조건만 담는다 — "조건 바꾸기" 는 아직 반쪽이다.** 저장된 파라미터 11개 중
`pinnedPlaceIds` · `preferFavorites` · `planId` · `regenerateDay` 는 응답에 넣지 않았다. 일정 저장이
받지 않는 값이라 **담기는 완전히 복원된다.** 다만 실패 화면의 "조건 바꾸기" 가 폼을 되살릴 때는
그 넷도 쓰므로(`frontend/src/types/ai-plan.ts` 의 `AiPlanRequestSnapshot`), 그쪽 복원은 여전히
프론트 저장소에 기댄다 — 다른 브라우저에서는 "꼭 넣을 장소" 와 "저장한 장소 우선" 이 조용히
초기화된다. 넓힐지는 계약 변경이라 #488 범위 밖으로 두고 여기 남긴다.

### 담은 일정을 함께 내린다 (`committedPlanId`) (필수)

작업 조회·SSE 응답에 `committedPlanId` 를 싣는다 — 이 작업의 초안을 이미 담아 만든 일정 아이디
([#970](https://github.com/8llow8llowMe/hondigagae/issues/970)). 화면은 값이 있으면 담기 버튼 대신
그 일정으로 가는 링크를 보여 준다. 담기 멱등은 plan-service 가 맡는다(`POST /api/v1/plans` 의
`sourceAiJobId`, `plan-service.md` "AI 초안 담기 멱등") — 이 값은 그 결과를 **보여 주는** 쪽이다.

- **잡에 저장하지 않는다.** `AiPlanJob`(Redis 모양)·`AiPlanJobStorePort` 는 그대로다. 잡에 적어 두면
  TTL 24h 와 함께 사라지고, 담은 일정을 지워도 잡은 모른다. 조회 때마다
  `PlanAiCommitQueryPort` → `PlanAiCommitClientAdapter` → plan-service
  `GET /internal/v1/plans/ai-commits/{jobId}?memberId=` 로 묻는다.
- **COMPLETED 에서만 묻는다.** 초안이 없으면 담을 것도 없다 — 대기·실행·실패·취소 상태의 폴링과
  이벤트마다 원격 호출이 붙지 않게 한다. 취소 응답(`cancelJob`)은 COMPLETED 가 될 수 없어 묻지 않고 null 이다.
- **소유권 검증 뒤에만 묻는다.** 남의 `jobId` 는 지금처럼 404 `AIPLAN_002` 이고 plan-service 까지
  가지 않는다(조건 노출과 같은 순서 원칙). plan 쪽도 `memberId` 로 한 번 더 거른다.
- **관용이다 — 못 물으면 null.** 같은 plan-service 를 부르는 `PlanOutlineClientAdapter` 는 503 을
  올리지만(재생성의 필수 입력), 이 어댑터는 서킷 오픈·5xx·타임아웃은 warn 로그와 함께, 404 는 로그 없이 비운다.
  던지면 plan-service 한 번 흔들림에 초안 조회가 503 이 되고, SSE 는 구독 콜백이 예외를 삼켜 종결
  이벤트를 못 보낸다. null 일 때 다시 담아도 plan-service 의 멱등 키가 기존 일정을 돌려주므로
  일정이 두 개 생기지 않는다.
- **담은 일정을 삭제하면 null 로 돌아간다.** plan 이 삭제 때 멱등 키를 비우므로 잡 화면은 담기 전
  모양이 되고, 다시 담으면 새 일정이 생긴다.
- **폴링과 SSE 가 같은 모양이다.** 둘 다 `AiPlanPresenter#toJobStatusResponse` 를 지나며, Snowflake 라
  문자열로 내린다(`coding-conventions.md` §7-1).
- **SSE 는 종결 이벤트마다 Feign 1회가 Redis pub/sub 리스너 스레드에서 돈다.** 구독 콜백이
  `getJobInfo` 를 다시 부르기 때문이다(하트비트의 종결 재확인은 같은 호출을 하트비트 스케줄러 스레드에서
  한다). 읽기 타임아웃(기본 5초)이 그 스레드를 붙잡는 상한이고, 서킷이 열리면 호출 없이 바로 null 이다.
  구독 하나가 받는 종결 이벤트는 한 번이라 호출도 구독당 한 번이다.
- 테스트: `AiPlanJobCommittedPlanTest`(상태·소유권·관용), `AiPlanJobCommittedPlanPresenterTest`(문자열),
  `PlanAiCommitClientAdapterTest`(예외 접기), `AiServiceApplicationTests`(plan-service 를 부르는 두 Feign
  클라이언트의 `contextId` 충돌 게이트).

### 취소는 협조적이다 (필수)

`POST /jobs/{jobId}/cancel` 은 **실행 중인 스레드를 멈추지 못한다.** LLM 호출은 블로킹이고
중간에 끊을 수단이 없다. 하는 일은 상태를 `CANCELED` 로 못 박는 것이고, 워커가 단계 경계마다
저장소를 다시 읽어 스스로 선다.

- 그래서 실익은 **가장 비싼 `DRAFTING` 에 들어가기 전에 서는 것**이다. 이미 들어간 뒤라면
  돌아온 초안을 버리는 것까지가 전부다 — 그것마저 안 하면 사용자가 취소한 일정이 완료로 뜬다.
- 취소는 실패가 아니다. `errorCode` 를 채우지 않는다 — 채우면 화면이 "실패했습니다" 를 띄우고
  지표에서도 장애와 섞인다.
- **멱등 키를 함께 풀어 준다.** 취소하고 같은 조건으로 다시 넣는 것이 취소의 주된 쓰임인데,
  키가 남아 있으면 취소된 잡을 그대로 돌려받는다.
- 이미 취소된 잡은 200(멱등), 완료·실패한 잡은 409(`AIPLAN_019`). 후자는 취소할 것이 없다는
  뜻이니 화면은 결과를 보여 주면 된다.
- `CANCELED` 는 종결 상태다 — 빠지면 대기 화면이 취소를 눌러 놓고도 하트비트 타임아웃까지
  스트림을 열어 둔다.

### 컨텍스트 창을 명시한다 (필수)

`ai-llm.context-tokens`(`num_ctx`)를 반드시 보낸다. **명시하지 않으면 Ollama 가 2,048 로
잡는다** — 모델이 128k 를 지원하든 서버 기본값이 상한이 되고, 넘는 프롬프트는 오류 없이
**조용히 잘린다.** 잘린 자리에 출력 스키마 지시가 있으면 모델이 스키마 밖 응답을 내놓고,
그것이 `AIPLAN_010` 으로 나온다 (#232).

실측한 프롬프트 크기다 (후보 50곳, 4일 일정).

| 구간 | 문자 수 |
| --- | ---: |
| 시스템 프롬프트 | 478 |
| 사용자 프롬프트 (후보 목록 포함) | 7,800 |
| 출력 스키마 지시 | 2,882 |
| **합계** | **11,160** |
| 준비물 프롬프트 (대조) | **695** |

**16배 차이가 dev 증상을 그대로 설명한다** — 준비물 생성은 성공하고 일정 생성만 실패했다.
한글이 3,400자 넘게 섞여 있어 토큰으로는 6,000~8,000 이고, `max-tokens`(출력)까지 같은 창에
들어가므로 기본값을 16,384 로 둔다.

- **`place-candidate-size` 와 함께 봐야 한다.** 프롬프트의 대부분이 후보 목록이라 후보 수가
  곧 프롬프트 크기다. 창을 줄이려면 후보를 줄인다.
- 창은 GPU 메모리(KV 캐시)를 쓴다. 늘리기만 하면 되는 값이 아니다.
- 실제 토큰 수는 `LLM usage ... inputTokens=` 로그로 확인한다. 프롬프트가 창의 70% 를 넘으면
  경고를 남긴다 — 잘림은 오류가 아니라 조용한 품질 저하라 미리 드러내야 한다.
- 위 표는 #232 당시 값이다. 출력 스키마를 줄인 뒤(#1128) 다시 잰 값은 아래 절에 있다.

### 출력 토큰을 줄인다 (필수, #1128)

**dev 에서 일정 생성이 1분 40초~2분 20초 걸렸다.** gpt-oss:20b · Radeon 780M iGPU 의 Ollama 로그에서 디코드가
**18.6 tok/s 로 고정**이고 출력이 **1,350~1,490 토큰**이라 디코드만 73~80초였다. 프롬프트를 줄이면 프리필만
줄고 이 시간은 그대로다 — 1분 안에 들려면 출력을 800 토큰 아래로 줄여야 한다. 실제 6박 7일 초안에서 낭비를 셌다.

| 낭비 | 실제 초안 | 결정 |
|---|---|---|
| 같은 숙소 항목을 같은 메모로 날마다 | 6번 | 숙소는 항목이 아니라 **그날의 `lodging` 번호** 하나다. 서버가 그날 끝에 `LODGING` 항목으로 펼친다 |
| 장소 없는 "점심 식사 — 식사 장소가 후보에 없으므로…" | 7번 | **장소 없는 항목을 만들지 않는다**(규칙 7). 식사는 음식점 후보가 있을 때만(규칙 3). 그래도 오면 번호가 없어 버린다 |
| `title` | 항목마다 | 서버가 어차피 후보 이름으로 덮어썼다 → 모델이 쓰지 않는다 |
| 18자리 `placeId` | 항목당 6~9토큰 | **후보 번호**(1부터)로 적는다. 후보 줄 · 기존 일정 줄에서 아이디를 뺐다 |
| `itemType` · 근거 `name` | 항목 · 근거마다 | 종류는 후보 분류로, 근거 이름은 코드표로 서버가 채운다 |
| 하루 재생성이 전체 일정을 다시 출력 | 7일치 | **그날 하루만 출력**시키고 어댑터도 대상 일자만 남긴다 — 화면은 그날만 쓴다 |

**모델이 쓰는 것** — `days[{day, items[{place, note}], lodging}]`, `reasons[{code, description}]`
(`LlmPlanDraftResponse`). 나머지는 `OllamaLlmAdapter` 가 채운다.

- **번호가 계약이다.** `place` · `lodging` 은 `query.safeCandidates()` 순서의 1부터 시작하는 번호다. 프롬프트
  (`AiPlanPromptFactory#userPrompt`)와 어댑터(`OllamaLlmAdapter#candidateAt`)가 같은 목록 순서를 쓴다.
  후보 줄은 `- 12. [필수 포함] 수월봉 | 관광지 | 실외 | 분류: … | 권역: 남서부 · 한경면` 처럼 번호가 맨 앞이다
  (#1246 부터 주소 대신 권역 · 읍면동, `동반 가능` 은 목록 머리에 한 번).
- **서버가 채우는 것** — `placeId` · `title` 은 그 번호의 후보 값, `itemType` 은 후보 분류(숙박 → `LODGING`,
  음식점 → `MEAL`, 그 밖 → `PLACE`), 근거 `name` 은 코드표(`PET_ALLOWED` 반려견 동반 가능 · `WEATHER_OK` 날씨 양호 ·
  `INDOOR_ALTERNATIVE` 실내 대안 · `REST_SLOT` 휴식 시간 확보, 모르는 코드는 "추천 이유" — 응답 계약
  `AiPlanReasonItem` 이 적어 둔 이름과 같다).
- **`lodging` 펼치기** — 숙박 후보면 그날 끝에 `LODGING` 항목을 붙이고 메모는 서버 문구(`AiPlanDraftFactGuard.LODGING_NOTE`)다.
  숙박 후보가 아니거나 목록 밖이면 무시하고 경고를 남긴다. 그날 마지막 항목이 이미 같은 숙소면 붙이지 않는다.
  **마지막 날인지는 보지 않는다** — 그날 숙박을 빼는 것은 `AiPlanDraftFactGuard` 의 규칙이고 주인을 둘로 두지 않는다.
- **버리는 것** — 번호가 없거나 목록 밖인 항목(위 "돌아온 번호를 후보 목록과 다시 대조한다").
- **근거는 최대 3개** — 프롬프트(규칙 4) · 스키마 설명 · 서버 세 곳이다. 서버는 **사실 대조 뒤에** 자른다 — 앞에서
  자르면 확인할 수 없어 빠질 근거(거리 · 혼잡)가 자리를 차지해 맞는 근거가 셋보다 적게 남는다.
- **메모는 한 문장 25자 안팎** — 프롬프트 지시뿐이다. 서버는 자르지 않는다(문장 중간에서 자르면 틀린 문장이 된다).
- **하루 재생성** — 기존 일정은 "겹치지 않게 참고만 할 것" 맥락으로 이름만 싣고, "N일차만 새로 짜서 그날 하루만
  출력할 것 · 다른 날에 있는 장소는 넣지 말 것(숙소는 이어 묵어도 됨)" 으로 지시한다. 응답 `days` 는 대상 일자
  하나다 — 다른 날이 섞여 오면 버리고, 하루만 왔는데 번호가 다르면 대상 일자로 바로잡고, 여러 날인데 대상 일자가
  없으면 비운다(FE 는 그날이 없으면 실패로 다룬다 — 빈 일자와 뜻이 다르다).
- **응답 DTO 모양은 그대로다**(FE 계약). 바뀐 것은 담기는 사실이다 — `itemType` 은 `PLACE` · `MEAL` · `LODGING` 셋,
  모든 항목에 `placeId`, 재생성 잡의 `days` 는 하루. Swagger `@Schema` 설명을 그에 맞췄다.
- 스키마 속성 순서(`@JsonPropertyOrder`)를 `place` → `note` 로 둔다. Spring AI 가 그 순서로 스키마를 만들고 모델은
  스키마 순서대로 쓰므로, 장소를 먼저 정하고 그 장소의 메모를 쓴다(지정하지 않으면 알파벳순이라 메모가 앞선다).
- 시스템 프롬프트의 **규칙 번호는 옮기지 않았다** — 이 문서와 주석이 "규칙 9번" · "규칙 11번" 처럼 부른다. 새
  스키마와 어긋난 규칙(1 · 2 · 3 · 4 · 7 · 11)만 같은 자리에서 고쳐 썼다.

**잰 크기.** 후보 50곳, `PlanPromptSizeTest` 와 같은 입력(반려견 1마리 · 날씨 전망 · 요청 메모)이다. Windows 에서 쟀다 —
스키마 지시는 들여쓴 JSON 의 줄바꿈이 `System.lineSeparator()` 라 Linux 에서는 줄 수만큼 짧다.

스키마 지시는 고정 머리말과 들여쓰기가 대부분이라 필드 설명보다 **필드 개수**가 크기를 정한다.
`PlanPromptSizeTest` 가 2,500자 상한과 "서버가 채울 필드가 스키마에 없음", "프롬프트에 10자리 이상 숫자가 없음" 을 잠근다.

**출력** — 같은 6박 7일 초안(일자당 장소 1~2 · 숙박 6박 · 근거)을 압축 JSON 으로 적으면 옛 스키마 약 2,950자
(장소 없는 점심 · 숙박 항목 포함) → 새 스키마 약 980자로 **약 1/3** 이다. 하루 재생성은 약 2,950자(전체) → 약
230자(하루)다. 토큰 수는 dev 의 `LLM timing ... outputTokens=` 로 확인한다 — gpt-oss 는 추론(analysis) 토큰도 출력
토큰으로 세므로, JSON 이 1/3 이 되어도 출력 토큰이 같은 비율로 줄지는 않는다.

**keep-alive (`ai-llm.keep-alive`, 기본 `30m`).** 첫 시도가 더 느린 것은 Ollama 기본 keep_alive(5분)가 지나 모델이
내려가고 다음 요청에 로드가 붙기 때문으로 본다(`LLM timing` 의 `loadMs` 가 0 이 아니다). **요청마다 싣는다** —
keep_alive 는 요청 단위 값이라 빠뜨린 요청 하나가 서버 기본으로 되돌린다. 일정 · 준비물 호출이 같은 옵션 조립
(`OllamaLlmAdapter#buildRequestOptions`)을 쓴다. **트레이드오프** — 그동안 Ollama 호스트의 메모리를 쥐고 있는다.
Ollama 가 다른 서비스와 같은 호스트면 붐빌 때 줄이고, `-1` 은 상주다(`AI_LLM_KEEP_ALIVE`). **요청 값이 서버
`OLLAMA_KEEP_ALIVE` 를 덮는다** (#1246) — dev 의 Ollama 는 전용 호스트(ollama-01, 서버 24h)인데 요청이 30분을 실어
30분 쉬면 모델이 내려갔고, 다음 첫 요청에 로드 6~8초가 붙었다. 전용 호스트면 `AI_LLM_KEEP_ALIVE=24h` 로 맞춘다.

**단계별 시간은 `Duration` 으로 온다 (#1235).** Spring AI 1.1.x 의 `OllamaChatModel` 은 Ollama 의 나노초 지표
(`total-duration` · `load-duration` · `prompt-eval-duration` · `eval-duration`)를 `java.time.Duration` 으로 바꿔
`ChatResponseMetadata` 에 싣는다. `OllamaLlmAdapter#durationMillis` 가 나노초 숫자만 읽던 동안 dev 의 `LLM timing` 은
`totalMs` · `loadMs` · `prefillMs` · `decodeMs` 가 **전부 null** 이었다 — 테스트가 가짜 응답에 나노초 `Long` 을 넣어
통과했다. 이제 `Duration` 을 읽고 숫자는 호환으로 남긴다. 고치기 전 dev 실측(2026-10-07)은 합계만 남았다 — 3일 일정
58.9초(입력 5,614 · 출력 301 토큰, 재시작 뒤 첫 호출), 준비물 37.2초(입력 1,699 · 출력 148 토큰, 직전 호출 5시간 뒤).
둘 다 로드가 섞였을 가능성이 높아, 배포 뒤 **같은 조건으로 연달아 두 번** 재서 첫 호출과 두 번째를 가른다.

**시간의 대부분은 입력 처리(prefill)이고, Ollama 가 그 값을 틀리게 보고한다 (#1246).** 값이 찍히자 생성 61~95초 중
38~69초가 어느 지표에도 없었다(`total − load − prefill − decode`). ollama-01 에서 직접 잰 결과 그 시간은 입력 길이를
따라 늘었다 — 후보 줄 10 · 50줄(입력 675 · 2,917 토큰)에 지표 밖 3.9 · 10.6초, 보고된 `prompt_eval_duration` 은
83 · 94ms 로 길이와 무관했다. 같은 시간대 다른 클라이언트 요청은 없었고(GIN 로그), 추론(think=low)은 60~146자로
짧았으며, 출력은 19~20 tok/s 로 예측대로다. 그래서:
- **`LLM timing` 에 `prefillEstMs`(= `totalMs − loadMs − decodeMs`)를 함께 남긴다.** `prefillMs` 보고값은 긴 입력에서
  믿지 않는다.
- **후보 줄을 짧게 둔다.** 전체 주소 대신 `권역 · 읍면동`(`권역: 남서부 · 한경면`), 모든 후보가 같은 `동반 가능` 은
  목록 머리에 한 번만 적고 다른 값(`부분 동반 가능` 등)만 줄에 남긴다. 도로명 · 번지는 모델이 쓸 곳이 없었다.
- **후보 목록을 요청 조건보다 앞에 둔다.** 전에는 기간 · 요청 문구가 맨 앞이라 거기서 갈린 뒤의 후보 목록(입력의
  대부분)을 매번 새로 처리했다(10/8 `inputTokens` 5,644 · 5,764 · 7,062 — 프롬프트 전체). 순서는 시스템 프롬프트 →
  후보 목록 → 여행 조건 · 반려견 · 날씨 · 재생성이다. 같은 지역 · 같은 요청 종류가 이어지면 Ollama 가 후보 목록까지
  캐시를 재사용한다(`inputTokens` 가 줄어든다). 동시 처리 1 · 모델 상주(keep-alive)일 때 잘 든다.

**후속 후보.** 스키마를 Ollama `format` 에 JSON 스키마로 직접 싣는 방법이 있다 — 지금은 `format=json` 에 스키마 지시
(2,246자)를 프롬프트로 싣는다. 싣고 나면 지시문을 프롬프트에서 뺄 수 있지만, gpt-oss 가 `format` 스키마를 지키는지
(harmony 출력 형식과 부딪히지 않는지) 먼저 확인해야 한다. 어느 쪽이든 dev 실측(출력 토큰 · 소요)으로 이 절의 숫자를 갱신한다.

### 실효 동시성은 1이다 — 기다림을 호출 밖에 둔다 (필수)

**앱 풀을 아무리 키워도 처리량은 늘지 않는다.** Ollama 가 `OLLAMA_NUM_PARALLEL=1` 이라 한 번에
하나만 추론하므로, 실효 처리량은 스레드 수와 무관하게 **"LLM 1회 소요당 1건"** 이다
([#508](https://github.com/8llow8llowMe/hondigagae/issues/508)).

**2026-09-13 dev 대조 실험**이 이 절의 근거다.

| | 결과 |
|---|---|
| 동시 2건 (날짜만 달리해 멱등성 회피) | **둘 다 FAILED** · `AIPLAN_020` · 123.5초 |
| 단독 1건 (같은 조건) | **COMPLETED** · 66.2초 |

123.5초는 `AI_LLM_TIMEOUT_MS=120000` 이다. **뒤에 누른 사람만 잃는 것이 아니라 먼저 누른
사람까지 잃는다** — 두 호출이 이미 전송된 채 Ollama 안에서 서로를 기다리는 동안 각자의 read
timeout 시계가 돌기 때문이다. 즉 **남을 기다린 시간이 내 타임아웃을 깎는다.**

- **기다림은 호출 밖에 있어야 한다.** 일정 생성은 `aiPlanTaskExecutor`(스레드 1)의 대기열에서,
  그 외 경로는 `LlmCallGate`(공정 세마포어 1)에서 차례를 기다린다. 차례를 받은 뒤에 HTTP 호출을
  시작하므로 **read timeout 은 "내 차례가 온 시점" 부터 잰다.**
- **타임아웃 산술은 한 수로 통일한다.** 잡 1건이 워커를 쥐는 벽시계 최악값은
  `게이트 대기 90 + 모델 호출 120 + 내부 조회(5초 × 최대 7회) 35 = 245초`이고, PENDING·RUNNING
  양쪽이 같은 수를 쓴다. **게이트 대기를 "드문 경로"라고 빼면 안 된다** — 한쪽 기준으로 잡은
  대기열이 다른 쪽에서 타임아웃을 넘겨, 대기열 끝의 잡이 정상 대기 중에 FAILED 가 된다. 조건은
  `대기열 길이 × 245초 ≤ pending-timeout-seconds` 이고 지금은 `1 × 245 ≤ 300` 이다.
  `AiPlanTaskExecutorTest` 가 이 부등식을 **설정값에서 직접 계산해** 잠근다(상수로 적으면 설정이
  바뀔 때 숫자만 남아 조용히 틀린다 — 실제로 내부 조회를 "약 15초"로 적었다가 최악 35초인 것을
  검토에서 잡았다).
- **게이트 대기 예산은 90초다** — 실측 한 턴(66초)보다 넉넉하되 최악 한 턴(120초)보다는 짧게.
  `timeout-ms` 와 같게 두면 잡 최악값이 275초로 올라 위 부등식의 여유가 사라지고, 동기 준비물
  생성이 요청 스레드를 4분까지 붙잡는다.
- **한계: 게이트 대기 중에는 취소를 보지 않는다.** 워커는 `DRAFTING` 체크포인트를 지난 뒤
  게이트에서 최대 90초 블로킹하므로, 그 사이의 취소는 차례가 온 뒤에야 반영된다(돌아온 초안은
  버리므로 잘못된 결과가 나가지는 않고 GPU 시간만 버린다). 취소를 대기 중에 보려면 포트 계약에
  체크포인트를 넣어야 해서 별건으로 둔다.
- **전제: ai-service 인스턴스가 하나다.** 세마포어는 프로세스 안에서만 공정하다. 인스턴스를 둘로
  늘리면 같은 Ollama 앞에서 다시 겹치므로, 스케일아웃 시에는 게이트를 프로세스 밖(Redis 분산 락)으로
  옮기거나 `OLLAMA_NUM_PARALLEL` 을 인스턴스 수만큼 올리고 재측정해야 한다.
- **게이트가 실제로 막는 것은 동기 준비물 생성과 일정 생성이 겹치는 경우다.** 준비물 생성은
  요청 스레드에서 바로 모델을 부르므로 워커 풀이 막아 주지 못한다. 일정 생성끼리는 풀이 1이라
  부딪히지 않고, 게이트는 풀 설정이 바뀌어도 계약이 유지되게 하는 방어선이다.
- **서킷보다 바깥이다.** 정상 대기를 slow-call 로 집계하면 멀쩡한 provider 를 차단한다.
- **`OLLAMA_NUM_PARALLEL` 을 올려 푸는 쪽은 택하지 않았다.** iGPU(Radeon 780M) 공유 메모리에서
  두 컨텍스트(`num_ctx=16384`)를 동시에 잡으면 개별 소요가 늘어 역효과일 수 있고, **재측정 없이
  올릴 근거가 없다.** 올리려면 인프라 저장소에서 바꾸고 이 절의 표를 다시 채운다.

#### 붐빔·과부하·조건을 세 코드로 가른다 (필수)

셋은 서로 다른 사건이고 **사용자가 할 일도 다르다.** 하나로 묶으면 조건과 무관한 실패에 대고
조건을 탓하게 된다 — `AIPLAN_020` 의 문구가 이 이슈 전까지 정확히 그랬다.

| 코드 | 언제 | 사용자가 보는 것 | 할 일 |
|---|---|---|---|
| `AIPLAN_004` JOB_QUEUE_FULL | **제출 시점**, 실행 1 + 대기 1 이 다 찼다(= 동시 3번째) | **202 + jobId** 로 받되 그 잡이 **즉시** `status=FAILED` `errorCode=AIPLAN_004` 다. 기다린 적이 없다 | 조건 그대로 잠시 후 다시 누른다 |
| `AIPLAN_021` LLM_BUSY | **실행 중**, 차례를 기다리다 못 받았다 | 200 + `status=FAILED`. 대기 화면이 실패로 바뀐다 | 조건 그대로 다시 누른다 |
| `AIPLAN_020` LLM_TIMEOUT | **내 차례에** 모델이 제한 시간을 넘겼다 | 200 + `status=FAILED` | 기간·조건을 줄인다 |

- **셋 다 폴링으로 온다.** 제출은 언제나 202 + jobId 이고, 갈리는 것은 **언제 종결되느냐**다 —
  `AIPLAN_004` 는 제출 직후 이미 종결, 나머지 둘은 돌다가 종결. 그래서 FE 는 분기를 늘릴 필요 없이
  기존 `status=FAILED` 경로에서 `errorCode` 만 보면 된다.
- **`AIPLAN_004` 의 `SERVICE_UNAVAILABLE`(503)은 이 경로에서 쓰이지 않는다.**
  `AiPlanJobProcessor#submitPlan` 이 `TaskRejectedException` 을 잡아 잡을 FAILED 로 저장하고
  `accepted(jobId)` 를 돌려주기 때문이다. 제출 자체를 503 으로 거절하는 쪽이 더 맞는지는
  FE 계약 변경이라 #495 와 함께 정한다 — **지금 코드의 사실은 202 다.**
- **`AIPLAN_020` 의 문구는 이제 참이다.** 대기를 게이트가 흡수하므로 여기 오는 것은 정말로
  "내 요청이 무겁다" 뿐이다. 그 전까지는 남이 눌렀다는 이유로 이 문구가 나갔다.
- **즉시 종결을 먼저 쓴다.** 대기열을 길게 잡아 5분 기다리게 했다가 실패시키는 것보다, 지금
  붐빈다고 바로 말하는 편이 낫다. 그래서 **동시 제출 2건까지 받고**(실행 1 + 대기 1) 3번째는
  제출 즉시 `AIPLAN_004` 로 종결한다 — 더 받으려면 위 부등식대로 PENDING 타임아웃을 함께 올린다.
- **준비물 생성(동기)도 같은 코드를 낸다.** 그쪽은 잡이 아니라 HTTP 응답이라 `AIPLAN_021` 이
  **503** 으로 나간다. 최악 응답 시간은 게이트 대기 90초 + 모델 호출 120초 = **210초**다.

**미결: FE 폴링 상한(90초)과 서버 최악 대기(245초)가 어긋난다.** 서버는 대기열 끝의 잡이 245초
안에 시작한다는 전제로 PENDING 타임아웃을 300초로 두는데, FE 는 `JOB_POLL_LIMIT_MS = 90_000`
에서 폴링을 끊고 수동 확인 화면을 띄운다(`frontend/src/lib/ai-plan/job.ts`). 2번째 제출자가
**정상 대기 중에** 화면상 포기 상태가 되므로, 두 숫자를 #495 에서 함께 맞춘다.
- FE 전달은 [#495](https://github.com/8llow8llowMe/hondigagae/issues/495) 와 함께 — `AIPLAN_021`
  은 **재시도 유도**, `AIPLAN_020` 은 **조건 수정 유도**로 문구가 갈라져야 한다.

### 실패 원인을 로그에서 가른다 (필수)

`AIPLAN_010`(파싱 실패)이 나면 다음을 함께 남긴다. 이것들이 **고칠 곳을 가른다.**

| 값 | 무엇을 알려 주는가 |
| --- | --- |
| `finishReason` | `length` 면 출력이 `num_predict` 에서 잘린 것이다 — 출력 예산 문제 |
| `promptTokens` / `contextTokens` | 프롬프트가 창에 가까우면 입력이 잘린 것이다 — 창·후보 수 문제 |
| `rawHead` | JSON 이 아닌 산문인지, 잘린 JSON 인지, 스키마가 다른 JSON 인지 |

원문과 파서 메시지는 각각 **500자로 끊는다.** 실패가 몰릴 때 로그가 폭발하면 안 되고, 원인을
가르는 데는 앞부분으로 충분하다. `textLength` 로 원래 길이는 남긴다.

**`LLM_TIMEOUT`(AIPLAN_020)을 `LLM_UNAVAILABLE`(AIPLAN_007)과 가른다.** 전에는 둘 다
AIPLAN_007 이라 "LLM 이 안 떠 있나" 와 "너무 오래 걸리나" 를 구분할 수 없었다. 사용자에게 할
말도 다르다 — 앞은 잠시 후 다시, 뒤는 조건을 줄이라는 안내다. 판정은 원인 사슬을 훑어서
한다(`SocketTimeoutException` 이 `ResourceAccessException` 안에 들어 있다).

### 파싱 실패를 재시도하지 않는다 (결정)

#232 가 물은 항목이다. **재시도도 부분 파싱도 하지 않는다.**

- 재시도는 같은 프롬프트를 다시 보내는 것이라 원인이 컨텍스트 잘림이면 **똑같이 실패한다.**
  90초가 180초가 되고 잡 실행 제한(기본 300초)에 더 가까워질 뿐이다.
- 부분 파싱은 깨진 JSON 의 앞부분을 살리는 일이라, "며칠치가 빠진 일정" 을 정상처럼 내려
  준다. 초안은 사용자가 그대로 담는 값이라 조용히 반쪽을 주면 안 된다.
- 대신 **원인을 드러내고 잘리지 않게 고치는 쪽**을 택했다. 스키마 밖 응답 자체는
  `format=json` + 스키마 지시 + 컨텍스트 창으로 줄인다.

### 빈 초안은 한 번 다시 부른다 (결정, #1268)

형식은 맞는데 **방문 항목(장소 · 식사)이 하루도 없는 초안**은 한 번만 다시 부르고, 그래도 비면
`AIPLAN_022` LLM_EMPTY_PLAN 으로 실패시킨다. 숙소만 있는 초안 · 하루 재생성에서 대상 일자가 없는 응답도
빈 초안이다.

- **왜 위 결정과 갈리나.** 파싱 실패의 흔한 원인(컨텍스트 잘림)은 같은 프롬프트면 똑같이 재현된다. 빈
  초안은 그렇지 않다 — dev 의 3일 일정(10/8, 입력 5.7k / 창 16k)이 출력 144토큰 · 번호 경고 0건으로 세 날
  모두 비어 왔고, 같은 조건의 바로 앞 실행은 채워졌다. 그 회차의 모델 선택이라 다시 부를 값이 있다.
- **전에는 그대로 "완료" 였다.** 사용자는 "N일차" 제목만 있는 빈 카드를 받았고 담을 수도 있었다.
- **일부 날만 비면 다시 부르지 않는다.** 한 번 더 부르면 7일은 90초가 더 붙는데, 빈 날 하나는 담은 뒤
  "이 날 다시 만들기" 로 채울 수 있다. 초안은 그대로 내고 화면이 그날을 안내한다(#1270).
- **시간 예산.** 다시 부르는 것은 전부 빈 경우뿐이고, 최악도 모델 호출 120초 × 2 + 후보 단계라 실행 제한
  300초 안이다. 다시 부르는 호출도 차례 게이트를 다시 탄다 — 그 사이 생긴 타임아웃 · 붐빔은 그 코드
  (`AIPLAN_020` · `021`)로 그대로 올린다. 첫 회차에 남길 것이 없기 때문이다.
- **원문을 남긴다.** 빈 날이 있으면 회차 · 빈 날 · finishReason · 원문 앞부분을 남긴다. 파싱 실패 때만
  원문을 남기던 탓에 10/8 의 빈 초안은 원인을 볼 수 없었다.

```
AI plan draft has days without a visit item attempt=1 emptyDays=[1, 2, 3] of=3 finishReason=stop rawHead={"days":[...
```

## 반려견 특성 주입

- 워커가 잡의 memberId + petIds 로 auth-service 내부 API 를 불러 특성(크기·체중·나이·활동량·
  더위/추위/소음 민감·사회성·산책 선호)을 프롬프트의 "함께 여행하는 반려견" 절로 싣는다.
  사회성은 **낮음일 때만** 제약("몰리는 장소를 피할 것")으로 싣는다 - 보통/높음은 제약이 아니다 (#380). 이 절이
  없으면 시스템 프롬프트의 "반려견 기준" 규칙이 빈 구호가 된다.
- 나이는 생년월 원문이 아니라 **파생값(개월 수)** 으로 받아 "7년 4개월" 표기로 싣는다 (#367) —
  이 값이 없으면 12살 노령견에게 종일 걷는 일정이 나간다. 모르면 줄 자체를 생략한다.
- 여러 마리면 마리별 절(`반려견 1`, `반려견 2`…)을 싣는다. 대괄호를 두지 않는 이유는 위
  "내부 표기가 새지 않게 한다" 항목이다 — 이 이름이 준비물 이유에 그대로 인용된다. 반려견 지정이 없으면
  대표 반려견 특성(`/internal/v1/pets/representative/condition`)을 쓴다.

### 다견 규칙은 쓰임마다 반대다 (필수)

같은 반려견 절을 일정 생성과 준비물이 함께 쓰지만, **여러 마리일 때 덧붙이는 규칙이 정반대**다.
그래서 규칙 문장을 절 안에 박지 않고 호출부가 넘긴다(`PLAN_MULTI_PET_RULE` /
`PACKING_MULTI_PET_RULE`).

| | 규칙 | 왜 |
|---|---|---|
| 일정 생성 | **가장 제약이 큰 아이**가 기준 (가장 큰 크기·가장 무거운 체중) | 한 마리라도 못 들어가면 그 장소는 갈 수 없다 |
| 준비물 | **합집합** — 한 아이에게만 필요한 물건도 넣는다 | 점수를 매기는 일이 아니라 목록을 만드는 일이다. 접으면 다른 아이 물건이 빠진다 |

준비물이 합집합인 대신 **어느 아이 때문인지 이유에 밝히게** 한다 — 항목마다 근거를 붙이는 것이
이 기능의 핵심이라, 합집합으로 만들면서 근거까지 흐려지면 목록 자체가 신뢰를 잃는다.
일자 날씨 판정이 `basisPetId` 로 같은 문제를 푼 것과 같은 방향이다.

준비물의 특성 조회 대상은 `PlanOutline.conditionPetIds()` 가 정한다 — `petIds` 가 있으면 전부,
없으면 대표 한 마리로 접는다(plan-service 가 `petIds` 를 내리기 전에 만들어진 **옛 일정 호환**).
조회는 벌크 한 번이다 (`coding-conventions.md` §9-7).
- 후보 장소 줄에는 입장 크기·체중 제한(allowedPetSize·maxPetWeightKg)을 함께 싣는다 —
  "입장 조건이 맞는 후보만 고를 것" 지시의 판정 근거다.
- 조회 실패·프로필 부재는 특성 없이 진행하되 경고를 남긴다 — auth 장애가 일정 생성 불가로
  번지면 안 된다. 그 경우 반려견 절 자체를 생략한다(없는 값을 지어 적지 않는다).

## 준비물 목록은 서버 규칙으로 짠다 (필수, #976)

모델 출력이 텍스트 정리만 거쳐 그대로 저장되던 자리다. dev 실측(3일, 말티즈 소형견 · 더위 민감,
17~24℃, 강수 10~20%)에서 존재하지 않는 `방충망 장갑`, 강수 10~20% 를 근거로 든 `소형견용 우산`,
배변봉투 자리에 `휴대용 화장지`, 이유가 따로 노는 `통풍 좋은 가벼운 재킷`, 24℃ 의 "더위에 민감한
말티즈" 수분 보충이 나왔다. 프롬프트 규칙 8~11 이 1차 방어고, `PackingListRules` 가 목록을 짠다.

| 겹 | 누가 정하나 | 내용 |
|---|---|---|
| 기본 품목 | **서버** | 배변봉투 · 휴대용 물그릇 · 리드줄 · 하네스 · 사료와 간식. 언제나 넣고 이유는 서버 문장이다. 모델이 같은 종류(`화장지` · `물병` · `목줄` 등)를 적으면 버린다 |
| 날씨 품목 | **서버, 예보 수치로** | 반려견 우비 · 쿨매트 · 반려견 옷. 문턱을 넘는 날이 있을 때만 넣고 그날 수치를 이유로 쓴다(`2일차 강수확률이 70%예요.`). 모델이 적은 같은 종류는 조건과 무관하게 버린다. 우산은 받지 않는다 |
| 조건부 품목 | 모델, **목록 안에서만** | 실제로 파는 반려견 여행 용품 낱말(물티슈 · 이동장 · 담요 · 진드기 기피제 · 인식표 · 구명조끼 …)에 걸리는 것만 받는다. 이유의 비 · 더위 · 추위 문장이 예보와 어긋나면 그 문장을 걷고, 걷은 뒤 남는 이유가 없으면 품목을 버린다. 처음부터 이유가 없던 품목은 남긴다 |

**순서는 이 여행에만 해당하는 것부터다** — 날씨 품목, 모델 품목, 기본 품목. 일정 상세의 준비물 요약
카드가 앞 5개만 보여 주므로(`PACKING_PREVIEW_MAX_ITEMS`), 기본 품목을 앞에 두면 모든 여행에서 그 5줄이 똑같다.

**문턱.** 강수확률 60% 이상(또는 강수형태가 `없음` · `정보 없음` 이 아닌 날)과 최고기온 31℃ 이상은 일정
프롬프트의 배치 지시와 같은 값이다. 최저기온 5℃ 이하, 더위 민감 28℃, 추위 민감 10℃ 는 준비물에서 새로
정했다. 반려견 특성은 **문턱을 낮출 뿐** 품목을 부르지 않는다 — 17~24℃ 의 더위 민감 말티즈에게 쿨매트는
필요 없다. 여러 마리면 한 마리라도 민감하면 낮춘다(다견 합집합 규칙과 같은 방향).

**낱말이 아니라 서술을 잡는다.** 비 문장을 `비가` 로 잡으면 "준비가 필요해요" 가 걸린다 — `비가 오` ·
`강수확률 N%` 처럼 서술로 잡는다. 날씨 품목 낱말도 같다. `방수` · `아이스` 는 뒤에 입을 것 · 식힐 것이 올 때만
날씨 품목이고(방수 배변패드 · 아이스박스는 다른 물건), 구명조끼 · 라이프재킷은 `조끼` · `재킷` 에 걸려도 옷이 아니다.

**목록 밖 품목은 버린다.** 좋은 물건이 목록에 없어 빠지는 것이 존재하지 않는 물건이 나가는 것보다 덜
나쁘다 — 사용자는 화면에서 직접 더할 수 있다. 목록에 없는 물건이 자주 버려지면(경고 로그
`LLM packing list corrected by server rules`) 목록을 늘린다.

**전망이 없으면 날씨 품목을 넣지 않는다.** 모르는 날씨를 지어내지 않는다 — 반려견 특성과 같은 관용 원칙이다.
