## S1. 계약

### `GET /api/v1/members/me` — 내 정보

```ts
type MemberMyInfo = {
  memberId: string
  email: string
  name: string
  nickname: string
  profileImageUrl: string | null
  role: CodeNameDescriptionMetadata
  /** 일반 계정이면 null. 'KAKAO' | 'NAVER' */
  provider: string | null
  hasPassword: boolean
}
```

### `PATCH /api/v1/members/me` — 내 정보 수정

**바꿀 수 있는 것은 `nickname` 하나뿐이다.** `MemberMyInfoUpdateRequest` 에 다른 필드가 없다.

| 필드       | 필수 | 제약       |
| ---------- | ---- | ---------- |
| `nickname` | ✅   | 1~**10자** |

> **프로필 이미지는 이 DTO 로 다루지 않는다.** DTO 주석이 이유를 적어 뒀다 — 임의 URL 을
> 회원 정보에 넣을 수 있으면 외부 이미지를 우리 서비스인 것처럼 노출시킬 수 있다.
> 업로드/삭제 전용 API 로만 바꾼다. **화면도 URL 입력란을 만들지 않는다.**

### 프로필 이미지

| 엔드포인트                         | 본문                                          | 응답                                   |
| ---------------------------------- | --------------------------------------------- | -------------------------------------- |
| `POST /members/me/profile-image`   | **`multipart/form-data`**, 파트명 `imageFile` | `{ profileImageKey, profileImageUrl }` |
| `DELETE /members/me/profile-image` | —                                             | `MemberMyInfoResponse` (전체)          |

- **jpg / png / gif / webp 만 허용**하고, 확장자가 아니라 **파일 내용(매직 바이트)으로
  판정**한다 (컨트롤러 설명). 화면의 `accept` 는 편의일 뿐 검증이 아니다.
- 기존 이미지가 있으면 교체하고 이전 파일은 서버가 지운다.
- **업로드 응답과 삭제 응답의 모양이 다르다.** 업로드는 `{key, url}` 만, 삭제는 회원 정보
  전체다. 업로드 후에는 캐시의 `profileImageUrl` 만 갈아끼우고, 삭제 후에는 응답으로 통째로 바꾼다.

### 비밀번호 — **세 가지 동작이 계정 상태로 갈린다**

| 엔드포인트                        | 언제 쓰나              | 본문                               |
| --------------------------------- | ---------------------- | ---------------------------------- |
| `POST /members/me/password`       | 비밀번호 **변경**      | `{ currentPassword, newPassword }` |
| `POST /members/me/password/setup` | 비밀번호 **최초 설정** | `{ newPassword }`                  |
| `DELETE /members/me/password`     | **소셜 전용으로 전환** | —                                  |

새 비밀번호 제약(세 API 공통): **8~20자, 영문자·숫자·특수문자 각 1개 이상, 공백 불가.**
정규식은 `^(?=.*[A-Za-z])(?=.*\d)(?=.*[!@#$%^&*()\-_=+\[\]{};:'",.<>/?\\|])\S+$` 다 —
**회원가입 폼과 같은 규칙이라 기존 검증을 재사용한다.**

### `POST /api/v1/members/me/withdraw` — 탈퇴

본문 없음. 응답 `Void`. **비밀번호 재확인을 받지 않는다** — 서버가 요구하지 않는다.

## S2. 계정 상태 3종 — `provider` × `hasPassword`

`MemberMyInfoResponse.hasPassword` 의 스키마 설명이 조합을 못박아 뒀다.

| `provider` | `hasPassword` | 상태          | 비밀번호 화면에서 할 수 있는 것              |
| ---------- | ------------- | ------------- | -------------------------------------------- |
| `null`     | `true`        | **일반 계정** | 변경                                         |
| `KAKAO` 등 | `false`       | **소셜 전용** | **최초 설정** (이메일 로그인 수단 추가)      |
| `KAKAO` 등 | `true`        | **연결됨**    | 변경 · **소셜 전용으로 전환**(비밀번호 제거) |

- **`provider === null && hasPassword === false` 는 나올 수 없다.** 나오면 서버 결함이다 —
  화면은 이 경우 아무 동작도 제시하지 않고 안내 문구만 낸다. 빈 화면을 만들지 않는다.
- **소셜 전용 전환은 되돌릴 수 있다** (다시 최초 설정). 그래도 파괴적 변경이라 확인을 받는다.
- 이 세 상태를 **한 화면(`/mypage/password`)이 분기로 처리한다.** 화면을 셋으로 쪼개면
  같은 폼이 세 벌이 된다.

## S3. multipart — **현재 BFF 로는 통과하지 못한다**

`app/api/bff/[...path]/route.ts` 는 요청 본문을 `await request.text()` 로 읽고
`Content-Type: application/json` 을 붙여 게이트웨이로 보낸다. **`multipart/form-data` 는
boundary 가 헤더에 있고 본문이 바이너리라 이 경로로 보내면 깨진다.**

→ **선행 공통 작업으로 BFF 에 multipart 통과 경로를 만든다** (이 저장소에서 파일 업로드가
처음이다). 요건:

- 요청 `Content-Type` 이 `multipart/form-data` 로 시작하면 **본문을 `ReadableStream`(또는
  `Blob`)으로 그대로 넘기고 원본 `Content-Type` 헤더를 보존**한다 (boundary 포함)
- 그 경로에서도 Authorization 주입과 401 → reissue 재시도는 그대로 지켜야 한다.
  **재시도는 본문을 두 번 읽어야 하므로 스트림을 그대로 흘리면 안 된다** — 파일 업로드는
  `ArrayBuffer` 로 한 번 읽어 버퍼에 들고 재시도에 재사용한다 (파일 크기 상한이 전제다)
- 응답은 지금처럼 JSON 이라 응답 경로는 손대지 않는다

> **파일 크기 상한이 계약에 없다.** 서버의 `spring.servlet.multipart.max-file-size` 를 확인해
> 화면에도 같은 값을 걸어야 한다 — 확인 전까지는 화면에서 상한을 말하지 않는다 (S5-1).
