## S1. 계약

### `GET /api/v1/members/me` — 내 정보

```ts
type MemberMyInfo = {
  memberId: string
  email: string
  name: string
  nickname: string
  profileImageUrl: string | null
  role: CodeNameDescriptionMetadata
  /** 일반 계정이면 null. 'KAKAO' | 'NAVER' */
  provider: string | null
  hasPassword: boolean
}
```

### `PATCH /api/v1/members/me` — 내 정보 수정

**바꿀 수 있는 것은 `nickname` 하나뿐이다.** `MemberMyInfoUpdateRequest` 에 다른 필드가 없다.

| 필드       | 필수 | 제약       |
| ---------- | ---- | ---------- |
| `nickname` | ✅   | 1~**10자** |

> **프로필 이미지는 이 DTO 로 다루지 않는다.** DTO 주석이 이유를 적어 뒀다 — 임의 URL 을
> 회원 정보에 넣을 수 있으면 외부 이미지를 우리 서비스인 것처럼 노출시킬 수 있다.
> 업로드/삭제 전용 API 로만 바꾼다. **화면도 URL 입력란을 만들지 않는다.**

### 프로필 이미지

| 엔드포인트                         | 본문                                          | 응답                                   |
| ---------------------------------- | --------------------------------------------- | -------------------------------------- |
| `POST /members/me/profile-image`   | **`multipart/form-data`**, 파트명 `imageFile` | `{ profileImageKey, profileImageUrl }` |
| `DELETE /members/me/profile-image` | —                                             | `MemberMyInfoResponse` (전체)          |

- **jpg / png / gif / webp 만 허용**하고, 확장자가 아니라 **파일 내용(매직 바이트)으로
  판정**한다 (컨트롤러 설명). 화면의 `accept` 는 편의일 뿐 검증이 아니다.
- 기존 이미지가 있으면 교체하고 이전 파일은 서버가 지운다.
- **업로드 응답과 삭제 응답의 모양이 다르다.** 업로드는 `{key, url}` 만, 삭제는 회원 정보
  전체다. 업로드 후에는 캐시의 `profileImageUrl` 만 갈아끼우고, 삭제 후에는 응답으로 통째로 바꾼다.

### 비밀번호 — **세 가지 동작이 계정 상태로 갈린다**

| 엔드포인트                        | 언제 쓰나              | 본문                               |
| --------------------------------- | ---------------------- | ---------------------------------- |
| `POST /members/me/password`       | 비밀번호 **변경**      | `{ currentPassword, newPassword }` |
| `POST /members/me/password/setup` | 비밀번호 **최초 설정** | `{ newPassword }`                  |
| `DELETE /members/me/password`     | **소셜 전용으로 전환** | —                                  |

새 비밀번호 제약(세 API 공통): **8~20자, 영문자·숫자·특수문자 각 1개 이상, 공백 불가.**
정규식은 `^(?=.*[A-Za-z])(?=.*\d)(?=.*[!@#$%^&*()\-_=+\[\]{};:'",.<>/?\\|])\S+$` 다 —
**회원가입 폼과 같은 규칙이라 기존 검증을 재사용한다.** 정규식 정본은
`src/lib/form/password-pattern.ts` 한 곳이고 회원가입 스키마·mock 이 같은 것을 쓴다.

#### 세 동작 중 둘은 **세션을 끊는다** (2026-08-31 소스 실측으로 추가)

`MemberWebController` 가 **변경**과 **소셜 전용 전환** 응답에 `clearRefreshCookie()` 를
싣는다. 재발급이 막히므로 access token 만료와 함께 로그아웃된다.

| 동작           | refresh 쿠키 | 화면이 할 일                               |
| -------------- | ------------ | ------------------------------------------ |
| 변경           | **삭제**     | 세션 정리 + `/login` 이동 (재로그인 안내)  |
| 최초 설정      | 유지         | `memberKeys.me()` invalidate — 여기 머문다 |
| 소셜 전용 전환 | **삭제**     | 세션 정리 + `/login` 이동                  |

invalidate 로만 끝내면 화면은 로그인된 것처럼 남아 있다가 **다음 조작에서야** 401 을
맞는다. `/login` 안내는 자유 텍스트가 아니라 **플래그 파라미터**(`?reauth=…`)로 넘긴다 —
쿼리에 문장을 실으면 링크를 만든 누구나 로그인 화면에 임의 문구를 띄울 수 있다
(`SignupDoneNotice` 의 `signedUp=1` 과 같은 규약).

### `POST /api/v1/members/me/withdraw` — 탈퇴

본문 없음. 응답 `Void`. **비밀번호 재확인을 받지 않는다** — 서버가 요구하지 않는다.
탈퇴도 **refresh 쿠키를 지운다** — 위 표와 같은 뒤처리가 필요하다.

## S2. 계정 상태 3종 — `provider` × `hasPassword`

`MemberMyInfoResponse.hasPassword` 의 스키마 설명이 조합을 못박아 뒀다.

| `provider` | `hasPassword` | 상태          | 비밀번호 화면에서 할 수 있는 것              |
| ---------- | ------------- | ------------- | -------------------------------------------- |
| `null`     | `true`        | **일반 계정** | 변경                                         |
| `KAKAO` 등 | `false`       | **소셜 전용** | **최초 설정** (이메일 로그인 수단 추가)      |
| `KAKAO` 등 | `true`        | **연결됨**    | 변경 · **소셜 전용으로 전환**(비밀번호 제거) |

- **`provider === null && hasPassword === false` 는 나올 수 없다.** 나오면 서버 결함이다 —
  화면은 이 경우 아무 동작도 제시하지 않고 안내 문구만 낸다. 빈 화면을 만들지 않는다.
- **소셜 전용 전환은 되돌릴 수 있다** (다시 최초 설정). 그래도 파괴적 변경이라 확인을 받는다.
- 이 세 상태를 **한 화면(`/mypage/password`)이 분기로 처리한다.** 화면을 셋으로 쪼개면
  같은 폼이 세 벌이 된다.

## S3. multipart — **BFF 통과 경로가 생겼다** (#79 완료)

원래 `app/api/bff/[...path]/route.ts` 는 본문을 `await request.text()` 로 읽고
`Content-Type: application/json` 을 붙여 보냈다. multipart 는 boundary 가 헤더에 있고 본문이
바이너리라 그 경로로는 깨진다. [#79](https://github.com/8llow8llowMe/hondigagae/issues/79) 에서
본문 처리를 `src/lib/api/forwarded-body.ts` 로 빼고 통과 경로를 만들었다.

- 원본 `Content-Type` 을 **그대로 보존**한다 (boundary 포함)
- 본문을 `ArrayBuffer` 로 읽어 **버퍼로 들고 있는다** — 401 → reissue 재시도가 같은 본문을
  다시 보내야 하므로 스트림은 쓸 수 없다
- Authorization 주입과 401 재시도는 JSON 경로와 동일하다
- 응답은 JSON 그대로라 응답 경로는 손대지 않았다

규칙 정본은 `docs/architecture-guide.md` §5. **화면은 `<input type="file">` 로 만든 `FormData`
를 파트명 `imageFile` 로 그대로 보내면 된다** — `Content-Type` 을 직접 지정하지 않는다
(지정하면 boundary 가 빠져 깨진다).

**mock 도 이 경로를 받는다.** `src/lib/api/mock/member-data.ts` 가 `POST
/members/me/profile-image` 를 처리하고 **파일을 저장하지 않고 고정 URL 을 돌려준다**
(바이너리 본문은 mock 계층에 `null` 로 들어온다).

> **허용 형식은 jpg · png · gif · webp** 이고 서버가 **매직 바이트로 판정**한다
> (`ImageFileType`). 화면의 `accept` 는 편의일 뿐 검증이 아니다. 실패 코드는
> `STORAGE_001`(파일 없음) · `STORAGE_002`(크기 초과) · `STORAGE_003`(형식) — 셋 다 400 이라
> `resultMessage` 를 그대로 노출한다.

> **업로드 상한은 5MB 다** (S5-1 해소). 서버가 두 겹으로 막는다 —
> `spring.servlet.multipart.max-file-size: 5MB` 와 `infra.storage.max-file-bytes: 5242880`.
> **화면도 업로드 전에 같은 값으로 검사한다** — BFF 가 본문을 통째로 메모리에 올리므로,
> 화면 검사가 서버 상한을 넘는 파일이 거기까지 가지 않게 막는 첫 방어선이다.

> **프로필 사진은 `next/image` 가 아니라 `<img>` 로 그린다** (#83 결정).
> 공개 주소가 `MINIO_PUBLIC_URL` 환경변수라 **환경마다 다르다** — local 은
> `http://localhost:9000` / 버킷 `hondigagae-local` 이고 dev·prod 는 소스에 실값이 없다.
> `remote-host.ts` 는 **고정 목록**이라, 여기에 등록하는 방식은 배포 환경이 바뀔 때마다
> `next.config.ts` 를 고쳐야 하고 등록되지 않은 호스트에서는 **아바타가 조용히 사라진다.**
> 아바타는 64px 고정이라 최적화 이득도 작다. 그래서 허용 목록에 넣지 않고 `<img>` 를 쓴다 —
> `remote-host.ts` 는 TourAPI 장소 이미지 전용으로 남는다.
