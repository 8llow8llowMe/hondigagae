# 홈 · 전역 내비게이션 공통 명세

> 작성자 / 작성일: seonghoho / 2026-08-27
> 관련 백엔드 서비스: `auth-service`(member·pet) · `tour-service`(place·insight) · `plan-service`(plan)
> 계약 확인 근거: **Swagger 미호출.** 게이트웨이 미기동. 컨트롤러 8개 **소스 실측**
> (origin/develop `d0d7c7d`). 기동 시 `/fe-api-check` 로 일괄 대조한다.
> 시각 컨셉: **데이터 신뢰형** (`DESIGN.md` §1). 토큰은 2차 세트 기준이다.

## S0. 개요

- **한 줄 정의**: 오늘 내 반려견 기준으로 무엇이 좋은지 데이터로 답하고, 나머지 화면으로 보낸다.
- **사용자가 달성하려는 것**: "지금 나가도 되나 / 어디로 가면 되나" 를 근거와 함께 확인.
- **왜 지금 만드나**: 화면 7개가 이미 있는데 **서로 연결돼 있지 않다.** `/` 에 `<a>` 가 0개고
  `nav`/`header` 랜드마크가 문서 전체에 0개다 (이슈 #15). 만든 화면에 도달할 방법이 없다.
- **범위에 포함**
  - `/` 홈 — 오늘 판정, 적합도 순 장소, 다가오는 일정, 긴급 시설 진입
  - 전역 nav — 데스크톱 헤더, 모바일 헤더 + 하단 탭바, 반려견 스위처
- **범위에서 제외**
  - 지도 (이슈 #14 — 카카오 앱 키 미발급)
  - 검색 입력 (장소 화면 소관)
  - 알림 센터 — **백엔드에 알림 API 가 없다**

## S1. 화면 목록

| 화면     | 경로 | 인증                 | 상태 |
| -------- | ---- | -------------------- | ---- |
| 홈       | `/`  | 불필요 (내용이 갈림) | 기획 |
| 전역 nav | 전역 | —                    | 기획 |

**홈은 보호 경로가 아니다.** 미로그인도 열리고, 로그인 여부로 **내용이 갈린다** (S4-2).
`proxy.ts` `PROTECTED_PATHS` 에 `/` 를 넣지 않는다 — 넣으면 첫 방문자가 로그인 화면부터 본다.

## S2. 사용 API

| #   | METHOD 경로                         | 용도               | 인증   | 홈에서 쓰는 곳           |
| --- | ----------------------------------- | ------------------ | ------ | ------------------------ |
| 1   | `GET /members/me/pets`              | 반려견 목록·스위처 | 필요   | 헤더 스위처, 판정 기준   |
| 2   | `GET /places/{placeId}/walk-safety` | 오늘 산책 판정     | 불필요 | 히어로 카드              |
| 3   | `GET /places/{placeId}/suitability` | 장소 적합도        | 불필요 | 적합도 순 카드           |
| 4   | `GET /plans`                        | 다가오는 일정      | 필요   | 일정 카드 (커서 1페이지) |
| 5   | `GET /plans/{planId}/weather`       | 일정 날씨 브리핑   | 필요   | 일정 카드의 일자별 요약  |
| 6   | `GET /places`                       | 장소 목록          | 불필요 | 적합도 대상 후보         |

- **Swagger 확인 여부**: 미확인 (사유는 문서 상단).
- **미구현 API**: 알림, 홈 요약(S5-1), 목록 단위 적합도(S5-2).

### S2-1. 홈 전용 API 가 없다 — 이 명세의 최대 제약

적합도(#3)와 산책 위험도(#2)는 **둘 다 장소별 엔드포인트**다.

```text
GET /places/{placeId}/walk-safety     ← placeId 가 필수다
GET /places/{placeId}/suitability     ← placeId 가 필수다
```

홈에는 "이 장소" 가 없다. 그래서 **기준 장소를 FE 가 정해야 한다.** 결정은 S5-1.

그리고 적합도 순 목록을 만들려면 **장소마다 #3 을 호출**해야 한다. 6장이면 6회다. 결정은 S5-2.

## S3. 데이터 모델

홈은 새 타입을 만들지 않는다. 기존 도메인 타입을 조합한다.

| 출처                       | 타입             | 홈이 쓰는 필드                                                                                             |
| -------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `types/pet.ts`             | `Pet`            | `name` · `sizeType.name` · `heatSensitive` · `coldSensitive`                                               |
| `WalkSafetyResponse`       | (신규 타입 필요) | `walkSafetyLevel` · `reasons[]` · `heatIndexCelsius` · `estimatedPavementCelsius` · `saferWindowStart/End` |
| `PlaceSuitabilityResponse` | (신규 타입 필요) | `score` · `suitabilityLevel` · `reasons[]` · `weather` · `congestion` · `alternativePlaces[]`              |
| `PlanWeatherResponse`      | (신규 타입 필요) | `title` · `startDate` · `endDate` · `dailyBriefings[]`                                                     |

**`src/types/insight.ts` · `src/types/plan.ts` 를 신설해야 한다.** 이 명세의 구현 이슈 범위다.

### S3-1. 등급 metadata 는 `ScoreMetricMetadata` 다

적합도·산책 위험도의 등급은 `EnumMetadata`(`code`/`name`/`description`)가 아니라
**`ScoreMetricMetadata`** 다. `scoreDescription` 같은 필드가 더 붙을 수 있으므로
`src/types/api.ts` 의 `EnumMetadata` 를 그대로 재사용하지 말고 **실측 후 별도 타입으로 둔다.**

### S3-2. 기준 시점이 세 가지로 섞인다

| API              | 기준            | 필드               |
| ---------------- | --------------- | ------------------ |
| 산책 위험도      | **시각**        | `targetDateTime`   |
| 적합도           | **일자**        | `targetDate`       |
| 일정 날씨 브리핑 | **일자별 배열** | `dailyBriefings[]` |

**한 화면에 나란히 두면 사용자가 "지금 기준인가 오늘 기준인가" 를 혼동한다.**
그래서 홈은 각 카드에 기준을 명시한다 — 히어로에 `14:00 기준`, 적합도 카드에 `오늘`.

### S3-3. null 이 매우 많다

| 필드                   | null / 빈 값이 되는 조건      | 화면 처리          |
| ---------------------- | ----------------------------- | ------------------ |
| `weather`              | 예보 범위 밖                  | 섹션 숨김          |
| `congestion.level`     | 연결 데이터 없음 → `UNKNOWN`  | "혼잡도 정보 없음" |
| `alternativePlaces`    | 비 예보가 아니면 빈 배열      | 섹션 숨김          |
| `saferWindowStart/End` | 같은 날 안에 안전 구간이 없음 | 줄 숨김            |
| `reasons[].scoreDelta` | `0` = 정보성 (감점이 아님)    | 지표 바 색을 중립  |

**숨기면 화면이 매번 다른 모양이 된다.** 그래서 홈은 **최소 골격**을 정한다 (S4-1).

## S4. 상태 / 에러

### S4-1. 홈의 최소 골격

null 이 많아도 홈이 무너지지 않게 **항상 존재하는 것**을 정한다.

| 영역          | 항상 있나 | 없을 때                                            |
| ------------- | --------- | -------------------------------------------------- |
| 전역 nav      | **항상**  | —                                                  |
| 오늘 판정     | 조건부    | 기준 장소가 없으면 **섹션 자체를 렌더하지 않는다** |
| 적합도 순     | **항상**  | 0건이면 `EmptyState` + 장소 찾기 진입              |
| 다가오는 일정 | 조건부    | 일정이 없으면 **일정 만들기 유도 카드**로 대체     |
| 긴급 시설 바  | **항상**  | —                                                  |

즉 **최악의 경우에도 nav + 적합도 영역 + 긴급 바**는 남는다. 빈 화면이 되지 않는다.

### S4-2. 로그인 여부로 갈리는 것

| 영역            | 미로그인                                     | 로그인                 |
| --------------- | -------------------------------------------- | ---------------------- |
| 헤더 (데스크톱) | 로그인·회원가입 버튼. **보호 메뉴 숨김**     | 반려견 스위처 + 프로필 |
| 탭바 (모바일)   | **탭 4개 유지.** 누르면 `returnTo` 로 로그인 | 그대로 동작            |
| 오늘 판정       | 반려견 기준이 없어 **일반 날씨 판정**으로    | 선택된 반려견 기준     |
| 적합도 순       | 반려견 기준 없는 목록                        | 반려견 기준 정렬       |
| 다가오는 일정   | **섹션 숨김**                                | 다음 일정              |

**데스크톱은 메뉴를 감추고 모바일은 탭을 유지한다** — 규칙이 다른 이유는 전역nav-세부명세 D4.

### S4-3. 네 상태

| 상태            | 컴포넌트     | 재시도   | 문구                                            |
| --------------- | ------------ | -------- | ----------------------------------------------- |
| loading         | `Skeleton`   | —        | —                                               |
| 적합도 0건      | `EmptyState` | **없음** | "표시할 장소가 없습니다" / "장소를 찾아보세요." |
| 5xx (섹션 단위) | `ErrorState` | **있음** | `common.temporaryErrorTitle` 재사용             |
| nullable        | 숨김         | —        | S3-3                                            |

**섹션 단위로 실패한다.** 적합도 조회가 죽어도 일정 카드와 nav 는 살아 있어야 한다.
홈 전체를 `ErrorState` 로 덮지 않는다 — 홈은 진입점이고, 진입점이 죽으면 아무 데도 갈 수 없다.

- 반려견 이름이 들어가는 문구는 `withObjectParticle()` / `withSubjectParticle()` 을 쓴다
  (`src/lib/text/korean.ts`). "몽실이에게" 는 조사가 고정이라 안전하지만,

- **권역 표의 온도에는 `최고` 라벨을 붙인다** (#206). `maxTemperature` 인데 숫자만 두면
  무슨 온도인지 알 수 없다. `minTemperature` 와 값이 같은 날이 많아 드러나지 않았을 뿐이다.
  낱말을 줄여 `최고` 만 쓴다 — 375px 에서 `권역 · 온도 · 강수 · 점수` 네 값이 한 줄에
  들어가야 한다 (실측 확인).

## S5. 미결 사항

### S5-1. 오늘 판정의 기준 장소 — **결정 필요**

- **선택지 A (추천)**: 최근 본 장소 (localStorage 에 `placeId` 1건)
- 선택지 B: 다가오는 일정의 첫 항목 장소
- 선택지 C: BE 에 홈 요약 API 요청
- **A 의 근거**: 왕복이 1회고, 사용자가 방금 본 장소라 맥락이 있다. 화면에 `{장소명} 기준` 을
  명시하면 오해가 없다. **`localStorage` 에 토큰이 아닌 값을 두는 것은 lint 로 막혀 있지 않다** —
  확인 필요 (`auth-guide.md` 는 토큰만 금지한다).
- **A 의 약점**: 첫 방문자에게는 기준이 없다 → 그때는 **섹션을 렌더하지 않는다** (S4-1).
- **B 의 약점**: 일정이 없는 사용자가 다수다. 그리고 일정 조회가 선행돼 왕복이 2회가 된다.
- **되돌리는 비용**: 낮다. 기준 장소를 고르는 함수 하나(`resolveBasisPlaceId()`)를 갈아끼운다.

### S5-2. 적합도 순 목록의 N+1 — **결정 필요**

목록 6장이면 `GET /places/{id}/suitability` 를 6회 호출한다.

- **선택지 A (1차 구현)**: 상위 N개(**N=3**)만 호출한다. 홈은 요약 화면이므로 3장이 적당하다.
- 선택지 B: BE 에 목록 단위 적합도 또는 `sort=suitability` 파라미터 요청
- **A 의 근거**: 3회는 병렬로 감당 가능하고, BE 요청 없이 지금 만들 수 있다.
- **A 의 약점**: **"적합도 순" 이라고 말할 수 없다.** 3장을 뽑은 뒤 그 3장만 정렬한 것이다.
  → 그래서 문구를 "오늘 맞는 곳" 으로 두고 **"적합도 순" 이라고 쓰지 않는다.**
- **되돌리는 비용**: 낮다. B 가 생기면 호출부만 바꾼다.

### S5-3. 24시간 병원 수를 하드코딩할지 — **해소됐다** (#206)

~~지금은 "3곳뿐" 을 문구에 박는다.~~ **개수를 단정하지 않는 문구로 바꿨다.**

실제 수는 `open24Only=true` 조회로만 알 수 있고 홈에서 그 왕복을 추가할 가치는 여전히
낮다. 그런데 "데이터가 바뀌면 문구가 거짓이 된다"고 알고 둔 그 일이 실제로 일어났다 —
dev `/emergencies/facilities` 가 0건을 주는 동안 **홈은 "3곳" 이라고 말하고 배너를 눌러
들어간 목록은 "반경 안에 없어요" 라고 말했다.**

배너가 전할 것은 "적으니 미리 확인해 두라" 는 **동기**이고 그것은 수를 세지 않고도 말할 수
있다. 정확한 수는 다음 화면(#13)이 센다 — **왕복을 늘리지 않고 단정을 뺐다.**

## S6. BE 후속 요청

### S6-1. 홈 요약 API

`GET /home/summary` 같은 엔드포인트가 있으면 S5-1·S5-2 가 동시에 해결된다.
지금은 FE 가 기준 장소를 추측하고 N회 호출한다.

### S6-2. 장소 목록에 적합도 정렬

`GET /places?sort=suitability&petId=...` 형태. 홈뿐 아니라 장소 목록 화면도 이걸 원한다.

### S6-3. 24시간 시설 수

`GET /emergencies/facilities` 응답에 `open24Count` 가 있으면 홈 문구를 데이터로 쓸 수 있다.
현재 `totalCount` 는 조회 조건 전체의 건수다.
