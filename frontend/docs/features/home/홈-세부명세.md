## D1. 레이아웃

### 모바일 (375 기준)

한 컬럼. **접힘선(844px) 위에 "오늘 판정" 과 첫 장소 카드가 들어와야 한다.**

```text
헤더 56
─── 접힘선 위 ───
기준 줄        18   (2026-08-27 · 제주시 / 14:00 기준)
오늘 판정 카드 ~300
적합도 카드 1장 ~230
─── 접힘선 844 ───
적합도 카드 2~3장
다가오는 일정
긴급 시설 바
탭바 64 (fixed)
```

`px-4`, 섹션 간 `gap-24`, 카드 내부 `p-16`.

### 데스크톱 (1024+)

**2단**. 좌측 `400px`(`--rail-context`) 고정 sticky + 우측 가변. 열 구분선은 우측 열의
`border-left` 다 (DESIGN.md §7-2).

| 좌측 (400) — 시간축     | 우측 (가변) — 공간축             |
| ----------------------- | -------------------------------- |
| 기준 줄 · 프로필        | 오늘 나가기 좋은 권역 (가로 N칸) |
| 오늘 판정 (산책 위험도) | 오늘 ○○에게 맞는 곳 (전폭 행)    |
| 오늘 산책하기 좋은 시간 | 비 올 때 갈 만한 실내 (조건부)   |
| 주변 동물병원 배너      | 다가오는 일정                    |

**좌측을 고정폭으로 두는 이유**: 판정의 숫자 정렬이 폭에 따라 흔들리면 값 비교가 어렵다.

**좌우를 가르는 기준은 축이다** (DESIGN.md §7-1). 좌측은 "지금 나가도 되나 → 그럼 언제",
우측은 "어느 권역 → 어느 장소 → 비 오면 어느 실내" 다. 권역 비교는 예전에 좌측 골든타임
아래에 있었는데, 좌측이 1277px 로 부풀어 `lg:sticky` 가 가용 높이(936px)를 넘겨 무력화되고
우측은 520px 이 비는 상태가 됐다. 옮긴 뒤 좌 907 / 우 976 이다.

**권역은 2단에서 가로로 편다.** 400px 레일에서 세로로 쌓던 5칸을 1000px 열에 그대로 두면
371px 를 세로로 먹는다 — 가로로 펴서 222px 이다. 칸 수는 `flex-1` 로 나눈다 (개수는 서버가
정하므로 `grid-cols-N` 으로 고정하지 않는다).

### 태블릿 (768~1023)

한 컬럼. 적합도 카드만 2열. `max-width: 720px`.

긴 한국어 실데이터로 확인할 항목:

- `ActivityLevel.LOW.description`("짧은 산책을 선호하며 장시간 활동을 힘들어합니다.") 급 길이의
  `reasons[].description` 이 375px 카드에서 **3줄을 넘기지 않는지**
- 장소명 최대 길이에서 등급 배지가 밀리지 않는지 → 배지를 `flex-shrink: 0`
- `35.0℃` 처럼 소수점이 붙은 값과 `52.4℃` 가 **자릿수 정렬되는지** (`tabular-nums`)

### D2-1. 왜 `MetricBadge` · `MetricValue` 를 공통으로 올리나

**적합도·산책 위험도·혼잡도가 전부 같은 표현을 쓴다.** 그리고 장소 상세·일정 상세에서 같은 배지가
다시 필요하다. `component-guide.md` §9 의 "2곳 이상에서 쓰이면 승격" 을 **선제 적용**한다 —
홈에서만 3곳(판정·적합도·혼잡도)에 쓰인다.

`MetricBadge` 계약:

```text
level: ScoreMetricMetadata   서버 metadata. name 을 그대로 렌더한다
tone:  'high' | 'mid' | 'low' | 'unknown'   code → tone 매핑은 순수 함수
```

**`tone` 을 호출부가 계산해 넘긴다.** 컴포넌트가 `code` 문자열을 해석하면 도메인이 컴포넌트로 샌다.

## D3. 데이터 흐름

```text
/ 진입 (서버) → readSession()
  ├─ 세션 없음 → 프리페치 0회. HomeView 가 공개 데이터만 조회
  └─ 세션 있음 → 병렬 프리페치 (전부 retry: false, 개별 catch)
        ├─ GET /members/me/pets            (nav 와 key 공유)
        ├─ GET /plans (1페이지)
        └─ GET /places (적합도 후보)
     → dehydrate → HydrationBoundary → HomeView (client)
                     ├─ 기준 장소 결정 → GET /places/{id}/walk-safety
                     ├─ 상위 3개 → GET /places/{id}/suitability × 3 (병렬)
                     │    └─ 응답의 congestion · indoorAlternatives 를 그대로 쓴다 (추가 호출 0)
                     ├─ getCurrentPosition()
                     │    ├─ GET /insights/walk-times            (좌표 필수)
                     │    └─ granted 일 때만 → GET /emergencies/facilities   (병원 배너)
                     └─ GET /insights/regional-weather           (좌표 불필요)
```

**혼잡도와 실내 대안은 새 조회가 아니다.** 둘 다 위 적합도 응답의 필드다 — 화면에 없던
것은 데이터가 없어서가 아니라 그리지 않았기 때문이다.

**병원 배너만 조회를 하나 늘린다.** 좌표를 이미 갖고 있어(골든타임용) 새로 물어보지 않고,
`kind === 'fallback'` 이면 아예 부르지 않는다 — 거리를 못 쓰면 보탤 것이 없다.
`staleTime` 은 `/emergency` 화면과 같은 **1분**이다 (`openNow` 가 시각에 따라 바뀐다).

| 항목                   | 내용                                                             |
| ---------------------- | ---------------------------------------------------------------- |
| React Query key        | `homeKeys.walkSafety(placeId)` · `homeKeys.suitability(placeId)` |
| staleTime / gcTime     | **5분 / 30분** — 날씨·혼잡도는 시간 단위로 바뀐다                |
| retry                  | `isRetriable` 기반 1회                                           |
| mutation 후 invalidate | 없음 (홈에 mutation 이 없다)                                     |
| 폴링 여부              | **없음**                                                         |

**`staleTime` 5분은 §7 표에 없는 도메인이다.** 근거를 주석으로 남긴다 —
장소 데이터(5분)와 같은 값을 쓰되 이유가 다르다: 장소는 배치라 안 바뀌고, 인사이트는
**기상 예보 단위가 1시간**이라 5분 재조회는 낭비다. `api-integration-guide.md` §7 표에
`장소 인사이트` 행을 추가해야 한다.

**적합도 3회 호출은 병렬이다.** `useQueries` 를 쓴다. 순차로 하면 3배 느리다.
하나가 실패하면 그 카드만 빠진다 — 나머지는 렌더한다.

## D4. 상호작용

| 트리거                     | 동작                              | 결과                               |
| -------------------------- | --------------------------------- | ---------------------------------- |
| 판정 카드 "판정 근거 보기" | 기준 장소의 상세로 이동           | `/places/{basisPlaceId}`           |
| 적합도 카드 클릭           | 장소 상세로 이동                  | `/places/{placeId}`                |

| "주변 동물병원 찾기"       | 긴급 시설 화면 (미구현 시 비활성) | 이슈 #13 이후 활성                 |
| **반려견 스위처 변경**     | 판정·적합도 **재조회**            | 스켈레톤 없이 이전 값 유지 후 교체 |
| 5xx (섹션)                 | 해당 섹션만 `ErrorState` + 재시도 | 다른 섹션은 그대로                 |

### D4-1. 근거는 접어 두고 펼친다

`reasons[]` 는 **점수 영향이 큰 순서**로 온다. 전부 보이면 카드가 길고, 자르면 근거가 약해진다.

| 위치           | 기본 노출 | 펼침               |
| -------------- | --------- | ------------------ |
| 오늘 판정 카드 | **2개**   | 카드 안에서 펼친다 |
| 적합도 카드    | **2개**   | 카드 안에서 펼친다 |

- 재정렬하지 않는다. 서버 순서가 곧 중요도다
- `scoreDelta` 가 **음수면 감점**, **0이면 정보성**이다. 지표 바 색으로 구분한다 (D5-2)
- 펼침은 `useState` — 한 컴포넌트 트리 안에서 끝난다 (`architecture-guide.md` §10)
- **숫자를 화면에 그대로 노출하지 않는다.** `scoreDelta: -27` 을 "−27점" 으로 보여주면
  점수 산식을 설명해야 한다. 부호는 **색과 위치**로만 전달한다 (D8-2 에 근거)

### D4-1-a. 카드 전부에 있는 문장은 목록 위로 올린다 (#304)

날씨는 **장소별 근거가 아니라 화면의 전제**다. 같은 날 같은 시군구면 세 장소에 똑같이
붙는데, 장소별 근거인 척 반복되면 세 장소의 실제 차이(동반 가능 여부 · 실내/야외)가 같은
문장 아래 묻힌다. 실측(1265×900, 로그인)에서 `풍랑 주의보 발효 중입니다…` 가 좌측 판정
1번 + 카드 3장 = **4번** 서 있었다.

| 항목      | 규칙                                                                       |
| --------- | -------------------------------------------------------------------------- |
| 판정 기준 | 로드된 카드 **전부**에 같은 `description` 이 있는가 (`splitSharedReasons`) |
| 견주는 값 | **`description`.** `code` 가 아니다                                        |
| 카드 1장  | 아무것도 떼지 않는다 — 비교 대상이 없다                                    |
| 뗀 문장   | 적합도 섹션 머리(목록 바로 위)에 **한 번만**                               |
| 노출 폭   | 데스크톱(`md:`)만. 카드 근거 자체가 데스크톱 전용이라 모바일은 그대로다    |

- **근거 코드를 FE 에 나열하지 않는다.** `WEATHER_WARNING_ACTIVE` 같은 코드로 거르면
  서버가 코드를 하나 더 낼 때 조용히 새어 나온다 (`frontend/CLAUDE.md`)
- **자리를 적합도 섹션으로 잡은 이유**: 좌측 판정 섹션은 기준 장소가 없는 첫 방문자에게
  렌더되지 않는다(S5-1). 거기에만 두면 그 사용자는 특보를 어디서도 못 본다
- **목록이 짧아지는 효과는 문장 길이에 달렸다.** 목 데이터 실측에서 행 높이는 96px 썸네일이
  잡고 있어 1265 / 870 에서 `136 · 159 · 137` 그대로였다 — 줄어든 것은 높이가 아니라
  **같은 문장의 반복**(3회 → 1회)이고, 2줄 상한에 밀려 안 보이던 장소별 문장이 드러났다
- **BE 후속 제안**: `reasons[]` 에 `scope`(GLOBAL / PLACE) 가 있으면 FE 가 텍스트 비교로
  추측하지 않아도 된다

### D4-1-b. 1등만 펼치고 나머지는 접는다 (#307)

`DESIGN.md` §1 — _"위계는 크기와 순서로 만든다. **낮은 우선순위는 접는다**"_. 홈은 요약
화면이라 `N=3` 을 골랐지만(공통명세 S5-2) 세 장이 전부 펼쳐져 있어 "요약" 이 아니라
"짧은 목록" 이었다.

| 항목      | 접힌 행 (2번째부터)                                  |
| --------- | ---------------------------------------------------- |
| 남는 것   | 이름 · 메타 줄(주소 · 실내/야외) · 등급 배지 · 점수  |
| 접는 것   | 근거 문장 · 속성 태그 열(동반 가능 · 실내 · 혼잡도)  |
| 썸네일    | 96px → **48px** (모바일 80px 은 그대로)              |
| 점수      | `hero`(28/900) → `row`(22/900). **등급 색은 그대로** |
| 세로 패딩 | `md:py-5` → `md:py-3`                                |

- **썸네일을 함께 줄이지 않으면 접기가 높이를 못 줄인다.** 행 높이를 96px 썸네일이 잡고
  있어, #304 에서 근거 두 줄을 걷어도 실측 136px 그대로였다
- **펼치는 장치를 두지 않는다.** 행 전체가 `<Link>` 라 그 안의 `<button>` 은 무효 HTML 이고,
  근거 전문은 상세 화면이 이미 갖고 있다. 펼침 상태가 없으므로 URL 에 둘지도 문제가 안 된다
- **모바일은 접지 않는다.** 접는 대상(근거 · 태그)이 애초에 `md:` 전용이라 접을 것이 없고,
  390px 에서 썸네일까지 줄이면 목록을 알아보는 유일한 단서를 가장 좁은 화면에서 뺏는다.
  그래서 이 갈래가 바꾸는 클래스는 **전부 `md:` 접두를 가진다**
- **"1등" 이 아니라 "첫 행" 이다.** `pickTopPlaces` 는 목록 앞 세 개를 그대로 집으므로
  (D8-1) 첫 행이 최고점이라는 보장이 없다 — `판단 근거 부족` 행이 첫째로 설 수 있다.
  순서를 바꾸는 것은 이 갈래의 일이 아니다 (BE 가 정렬된 홈 요약을 주면 함께 풀린다)

**실측 (1265 / 870, `MOCK_API=true`)**

|         | 목록 높이 | 행 높이               | 섹션 안 숫자 노드 |
| ------- | --------- | --------------------- | ----------------- |
| 접기 전 | 410       | 136 · 137 · 137       | 8                 |
| 접기 후 | **314**   | 136 · **89** · **89** | **6**             |

390 은 섹션 465px · 행 128 · 107 · 107 · 썸네일 80 으로 **접기 전과 완전히 같다.**

### D4-2. 반려견을 바꿀 때 스켈레톤을 띄우지 않는다

React Query 의 `placeholderData` 로 이전 반려견의 값을 유지하고, 새 값이 오면 교체한다.
스켈레톤으로 되돌리면 화면이 깜빡여 **"바꾼 게 반영됐나" 를 알 수 없다.**
대신 카드에 `aria-busy` 를 걸고 옅은 투명도를 준다.

## D5. 상태별 화면

### D5-1. 섹션별 상태

| 섹션          | loading      | 없음 / 0건                       | 5xx                   |
| ------------- | ------------ | -------------------------------- | --------------------- |
| 오늘 판정     | `Skeleton`   | **섹션 미렌더** (기준 장소 없음) | `ErrorState` + 재시도 |
| 골든타임      | `Skeleton`   | 서버 `forecastCoverage` 문구     | **섹션 미렌더**       |
| 권역 비교     | `Skeleton`   | 예보 없는 권역도 자리를 지킨다   | **섹션 미렌더**       |
| 오늘 맞는 곳  | `Skeleton`×2 | `EmptyState` + 장소 찾기 진입    | `ErrorState` + 재시도 |
| 실내 대안     | —            | **섹션 미렌더** (비 예보 아님)   | 미렌더                |
| 다가오는 일정 | `Skeleton`   | 두 갈래 — 아래 D5-1a             | 섹션 미렌더           |
| 긴급 시설 바  | —            | **항상 있다**                    | —                     |

**홈 전체를 `ErrorState` 로 덮지 않는다.** 진입점이 죽으면 아무 데도 갈 수 없다 (공통명세 S4-3).

#### D5-1a. 다가오는 일정의 빈 상태는 두 갈래다

**`GET /plans` 는 날짜순이 아니다** — 계약이 "일정 아이디 내림차순(**최근 생성순**)" 이라고
적어 두고 있고 날짜 필터 파라미터도 없다. 그래서 응답 첫 건은 "가장 최근에 만든 일정" 이지
"가장 가까운 일정" 이 아니다. **화면이 걸러 정렬한다** (`lib/plan/upcoming.ts`).

- 지난 일정의 기준은 **`endDate`** 다 (`isPastPlan`). 오늘이 여행 중인 날이면 아직 안 지났다.
- 정렬은 `startDate` 오름차순.
- **오늘은 서버가 정한다** — 클라이언트가 `new Date()` 를 부르면 자정을 걸칠 때 서버와
  브라우저가 서로 다른 일정을 고른다 (`todayIso` prop · `lib/date/day.ts` `dayToLocalNoon`).

| 상태                        | 문구                                                       |
| --------------------------- | ---------------------------------------------------------- |
| 일정이 아예 없음            | `noPlanTitle` "아직 일정이 없어요" + 만들기 유도           |
| 일정은 있는데 **전부 지남** | `noUpcomingPlanTitle` "다가오는 일정이 없어요" + 목록 안내 |

**둘을 한 문구로 묶지 않는다.** 넷 다 지난 계정에 "아직 일정이 없어요" 라고 말하면 사용자는
자기 일정이 사라졌다고 읽는다. 다음 행동도 다르다 — 앞은 만들기, 뒤는 목록으로 보내기다.

### D5-2. 지표 바와 색 (`DESIGN.md` 2차 세트)

| 대상                    | tone      | `-500` (바) | `-700` (텍스트) | `-100` (배지 배경) |
| ----------------------- | --------- | ----------- | --------------- | ------------------ |
| 등급 `HIGH`             | `high`    | `#1F7A55`   | `#16563C`       | `#E4F0EA`          |
| 등급 `MEDIUM`           | `mid`     | `#B0761A`   | `#8A5F0F`       | `#FEF4E0`          |
| 등급 `LOW`              | `low`     | `#6B7280`   | `#4B5563`       | `#EEF0F3`          |
| `UNKNOWN` / 정보성 근거 | `unknown` | `#A8AEB8`   | `--fg-muted`    | 없음 (테두리)      |

**주의 3가지**

1. **`--metric-mid-500`(`#B0761A`) 을 12px 텍스트에 쓰지 않는다.** 흰 배경 3.85:1 로 미달이다.
   배지 텍스트는 `-700`(`#8A5F0F`, tint 위 5.16:1)을 쓴다.
2. **큰 지표 숫자에는 `-500` 이 허용된다.** 22px 이상 + weight 900 은 대형 텍스트라 3:1 기준이다.
3. **`UNKNOWN` 에 색을 주지 않는다.** 점선 테두리 + `--fg-muted` 텍스트. 혼잡도가 실제로 이 상태로 온다.

### D5-3. 미로그인 홈

| 영역          | 표현                                                                 |
| ------------- | -------------------------------------------------------------------- |
| 기준 줄       | 날짜 + 지역만 (반려견 이름 없음)                                     |
| 오늘 판정     | 반려견 기준 없이 **날씨·노면만**. "반려견을 등록하면 맞춤 판정" 안내 |
| 오늘 맞는 곳  | 제목을 `suitabilityFallback`("오늘 갈 만한 곳")으로                  |
| 다가오는 일정 | **섹션 미렌더**                                                      |
| 긴급 시설 바  | 그대로                                                               |

**로그인을 강요하지 않는다.** 첫 방문자가 서비스의 가치(데이터 판정)를 먼저 보고 가입하게 한다.

## D6. 접근성

- 섹션 제목은 `<h2>`, 화면 제목은 `<h1>`. `EmptyState`/`ErrorState` 제목도 heading
- **등급을 색만으로 전달하지 않는다** — 색 + 서버 `name` 텍스트 + 지표 바 3중
- 지표 바는 장식이 아니라 정보다. `aria-hidden` 을 붙이지 않고, 배지 전체를 하나의 라벨로 읽히게 한다
- 큰 숫자에 단위를 **텍스트로** 붙인다. `℃` 를 아이콘으로 대체하지 않는다
- "근거 n개 더 보기" 는 `<button aria-expanded>` 다. `<div onClick>` 이 아니다
- 카드 전체를 클릭 대상으로 만들 때 `Link` 로 감싼다. **카드 안에 중첩 링크를 두지 않는다** —
  "근거 더 보기" 버튼이 카드 안에 있으므로 **카드 전체를 링크로 만들지 않고 제목만 링크**로 한다
- `tabular-nums` 는 시각적 정렬이므로 스크린리더에 영향이 없다. 값 자체를 읽을 수 있게 텍스트로 둔다

**D6 의 중첩 링크 결정이 D4 와 충돌한다** — D4 는 "적합도 카드 클릭 → 장소 상세" 라고 적었다.
카드 안에 펼침 버튼이 있으면 카드 전체 링크는 중첩이 된다. **제목만 링크**로 확정한다.

## D8. 미결 사항

### D8-1. "적합도 순" 이라고 쓰지 않는다 — 확정

상위 3개만 적합도를 조회하므로(공통명세 S5-2) **전체 정렬이 아니다.**
제목을 "오늘 {이름}에게 맞는 곳" 으로 두고 정렬을 주장하지 않는다.
`sortNote` 는 "오늘 날씨와 혼잡도 반영" 이다 — 사실이다.

BE 가 목록 단위 적합도를 주면(S6-2) 그때 "적합도 순" 으로 바꾼다.

### D8-2. `scoreDelta` 숫자를 노출하지 않는다 — 확정

- **선택지 A (채택)**: 부호를 **색·위치로만** 전달. 숫자 미노출
- 선택지 B: "−27점" 처럼 표기
- **근거**: 점수 산식이 공개되지 않았다. `-27` 을 보여주면 사용자가 "왜 27인가" 를 묻게 되고
  답할 근거가 없다. 그리고 `description` 이 이미 완성 문장으로 이유를 말한다
- **되돌리는 비용**: 없음. `ReasonList` 에 prop 하나.

### D8-3. 홈에 지도를 두지 않는다 — 확정

카카오 앱 키 미발급(#14)이 직접 이유지만, 키가 생겨도 홈에 지도를 두지 않는다 —
홈은 **판정을 읽는 화면**이고 지도는 **탐색하는 화면**이다. 목적이 다르다.
