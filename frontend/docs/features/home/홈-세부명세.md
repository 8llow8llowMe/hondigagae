#### 모바일 순서를 DOM 순서로 정한다 (#1356)

1024 미만은 두 열을 **좌 → 우로 이어 붙인다.** 그래서 한 컬럼에서 무엇이 첫 화면에 드는지는
**좌측 레일의 길이가 정한다.** 예전에는 좌측 레일이 `[요약 카드 · 소개 카드 · AI · 올레 · 병원
배너]` 라, 그 넷(375 에서 약 330px)과 권역(약 270px)이 장소 추천보다 먼저 섰다.

| 실측 375×812 · 비로그인 · dev API |  예전 | #1356 |
| --------------------------------- | ----: | ----: |
| `오늘 갈 만한 곳` 머리 top        |  1149 |   585 |
| 첫 장소 카드 top                  | ~1200 |   645 |
| 문서 높이                         |  1845 |  1592 |

- **좌측 레일은 요약 카드 한 장이다.** 소개 카드는 우측 열 머리로, 배너 셋은 우측 열의 바로가기
  한 줄(`HomeShortcuts`)로, 권역은 우측 열 끝으로 옮겼다.
- **우측 열 순서가 곧 모바일 순서다**: 여행 배너(1024 이상 사본) → 소개 → 실내(조건부, #1380 —
  D10-5) → 오늘 갈 만한 곳 → 바로가기 → 일정 → 권역.
- **`order` · `display: contents` 로 당기지 않는다.** 보이는 순서와 키보드 · 스크린리더 순서가
  갈린다(WCAG 1.3.2 · 2.4.3, D5-3-a 기각안). DOM 을 모바일 우선순위로 짰다.
- **골든타임 곡선은 모바일에서 접어 둔다** (`WalkTimesSection` `collapseCurveOnMobile`). 시각 한
  줄과 등급 문장이 "언제" 의 답이고 시간대별 표(약 150px)는 펼쳐 보는 근거다. 기준 캡션(`제주시
기준 · …`)은 접혀도 남는다. `md` 이상은 언제나 펼쳐 둔다 — 판정 접힘과 같은 경계다. 산책 코스
  상세는 넘기지 않는다. **펼침 버튼은 제목 줄 오른쪽 `시간대별 ▾` 다** (#1360) — 곡선 위 독립 줄
  (44 + 간격 12)이 첫 장소 카드를 밀었다. `-my-2` 로 줄 높이는 제목 그대로, 누르는 자리는 44.
  접근 이름은 `시간대별 기온 · 노면 보기` 로 보이는 글자로 시작한다(WCAG 2.5.3). #730 이 제목 줄에서
  되돌린 것은 글자 없는 화살표였다 — 여기는 여는 대상이 글자로 서 있다.
- **권역 점수가 전부 같은 날은 모바일에서 칸 레일을 접는다.** 머리 문장(`권역별 차이가 없어요` —
  #1380 전에는 `오늘은 어느 권역이든 좋아요`, D10-7)이 이미 결론이고 칸은 같은 숫자를 늘어놓는다. 견줄 거리가 있는 날(단독 1위 · 일부 동점
  · 추천 없음)은 접지 않는다 — 권역은 서로 견주라고 있는 표다(#530).
- **`오늘 갈 만한 곳` 머리에 모바일 `장소 찾기 ›` 글자 링크를 둔다.** 버튼은 `md` 이상 전용이라
  모바일은 캐러셀 끝 카드까지 밀어야만 목록에 닿았다.
- **실내 대안 줄마다 거리를 잰 기준 장소를 적는다** — `성산일출봉에서 직선 3km`. 홈은 장소
  여러 곳의 대안을 한 목록으로 접어서(`collectIndoorAlternatives`) `직선 3km` 만으로는 어디서
  3km 인지 알 수 없었다. 겹친 대안은 가장 가까운 거리를 남기고, **이름도 그 거리를 실어 온
  응답의 것**을 남긴다(`IndoorAlternative.nearPlaceTitle`).
- **바로가기 한 줄**(`HomeShortcuts`)은 세 칸 모두 아이콘 · 이름 · 짧은 설명줄이다. 병원 칸만
  danger 색이고 설명줄이 상태에 따라 바뀐다(`hospitalShortcutCaption` — 이름 없이 열림 여부와
  거리). 랜드마크를 늘리지 않게 `nav` 가 아니라 이름 붙은 목록(`ul[aria-label=바로가기]`)이다.
- **비로그인 등록 유도 줄은 모바일에서 제목 + 버튼 한 줄이다** (#1360). 설명(`크기·더위 민감도까지
…`)이 375 에서 두 줄로 접혀 줄이 101px 이었다 — 설명은 `md` 이상에만 둔다. 제목과 버튼만으로
  이유와 할 일이 읽힌다.

| 실측 375×812 · 비로그인 · mock (접힘선 748) | #1356 뒤 |   #1360 |
| ------------------------------------------- | -------: | ------: |
| 첫 방문 — 첫 카드 사진                      |  645–821 | 567–743 |
| 재방문 — 첫 카드 전체                       |  561–835 | 483–757 |

- **남은 한계**: 375 재방문에서 카드 아랫단 9px 이 접힘선을 넘는다(390 은 카드 전체 안). 판정 접힘
  줄의 대표 지점 캡션(#636 e2e 가 첫 화면을 요구)과 소개 카드는 건드리지 않았다.

### 데스크톱 (1024+)

**2단**. 좌측 `400px`(`--rail-context`) 고정 sticky + 우측 가변. 열 구분선은 우측 열의
`border-left` 다 (DESIGN.md §7-2).

| 좌측 (400) — 시간축     | 우측 (가변) — 지금 할 일                 |
| ----------------------- | ---------------------------------------- |
|                         | 여행 배너 (#1113, 조건부 · D5-1c)        |
| 프로필                  | 서비스 소개 카드 (#950, 조건부)          |
| 오늘 판정 (산책 위험도) | 비 올 때 갈 만한 실내 (조건부, D10-5)    |
| 오늘 산책하기 좋은 시간 | 오늘 ○○과 갈 만한 곳 (사진 카드 3열)     |
|                         | 바로가기 (AI 일정 · 제주올레 · 동물병원) |
|                         | 다가오는 일정                            |
|                         | 오늘 나가기 좋은 권역 (가로 레일)        |

**#1356 으로 좌측은 요약 카드 한 장이다.** 배너 셋과 소개 카드를 우측으로 옮긴 것은 모바일 순서
때문이지만(위 "모바일 순서를 DOM 순서로"), 데스크톱도 이득이다 — 레일이 짧아져 특보 날에도
`lg:sticky` 예산(가용 936px) 안이다.

**좌측을 고정폭으로 두는 이유**: 판정의 숫자 정렬이 폭에 따라 흔들리면 값 비교가 어렵다.

**좌우를 가르는 기준은 축이다** (DESIGN.md §7-1). 좌측은 "지금 나가도 되나 → 그럼 언제",
우측은 "어느 권역 → 어느 장소 → 비 오면 어느 실내" 다. 권역 비교는 예전에 좌측 골든타임
아래에 있었는데, 좌측이 1277px 로 부풀어 `lg:sticky` 가 가용 높이(936px)를 넘겨 무력화되고
우측은 520px 이 비는 상태가 됐다. 옮긴 뒤 좌 907 / 우 976 이다.

**서비스 소개 카드는 우측 열 머리다** (#963 → #1356). 좌측 첫 카드가 약 720px 이라 그 아래에
서면 1024×768 · 1280×800 첫 화면 밖이었다. 우측 머리라 세 폭 모두 첫 화면 안이다. 1024 미만도
같은 DOM 자리(요약 카드 바로 다음)라 사본이 없다 — D5-3-a.

**권역은 모든 폭에서 가로 레일이다** (#530). 예전에는 1024 미만에서 세로 목록으로 풀었는데,
**권역은 서로 견주라고 있는 표다** — 세로로 세우면 한 번에 한 권역만 보여 비교가 안 되고,
좁은 폭일수록 칸 한 장이 화면의 5분의 1을 먹는다. 칸은 고정 폭(`w-44` 176 / `lg:w-46` 184)
이고 넘치는 몫은 `.scroll-rail` 의 스냅·페이드·화살표가 맡는다. 칸 수를 `grid-cols-N` 으로
고정하지 않는다 — 개수는 서버가 정한다 (dev 실측 5개).

**칸 폭과 숫자 자리는 함께 움직인다.** 좁은 폭은 `w-44` + 숫자 `w-20`, `lg` 는 `w-46` +
`w-22` 다. 한쪽만 내리면 값 줄이 조용히 접힌다 — `src/styles/overlay-and-region-cell.test.ts`
가 산식으로 잡는다.

### D2-1. 왜 `MetricBadge` · `MetricValue` 를 공통으로 올리나

**적합도·산책 위험도·혼잡도가 전부 같은 표현을 쓴다.** 그리고 장소 상세·일정 상세에서 같은 배지가
다시 필요하다. `component-guide.md` §9 의 "2곳 이상에서 쓰이면 승격" 을 **선제 적용**한다 —
홈에서만 3곳(판정·적합도·혼잡도)에 쓰인다.

`MetricBadge` 계약:

```text
level: ScoreMetricMetadata   서버 metadata. name 을 그대로 렌더한다
tone:  'high' | 'mid' | 'low' | 'unknown'   code → tone 매핑은 순수 함수
```

**`tone` 을 호출부가 계산해 넘긴다.** 컴포넌트가 `code` 문자열을 해석하면 도메인이 컴포넌트로 샌다.

```text
                     └─ GET /insights/regional-weather           (좌표 불필요)
```

**골든타임은 서버도 한 번 받는다** (#1142). 홈의 LCP 요소가 골든타임 문장인데, 위치 판정이
끝나야 조회해 FCP 보다 약 5초 늦게 그려졌다. 서버가 **세션과 무관하게** 제주 중심 · 조건 없음
(`WALK_TIMES_PREFETCH_POSITION` · `conditionKey(null)`)으로 받아 같은 key 로 캐시에 넣고,
클라이언트는 위치를 알기 전에도 같은 좌표로 조회한다(`walkTimesQueryPosition`). 비로그인 첫
화면은 그 캐시를 그대로 써 **클라이언트 조회가 0회**다. 허용된 사용자는 위치가 정해지면 현재
위치로 다시 받고, 그동안 기준 줄은 보이는 데이터의 좌표(`제주시 기준`)를 말한다
(`walkTimesBasis`). 반려견 조건이 있는 사용자는 key 가 달라 예전처럼 클라이언트가 받는다.

**혼잡도와 실내 대안은 새 조회가 아니다.** 둘 다 위 추천 항목의 필드다(#1380 전에는 적합도
응답) — 화면에 없던 것은 데이터가 없어서가 아니라 그리지 않았기 때문이다.

**홈은 장소 목록(`GET /places`)을 받지 않는다** (#1380). 그 목록의 쓰임은 적합도를 잴 후보(앞
3곳)와 끝 카드의 전체 수뿐이었다 — 추천 API 가 후보를 고르고 끝 카드는 수를 말하지 않는다 (D10-4).

**바로가기 병원 칸만 조회를 하나 늘린다.** 칸에는 시설 이름 없이 열림 여부와 거리만 싣는다
(`24시간 · 480m` — 칸 폭 약 110px, #1356). 좌표를 이미 갖고 있어(골든타임용) 새로 물어보지 않고,
`kind === 'fallback'` 이면 아예 부르지 않는다 — 거리를 못 쓰면 보탤 것이 없다.
`staleTime` 은 `/emergency` 화면과 같은 **1분**이다 (`openNow` 가 시각에 따라 바뀐다).

| 항목                   | 내용                                                                             |
| ---------------------- | -------------------------------------------------------------------------------- |
| React Query key        | `insightKeys.walkSafety(placeId, 조건)` · `insightKeys.recommendations(조건, 3)` |
| staleTime / gcTime     | **5분 / 30분** — 날씨·혼잡도는 시간 단위로 바뀐다                                |
| retry                  | `isRetriable` 기반 1회                                                           |
| mutation 후 invalidate | 없음 (홈에 mutation 이 없다)                                                     |
| 폴링 여부              | **없음**                                                                         |

**`staleTime` 5분은 §7 표에 없는 도메인이다.** 근거를 주석으로 남긴다 —
장소 데이터(5분)와 같은 값을 쓰되 이유가 다르다: 장소는 배치라 안 바뀌고, 인사이트는
**기상 예보 단위가 1시간**이라 5분 재조회는 낭비다. `api-integration-guide.md` §7 표에
`장소 인사이트` 행을 추가해야 한다.

~~**적합도 3회 호출은 병렬이다.**~~ **#1380 에서 추천 한 번으로 바뀌었다** (D10-1). 예전에는
`useQueries` 로 적합도 3건을 병렬로 불렀고 하나가 실패하면 그 카드만 빠졌다 — 이제는 한 응답이라
카드가 함께 서거나 함께 빠진다(오류 갈래는 D10-1 표).

### D4-1. 근거는 접지 않는다 (#840)

`reasons[]` 는 **점수 영향이 큰 순서**로 온다. 예전에는 앞 2개만 세우고 나머지를 펼침 버튼
뒤에 뒀는데, **접어서 아끼는 것은 문장 한 줄(약 22px)인데 버튼이 44px**(`Button` 의 `md`)이라
근거가 3개인 흔한 경우 순손실이었다.

| 위치           | 노출                                      |
| -------------- | ----------------------------------------- |
| 오늘 판정 카드 | **전부.** 공용 `ReasonList` 를 쓴다       |
| 적합도 카드    | 앞 **2개.** 나머지는 장소 상세에서 읽는다 |

- 재정렬하지 않는다. 서버 순서가 곧 중요도다
- `scoreDelta` 가 **음수면 감점**, **0이면 정보성**이다. 지표 바 색으로 구분한다 (D5-2)
- **펼치는 장치를 두지 않는다.** 적합도 카드가 2개에서 자르는 것은 좁은 행에 세로 공간이
  없어서고, 근거 전문은 장소 상세가 이미 갖고 있다
- 펼침 상태가 없어 `ReasonList` 는 `'use client'` 가 아니다 — 서버 컴포넌트에서도 쓴다
- **숫자를 화면에 그대로 노출하지 않는다.** `scoreDelta: -27` 을 "−27점" 으로 보여주면
  점수 산식을 설명해야 한다. 부호는 **색과 위치**로만 전달한다 (D8-2 에 근거)

### D4-1-a. 카드 전부에 있는 문장은 목록 위로 올린다 (#304)

날씨는 **장소별 근거가 아니라 화면의 전제**다. 같은 날 같은 시군구면 세 장소에 똑같이
붙는데, 장소별 근거인 척 반복되면 세 장소의 실제 차이(동반 가능 여부 · 실내/야외)가 같은
문장 아래 묻힌다. 실측(1265×900, 로그인)에서 `풍랑 주의보 발효 중입니다…` 가 좌측 판정
1번 + 카드 3장 = **4번** 서 있었다.

| 항목      | 규칙                                                                       |
| --------- | -------------------------------------------------------------------------- |
| 판정 기준 | 로드된 카드 **전부**에 같은 `description` 이 있는가 (`splitSharedReasons`) |
| 견주는 값 | **`description`.** `code` 가 아니다                                        |
| 카드 1장  | 아무것도 떼지 않는다 — 비교 대상이 없다                                    |
| 뗀 문장   | 적합도 섹션 머리(목록 바로 위)에 **한 번만**                               |
| 노출 폭   | 데스크톱(`md:`)만. 카드 근거 자체가 데스크톱 전용이라 모바일은 그대로다    |

- **근거 코드를 FE 에 나열하지 않는다.** `WEATHER_WARNING_ACTIVE` 같은 코드로 거르면
  서버가 코드를 하나 더 낼 때 조용히 새어 나온다 (`frontend/CLAUDE.md`)
- **자리를 적합도 섹션으로 잡은 이유**: 좌측 판정 섹션은 기준 장소가 없는 첫 방문자에게
  렌더되지 않는다(S5-1). 거기에만 두면 그 사용자는 특보를 어디서도 못 본다
  — **특보 배지 자체는 이제 페이지 최상단 `WeatherWarningStrip` 이 맡는다** (D0, #349).
  이 줄은 공통 근거 **문장**(`description`)의 자리를 말하는 것이고 배지와 다른 것이다
- **목록이 짧아지는 효과는 문장 길이에 달렸다.** 목 데이터 실측에서 행 높이는 96px 썸네일이
  잡고 있어 1265 / 870 에서 `136 · 159 · 137` 그대로였다 — 줄어든 것은 높이가 아니라
  **같은 문장의 반복**(3회 → 1회)이고, 2줄 상한에 밀려 안 보이던 장소별 문장이 드러났다
- **BE 후속 제안**: `reasons[]` 에 `scope`(GLOBAL / PLACE) 가 있으면 FE 가 텍스트 비교로
  추측하지 않아도 된다

### D4-1-b. 1등만 펼치고 나머지는 접는다 (#307)

> **#1069 에서 대체됐다 — 아래 D4-1-e.** 행이 사진 카드로 바뀌며 순위로 접지 않는다. 이 절은
> 행 시절의 결정 기록으로 남긴다.

`DESIGN.md` §1 — _"위계는 크기와 순서로 만든다. **낮은 우선순위는 접는다**"_. 홈은 요약
화면이라 `N=3` 을 골랐지만(공통명세 S5-2) 세 장이 전부 펼쳐져 있어 "요약" 이 아니라
"짧은 목록" 이었다.

| 항목      | 접힌 행 (2번째부터)                                  |
| --------- | ---------------------------------------------------- |
| 남는 것   | 이름 · 메타 줄(주소 · 실내/야외) · 등급 배지 · 점수  |
| 접는 것   | 근거 문장 · 속성 태그 열(동반 가능 · 실내 · 혼잡도)  |
| 썸네일    | 96px → **48px** (모바일 80px 은 그대로)              |
| 점수      | `hero`(28/900) → `row`(22/900). **등급 색은 그대로** |
| 세로 패딩 | `md:py-5` → `md:py-3`                                |

- **썸네일을 함께 줄이지 않으면 접기가 높이를 못 줄인다.** 행 높이를 96px 썸네일이 잡고
  있어, #304 에서 근거 두 줄을 걷어도 실측 136px 그대로였다
- **펼치는 장치를 두지 않는다.** 행 전체가 `<Link>` 라 그 안의 `<button>` 은 무효 HTML 이고,
  근거 전문은 상세 화면이 이미 갖고 있다. 펼침 상태가 없으므로 URL 에 둘지도 문제가 안 된다
- **모바일은 접지 않는다.** 접는 대상(근거 · 태그)이 애초에 `md:` 전용이라 접을 것이 없고,
  390px 에서 썸네일까지 줄이면 목록을 알아보는 유일한 단서를 가장 좁은 화면에서 뺏는다.
  그래서 이 갈래가 바꾸는 클래스는 **전부 `md:` 접두를 가진다**
- **"1등" 이 아니라 "첫 행" 이다.** (#1380 이전 기록) 당시 `pickTopPlaces` 는 목록 앞 세 개를 그대로 집어
  (D8-1) 첫 행이 최고점이라는 보장이 없었다 — `판단 근거 부족` 행이 첫째로 설 수 있었다. **#1380 에서 풀렸다** —
  추천 API 가 점수순으로 주고 점수 없는 곳을 빼므로 첫 행이 최고점이다(D10-2)

**실측 (1265 / 870, `MOCK_API=true`)**

|         | 목록 높이 | 행 높이               | 섹션 안 숫자 노드 |
| ------- | --------- | --------------------- | ----------------- |
| 접기 전 | 410       | 136 · 137 · 137       | 8                 |
| 접기 후 | **314**   | 136 · **89** · **89** | **6**             |

390 은 섹션 465px · 행 128 · 107 · 107 · 썸네일 80 으로 **접기 전과 완전히 같다.**

### D4-1-e. 추천 장소를 사진 카드로 — 캐러셀 · 3열 그리드 · 끝 카드 (#1069)

추천은 최대 3곳이라 세로 목록의 장점(여러 행 비교)이 없었다. 모바일은 오른쪽 칸에 칩 ·
배지 · 점수가 몰려 제목이 세 줄로 꺾였고, 데스크톱은 썸네일 96 옆이 수백 px 비어 있었다.

- **카드 — 전제 → 정체 → 판정.** 사진 16:10(없으면 카테고리 일러스트) 왼쪽 위에 동반 칩
  (흰 바탕 + `--shadow-md`), 제목 18/600 최대 2줄(옆에 아무것도 없음), `지역 · 실내외`,
  판정 줄 `82/100 여행 적합 · 혼잡`(숫자만 등급 색 · 등급어는 `-700` 글자 · 혼잡은 `HIGH`
  일 때만). **순위로 접지 않는다** — 동반 칩이 모든 순위에 선다. 위계는 순서가 만든다.
- **틀 — 1024 미만 캐러셀 · 이상 3열 그리드** (`DESIGN.md` §7-4). 카드 폭 82%(768~1023 은
  44%), `scroll-snap`, 화살표 없음. 구성이 바뀌면 틀을 새로 세워(`key`) 1위가 항상 첫 장이다.
- **근거 한 줄 — `md` 이상.** 공통 근거를 뺀 나머지 중 감점 → 서버 순서의 첫 문장
  (`pickCardReason`). 서버 문장 그대로, 자르지 않는다. 공통 근거는 D4-1-a 대로 목록 위 한 곳.
- **끝 카드** (`placeCardsEnd`). 카드가 3장 미만이면 `장소 전체 보기 ›`(`--band` 채움)가
  남은 빈 칸을 **전부** 차지한다. 3장이 다 차면 끝 카드 없이 머리의 `장소 찾기` 가 맡는다. 목록
  아래 버튼 줄 둘과 머리 아래 `N곳` 줄을 걷었다. **#1380 에서 수(`장소 N곳`)와 점수 못 낸 곳의 줄을
  걷었다** (D10-4).
- **목록 위 1px 선을 걷었다**(#530 의 것). 첫 항목이 사진 면이라 머리말과 저절로 갈린다.
- **카드 사진은 지연 로딩하지 않고, 첫 카드만 `preload` 다** (#1358). #1356 으로 사진이 첫 화면
  안에 들며 LCP 요소가 됐는데 `next/image` 기본값이 지연 로딩이라 늦게 불렸다. 1024 이상 3열은
  세 장이 다 첫 화면이고(실측: 둘째 장 사진이 LCP), 모바일 캐러셀도 둘째 장이 걸쳐 보인다 —
  그래서 셋 다 `eager`. 미리 받기(`preload`)는 대역폭을 나눠 쓰지 않게 첫 장만이다.

### D4-1-c. 곡선의 세로 막대를 걷고 추천 구간을 면으로 표시한다 (#312)

세로 막대는 `h-8 w-2` **고정**이라 길이가 변하지 않았다. 즉 **막대의 형태(길이=크기)를
하고 있으면서 실제로는 범주(등급)만 담고 있었다** — 사람은 막대를 보면 길이를 읽으려 하는데
읽을 것이 없었다. `DESIGN.md` §10 이 이미 금지하고 있다(장식성 세로 바는 `ReasonList` 근거
부호의 3px 바에만).

그리고 곡선에 구멍이 하나 있었다. 위에서 `18:00 – 21:00` 을 추천해 놓고 **아래 셀 중 어느
것이 그 구간인지 표시가 없었다.**

| 항목      | 값                                                                           |
| --------- | ---------------------------------------------------------------------------- |
| 구간 계산 | `lib/insight/golden-window.ts` — `isWithinGoldenWindow` · `markGoldenWindow` |
| 비교 방법 | **문자열 사전순.** `Date` 로 파싱하면 지역 시각이 브라우저 타임존으로 밀린다 |
| 경계      | **양끝 포함.** 문장이 적은 두 시각을 셀에서 빼면 문장과 그림이 어긋난다      |
| 면의 색   | **칸마다의 등급** `-100` 층 (#656). `goldenLevel` 은 곡선에서 쓰지 않는다    |
| 등급 색   | **노면 숫자에 `-700` 층**으로 내려왔다 (걷어낸 막대가 갖고 있던 정보)        |
| 등급 이름 | 셀의 `sr-only` 로 남는다 — 면도 숫자도 스크린리더에는 아무 말을 못 한다      |
| 라운드    | 주지 않는다 — 목록·섹션에 라운드가 없다 (§0)                                 |

- **칸 간격을 `gap` 이 아니라 셀 안쪽 padding 으로 준다.** `gap` 이면 면이 칸마다 끊겨
  줄무늬로 읽힌다. 간격은 6 → **8**(스케일 안 값, §4)이 되고 칸 피치는 54 → 56 이다
- **구간이 없는 날·뒤집힌 구간은 어느 칸도 들지 않는다.** 없는 추천을 화면이 만들지 않는다

| --- | ------- | -------------- | ---------------------------- |
| 전  | 110     | —              | 없음 (막대만)                |
| 후  | **74**  | 223            | 18 · 19 · 20 · 21시 4칸 연속 |

대비: 노면 숫자 `-700` 이 면 위에서 **7.39:1**, 흰 배경에서 5.2~5.64:1 로 모두 AA 를 넘는다.

#### 면의 색을 시각별 등급으로 바꾼다 (#656)

`#312` 는 면을 `goldenLevel` **한 톤**으로 칠하면서 _"칸마다 색이 갈리면 면이 아니라
줄무늬가 된다"_ 고 적었다. **그 판단이 틀렸다.** `11:00 – 23:00` 창 안에서 14 · 15시만
주의였던 날(2026-09-15 dev 실측, 진단 H-2) 면은 그 사실을 한 번도 말하지 못했고, 창 전체가
한 등급인 것처럼 읽혔다 — 배지가 모순으로 읽힌 것과 **같은 원인**이다 (#637).

#637 이 그 사실을 헤드라인 아래 문장으로 옮겼다. **면도 같은 말을 해야 한다.** 문장이
`14–15시는 … 주의` 라고 적는데 면이 내내 한 색이면, 이 섹션이 두 번 겪은 실패(곡선과 문장이
서로 다른 말을 한다, #270)가 다시 난다.

| 항목           | 값                                                                                     |
| -------------- | -------------------------------------------------------------------------------------- |
| 톤 계산        | `walkSafetyTone(hour.walkSafetyLevel.code)` — 칸마다                                   |
| 톤 표          | `WINDOW_TINT: Record<MetricTone, string>` — 값이 늘면 타입체커가 잡는다 (component §2) |
| 색 추가        | **없다.** `DESIGN.md` §2-3 등급 토큰 `-100` 층 그대로                                  |
| 같은 등급 잇기 | 라운드 없음 + `gap` 없음(간격은 셀 안쪽 padding). 색이 갈리는 자리에만 경계가 생긴다   |
| 등급 모르는 칸 | `--band` 중립 면. 등급 색을 주지 않고, 비우지도 않는다 (아래)                          |
| 창 밖          | 등급이 무엇이든 면이 없다 — 면의 첫째 사실은 여전히 "서버가 추천한 구간" 이다          |
| `goldenLevel`  | 곡선에서 빠진다. 헤드라인 시각의 색으로만 남는다 (`GoldenWindow`)                      |

**등급을 모르는 칸**(`walkSafetyTone` 이 `unknown` 으로 떨어지는 칸)은 두 규칙에 동시에
걸린다 — 등급 색을 주면 모르는 것을 아는 것처럼 말하고(§2-3: `UNKNOWN` 에는 tint 가 없다),
비우면 그 칸이 **추천 구간 밖**으로 읽혀 문장이 적은 시각과 면이 어긋난다. 그래서 등급을
말하지 않는 **중립 면(`--band`)으로 자리만 지킨다.**

**점선을 쓰지 않는다.** 장소 상세 혼잡도의 `점선은 아직 모르는 날이에요`(혼잡도-집중률
세부명세 D8)는 **그릴 막대가 없는** 칸의 표기다. 여기 칸에는 기온·노면 숫자가 그대로 있고
모르는 것은 등급 하나뿐이다. 게다가 점선 테두리를 칸마다 두르면 **모르는 칸이 이어질 때 그
사이에 선이 생겨** 같은 등급을 잇는다는 이 면의 규칙과 정면으로 어긋난다. 모른다는 사실은
색이 아니라 낱말이 말한다 — 노면 숫자가 등급 색을 받지 않고(`--fg-muted`), 셀의 `sr-only` 가
서버 `name` 을 그대로 읽는다.

**색만으로 전하지 않는다.** 등급 분포는 헤드라인 아래 문장이 이미 낱말로 말하고(#637),
칸마다의 등급은 `sr-only` 가 읽는다. 면은 그 두 채널의 보조다.

**소개 페이지 견본**(`GoldenCurveSpecimen`, #635)은 **창 안이 전부 한 등급인 날**이라 한
색인 채로 실제와 어긋나지 않는다. 다만 범례가 어긋날 뻔했다 — `추천 구간` 한 낱말이면 초록
견본이 "초록 = 추천 구간" 을 가르치고, 그렇게 배운 사람은 실제 창 안의 황갈색 칸을 추천에서
빠진 시각으로 읽는다. 범례 문구가 색의 뜻을 함께 적는다:
`추천 구간 · 색은 시각별 등급`(`messages.about.specimen.curveLegendWindow`).

### D4-1-d. 출처와 계산 입력은 근거를 여는 자리 안에 둔다 (#317)

`weatherProviderName`(출처)과 `humidity`(계산 입력)는 응답에 있는데 화면 어디에도
안 나오던 필드다. **출처를 밝히는 것은 이 서비스의 정체성과 맞는다** — `DESIGN.md` §1 이
시각 컨셉을 "데이터 신뢰형" 으로 잡았다.

**다만 상시 노출 줄을 새로 만들지 않는다.** 홈 첫 화면에 이미 숫자값이 빽빽하고, 이 둘을
늘 세우면 밀도 문제를 키우면서 정작 행동은 하나도 바꾸지 않는다.

| 항목      | 값                                                                      |
| --------- | ----------------------------------------------------------------------- |
| 컴포넌트  | `components/basis-footnote.tsx` — 홈과 장소 상세가 **같은 조각**을 쓴다 |
| 홈 자리   | `InfoTip` 말풍선 안, `feelsLikeBasis` 아래 (D4-1-e)                     |
| 상세 자리 | `체감온도 계산 근거` 문단 안, 같은 문장 바로 아래 (`gap-1`)             |
| 모양      | **한 줄.** `계산에 쓴 상대습도 78% · 출처 기상청 단기예보`              |
| `null`    | 그 조각만 뺀다. 둘 다 없으면 각주 자체가 없다                           |

- **`습도 60%` 를 단독으로 세우지 않는다.** 그것만 있으면 사용자가 할 수 있는 일이 없다 —
  바로 위 `feelsLikeBasis` 가 _"기온과 상대습도로 습구온도를 구해 산출하며"_ 라고 말하고,
  이 값이 그 문장이 말하는 입력의 실제 수치다. 붙여 두면 서로를 설명한다
- **`0%` 는 값이다.** `null` 과 같이 취급하면 건조한 날의 입력이 사라진다
- **홈과 상세가 같은 조각을 쓴다.** 같은 두 값을 두 화면이 다르게 적으면 사용자는 서로 다른
  사실로 읽는다

**실측 (1265, 로그인)**: 말풍선을 **닫은 상태에서 홈 첫 화면의 숫자 노드가 37개로 그대로다.**
열었을 때만 38개가 된다 — 늘어난 한 줄은 사용자가 연 자리 안에 있다.

### D4-2. 반려견을 바꿀 때 스켈레톤을 띄우지 않는다

React Query 의 `placeholderData` 로 이전 반려견의 값을 유지하고, 새 값이 오면 교체한다.
스켈레톤으로 되돌리면 화면이 깜빡여 **"바꾼 게 반영됐나" 를 알 수 없다.**
대신 카드에 `aria-busy` 를 걸고 옅은 투명도를 준다.

**홈 전체를 `ErrorState` 로 덮지 않는다.** 진입점이 죽으면 아무 데도 갈 수 없다 (공통명세 S4-3).

#### D5-1a. 다가오는 일정의 빈 상태는 두 갈래다

**`GET /plans` 는 날짜순이 아니다** — 계약이 "일정 아이디 내림차순(**최근 생성순**)" 이라고
적어 두고 있고 날짜 필터 파라미터도 없다. 그래서 응답 첫 건은 "가장 최근에 만든 일정" 이지
"가장 가까운 일정" 이 아니다. **화면이 걸러 정렬한다** (`lib/plan/upcoming.ts`).

- 지난 일정의 기준은 **`endDate`** 다 (`isPastPlan`). 오늘이 여행 중인 날이면 아직 안 지났다.
- 정렬은 `startDate` 오름차순.
- **오늘은 서버가 정한다** — 클라이언트가 `new Date()` 를 부르면 자정을 걸칠 때 서버와
  브라우저가 서로 다른 일정을 고른다 (`todayIso` prop · `lib/date/day.ts` `dayToLocalNoon`).

| 상태                        | 문구                                                       |
| --------------------------- | ---------------------------------------------------------- |
| 일정이 아예 없음            | `noPlanTitle` "아직 일정이 없어요" + 만들기 유도           |
| 일정은 있는데 **전부 지남** | `noUpcomingPlanTitle` "다가오는 일정이 없어요" + 목록 안내 |

**둘을 한 문구로 묶지 않는다.** 넷 다 지난 계정에 "아직 일정이 없어요" 라고 말하면 사용자는
자기 일정이 사라졌다고 읽는다. 다음 행동도 다르다 — 앞은 만들기, 뒤는 목록으로 보내기다.

#### D5-1c. 출발 임박 · 여행 중 일정은 첫 화면 배너로 올린다 (#1113)

일정은 홈 맨 아래 `다가오는 일정` 한 줄뿐이었다 — 375 y=1766 / 2034, 1440 y=905 로 첫 화면 밖.
여행 당일에 홈을 연 사람이 오늘의 브리핑에 닿으려면 맨 아래 → 일정 상세 → 배너를 거쳐야 했다.

**새 API 도 새 판정도 없다.** 홈이 이미 받는 `GET /plans` 에서 `pickTripBanner`
(`src/lib/plan/trip-banner.ts`)가 고른다 — 고르기는 `pickUpcomingPlans`, 브리핑 갈래는
`pickBriefingDate`(일정 상세 배너와 같은 규칙), 남은 일수는 `planPhaseOf` 다.

| 시점                  | 제목                      | 설명                   | 이동                   |
| --------------------- | ------------------------- | ---------------------- | ---------------------- |
| 출발 7 ~ 2일 전       | `D-{N} · {일정 제목}`     | `{10월 6일 (화)} 출발` | `/plans/{id}`          |
| 출발 하루 전          | `내일 출발 · 브리핑 보기` | `{일정 제목}`          | `/plans/{id}/briefing` |
| 출발 당일 ~ 마지막 날 | `오늘의 브리핑 · {N}일차` | `{일정 제목}`          | `/plans/{id}/briefing` |
| 그 밖 · 게스트        | 서지 않는다               |                        |                        |

- **가장 가까운 한 건만** 선다. 출발일 순이라 여행 중인 일정이 있으면 그것이 먼저다.
- **기간이 성립하지 않는 일정은 후보에서 먼저 뺀다** — 날짜를 못 읽거나 종료일이 시작일보다 앞선
  것. `planPhaseOf` 는 시작일만 보고 `upcoming` 을 줘서, 상세 브리핑이 거절하는 일정을 홈이 `D-N` 으로
  부를 수 있었고, 문자열 정렬에서 맨 앞에 오는 깨진 시작일이 정상 일정을 가릴 수 있었다.
- **당일 · 전날 제목은 일정 상세 브리핑 배너와 같은 말이다** (`plan.briefingBanner*Title`). 당일은
  홈에 일자 카드가 없어 `N일차` 를 붙인다.
- **D-N 은 상세로 보낸다.** 2일 이상 남은 날 브리핑은 기간 밖(`아직 브리핑할 날이 아니에요`)이다.
- **상태를 보지 않는다** — 브리핑 배너와 같은 이유(여행브리핑 D8-5).
- **면은 `Surface tone="brand"` 다** (DESIGN.md §0-3 — 시간이 정한 진입점). 새 토큰이 없다.
  `leading` 은 주지 않는다(아이콘 자리는 danger 고정). 당일만 더 진한 면으로 칠하는 안은 `Surface`
  에 변형을 더해야 해 이번에 하지 않았다.
- **자리가 폭마다 다르다.** 1024 미만은 좌측 레일의 **첫 카드**(프로필 위), 1024 이상은 **우측 열
  머리**(서비스 소개 카드 · `오늘 갈 만한 곳` 위, #1356 전에는 권역 위)다. 한 컬럼에서 우측 열은 좌측 레일 뒤라(375 y≈1128) 거기 두면
  첫 화면에 닿지 않고, 1024 이상에서 좌측 머리에 두면 레일 sticky 예산을 다시 깬다. 두 사본을
  `lg:hidden` · `hidden lg:block` 으로 두고 보이는 쪽만 그린다 — 서비스 소개 카드(D5-3-a)와 같은
  처리라 숨은 사본은 탭 순서 · 접근성 트리에서 빠진다. 실측(mock): 375 · 768 · 1280 에서 보이는
  배너 링크 1개, 가로 스크롤 없음.
- **배너에 선 일정은 아래 `다가오는 일정` 에서 뺀다** (`pickHomePlans` — 배너 · 아래 목록 · 섹션 노출을 한 번에 낸다). 같은 목적지가 한 화면에 두 번 서지 않게
  한다. 빼고 남는 일정이 없으면 **섹션째 숨긴다** — 그때 `다가오는 일정이 없어요` 를 그리면 바로
  위 배너와 정면으로 어긋난다. 남으면 그 다음 일정이 선다.

#### D5-1b. 다가오는 일정 행의 날짜 줄은 목록 행과 같은 모양이다 (#998)

- 기간은 **`formatPlanDateRange`** 로 쓴다 — `2026년 9월 12일 (토) – 9월 14일 (월)`. 목록 행
  (`plan-row.tsx`)과 같은 함수다. 예전에는 이 줄만 `2026-09-12 – 09-14` 로 ISO 를 잘라 썼다.
- **`formatPlanDateRangeCompact` 를 쓰지 않는다.** 그 함수는 개요 카드에서만 쓰는 예외다(#841, 같은
  화면의 일자 카드와 모양을 맞추려고 쓴다). 홈에는 나란히 놓인 일자 카드가 없다 — 홈과 목록이
  같은 일정을 다른 모양으로 부르면 안 된다.
- 뒤에 붙는 말: 모바일은 ` · 상태명`, 데스크톱은 ` · D-N` · ` · 오늘 N일차` (행 주석 참고).
- **줄바꿈 정책은 목록 행과 같다** — 전역 `keep-all` + 일반 줄바꿈이고, 자르지 않는다. 실측
  (2026-09-28, 목 서버, 기둥을 가장 넓은 `여행 중` 으로 바꿔 넣음): 390px 에서는 해를 넘기는
  기간 + 상태명까지 한 줄에 선다(글자 폭 265 / 줄 폭 289). 375px 에서는 그 조합 하나만 상태명
  앞 공백에서 두 줄로 접히고, 넘침(`scrollWidth > clientWidth`)은 어느 폭에서도 없다.

2. **큰 지표 숫자에는 `-500` 이 허용된다.** 22px 이상 + weight 900 은 대형 텍스트라 3:1 기준이다.

**#1356 부터 한 벌이다.** 홈 DOM 을 모바일 우선으로 다시 짜면서(D1) 1024 미만 · 이상의 자리가 우측
열 머리 한 곳으로 모였다 — 아래 사본 두 벌 방식과 그 근거는 기록으로 남긴다. 기각한 두 안
(`display: contents` + `order`, `matchMedia`)의 이유는 지금도 그대로이고, 그래서 한 벌로 모은 방법이
`order` 가 아니라 DOM 재배치다.

**(#963 ~ #1356) 두 자리에 두고 보이는 쪽만 그렸다.** 좌측 첫 카드 아래의 사본은 `lg:hidden`, 우측 권역
카드 아래의 사본은 `hidden lg:block` 이다(`home-view.tsx`). 두 사본 모두 **자기 자리의 바로 다음
형제가 다음 카드**라, 1024 미만 DOM 은 이 개정 전과 같고 × 뒤 초점도 "다음 형제" 그대로다.

- **숨은 사본은 `display: none` 이다** — 탭 순서와 접근성 트리에서 빠지므로 두 번 서지도 읽히지도
  않는다(375 · 768 · 1024 · 1280 · 1440 에서 Tab 한 바퀴에 카드 링크 1번 실측).
- **닫기는 한 상태다.** `HomeView` 가 갖고 두 사본이 `onDismiss` 로 나눠 쓴다. 사본마다 상태를
  가지면 닫은 뒤 창을 1024 너머로 바꾸는 순간 숨었던 사본이 선다. 쿠키 변화를 구독하게 하는
  안보다 단순하고, 쿠키를 못 쓰는 브라우저에서도 닫힌다.
- **대가**: 서버 HTML 에 카드 마크업이 한 벌 더 실린다(링크 하나 · 버튼 하나).
- **권역 골격 높이를 실화면에 맞췄다.** 권역 비교는 클라이언트 조회라 첫 그림은 골격이고, 1024
  이상에서 카드가 그 바로 아래 첫 화면 안에 선다. 골격 206 · 실화면 267 이던 동안 데이터가 오면
  카드가 61px 내려갔다 — 골격 마지막 칸 `h-24` → `h-40` 으로 밀림 3px(375 는 79 → 15).
- **권역 조회가 실패하면 카드가 우측 열 머리에 선다.** 섹션이 통째로 숨는 규칙(D0) 그대로다.
  좌측 열이 오늘 상태를 말하고 있어 "오늘 상태 다음" 원칙은 두 열을 같이 보면 성립한다 — 받아들인다.
- e2e `home-first-visit.spec.ts` 가 390 · 1024×768 · 1280×800 에서 보이는 카드 링크가 하나이고
  스크롤 없이 첫 화면 안인지 잰다(`getByRole` 은 `display: none` 을 뺀다).
- **기각 — `display: contents` + `order`(DOM 한 벌)**: 구현했다가 걷었다. 1024 미만에서 두 스택을
  풀고 `order` 로 당기면 카드의 DOM 순서가 권역 뒤로 가서, 이 카드의 주 청중인 모바일에서
  키보드 · 스크린리더가 보이는 순서와 다르게 닿는다(WCAG 1.3.2 · 2.4.3). 두 스택이 맞닿던 간격도
  바뀌어(375 0 → 8, 768 48 → 24) 1024 미만 홈 전체가 달라졌다.
- **기각 — `matchMedia` 로 한 자리만**: 서버는 폭을 모른다. 한쪽 폭에서 하이드레이션 뒤 카드가
  자리를 옮겨 목록이 밀린다 — 위 `기억` 행의 "첫 그림부터 제자리" 가 깨진다.

**맨 아래 `/about` 링크는 남긴다.** 카드를 닫은 뒤 모바일의 유일한 통로이고, 가입 전 모바일
방문자가 약관에 닿는 유일한 길이기도 하다 (`home-about-link.test.ts` 가 둘을 함께 잠근다).

## D8. 미결 사항

### D8-1. "적합도 순" 이라고 쓰지 않는다 — 확정

> **#1380 에서 다시 봤다 — D10-2 · D10-3 이 이 절을 대체한다.** 전제(목록 앞 3곳만 잰다)가 사라졌고
> `orderByScore` 를 걷었다. "적합도 순" 이라고 쓰지 않는다는 결론은 남는다 — 이유가 바뀌었다(D10-3).
> 아래는 #1356 시점의 기록이다.

상위 3개만 적합도를 조회하므로(공통명세 S5-2) **전체 정렬이 아니다.**

**뽑은 3장 안에서는 점수 높은 순으로 세운다** (#1356, `orderByScore`). 응답 도착 순서(= 목록 앞
3개의 순서) 그대로 두었더니 첫 카드가 40점 `주의 필요` 이고 60점이 그 뒤에 서는 날이 있었다 —
첫 카드는 "가장 권하는 곳" 으로 읽힌다. 3장 안의 정렬이라 제목은 여전히 정렬을 주장하지 않는다.
같은 점수는 들어온 순서를 지키고, 점수 없음(`null`)은 맨 뒤다.
제목을 "오늘 {이름}에게 맞는 곳" 으로 두고 정렬을 주장하지 않는다.
`sortNote` 는 "오늘 날씨와 혼잡도 반영" 이다 — 사실이다. 문구는 응답의 반영 축(`appliedFactorsOf`)에
따라 바뀌고, 둘 다 반영되지 않으면 내지 않는다. **#1065 부터 제목 아래 캡션이 아니라 제목 옆 ⓘ 안이다**
(모바일 짧은 사본 `sortNoteShort` 는 걷었다). 데스크톱의 `N곳` 개수 줄은 그대로 남는다.

BE 가 목록 단위 적합도를 주면(S6-2) 그때 "적합도 순" 으로 바꾼다.

### D10-2. 순서는 서버 것 — FE 재정렬(`orderByScore`)을 걷는다

서버가 점수 desc → 동반 `ALLOWED` 먼저 → 덜 붐비는 곳 → `placeId` asc 로 세우고, 같은 유형은 `limit`
의 절반(올림)까지 먼저 담는 다양성 규칙을 건 뒤 다시 정렬 순으로 준다(BE §6-5). FE 가 점수로 다시
세우면 안정 정렬이라 결과는 같지만 **순서의 정본이 둘이 된다** — 서버 규칙이 바뀌면 FE 정렬이 그것을
조용히 덮는다. `orderByScore` 는 목록 앞 3곳을 도착 순서대로 받던 때(#1356)의 처방이라 함께 걷었다.
기준 장소를 빼도 나머지 순서는 그대로다.

### D10-3. 제목 — `갈 만한 곳` 을 지키되, 전부 `주의 필요` 이하면 낮춘다 (D8-1 재검토)

- **`적합도 순` · `맞는 곳` · `추천` 으로 올리지 않는다.** 이제 서버가 후보 전부를 같은 적합도 규칙으로
  재지만, 순서에는 유형 다양성(같은 유형은 절반까지)이 섞여 점수 순만으로 설명되지 않는다 — 다양성으로
  채운 자리가 그 아래 후보보다 낮을 수 있다. D8-1 의 결론("정렬을 주장하지 않는다")은 남고 이유가
  "3곳만 잰다" 에서 "다양성이 섞인다" 로 바뀌었다.
- **`갈 만한 곳` 은 이제 지킬 수 있는 약속이다** — 동반 미확인 · 점수 없음은 서버가 뺐다. 단, 추천은
  **가장 나은 곳**을 고를 뿐이라 비 · 특보 날에는 1위도 `주의 필요` 다.
- **카드로 선 곳이 전부 `LOW`(주의 필요) 이하면 제목을 `오늘 장소 상황` 으로 낮춘다**
  (`allCardsCautious`, `messages.home.suitabilityCautiousHeading`). "이하" 는 `LOW` 와 `INSUFFICIENT`
  다 — 후자는 추천에 오지 않지만 갈 만하다는 근거도 아니다. 모르는 새 등급은 셈에 넣지 않는다(모르는
  것을 나쁘다고 말하지 않는다). 등급 코드는 shared-travel `SuitabilityLevel`(80 이상 HIGH · 60 이상
  MEDIUM · 그 아래 LOW) 실측이다.
- **한 곳이라도 `보통` 이상이면 그대로다** — 그 곳이 1위(첫 카드)다. 카드가 없는 동안(골격 · 빈 상태 ·
  오류)은 바꾸지 않는다.
- **판정은 렌더된 카드 기준이다** — 기준 장소를 뺀 뒤의 카드다. 반려견 이름은 넣지 않는다(조사가 설
  자리가 없고, 조건 반영은 ⓘ 가 말한다).

### D10-4. 끝 카드 — 수를 걷는다

`장소 {n}곳 전체 보기` 의 `{n}` 은 목록 전체 수(#905 R7)였는데 추천 API 는 그 수를 주지 않는다. 수를 위해
목록을 따로 부르면 걷어 낸 왕복이 돌아온다 — **`장소 전체 보기 ›`** 로 바꿨다. 점수를 못 낸 곳의 줄
(`unscoredInAllPlaces`)도 걷었다 — 서버가 그런 곳을 추천에서 뺀다(`unscored` 는 늘 0). 끝 카드는 후보가
모자라거나 기준 장소가 추천에 들어 카드가 3장 미만인 날에만 선다.

### D10-5. 실내 대안을 추천 카드 위로

- **`IndoorAlternativesSection` 을 `오늘 갈 만한 곳` 바로 위로 옮겼다** (모바일 · 데스크톱 같은 DOM 자리).
  대안이 서는 날은 서버가 비 예보로 채운 날이고 그날 카드는 전부 야외 감점을 달았다 — 먼저 볼 것이 실내다.
- **조건을 따로 세우지 않는다.** 섹션은 대안이 있을 때만 서고(빈 배열이면 미렌더), 대안은 비 예보 +
  실내 없음일 때만 온다. "비 · 특보일에는 위로" 가 곧 "서는 날은 늘 위" 다. 특보만 있고 비 예보가 없는
  날은 대안이 없어 섹션도 없다 — 지금처럼 아무것도 없다.
- **DOM 순서로 올린다** — `order` 금지(WCAG 1.3.2, D1). 캡션은 `위 목록의 장소에서` → **`아래 장소에서
가까운 실내예요`**. 소개 카드 × 뒤 초점은 다음 형제 카드(실내 대안이 선 날은 그 카드)로 간다.
- **대가**: 대안은 추천과 같은 응답이라, 골격이 서 있는 동안 자리가 없다가 데이터가 오는 순간 위에
  끼어든다 — 그 순간 `오늘 갈 만한 곳` 머리가 섹션 높이만큼 내려간다(골격 → 카드 교체와 같은 순간이다).

### D10-6. 추천 응답의 특보 — 띠의 소스에 넣는다, 목록 머리에 따로 세우지 않는다

추천 응답 머리의 `weatherWarning` 은 다른 응답과 같은 **단일 지점 특보**다(기준 일자가 오늘일 때만 —
홈은 날짜를 보내지 않는다). 홈은 특보를 최상단 `WeatherWarningStrip` 한 곳에서만 말한다(#349) — 목록
머리에 한 번 더 세우면 같은 사실이 한 화면에 두 번 선다. 그래서 `pickWeatherWarning` 의 **마지막
후보**로 넣었다: 콜드면 18초가 걸려 가장 늦게 오므로 권역 · 판정 · 골든타임이 모두 실패한 날의 폴백이다.
특보 문장 자체(`WEATHER_WARNING_ACTIVE` 근거)는 카드 전부에 붙으므로 D4-1-a 대로 목록 위 공통 근거로
한 번 선다(`md` 이상).

### D10-7. 권역 동점 문구 — `권역별 차이가 없어요`

`regionTiedAll` 이 `오늘은 어느 권역이든 좋아요` 에서 **`권역별 차이가 없어요`** 로 바뀌었다. 다섯 권역이
모두 강수 90% 로 같은 점수인 날에도 "좋아요" 가 나가 바로 아래 근거(`야외 일정에 영향`)와 부딪쳤다
(ux-review §3-4). 동점은 "어디든 좋다" 가 아니라 "고를 차이가 없다" 다 (권역-점수-라벨-세부명세 갱신).

### D10-8. 빈 상태 — `items: []`

추천할 곳이 없으면 서버는 `items: []`(200)다 — 예보 범위 밖 날짜, 또는 후보 전부가 점수를 못 낸 날(BE는
그 빈 결과를 캐시하지 않는다). 홈은 날짜를 보내지 않아 앞의 경우는 없고, 실제로는 날씨 원천이 죽은 날이다.
**기존 `emptyPlacesTitle` · `emptyPlacesDesc`(`표시할 장소가 없어요` · `장소를 찾아보세요.`) + `장소 찾기 ›`
를 그대로 쓴다** — 사실(보여 줄 카드가 없다)만 말하고 원인을 짐작하지 않으며, 다음 행동(목록에서 찾기)이
맞다. 재시도 버튼은 달지 않는다 — 200 이고 BE 가 빈 결과를 캐시하지 않아 다음 방문이 곧 재시도다.
기준 장소를 빼서 카드가 0장이 된 경우(추천 1곳 = 기준 장소)도 같은 빈 상태다.
