> **폼 본체는 [등록-세부명세.md](등록-세부명세.md) 가 정본이다.** 이 문서는 **차이와 삭제 흐름**만 적는다.

## D0. 화면 정의

- **경로**: `/pets/[petId]` (라우트 그룹 `(main)`)
- **인증**: 필요
- **한 줄 정의**: 등록한 반려견의 프로필을 고치거나 삭제한다
- **읽기 전용 상세 화면을 두지 않는다.** 근거는 공통명세 S5-1 — `PetItem` 과 `PetResponse` 가 필드 단위로 동일해 상세가 목록 카드보다 더 보여줄 것이 없다
- **범위에서 제외**: 일정 이력, AI 추천 이력 (그 값이 생기면 이 경로를 상세로 바꾸고 폼을 `/edit` 으로 옮긴다)

## D1~D2. 등록과의 차이

레이아웃은 등록과 같은 스택(`Canvas` + `SurfaceStack max-w-2xl`)인데 **카드가 둘**이다
(`DESIGN.md §0`, 이슈 #464).

| 순서 | 카드/블록                   | 무엇이 다른가                                        |
| ---- | --------------------------- | ---------------------------------------------------- |
| 1    | **사진과 대표 지정** (카드) | 전용 엔드포인트라 **저장 버튼과 무관하게 바로 반영** |
| 2    | **반려견 정보 수정** (카드) | `PetForm`. 저장을 눌러야 반영                        |
| 3    | 삭제 (카드 아님, L0)        | 액션이고 "이 아이를 지운다" 는 다른 이야기다         |
| 4    | `목록으로` (카드 아님, L0)  | 등록 화면과 같은 자리                                |

**카드 경계가 "바로 반영" 과 "저장해야 반영" 을 가른다.** 2a 때는 `PetPhotoSection` 이
스스로 `border-b` 를 긋고 삭제가 폼 `footer` 안에서 `border-t` 를 그어 수제 구분선 둘이
그 일을 했다 — §0 의 "카드 경계는 이야기 단위" 가 그대로 맡는다.

**`lead` 는 폼 카드가 갖는다.** `DESIGN.md §3-1` 은 그 등급을 **"화면의 주인공 섹션"** 으로
못박는다 — "카드가 하나일 때" 가 아니다(홈이 반례다: 카드 여럿에 적합도만 `lead`). 이 화면의
주인공은 정보를 고치는 쪽이고, 그래야 **등록 화면과 같은 폼이 같은 크기**로 선다.

**폼 카드 제목은 페이지 이름과 갈라 둔다** — `h1`(`sr-only`)이 `반려견 정보 수정`, 카드는
`반려견 정보` 다. 카드 판정 ①이 요구하는 것은 **그 카드가 담는 것의 이름**이지 페이지 이름이
아니고, 같은 문구가 `h1`·`h2` 로 두 번 들리면 §1 에 걸린다. 카드가 하나인 등록 화면은 페이지
이름을 그대로 쓴다(#453 과 같음).

**폼 안 섹션 제목은 `h3` 다** — 카드가 `h2` 를 가지므로 한 단 내려왔다(목록 행과 같은 이유).

컴포넌트는 `PetForm` 을 공용한다 — 백엔드가 `PetSaveRequest` 를 등록·수정에 공유하므로(공통명세 S2) 폼이 하나여야 계약과 어긋나지 않는다.

`PetForm` 이 props 로 받는 차이:

| props           | 등록                    | 수정                           |
| --------------- | ----------------------- | ------------------------------ |
| `initialValues` | `EMPTY_PET_FORM_VALUES` | `toPetFormValues(pet)`         |
| `submitLabel`   | "등록하기"              | "저장하기"                     |
| `onSubmit`      | `POST /members/me/pets` | `PUT /members/me/pets/{petId}` |

**`footer` prop 은 없어졌다** (#464). 삭제 영역과 `목록으로` 가 둘 다 카드 밖으로 나가면서
폼이 자기 아래에 남의 것을 그릴 이유가 사라졌다 — 배치는 `PetEditView` 가 갖는다.

추가 컴포넌트:

| 컴포넌트           | 신규/기존 | 위치                                      | 비고                               |
| ------------------ | --------- | ----------------------------------------- | ---------------------------------- |
| `PetEditPage`      | 신규      | `app/(main)/pets/[petId]/page.tsx`        | 서버 컴포넌트. 프리페치 + 404 판정 |
| `PetEditSection`   | 신규      | `src/features/pet/pet-edit-section.tsx`   | `'use client'`. 조회 + 폼 조립     |
| `PetDeleteSection` | 신규      | `src/features/pet/pet-delete-section.tsx` | `'use client'`. 확인 단계 포함     |
| `not-found.tsx`    | 신규      | `app/(main)/pets/[petId]/not-found.tsx`   | `PET_001`                          |
| `error.tsx`        | 신규      | `app/(main)/pets/[petId]/error.tsx`       | 경계                               |

**삭제 확인에 `Modal` 을 새로 만들지 않는다.** `src/components/` 에 `Modal` 이 없고, 이 화면 하나를 위해 focus trap·스크롤 잠금·포커스 복귀를 갖춘 공통 컴포넌트를 설계하는 것은 범위를 넘는다 (`component-guide.md` §7 이 `Modal` 에 요구하는 계약이 크다). **인라인 2단계 확인**으로 간다 — D4-2.

## D3. 데이터 흐름

```text
/pets/{petId} 진입 (서버)
  ├─ petId 가 숫자가 아니면 → 400 PET_113 → error 경계 (notFound 가 아니다!)
  └─ serverFetch GET /members/me/pets/{petId} (retry: false)
       ├─ 404 PET_001 → notFound() → not-found.tsx
       └─ 성공 → dehydrate → HydrationBoundary
                              → PetEditSection (client, useQuery 같은 key)
                                   → PetForm(initialValues = toPetFormValues(pet))
```

| 항목                   | 내용                                                          |
| ---------------------- | ------------------------------------------------------------- |
| API                    | `GET` / `PUT` / `DELETE /members/me/pets/{petId}`             |
| React Query key        | `petKeys.detail(petId)`                                       |
| staleTime / gcTime     | 1분 / 10분 (`§7`)                                             |
| retry                  | 1 (클라이언트) / **`false`** (서버 프리페치)                  |
| mutation 후 invalidate | **`petKeys.all`** — 목록의 `totalCount` 가 상한 판정에 쓰인다 |
| 폴링 여부              | 없음                                                          |

**`PUT` 은 부분 수정이 아니다.** 10개 필드를 통째로 덮어쓴다(공통명세 S2). `toPetSavePayload()` 가 항상 전량을 담으므로 폼이 이 계약을 자동으로 만족한다 — **필드를 조건부로 빼는 최적화를 넣지 않는다.** 넣으면 그 필드가 서버에서 기본값으로 덮인다.

## D4. 상호작용

등록 명세 D4 의 모든 행이 그대로 적용된다. 아래는 **추가·변경분**이다.

### D4-1. 수정 고유

| 트리거      | 동작                                     | 결과                                          |
| ----------- | ---------------------------------------- | --------------------------------------------- |
| 저장 성공   | `invalidate(petKeys.all)` → `/pets` 이동 | `replace`. 뒤로가기로 폼에 돌아오지 않는다    |
| 저장 중 404 | `not-found` 로 보내지 않고 폼 위 안내    | 다른 탭에서 삭제된 경합이다. 목록 링크를 낸다 |
| `PET_002`   | **발생하지 않는다**                      | 상한은 등록에만 걸린다                        |

**저장 중 404 를 `notFound()` 로 처리하지 않는다.** 진입 시점의 404 는 "잘못된 주소" 지만, 저장 시점의 404 는 "방금까지 있었는데 사라졌다" 다. 후자를 404 화면으로 보내면 사용자가 입력한 값을 잃는다. 폼을 유지하고 안내만 낸다.

### D4-2. 삭제 — 인라인 2단계 확인

```text
[삭제하기] 클릭
   → 같은 자리에서 확인 단계로 전환
     "삭제하면 되돌릴 수 없어요. {이름} 을 삭제할까요?"
     [취소]  [삭제]
        ├─ 취소 → 1단계로 복귀
        └─ 삭제 → DELETE → invalidate(petKeys.all) → /pets 이동
```

| 트리거         | 동작                            | 결과                           |
| -------------- | ------------------------------- | ------------------------------ |
| "삭제하기"     | 확인 단계로 전환. **요청 없음** | 취소 가능                      |
| "취소"         | 1단계 복귀                      | 아무 일도 일어나지 않는다      |
| "삭제" (확인)  | `DELETE` → `/pets` 이동         | `replace`                      |
| 삭제 중 재클릭 | 재진입 가드로 무시              | 요청 1회만 나감                |
| 삭제 중 404    | 목록으로 이동                   | 이미 지워진 것이므로 목적 달성 |
| 삭제 중 5xx    | 확인 단계 유지 + `FormAlert`    | 다시 시도 가능                 |

**"되돌릴 수 없어요" 라고 쓴다.** 백엔드는 소프트 삭제지만(공통명세 S2) **사용자에게 복원 수단이 없다.** 서버 구현을 근거로 "복원할 수 있어요" 라고 쓰면 거짓이 된다.

**삭제 응답은 `dataBody: null` 이다** → `unwrapVoid()` 를 쓴다. `unwrap()` 을 쓰면 null 을 실패로 오인한다.

## D5. 상태별 화면

등록 명세 D5 에 아래가 추가된다.

| 상태                         | 표현                                           | 폼       | 재시도   |
| ---------------------------- | ---------------------------------------------- | -------- | -------- |
| loading (진입)               | `Skeleton` 폼 셸                               | —        | —        |
| 404 `PET_001` (진입)         | `not-found.tsx` — "존재하지 않는 반려견입니다" | 없음     | **없음** |
| 400 `PET_113` (숫자 아닌 id) | `error.tsx` — 잘못된 주소                      | 없음     | 없음     |
| 404 (저장·삭제 중)           | 폼 유지 + `FormAlert` + 목록 링크              | **유지** | 없음     |
| 삭제 확인 단계               | 확인 문구 + [취소] [삭제]                      | 유지     | —        |

`/pets/abc` 가 **404 가 아니라 400** 이라는 점이 여기서 실제로 드러난다(공통명세 S4-3). 컨트롤러가 `@PathVariable long` 이라 `MethodArgumentTypeMismatchException` → `PET_113` 이다. `notFound()` 가 걸리지 않으므로 `error.tsx` 가 받는다.

## D6. 접근성

등록 명세 D6 에 아래가 추가된다.

- 삭제 확인 단계로 전환되면 **"삭제" 버튼으로 포커스를 옮기지 않는다.** 파괴적 동작에 포커스를 놓으면 Enter 연타로 실수한다. **"취소" 에 포커스**를 둔다
- 확인 문구는 `role="alert"` 로 낸다 — 전환이 시각적으로만 전달되면 스크린리더 사용자가 무엇을 확인하는지 모른다
- 삭제 버튼은 `variant="danger"` 이고, 색만으로 구분하지 않는다 (문구가 "삭제" 다)

## D8. 미결 사항

### D8-1. 삭제 확인 — ~~인라인 2단계~~ → **`ConfirmModal`** (이슈 [#70](https://github.com/8llow8llowMe/hondigagae/issues/70) 에서 전환)

원래 판단(2026-08-27):

- **선택지 A (당시 채택)**: 인라인 2단계 확인 (같은 자리에서 전환)
- 선택지 B: `Modal` 공통 컴포넌트를 만들어 다이얼로그로
- 선택지 C: `window.confirm()`
- **당시 근거**: `src/components/` 에 `Modal` 이 없고, `component-guide.md` §7 이 요구하는 계약(focus trap, `Esc`, 스크롤 잠금, 포커스 복귀)이 커서 이 화면 하나를 위해 설계할 범위가 아니다
- **되돌리는 비용**: 낮다 — "`Modal` 이 생기는 시점에 `PetDeleteSection` 내부만 교체한다" 고 적어 뒀다

**그 시점이 왔다.** `ConfirmModal`(`src/components/confirm-modal.tsx`)이 그 뒤에 생겼고
계약을 이미 지킨다. 아트보드(`혼디가개 마이페이지·내 반려견.dc.html`)도 `role="dialog"
aria-modal="true"` 다이얼로그다 — **인라인은 아트보드와 달랐다.**

적어 둔 대로 `PetDeleteConfirm` 내부만 바뀌었고 바깥 계약(삭제 → 목록 이동)은 그대로다.

문구는 아트보드를 따르되 **"초코가 들어간 일정 1개는 그대로 남지만" 은 쓰지 않는다** —
일정 개수를 주는 API 가 없다. 셀 수 없는 것을 숫자로 적으면 그 문장이 거짓이 된다.
남긴 것은 "판정 기준이 사라져요. 되돌릴 수 없어요." 다.

### D8-2. 저장 성공 후 이동 — 목록으로 간다

등록(D8-1)과 같은 이유로 목록으로 `replace` 한다. 수정 화면에 머물면 "저장됐나" 를 알 수 없어 별도 안내 배너가 필요해지고, 그 배너는 목록의 갱신된 카드가 이미 하는 일이다.

## D9. BE 후속 요청

공통명세 S6 의 3건 외에, 이 화면에서 새로 드러난 것은 없다. 소프트 삭제는 **일정 참조를 지키기 위한 의도된 설계**이므로 요청 대상이 아니다 — 다만 사용자에게 복원 수단이 없다는 점을 문구가 정직하게 반영한다 (D4-2).
