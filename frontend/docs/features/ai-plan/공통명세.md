## S0. 화면 정의

| 화면           | 경로                     | 인증     | 초기 데이터                       |
| -------------- | ------------------------ | -------- | --------------------------------- |
| 조건 입력      | `/ai-plans/new`          | **필수** | 반려견 목록만 client 조회         |
| 생성 대기·결과 | `/ai-plans/jobs/[jobId]` | **필수** | `GET /ai-plans/jobs/{jobId}` 폴링 |

route group `(main)`. `proxy.ts` `PROTECTED_PATHS` 에 `'/ai-plans'` 가 **이미 있다.**

**두 화면을 한 이슈로 묶는다.** 제출 응답이 `jobId` 뿐이라 대기 화면 없이는 입력 화면이
아무 데도 가지 못한다.

**입력 화면은 접힌다.** 펼친 채로 두는 것은 필수 둘(기간 · 반려견)과 자유 요청뿐이고,
기본값이 있는 선택 항목 넷(지역 · 예산 · 저장한 곳 우선 · 꼭 넣을 곳)은 「더 자세히
정할게요」 하나로 묶어 접는다.

- 펼침 여부는 **마운트 시 1회** 판정한다(`lib/ai-plan/details.ts` 의 `hasAnyDetail`).
  반응형으로 두면 접힌 필드에 입력하다 마지막 값을 지우는 순간 그 섹션이 스스로 접힌다.
- `?from={jobId}` 로 조건을 되살려 들어오면 복원된 스냅샷이 첫 렌더 전에 값을 채우므로
  **펼쳐진 채**로 뜬다.
- 접힌 섹션 안의 필드(`sigunguCode` · `budgetManwon` · `preferFavorites` · `pinnedPlaces` —
  코드의 `COLLAPSED_FIELDS`)에서 검증 오류가 나면 **먼저 펼친다.** 오류 메시지를 화면에
  올리는 것이 이 규칙의 목적이다.
- 펼친 뒤 **포커스까지 옮기는 것은 `budgetManwon` 뿐이다.** `sigunguCode`(칩 그룹)와
  `pinnedPlaces`(목록)는 그 키를 `id`/`name` 으로 다는 요소가 없어 포커스가 옮겨지지
  않는다 — `docs/form-guide.md` §8 이 이 두 키에서만 성립하지 않는다.
- **자유 요청은 접기 밖이다.** 기본값이 없고 결과 품질에 가장 크게 기여하는 입력이라
  접으면 아무도 쓰지 않는다. 다만 **맨 위가 아니라 필수 뒤**다 — 첫 요소가 빈
  텍스트박스면 "뭘 써야 하지" 에서 막힌다.
- **단계별 위저드로 쪼개지 않는다.** 기각 근거는
  `docs/superpowers/specs/2026-09-09-plan-create-layout-design.md` §2.

### S0-1. 표면 — 3층(3a) 배치 (#473)

정본은 `DESIGN.md §0` 과 `docs/styling-guide.md` §3-1 이고, 여기에는 **이 두 화면이 내린
판정**만 적는다. 로드맵 [#455](https://github.com/8llow8llowMe/hondigagae/issues/455) 의 11번.

| 자리                       | 무엇                                                                    |
| -------------------------- | ----------------------------------------------------------------------- |
| 두 페이지의 `main`         | `Canvas` — L0 바닥(`--bg-sunken`), **전폭**                             |
| 조건 입력의 폭·간격        | `SurfaceStack mx-auto w-full max-w-2xl` (폼 규약 #453 · #464)           |
| 작업 상태의 폭·간격        | `SurfaceStack mx-auto w-full max-w-screen-md` — 뷰가 그린다             |
| 조건 입력 카드             | `Surface lead title=createTitle description=createDescription` **하나** |
| 작업 상태 카드 (완료 제외) | `Surface aria-label=jobTitle` **하나**                                  |
| 완료                       | 초안 개요 카드 하나 + **일자마다 카드 하나** + 카드 밖 L0 담기 패널     |

- **조건 입력은 상태 넷이 한 카드에 든다** — 조회 중 · 조회 오류 · 반려견 0마리 · 폼.
  상태에 따라 카드가 생겼다 사라지지 않는다([#440](https://github.com/8llow8llowMe/hondigagae/issues/440) 판단).
  카드를 그리는 것은 페이지가 아니라 **뷰**다 — 그래야 `inset="card"` 와 그 인셋이 어느 카드
  안쪽 값인지가 한 파일에서 보인다.
- **폼 래퍼는 `INSET_CLASS.card` + `pt-3 pb-6`** 다. #453 이 정한 리듬(위 여백 + 제목 줄
  `pb-3` = 폼 `gap`, 아래 = 폼 `gap`)을 **이 폼의 `gap-6`(24)로 다시 계산한 값**이다 —
  일정 만들기 폼(`gap-5`)의 `pt-2 pb-5` 를 그대로 베끼면 12px 어긋난다.
- **접기 블록(`더 자세히 정할게요`)은 자기 카드가 아니다.** "조건을 더 준다" 는 폼과 같은
  화자라 카드 판정 3문을 통과하지 못한다. 카드 안 L2 로 남고 **토글 제목이 `h3`**,
  그 안의 `추가 옵션` 이 `h4` 다 — 카드가 `h2` 를 가지므로 한 단씩 내려간다.
- **꼭 넣을 장소 피커는 오버레이라 카드가 아니다**(§3-2 · radius 16 채널). 안의 목록만
  `RowList`/`Row` → `SurfaceList` + `li` + `INSET_CLASS.panel` 로 옮겼다. **선택 표시는
  `--row-selected` 채움 그대로** 둔다 — `Row.selected` 가 그리던 것이 이 tint 하나였고,
  §0 이 금지하는 것은 아이템 **테두리**다. 시트 안 좌우 축(기준 줄 · 안내 줄 · 스켈레톤 ·
  행 · 빈/오류 상태)을 `INSET_CLASS.panel` 하나로 모았다 — 하나만 옮기면 md 에서 세로선이
  어긋난다.
  - **그 축은 `card` 가 아니라 `panel`(평평한 16)이다**(`src/lib/ui/inset.ts` JSDoc).
    시트는 md 이상에서 `md:max-w-sm`(384) **고정 폭 컨테이너**이고 `md:` 는 언제나 **뷰포트**
    기준이라, `card` 의 `md:px-5` 는 컨테이너 자신의 폭이 아니라 화면 폭을 보고 붙는다 —
    `BottomSheet` 자신의 머리와 footer 는 평평한 `px-4` 라 본문만 20 으로 밀린다(1280 실측:
    시트 폭 384 · 제목과 푸터 16 · 목록 행만 20 → **4px 어긋남**). `card` 는 3층 표면
    **안쪽 전용**이고 시트는 카드가 아니다. 저장소의 다른 시트 본문
    (`place-add-to-plan-sheet` · `map-sheet` · `place-login-prompt-sheet`)도 전부 평평한 16 이고,
    `inset="panel"` 을 쓰는 `emergency-map-view`(400px 패널)도 같은 이유다.
    **#473 이슈 본문이 `INSET_CLASS.card` 라고 적은 것은 틀렸다** — 정본은 `inset.ts` 다.
- **작업 상태의 `h1` 은 여섯 분기 전부에 있다.** 껍데기(`AiPlanJobShell`)가 한 번 그리고
  모든 상태가 공유한다 — 없으면 문서의 최상위 제목이 진행 표시의 `h2` 가 되어 무슨 화면인지
  알 수 없다(하루 재생성 [#451](https://github.com/8llow8llowMe/hondigagae/issues/451) 과 같은
  판단. 옮기기 전에는 이 화면에 `h1` 이 아예 없었다). **머리는 카드가 아니고** 인셋만 카드
  안 글줄과 같은 축이다.
- **완료만 카드를 스스로 그린다**(`bare`). 초안 개요(제목 · AI 배지 · 요약 · 미저장 문구 ·
  부분 생성 · `reasons`)가 카드 하나, 일자마다 카드 하나
  ([#447](https://github.com/8llow8llowMe/hondigagae/issues/447) 일정 상세와 같은 판정 —
  일자 제목이 `h3` → `h2`), **담기 패널은 액션이라 카드 밖 L0** 이다.
  - 그래서 `AiPlanDraftPreview` 의 **`footer` prop 을 걷었다** — 배치는 담는 쪽
    (`AiPlanJobView`)이 갖는다(반려견 폼 [#464](https://github.com/8llow8llowMe/hondigagae/issues/464)
    가 `PetForm.footer` 를 걷은 것과 같은 이동). 래퍼로 묶지 않아야 카드 사이 간격을
    `SurfaceStack` 이 담기 패널에도 준다.
  - 조건을 잃어 담을 수 없는 갈래(S5 함정 1)는 담기 패널 자리에 `EmptyState inset="card"` 를
    세운다 — 같은 L0 자리이고, 한 줄짜리라 카드가 아니다.
  - 부분 생성 블록의 `bg-band` 는 **카드 안 L2 채움이라 유지**한다(§0 "같은 카드 안을
    나눈다 — 1px 구분선 또는 `--band` 채움").
- **`AiPlanCanceled` 에 `inset?: Inset`(기본 `'main'`)을 더했다** — `AiPlanProgress` ·
  `AiPlanFailed` 가 이미 가진 계약이다. 기본값을 바꾸지 않아 하루 재생성 호출부는 무변경이다.
- 이 전환으로 **2a 프리미티브(`Band`·`Section`·`Row`·`RowList`)의 production 사용처가 0** 이
  됐고, 로드맵 #455 의 12번([#475](https://github.com/8llow8llowMe/hondigagae/issues/475))이
  `surface.tsx` 에서 **네 개를 지웠다.**
- **범위 밖**: `error.tsx` · `not-found.tsx` 라우트 상태 파일(12번이 옮겼다), 카드 안

## S1. 계약

### `POST /api/v1/ai-plans` — 제출 (202)

| 필드              | 필수 | 제약                                              | 오류 코드                         |
| ----------------- | ---- | ------------------------------------------------- | --------------------------------- |
| `areaCode`        | ✅   | `@NotBlank` (제주 = `'39'`)                       | `AIPLAN_101`                      |
| `sigunguCode`     | —    | `@Size(max = 10)` (제주시 `'4'` · 서귀포시 `'3'`) | `AIPLAN_115`                      |
| `startDate`       | ✅   | `@NotNull` `YYYY-MM-DD`                           | `AIPLAN_102`                      |
| `endDate`         | ✅   | `@NotNull` `YYYY-MM-DD`                           | `AIPLAN_103` / `AIPLAN_001`(역전) |
| `petId`           | —    | `Long`, **`@Positive` 만**                        | `AIPLAN_105`                      |
| `petIds`          | —    | `Long[]`, **최대 5**                              | `AIPLAN_108` / `AIPLAN_110`       |
| `pinnedPlaceIds`  | —    | `Long[]`, **최대 10**                             | `AIPLAN_109` / `AIPLAN_110`       |
| `preferFavorites` | —    | `Boolean`, 기본 `false`                           | —                                 |
| `budget`          | —    | `Long`, **`@Positive`**                           | `AIPLAN_106`                      |
| `requestNote`     | —    | 500자 이하                                        | `AIPLAN_107`                      |
| `planId`          | —    | `Long`, `@Positive`                               | `AIPLAN_111`                      |
| `regenerateDay`   | —    | `Integer`, `@Positive` (1부터)                    | `AIPLAN_112`                      |

**`petId` 는 필수가 아니다.** `@NotNull` 이 없다 — `petIds` 가 있으면 그것을 쓰고, 둘 다
없으면 **워커가 대표 반려견으로 대신한다**(`effectivePetIds()`). 그래도 **화면은 필수로
둔다**: 어느 아이 기준으로 짠 일정인지 사용자가 알아야 결과를 판단할 수 있다.

**`preferFavorites` · `pinnedPlaceIds` 는 [#128](https://github.com/8llow8llowMe/hondigagae/issues/128)
로 붙였다** (아트보드 05 절). `preferFavorites` 는 **켤 때만 보낸다** — 서버가
`Boolean.TRUE.equals()` 로 받아 기본이 `false` 다. `pinnedPlaceIds` 는 비어 있으면 키를 뺀다.

**필드명이 `includeFavorites` 가 아니라 `preferFavorites` 다.** #128 이슈 본문이 앞 이름으로
적었는데 실측은 `preferFavorites` 다 — 그대로 구현하면 옵션이 조용히 무시된다.

**`petIds` 를 보낸다** ([#128](https://github.com/8llow8llowMe/hondigagae/issues/128)).
**한 마리여도 배열이다** — 서버가 `petIds` 를 `petId` 보다 우선하므로 결과가 같고, 두
경로를 남기면 제출·스냅샷·복원 세 곳에 각각 분기가 생긴다. 세부는
[다견선택-세부명세.md](다견선택-세부명세.md).

**저장은 여전히 한 마리다.** `plan-service` 의 `Plan` 은 `long petId` **단일이고
`PlanCreateRequest` 에도 `petIds` 가 없다.** 그래서 담기 직전에 **판정 기준이 될 한 마리를
사람이 고른다** — 자동으로 고르지 않는 이유는 프롬프트의 "가장 제약이 큰 아이" 가
입장 제한(크기·체중) 축이고 저장 후 날씨 판정은 민감도(더위·추위) 축이라 서로 다르기
때문이다 (S8-8 · 세부명세 D0·D4).

**`planId` + `regenerateDay` 는 이 두 화면에서 보내지 않는다** — 아트보드 03 은 **저장 전
미리보기**에서 하루 재생성을 하는데 계약은 `planId`(이미 저장된 일정)를 요구한다
(S2 · #90). **저장된 일정에서는 보낸다** — 하루 재생성 화면이 그 일을 한다 (S2-1).
회귀는 `lib/ai-plan/submit.test.ts` 가 막는다: 생성 경로의 payload 에 두 필드가 새어
들어가면 실패한다.

응답 `{ submissionStatus: CodeNameDescriptionMetadata, jobId: string }`, **HTTP 202**.

- **반려견 식별자는 `Long` 이다** — 일정 생성과 같이 Snowflake 라 `Number()` 로 바꾸면
  정밀도를 잃는다. **문자열 그대로 실어 보내고 Jackson 이 읽게 한다** (plan 공통명세 S1).
- **`budget` 은 `@Positive` 다. 일정 생성(`@PositiveOrZero`)과 다르다.** `0` 을 보내면 400 이다.
  "상관없음" 은 `0` 이 아니라 **필드 생략**으로 표현한다.
- **`sigunguCode` 는 고른 값만 보낸다** ([#251](https://github.com/8llow8llowMe/hondigagae/issues/251)).
  `null`("제주 전체")이면 키를 뺀다 — 빈 문자열을 보내도 서버가 null 로 접지만, 생략이
  "좁히지 않았다" 를 그대로 말한다. **좁혀서 후보가 없으면 서버가 지역 전체로 넓히지 않고
  `AIPLAN_012` 로 작업을 실패시킨다**(HTTP 200 + `FAILED`) — 그때 화면은 서버 문구 아래에
  "지역을 넓혀 보세요" 를 덧붙인다. 좁힌 지역이 원인일 수 있다는 것은 **화면만 안다**:
  서버는 요청에 `sigunguCode` 가 있었다는 사실을 응답에 싣지 않는다.
- **멱등하다.** 같은 사용자의 같은 요청이 진행 중이면 기존 `jobId` 를 그대로 준다
  (컨트롤러 설명). 중복 제출을 화면이 따로 막을 필요가 없다.

### `GET /api/v1/ai-plans/jobs/{jobId}` — 작업 조회

```ts
type AiPlanJobStatus = {
  jobId: string
  /** PENDING | RUNNING | COMPLETED | FAILED | CANCELED */
  status: CodeNameDescriptionMetadata
  /**
   * 지금 밟고 있는 세부 단계 (#250).
   * CONDITIONS 조건 확인 → CANDIDATES 후보 장소 수집 → WEATHER 날씨 전망 반영 → DRAFTING 일정 구성
   *
   * PENDING 이면 null. 종결 상태에는 마지막으로 밟은 단계가 남는다
   */
  step: CodeNameDescriptionMetadata | null
  /** 1부터. PENDING 이면 null */
  stepOrder: number | null
  /** 전체 단계 수. **화면이 상수로 적지 않는다** — 단계가 늘면 이 값도 는다 */
  totalSteps: number
  /** COMPLETED 일 때만 */
  planDraft: {
    days: { day: number; items: AiPlanScheduleItem[] }[]
    reasons: { code: string; name: string; description: string }[]
  } | null
  /** FAILED 일 때만. **취소는 비어 있다** — 취소는 실패가 아니다 */
  errorCode: string | null
  errorMessage: string | null
}

type AiPlanScheduleItem = {
  /** 'PLACE' | 'MEAL' | 'LODGING' | 'MOVE' — **문자열이지 metadata 가 아니다.** 초안에 'WALK' 는 오지 않는다 (#89) */
  itemType: string
  /** plan-service 에 저장할 때 targetId 로 쓴다. 이동이거나 검증되지 않은 장소면 null */
  placeId: string | null
  title: string
  note: string
}
```

- **작업 실패는 HTTP 200 + `status.code === 'FAILED'`** 다. 5xx 화면으로 다루지 않는다
  (`api-integration-guide.md` §5).
- **타인의 `jobId` 는 404** (`AIPLAN_002`).
- `status` 는 **metadata 객체**라 `name`/`description` 을 그대로 렌더한다. 한국어 매핑 테이블을
  만들지 않는다. **`step` 도 같은 metadata** 이고 같은 규칙을 따른다 (#250).
- **`PENDING` 이면 `step`·`stepOrder` 가 null 이다.** 0 이나 1 로 채우면 화면이 시작한 것으로
  그린다. 판정은 `lib/ai-plan/job.ts` 의 `jobStepProgress()` 하나가 맡는다.

### `POST /api/v1/ai-plans/jobs/{jobId}/cancel` — 작업 취소 (#250)

응답은 **취소된 작업**이라 조회와 같은 모양이다. 본문은 없다.

- **협조적 취소다.** 실행 중인 LLM 호출을 끊지 못하고, 워커가 **단계 경계마다** 상태를 다시 읽어
  스스로 선다. 실익은 가장 비싼 `DRAFTING` 에 들어가기 전에 서는 것이고, 이미 들어갔다면 돌아온
  초안을 버리는 것까지가 전부다 — **즉시 중단을 전제로 화면을 짜지 않는다.**
- **취소는 실패가 아니다.** `errorCode` 를 채우지 않으므로 실패 화면에 태우면 사유 없는
  "일정을 만들지 못했어요" 가 뜬다. `AiPlanCanceled` 로 가른다.
- **멱등 키를 함께 풀어 준다.** 취소 후 같은 조건 재제출이 주된 쓰임이라, 키가 남으면 취소된
  잡을 그대로 돌려받는다. 그래서 `같은 조건으로 다시 만들기` 는 **새 `jobId`** 를 받는다.
- 이미 취소된 작업은 **200 (멱등)**, 완료·실패한 작업은 **409 `AIPLAN_019`** 다. 409 는 오류로
  띄우지 않고 다시 조회해 결과 화면으로 넘긴다 — 요청이 아니라 대상의 상태가 지나간 것이다.
- 타인·없는 `jobId` 는 조회와 같이 **404 `AIPLAN_002`**.

## S3. SSE 구독 — **폴링 앞에 서고, 끊기면 폴링이 받는다** (#91)

백엔드 `GET /ai-plans/jobs/{jobId}/stream`(커밋 `b7daa3a`). 스키마 설명이 "브라우저 기본
`EventSource` 는 Authorization 헤더를 지원하지 않으니 fetch 기반 SSE 클라이언트를 쓰라" 고
안내하지만, **이 저장소에서는 그 안내가 적용되지 않는다** — 브라우저는 게이트웨이를 직접
부르지 않고 `/api/bff` 를 거치며 토큰은 BFF 가 붙인다. 그래서 `EventSource` 로 충분하고
`@microsoft/fetch-event-source` 같은 의존을 들이지 않았다.

**선행 작업은 BFF 개조였다.** `app/api/bff/[...path]/route.ts` 가 응답을 통째로 버퍼링해
(`await response.text()`) 스트림을 그대로 태우면 작업이 끝난 뒤에야 이벤트가 한꺼번에
도착했다 — 폴링만도 못하다. 지금은 요청 `Accept` 가 `text/event-stream` 이면 별도 분기로
빠져 `response.body` 를 그대로 흘려보낸다(`handleEventStream`).

### 계약 실측에서 나온 함정 (전부 이슈 체크리스트에 없던 것)

| 사실                                                                  | 함의                                                                                                                                            |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 이벤트 이름이 **`job-update`** (`AiPlanJobSseStreamer.EVENT_NAME`)    | `onmessage` 로 오지 않는다. `addEventListener('job-update')` 필수 — 하트비트뿐 아니라 **데이터 이벤트도** 마찬가지다                            |
| `data` 가 조회 응답의 **`dataBody` 와 동일** (컨트롤러 설명)          | 공통 래퍼가 없다. `unwrap()` 을 태우면 안 된다 (`parseJobEvent`)                                                                                |
| 종결 상태 후 서버가 `emitter.complete()`                              | `EventSource` 는 서버가 닫은 연결을 **자동 재연결** 대상으로 본다. 종결에서 우리가 `close()` 하지 않으면 무한 재구독이다                        |
| 스트림 엔드포인트가 `produces = text/event-stream`                    | BFF 가 고정으로 박던 `Accept: application/json` 을 그대로 보내면 **406**. 부르기 전에 알아야 해 **요청**으로 판정한다                           |
| 스트림 시작 전 오류(`AIPLAN_002` 404 · 401)는 **일반 JSON** 으로 온다 | 응답 Content-Type 이 SSE 가 아니면 기존 버퍼링 경로로 되돌려 공통 에러 봉투를 유지한다                                                          |
| **`CANCELED` 도 종결이다** (#250)                                     | 취소는 별도 이벤트가 아니라 `CANCELED` 상태 이벤트로 오고 서버가 그 직후 닫는다. `isTerminalJob` 에서 빠지면 취소한 작업에서 무한 재구독이 돈다 |

### 결정

| 항목                 | 결정                                                                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 화면 변경            | **없다.** 구독이 폴링과 **같은 query 캐시**(`aiPlanKeys.job`)에 써서 `ai-plan-job-view.tsx` 는 출처를 모른다                                                                                                 |
| 폴링과의 관계        | 구독이 살아 있으면 2초 폴링을 멈추고 **30초 확인만 남긴다**(`JOB_STREAM_SAFETY_POLL_MS`). 끊기면 2초로 돌아온다. **첫 조회 1회는 구독 여부와 무관하게 돈다** — 구독이 열리기까지의 공백과 SSE 차단 환경 대비 |
| 순서 엇갈림          | `mergeJobUpdate` 가 **종결 상태를 진행 중으로 되돌리지 않는다**. 늦게 도착한 폴링 응답이 완료 화면을 대기 화면으로 되돌리는 것을 막는다                                                                      |
| 401                  | **스트림 시작 전 401 만 재발급 1회 + 재구독.** 흐르는 스트림에 새 토큰을 주입할 방법이 없어 중간 끊김은 폴링에 넘긴다 (폴링은 기존 BFF 경로라 재발급이 거기서 돈다)                                          |
| 토큰 스트립          | **건너뛴다.** 이벤트 `data` 는 `AiPlanJobStatusResponse` — 토큰이 들어올 자리가 없다. 스트립하려면 프레임마다 파싱해야 하고 그 순간 통과가 아니라 변환이 된다                                                |
| 25초 하트비트        | SSE 코멘트 프레임이라 `addEventListener` 로 오지 않는다. 클라이언트 처리 없음                                                                                                                                |
| 게이트웨이 연결 정리 | 스트림 fetch 에 `request.signal` 을 넘긴다. 넘기지 않으면 사용자가 화면을 떠난 뒤에도 `SseEmitter` 가 남는다                                                                                                 |

**폴링을 완전히 끄지 않는 이유**: 백엔드 25초 하트비트는 SSE 코멘트 프레임이라
`addEventListener` 로 오지 않고, 데이터 이벤트는 상태가 바뀔 때만 온다 — **"조용한 것" 과
"끊긴 것" 을 클라이언트가 구분할 수 없다.** 중간 프록시가 조용히 끊어 `EventSource` 가
반열림으로 남으면 `onerror` 가 늦게 오거나 오지 않는데, 그때 폴링이 완전히 꺼져 있으면
폴링 상한까지 화면이 멈춘다. 30초 확인이 그 구멍을 좁힌다. **#495 로 상한이 330초가
되어 이 구멍도 3.7배가 됐다** — 그만큼 이 확인 주기의 몸값이 올랐다.

아트보드는 폴링 2초로 그려져 있으나 **간격 표기는 화면에 드러나지 않아** 구독으로 바꿔도
아트보드와 어긋나지 않는다.

## S4. 폴링

| 항목      | 값                                                                       |
| --------- | ------------------------------------------------------------------------ |
| 간격      | **2초** (아트보드)                                                       |
| 종료 조건 | `status.code` 가 `COMPLETED` 또는 `FAILED`                               |
| 상한      | **330초** (#495). 넘으면 폴링을 멈추고 "오래 걸려요 + 다시 확인" 을 준다 |
| 탭 비활성 | React Query 기본대로 멈춘다 — 돌아오면 재개된다                          |
| 재시도    | 폴링 요청 자체가 5xx 면 다음 주기에 자연히 다시 시도한다                 |

- 상한 근거 (#495): BE 가 잡을 포기하는 시각에 맞춘다. `expireIfStuck` 는 `PENDING` 을
  `createdAt`, `RUNNING` 을 `startedAt` 기준으로 **각각 300초**씩 따로 재므로, 단독 실행
  잡은 최악 300초, 대기열에 선 잡은 `startedAt` 이 최대 245초 늦어 최악 545초다.
  330초는 **단독 실행 갈래**를 덮는 값(300 + 전파 여유 30)이다.
  - 예전 근거였던 "수십 초의 3배 여유(90초)" 는 틀렸다 — dev 실측이 52~80초라 3배가
    아니라 1.1배였고, BE 예산 대비로는 0.3배였다.
  - **줄 선 잡이 상한을 넘기는 것은 알고 받아들인 갈래다.** 그때 뜨는 것은 실패가 아니라
    수동 확인 화면이고, 그 화면이 "만들기는 계속되고 있어요" 라고 말한다. 575초까지
    올려 모든 갈래를 덮는 안은 9분 35초를 말없이 기다리게 하는 대가가 더 커서 접었다.
  - **`AIPLAN_006 JOB_TIMEOUT`(504) 은 서버 쪽 타임아웃이라 화면 상한과 별개다.**
    단독 실행 갈래에서는 상한보다 먼저 도착해 `status=FAILED` 로 폴링을 자연 종료시킨다.
- **`jobId` 가 URL 에 있다.** 새로고침·뒤로가기에서 대기 화면이 살아남는다
  (`architecture-guide.md` §10 — URL 이 기본). 제출 후 `router.replace('/ai-plans/jobs/{jobId}')`.

## S5. 초안 → 확정: `POST /plans` 매핑

**AI 는 제안만 하고 저장·확정은 plan-service 가 한다.** "담기" 가 곧 `POST /plans` 다.

| `PlanCreatePayload`   | 어디서                                |
| --------------------- | ------------------------------------- |
| `petId`               | **담기 패널의 판정 기준 선택** (#128) |
| `areaCode`            | **입력 폼** — `'39'` 고정             |
| `startDate`/`endDate` | **입력 폼**                           |
| `budget`              | **입력 폼** (선택)                    |
| `title`               | **없다 — S8 미결 1**                  |
| `items[]`             | `planDraft.days[].items[]` 를 평탄화  |

항목 매핑:

| `PlanItemRequest` | `AiPlanScheduleItem`              |
| ----------------- | --------------------------------- |
| `day`             | `AiPlanDayItem.day`               |
| `sequence`        | 그 일자 배열의 **인덱스**         |
| `itemType`        | `itemType` 그대로                 |
| `targetId`        | `placeId` — **문자열로 보낸다**   |
| `title`           | `title` (**100자 초과면 자른다**) |
| `memo`            | `note` (**500자 초과면 자른다**)  |
| `startTime`       | **보내지 않는다** (초안에 없다)   |

### 함정 셋

1. **입력 폼 값을 대기 화면까지 들고 가야 한다.** 초안에 반려견·`areaCode`·기간·예산이
   없는데 `POST /plans` 에는 필요하다. 스냅샷은 **`pets[]` 배열**이고, 옛 모양
   (`petId`·`petName`)은 읽을 때 한 마리 배열로 승격한다 — 배포 직후 대기 화면에 있던
   사용자의 담기가 막히지 않게 (세부명세 D2-3). **`jobId` 로는 되살릴 수 없다** — 작업 조회 응답에
   요청 조건이 없다. → 제출할 때 `sessionStorage` 에 `jobId` 를 키로 조건을 저장하고,
   대기 화면이 그것을 읽는다. **없으면 담기를 막고 조건을 다시 받는다**(다른 기기에서
   같은 URL 을 열면 실제로 없다).
2. **~~`itemType: 'WALK'` 에 `placeId` 가 실려 올 수 있다.~~ 해소됐다**
   ([#89](https://github.com/8llow8llowMe/hondigagae/issues/89) ·
   [#252](https://github.com/8llow8llowMe/hondigagae/issues/252)).
   `AiPlanScheduleItem.placeId` 는 "장소 아이디" 인데 `PlanItemRequest.targetId` 는 `WALK` 일 때
   **`walk_course.id`** 였고, 백엔드 `PLACE_TARGET_TYPES` 가 `WALK` 를 검증에서 빼기 때문에
   **틀린 id 가 조용히 저장됐다.** FE 는 `WALK` 의 `targetId` 를 보내지 않는 우회를 뒀었다.

   BE 가 원인을 없앴다 — 초안 프롬프트 스키마에서 `WALK` 를 빼고
   (`LlmPlanDraftResponse`: `PLACE`·`MEAL`·`LODGING`·`MOVE` 넷), 그럼에도 모델이 `WALK` 에
   장소를 실으면 `OllamaLlmAdapter.resolveItemType` 이 `PLACE` 로 바로잡는다. 모르는 코드도
   같은 자리에서 `PLACE` 로 접는다.
   → **초안의 모든 `itemType` 은 `place.id` 를 `targetId` 로 받는 유형이다.** 유형으로 가리지 않고
   `placeId` 가 있으면 그대로 보낸다. **산책 일정은 `PLACE` 로 오고 성격은 `title`·`note` 에 담긴다** —
   `itemTypeLabel('WALK')` 은 남긴다(저장된 일정에는 사용자가 직접 만든 `WALK` 항목이 있다).

3. **`POST /plans` 는 `items` 를 함께 받고 `PLAN_004` 로 거부할 수 있다.** 초안의 장소가
   그 사이 delisting 되면 저장 전체가 실패한다. 그때 **초안을 버리지 않고** 해당 항목을 빼고
   다시 담을 수 있게 한다.

   **판정 근거를 404 로 잡으면 안 된다** (이슈 [#146](https://github.com/8llow8llowMe/hondigagae/issues/146)).
   백엔드가 `findVisiblePlaceIds` 로 거르는 것이 둘인데 **상세 응답에서 드러나는 모양이 다르다**:

   | 사유                       | `GET /places/{placeId}`                                                |
   | -------------------------- | ---------------------------------------------------------------------- |
   | 원천에서 사라짐(delisting) | **200 + `delisted: true`** — 기존 일정이 참조하는 장소라 계속 응답한다 |
   | 병합(`mergedIntoId`)       | **404**                                                                |

   초기 구현이 404 만 봤고, 그래서 **정작 delisted 는 한 번도 잡지 못했다** — 경고 없이
   담기에서 400 을 맞았다. 판정은 `lib/place/availability.ts` 의 `isPlaceUnavailable` 하나가 갖는다.

## S6. 결과 화면이 말해야 하는 것

- **`days.length` 가 여행 일수보다 적을 수 있다.** `status` 는 `COMPLETED` 인데 일부 일자가
  비는 경우다. **감추지 않는다** — "N일 중 M일만 만들었어요" 를 그대로 쓰고, 나머지는 담은
  뒤 일정 상세에서 채우라고 안내한다. 아트보드 02 ③ 의 태도를 계약이 허용하는 만큼만 옮긴 것이다.
- 항목 행의 `제주시 한림읍 · 야외 · 4.1km` 는 초안에 없다 → **항목당 `GET /places/{placeId}`**
  로 보강한다. 방식·캐시 키·실패 처리는 **일정 상세와 같다**
  (`features/plan/일정상세-세부명세.md` D3). `placeId` 가 null 인 항목은 부르지 않는다.
  주소와 **좌표를 같은 응답에서 꺼낸다** — 좌표는 거리 계산의 유일한 출처다 (#100).
- 거리는 **직선거리**고 그 낱말을 반드시 붙인다. 계산은 `lib/geo/distance.ts`,
  기준 판정은 `lib/ai-plan/draft-distance.ts` 다 (#100).
  - **기준은 직전 항목 하나뿐이다.** 일정 상세는 일자의 첫 항목을 _앞선 날의 숙소_ 기준으로
    재지만(`lodgingBasisFor`), 초안의 `itemType` 은 **LLM 산출 raw string** 이라 숙소를
    믿고 고를 수 없다 — 숙소가 아닌 항목을 "숙소에서" 라고 말하게 된다. 담은 뒤 일정
    상세는 enum 으로 정규화된 값을 보므로 그쪽에서 숙소 기준이 살아난다
  - **일자 경계를 넘겨 재지 않는다.** 전날 마지막 → 다음 날 첫 항목 사이에는 숙박이 있다
  - 좌표를 모르는 항목(보강 실패 · `MOVE` 처럼 `placeId` 가 없는 항목)은 **거리 줄이
    사라진다.** `0m` 를 쓰지 않는다 — "같은 자리" 와 "모른다" 는 다르다
  - 30km 이상은 경고 톤 + `— 하루 이동이 깁니다.` 문장이다. 임계값은
    `LONG_TRIP_THRESHOLD_M` 하나이며 화면마다 숫자를 두지 않는다
- `reasons` 는 **초안 전체에 대한 XAI** 다. 일자별이 아니다 → 상단에 한 번 `ReasonList` 로 낸다.
- `note` 는 항목별 이유다 → 행 아래 한 줄.

## S9. 구현하며 확정한 것 (이슈 #84)

명세 작성 시점에 없던 판단이다. 근거는 전부 **백엔드 소스 실측**이다.

| #   | 항목                                             | 결정                                                                                                                                                                                                                                                                                                                                                   |

### 미검증으로 남은 것

- **Swagger 실호출 대조를 못 했다** — 백엔드가 로컬에 뜨지 않는다. 계약은 전부 소스 실측
  기준이며 [#67](https://github.com/8llow8llowMe/hondigagae/issues/67) 로 이월한다.
- `POST /ai-plans` 의 **202 를 `unwrap()` 이 통과시키는지** 는 mock 으로만 확인했다
  (`dataHeader.success` 로 판정하므로 통과한다 — 실서버에서 재확인).
- `AIPLAN_003`/`AIPLAN_004`(503 대기열) 화면은 **mock 이 흉내 내지 않는다.** 서버가
  `resultMessage` 를 친절하게 주므로 `FormAlert` 로 그대로 노출하는 것까지만 배선했다.
- **탭이 비활성이면 폴링이 멈춘다** (React Query 기본, 명세 S4 가 의도한 동작). 브라우저
  프리뷰 페인이 hidden 이면 `document.hidden === true` 라 검증 시 폴링이 안 도는 것으로
  보인다 — 제품 결함이 아니다.
