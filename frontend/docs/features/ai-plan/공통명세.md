## S1. 계약

### `POST /api/v1/ai-plans` — 제출 (202)

| 필드          | 필수 | 제약                    | 오류 코드                   |
| ------------- | ---- | ----------------------- | --------------------------- |
| `areaCode`    | ✅   | 문자열 (제주 = `'39'`)  | `AIPLAN_100`                |
| `startDate`   | ✅   | `YYYY-MM-DD`            | `AIPLAN_100`                |
| `endDate`     | ✅   | `YYYY-MM-DD`            | `AIPLAN_100` / `AIPLAN_001` |
| `petId`       | ✅   | `Long`, **양수**        | `AIPLAN_100`                |
| `budget`      | —    | `Long`, **`@Positive`** | `AIPLAN_100`                |
| `requestNote` | —    | 500자 이하              | `AIPLAN_100`                |

응답 `{ submissionStatus: CodeNameDescriptionMetadata, jobId: string }`, **HTTP 202**.

- **`petId` 는 `Long` 이다** — 일정 생성과 같이 Snowflake 라 `Number()` 로 바꾸면 정밀도를
  잃는다. **문자열 그대로 실어 보내고 Jackson 이 읽게 한다** (plan 공통명세 S1).
- **`budget` 은 `@Positive` 다. 일정 생성(`@PositiveOrZero`)과 다르다.** `0` 을 보내면 400 이다.
  "상관없음" 은 `0` 이 아니라 **필드 생략**으로 표현한다.
- **`sigunguCode` 가 없다.** `PlanCreateRequest` 에는 있지만 이쪽에는 없다 → **지역을 제주시 /
  서귀포시로 좁힐 수 없다** (S2).
- **멱등하다.** 같은 사용자의 같은 요청이 진행 중이면 기존 `jobId` 를 그대로 준다
  (컨트롤러 설명). 중복 제출을 화면이 따로 막을 필요가 없다.

### `GET /api/v1/ai-plans/jobs/{jobId}` — 작업 조회

```ts
type AiPlanJobStatus = {
  jobId: string
  /** PENDING | RUNNING | COMPLETED | FAILED */
  status: CodeNameDescriptionMetadata
  /** COMPLETED 일 때만 */
  planDraft: {
    days: { day: number; items: AiPlanScheduleItem[] }[]
    reasons: { code: string; name: string; description: string }[]
  } | null
  /** FAILED 일 때만 */
  errorCode: string | null
  errorMessage: string | null
}

type AiPlanScheduleItem = {
  /** 'PLACE' | 'MEAL' | 'LODGING' | 'WALK' | 'MOVE' — **문자열이지 metadata 가 아니다** */
  itemType: string
  /** plan-service 에 저장할 때 targetId 로 쓴다. 이동이거나 검증되지 않은 장소면 null */
  placeId: string | null
  title: string
  note: string
}
```

- **작업 실패는 HTTP 200 + `status.code === 'FAILED'`** 다. 5xx 화면으로 다루지 않는다
  (`api-integration-guide.md` §5).
- **타인의 `jobId` 는 404** (`AIPLAN_002`).
- `status` 는 **metadata 객체**라 `name`/`description` 을 그대로 렌더한다. 한국어 매핑 테이블을
  만들지 않는다.

### `GET /api/v1/ai-plans/jobs/{jobId}/stream` — SSE (신설)

**이번 이슈에서 쓰지 않는다. S3 참고.**

## S2. 아트보드에 있으나 **구현하지 않는 것**

이 화면은 아트보드와 계약의 격차가 가장 크다. 뺀 것을 전부 적는다.

| 아트보드                                     | 빼는 이유                                                                                                                         |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **진행 단계 5개** (`3 / 5 단계`)             | `AiPlanJobStatus` 는 `PENDING`·`RUNNING`·`COMPLETED`·`FAILED` 넷뿐이다. **세부 단계가 계약에 없다** — 지어내면 거짓 진행률이 된다 |
| **`약 12초 남음`**                           | 남은 시간 필드가 없다. 대신 제출 화면의 "20초쯤 걸려요" 를 유지한다 (그건 우리가 하는 약속이지 서버 값이 아니다)                  |
| **부분 성공 (`3일 중 2일만`)**               | `status` 에 부분 성공이 없다. `COMPLETED` 아니면 `FAILED` 다. `days` 가 일수보다 짧을 수는 있어 **그건 표시한다**(S6)             |
| **`이 날 다시 만들기` · `전체 다시 만들기`** | **재생성 API 가 없다.** `POST /ai-plans` 로 새로 제출하는 것뿐이라, "전체 다시" 만 남기고 일자 단위 재생성은 뺀다                 |
| **`말로 고치기` (자연어 수정)**              | 수정 API 가 없다                                                                                                                  |
| **`취소`**                                   | 작업 취소 API 가 없다. 대기 화면을 벗어나는 것으로 갈음하고, **취소라고 부르지 않는다**                                           |
| **`알림 받고 나가기`**                       | 알림 기능이 없다                                                                                                                  |
| **일자별 적합도 배지 (`주의` · `양호`)**     | 판정은 `GET /plans/{planId}/weather` 인데 **담기 전에는 `planId` 가 없다.** 초안에 판정을 붙일 방법이 없다                        |
| **`지역: 제주시 / 서귀포시`**                | `AiPlanCreateRequest` 에 `sigunguCode` 가 없다 → **제주 전체 고정.** 선택지가 하나면 컨트롤을 두지 않는다 (plan S9 규칙)          |
| **`이 날 산책`**                             | 대상 `placeId` 를 고를 근거가 초안에 없다 (`representativePlaceId` 는 일정 판정 응답에만 있다)                                    |

**뺀 것 중 넷은 BE 후속 요청으로 뗀다**: 작업 세부 단계, 일자 단위 재생성, 작업 취소,
`sigunguCode`. 나머지는 기능 자체가 없다.

## S3. SSE 는 이번에 쓰지 않는다 — **BFF 가 스트림을 통과시키지 못한다**

백엔드에 `GET /ai-plans/jobs/{jobId}/stream` 이 생겼다(커밋 `b7daa3a`). 스키마 설명이
"브라우저 기본 `EventSource` 는 Authorization 헤더를 지원하지 않으니 fetch 기반 SSE
클라이언트를 쓰라" 고 안내한다.

**이 저장소에서는 그 안내가 그대로 적용되지 않는다.** 브라우저는 게이트웨이를 직접 부르지
않고 `/api/bff` 프록시를 거치며, 토큰은 BFF 가 붙인다 — 그래서 `EventSource` 로도 헤더 문제는
없다. **문제는 프록시 자체다.**

`app/api/bff/[...path]/route.ts` 는

```ts
const text = await response.text() // ← 본문을 통째로 버퍼링한다
return NextResponse.json(stripped.body, { status: result.status })
```

라서 **스트림이 끝날 때까지 아무것도 흘려보내지 않는다.** SSE 를 붙이면 작업이 끝난 뒤에야
이벤트가 한꺼번에 도착해 폴링만도 못하다.

→ **이번 이슈는 폴링만 쓴다.** 아트보드도 폴링 2초로 그려져 있다.
**SSE 는 BFF 스트리밍 통과 작업과 함께 별도 이슈로 뗀다.**

## S4. 폴링

| 항목      | 값                                                               |
| --------- | ---------------------------------------------------------------- |
| 간격      | **2초** (아트보드)                                               |
| 종료 조건 | `status.code` 가 `COMPLETED` 또는 `FAILED`                       |
| 상한      | **90초**. 넘으면 폴링을 멈추고 "오래 걸려요 + 다시 확인" 을 준다 |
| 탭 비활성 | React Query 기본대로 멈춘다 — 돌아오면 재개된다                  |
| 재시도    | 폴링 요청 자체가 5xx 면 다음 주기에 자연히 다시 시도한다         |

- 상한 근거: 백엔드 스키마가 "로컬 LLM 기준 수십 초" 라 한다. 90초는 그 3배 여유다.
  **`AIPLAN_006 JOB_TIMEOUT`(504) 은 서버 쪽 타임아웃이라 화면 상한과 별개다.**
- **`jobId` 가 URL 에 있다.** 새로고침·뒤로가기에서 대기 화면이 살아남는다
  (`architecture-guide.md` §10 — URL 이 기본). 제출 후 `router.replace('/ai-plans/jobs/{jobId}')`.

## S5. 초안 → 확정: `POST /plans` 매핑

**AI 는 제안만 하고 저장·확정은 plan-service 가 한다.** "담기" 가 곧 `POST /plans` 다.

| `PlanCreatePayload`   | 어디서                               |
| --------------------- | ------------------------------------ |
| `petId`               | **입력 폼** (초안에 없다)            |
| `areaCode`            | **입력 폼** — `'39'` 고정            |
| `startDate`/`endDate` | **입력 폼**                          |
| `budget`              | **입력 폼** (선택)                   |
| `title`               | **없다 — S8 미결 1**                 |
| `items[]`             | `planDraft.days[].items[]` 를 평탄화 |

항목 매핑:

| `PlanItemRequest` | `AiPlanScheduleItem`              |
| ----------------- | --------------------------------- |
| `day`             | `AiPlanDayItem.day`               |
| `sequence`        | 그 일자 배열의 **인덱스**         |
| `itemType`        | `itemType` 그대로                 |
| `targetId`        | `placeId` — **문자열로 보낸다**   |
| `title`           | `title` (**100자 초과면 자른다**) |
| `memo`            | `note` (**500자 초과면 자른다**)  |
| `startTime`       | **보내지 않는다** (초안에 없다)   |

### 함정 셋

1. **입력 폼 값을 대기 화면까지 들고 가야 한다.** 초안에 `petId`·`areaCode`·기간·예산이
   없는데 `POST /plans` 에는 필요하다. **`jobId` 로는 되살릴 수 없다** — 작업 조회 응답에
   요청 조건이 없다. → 제출할 때 `sessionStorage` 에 `jobId` 를 키로 조건을 저장하고,
   대기 화면이 그것을 읽는다. **없으면 담기를 막고 조건을 다시 받는다**(다른 기기에서
   같은 URL 을 열면 실제로 없다).
2. **`itemType: 'WALK'` 에 `placeId` 가 실려 올 수 있다.** `AiPlanScheduleItem.placeId` 는
   "장소 아이디" 인데 `PlanItemRequest.targetId` 는 `WALK` 일 때 **`walk_course.id`** 다.
   백엔드 `PLACE_TARGET_TYPES` 가 `WALK` 를 검증에서 빼기 때문에 **틀린 id 가 조용히 저장된다.**
   → **`WALK` 항목은 `targetId` 를 보내지 않는다.** BE 이슈로도 뗀다.
3. **`POST /plans` 는 `items` 를 함께 받고 `PLAN_004` 로 거부할 수 있다.** 초안의 장소가
   그 사이 delisting 되면 저장 전체가 실패한다. 그때 **초안을 버리지 않고** 해당 항목을 빼고
   다시 담을 수 있게 한다.

## S6. 결과 화면이 말해야 하는 것

- **`days.length` 가 여행 일수보다 적을 수 있다.** `status` 는 `COMPLETED` 인데 일부 일자가
  비는 경우다. **감추지 않는다** — "N일 중 M일만 만들었어요" 를 그대로 쓰고, 나머지는 담은
  뒤 일정 상세에서 채우라고 안내한다. 아트보드 02 ③ 의 태도를 계약이 허용하는 만큼만 옮긴 것이다.
- 항목 행의 `제주시 한림읍 · 야외 · 4.1km` 는 초안에 없다 → **항목당 `GET /places/{placeId}`**
  로 보강한다. 방식·캐시 키·실패 처리는 **일정 상세와 같다**
  (`features/plan/일정상세-세부명세.md` D3). `placeId` 가 null 인 항목은 부르지 않는다.
- `reasons` 는 **초안 전체에 대한 XAI** 다. 일자별이 아니다 → 상단에 한 번 `ReasonList` 로 낸다.
- `note` 는 항목별 이유다 → 행 아래 한 줄.

## S7. 상태 화면

| 상태                        | 표시                               | 문구 (확정)                                                                            |
| --------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------- |
| 제출 중                     | 버튼 `disabled` + 진행             | —                                                                                      |
| `PENDING` / `RUNNING`       | 진행 표시 + **서버 `description`** | 서버 문구 그대로. **단계 목록을 만들지 않는다**                                        |
| 폴링 30초 초과              | 안내 추가                          | `아직 만들고 있어요. 조금만 더 기다려 주세요.`                                         |
| 폴링 90초 초과              | 폴링 중단 + 수동 확인              | `시간이 오래 걸리고 있어요.` + `다시 확인하기`                                         |
| `COMPLETED`                 | 미리보기                           |                                                                                        |
| `COMPLETED` · `days` 부족   | 미리보기 + 안내                    | `{총}일 중 {만든}일만 만들었어요.`                                                     |
| `FAILED`                    | **`ErrorState` 를 쓰지 않는다**    | 서버 `errorMessage` 그대로 + `같은 조건으로 다시 시도` · `조건 바꾸기` · `직접 만들기` |
| 작업 404 (`AIPLAN_002`)     | `not-found` 성격                   | `찾을 수 없는 작업이에요` + `/ai-plans/new` 링크                                       |
| 제출 5xx (`AIPLAN_003/004`) | `FormAlert` + 재시도               | 서버 `resultMessage` 그대로 (대기열 가득참 안내가 이미 친절하다)                       |
| 담기 실패 `PLAN_004`        | 항목 지목 + 빼고 담기              | `일부 장소를 더 이상 담을 수 없어요.`                                                  |
| 반려견 0마리                | 폼 대신 등록 유도                  | plan 만들기와 같은 문구 재사용                                                         |

**`FAILED` 에 "일시 장애" 문구를 쓰지 않는다.** 5xx 가 아니고, 실패 이유가 조건 문제일 수
있다(`AIPLAN_012 NO_PLACE_CANDIDATES` — "조건에 맞는 장소를 찾지 못했습니다"). **입력 조건은
그대로 남기고** 재시도·조건 변경·직접 만들기 세 갈래를 준다 (아트보드 02 ②).

## S8. 미결 사항

| 5   | SSE                                                 | ① 이번엔 폴링 ② BFF 스트리밍까지 이번에                                                | **①.** S3 — BFF 개조는 이 화면보다 넓은 작업이다                                                    |
| 6   | 진행 단계 5개                                       | ① 서버 `description` 만 ② 우리가 단계를 지어낸다                                       | **①.** 지어낸 진행률은 거짓말이다. BE 후속 요청으로 뗀다                                            |
