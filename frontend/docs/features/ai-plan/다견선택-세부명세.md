## 이 문서의 범위

**AI 일정 생성에서 반려견을 여러 마리 고를 수 있게 한다.** 백엔드 생성 계약이 이미
다견을 지원하는데 FE 가 단일 `petId` 만 보내 기능이 잠겨 있던 것을 연다.

**범위 밖 (의도적)**

| 항목                       | 이유                                                                                                                                                  |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 일정 자체를 다견으로 저장  | `PlanCreateRequest.petId` 가 `@NotNull` 단일이고 `PlanEntity.petId` 도 단일 컬럼이다. **BE 선행이 필요하다** — #128 에 기록했고 추적 이슈는 아직 없다 |
| 날씨·산책 판정의 다견 기준 | `PlanWeatherProcessor:51` 이 `plan.petId()` 하나로 조회한다. 위와 같은 선행 조건                                                                      |
| 하루 재생성                | #128 의 다른 항목이고 #90 에 막혀 있다                                                                                                                |
| 일정 목록의 반려견 필터    | **이미 다중이다** (`PlanFilters.petIds`, 클라이언트 필터). 손대지 않아도 동작한다                                                                     |

## D0. 무엇이 이미 되어 있는가 (실측)

이 작업이 "새 기능 구현" 이 아니라 **잠금 해제**인 이유다.

| 단계      | 상태          | 근거                                                                                                                                                                            |
| --------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 생성 요청 | **다견 완비** | `AiPlanCreateRequest.petIds` `@Size(max = 5)`. `effectivePetIds()` 가 _"`petIds` 가 있으면 그것을, 없으면 `petId`, 둘 다 없으면 대표견"_                                        |
| 조건 조회 | **다견 완비** | `PetConditionClientAdapter.findConditions(memberId, petIds)` 가 N 마리를 가져온다                                                                                               |
| 프롬프트  | **다견 완비** | `AiPlanPromptFactory#appendPetSection` 이 `반려견 1`…`반려견 N` 을 나열하고 마지막에 지시를 붙인다: `입장 제한(크기·체중)은 가장 큰 크기와 가장 무거운 체중 기준으로 판정할 것` |
| 저장      | **단일**      | `PlanCreateRequest.petId` `@NotNull`                                                                                                                                            |
| 판정      | **단일**      | `PlanWeatherProcessor:51` `petConditionQueryPort.findCondition(memberId, plan.petId())`                                                                                         |

아트보드 01 이 요구한 **"더 민감한 아이 기준"** 은 백엔드 프롬프트에 이미 들어 있다.
FE 가 그 규칙을 복제하지 않는다.

### 두 축이 다르다 — 자동 선택을 하지 않는 이유

프롬프트의 "가장 제약이 큰 아이" 는 **입장 제한(크기·체중)** 축이다. 저장 후 날씨 판정이
쓰는 것은 **민감도(더위·추위·소음)** 축이다. _가장 큰 아이가 더위에 가장 약한 아이라는
보장이 없다._ 그래서 담기 기준을 FE 가 자동으로 고르지 않고 **사람이 정한다** (D4).

## D1. 아트보드에서 벗어난 것

| 이탈                                           | 근거                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **반려견 선택을 라디오에서 체크박스로 바꾼다** | 아트보드 01 근거 블록은 _"반려견은 라디오 — 한 마리 / 일정은 `petId` 하나에 붙는다 / 두 마리를 함께 고르게 하면 **판정 기준이 모호해진다** / 다견 여행은 '더 민감한 아이 기준' 문구와 함께 별도 설계가 필요하다"_ 라고 적었다. **반대 근거가 "모호해진다" 하나이고, 이 설계가 그것을 정면으로 없앤다** — 담기 직전에 판정 기준을 _사람이 명시적으로 고르므로_ 모호한 구간이 생기지 않는다. 아트보드가 말한 "별도 설계" 의 API 쪽은 백엔드가 이미 만들어 두었다 (D0) |

**아트보드 갱신은 후속으로 둔다.** 이 문서가 이탈 근거의 정본이고, 아트보드가 갱신되면
이 표를 지운다.

## D2. 데이터 흐름

```text
조건 폼              제출                 스냅샷(sessionStorage)        담기
petIds[]     →  petIds 전송   →   pets: [{petId, name}]   →   기준 1마리 → petId
```

### D2-1. 타입 변경 4곳

| 대상                    | 지금                     | 바뀜                                      |
| ----------------------- | ------------------------ | ----------------------------------------- |
| `AiPlanFormValues`      | `petId: string`          | `petIds: string[]`                        |
| `AiPlanSubmitPayload`   | `petId: string`          | `petIds: string[]`                        |
| `AiPlanRequestSnapshot` | `petId` · `petName`      | `pets: { petId: string; name: string }[]` |
| `draftToPlanPayload()`  | `snapshot.petId` 를 읽음 | 기준 `petId` 를 **인자로 받음**           |

### D2-2. 한 마리여도 `petIds` 로 통일한다

`effectivePetIds()` 가 `petIds` 를 우선하므로 결과가 같다. 두 경로를 남기면
**"1마리는 `petId`, 2마리는 `petIds`" 분기가 제출·스냅샷·복원 세 곳에 각각 생긴다.**

이 결정은 기존 잠금 하나를 **의도적으로 뒤집는다**: `submit.test.ts` 의
_"아직 보내지 않는 필드가 새어 나가지 않는다 — `petIds`·`planId`·`regenerateDay`"_.
그 테스트는 지금 이 변경을 막으려고 있던 것이 아니라 **미완성 필드가 새는 것**을 막으려고
있었다. `petIds` 만 잠금에서 빼고 `planId`·`regenerateDay` 는 그대로 둔다 — 그 둘은 여전히
미완성이다 (#90).

### D2-3. 옛 스냅샷을 승격해서 읽는다

`sessionStorage` 에 이미 `{ petId, petName }` 모양으로 저장된 **진행 중인 작업**이 있다.
`toSnapshot()` 이 새 모양만 받으면 `readAiPlanRequest` 가 `null` 을 주고, 배포 직후 대기
화면에 있던 사용자는 **담기를 할 수 없다** (명세 S5 함정 1 의 "조건이 없으면 담기를 막는다"
경로로 떨어진다).

옛 모양이면 `pets: [{ petId, name: petName }]` 로 올려 읽는다. 승격은 읽기에서만 하고
쓰기는 항상 새 모양이다 — 양방향 호환을 만들면 지울 시점이 사라진다.

## D3. 조건 입력 화면

`RadioGroup` → **체크박스 그룹**.

### D3-1. `PetCheckboxGroup` 을 feature 안에 만든다

`src/components/checkbox.tsx` 는 **단일 체크박스**다 — 그룹 시맨틱이 없다. `RadioGroup` 이
갖고 있는 것(`<fieldset>` + `<legend>`, `fieldErrorId()` 공유, 44px 터치 영역,
`bg-row-selected` 선택 틴트, `aria-invalid` 를 fieldset 에만)을 폼 파일에 그대로 베끼면
**`component-guide.md` §7 의 오류 배선 규칙이 두 벌이 된다.**

그래서 `RadioGroup` 을 그대로 본뜬 그룹 컴포넌트를 만들되, **`src/features/ai-plan/` 안에
둔다** — `component-guide.md` §9 가 _"2곳 이상의 feature 에서 쓰이면 `src/components/` 로
올린다. **1곳이면 feature 안에 둔다**"_ 라고 정했고 지금 사용처는 하나다. 두 번째 사용처가
생기면 그때 승격하고 도메인 용어(`pet`)를 prop 이름에서 뗀다.

**`RadioGroup` 을 확장하지 않는다.** 단일/다중은 `value: T` ↔ `values: T[]` 로 타입이
갈리고, `name` 공유·`role` ·키보드 이동 규칙이 라디오와 체크박스에서 다르다. optional prop
하나로 두 동작을 겸하게 만들면 §9 의 "기본 동작을 바꾸는 변경" 에 해당한다.

### D3-2. 규칙

**문구는 그대로 쓴다.** `messages.aiPlan.fieldPet` 이 이미 `함께 갈 반려견` 이고
`fieldPetHint` 도 마릿수를 전제하지 않는다 — 복수로 바꿀 말이 없다.

| 항목                    | 규칙                                                                                                                                                |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 상한                    | **5** — BE `@Size(max = 5)` 이자 회원당 반려견 상한(`MAX_PET_COUNT`)과 같다. 실질적으로 "전부 고르기" 가 가능하므로 **화면이 상한을 말하지 않는다** |
| 하한                    | 1. 0 마리는 검증 오류다 (기존 `petId` 필수 검증 자리를 그대로 쓴다)                                                                                 |
| 반려견이 1마리뿐인 회원 | 지금처럼 자동 선택된다 (`pets.length === 1`). 화면이 사실상 그대로다                                                                                |
| 반려견이 0마리          | 지금과 같다 — 폼을 채울 수 없어 등록으로 안내한다                                                                                                   |

**상한에 닿았을 때 남은 체크박스를 비활성하지 않는다.** 5마리를 등록한 회원만 닿을 수
있고 그때는 이미 전부 고른 상태라, 비활성 상태가 화면에 나타날 일이 없다.

## D4. 담기 — 판정 기준 선택 (**철회됨 · #174**)

> **이 절의 설계는 더 이상 코드에 없다.** [#152](https://github.com/8llow8llowMe/hondigagae/issues/152)
> 가 `PlanCreateRequest.petIds` 를 받으면서 담기가 동반한 아이를 **전부** 싣게 됐고
> ([#174](https://github.com/8llow8llowMe/hondigagae/issues/174)), 고를 것이 없어져 컨트롤을 걷었다.
> 서버가 `petIds` 의 **첫 번째를 대표 반려견**으로 삼으므로 조건 입력에서 체크한 순서가
> 저장까지 그대로 간다.
>
> **아래는 왜 한때 사람에게 고르게 했는지의 기록으로 남긴다.** 이 판단이 없었다면 두 마리로
> 만든 초안이 저장되는 순간 한 마리가 되는 것을 아무도 모른 채 넘어갔을 것이다.

**`petIds.length >= 2` 일 때만** 담기 패널에 `RadioGroup` 한 줄이 나타난다.
**1마리면 렌더하지 않는다** — 지금 화면과 동일하다.

| 항목   | 규칙                                                                            |
| ------ | ------------------------------------------------------------------------------- |
| 기본값 | **먼저 고른 아이** (스냅샷 `pets` 의 첫 번째)                                   |
| 문구   | 무엇이 걸린 일인지 말한다 — 저장 후 날씨·산책 판정이 이 아이 기준이 된다는 사실 |
| 위치   | 제목 입력 아래, 담기 버튼 위                                                    |

### 기본값이 대표견이 아닌 이유 (실측으로 바뀐 결정)

설계 단계에서는 "고른 아이 중 대표견" 을 기본값으로 두려 했으나, **대기 화면
(`ai-plan-job-view.tsx`)이 반려견 목록을 전혀 갖고 있지 않다.** 대표견을 알려면
`usePetList()` 를 이 화면에 새로 붙여야 하고, 그것은 **기본값 하나를 위해 화면의 데이터
의존을 늘리는 것**이다 — 조회가 늦거나 실패하면 기본값이 흔들린다.

스냅샷 `pets` 의 순서는 사용자가 체크한 순서다. 그래서 **먼저 고른 아이**를 기본값으로
쓴다. 설명 가능한 규칙이고, 어차피 바로 옆에서 바꿀 수 있다.

### 왜 담기 시점인가

초안을 **본 뒤에** 하는 판단이다. "실내 위주로 나왔네 → 더위 타는 초코 기준으로 보자" 가
자연스럽지, 초안을 보기도 전에 기준을 정하라는 것은 이르다. 조건 폼은 아트보드 01 이 이미
길다고 보고 예산을 칩으로 줄인 화면이라 컨트롤을 하나 더 얹지 않는다.

## D5. 문구

**`defaultPlanTitle` 을 고치지 않는다.** 이름을 `·` 로 이어 `몽실이·초코` 를 넘기면
`withCompanionParticle` 이 **마지막 글자의 받침**을 보므로 `몽실이·초코와 제주 2박 3일` 이
나온다(실측 확인: `코` 는 받침 없음 → `와`). 조사 로직을 복제하지 않는다.

요약 줄(`ai-plan-job-view.tsx:385`)도 같은 이어붙인 문자열을 쓴다.

3. **아트보드 갱신 시점** — D1 의 이탈 표가 정본을 대신하고 있다.
