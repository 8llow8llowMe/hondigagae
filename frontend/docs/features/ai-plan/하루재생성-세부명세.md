## 이 문서의 범위

**이미 저장된 일정에서 하루만 AI 로 다시 짠다.** 백엔드 생성 계약이 `planId` + `regenerateDay`
를 이미 받는데 FE 에 진입점이 없어 기능이 잠겨 있던 것을 연다.

**범위 밖 (의도적)**

| 항목                                 | 이유                                                                                                                                                                                                                                                                                |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **저장 전 미리보기에서 하루 재생성** | 계약이 `planId`(이미 저장된 일정)를 요구한다. 아트보드 03 이 그린 위치이고 [#90](https://github.com/8llow8llowMe/hondigagae/issues/90) 이 선행이다                                                                                                                                  |
| 하루 재생성의 취소                   | 계약에는 생겼다([#250](https://github.com/8llow8llowMe/hondigagae/issues/250)). **끝난 뒤 갈 곳이 달라 이 화면에는 두지 않았다** — 새 일정은 "같은 조건으로 다시" 가 답이지만 여기는 일정과 그 날이 그대로 남아 있어 제출 화면으로 되돌리는 것이 맞다                               |
| `sigunguCode` 전달                   | 계약에는 생겼다([#251](https://github.com/8llow8llowMe/hondigagae/issues/251)). **저장된 일정에 실을 값이 아직 없다** — 담기가 이제 `sigunguCode` 를 보내므로 앞으로 만드는 일정은 갖게 되지만, 기존 일정은 전부 `null` 이다. 재생성이 무엇을 물려받을지는 그 값이 쌓인 뒤에 정한다 |
| 일정 전체 재생성                     | 조건 입력(`/ai-plans/new`)이 이미 그 일을 한다. 새 일정이 만들어질 뿐이다                                                                                                                                                                                                           |
| 되돌리기(undo)                       | 계약에 일자 이력이 없다. **되돌릴 수 없다는 사실을 확정 전에 말하는 것**으로 대신한다 (R5)                                                                                                                                                                                          |

### 제출이 물려받는 두 전제 (필수)

**재생성은 `POST /ai-plans` 를 재사용하므로 그 API 의 전제를 그대로 물려받는다.**
`AiPlanJobProcessor.submitPlan:55-62` 이 `validateRegenerateRequest` **앞에서** 본다.

| 전제                                                        | 코드               | 결과                                                           |
| ----------------------------------------------------------- | ------------------ | -------------------------------------------------------------- |
| `startDate` 가 오늘보다 이전이면 안 된다                    | `AIPLAN_017` (400) | **이미 시작하거나 끝난 여행은 하루 재생성을 쓸 수 없다**       |
| `ChronoUnit.DAYS.between(start, end) + 1 > 10` 이면 안 된다 | `AIPLAN_018` (400) | **11일 이상 일정은 쓸 수 없다** — plan-service 상한은 30일이다 |

제출 본문은 **저장된 일정의 `startDate`/`endDate` 를 그대로 싣는다**(`toDayRegeneratePayload`).
그래서 두 전제는 "잘못 입력하면 나는 오류" 가 아니라 **일정 단위의 영구 제약**이다 —
_"2일차를 여행 중인데 내일이 비 예보라 3일차를 다시 짠다"_ 는 **이 계약으로 할 수 없다.**

**그래서 화면이 진입점을 내지 않는다.** 판정은 `lib/ai-plan/regenerate.ts` 의
`dayRegenerateBlock(plan, today)` 하나가 갖고, **일정 상세(진입점)와 재생성 뷰(주소 직접
입력)가 같은 함수를 쓴다.** 뷰는 이유를 `EmptyState` 로 말한다 — 주소가 맞고 그 일자도
있으므로 말없이 되돌려 보내면 버튼이 고장 난 것처럼 보인다.

> 여행 중 하루 재생성은 **백엔드 후속**이다. `AIPLAN_017` 을 재생성 갈래에서 완화하거나
> (`planId` 가 있으면 시작일 검사를 건너뛴다) `MAX_TRIP_DAYS` 를 plan-service 와 맞추는
> 것이 필요하다. FE 는 그 전까지 진입점을 감춘다.

## R1. 아트보드에서 벗어난 것

| 이탈                                                                  | 근거                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`이 날 다시 만들기` 를 저장 전 미리보기가 아니라 일정 상세에 둔다** | 아트보드 03 은 담기 전 초안 미리보기에 버튼을 그렸다. **계약이 그것을 할 수 없다** — `regenerateDay` 는 `planId` 와 함께여야 하고 `planId` 는 저장된 일정에만 있다. 저장 전 초안에는 `planId` 가 없다. 아트보드를 정본으로 두려면 백엔드가 "초안 재생성" 을 새로 만들어야 하고 그것이 #90 이다. **그동안 기능을 잠가 두는 것보다, 계약이 지금 할 수 있는 자리에 여는 편이 낫다** |

`ai-plan-draft-preview.tsx` 는 이미 _"일자 단위 재생성은 `planId` 가 필요해 담은 뒤에만
가능하다"_ 를 주석으로 달아 두어, 이 판단과 어긋나지 않는다.

**아트보드 갱신은 후속으로 둔다.** 이 문서가 이탈 근거의 정본이고, 아트보드가 갱신되면
이 표를 지운다. `다견선택-세부명세.md` D1 과 같은 방식이다.

## R2. 라우트와 화면 상태

**새 라우트 하나다.** `app/(main)/plans/[planId]/days/[day]/regenerate/page.tsx`

이미 있는 `days/[day]/add` 와 같은 자리이고, 그 페이지의 규칙을 그대로 따른다.

- `loading.tsx` 를 두지 않는다 — `notFound()` 가 HTTP 상태를 바꿔야 한다
- 경로의 `day` 를 `/^\d+$/` 와 `>= 1` 로 막는다. 숫자가 아니거나 0 이면 없는 페이지다
- 일정 상세를 `fetchQuery` + try/catch 로 프리페치하고 404 는 `notFound()` 로 낸다
- 기간 상한(`day > totalDays`)은 상세를 받은 **뷰가** 판단한다 (`add` 화면과 같은 분담).
  없는 일자면 화면을 세우지 않고 `/plans/{planId}` 로 보낸다 — 라우트는 `totalDays` 를
  모르므로 `notFound()` 로 낼 수 없다

### R2-1. `jobId` 는 쿼리다

```text
/plans/{planId}/days/{day}/regenerate            제출 (메모 입력)
/plans/{planId}/days/{day}/regenerate?jobId=…    대기 → 비교 → 확정
```

**한 화면의 세 상태이지 세 화면이 아니다.** `planId` + `day` 가 이 작업의 신원이고 `jobId`
는 그 안에서 잠깐 생기는 상태다. 경로에 넣으면 신원이 둘이 된다.

**쿼리에 두는 이유는 새로고침·이탈에 견디기 위해서다.** 작업이 수십 초 걸리므로 주소가
작업을 가리켜야 한다. `/ai-plans/jobs/[jobId]` 가 `jobId` 를 경로에 든 것과 목적이 같다.

### R2-2. `sessionStorage` 스냅샷을 쓰지 않는다

기존 AI 생성이 스냅샷을 쓰는 이유는 **초안에 반려견·기간·예산이 없고 작업 조회 응답에도
없어서** 담기(`POST /plans`)를 되살릴 수 없기 때문이다 (`request-store.ts`).

**여기는 `planId` 가 그 역할을 한다.** 조건이 전부 일정에서 다시 나오고, 되붙이기
(`PUT .../days/{day}/items`)에는 항목만 있으면 된다. 보관할 것이 없으므로 보관하지 않는다.

### R3-1. 뒤 둘을 보내지 않는 이유

**일정에 저장되지 않는 값이다.** `PlanDetail` 에 두 필드가 없고 `PlanCreateRequest` 에도
없다. 원래 일정을 AI 로 만들 때 무엇을 골랐는지는 그 탭의 `sessionStorage` 에만 있었고
이미 사라졌을 수 있다. **모르는 값을 지어내지 않는다** — 특히 `pinnedPlaceIds` 는 "반드시
배치" 약속이라 잘못 실으면 사용자가 요구한 적 없는 장소가 그 날에 박힌다.

### R3-2. AI 로 만든 일정이 아니어도 된다

재생성에 필요한 것은 `planId` · 일차 · 일정 자신의 필드뿐이다. 직접 만든 일정에도 진입점을
낸다. **항목이 0개인 날에도 낸다** — 그때가 가장 필요한 순간이다.

### R3-3. 멱등을 그대로 쓴다

`POST /ai-plans` 는 같은 요청이 진행 중이면 기존 `jobId` 를 준다(HTTP 202). 사용자가 뒤로
갔다 다시 제출해도 작업이 둘로 늘지 않는다. FE 가 따로 막지 않는다.

## R4. 되붙이기 — 목표 일자만

**초안은 모든 날을 담아 온다.** 프롬프트가 그렇게 지시한다.

> `AiPlanPromptFactory#appendRegenerateSection`
> _"위 일정에서 {N}일차만 새로 구성할 것. 나머지 날은 기존 항목을 순서까지 그대로 유지해
> **전체 일정을 출력**할 것"_

**그중 목표 일자 하나만 쓴다.**

```text
draft.days.find((entry) => entry.day === regenerateDay)
  → PlanItemPayload[]        (draft-to-plan 의 매핑 규칙 재사용)
  → PUT /plans/{planId}/days/{day}/items
```

### R4-1. 다른 날을 반영하지 않는 이유

프롬프트는 나머지 날의 보존을 **부탁**할 뿐 강제하지 않는다. 이 저장소는 이미 LLM 산출물을
못 믿는 전제로 짜여 있다 — `draft-to-plan.ts` 가 기간 밖 일차를 걸러내고(`OllamaLlmAdapter.toDomain`
은 클램프하지 않는다), `AiPlanScheduleItem.title` 이 `null` 로 올 수 있다고 타입에 적어 두었다.

**사용자는 하루만 바꾸겠다고 말했다.** 다른 날이 조용히 바뀌면 그 약속이 깨진다. 게다가
일자별 PUT 은 원자적이지 않아, 여러 날을 쓰다 중간에 실패하면 **반쯤 바뀐 일정**이 남는다.

**다른 날이 달라졌다는 사실도 알리지 않는다.** 사용자가 할 수 있는 일이 없어 잡음이다.

### R4-2. 목표 일자가 없으면 실패다

LLM 이 그 날을 빼먹으면 `find` 가 `undefined` 를 준다. **빈 항목으로 PUT 하지 않는다** —
`PlanDayItemsReplacePayload` 는 빈 목록을 "그 일자 전부 삭제" 로 읽는다. 재생성 실패로
다루고 다시 시도하게 한다.

### R4-3. 매핑은 `draft-to-plan` 규칙 그대로다

`WALK` 은 `targetId` 를 보내지 않고(`walk_course.id` 와 `placeId` 가 어긋난다 — [#89](https://github.com/8llow8llowMe/hondigagae/issues/89)),
`title` 은 100자 · `memo` 는 500자로 자르고, `sequence` 는 0부터 다시 매긴다. **규칙을
복제하지 않고 함수를 나눠 쓴다** — 두 벌이 되면 반드시 갈라진다.

`day` 는 경로값으로 덮어쓰되 `@Min(1)` 이 먼저 도므로 1 이상으로 채워 보낸다.

## R5. 비교 화면

확정 전에 **지금 그 일자**와 **바뀌는 모습**을 나란히 둔다.

```text
[ 지금 ]                      [ 이렇게 바뀌어요 ]
1 제주특별자치도립김창열미술관   1 오설록 티뮤지엄 카페
2 동문재래시장                 2 사려니숲길 산책
3 애월 펜션                    3 애월 펜션
```

**교체는 되돌릴 수 없으므로 무엇을 잃는지 눈으로 보여 주는 것이 유일한 방어다.** 계약에
일자 이력이 없어 undo 를 만들 수 없다.

화면이 두 가지를 말한다.

1. **되돌릴 수 없다** — 지금 일자는 사라진다
2. **그 날 '다녀옴' 표시가 초기화된다** — 일정 상세가 이미 쓰는 사실이다
   (`순서를 바꾸거나 장소를 담으면 이 날의 '다녀옴' 표시가 초기화돼요`)

항목이 0개인 날은 "지금" 쪽이 빈다. **비었다고 말하고 넘어간다** — 그 상태가 사실이다.

| 작업 실패 (**200** + `FAILED`)          | `ai-plan-failed` 재사용. `dataHeader.success` 만 보면 놓친다 (api-integration-guide §5). **제목은 `regenerateDayFailedTitle` 로 바꾼다** — 하루가 실패했을 뿐 일정은 그대로다                                                                                                                                                                       |
| 작업 조회 **404** (`AIPLAN_002`)        | `EmptyState` + 제출 상태로 돌아가는 갈래. **재시도 버튼을 달지 않는다** — 정리된 작업이나 남의 작업은 다시 불러도 없다. 생성 경로와 달리 `/ai-plans/new` 로 보내지 않는다 (일정이 그대로 있다)                                                                                                                                                      |
| 초안에 목표 일자가 없다                 | 재생성 실패로 다룬다 (R4-2). 다시 시도                                                                                                                                                                                                                                                                                                              |
| `PUT` 의 `PLAN_004` (사라진 장소)       | `save-error.ts` 가 이미 분류한다. **초안을 버리지 않고** 그 항목만 빼고 다시 담는다. **뺀 뒤에는 `regenerateDayExcludedPlace` 를 말한다** — 편집모드 문구는 사용자가 목록에서 빼라고 지시하는데 이 화면의 `이렇게 바뀌어요` 열은 읽기 전용이다. 장소 조회가 진행 중이면 **확정 버튼을 함께 잠근다** (뺄 목록이 아직 비어 있어 같은 400 만 반복한다) |
| `PUT` 의 `PLAN_002` (기간 밖 일자)      | 매핑이 먼저 거르므로 안 나야 한다. 나면 같은 오류 표시                                                                                                                                                                                                                                                                                              |
| `PUT` 의 `PLAN_001` (404·남의 일정)     | 일정 목록으로 보낸다                                                                                                                                                                                                                                                                                                                                |
| SSE 끊김                                | 기존 폴링 안전망이 그대로 받는다 (`JOB_STREAM_SAFETY_POLL_MS`, #91)                                                                                                                                                                                                                                                                                 |

## R8. 경계

- **서버 컴포넌트는 라우트 페이지 하나다.** 뷰부터 `'use client'` — 작업 구독과 폼이 있다
- 백엔드를 브라우저에서 직접 부르지 않는다. 전부 `/api/bff` 경유이고, SSE 만 `EventSource`
  가 BFF 경로를 연다 (기존 규칙)
- 되붙이기 성공 후 `planKeys.detail(planId)` 와 `planKeys.weather(planId)` 를 무효화한다 —
  일자가 바뀌면 그 날 판정도 다시 와야 한다. **두 key 가 나뉘어 있으므로 둘 다 부른다**
  (`queries.ts:12` 이 나눈 이유를 적어 두었다)
- 성공 시 `/plans/{planId}` 로 **`replace`** 한다. 뒤로 가기가 이미 끝난 작업으로
  돌아가면 안 된다. 그 일자로 앵커 스크롤한다 (`use-anchor-scroll`)

## R9. 테스트 케이스

이 저장소 방식 그대로 — node 환경 + `renderToStaticMarkup` 문자열 assertion.

### 순수 로직 (TDD)

`lib/ai-plan/regenerate.ts`

- 일정 → payload: `areaCode`·기간·`petIds` 순서가 그대로 실린다
- `budget` 이 `null` 이면 **키가 없다**
- `requestNote` 가 빈 문자열이면 **키가 없다**
- `planId`·`regenerateDay` 가 실린다
- **`preferFavorites`·`pinnedPlaceIds` 키가 없다**
- 초안 → 항목: 목표 일자만 뽑는다 (다른 날이 있어도 무시)
- 목표 일자가 없으면 `null` (빈 배열이 아니다 — R4-2)
- `WALK` 항목에 `targetId` 가 없다
- `title` 이 `null` 인 항목을 만나도 죽지 않는다

### 렌더 분기

- 비교 컴포넌트: 양쪽 항목이 다 나온다 / "지금" 이 비면 빈 안내가 나온다
- 되돌릴 수 없다는 문구와 '다녀옴' 초기화 문구가 확정 버튼 앞에 있다
- 일자 헤더에 `다시 만들기` 가 있고 링크가 `/plans/{id}/days/{day}/regenerate` 다

### 회귀

- **`submit.test.ts:132` 를 지우지 않고 뜻을 바꾼다.** 지금은 _"planId·regenerateDay 는
  여전히 새지 않는다"_ 인데, **생성 경로(`/ai-plans/new`)에서는 여전히 안 실리고 재생성
  경로에서만 실린다**로 바꾼다. 잠금을 없애면 생성 요청에 두 필드가 새어 들어가는 회귀를
  아무도 막지 않게 된다
- 한 마리 일정도 `petIds` 원소 하나로 실린다
