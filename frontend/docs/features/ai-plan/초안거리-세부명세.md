## 이 문서의 범위

**새 화면이 아니다.** 이미 있는 결과 화면(`/ai-plans/jobs/[jobId]`)의 **항목 행 한 줄**을
추가한다. 라우트·API·상태 머신은 그대로다.

[#84](https://github.com/8llow8llowMe/hondigagae/issues/84)(AI 일정 생성)가 이 자리를
**의도적으로 비워 뒀다**(공통명세 S9-3). 조건은 "일정 상세(#80)의 `src/lib/geo/distance.ts`
가 develop 에 들어올 것" 이었고, **충족됐다** — `7362397` 기준으로 그 모듈이 있고
`features/plan/plan-item-row.tsx` 가 이미 쓰고 있다.

> **이 이슈의 요점은 거리 계산이 아니라 "두 화면이 같은 규칙을 쓴다" 는 것이다.**
> 계산식·임계값·문구·기준점 중 하나라도 각자 두면 같은 동선이 두 화면에서 다르게 보인다.
> 아래 D2 의 모듈 분리는 전부 그 목적에서 나온 결정이다.

## D1. 레이아웃

거리 줄은 **주소 아래 · `note`(AI 이유) 위**에 들어간다.

```text
① 제주특별자치도립김창열미술관   [장소]        ← 제목 + 유형 배지
   제주특별자치도 제주시 한림읍 …              ← 주소 (보강, nullable)
   직선 4.1km 이동                             ← ★ 이번에 추가
   오전이라 노면이 덜 뜨거워요.                ← note (서버 문구)
```

**위치 정보(주소 · 거리)를 붙여 두고 AI 문구를 마지막에 둔다.** 사실과 설명을 섞지 않는
것이 아트보드 03 의 순서이고, `plan-item-row.tsx` 도 주소 바로 아래에 거리를 둔다.

- 모바일(390) · 데스크톱(1024+) 모두 같다. 행이 이미 2열(순번 원 + 본문)이고 거리는 본문
  칼럼 안의 한 줄이라 **브레이크포인트 분기가 없다**
- 타이포는 `text-caption` + `tabular-nums`(숫자 폭 흔들림 방지) — `plan-item-row.tsx` 와 동일
- 긴 이동(30km 이상)이면 **그 줄만** `text-metric-low-700`. 나머지는 `text-fg-muted`

**긴 이동 경고 배지를 새로 만들지 않는다.** 행 자체가 말하는 것이 편집 동기를 만든다
(아트보드 01 주석 · 일정상세 D3). 초안 미리보기의 "편집" 은 **빼기 토글과 다시 만들기**다.

### 긴 한국어 실데이터로 확인할 항목

- 공백 없는 긴 장소명(`제주특별자치도립김창열미술관`) 아래에서 거리 줄이 밀리지 않는가
- `note` 가 2줄 이상일 때 거리 줄이 note 와 시각적으로 붙어 보이지 않는가(`mt-1` 유지)
- 한 일자에서 거리 줄이 **하나만** 그려질 때(아래 D5 참고) 여백이 비어 보이지 않는가

### D2-1. 왜 `toItemRows` 를 그냥 재사용하지 못하는가

`lib/plan/detail.ts` 의 두 함수는 **`PlanItemDetail` 로 못박혀 있다.**

|            | 일정 상세                                          | AI 초안                                       |
| ---------- | -------------------------------------------------- | --------------------------------------------- |
| 항목 타입  | `PlanItemDetail`                                   | `AiPlanScheduleItem`                          |
| `itemType` | `CodeNameMetadata` (`item.itemType.code`)          | **raw string** (`item.itemType`)              |
| 좌표 키    | `item.targetId`                                    | `item.placeId`                                |
| 일자 그룹  | `PlanDayGroup` (FE 가 `groupItemsByDay` 로 만든다) | `AiPlanDayItem` (**서버가 이미 나눠서 준다**) |

즉 **규칙은 같고 접근자만 다르다.** 그래서 규칙을 제네릭으로 빼고 접근자를 주입한다.

### D2-2. 확정한 분리 — 제네릭 코어 + 도메인별 얇은 바인딩

이슈 착수 노트는 **(a) `toItemRows` 를 제네릭으로 연다** / **(b) 초안 쪽에 매퍼를 따로
둔다** 두 갈래를 적어 뒀다. **둘 다 쓰지 않고 그 사이를 택한다.**

- (b)는 기준점 규칙이 두 벌이 된다 — 이 이슈가 막으려는 것 그 자체다
- (a)는 규칙을 한 곳에 두지만 **이미 머지된 일정 상세의 공개 시그니처를 바꾼다.**
  `plan-detail-section.tsx`·`detail.test.ts`(4 케이스)·`plan-item-row.tsx` 가 전부
  `PlanItemRowModel` 에 붙어 있어, 표시 전용 이슈가 일정 상세 회귀 위험을 진다

**확정**: 제네릭 코어를 새 파일로 만들고, `lib/plan/detail.ts` 는 **시그니처를 그대로 둔 채
위임만** 한다. 초안은 자기 바인딩을 따로 갖는다.

```ts
// src/lib/plan/item-distance.ts — 규칙 정본. 항목 타입을 모른다
export type ItemDistanceKind = 'lodging' | 'previous'

export type ItemDistanceRow<T> = {
  item: T
  /** 직선거리(m). 한쪽이라도 좌표가 없으면 null */
  distanceMeters: number | null
  /** null 이면 거리 줄을 렌더하지 않는다 */
  distanceKind: ItemDistanceKind | null
}

export function toDistanceRows<T>(
  items: readonly T[],
  coordOf: (item: T) => LatLng | null,
  lodgingBasis: T | null,
): ItemDistanceRow<T>[]

export function lodgingBasisOf<T>(
  day: number,
  days: readonly { day: number; items: readonly T[] }[],
  isLodging: (item: T) => boolean,
): T | null
```

```ts
// src/lib/plan/detail.ts — 공개 시그니처는 그대로. 규칙만 넘긴다
export type PlanItemDistanceKind = ItemDistanceKind
export type PlanItemRowModel = ItemDistanceRow<PlanItemDetail>

export function lodgingBasisFor(day: number, days: PlanDayGroup[]): PlanItemDetail | null {
  return lodgingBasisOf(day, days, (item) => item.itemType.code === 'LODGING')
}

export function toItemRows(items, coordOf, lodgingBasis): PlanItemRowModel[] {
  return toDistanceRows(items, coordOf, lodgingBasis)
}
```

```ts
// src/lib/ai-plan/draft-distance.ts — 초안 바인딩. 'LODGING' 리터럴이 여기 하나만 있다
export function draftLodgingBasis(day: number, days: AiPlanDayItem[]): AiPlanScheduleItem | null {
  return lodgingBasisOf(day, days, (item) => item.itemType === 'LODGING')
}
```

**`lib/plan/detail.test.ts` 를 지우거나 옮기지 않는다.** 그 4 케이스가 위임이 깨지지 않았다는
회귀 테스트가 된다. 제네릭 코어의 단위 테스트는 `item-distance.test.ts` 로 **따로** 쓴다.

### D2-3. 행 컴포넌트는 모델이 아니라 원시값을 받는다

`plan-item-row.tsx` 는 `model: PlanItemRowModel` 을 통째로 받지만, `AiPlanDraftItemRow` 는
**이미 `item` + 원시 props(`address`·`delisted`·`excluded`) 구조**다. 그 결을 지킨다:

```ts
distanceMeters?: number | null
distanceKind?: ItemDistanceKind | null   // 없거나 null 이면 줄을 그리지 않는다
```

이 저장소는 jsdom 없이 `renderToStaticMarkup` 문자열 assertion 으로 테스트한다
(`docs/testing-guide.md` §1). **원시 props 여야 렌더 테스트에서 케이스를 직접 만든다.**

### 새 요청이 없다 — 좌표는 이미 손에 있다

```text
useDraftPlaces(draft)
```

**요청도 캐시 키도 늘어나지 않는다.** 같은 `useMemo` 안에서 `toLatLng(detail)` 을 한 번 더
부를 뿐이다.

| 항목              | 내용                                                     |
| ----------------- | -------------------------------------------------------- |
| API               | **없음** (기존 `GET /places/{placeId}` 보강 결과 재사용) |

| 폴링              | 변경 없음                                                |

### 좌표 변환은 `toLatLng` 을 통과시킨다

`PlaceDetail.lat`/`lng` 는 **둘 다 nullable 이고 `0` 이 실려 오는 장소가 있다.**
`lib/geo/coord.ts` 의 `toLatLng` 이 `null`·비유한값·`0`·범위 밖을 전부 `null` 로 접는다 —
**직접 `{ lat, lng }` 를 만들지 않는다.** 그러지 않으면 좌표 미상 장소가 기니만(0,0)으로
잡혀 제주에서 **9,000km 짜리 "긴 이동"** 이 생긴다.

## D3-1. 기준점 규칙 — 일정 상세와 **같다**

| 위치                                  | 기준                           | 문구                        |
| ------------------------------------- | ------------------------------ | --------------------------- |
| 그 일자의 **첫 항목**                 | **앞선 날**의 마지막 `LODGING` | `숙소에서 직선 {distance}`  |
| **2번째부터**                         | **직전 항목**(배열 인덱스 −1)  | `직선 {distance} 이동`      |
| 기준이 없거나 어느 한쪽 좌표가 없으면 | —                              | **줄 자체를 그리지 않는다** |

- **"그날의 숙소" 를 기준으로 쓰지 않는다.** 일정 상세가 실렌더에서 되돌린 판단이다 —
  1일차 첫 항목에 `숙소에서 직선 14.8km` 가 붙었고 그 숙소는 **그날 저녁에 체크인할 곳**
  이었다 (`detail.ts` `lodgingBasisFor` 주석)
- **1일차 첫 항목에는 아무것도 붙지 않는다.** 앞선 날이 없다. 이슈 본문의 테스트 케이스
  "첫 항목(기준 없음)" 이 이것이다
- **초안에도 `LODGING` 이 실제로 온다.** ai-service `StubLlmAdapter.sampleDay` 가 1일차에
  `LODGING`("숙소 체크인")을 넣고 `LlmPlanDraftResponse` 스키마도 `LODGING` 을 허용한다 —
  **2일차부터는 숙소 기준 줄이 실제로 그려진다.** "초안엔 숙소가 없다" 는 가정으로 규칙을
  줄이면 안 된다

### 기준 항목을 건너뛰지 않는다

직전 항목에 좌표가 없으면 **그 앞으로 더 거슬러 올라가지 않는다.** 거리를 없는 것으로 둔다.

건너뛰면 `직선 12km 이동` 이 실제로는 **두 구간 합**을 건너뛴 값이라 무엇에서 잰 거리인지
행이 말할 수 없게 된다. 일정 상세가 `items[index - 1]` 을 그대로 쓰는 것과 같은 처리다.

### 빼기(`excluded`) 는 거리에 영향을 주지 않는다

담기에서 뺀 항목도 **거리 사슬에 그대로 남는다.**

- 미리보기가 보여 주는 것은 **AI 가 낸 동선**이다. 토글할 때마다 아래 행들의 거리가 줄줄이
  바뀌면 무엇을 보고 있는지 알 수 없다
- `excluded` 는 `PLAN_004` 복구용 임시 표시이고(공통명세 S5 함정 3), 담고 나면 일정 상세가
  **저장된 항목으로 다시 계산한다** — 최종 수치는 그쪽이 정본이다

### 문구를 새로 만들지 않는다

`messages.plan.distanceFromLodging` · `distanceFromPrevious` · `longTripSuffix` 를
**그대로 쓴다.** `messages.aiPlan` 아래에 복제본을 만들지 않는다 — 두 화면이 같은 것을
다른 말로 부르면 사용자가 다른 계산으로 읽는다.

**"직선" 을 반드시 넣는다.** 제주는 산간·해안도로가 많아 주행거리와 크게 다르다. `4.1km`
만 쓰면 주행거리로 읽힌다 (`messages/plan.ts:151-155` 근거 주석 · 일정상세 D3).

### `WALK`/`MOVE` 에 거리가 붙지 않는 것은 결함이 아니다

`useDraftPlaces` 는 `draftPlaceIds` 가 고른 id 만 부르고, 그것은 `PLACE`·`MEAL`·`LODGING`
뿐이다. `WALK` 는 `placeId` 가 실려 와도 **`walk_course.id` 와 어긋나 있어**(#89) 보강
대상이 아니고, `MOVE` 는 `placeId` 가 `null` 이다.

**결과: 그 두 항목은 자기 거리도 없고, 바로 다음 항목의 거리도 끊는다.** mock 의 한 일자
(`PLACE` → `MEAL` → `WALK` → `MOVE`)에서는 **거리 줄이 2번째 항목 하나에만** 그려진다.
이것이 정상 동작이며, D7 의 렌더 테스트가 이 모양을 고정한다.

## D6. 접근성

- **색만으로 전달하지 않는다.** 긴 이동은 경고 톤 + `— 하루 이동이 깁니다.` 문장이 함께
  간다. 이미 `messages.plan.longTripSuffix` 가 그 목적으로 있다
- 거리 줄은 **본문 텍스트**다. `aria-label`·`role` 을 추가하지 않는다 — 스크린리더가 그냥 읽는다
- `tabular-nums` 로 숫자 폭을 고정한다 (시각적 안정 · 저시력 사용자 스캔)
- 순번 원(`aria-hidden`)과 달리 거리는 **자료**다. a11y 트리에서 빼지 않는다
- 새 인터랙티브 요소가 없어 키보드 순회·44px 터치 영역 변경 없음

## D10. 검증 계획 — **브라우저로 봐야 한다**

### 로컬 백엔드로는 거리가 하나도 보이지 않는다 (소스 실측)

`ai-llm.enabled=false`(기본값)이면 `StubLlmAdapter` 가 뜨는데, **그 어댑터는 항목에
`placeId` 를 채우지 않는다** — `item(itemType, title, note)` 3-인자 빌더뿐이고 `placeId`
필드를 세팅하는 코드가 없다.

**결과: 실서버 스텁으로 만든 초안은 주소도 거리도 전부 비어 있다. 제품 결함이 아니다.**
`ai-plan-data.ts` mock 이 실제 `MOCK_PLACES` 의 id 를 실어 주므로 **검증은 FE mock 으로
한다.**

### 절차

1. 백그라운드 Bash 로 `./node_modules/.bin/next dev -p <포트>` (`preview_start` 런처는
   이 환경에서 프로세스를 못 띄운다). `localhost:3000`/`3001` 은 점유돼 있고
   **`127.0.0.1` 로 붙지 않는다**
2. `/ai-plans/new` 에서 **3일 이상** 기간으로 제출 → `/ai-plans/jobs/{jobId}` 로 이동
3. **폴링 3회를 채워야 `COMPLETED` 가 된다.** 브라우저 페인이 hidden 이면 React Query 가
   폴링을 멈춘다(`fetchStatus: 'paused'`) — **페인을 보이는 상태로 두거나** 새로고침으로
   조회를 진행시킨다. 제품 결함이 아니다
4. 확인할 것:
   - 2번째 항목에 `직선 N km 이동` 이 붙는가
   - 1일차 첫 항목에 아무것도 붙지 않는가
   - `WALK`·`MOVE` 행에 거리가 없는가 (한 일자에 거리 줄이 **1개**)
   - 주소가 늦게 붙을 때 **거리도 같이** 늦게 붙는가 (레이아웃 점프 확인)
5. 종료: `pkill` + `lsof -ti:<포트> | xargs kill -9`

> **`use-draft-places.ts` 의 `useMemo` 를 건드리는 것이 이 이슈의 유일한 상태 위험이다.**
> 반환 객체가 커지므로 의존성 배열과 재생성 주기를 눈으로 확인한다. 나머지는 표시 전용
> 컴포넌트 + 순수 함수라 렌더·단위 테스트로 덮인다.
