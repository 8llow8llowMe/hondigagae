> 상위 공통명세: `docs/features/auth/공통명세.md`
> 작성자 / 작성일: seonghoho / 2026-08-27

## D0. 화면 정의

- **경로**: `/login` (`app/(auth)/login/page.tsx`, 라우트 그룹이라 URL 에 `(auth)` 는 없다)
- **인증**: **불필요.** `PROTECTED_PATHS` 에 넣지 않는다 — 넣으면 무한 리다이렉트가 된다.
- **진입 경로**
  - 보호 경로 접근 시 `proxy.ts` 리다이렉트 → `/login?returnTo=<원래 경로>`
  - 회원가입 완료 후 이동
  - 직접 진입
- **이탈 경로**
  - 로그인 성공 → `returnTo` 또는 `/`
  - 회원가입 링크 → `/signup`

### `returnTo` 검증 (보안)

`returnTo` 는 **쿼리스트링이라 사용자가 조작할 수 있다.** 그대로 리다이렉트하면 오픈 리다이렉트다.

- **`/` 로 시작하는 같은 오리진 경로만 허용**한다.
- `//evil.com`, `/\evil.com`, `http://…`, `javascript:` 는 거부하고 `/` 로 보낸다.
- 판정은 `src/lib/http/redirect.ts` 의 순수 함수로 두고 테스트한다.

> **이 파일은 아직 없다.** `auth-guide.md` §5 와 `architecture-guide.md` §7 이 "같은 오리진
> 리다이렉트는 이 헬퍼를 쓴다"고 이미 규정해 뒀지만 실물이 없다. 이번 작업에서 만든다.

## D1. 레이아웃

한 컬럼 중앙 정렬. 지도가 붙을 여지가 없는 화면이라 데스크톱에서도 컬럼을 넓히지 않는다.

- 모바일 (375): `px-4`, 폼 전체 폭
- 태블릿 (768) / 데스크톱: `max-w-sm` 중앙 정렬, 상단 여백 확보

긴 한국어 실데이터로 확인할 항목:

- 서버 오류 문구가 길다 — `"이미 %s(으)로 가입된 계정입니다. 해당 소셜 로그인을 이용해주세요."` 가
  2줄로 넘어갈 때 레이아웃이 밀리지 않는지
- 이메일이 길 때 입력 필드가 잘리지 않는지

## D2. 컴포넌트 구성

| `Field`             | 신규 공통 | `src/components/field.tsx`         | label + error + aria 배선             |

**새로 만드는 공통 컴포넌트 3종의 이유**: `src/components/` 에 입력 계열이 하나도 없다.
`component-guide.md` §7 이 `Input 계열` 의 접근성 계약을 이미 정의해 뒀으므로 그것을 구현한다.

`Field` 와 `Input` 을 나누는 이유: label/error/aria 배선은 `Select`·`Textarea`·라디오에서도
그대로 필요하다. `Input` 에 합치면 #12 반려견 폼에서 다시 뜯게 된다.

## D3. 데이터 흐름

```text
/login 진입 (서버) → readSession()
  ├─ 세션 있음 → redirect(safeReturnTo(returnTo))  — 서버 307, 화면 없음 (#1082)
  └─ 세션 없음 → LoginForm (클라이언트)
                   제출 → clientFetch POST /auth/login
                        → BFF 가 accessToken 을 세션에 봉인하고 body 에서 제거
                        → 성공 시 location.replace(safeReturnTo)  — 문서째 새로 받는다 (#1075)
```

| 항목                   | 내용                                                           |
| ---------------------- | -------------------------------------------------------------- |
| API                    | `POST /auth/login`, `POST /auth/logout`                        |
| React Query key        | **없음** (mutation 전용, 캐시하지 않음)                        |
| staleTime / retry      | `retry: false` — 401 을 재시도하지 않는다 (`auth-guide.md` §3) |
| mutation 후 invalidate | `queryClient.clear()` — 이전 사용자 캐시가 남으면 안 된다      |
| 폴링 여부              | 없음                                                           |

**로그인 성공 후 `queryClient.clear()` 를 반드시 호출한다.** 로그아웃 후 다른 계정으로
로그인했을 때 이전 계정의 캐시가 그대로 보이는 것을 막는다.

이동은 **`location.replace()`** 다 — `router.replace()` 가 아니다 (#1075). `push`/`assign` 을
쓰면 뒤로가기로 로그인 화면에 돌아오므로 히스토리를 **대체**한다는 점은 그대로다.

**문서를 통째로 새로 받는 이유는 클라이언트 라우터 캐시다.** 비로그인일 때 받은 응답이 캐시에
남고, 세션이 생기는 순간 전부 낡은 값이 되는데 캐시를 통째로 비우는 공개 API 가 없다.

- **route cache 는 URL → 라우트 트리를 기억한다.** 비로그인으로 `반려견 등록하기`(`/pets/new`)를
  누르면 proxy 가 `/login?returnTo=%2Fpets%2Fnew` 로 보내고, 캐시에는 `/pets/new` 의 트리가
  **로그인 화면**으로 남는다. 그 뒤 `router.replace('/pets/new')` 는 요청을 보내지 않고 이 캐시를
  써서 로그인 화면에 머문다 (목 10/10 재현, `/pets/new` 요청 0건).
- **`router.refresh()` 로는 못 고친다.** refresh 는 segment cache 만 비우고 route cache 는 남긴다
  (`next/dist/client/components/router-reducer/reducers/refresh-reducer.js`). #1013 이 `replace` 뒤에
  `refresh` 를 붙인 뒤로는 머문 로그인 화면을 새 쿠키로 다시 그려 **"이미 로그인되어 있어요"** 가
  떴다 (#1075 의 증상). `refresh` 를 먼저 불러도 로그인 폼에 머문다.
- **#1013 의 방어는 이 이동이 대신한다.** 새 문서는 서버가 새 쿠키로 `(main)` 레이아웃까지 전부
  다시 그리므로 헤더가 비로그인 모양으로 남을 수 없다. `queryClient.clear()` 는 새 문서가 도착하기
  전까지의 틈을 막으려고 그대로 부른다. 둘은 `enterSession` 이 한 자리에서 부르고, 소셜 콜백도 같은
  함수를 쓴다.

### 세션이 있으면 리다이렉트한다 (#1082, 2026-10-01 개정)

**예전에는 "이미 로그인되어 있어요" 안내 + `이어서 이용하기` 링크 + `로그아웃` 버튼을 그렸다**
(`LoggedInNotice`, 공통명세 S5-5 (a)). 이 화면이 로그아웃의 유일한 진입점이라서였는데, 계정
메뉴 · 마이페이지 로그아웃이 생기며 그 근거가 사라졌고, 안내는 누구로 · 어디로 가는지 말하지
않았다. 그래서 **세션이 있으면 그리지 않고 `redirect(target)` 한다** — `target` 은 폼이 쓰는
것과 같은 `safeReturnTo(returnTo)` 다. `/signup` · `/signup/social/[provider]` 도 같다.

- **문서 요청이면 HTTP 307 이다.** `(auth)` 에 `loading.tsx` 가 없어 응답이 스트리밍되기 전에
  상태를 바꿀 수 있다 (`(auth)/layout.tsx` 머리주석).
- **클라이언트 이동이면 RSC 응답 안의 리다이렉트를 라우터가 따라간다** (RSC 요청 자체는 200).
- **라우터 캐시에 남지 않는다** (실측, 목 · `next dev --webpack`). #1075 는 proxy 리다이렉트의
  결과가 route cache 에 _원래 URL 의 트리_ 로 남아 깨졌다. 같은 일이 여기서도 나는지 봤다 —
  로그인 상태에서 `/login` 으로 클라이언트 이동(→ 홈) 뒤 계정 메뉴로 로그아웃(문서를 바꾸지
  않는다)하고 헤더 `로그인` 을 누르면, `/login` RSC 를 **새로 요청해** 로그인 폼이 선다. 같은
  리다이렉트를 두 번 연달아 타도 둘 다 목적지에 닿는다. `e2e/authed-auth-redirect.spec.ts` 가 잠근다.

`/password/reset` 은 세션을 읽지 않는다 — 공통명세 S5-5 개정.

## D4. 상호작용

| 트리거                  | 동작                                                        | 결과                                                                 |
| ----------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------- |
| 이메일/비밀번호 입력    | `values` 갱신 + **해당 필드 오류만** 제거                   | 오류 메시지 사라짐                                                   |
| 제출 (버튼 / Enter)     | 클라이언트 검증 → 통과 시 요청                              | 실패 시 요청을 보내지 않고 첫 오류 필드로 포커스                     |
| 제출 중 재제출          | 재진입 가드로 무시                                          | 요청 1회만 나감                                                      |
| 제출 중 소셜 버튼       | 두 버튼 다 `disabled` — 응답 · 이동이 끝날 때까지 (#1084)   | 제공자 화면으로 떠나지 않는다 (D11)                                  |
| 제출 중 직전 실패       | 걷는다 — 401 알림 · 일시 장애 모두 (#1084)                  | 결과가 다시 실패면 그때 다시 선다 (D11)                              |
| 401 응답                | `FormAlert` 에 서버 문구                                    | 비밀번호 필드만 비우고 이메일은 유지, 비밀번호로 포커스              |
| 429 응답                | `FormAlert` 에 서버 문구. **`ErrorState` 로 바꾸지 않는다** | **제출 버튼은 활성 유지.** 시간이 지나면 되므로 영구 차단하지 않는다 |
| 5xx / 무응답            | 폼 안 `ErrorState` 하나 + 재시도 (#1079)                    | 폼은 그대로 유지. **`FormAlert` 를 함께 세우지 않는다**              |
| 비밀번호 표시 토글      | `type` 전환, `aria-pressed` 갱신                            | 값 유지                                                              |
| "회원가입" 링크         | `/signup` 이동 (`returnTo` 를 물고 감)                      | 가입 후 로그인 → 원래 목적지로 복귀                                  |
| 진입 (세션이 있는 상태) | 서버 `redirect` (#1082)                                     | 폼 없이 `returnTo` 로 간다                                           |

**401 에서 이메일을 지우지 않는다.** 오타는 대개 비밀번호 쪽이고, 이메일까지 지우면
재입력 부담이 커진다.

## D5. 상태별 화면

| 상태                         | 표시                             | 문구 (확정)                                                                         |
| ---------------------------- | -------------------------------- | ----------------------------------------------------------------------------------- |
| loading (제출 중)            | 버튼 `disabled` + `aria-busy`    | "로그인 중"                                                                         |
| success                      | 즉시 이동                        | —                                                                                   |
| 클라이언트 검증 실패         | 필드 에러                        | `messages.form.*` (§클라이언트 문구)                                                |
| 로그인 실패 (401 `AUTH_006`) | `FormAlert`                      | **서버 `resultMessage` 그대로**                                                     |
| 잠금 (429 `AUTH_015`)        | `FormAlert`, 재시도 버튼 없음    | **서버 `resultMessage` 그대로**                                                     |
| 소셜 계정 (400 `MEMBER_007`) | `FormAlert`                      | **서버 `resultMessage` 그대로**                                                     |
| 일시 장애 (5xx)              | `ErrorState` + 재시도 (단독)     | `messages.common.temporaryError*` — 서버 문구 알림은 함께 서지 않는다 (#1079)       |
| 이미 로그인됨                | 서버 리다이렉트 · 화면 없음 (D3) | 없음 — 예전 안내("이미 로그인되어 있어요" · "이어서 이용하기")는 #1082 에서 걷었다. |

**데이터 부재(404)는 이 화면에 없다.** 로그인 실패는 계정 열거 방지를 위해 401 로 통일된다.

**폼 전체 실패는 한 자리에 하나만 선다** ([#1079](https://github.com/8llow8llowMe/hondigagae/issues/1079)).
5xx · 무응답이면 폼 안 `ErrorState`, 그 밖은 `FormAlert` 다. 예전에는 `apiErrorToFormErrors` 가
5xx 에도 `form` 을 채워 `ErrorState` 아래에 서버 문구 `FormAlert` 가 또 섰다 — 같은 실패를 두 번
말하고 재시도 수단도 둘이었다. 거기에 `ErrorState` 의 세로 48 × 2 가 얹혀 375 에서 폼이 약 250px
밀려 소셜 버튼이 접힘선 밑으로 갔다.

- 판정은 `src/lib/form/form-failure-display.ts` 의 `formFailureDisplay` 하나, 그리는 쪽은
  `src/components/form-failure.tsx` 의 `FormFailure` 하나다(#1101 에서 공용으로 올렸다). 가입 세 단계 · 재설정 두 단계도 같다.
- 폼 안 `ErrorState` 는 `flush` 다 — 인증 카드가 이미 여백을 갖는다. 2026-10-01 실측(375 · 503):
  소셜 버튼이 101px 내려가고 바닥이 699 로 접힘선(812) 위에 남는다
  (`e2e/auth-failure-surfaces.spec.ts`).
- 숨긴 `FormAlert` 의 두 몫(`role="alert"` · 제출 실패 뒤 포커스 대상)은 일시 장애 표시의 바깥
  상자가 넘겨받는다 (D6).

### 클라이언트 검증 문구 (`src/lib/messages/form.ts`)

백엔드 `AuthValidationMessage` 와 **같은 문구**를 쓴다. 대응 코드를 주석으로 남긴다.

| 필드     | 조건      | 문구                             | 대응 백엔드 코드 |
| -------- | --------- | -------------------------------- | ---------------- |
| email    | 비어 있음 | 이메일은 필수입니다.             | `AUTH_101`       |
| email    | 형식 오류 | 이메일 형식이 올바르지 않습니다. | `AUTH_102`       |
| password | 비어 있음 | 비밀번호는 필수입니다.           | `AUTH_103`       |

**로그인은 서버 검증이 없다** (`@Valid` 누락 — 공통명세 S5-1). 위 3건이 유일한 방어다.
비밀번호 형식은 검사하지 않는다 — 기존 계정의 비밀번호 규칙이 바뀌었을 수 있고,
로그인에서 형식을 막으면 정상 계정이 로그인하지 못한다.

## D6. 접근성

- 입력 2개 모두 `label` 연결. placeholder 를 label 대신 쓰지 않는다.
- `autoComplete`: 이메일 `username`, 비밀번호 `current-password`
- `type="email"` / `inputMode="email"` — 모바일 키보드 전환
- 오류 시 `aria-invalid="true"` + `aria-describedby` 로 메시지 연결
- 폼 전체 오류는 `role="alert"` — 제출 후 화면 변화가 없으면 스크린리더가 실패를 모른다
- 제출 실패 시 첫 오류 필드로 포커스 이동
  - **필드 오류가 없는 실패**(5xx · 무응답 · 429 `AUTH_015` · 400 `MEMBER_007`)는 `FormAlert` 로
    옮긴다 (#1078, `form-guide.md` §8). 제출 중 버튼이 `disabled` 가 되며 포커스가 `BODY` 로
    떨어져 거기 남았다. 401 은 지금처럼 비밀번호를 비우고 그 칸이다.
  - **5xx · 무응답은 `FormAlert` 가 아니라 폼 안 일시 장애 표시**(`data-form-temporary-error`)로
    간다 (#1079). 그 화면에는 `FormAlert` 가 서지 않는다. 재시도 버튼이 아니라 표시 상자인 것은
    오프라인이면 버튼이 걷히고, 버튼만 받으면 "다시 시도" 만 읽혀 무엇이 실패했는지 모르기
    때문이다. 다음 Tab 이 재시도 버튼이다.
- 비밀번호 표시 토글은 icon-only → `aria-label` + `aria-pressed`
- 터치 영역 44px 이상 (토글 버튼 포함)
- 색 외 전달 수단: 오류는 색 + 아이콘 + 텍스트

## D10. 화면 재배치 · 이메일 기억하기 (#1081, 2026-10-01)

> 확정: 사용자 2026-10-01 (이슈 #1081 본문이 정본). UX 리뷰 항목 M4 · L1 · L6.
> D1 · D4 의 링크 자리(회원가입 · 비밀번호 찾기가 폼 아래 가운데 정렬)는 이 절로 바뀌었다.

### 배치 (위에서 아래로)

1. 제목 · 이메일 · 비밀번호
2. **비밀번호 바로 아래 한 줄** — 왼쪽 `이메일 기억하기` 체크박스 · 오른쪽 `비밀번호 찾기` 링크.
   켜면 그 줄 아래 전폭 캡션 _"이 기기에 이메일만 저장돼요. 공용 기기에서는 해제해 주세요."_
3. 로그인 버튼
4. `또는` 구분선 + 소셜 버튼 (`LoginDivider`)
5. 맨 아래 _"아직 회원이 아니신가요? 회원가입"_ (`LoginSignupPrompt`, `returnTo` 를 문다)

텍스트 링크(비밀번호 찾기 · 회원가입)는 `min-h-11` 로 누르는 자리를 44 로 둔다 (DESIGN.md §7 #905 R3).
비밀번호 찾기가 폼 밖 맨 아래에서 비밀번호 옆으로 올라온 이유: 비밀번호가 막힌 사람이 소셜
버튼을 지나서야 찾았다. 링크 문구는 한 줄에 서도록 `비밀번호를 잊으셨나요?` → `비밀번호 찾기`.

캡션을 체크박스 `description` 이 아니라 줄 전체 폭에 두는 이유: 왼쪽 칸에 넣으면 375 에서 링크
몫을 뺀 폭으로 줄이 세 번 바뀐다.

### 이메일 기억하기 규칙

| 항목           | 규칙                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------ |
| 저장소         | `localStorage` `hdg_saved_login_email`. 접근은 전부 `try/catch` (`src/lib/auth/saved-login-email.ts`)  |
| 저장하는 것    | **이메일만.** 비밀번호 · 토큰은 저장하지 않는다                                                        |
| 기본값         | **꺼짐.** 저장값이 있으면 켜진 채로 복원한다 (마운트 뒤 effect — 서버 렌더와 첫 렌더를 맞추려고)       |
| 저장 시점      | **로그인 성공 시에만.** 실패(401 · 429 · `MEMBER_007` 소셜 전용 · 5xx)는 저장하지 않는다               |
| 해제           | 체크를 끄는 **즉시** 삭제 — 로그인하지 않고 떠나도 남지 않는다                                         |
| 첫 값 우선순위 | `?email=` 쿼리 > 저장값. 체크 상태는 쿼리와 무관하게 저장값 유무를 따른다 (`resolveInitialLoginEmail`) |
| 유지           | 로그아웃 · 비밀번호 변경 (`reauth=password-changed`)                                                   |
| 삭제           | 탈퇴 (`withdrawn`) · 소셜 전용 전환 (`password-removed`) — `useSessionExit` 가 이동 **전에** 지운다    |
| 소셜 로그인    | 저장값을 읽지도 쓰지도 않는다                                                                          |

**체크 상태가 쿼리를 따르지 않는 이유**: 이 기기에서 기억하기를 켜 둔 선택은 이메일 칸에 무엇이
채워졌든 유효하다. 쿼리가 왔다고 끄면 로그인 성공 뒤 저장이 조용히 멈춘다. 켜진 체크와 캡션이
보이므로 사용자가 끌 수 있다.

**삭제를 로그인 화면(`?reauth=`)이 아니라 `useSessionExit` 에서 하는 이유**: 쿼리는 누구나 만들
수 있는 링크라 실제 성공과 무관하게 지워진다. `useSessionExit(reason)` 은 서버가 탈퇴 · 전환
성공을 돌려준 뒤에만 불리고, 두 흐름(`withdraw-modal` · `remove-password-section`)이 모두 여기를
지난다. 이동 전에 지우므로 로그인 화면이 저장값을 읽을 때 이미 비어 있다.

**알려진 한계**: 기억한 이메일이 탈퇴한 계정의 것인지 대조하지 않는다. A 가 기억해 둔 기기에서
B 가 소셜로 로그인해 탈퇴하면 A 의 기억도 지워진다 — 편의값 하나를 잃을 뿐이라 대조 비용을
들이지 않는다.

### 입력 보조 (L1 · L6)

- **이메일이 채워져 오면(쿼리 · 저장값) 비밀번호로 포커스를 옮긴다.** 빈 채로 오면 건드리지
  않는다 — 모바일에서 키보드가 화면을 덮은 채 시작하지 않게.
- 비밀번호 칸에서 Caps Lock 이 켜져 있으면 `hint` 자리에 _"Caps Lock이 켜져 있어요."_ 를 띄운다.
  `getModifierState('CapsLock')` 은 키 이벤트에만 있어 첫 키 입력부터 뜬다. 칸을 떠나면 끈다.
- `enterKeyHint`: 이메일 `next` · 비밀번호 `done`.
- 비밀번호 칸은 공용 `PasswordInput` (#1080) 으로 옮겼다. 토글 배선은 같고, 표시 상태는 컴포넌트가
  갖는다. Caps Lock 키 이벤트는 native prop 이라 공용 컴포넌트를 고치지 않고 받는다.
- **로그인 성공 뒤 이동이 끝날 때까지 버튼을 `loading` 으로 둔다.** `useForm` 의 `isSubmitting`
  은 `onSuccess` 직후 내려가 새 화면이 뜨기 전 틈에 두 번째 요청이 나갈 수 있었다.

## D11. 제출 중 표시 (#1084, 2026-10-01)

UX 검토 L2 실측 두 가지.

**요청이 도는 동안 직전 폼 전체 실패를 걷는다.** 예전에는 401 알림("이메일 또는 비밀번호가 …")이
다시 낸 요청이 도는 동안에도 서 있어, 버튼은 "로그인 중" 인데 화면은 "실패했다" 를 함께 말했다.
직전 실패는 새 시도가 시작된 순간 낡은 정보다. 일시 장애(5xx)도 같다 — 재시도를 눌러도
"잠시 문제가 생겼어요" 가 남으면 눌렸는지 알 수 없다. 판정은 `FormFailure` 의 **필수** prop
`submitting` 하나다: 로그인 · 가입 세 단계 · 재설정 두 단계가 같은 자리를 쓰므로 한 번에 걸린다
(코드 단계는 재발송 중에도). 필드 오류는 그대로 둔다 — 고친 필드만 지우는 규칙(D4)이 이미 있다.

**이메일 로그인이 도는 동안 소셜 버튼을 잠근다.** 예전에는 그대로 눌려, 이메일 로그인 응답을
기다리는 사이 제공자 인가 화면으로 떠났다. 페이지는 서버 컴포넌트라 형제 사이의 상태를 들 수
없어 `LoginMethods`(이메일 폼 · "또는" · 소셜 버튼 · 회원가입 입구)를 한 클라이언트 경계로 묶었다.
묶은 이유는 이 상태 하나라 Fragment 를 돌려주고 간격은 페이지의 `gap-4` 를 그대로 쓴다. 잠그는
기간은 버튼의 `loading` 과 같다 — 성공 뒤 이동이 끝날 때까지(D10 "이동이 끝날 때까지"). 안내
문구는 달지 않는다: 1초 남짓이면 풀리고 그 동안 이유는 바로 위 "로그인 중" 버튼이 말한다.

**알리는 자리는 effect 가 아니라 제출 핸들러다.** `submitting` 을 effect 로 내보냈을 때 실측에서
"로그인 중" 이 보인 직후에도 소셜 버튼이 아직 눌렸다 — effect 가 그린 뒤에 돌고, 거기서 부른 부모
setState 가 렌더를 한 번 더 기다린다. 요청을 내는 `onSubmit` 첫 줄에서 알리면 `isSubmitting` 과
같은 배치로 한 렌더에 잠긴다. 실패로 끝나면 풀고, 성공이면 이동이 끝날 때까지 둔다.

테스트: 렌더 `form-failure.test.ts` · `login-form.test.ts` · `social-login-buttons.test.ts`,
e2e `e2e/auth-submitting.spec.ts`(응답을 route 로 붙잡아 "로그인 중" 순간을 본다).

반대 방향(소셜 이동 중 이메일 제출)은 잠그지 않았다 — 소셜은 `authorize` 응답 즉시 문서를 떠나
겹치는 틈이 짧고, 이 이슈의 실측 대상이 아니었다.
