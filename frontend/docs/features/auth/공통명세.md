## S0. 개요

- **한 줄 정의**: 이메일 계정으로 가입하고 로그인해 보호 화면에 진입한다.
- **사용자가 달성하려는 것**: 반려견 프로필·여행 일정 등 자기 데이터를 쓰기 위한 신원 확보.
- **범위에 포함**
  - `/login` — 이메일 + 비밀번호 로그인, `returnTo` 복귀
    (로그아웃은 계정 메뉴 · 마이페이지로 옮겨 갔다 — S5-5 개정, #1082)
  - `/signup` — 이메일 인증코드 발송 → 검증 → 가입
  - **폼 규약 정본 `docs/form-guide.md` (T4)** 최초 적용
  - mock 인증 계층 (백엔드 미기동 상태에서 화면·세션 검증)
- **범위에서 제외**
  - 소셜 로그인 2-step (`GET /auth/{provider}/authorize` → `/login`) — 별도 이슈.
    앱 키·redirect URI 등록이 선행이라 지금 만들어도 실동작을 검증할 수 없다.
  - `/mypage` 내 정보·비밀번호 변경·탈퇴 — 별도 이슈
  - 전역 nav / 헤더 — 이슈 #15
  - 비밀번호 찾기·재설정 — **백엔드에 해당 API 가 없다** (S5-3)

## S1. 화면 목록

| 화면     | 경로      | 인증                          | 상태 |
| -------- | --------- | ----------------------------- | ---- |
| 로그인   | `/login`  | 불필요 (라우트 그룹 `(auth)`) | 기획 |
| 회원가입 | `/signup` | 불필요                        | 기획 |

`(auth)` 는 라우트 그룹이라 URL 에 나타나지 않는다. `PROTECTED_PATHS` 에 넣지 않는다 —
로그인 화면이 보호 대상이 되면 무한 리다이렉트가 된다.

## S2. 사용 API

| #   | METHOD 경로                           | 용도          | 인증   | 비고                                              |
| --- | ------------------------------------- | ------------- | ------ | ------------------------------------------------- |
| 1   | `POST /api/v1/auth/login`             | 이메일 로그인 | 불필요 | **`@Valid` 누락** → 서버 검증 없음 (S5-1)         |
| 2   | `POST /api/v1/auth/logout`            | 로그아웃      | 필요   | `Set-Cookie` 로 refresh 쿠키 삭제                 |
| 3   | `POST /api/v1/auth/email/send-code`   | 인증코드 발송 | 불필요 | **60초 쿨다운**. 가입 여부와 무관하게 항상 성공   |
| 4   | `POST /api/v1/auth/email/verify-code` | 인증코드 검증 | 불필요 | 성공 후 **30분** 내 가입해야 한다                 |
| 5   | `POST /api/v1/members/signup`         | 회원가입      | 불필요 | 응답 `dataBody` 는 `null` — **자동 로그인 안 됨** |
| 6   | `POST /api/v1/auth/token/reissue`     | 토큰 재발급   | 쿠키   | BFF 가 이미 처리 중 (신규 호출부 없음)            |

- **Swagger 확인 여부**: 미확인. 백엔드 미기동 (사유는 문서 상단).
- **미구현 API**: 비밀번호 재설정 (S5-3).

### 회원가입은 3단계 호출이다

```text
send-code(email)  →  [메일 수신]  →  verify-code(email, code)  →  signup(email, password, name, nickname)
      60초 쿨다운                          성공 시 30분 유효
```

`verify-code` 성공은 **서버에 상태로 남는다.** 프론트가 토큰을 받아 signup 에 넘기는 방식이
아니다. 즉 verify 와 signup 사이에 새로고침이 나도 30분 안이면 가입할 수 있다.
반대로 30분이 지나면 `MEMBER_006`(이메일 인증 미완료, 400)이 온다.

## S3. 데이터 모델

```ts
// POST /auth/login — 요청 (AuthGeneralLoginRequest 실측)
type LoginRequest = { email: string; password: string }

// POST /auth/login — dataBody (AuthGeneralLoginResponse 실측)
type LoginResponse = { accessToken: string; memberId: string }

// POST /members/signup — 요청 (MemberGeneralSignupRequest 실측)
type SignupRequest = {
  email: string
  password: string // 8~20자, 영문자+숫자+특수문자 각 1자 이상, 공백 불가
  name: string // 10자 이하
  nickname: string // 10자 이하
}

// POST /auth/email/send-code, /verify-code — 요청
type EmailCodeSendRequest = { email: string }
type EmailCodeVerifyRequest = { email: string; code: string }
```

- **nullable 필드**: 없음. 요청은 전부 필수다.
- **문자열 ID**: `memberId` 는 **`string`** 이다. `Number()` 로 파싱하지 않는다 (`auth-guide.md` §4).
- **enum metadata 필드**: 없음.
- **응답 `dataBody`**: `signup` / `logout` / `verify-code` / `send-code` 는 모두 `null` 이다.
  `unwrap()` 은 `dataBody === null` 을 실패로 보고 던지므로 **이 호출들에 `unwrap()` 을 쓰면 안 된다** (S5-4).

### 브라우저가 보는 것

BFF 가 `dataBody` 에서 `accessToken` 을 제거한 뒤 내려보낸다. 로그인 응답에서
**브라우저 JS 가 받는 것은 `memberId` 뿐**이다 (`auth-guide.md` §8).

## S4. 상태 / 에러

| 상태                   | 조건                                | 화면                               | 문구                           |
| ---------------------- | ----------------------------------- | ---------------------------------- | ------------------------------ |
| loading                | 제출 중                             | 버튼 `disabled` + `aria-busy`      | 직전 폼 전체 실패는 걷는다     |
| 입력 오류 (400)        | Bean Validation 실패                | 필드 에러                          | 서버 `errors[].message` 그대로 |
| 로그인 실패 (401)      | `AUTH_006`                          | 폼 전체 오류 (`role="alert"`)      | 서버 문구 그대로               |
| 인증코드 오류 (400)    | `AUTH_004` 불일치 / `AUTH_005` 만료 | 코드 필드 에러                     | 서버 문구 그대로               |
| 이메일 중복 (409)      | `MEMBER_001`                        | 이메일 필드 에러 + 로그인 링크     | 서버 문구 + "로그인하기"       |
| 쿨다운·잠금 (429)      | `AUTH_003` 재전송 / `AUTH_015` 잠금 | 폼 전체 오류, **재시도 버튼 없음** | 서버 문구 그대로               |
| 소셜 계정 (400)        | `MEMBER_007`                        | 폼 전체 오류                       | 서버 문구 그대로               |
| 일시 장애 (5xx·무응답) | 게이트웨이 다운 등                  | ErrorState (**재시도 있음**)       | `messages.common.temporary*`   |

**404 는 이 화면들에 나오지 않는다.** 로그인 실패를 404로 내리지 않는 것은 계정 열거 방지
설계다 (`AuthErrorCode.LOGIN_FAILED` 주석). 존재하지 않는 이메일도 **401 로 동일하게** 응답한다.

### `ErrorKind` 를 확장한다

현재 `classify()` 는 409·429 를 모두 `'forbidden'` 으로 뭉갠다. 위 표의 분기를 만들 수 없다.

```ts
type ErrorKind =
  | 'validation' // 400
  | 'unauthorized' // 401
  | 'not-found' // 404
  | 'conflict' // 409  ← 추가
  | 'rate-limited' // 429  ← 추가
  | 'forbidden' // 그 외 4xx
  | 'temporary' // 5xx · 무응답
```

`isRetriable` 은 **429 에 `false`** 를 유지한다. 즉시 재시도는 무의미하고, 잠금 상황에서
재시도 버튼을 주면 사용자가 잠금을 연장한다. 안내 문구로만 처리한다.

### BFF 결함 — 로그인 실패를 토큰 만료로 오인한다

`app/api/bff/[...path]/route.ts` 는 **401 이면 재발급 후 원 요청을 재시도**한다.
조건은 `session !== null && !isReissuePath(path)` 뿐이다.

그런데 `POST /auth/login` 의 로그인 실패도 **401**(`AUTH_006`)이다. 세션이 남은 채로
(만료된 세션 보유, 다른 계정으로 재로그인) 로그인에 실패하면:

```text
login 401 → reissue → login 재시도 → 401
```

**같은 자격증명으로 로그인 실패가 2회 카운트된다.** `AUTH_015` 잠금이 절반의 시도로 걸린다.

→ 재발급 대상에서 **인증 진입 엔드포인트를 제외**한다. `isReissuePath` 옆에
`isAuthEntryPath`(`/auth/login`, `/auth/{provider}/login`)를 두고 조건에 더한다.
재발급으로 복구할 수 있는 401 이 아니기 때문이다.

## S7. 로그아웃 뒤 라우터 캐시 (#1099, 2026-10-01)

로그아웃은 **문서를 바꾸지 않는 이동**이다 — 계정 메뉴(`account-menu.tsx`)는
`router.replace('/')` → `router.refresh()`, 마이페이지 · 비밀번호 변경 · 소셜 전용 전환 ·
탈퇴(`use-session-exit.ts`)는 `router.replace('/login…')` → `router.refresh()`. 로그인 쪽은
#1075 에서 `location.replace` 로 바꿨다(로그인 세부명세 D3). 반대 방향에서도 로그인 상태에서
받아 둔 Next 클라이언트 캐시가 남아 직전 사용자 화면을 다시 그리는지 확인했다.

**결론 — 로그아웃이 끝난 뒤에는 그리지 않는다. 이동 방식은 바꾸지 않는다.**

### 재현 조건과 결과

- 목 · `next dev --webpack` · next 16.3.3 · Chromium(Playwright headless). 홈에서 출발해 화면 안
  링크로 `/mypage` · `/favorites` · `/pets` · `/plans` 를 돈 뒤(문서 1개 유지) 로그아웃했다.
- 직전 사용자 표식(닉네임 · 반려견 이름 · 일정 제목)을 `MutationObserver` 로 **매 변경마다**
  봤다. 단언 시점의 화면만 보면 잠깐 그렸다가 로그인으로 간 경우를 놓친다.
- **앞으로 이동** — 캐시된 보호 경로 넷 모두 RSC 를 새로 요청했고, proxy 가 307 로
  `/login?returnTo=…` 에 보냈다. 계정 메뉴 · 마이페이지 로그아웃 모두 표식 0건.
- **뒤로가기** — 로그아웃 전 히스토리 항목 셋 모두 새로 요청해 로그인에 섰다. 표식 0건.
- 계정 메뉴 · 마이페이지 각 갈래 여러 차례, CPU 스로틀 1배 · 6배(CDP
  `Emulation.setCPUThrottlingRate`)에서 같았다. `e2e/logout-router-cache.spec.ts` 가 잠근다.

### 왜 안전한가

- **route cache 는 남는다.** 그러나 URL → 라우트 트리의 **모양**만 든다. 로그인 때 받은
  `/plans` 의 트리는 비로그인에도 같은 `(main)/plans` 라 낡지 않았다. 그 트리로 이동하면 세그먼트
  데이터를 새로 요청하고, proxy 가 그 요청에서 로그인으로 보낸다. #1075 는 이 캐시에 **리다이렉트
  결과**(그 URL = 로그인 화면)가 남아서 깨졌고, 여기서는 그런 기록이 생기지 않는다.
- **데이터는 segment cache 와 BFCache 에 있다.** BFCache 는 뒤로/앞으로 가기가 **요청 없이**
  다시 그리는 동적 데이터다(`segment-cache/bfcache.js`, 뒤로가기는 stale time 도 보지 않는다).
  서버 프리페치(`HydrationBoundary`)가 실린 RSC 라 직전 사용자 데이터가 그대로 든다.
- **둘을 비우는 것이 `router.refresh()` 다.** `refresh-reducer.js` 가 segment cache 버전과
  BFCache 버전(`invalidateBfCache`)을 **전역으로** 올린다 — 현재 화면만이 아니다.
- **변이로 확인했다.** `refresh` 를 빼면 로그아웃 뒤 뒤로가기가 직전 사용자의 일정 목록과
  마이페이지(닉네임 · 이메일)를 **요청 0건으로** 그렸고 헤더도 로그인 모양으로 남았다. e2e 세 건이
  모두 깨진다. **`refresh` 는 헤더만을 위한 줄이 아니다.**

### 남는 틈 — 이동이 끝나기 전의 뒤로가기 (고치지 않음)

`refresh` 는 라우터 action queue 에서 `replace` **뒤에** 줄 선다. 뒤로가기(`ACTION_RESTORE`)는
대기 중인 이동을 밀어내고 곧바로 돈다(`app-router-instance.js` 의 `dispatchAction`). 그래서
**로그아웃 응답 ~ 목적지 이동 완료 사이**에 뒤로가기를 누르면, 아직 무효화되지 않은 BFCache 의
직전 화면(일정 목록)이 잠깐 그려지고 이어서 `refresh` 가 그 URL 을 다시 물어 로그인으로 간다.

- 응답 직후(0 ~ 300ms) 누르면 계정 메뉴 21/21, 마이페이지 4/4 재현(스로틀 1 · 6배, 목적지 응답
  지연 0 · 2.5초). 800ms 이상 뒤에 누르면 0/4.
- **보는 사람은 방금 로그아웃을 누른 본인이고**, 틈이 지나면 닫힌다. 기기를 넘겨받은 다른 사람이
  나중에 뒤로가기를 누르는 경우는 위의 안전한 갈래다.
- 로그아웃 POST 가 **진행 중일 때** 누르는 경우도 같은 모양이다. 응답 전에는 캐시를 비울 근거가
  없어 어느 안으로도 닫히지 않는다.

버린 대안 (모두 목으로 실측):

- **`location.replace(href)`** (`enterSession` 과 같은 방식) — 새 문서가 오기 전에 뒤로가기를
  누르면 브라우저가 그 이동을 취소하고 **같은 문서 안의 히스토리 이동**으로 돌아간다. Next 가
  BFCache 로 직전 화면을 그리고, `refresh` 가 없으니 **그 화면에 머문다**(로그인으로 가지 않는다).
  지금보다 나쁘다.
- **`refresh` → `replace`** — 큐가 비어 있으면 `refresh` 의 무효화가 호출 즉시 돌아 틈이 닫힌다.
  그러나 곧 `replace` 에 밀려 버려지는 `refresh` 가 **떠나는 보호 화면의 RSC 를 매 로그아웃마다**
  요청한다(307 + 로그인 RSC). 경합하면 그 응답이 문서 이동으로 이어져
  `/login?returnTo=<떠난 화면>` 에 떨어졌다.
- **`refresh` → `replace` → `refresh`** — 틈은 닫혔다(계정 메뉴 3/3, 마이페이지 2/2). 비용은 위와
  같고, "큐가 비어 있을 때 `refresh` 의 reducer 가 동기로 돈다" 는 Next 내부 동작에 기댄다.

**본인에게 1초 안쪽으로 보이는 틈을 막으려고 매 로그아웃에 요청을 더하고 내부 동작에 기대는 것은
남는 것이 없다고 봤다.** 다른 사람에게 보이는 경로가 생기면(예: 로그아웃 뒤 자동 이동이 없어지는
변경) 다시 판단한다.

## S8. 인증 셸 — 모바일 한 면 · 표식은 화면이 단다 (#1283, 2026-10-08)

| 폭    | 바닥               | 폼                                            | 세로 정렬 |
| ----- | ------------------ | --------------------------------------------- | --------- |
| < 768 | 흰 바탕 한 면      | 카드 없음, 좌우 20                            | 위쪽      |
| ≥ 768 | `bg-bg-sunken`(L0) | 흰 카드(L1) · 테두리 · radius 12 · `max-w-sm` | 가운데    |

- 375 에서 카드는 화면을 거의 다 차지해 경계가 하는 일이 없고, 테두리 · 좌우 여백이 겹쳐 박스 안의 박스로
  보였다(C1). 카카오 · 네이버 · 토스의 모바일 인증 화면은 카드 없는 한 면이다.
- 모바일 가운데 정렬은 화면마다 내용 높이가 달라 넘길 때 첫 줄이 튀었다(C2) — 위쪽 정렬로 바꿨다.
- **락업(`AuthBrand`)은 들어오는 자리(로그인 · 소셜 콜백)에만**, 하위 화면(회원가입 · 소셜 가입 동의 ·
  비밀번호 찾기)은 **`AuthTopBar`(`←` + 선택적 화면 이름)** 를 단다(C3). #532 가 셸에 두었던 락업을 화면으로
  내렸다 — 셸이 넷 모두에 그리면 하위 화면에서 락업과 `←` 가 같은 첫 줄을 다툰다.
