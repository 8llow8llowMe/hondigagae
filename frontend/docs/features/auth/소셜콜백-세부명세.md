## D0. 화면 정의

- **경로**: `/(auth)/oauth/[provider]/callback` — route group `(auth)`
- **인증**: 불필요. `PROTECTED_PATHS` 에 넣지 않는다
- **진입 경로**: 소셜 제공자의 리다이렉트 (**우리 화면에서 링크로 오지 않는다**)
- **이탈 경로**: `returnTo` 또는 `/` (성공) · `/login` (실패)

**로그인 화면에 소셜 버튼을 다는 것도 이 이슈다.** 콜백만 만들면 진입점이 없다.

## D1. 계약 — 서버가 리다이렉트를 대신 해주지 않는다

```text
1) GET /auth/{provider}/authorize      → { authorizationUrl }   ※ state 10분 유효
2) 사용자를 authorizationUrl 로 이동   ※ 우리가 location 을 바꾼다
3) 제공자가 /oauth/{provider}/callback?code=&state= 로 돌려보낸다
4) GET /auth/{provider}/login?code=&state=  → 일반 로그인과 동일한 응답 + Set-Cookie
```

`provider`: **`kakao` · `naver`** (`OAuthProvider` enum, 소문자 경로).

- **4단계를 반드시 `/api/bff` 로 부른다.** BFF 가 응답 body 의 `accessToken` 을 벗겨 세션
  쿠키에 봉인하고 게이트웨이의 refresh 쿠키를 함께 담는다 (`architecture-guide.md` §5).
  게이트웨이를 직접 부르면 **토큰이 브라우저 JS 에 노출되고 세션이 만들어지지 않는다.**
- 미가입 이메일이면 **자동 회원가입 후 로그인**한다 (컨트롤러 설명). 화면에 가입 단계가 없다.
- **일반 계정(이메일+비밀번호)에 소셜로 로그인하면 그 계정에 소셜이 자동 연결된다**
  (`OAuthLoginProcessor.resolveExistingMember` — 연결 통보 메일까지 나간다). `AUTH_008` 은
  **이미 *다른* 소셜로 가입된 경우**에만 나온다. 화면이 따로 할 일은 없지만, 같은 이메일로
  두 수단이 생기는 것이 정상 동작이라는 점은 알고 있어야 한다.

### 오류 — 전부 4단계에서 나온다

| 코드         | HTTP | 뜻                                 | 화면                                                   |
| ------------ | ---- | ---------------------------------- | ------------------------------------------------------ |
| `AUTH_007`   | 400  | 지원하지 않는 provider (아래 참고) | 처음부터 다시                                          |
| `AUTH_008`   | 409  | **이미 다른 소셜로 가입된 계정**   | 서버 문구가 어느 provider 인지 말해 준다 → 그대로 노출 |
| `AUTH_009`   | 400  | 이메일 제공 **동의 필요**          | 동의 안내 + 다시 시도                                  |
| `AUTH_010`   | 401  | **state 무효** (10분 만료 · 위조)  | 처음부터 다시                                          |
| `AUTH_011`   | 400  | 프로필(닉네임) 제공 **동의 필요**  | 동의 안내 + 다시 시도                                  |
| `AUTH_012`   | 400  | 소셜 계정 이메일 **미인증**        | 제공자에서 인증 후 다시                                |
| `AUTH_013`   | 400  | 인증 실패                          | 처음부터 다시                                          |
| `AUTH_014`   | 502  | **제공자와 통신 불가**             | 잠시 후 다시 (우리 잘못이 아니다)                      |
| `MEMBER_010` | 400  | **가입 동의 누락** (최초 연동)     | `/signup` 으로 — 회원가입 화면에서 동의 후 다시 (#688) |
| `MEMBER_011` | 400  | **만 14세 확인 누락** (최초 연동)  | 〃                                                     |

**문구를 우리가 짓지 않는다.** 위 코드 전부 `resultMessage` 가 이미 행동을 안내한다
(예: `AUTH_008` 은 어느 소셜로 가입됐는지까지 알려준다). `errorCode` 로는 **다음 행동만**
가른다 — "다시 시도" 인지 "제공자에서 조치" 인지.

> **`AUTH_007` 은 사용자 입력으로는 사실상 나오지 않는다.** 컨트롤러가
> `@PathVariable OAuthProvider` 라 모르는 provider 는 `WebConfig` 의 컨버터에서 먼저
> 터지고(`fromName` → `IllegalArgumentException`), 그 예외는 `MethodArgumentTypeMismatchException`
> 이 되는데 **`AuthExceptionHandler` 가 그것을 처리하지 않는다** (`AUTH_105`
> `PARAMETER_TYPE_INVALID` 가 선언만 되어 있고 쓰이지 않는다). → **BE 후속 필요.**
>
> FE 는 여기에 기대지 않는다: 경로 세그먼트가 `kakao`·`naver` 가 아니면 **요청을 보내지 않고**
> "잘못된 접근" 으로 간다 (`use-oauth-exchange.ts` 의 `isOAuthProvider`). 서버 응답이
> 무엇이든 화면은 성립한다.

## D3. 데이터 흐름

```text
[로그인 화면]  소셜 버튼 → GET /auth/{provider}/authorize
               → sessionStorage 에 returnTo 저장
               → window.location.assign(authorizationUrl)

[콜백 화면]    searchParams 에서 code · state
               → GET /api/bff/auth/{provider}/login?code=&state=
               → 성공: router.replace(returnTo ?? '/')
               → 실패: 오류 화면
```

| 항목        | 내용                                                               |
| ----------- | ------------------------------------------------------------------ |
| API         | `authorize` (버튼) · `login` (콜백)                                |
| React Query | **쓰지 않는다** — 캐시하면 안 되는 1회용 교환이다                  |
| 성공 후     | `queryClient.clear()` 후 이동 — 이전 사용자의 캐시를 남기지 않는다 |
| `returnTo`  | `sessionStorage`. **URL 에 싣지 않는다** (open redirect 표면)      |

### 반드시 지킬 것 셋

1. **교환은 정확히 한 번만 실행한다.** React 18 StrictMode 는 개발 모드에서 effect 를 두 번
   돌리고, 그러면 **성공한 뒤 곧바로 실패 화면이 뜬다.** `useRef` 가드로 막는다 — 이 화면에서
   가장 흔한 버그다.

   > **실패 코드는 `code` 재사용이 아니라 `AUTH_010` 이다** (구현 중 소스 실측으로 정정).
   > `state` 를 Redis `GETDEL` 로 조회와 동시에 지우기 때문에(`RedisOAuthStateStoreAdapter.consume`)
   > **두 번째 호출은 `code` 에 닿기도 전에 state 검증에서 막힌다.** 실패해도 소비되므로
   > 재시도 자체가 불가능하다 — 그래서 오류 화면의 다음 행동이 모두 `/login` 이다.

2. **성공 후 `code`·`state` 를 주소에서 지운다.** `router.replace` 로 이동하면 히스토리에도
   남지 않는다. 남겨 두면 뒤로가기로 같은 코드를 다시 쓰려다 실패 화면을 본다.

3. **`returnTo` 는 같은 오리진의 경로만 허용한다.** `sessionStorage` 에서 읽은 값이라도
   `/` 로 시작하고 `//` 로 시작하지 않는 문자열만 쓴다. 아니면 `/` 로 보낸다.
   `proxy.ts` 가 이미 `?returnTo=` 로 보호 경로를 돌려보내므로 그 값을 이어받는다.

## D4. 상호작용

| 트리거                | 동작                        | 결과                                                     |
| --------------------- | --------------------------- | -------------------------------------------------------- |
| 소셜 버튼             | `authorize` → 제공자로 이동 | 실패하면 로그인 화면에 `FormAlert`                       |
| 콜백 진입             | 교환 1회                    | 성공 → 이동 / 실패 → 오류 화면                           |
| `code`·`state` 없음   | 교환하지 않는다             | 잘못된 진입 안내 + `/login`                              |
| 오류 화면 `다시 시도` | `/login` 으로               | **콜백에서 재시도하지 않는다** — `code` 가 이미 소모됐다 |

| 상태                                         | 표시               | 문구 (확정)                                                        |
| -------------------------------------------- | ------------------ | ------------------------------------------------------------------ |

| 성공                                         | (즉시 이동)        | —                                                                  |

| 가입 동의 누락 (`MEMBER_010`/`MEMBER_011`)   | 안내 + `/signup`   | 서버 `resultMessage` 그대로 + `회원가입에서 동의하기` (#688)       |

**성공 화면을 만들지 않는다.** 성공하면 곧바로 원래 가려던 곳으로 보낸다.

## D6. 접근성

- 교환 중 상태를 `aria-live="polite"` 로 알린다 — 화면이 저절로 바뀌는 유일한 화면이다
- 소셜 버튼은 제공자 이름을 텍스트로 담는다. **로고만 두지 않는다**
- 오류 화면의 다음 행동은 링크가 아니라 `Button` — `/login` 으로의 이동이지만 재시도의 의미다
  (→ **이동이므로 `<a>` 가 맞다.** `place-back-link.tsx` 와 같은 판단을 따른다)

## D7. 테스트 케이스

**순수 로직**

- `returnTo` 검증 — `/plans` 통과 / `//evil.com` 거부 / `https://evil.com` 거부 / `null`→`/`
- 오류 코드 → 다음 행동 매핑 (다시 시도 / 제공자에서 조치 / 잘못된 접근)

**렌더 분기**

- `code` 없음 → 교환하지 않고 안내
- `AUTH_008` → 서버 문구가 그대로 나온다
- **교환이 두 번 실행되지 않는다** (가드 회귀 테스트)
- 성공 시 성공 화면을 렌더하지 않는다

**mock**

`auth-data.ts` 에 `authorize` 와 `{provider}/login` 을 추가한다. **state 를 소비하게 만든다**
(백엔드 `GETDEL` 과 같은 성질) — 그것이 중복 실행 가드를 화면으로 확인할 수 있게 하는 유일한
장치다. 초안은 "같은 `code` 를 두 번 쓰면 실패" 로 적었는데, 실제 메커니즘은 state 쪽이다.

오류 시나리오는 **`code` 에 든 조각**으로 만든다 (`OAUTH_CODE_SCENARIOS`):
`email-denied`→`AUTH_009` · `profile-denied`→`AUTH_011` · `unverified`→`AUTH_012` ·
`unavailable`→`AUTH_014` · `linked`→프로필 이메일을 `social@` 로 바꿔 **`AUTH_008` 이 규칙대로
발생**하게 한다 (응답을 손으로 박지 않는다). `authorize` 에 시나리오 파라미터를 만들지 않는다 —
백엔드 계약에 없는 입구에 화면이 의존하게 된다.

**동의는 state 와 함께 보관한다** (#688). `authorize` 가 쿼리에서 읽어 `oauthStates` 의 값으로
넣고, `{provider}/login` 이 **신규 생성 직전에만** 꺼내 본다 — 백엔드 `validateSignupConsent` 와
같은 자리다. 기존 회원의 로그인은 동의와 무관하게 통과해야 하므로 이 분기 밖에 두면 안 된다.
문서 동의를 먼저 보아 `MEMBER_010` 이 `MEMBER_011` 을 가리는 순서까지 같게 맞춘다.

**provider 별 고정 계정**:

- `kakao` → `social@`(KAKAO · 비밀번호 없음). **#83 의 소셜 전용 분기를 브라우저로 볼 수 있는
  유일한 문이다** — 비밀번호가 없어 이메일 로그인이 불가능한 계정이라, 이 mock 이 없으면
  `/mypage/password` 의 소셜 전용 경로가 렌더 테스트로만 검증된 상태로 남는다.
- `naver` → 미가입 이메일 → **자동 회원가입 경로**.
