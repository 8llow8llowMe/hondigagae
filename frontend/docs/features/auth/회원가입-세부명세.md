## D0. 화면 정의

- **경로**: `/signup` (`app/(auth)/signup/page.tsx`)
- **인증**: **불필요.**
- **진입 경로**: `/login` 의 "회원가입" 링크 (`returnTo` 를 물고 온다), 직접 진입
- **이탈 경로**: 가입 완료 → `/login?returnTo=…` (자동 로그인되지 않는다), 하단 "이미 계정이
  있나요? 로그인" 링크 → `/login?returnTo=…` (#1083 — **`returnTo` 를 이어받는다**)

**가입 응답은 `dataBody: null` 이다.** 토큰을 주지 않으므로 가입 직후 자동 로그인은
불가능하다. 완료 후 로그인 화면으로 보내고 이메일을 미리 채워 준다.

## D1. 레이아웃

로그인과 같은 `(auth)` 셸. 단계 표시를 상단에 둔다.

**세로 순서 (#1083 에서 확정)** — 세 단계 모두 같다.

```text
제목 "회원가입"
단계 표시 "3단계 중 N단계"          ← SignupHeading
가입 동의 (모두 동의해요 / ─── / 필수 3종)  ← SignupConsentFields
단계 폼 (1: 이메일 · 2: 받는 이메일 + 코드 · 3: 가입할 이메일 + 프로필)
소셜 버튼 (카카오 · 네이버)
"이미 계정이 있나요? 로그인"          ← SignupLoginPrompt
```

> **#1083 이전에는 단계 표시가 동의 블록 아래였다.** 단계 표시가 단계 컴포넌트 안에 있었고,
> 동의 블록은 그 위(화면 단위, D10)에 섰기 때문이다 — 이 절의 "상단" 과 어긋났다. 단계 표시를
> 단계 컴포넌트 밖 `SignupHeading` 으로 빼 제목 바로 아래로 올렸다. 단계 컴포넌트는 이제
> 단계 표시를 그리지 않는다(테스트가 잠근다 — 한 화면에 두 번 서지 않게).

- 모바일 (375): 한 컬럼, 단계 표시는 텍스트 (`2 / 3`)
- 태블릿 / 데스크톱: `max-w-sm` 중앙 정렬

긴 한국어 실데이터로 확인할 항목:

- `MEMBER_105` 문구가 길다 — `"비밀번호는 공백 없이 영문자, 숫자, 특수문자를 각각 1자 이상 포함해야 합니다."`
  가 필드 아래에서 2~3줄이 될 때 다음 필드를 밀어내는 정도
- `MEMBER_001` — `"이미 가입된 이메일 (verylongaddress@example.com)입니다."` 의 줄바꿈

## D3. 데이터 흐름

```text
1단계  이메일 입력 → POST /auth/email/send-code
                     → 성공 → 2단계 + 60초 쿨다운 시작
2단계  코드 입력   → POST /auth/email/verify-code
                     → 성공 → 3단계  (인증 상태는 서버에 30분 유지)
3단계  프로필 입력 → POST /members/signup
                     → 성공 → /login?returnTo=…&email=…
```

**3단계 요청 바디에 동의 3종이 함께 실린다** (백엔드 #607 · #608, 이슈 #688).

```json
{
  "email": "...",
  "password": "...",
  "name": "...",
  "nickname": "...",
  "termsAgreed": true,
  "privacyAgreed": true,
  "ageOver14Confirmed": true
}
```

셋 다 **필수이며 `true` 여야 한다.** 빠뜨리거나 `false` 면 400 이다 — 요청 DTO 가 primitive
`boolean` + `@AssertTrue` 라 **필드를 아예 빼고 보낸 요청도 `false` 로 채워져 걸린다.**

| 항목                   | 내용                                                     |
| ---------------------- | -------------------------------------------------------- |
| API                    | `send-code`, `verify-code`, `signup` (3개 모두 mutation) |
| React Query key        | **없음** (mutation 전용)                                 |
| staleTime / retry      | `retry: false`                                           |
| mutation 후 invalidate | 없음 (로그인 전이라 캐시 없음)                           |
| 폴링 여부              | 없음. 쿨다운은 `setInterval` 카운트다운 (요청 아님)      |

**인증 상태는 프론트가 아니라 서버가 들고 있다.** `verify-code` 는 토큰을 반환하지 않고
서버에 "이 이메일은 인증됨(30분)"을 남긴다. 프론트는 단계 UI 만 관리한다.

**따라서 새로고침하면 1단계로 돌아간다.** 서버 인증은 살아 있으므로 같은 이메일로
코드를 다시 받아 진행하면 된다. 이 동작을 D8-1 에 미결로 남긴다.

| `MEMBER_006` 인증 미완료 (400) | `FormAlert` + **1단계로 되돌림**      | 30분이 지났다                        |

| `MEMBER_010/011` (400)         | 해당 동의 체크박스 오류               | **`field` 가 없다 — 코드로 가른다**  |
| 5xx / 무응답                   | `ErrorState` + 재시도                 | 단계·입력값 유지                     |

### 이메일 중복은 3단계에서야 드러난다

`send-code` 는 **가입 여부와 무관하게 항상 성공**한다 (계정 열거 방지 설계).
그래서 이미 가입된 이메일도 1·2단계를 통과하고, `signup` 에서 409 `MEMBER_001` 로 막힌다.

**이 흐름을 없앨 수 없다.** 백엔드 설계가 의도한 것이다. 화면이 할 일:

- 409 를 받으면 이메일 필드에 서버 문구를 붙이고 **"로그인하기" 링크를 함께 준다.**
  링크는 `/login?returnTo=…&email=<입력한 이메일>` 로 이메일을 넘겨 재입력을 없앤다.
- 3단계까지 입력한 비밀번호·이름·닉네임은 버린다. 다른 계정 정보이므로 유지할 이유가 없다.

> **필드 에러가 아니라 폼 전체 오류로 낸다** (2026-08-27 구현 시 정정).
> 초안은 "이메일 필드 에러"로 적었지만 **3단계 화면에는 이메일 입력이 없다** — 비밀번호·이름·닉네임만
> 있다. 붙일 필드가 없으므로 `FormAlert`(`role="alert"`) + 로그인 링크로 낸다. 링크가 이메일을
> 실어 보내므로 사용자는 재입력 없이 로그인으로 넘어간다.

```text
^(?=.*[A-Za-z])(?=.*\d)(?=.*[!@#$%^&*()\-_=+\[\]{};:'",.<>/?\\|])\S+$
```

## D6. 접근성

- 단계 전환 시 **새 단계의 첫 입력으로 포커스를 옮긴다.** 옮기지 않으면 키보드 사용자가
  단계가 바뀐 것을 모른다.
- 단계 표시는 텍스트로도 읽힌다 (`3단계 중 2단계`). 색·아이콘만으로 표현하지 않는다.
- **전체 동의는 가입 동의 그룹(`fieldset` / `legend`) 안에 선다** — 스크린리더가 "가입 동의,
  모두 동의해요" 로 무엇의 전체인지 함께 읽는다. `aria-controls` 로 필수 3종의 id 를 가리킨다.
  체크 상태는 네이티브 `checked` 로만 전한다(`aria-checked` 를 덮어쓰지 않는다).
- 2·3단계 이메일은 **입력이 아니라 값 표시**라 `dl`/`dt`/`dd` 로 라벨과 묶는다.
- `autoComplete`: 이메일 `username`, 코드 `one-time-code`, 비밀번호 `new-password`,
  이름 `name`, 닉네임 `nickname`
- 코드 입력은 `inputMode="text"` — 백엔드 예시가 `A3K7MP2X` 로 **영숫자 혼합**이다.
  `numeric` 으로 두면 영문자를 못 넣는다.
- **코드는 입력 중에 바로 대문자로 바꾸고 공백을 지운다** (#1078, 사용자 결정 2026-10-01).
  백엔드가 대문자로만 만들고(`VerificationCodeGenerator`) 대소문자를 가려 비교해서
  (`EmailVerificationProcessor`), `' a3k7mp2x '` 는 맞는 코드인데도 늘 `AUTH_004` 였다.
  - 칸은 `VerificationCodeInput` 이다 — 재설정 2단계와 같은 것. 정규화는
    `lib/auth/verification-code.ts` 하나이고, 스키마(`codeSchema`)도 제출 직전 같은 함수로 고친다.
  - 가운데를 고쳐도 **커서가 끝으로 튀지 않는다** — 입력 순간의 커서로 새 자리를 셈해 렌더 직후 되돌린다.
  - `autoCapitalize="characters"` · `autoCorrect="off"` · `spellCheck={false}`.
  - **8자 제한은 정규화가 건다. 네이티브 `maxLength` 를 쓰지 않는다** — 브라우저가 붙여넣은
    글자를 `maxlength` 로 먼저 잘라, 공백 섞인 코드(`' a3k7mp2x'`)가 정규화 전에 7자로 잘린다.
- **제출 실패 뒤 포커스** (#1078) — 1 · 2 · 3단계 모두 `submitCount` effect 가 옮긴다
  (`form-guide.md` §8). 첫 오류 필드 → 폼 전체 알림 → 폼의 첫 입력 순이다. 1단계 빈 제출은
  이메일 칸, 3단계 409(`MEMBER_001`)는 `FormAlert`, 서버 동의 오류는 그 체크박스다.
  `AUTH_005` · `MEMBER_006` 처럼 1단계로 되돌리는 실패는 위 단계 전환 규칙이 이메일 칸으로 옮긴다.
- 쿨다운 카운트다운은 `aria-live="polite"`. 매 초 읽히지 않도록 **10초 단위로만** 갱신 알림.
- 오류 시 `aria-invalid` + `aria-describedby`, 폼 전체 오류는 `role="alert"`
- 터치 영역 44px 이상
- **3단계 비밀번호 칸은 규칙을 틀리기 전에 보여 준다** (#1080) — `Field.hint` 에
  `8~20자, 영문 · 숫자 · 특수문자 각 1자 이상`(`messages.form.passwordRule`). 틀리면 그 자리를
  오류 문구가 대신한다. 규칙 문구는 백엔드 문구의 복제본이 아니라 길이 + 문자 구성을 한 줄로
  합친 안내다 — 오류 문구(`MEMBER_104` · `MEMBER_105`)는 D5 표 그대로다.
- **비밀번호 칸에 로그인과 같은 눈 토글을 단다** (`PasswordInput`, #1080). 가려진 채로 시작한다.
- **비밀번호 확인 칸은 두지 않는다** (#1080 기본 결정). 확인 칸이 막는 것은 "친 값이 생각한 값과
  다르다" 인데, 토글로 친 값을 직접 보고 고칠 수 있다. 칸이 하나 늘면 3단계가 네 칸이 된다.

- **순수 로직**

## D10. 가입 동의 · 만 14세 확인 (이슈 #688)

D8-5 의 "(a) 넣지 않음" 전제는 **백엔드 #607 · #608 이 머지되며 뒤집혔다.** 요청 DTO 에 자리가
없어서 넣지 않았던 것인데, 이제는 자리가 있을 뿐 아니라 **없으면 가입이 전부 400 이다.**

### 계약

| 입구                                  | 전달 방법                                                        | 필수 여부                                                   |
| ------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------- |
| 일반 가입 `POST /members/signup`      | 요청 바디 `termsAgreed` · `privacyAgreed` · `ageOver14Confirmed` | **필수. 셋 다 `true`**                                      |
| 소셜 `GET /auth/{provider}/authorize` | 쿼리 파라미터 같은 이름 3개                                      | 선택(기본 `false`). **최초 연동(= 신규 가입)에서만** 쓰인다 |

### 오류 코드

| 항목                   | 형식 검증(`field` 있음) | 프로세서(`field` 없음) | 표시할 곳     |
| ---------------------- | ----------------------- | ---------------------- | ------------- |
| 이용약관 동의          | `MEMBER_115`            | `MEMBER_010`           | 약관 체크박스 |
| 개인정보 처리방침 동의 | `MEMBER_116`            | `MEMBER_010`           | 방침 체크박스 |
| 만 14세 이상 확인      | `MEMBER_117`            | `MEMBER_011`           | 연령 체크박스 |

`MEMBER_1xx` 는 web 경계의 `@AssertTrue` 라 `fieldErrors[].field` 로 항목이 함께 온다 —
기존 필드 매핑(`field-errors.ts`)을 그대로 탄다. `MEMBER_010` / `MEMBER_011` 은 프로세서가
던지는 도메인 예외라 `field` 가 없어 **코드로 어느 체크박스인지 판정한다**
(`src/lib/auth/signup-consent.ts` 의 `consentCodeTargets`).

`MEMBER_010` 은 약관과 방침을 구분하지 않는다(서버가 하나로 던진다). 그래서 **아직 켜지지 않은
쪽에만** 문구를 붙인다 — 이미 켠 체크박스에 "동의해야 합니다" 가 붙으면 "다 했는데 왜 안 되지"
가 된다.

### 배치 — 체크박스는 3단계 안이 아니라 **화면 단위**다

이슈 초안은 `ProfileStep`(3단계) 안에 두라고 적었지만 **그 자리로는 소셜 경로를 덮지 못한다.**

- 같은 화면의 소셜 버튼은 **1단계부터 보인다.** 3단계 폼 안에 동의를 가두면, 소셜로 가입하려는
  사용자는 동의할 방법이 없다.
- 소셜은 **`/authorize` 를 부르기 전에만** 동의를 실을 수 있다. OAuth 인가코드가 1회용이라
  콜백에서 거부하면 되돌릴 수 없다 — 제공자 인가 화면부터 통째로 다시 밟아야 한다.
- 두 입구가 각자 체크박스를 들면 같은 화면에 같은 질문이 두 벌 서고, 3단계에서 둘이 동시에 보인다.

그래서 동의 상태는 `SignupScreen` 이 소유하고, 체크박스는 **제목 바로 아래·단계 폼 위**에 한 벌만
선다. 3단계에서는 그 자리가 곧 제출 버튼 위이기도 하다.

> **이 판단의 부작용이 #707 로 해소됐다.** "동의를 실을 수 있는 유일한 입구가 이 화면" 이라는
> 근거는 맞았지만, 그 결론으로 **콜백에서 튕겨 돌아온 사용자까지 이 화면으로 보냈다.** 그 사용자는
> 쓸 일 없는 이메일 입력(`필수` 표시가 붙은)과 `3단계 중 1단계` 와 **들어오지 않은 제공자 버튼**을
> 함께 보았다. 아래 "D11" 이 그 목적지를 갈라낸다. **이 화면의 배치는 바뀌지 않는다.**

### 전체 동의 (이슈 #1083)

필수 3종 위에 **"모두 동의해요"** 하나를 두고 선으로 가른다.

- **전체 동의는 저장하지 않는다.** 체크 상태는 `isSignupConsentComplete(consent)` 에서 파생한다.
  그래서 양방향이 저절로 맞는다 — 하나라도 끄면 전체도 풀리고, 셋을 하나씩 다 켜면 전체도
  켜진다. 코드로 남는 것은 "전체를 눌러 셋을 한꺼번에 바꾸는" 한 방향뿐이다
  (`setAllSignupConsent`). 따로 들었다면 두 방향을 맞추는 코드가 각각 필요하고 하나라도
  빠지면 화면이 거짓말을 한다.
- **"일부만 켜짐"(indeterminate)을 두지 않는다.** 이 이슈가 정한 규칙이 "하나라도 풀리면 전체도
  풀림" 이라 전체는 켜짐/꺼짐 둘뿐이다. 네이티브 `indeterminate` 는 HTML 속성이 아니라 DOM
  프로퍼티라 effect 없이는 켤 수 없고, 각 항목의 상태는 바로 아래에서 따로 읽힌다.
- **세 항목이 전부 필수라 "전체" 가 곧 "필수 전체" 다.** 선택 동의(예: 마케팅 수신)가 생기면
  전체 동의가 그것까지 켜야 하는지 · 소셜 버튼 게이트는 필수만 보는지를 다시 정해야 한다 —
  `setAllSignupConsent` 는 `SIGNUP_CONSENT_KEYS` 전부를 켠다.
- **두 입구가 같이 쓴다.** `/signup` 과 `/signup/social/{provider}` 둘 다 `SignupConsentFields`
  를 재사용하므로 전체 동의도 둘 다에 선다. 소유자(`SignupScreen` ·
  `SocialSignupConsentScreen`)가 각자 `setAllSignupConsent` 로 상태를 바꾼다.
- 전체 동의로 값을 바꾸면 **세 항목의 동의 오류를 함께 지운다** (`clearConsentErrors`). 한 항목을
  바꾸면 그 항목만 지우는 기존 규칙을 세 항목으로 넓힌 것이다.
- **행 사이를 띄우지 않는다** (행 간격 정리). 행마다 44 높이(체크박스 라벨 · "전문 보기")가
  이미 누르는 자리를 벌려 두는데, 그 위에 gap 8 을 더 얹으면(행 간 52) 세 줄이 한 목록이 아니라
  따로 떨어진 질문처럼 읽혔다. 이제 행 간 44 이고, 전체 동의와의 구분은 선 하나가 맡는다.

### 소셜 버튼

- **가입 화면**: 동의 3종이 다 켜질 때까지 `disabled` 이고, 왜 못 누르는지 글자로 말한다
  (`messages.auth.socialConsentRequired`). 켜지면 `/authorize` 쿼리에 실어 보낸다.
- **로그인 화면**: 기존 회원용이라 동의를 묻지 않는다(`consent` prop 을 넘기지 않는다).
  신규 사용자가 여기로 들어와 최초 연동이 되면 콜백이 `MEMBER_010` / `MEMBER_011` 로 거부하고,
  `OAuthCallbackStatus` 가 **`/signup/social/{provider}` 로** "가입 동의하기" 를 준다 (#707;
  #688 때는 `/signup` 이었다). 다른 오류와 달리 목적지가 `/login` 이 아닌 이유는, 로그인 화면으로
  돌아가면 같은 실패를 그대로 반복해서다.

### 동의한 문서의 판이 함께 저장된다

백엔드는 동의 시각과 함께 **그 시점의 문서 버전**을 남기고, 그 값은 `legal.terms-version` /
`legal.privacy-version` 설정으로 우리 상수(`src/lib/legal/*.ts` 의 `version`)를 따라 적는다.
**문서를 개정할 때 두 값을 같은 배포로 함께 올린다.** 어긋나면 화면은 새 판을 보여주고 이력에는
옛 판이 남는다.

## D11. 가입 동의의 두 입구 (이슈 #707)

D10 은 동의 체크박스를 회원가입 화면에 두면서 **소셜 콜백의 목적지까지 그 화면으로 정했다.**
동의를 실을 수 있는 자리가 거기뿐이었기 때문인데, 그 결정 하나에 **성질이 다른 두 사용자**가
묶여 있었다. 이제 갈랐다 — **화면이 둘이고, 동의 계약은 하나다.**

| 입구                                              | 화면                        | 보이는 것                                     | 왜                                                                   |
| ------------------------------------------------- | --------------------------- | --------------------------------------------- | -------------------------------------------------------------------- |
| 처음부터 회원가입 화면에 온 사용자                | `/signup`                   | 3단계 이메일 폼 + 동의 3종 + **소셜 버튼 둘** | 아직 수단을 고르지 않았다. 소셜 버튼 둘은 "더 짧은 길" 안내다 (D8-3) |
| 콜백에서 `MEMBER_010`/`MEMBER_011` 로 튕긴 사용자 | `/signup/social/{provider}` | 동의 3종 + **들어온 제공자 버튼 하나**        | 수단을 이미 골랐고 제공자 동의까지 마쳤다. 남은 것은 우리 동의뿐이다 |

**`/signup` 은 이 이슈로 바뀌지 않는다.** 바뀐 것은 콜백의 목적지 계산
(`oauth-callback-view.tsx` 의 `signupConsentPath`)뿐이다.

### 왜 제공자 버튼을 하나로 좁히는가

이메일 폼과 단계 표시는 **쓸모없을 뿐**이지만, **들어오지 않은 제공자 버튼은 해롭다.** 카카오로
시작한 사용자가 동의를 켜고 바로 아래 네이버를 누르면 우리는 그것을 **다른 이메일의 다른 가입**
으로 처리한다 — 사용자는 "방금 카카오로 하던 것" 을 잇는다고 생각한다. 좁히는 수단은
`SocialLoginButtons` 의 `providers` prop 이고, 기본값이 전체라 `/login` · `/signup` 은 그대로다.

| `SocialSignupConsentPage`   | `app/(auth)/signup/social/[provider]/page.tsx`       | 서버 컴포넌트. 제공자 검증 → 세션 → 화면                         |
| `SocialSignupConsentScreen` | `src/features/auth/social-signup-consent-screen.tsx` | `'use client'`. **동의 상태 소유** (`SignupScreen` 과 같은 역할) |
| `SignupConsentFields`       | `src/features/auth/signup-consent-fields.tsx`        | **그대로 재사용.** 체크박스를 새로 만들지 않는다                 |
| `SocialLoginButtons`        | `src/features/auth/social-login-buttons.tsx`         | `providers={[provider]}` 로 하나만 그린다                        |

### 제공자 세그먼트는 404 로 거절한다

경로 세그먼트는 사용자가 손으로 바꿀 수 있어 `isOAuthProvider` 로 거르고, 통과하지 못하면
`notFound()` 다. **소셜 콜백(`oauth/[provider]/callback`)이 같은 상황에서 "잘못된 접근이에요" 를
그리는 것과 다르다** — 그 자리는 제공자가 돌려보내는 착지점이라 제공자 설정이 어긋난 경우까지
다음 행동을 줘야 한다. 이 화면은 우리 링크로만 들어오므로 그런 사정이 없고, 200 으로 답하면
크롤러가 없는 페이지를 정상으로 읽고 모니터링도 실패를 세지 못한다.

**검사는 `readSession()` 보다 먼저 온다.** 뒤로 미루면 세션이 있는 사용자에게 404 대신
목적지 리다이렉트가 나가 같은 주소가 세션 유무로 다른 상태를 답한다.

**콜백 쪽은 404 로 안내하지 않는다.** 제공자를 특정하지 못하면 곧바로 404 인 주소를 주는 대신
`/signup` 으로 떨어진다 — 그 화면에도 동의 블록이 있으므로 길이 길 뿐 막다른 곳은 아니다.

### 화면은 남은 일 하나를 말한다 (#1083 에서 단순화)

인가코드는 1회용이고 `state` 는 서버가 조회와 동시에 지운다(Redis `GETDEL`). 방금 받은 것으로
재시도할 방법이 없어 `/authorize` 를 처음부터 다시 부른다. **다만 제공자 쪽 동의는 이미 끝나
있어 동의 화면 없이 곧장 돌아온다.**

#707 은 이 이유를 화면에 그대로 적었다("…동의는 이미 마쳤어요. 보안상 방금 받은 인증을 다시 쓸
수 없어…"). 두 줄이 넘고 기술 용어가 섞여, #1083 에서 **남은 일 하나만** 말하게 바꿨다:

> 아래 항목에 동의하고 카카오 로그인을 한 번 더 누르면 가입이 끝나요.

- 사용자에게 필요한 것은 이유가 아니라 **무엇을 누르면 끝나는지**다. "또 처음부터" 로 읽히는
  것은 "한 번 더 누르면 끝나요" 가 막는다 — 남은 일이 버튼 하나라는 말이다.
- **버튼 문구를 그대로 부른다** (`socialLoginLabel` = `카카오 로그인`). 안내와 버튼 글자가
  같아야 "그 버튼" 을 찾는다. 테스트가 둘의 포함 관계를 잠근다.
- 이유(인가코드 1회용)는 코드 주석과 이 절에만 남긴다
  (`messages.auth.socialSignupConsentNotice`).

### 라벨은 `{제공자} 로그인` 그대로다

이슈는 `카카오로 계속하기` 도 허용했지만 **쓰지 않았다.** 소셜콜백-세부명세 D8-1 이 각 사
브랜드 가이드를 근거로 `…로 계속하기` 를 버리고 `… 로그인` 으로 고정했고, 그 근거(마크를 단
버튼의 문구는 가이드가 정한다)는 이 화면에서도 그대로다. 이슈가 요구한 것은 **선택지가 하나**인
것이고 그것은 버튼 수로 이미 달성된다.
