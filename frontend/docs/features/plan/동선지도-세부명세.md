## 이 문서의 범위

**새 화면이 아니다.** 이미 있는 두 화면에 카드 하나씩을 더한다. 라우트·API·상태 머신은 그대로다.

| 화면                     | 더하는 것                       | 도로 경로 |
| ------------------------ | ------------------------------- | --------- |
| `/plans/[planId]`        | 일자별 동선 카드                | **있다**  |
| `/ai-plans/jobs/[jobId]` | 초안 동선 카드                  | 없다      |

## D0. 화면 정의

- **경로**: `/plans/[planId]` · `/ai-plans/jobs/[jobId]` — route group `(main)`. **변경 없다**
- **인증**: 필요. `proxy.ts` `PROTECTED_PATHS` 에 `'/plans'` · `'/ai-plans'` 가 이미 있다. **추가 등록 없음**
- **적용 상태**
  - 일정 상세 — 상세 조회 성공 시. 상태(`DRAFT`/`CONFIRMED`)로 갈리지 않는다
  - AI 초안 — `COMPLETED` + `planDraft !== null` 일 때의 미리보기뿐. 진행·실패·조회 실패 화면은 손대지 않는다.
    **조건 유실(`snapshot === null`) 분기에도 적용한다** — 그 분기도 같은 `AiPlanDraftPreview` 를 그린다
- **진입/이탈 경로**: 변경 없다
- **선택된 일자**: `?day=` (기본 `1`). 필터·탭은 URL `searchParams` 에 둔다는 저장소 규칙 그대로다

## D1. 레이아웃

### D1-1. 일정 상세

**우측 일자 열의 맨 위**다. `rail-layout-split` 을 건드리지 않는다.

```text
데스크톱 (1024+)                        모바일 (390)
┌─────────┬────────────────────┐        ┌──────────────┐
│ 개요     │ ★ 동선 카드         │        │ 개요          │
│ 브리핑   │ ────────────────── │        │ ★ 동선 카드   │
│ 준비물   │ 1일차 카드          │        │ 1일차 카드    │
│         │ 2일차 카드          │        │ 2일차 카드    │
└─────────┴────────────────────┘        └──────────────┘
  rail-split-top    rail-split-main
```

**좌측 레일이 아니다.** 레일은 의도적으로 고정(sticky)이 아니라(`plan-detail-section.tsx` 의
레일 주석) 일자 카드를 읽으며 내려가면 화면에서 사라진다. 지도와 목록은 서로를 가리키는
한 쌍이라 **같은 열**에 있어야 대응이 유지된다.

**카드 내부 순서**

```text
동선                                    ← Surface title
[1일차] [2일차] [3일차]                 ← 일자 칩. 선택은 Chip 의 bg-band
┌────────────────────────────────┐
│           지도                  │     ← h-56 (224) · md:h-64 (256)
└────────────────────────────────┘
1일차 5곳 · 직선 합계 31km              ← 요약. tabular-nums
2곳은 위치를 알 수 없어 지도에 없어요    ← 결손이 있을 때만 (D5)
```

**높이를 종횡비가 아니라 값으로 고정한다.** `PlaceMiniMap` 과 같은 판단이다 — 종횡비로
두면 데스크톱 우측 열(700+)에서 지도가 자라 일자 카드를 화면 밖으로 밀어낸다. 다만
`PlaceMiniMap`(h-44/h-52)보다 한 단계 크다: 저쪽은 핀 하나의 "여기가 어디쯤" 이고
여기는 **여러 점과 그 사이의 모양**을 읽어야 한다.

### D1-2. AI 초안

단일 컬럼 스택이다. **개요 카드 다음, 일자 카드 앞.**

```text
초안 개요 (제목 · AI 배지 · 요약 · reasons)
★ 이 초안의 동선
1일차 카드 (항목별 빼기 토글)
2일차 카드
이 일정 담기
```

카드 내부는 D1-1 과 같되 제목이 `이 초안의 동선` 이고 **도로 층이 없다**(D3-4).

### D1-3. 공통

- 모바일·데스크톱 모두 카드 구조가 같다. **브레이크포인트 분기는 지도 높이뿐이다**
- 일자 칩은 `Chip` 을 그대로 쓴다. 선택 표시는 `bg-band` — `ViewToggle` 의 반전 톤이 아니다
  (`emergency-type-segment.tsx` 가 같은 판단을 했다)
- 카드 사이 간격은 `SurfaceStack` 이 낸다. **자기 여백을 붙이지 않는다**

### D2-1. `lib/map/route.ts` — 직선 층 (레인 A)

**항목 타입에 의존하지 않는다.** `초안거리-세부명세.md` D2-2 가 `item-distance` 에 내린
결정과 같은 이유다 — 일정 상세(`PlanItemDetail`)와 초안(`AiPlanScheduleItem`)은
`itemType` 의 모양도 좌표를 얻는 경로도 다르지만 **규칙은 같다.**

```ts
export type RouteStop = {
  /** planItemId 또는 placeId. 목록 행과 지도를 잇는 열쇠다 */
  id: string
  /** 화면 순번. **1부터** — sequence 가 아니라 좌표가 있는 항목만 센 번호다 */
  order: number
  title: string
  coord: LatLng
}

export type RouteLeg = {
  fromId: string
  toId: string
  /** 직선거리(m) */
  straightMeters: number
  /** 어제 잔 숙소에서 들어오는 구간인가. 점선으로 그린다 */
  fromLodging: boolean
}

export type RouteModel = {
  stops: RouteStop[]
  legs: RouteLeg[]
  /**
   * 좌표가 없어 지도에서 빠진 항목 수. **`MOVE` 는 세지 않는다** — 그 항목은 원래
   * 가리킬 자리가 없고, 세면 "위치를 알 수 없는 곳" 이 매번 1 이상이 된다
   */
  omittedCount: number
  /** 직선 합계(m). 요약 줄이 쓴다 */
  totalStraightMeters: number
}

export function toRouteModel(input: {
  items: readonly { id: string; itemTypeCode: string; title: string; coord: LatLng | null }[]
  /** 앞선 날의 마지막 숙소. 없으면 null */
  lodgingBasis: { id: string; title: string; coord: LatLng | null } | null
}): RouteModel
```

> **`order` 를 `sequence` 로 쓰지 않는다.** 좌표 없는 항목을 건너뛰고 나면 핀 번호가
> `1, 2, 4` 처럼 튄다. 사용자는 "3번이 어디 갔나" 를 묻게 되고, 그 답은 지도가 아니라
> 결손 고지 줄(D5)이 한다. 핀은 **보이는 것들의 순서**만 말한다.

**숙소 기준은 `lodgingBasisFor` 를 그대로 받는다.** 여기서 다시 찾지 않는다 — 그 규칙
("그날이 아니라 **앞선 날**의 마지막 숙소")은 `lib/plan/detail.ts` 가 갖고 있고, 거리 줄과
지도가 같은 기준을 써야 숫자와 그림이 같은 말을 한다.

### D2-2. `MapCanvas` 의 새 인터페이스 (레인 A)

```ts
export type MapRouteSegment = {
  path: LatLng[]
  /**
   * `default` 그날의 동선 · `dashed` 어제 숙소 진입 · `emphasis` 긴 구간.
   * **색으로 가르지 않는다** — 하나의 선색(`--brand-500`)에 굵기와 패턴만 달리한다
   */
  tone: 'default' | 'dashed' | 'emphasis'
}

route?: MapRouteSegment[] | null
```

- **`polylinesRef` 를 따로 둔다.** 처음에는 `overlaysRef` 에 함께 태우려 했는데(정리를
  한 번 더 잊을 자리를 안 만들려고), 핀 effect 가 **매번 그 배열을 통째로 비우고 다시
  그린다** — `pins` 는 조회 결과라 자주 새 배열이 된다. 선이 거기 섞이면 핀이 갱신될
  때마다 선도 지워졌다 그려져 깜빡인다. 대신 **언마운트 정리가 두 배열 모두** 진다
- **`route` 가 바뀌면 polyline 만 다시 그린다.** 핀 effect 와 합치지 않는다 — 핀은
  선택·확대 단계마다 다시 그려지지만(묶음이 풀리고 맺힌다) 선은 일자가 바뀔 때만
  바뀐다. 한 effect 에 두면 도로 층이 늦게 오는 레인 B 에서 한 프레임씩 깜빡인다
- **선색은 `getComputedStyle` 로 토큰에서 읽는다.** Polyline 은 DOM 이 아니라 캔버스라
  CSS 가 닿지 않는다. 상수로 박으면 `DESIGN.md` 팔레트가 바뀔 때 여기만 남는다.
  빈 문자열이면 폴백 상수를 쓴다(SDK 가 잘못된 색 문자열에 조용히 실패한다)

#### 순번 핀 — `MapPin.order`

`order` 를 주면 이름표 대신 **숫자 원**으로 그린다. 4~6곳이 1km 안에 몰리는 하루 동선에서
이름표를 다 펴면 서로 덮어 아무것도 못 읽는다 — `/places` 가 이름표를 쓰는 이유("어느
곳인지 눌러봐야 안다")가 여기서는 성립하지 않는다. **순서가 곧 그 핀의 신원**이고 이름은
고르면 붙는다(`.map-pin-selected`). 보조기기는 두 상태 모두에서 `1. 협재해수욕장` 을 읽는다.

원은 **묶음(`.map-cluster`)과 같은 CSS 를 쓴다.** 둘 다 "이 자리에 무엇이 있다" 를 폭 고정
원으로 말하고, 같은 지도 위에서 크기가 갈리면 그 차이가 뜻으로 읽힌다. 다른 것은 **누르면
일어나는 일**뿐이라(묶음은 확대, 순번은 선택) `aria-label` 과 핸들러가 가른다.

**순번 핀은 묶지 않는다.** 묶음은 "이 구역에 여럿" 을 한 원으로 접는 장치인데 동선에서는
그 여럿의 **순서**가 내용이다. 접는 순간 선은 남고 핀만 사라져 "선이 지나가는데 점이 없는"
지도가 된다. `clusterByGrid` 에 셀 크기 `0` 을 넘겨 끈다.

| tone       | strokeWeight | strokeStyle | strokeOpacity |
| ---------- | ------------ | ----------- | ------------- |
| `default`  | 4            | `solid`     | 0.9           |
| `dashed`   | 3            | `shortdash` | 0.7           |
| `emphasis` | 7            | `solid`     | 0.9           |

### D2-3. `lib/map/directions.ts` — 도로 층 (레인 B)

```ts
export type RoadSection = {
  path: LatLng[]
  distanceMeters: number
  durationSeconds: number
}

export type RoadPath = {
  /** 구간. **`stops.length - 1` 개다** — 카카오의 sections 가 경유지 수 + 1 개로 온다 */
  sections: RoadSection[]
  totalDistanceMeters: number
  totalDurationSeconds: number
  /** 통행료(원). 없으면 0 */
  tollWon: number
}

/** `[경도, 위도, 경도, 위도, …]` 평탄 배열을 좌표 목록으로 편다 */
export function flatVertexesToLatLng(vertexes: readonly number[]): LatLng[]
```

> **`vertexes` 는 경도가 먼저다.** `[127.109, 37.394, …]` 로 오고 순서가 `x(경도), y(위도)` 다.
> 카카오 지도 SDK 의 `LatLng(위도, 경도)` 와 **반대**라, 그대로 넣으면 선이 중국 내륙에
> 그려진다. 홀수 길이 배열은 응답이 깨진 것이므로 **`null` 을 내고 직선으로 되돌린다** —
> 마지막 좌표를 버리고 그리지 않는다.

> **`summary=true` 를 보내면 안 된다.** 이름이 "요약" 이라 전송량을 줄이려고 켜기 쉬운데,
> 그 값은 `sections` 의 `bound`·**`roads`**·`guides` 를 **응답에서 뺀다**. `roads` 가 빠지면
> `vertexes` 도 없어서 **선이 아예 그려지지 않는다.** 기본값 `false` 를 그대로 둔다 —
> 이 요청의 목적이 요약이 아니라 좌표다.

**실패 판정은 HTTP 상태가 아니라 `routes[0].result_code` 다.** `0` 이 성공이고
(`result_msg: "길찾기 성공"`), 경로를 못 찾은 경우도 200 으로 온다. `dataHeader.success` 를
봐야 하는 우리 백엔드와 같은 모양의 함정이라 **200 만 보고 넘기지 않는다.**

```text
│ coords(초안)      │        │   → RoadPath.sections    │
└──────────────────┘        └─────────────────────────┘
        │                              │
        ▼                              ▼
   RouteModel  ────────────▶  MapRouteSegment[]  ────▶  MapCanvas
```

**직선 층은 새 요청이 없다.** 일정 상세는 `GET /plans/{planId}` 가 항목마다 `place` 를
함께 주고(#86), 초안은 `use-draft-places.ts` 의 `coords` 가 이미 있다(#100). **둘 다
이번 이슈가 요청을 하나도 늘리지 않는다.**

**도로 층이 실패해도 지도는 선다.** `RoadPath` 가 `null` 이면 직선 세그먼트를 그대로
그린다 — 쿼터 소진·장애·네트워크 실패 어느 쪽이든 같다. 이것이 두 층으로 나눈 이유다.

### D3-2. 카카오 길찾기 계약과 **저장 금지**

| 항목      | 값                                                                                              |
| --------- | ----------------------------------------------------------------------------------------------- |
| 기본 호출 | `GET https://apis-navi.kakaomobility.com/v1/directions` — 경유지 **최대 5**, 일 **10,000건**    |
| 초과 호출 | `POST https://apis-navi.kakaomobility.com/v1/waypoints/directions` — 경유지 최대 30, 일 5,000건 |
| 인증      | `Authorization: KakaoAK ${REST_API_KEY}`                                                        |
| 좌표 형식 | `origin=${경도},${위도}` · `waypoints` 는 `\|` 로 연결                                          |
| 응답      | `routes[].sections[].roads[].vertexes` · `summary{distance, duration, fare{toll}, bound}`       |

**정류점이 7곳 이하면 `/v1/directions` 다** (출발 1 + 경유 5 + 도착 1). 쿼터가 두 배이고
하루 일정이 그 안에 드는 경우가 대부분이다. 넘는 일자만 `waypoints` 로 넘긴다 —
**응답 모양이 같아 `toRoadPath` 는 하나다.**

> **응답을 저장·캐싱할 수 없다.** 카카오 공식 답변(DevTalk):
>
> - "DB 및 캐시서버 등에 데이터를 저장, 재사용 구조가 아닌 **1회 호출 결과를 임시 유지 후
>   종료 시 즉시 폐기하는 구조라면 허용**됩니다"
> - "결과값 기반의 **가공 데이터의 DB저장 및 활용은 허용되지 않습니다**"
> - "**개발 환경 및 실서비스 구분 없이** 결과값의 DB저장은 허용되지 않으므로, 보관 중인
>   개발용 샘플 데이터는 확인 후 폐기해 주시기 바랍니다"
>
> 귀결 넷:
>
> 1. **Redis·DB·파일 저장 금지.** BE 후속 요청으로도 올리지 않는다 (D9)
> 2. **`unstable_cache` · Route Segment `revalidate` 금지.** 서버 캐시는 "캐시서버" 다.
>    route handler 는 `export const dynamic = 'force-dynamic'` + 응답에 `Cache-Control: no-store`
> 3. **`localStorage`·IndexedDB 금지**
> 4. **테스트 픽스처에 실제 응답을 커밋하지 않는다** (D7)

### D3-3. 도로 층의 수명 — React Query

```ts
// features/plan/queries.ts
export const routeKeys = {
  all: ['plan-route'] as const,
  day: (planId: string, day: number, signature: string) =>
    [...routeKeys.all, planId, day, signature] as const,
}
```

| 옵션                   | 값                    | 근거                                                                                 |
| ---------------------- | --------------------- | ------------------------------------------------------------------------------------ |
| `staleTime`            | `Infinity`            | 카드가 살아 있는 동안이 "그 호출의 목적" 이다. 일자 칩을 왕복해도 다시 부르지 않는다 |
| `gcTime`               | `Infinity`            | 아래 명시 폐기가 대신한다                                                            |
| `retry`                | `1`                   | 5xx·무응답만. 전역 `isRetriable` 그대로                                              |
| `refetchOnWindowFocus` | `false` (전역 기본값) | 탭 전환마다 부르면 쿼터가 샌다                                                       |

> **`gcTime: 0` 이 아니라 명시 폐기다.** `0` 이면 일자 칩을 2일차로 옮기는 순간 1일차
> 쿼리의 관찰자가 사라져 즉시 버려지고, 되돌아올 때 **또 한 건**이 나간다. 칩 왕복은 이
> 카드의 기본 동작이라 그 배수가 그대로 쿼터가 된다.
>
> 그래서 카드가 언마운트될 때 **한 번에 지운다** — "목적 종료 시 즉시 폐기" 를 코드로
> 정확히 옮긴 것이 이쪽이다.

```ts
// use-plan-road-route.ts
useEffect(() => () => queryClient.removeQueries({ queryKey: routeKeys.all }), [queryClient])
```

**키의 `signature` 는 좌표 시퀀스의 지문이다.** 순서를 바꾸거나 항목을 더하면 새 키가 되고,
메모만 고치면 같은 키다. `planId` 를 키에 남기는 것은 **다른 일정끼리 재사용하지 않기
위해서다** — 좌표만으로 키를 잡으면 "같은 코스면 재사용" 이 되어 정책이 금지한 재사용
구조에 가까워진다.

**표준값 표(`api-integration-guide.md` §7)에서 벗어나므로 근거를 코드 주석에 남긴다.**
일정 상세가 30초/10분인데 이쪽은 정책이 수명을 정한다.

### D3-4. AI 초안에 도로 층을 두지 않는다

1. **편집 중인 화면이다.** 빼기 토글마다 좌표 시퀀스가 바뀌어 새 키가 되고, 한 세션에서
   수십 건이 나간다
2. **아직 저장되지 않은 초안**이다. 정확한 주행거리보다 **모양**이 중요하고, 되돌아가는
   동선은 직선으로도 다 보인다
3. **좌표가 늦게 도착한다.** 항목당 `/places/{id}` 가 병렬로 채워지는 중이라 시퀀스가
   여러 번 흔들린다 — 그때마다 부르면 버려지는 호출이 대부분이다

## D4. 상호작용

| 동작               | 결과                                                                                                                                           |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 일자 칩 누름       | `?day=` 갱신(`replace`) → 지도가 그 일자로. **모바일은 그 일자 카드로 스크롤**(`useAnchorScroll` 재사용)                                       |
| 목록 행 누름       | 그 핀이 선택된다(`selectedId`). 핀에 이름표가 붙는다                                                                                           |
| 핀 누름            | 그 행으로 스크롤 + 행 tint(`--row-selected`)                                                                                                   |
| 지도 이동·확대     | **아무것도 재조회하지 않는다.** 이 카드는 보이는 영역으로 목록을 거르지 않는다 — `/places` 지도와 다른 점이다                                  |
| 초안에서 항목 빼기 | 그 핀과 인접 구간이 사라지고 요약 줄의 합계가 줄어든다. **거리 줄(#100)은 영향받지 않는다** (초안거리 D3-1 "빼기는 거리에 영향을 주지 않는다") |

**카메라는 `camera` prop 으로 한 번만 확정한다.** `stops` 를 담는 사각형에서 `anchor` 와
`spanMeters` 를 계산하고 `anchorRatio: 0.5` 를 준다(주인공이 여럿인 지도라 정중앙이다).
**`useMemo` 가 필수다** — 렌더 중에 새 객체를 만들면 칩을 누를 때마다 카메라가 되돌아간다
(`PlaceMiniMap`·`use-emergency-board.ts` 가 같은 함정을 같은 방법으로 막는다).

> 도로 층이 도착해도 **카메라를 다시 맞추지 않는다.** 응답의 `bound` 가 더 정확하지만,
> 사용자가 이미 지도를 만졌을 수 있고 그때 화면이 튀는 것이 정확도보다 나쁘다.

## D5. 상태별 화면

| 상태                | 지도                     | 요약 줄                                      |
| ------------------- | ------------------------ | -------------------------------------------- |
| 좌표 2곳 이상       | 핀 + 선                  | `1일차 5곳 · 직선 합계 31km`                 |
| 좌표 **1곳**        | 핀 하나. **선 없음**     | `1일차 1곳`                                  |
| 좌표 **0곳**        | **카드 전체가 없다**     | —                                            |
| 결손 있음           | 있는 것만                | 위 + `2곳은 위치를 알 수 없어 지도에 없어요` |
| 그 일자에 항목 없음 | **카드 전체가 없다**     | —                                            |
| 도로 층 로딩 중     | **직선이 그려져 있다**   | 직선 합계. 스켈레톤을 쓰지 않는다            |
| 도로 층 도착        | 선이 도로를 따라 바뀜    | `1일차 5곳 · 41km · 1시간 12분`              |
| 도로 층 실패        | 직선 그대로              | 직선 합계. **오류를 말하지 않는다**          |
| 지도 SDK 실패       | **카드 전체가 사라진다** | —                                            |

**도로 층 실패를 사용자에게 말하지 않는다.** 사용자가 요청한 것은 "동선 보기" 이고 그것은
직선으로 이미 충족됐다. 실패를 알리면 고칠 수 없는 일에 주의를 끌 뿐이다. 실패는 콘솔과
서버 로그에 남긴다.

**지도 SDK 가 실패하면 카드가 통째로 사라진다.** `PlaceMiniMap` 과 같은 판단이다 —
여기에는 되돌릴 목록 갈래가 따로 없고, 거리 줄은 원래 자리(항목 행)에 그대로 남으므로
정보가 사라지지 않는다. `/places` 지도처럼 "목록으로 보여드릴게요" 를 띄우지 않는다.

### 문구 (`lib/messages/map.ts` 에 추가)

```ts
routeHeading: '동선',
routeHeadingDraft: '이 초안의 동선',
/** `{day}` `{n}` 치환 */
```

> 언제나 직선이라 그대로 두고, 요약 줄만 층에 따라 갈린다. 같은 카드 안에서 한쪽은
> "직선 합계 31km", 다른 쪽은 "41km · 1시간 12분" 이 되는데 **그 차이가 곧 제주의 산간이다** —
> 숨기지 않는다.

## D6. 접근성

- 지도는 **보조 자료다.** 순서·거리는 항목 행이 이미 말하므로 지도에 `role="img"` 와 긴
  설명을 붙이지 않는다
- 일자 칩은 **링크**이고 `role="radio"` 로 `ChipGroup`(`radiogroup`) 안에 선다. 주소를
  바꾸는 일이라 새 탭·복사가 되어야 하고(그래서 `<button>` 이 아니다), 배타 축이라
  라디오다. 생김새는 `Chip` 과 같은 문자열을 쓴다 — 두 컨트롤이 갈리면 배운 규칙이 깨진다
- **하루짜리 일정에는 칩을 그리지 않는다.** 칩 하나만 선 축은 축이 아니다
- 핀은 `<button type="button">` + `aria-pressed`. 기존 `.map-pin` 그대로다
- 요약 줄과 결손 고지는 **지도 아래 텍스트**다. 지도 안에 그리지 않는다
- 결손 고지는 `role="status"` 를 주지 않는다 — 실시간 변화가 아니라 그 일자의 사실이다
- 선 톤 세 가지는 **색이 아니라 굵기·패턴**이라 색각과 무관하다. 긴 구간의 뜻은 요약 줄의
  숫자가 마저 말한다

## D8. 미결 사항

### D8-1. React Query 메모리 유지가 허용 범위인가 — **확인 요청 대상**

D3-3 의 구조("카드가 살아 있는 동안 유지, 언마운트 시 즉시 폐기")는 공식 답변의
"1회 호출 결과를 임시 유지 후 종료 시 즉시 폐기" 에 맞춘 것이지만, **우리의 "목적" 이
어디까지인지는 우리가 정할 수 없다.**

- **선택지 A (채택)** — 위 구조로 구현하고, **구현과 병행해 DevTalk 에 문의**한다.
  회신을 `docs/external-api-guide.md` 에 인용해 남긴다
- 선택지 B — 회신까지 착수 보류. 레인 A(직선)는 정책과 무관하므로 보류할 이유가 없어 기각
- 선택지 C — `gcTime: 0` 으로 최대한 보수적으로. 칩 왕복마다 호출이 배가 되어 기각

**문의 문안은 구조를 그대로 적는다** — "한 화면에서 1~N일차를 각각 1회씩 호출하고,
그 화면을 떠날 때 전부 폐기하며, 다른 사용자·다른 일정에 재사용하지 않습니다".

### D8-2. 전체 화면 지도 보기(`?view=map`)를 만들 것인가

담기 화면은 이미 그 문법을 쓴다(#370). 일정 상세도 같게 하면 "확인" 은 인라인 카드,
"설계" 는 전체 지도로 갈린다.

- **선택지 A (채택)** — 이번엔 인라인 카드만. 카드가 실제로 쓰이는지 본 뒤 별 이슈로 뗀다
- 선택지 B — 함께. 라우트·시트·상태가 붙어 범위가 두 배가 되고, 아직 아트보드가 없다

### D8-3. 홈에 동선 지도를 둘 것인가 — **이번 범위 밖**

홈은 일정을 **여럿 나열**하는 자리다. 카드마다 도로 층을 부르면 목록 길이만큼 배수가
붙고, 그중 대부분은 열어 보지도 않는다. 넣는다면 **직선 + 핀까지**이고(0건), 그것도
홈 화면 명세(`docs/features/home/`)가 결정할 일이다. 이 문서는 **규칙만 남긴다**:
홈에서 도로 층을 부르지 않는다.

### D8-4. 긴 이동 임계값을 시간으로 바꿀 것인가

도로 층이 `durationSeconds` 를 주므로 "하루 이동이 깁니다" 를 거리가 아니라 시간으로
말할 수 있다. 다만 **직선 층에는 시간이 없어** 두 층의 판정이 갈린다.

- **선택지 A (채택)** — 이번엔 `LONG_TRIP_THRESHOLD_M`(30km) 그대로. 두 층이 같은 기준을
  쓰는 것이 우선이다
- 선택지 B — 도로 층이 있을 때만 시간 기준. 같은 구간이 층에 따라 다르게 강조되어 기각

## D11. 검증 계획

### 직선 층 (레인 A·C)

로컬 FE + dev 게이트웨이. 좌표는 실제 장소 데이터라 목이 필요 없다.

1. `pnpm dev --port 5174` (**포트 고정** — 아래 "눈으로 봐야 하는 것" 참고)
2. 항목이 4곳 이상인 일정으로 `/plans/{planId}` 진입 → 선과 순번 핀 확인
3. 일자 칩 왕복 → 카메라가 되돌아가지 않는지(`useMemo` 누락 증상)
4. 좌표 없는 항목을 포함한 일자 → 순번이 이어지는지 + 결손 고지
5. 390 / 1024 / 1440 에서 지도 높이와 카드 넘침

### 눈으로 봐야 하는 것 — **자동 검증이 닿지 않는 경계**

**카카오 지도 JS 키의 허용 도메인에 `localhost:5174` 만 등록돼 있다.** 다른 포트에서는
SDK 가 스크립트 실패로 떨어지고, 이 카드는 그때 **스스로 사라지도록** 설계돼 있다(D5).
그래서:

- **e2e(playwright, 5175)로는 지도를 볼 수 없다.** 그 하네스는 애초에 폴백을 전제로
  짜여 있다 (`e2e/helpers/map-fallback.ts` 머리주석)
- vitest 는 node 환경이라 마크업 문자열만 본다 — 칩·요약·결손 고지까지가 한계다
- 즉 **선이 실제로 그려지는 것은 5174 + 로그인 상태에서 사람이 봐야 한다**

자동으로 덮은 경계는 여기까지다:

| 확인한 것                                                | 방법                                             |
| -------------------------------------------------------- | ------------------------------------------------ |
| 정류점·구간·순번·결손·합계 규칙                          | `src/lib/map/route.test.ts` (20)                 |
| 칩 · 요약 문구 · 결손 고지 · 빈 갈래                     | `src/features/plan/plan-route-card.test.ts` (12) |
| `place ?? walkCourse` 좌표 선택                          | `src/lib/plan/detail.test.ts`                    |
| `MapCanvas` 회귀(핀·묶음이 그대로 그려진다)              | 5174 실측 — `.map-pin` 10 · `.map-cluster` 1     |
| `--brand-500` 이 JS 에서 읽힌다(폴백 상수로 안 떨어진다) | 5174 콘솔 실측 — `#2e9b6b`                       |
| SDK 가 `solid`·`shortdash` 와 그 색 문자열을 받는다      | 5174 에서 `Polyline` 직접 생성 실측              |

### 도로 층 (레인 B)

1. `.env.local` 에 `KAKAO_REST_API_KEY` (**`NEXT_PUBLIC_` 없이**)
2. 네트워크 탭에서 `/api/directions` 응답 헤더에 `Cache-Control: no-store` 확인
3. 같은 화면에서 일자 칩을 5회 왕복 → **호출이 일자 수만큼만** 나가는지
4. 다른 화면으로 나갔다 돌아오기 → **다시 호출되는지**(폐기가 동작하는지)
5. 키를 일부러 틀리게 → 직선으로 되돌아가고 **화면에 오류가 없는지**
6. 7곳 초과 일자 → `waypoints` 갈래로 넘어가는지

> **카카오 개발자 콘솔에서 REST API 키에 호출 허용 IP 를 등록한다.** 로컬 개발 IP 와
> 배포 환경 IP 가 다르므로 둘 다 필요하다. 등록하지 않으면 401 이 나고, 그 증상은
> "키가 틀렸다" 와 구별되지 않는다.
