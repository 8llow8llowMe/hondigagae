## 이 문서의 범위

`GET /plans/{planId}/briefing?date=` 하나를 붙인다. **새 판정이 아니라 기존 판정의 합본**이고
서버가 LLM 을 부르지 않는다(컨트롤러 설명). 화면도 문장을 지어내지 않는다.

**범위 밖 (명시)**

- **준비물을 브리핑에 합치기.** 서버가 일부러 뺐다 — `PlanBriefingResponse` javadoc 이
  _"준비물은 담지 않는다. ai-service 의 준비물 API 가 따로 있고, 이 응답은 LLM 을 부르지
  않는 결정적 조합만 묶는다"_ 고 적는다. 준비물은 일정 상세 좌측 레일에 이미 있다(#586).
- **LLM 문장 생성.** 요약도 조언도 만들지 않는다.
- **일자 넘기기(다른 일차 브리핑 보기).** 화면이 날짜를 하나 고른다 (D3-1) — 선택 UI 는
  D8-2 미결.
- **곡선 문장(`describeGoldenWindow`)**. 홈의 `골든타임-문구-세부명세.md` 가 정본이고 이
  화면은 그 문장을 쓰지 않는다 (D2 · D8-3).

## D0. 화면 정의

- **경로**: `/plans/[planId]/briefing` — route group `(main)`
- **인증**: **필요**. `proxy.ts` `PROTECTED_PATHS` 의 `'/plans'` 가 `startsWith('/plans/')`
  로 이미 덮는다. **추가 등록이 없다** (`/plans/[planId]/emergency` 와 같다).
- **진입 경로**: 일정 상세(`/plans/[planId]`) 좌측 레일의 배너 **하나뿐**. 노출 조건은 D3-1.
- **이탈 경로**: 일정 상세(뒤로) · 없는 일정이면 `not-found`

**왜 별도 라우트인가.** 일정 상세 안에 펼치면 상세가 그만큼 밀린다 — 응급 브리핑(#125)이
같은 이유로 별도 라우트다. 브리핑은 하루치 합본이라 카드 네 장이고, 상세의 좌측 레일은
이미 개요 · 준비물 · 후기 · 배너로 차 있다(`일정상세-세부명세.md` D11-3).

## D3. 데이터 흐름

```text
서버 (page.tsx)                          클라이언트 (PlanBriefingView)
──────────────────────────────────       ─────────────────────────────────────────
readSession()
GET /plans/{planId}   ── 404 가드 ──▶
  fetchQuery + try/catch, retry:false
  404 → notFound()
today = todayDay(new Date())
target = pickBriefingDate(...)
  null → 기간 밖 안내 (요청 없음)
  date 를 prop 으로 넘긴다        ────▶ GET /plans/{planId}/briefing?date=…
                                        GET /members/me/pets           (기준 반려견 조건)
                                        GET /insights/walk-times?lat=&lng=  (곡선, 조건부)
```

| 항목                   | 내용                                                                                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| API                    | `GET /plans/{planId}` (서버, 404 가드 전용) · `GET /plans/{planId}/briefing?date=` · `GET /members/me/pets` · `GET /insights/walk-times` |
| React Query key        | `planKeys.briefing(planId, date)` (신규) · `petKeys.list()` (기존) · `insightKeys.walkTimes(lat, lng, conditionKey)` (**기존 그대로**)   |
| staleTime / retry      | 브리핑·곡선 = `INSIGHT_QUERY_OPTIONS` (5분 / 30분, error-aware retry 1). 서버 `fetchQuery` 는 `retry: false`                             |
| mutation 후 invalidate | 없다 — 읽기 전용 화면이다                                                                                                                |
| 폴링 여부              | 없다                                                                                                                                     |

- **브리핑을 서버에서 프리페치하지 않는다.** 응답 하나가 auth 특성 1 + tour 적합도 최대 5 +
  장소 요약 1 + 특보 1 + 골든타임 1 의 원격 호출을 묶는다 (`PlanBriefingProcessor` 머리주석).
  서버 렌더가 그만큼 붙잡힌다 — **응급 브리핑 페이지가 같은 이유로 자기 응답을 프리페치하지
  않는다** (`plans/[planId]/emergency/page.tsx` 머리주석). 404 가드에 필요한 것은 상세뿐이다.
- **`loading.tsx` 를 두지 않는다.** `notFound()` 가 HTTP 상태를 바꿔야 하는데 Suspense 경계가
  있으면 soft 404 가 된다 (`architecture-guide.md` §7).
- **`staleTime` 이 일정(30초)이 아니라 인사이트(5분)다.** 이 응답의 내용은 예보 판정이고
  예보 단위가 1시간이다 — 일정 본문처럼 mutation 으로 흔들리지 않는다
  (`api-integration-guide.md` §7 `장소 인사이트` 행과 같은 근거).
- **곡선은 같은 key 를 쓴다.** 좌표·조건이 같으면 홈에서 이미 받아 둔 곡선을 그대로 쓴다.

### D3-1. `date` 는 화면이 고른다 — `pickBriefingDate()`

`date` 는 **필수 쿼리 파라미터**다 (`@RequestParam LocalDate date`, 컨트롤러 285줄). 서버는
기본값을 주지 않고, 기간 밖이면 **`PLAN_002` 400** 이다 (`PlanBriefingProcessor.resolveDay`).
그래서 **부를 날짜를 화면이 정하고, 정할 수 없으면 아예 부르지 않는다.**

```ts
// src/lib/plan/briefing.ts
export type BriefingTarget =
  | { kind: 'TODAY'; date: string } // 오늘이 여행 기간 안
  | { kind: 'EVE'; date: string } // 오늘이 출발 하루 전 → 시작일을 본다

/** today 는 `todayDay(서버가 만든 Date)` 가 준 `YYYY-MM-DD` 다 */
export function pickBriefingDate(
  startDate: string,
  endDate: string,
  today: string,
): BriefingTarget | null
```

| #   | 조건                                                   | 결과                               |
| --- | ------------------------------------------------------ | ---------------------------------- |
| 1   | `startDate` · `endDate` · `today` 중 못 읽는 값이 있다 | `null`                             |
| 2   | `endDate < startDate` (역전 데이터)                    | `null`                             |
| 3   | `startDate <= today <= endDate`                        | `{ kind: 'TODAY', date: today }`   |
| 4   | `today === startDate 의 하루 전`                       | `{ kind: 'EVE', date: startDate }` |
| 5   | 그 밖 (출발 이틀 전 이상 · 종료 후)                    | `null`                             |

- **날짜 비교는 문자열로 한다.** `YYYY-MM-DD` 는 사전순 = 시간순이다. 유효성만
  `parseDay()` 로 보고, "하루 전" 은 `addPlanDays(startDate, -1)` 로 만든다 (`lib/date/day.ts`
  · `lib/plan/date.ts` 의 기존 규칙 — `Date` 로 로컬 산술을 하지 않는다).
- **여행 중에는 오늘을 본다.** 3번이 4번보다 먼저다 — 여행 2일차 아침에 여는 사람에게
  1일차 브리핑을 주면 안 된다.
- **`planPhaseOf()` 를 쓰지 않는다.** 저쪽은 `D-DAY` 배지를 위해 **출발 당일을
  `upcoming`** 에 남기는 축이라 (`lib/plan/date.ts` 주석) 여기서 쓰면 당일이 "아직 안 갔다"
  쪽으로 떨어진다. 질문이 다르면 함수도 다르다.
- **상태(`DRAFT`/`CONFIRMED`/`COMPLETED`)로 가르지 않는다.** 서버가 상태를 보지 않고
  (`PlanWebFacade.getPlanBriefing` → `getOwnedPlan` 뿐), `COMPLETED` 로 가는 자동 전이도
  없다 (`screen-inventory.md` §4). 날짜 축 하나로만 판정한다.

**FE 가 고른 `date` 가 "오늘" 인지 단정하지 않는다.** 서버는 `date.equals(LocalDate.now(clock))`
로 자기 시계를 본다 (`PlanBriefingProcessor:113`). 자정 전후 요청이면 FE 의 `kind` 와 서버의
`today` 가 갈릴 수 있다 — **화면에 쓰는 것은 언제나 응답의 `today` · `date` · `day` 다.**
`kind` 는 배너 문구를 고르는 데에만 쓴다.

### D3-2. 응답 타입 (`src/types/plan.ts` 신규)

```ts
/** `GET /plans/{planId}/briefing?date=` — 하루치 합본 (#626) */
export type PlanBriefingResponse = {
  planId: string
  planTitle: string
  /** 1부터 */
  day: number
  /** `YYYY-MM-DD` */
  date: string
  /** **false 면 weatherWarning·walkTimes 가 null 이고 각 이유 문장이 채워진다** */
  today: boolean
  petIds: string[]
  /** 판정을 못 냈으면 null */
  basisPetId: string | null
  petConditionApplied: boolean
  schedule: PlanBriefingSchedule
  /** 일정 날씨 브리핑의 하루치와 **같은 타입**이다 (`PlanDayWeatherItem`) */
  weather: PlanDayWeatherItem | null
  weatherWarning: PlanBriefingWeatherWarning | null
  /** 값이 있으면 **"특보 없음" 이 아니다** */
  weatherWarningUnavailableReason: string | null
  walkTimes: PlanBriefingWalkTimes | null
  walkTimesUnavailableReason: string | null
}

export type PlanBriefingSchedule = {
  itemCount: number
  visitedCount: number
  /** 항목이 없으면 null. 항목이 하나면 first === last */

  lastItem: PlanBriefingItemSummary | null
  representativePlaceId: string | null
  representativePlaceTitle: string | null
}

export type PlanBriefingItemSummary = {
  planItemId: string
  /** 0부터 */
  sequence: number
  /**
   * **metadata 가 아니라 enum 값 문자열이다** — `PLACE`/`MEAL`/`LODGING`/`WALK`/`MOVE`.
   * 같은 응답군의 `PlanItemDetail.itemType` 은 metadata 객체라 모양이 다르다 (D9-1).
   */
  itemType: PlanItemTypeCode
  title: string
  /** `HH:mm:ss`. 시각을 지정하지 않은 항목은 null */

export type PlanBriefingWeatherWarning = {
  type: CodeNameMetadata
  level: CodeNameMetadata

  recommendationSuppressed: boolean
  /** `YYYY-MM-DDTHH:mm:ss`. 원천이 주지 않으면 null */
  effectiveAt: string | null
}

export type PlanBriefingWalkTimes = {
  /** **응답에서 좌표가 오는 유일한 자리다** (D3-3) */
  lat: number
  lng: number
  from: string
  forecastCoverage: CodeNameMetadata | null
  goldenStart: string | null
  goldenEnd: string | null
  goldenLevel: ScoreMetricMetadata | null
  /** `AVAILABLE` · `SUPPRESSED_BY_WARNING` · `ALL_HOURS_RISKY` · `NO_FORECAST` */
  goldenWindowStatus: CodeNameMetadata | null
  petConditionApplied: boolean
}
```

- `weather` 는 **기존 `PlanDayWeatherItem` 을 그대로 쓴다.** 프레젠터가 일정 날씨 브리핑과
  같은 변환(`PlanWeatherPresenter.toDayItem`)을 쓴다 (`PlanBriefingPresenter:43`) — 타입을
  새로 만들면 두 화면이 갈린다.
- `forecastCoverage` · `goldenWindowStatus` 는 서버 쪽이 `CodeNameDescriptionMetadata` 라
  **FE `CodeNameMetadata`(code·name·description) 와 같은 모양**이다.
- `null` 허용을 지운 채 타이핑하지 않는다 — metadata 필드는 프레젠터가 `code == null` 이면
  통째로 null 을 낸다 (`PlanBriefingPresenter.toMetadata`).

### D3-3. 곡선 — 좌표가 있을 때만 따로 부른다

**시간대별 곡선은 이 응답에 없다.** `PlanBriefingWalkTimesItem` javadoc: _"브리핑은 '그날
하나' 를 묶는 요약이라 곡선을 실으면 응답이 몇 배로 커진다. 곡선이 필요하면 여기 실린
좌표로 tour 를 직접 부른다."_

**좌표는 `walkTimes.lat` / `walkTimes.lng` 하나뿐이다.** `schedule` 에는 좌표가 없다 —
내부 `ScheduleInfo` 는 `representativeLat/Lng` 를 들고 있지만 **웹 DTO 로 내보내지 않고**
프레젠터가 그 값을 `walkTimes` 에만 싣는다 (`PlanBriefingPresenter:97~104`). 그래서
`walkTimes === null` 이면 **이 응답만으로는 부를 좌표가 없다.**

| 갈래                   | 곡선 조회                                       | 화면                                                    |
| ---------------------- | ----------------------------------------------- | ------------------------------------------------------- |
| `walkTimes !== null`   | **한다** — `walkTimesPath(lat, lng, condition)` | 창·상태(브리핑 응답) + 곡선(조회 응답)                  |
| `walkTimes === null`   | **안 한다**                                     | `walkTimesUnavailableReason` 문장 그대로 (D5-4)         |
| 곡선 조회가 5xx·무응답 | —                                               | 곡선 자리만 실패 + `다시 시도`. 창·상태는 그대로 남는다 |

- **일정 상세의 `item.place.lat/lng` 로 좌표를 메우지 않는다.** 가능은 하지만(`PlanItemDetail`
  에 좌표가 있다) `walkTimes` 가 null 인 날은 **`today=false` 이거나 서버가 골든타임을 못 낸
  날**이다. 그날 "오늘 기준" 곡선을 우리가 따로 그려 붙이면, 서버가 "이 날은 판정하지
  않았다" 고 말하는 옆에서 화면이 판정을 하나 만들어 내는 셈이 된다. → **D8-1**.
- **조건(`condition`)은 기준 반려견 것을 쓴다.** `basisPetId` 로 `petKeys.list()` 에서 그
  아이를 찾아 `toPetCondition(pet)` 로 만든다. 못 찾으면 `null` 을 보낸다 — 서버가 일반
  조건으로 판정하고, 그 사실은 응답 `petConditionApplied` 가 말한다.
- **조회 응답의 `goldenStart`/`goldenEnd`/`goldenWindowStatus` 는 쓰지 않는다.** 창과 상태는
  **브리핑 응답**이 정본이다 (한 질문에 한 곳이 답한다, DESIGN.md §1). 쓰는 것은 `hourly`
  하나다. 두 값이 갈리는 경우(자정 경계·조건 차이)에 화면이 두 답을 동시에 말하지 않는다.

  어제 열어 둔 탭을 새로 고치면 어제 브리핑이 아니라 오늘 브리핑이 뜬다 — D8-2.

## D5. 상태별 화면

문구는 여기서 **확정**한다. `messages.plan.briefing*` 에 넣고 구현자가 새로 짓지 않는다.

### D5-0. 화면 단위

| 상태                                | 표시                          | 문구 (확정)                                                                                                     |
| ----------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------- |
| loading                             | 카드 4장 `Skeleton`           | —                                                                                                               |
| success                             | D5-1 ~ D5-4                   | —                                                                                                               |
| 일정 없음 / 타인 일정 (404)         | `notFound()` (서버)           | 세그먼트 `not-found.tsx` — 상세와 같은 문구                                                                     |
| 기간 밖 (`pickBriefingDate` → null) | `EmptyState` (**요청 안 함**) | 제목 `아직 브리핑할 날이 아니에요` / 설명 `출발 하루 전부터 여행 마지막 날까지 볼 수 있어요` / 액션 `일정 보기` |
| 브리핑 400 (`PLAN_002`)             | `ErrorState` + `다시 시도`    | 서버 `resultMessage` 그대로 + `일정 기간이 바뀐 것 같아요. 일정을 다시 열어 주세요`                             |
| 브리핑 5xx · 무응답                 | `ErrorState` + `다시 시도`    | `브리핑을 불러오지 못했어요`                                                                                    |

- **400 에 재시도를 다는 것은 이 자리 한정이다.** 화면이 기간 안의 날짜만 보내므로
  `PLAN_002` 는 "그 사이 기간이 수정됐다" 는 뜻이고, 다시 열면 풀린다. 입력 폼이 아니라
  고칠 필드가 없어 `일정 보기` 를 함께 준다.

### D5-1. 그날 일정 (`schedule`)

| 상태                         | 문구 (확정)                                                                                  |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| 항목 있음                    | `항목 {itemCount}개 · 다녀온 곳 {visitedCount}개`                                            |
| `firstItem`                  | `처음 {HH:mm} {title}` — `startTime` 이 null 이면 시각 없이 `처음 {title}`                   |
| `lastItem`                   | `마지막 …` (같은 규칙). **`itemCount === 1` 이면 `마지막` 줄을 내지 않는다** (같은 항목이다) |
| `representativePlaceTitle`   | `이 날 기준 장소 · {title}`                                                                  |
| 항목 0개 (`itemCount === 0`) | `이 날에는 담긴 항목이 없어요` + 액션 `일정에 장소 담기` → `/plans/{planId}/days/{day}/add`  |

- **시각은 문자열 슬라이스로 만든다** (`startTime.slice(0, 5)`). `Date` 로 파싱하면 브라우저
  타임존에 따라 한 시간 밀린다 — 홈 `hourMinute` 과 같은 규칙.
- **항목 유형(`itemType`)을 화면에 적지 않는다.** 여기만 metadata 가 아니라 `PLACE` 같은
  enum 문자열로 와서, 적으려면 FE 에 한국어 매핑 테이블을 만들어야 한다 (루트 `CLAUDE.md`
  금지). 서버에 metadata 를 요청해 두고(D9-1) 그때 붙인다.
- `visitedCount` 는 0 이어도 적는다 — 출발 전에는 늘 0 이고, 그 0 이 "아직 안 다녀왔다" 는
  정보다.

### D5-2. 날씨와 적합도 (`weather`)

- `PlanDayVerdict` 를 그대로 쓴다 — `verdict={weather ?? undefined}`,
  `petConditionApplied={petConditionApplied}`, `basisPetName={basisPetNameOf(basisPetId, petIds, petNames)}`,
  `failed={false}`, `dayHasItems={schedule.itemCount > 0}`.
- `score` · `suitabilityLevel` 이 null 이면 **판정을 못 낸 것이지 낮은 것이 아니다.**
  `unavailableReason` 을 문장 그대로 쓰고 0점·회색 배지로 만들지 않는다 (상세 D3 과 같은 규칙).
- `weather === null` 은 프레젠터상 나오지 않아야 하지만(브리핑은 항상 하루치를 만든다)
  타입은 null 을 허용한다 — 그때는 카드 자리에 `날씨 판정을 받지 못했어요` 한 줄.
- 온도는 `℃` 를 붙인다 (`MetricValue` 기존 규칙).

### D5-3. 기상특보 — **이 화면의 핵심 규칙**

`weatherWarning` 과 `weatherWarningUnavailableReason` **둘을 함께 봐야** 무엇을 말할지 정해진다.
`PlanBriefingResponse` javadoc: _"특보는 필드와 이유가 둘 다 null 일 때만 '발효 중인 특보
없음' 이다 — 확인하지 못한 날은 이유가 채워진다."_

| `weatherWarning` | `...UnavailableReason` | 화면                                                                                |
| ---------------- | ---------------------- | ----------------------------------------------------------------------------------- |
| 있음             | null                   | `WeatherWarningBadge` + `level.description` + (`effectiveAt` 있으면 `{HH:mm} 발효`) |
| **null**         | **null**               | **`발효 중인 기상특보가 없어요`** — 이 조합에서만 이렇게 쓴다                       |
| null             | 문장                   | 제목 `기상특보를 확인하지 못했어요` + **서버 문장 그대로**                          |
| 있음             | 문장 (오지 않아야 함)  | 배지를 그린다. 문장은 그 아래 보조 줄                                               |

서버가 보내는 이유 문장은 **둘뿐**이다 (`PlanBriefingProcessor:69~71`):

- `기상특보는 출발 당일에만 확인합니다.` — `today=false` 일 때
- `기상특보 정보를 가져오지 못했습니다. 기상청 발표를 직접 확인해 주세요.` — 조회 실패

- **`weatherWarningUnavailableReason` 이 있을 때 "특보 없음" 으로 쓰지 않는다.** 그렇게 쓰면
  태풍경보를 조용히 지운다 (서버 javadoc 이 같은 말을 한다).
- **`weatherWarningUnavailableReasonCode === 'LOOKUP_FAILED'` 에만 `다시 시도` 를 단다**
  (#716 · D12). `NOT_TODAY` 는 재시도해도 생기지 않는 값이라 버튼을 달면 계속 누른다
  (홈 `NoForecast` 의 `DAY_ENDED` 판단과 같은 축). **문장을 파싱하지 않는다** — 판단은
  코드로 한다. **모르는 코드는 재시도 없는 쪽으로 떨어진다.**
- **위 표의 세 상태 규칙은 코드가 생긴 뒤에도 그대로다** — `weatherWarning` 과 **문장과
  코드가 모두** null 일 때만 "특보 없음" 이다. 코드만 있고 문장이 없으면 "확인하지 못함"
  제목만 세운다.
- **배지는 이 화면에 하나뿐이다** (DESIGN.md §1 "기상특보는 화면당 1회"). 배지 옆 문장은
  `level.description` 이다 — `type.description` 은 서버가 판정 근거(`WEATHER_WARNING_ACTIVE`)
  조립에 쓰므로 `PlanDayVerdict` 의 `reasons` 에 이미 들어 있다.
- `recommendationSuppressed === true` 면 한 줄 더: `경보가 발효 중이라 야외 일정은 미루는 게 좋아요`.
  **`level.code` 로 직접 판정하지 않는다** — 서버 DTO 가 그 값을 쓰라고 못박는다.
- `effectiveAt` 은 `slice(11, 16)` 으로 `HH:mm` 만 쓴다. null 이면 그 줄을 빼고, "시각 미상"
  같은 말을 만들지 않는다.

### D5-4. 산책하기 좋은 시간 (`walkTimes`)

| 조건                                                | 화면                                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `walkTimes === null`                                | `walkTimesUnavailableReason` **문장 그대로** 한 줄 + 아래 사유별 꼬리 (#716 · D12)           |
| `goldenWindowStatus.code === 'AVAILABLE'` + 창 있음 | `{HH:mm} – {HH:mm}` (`title-1`, `goldenLevel` 톤) + 그 아래 `goldenWindowStatus.description` |
| 그 밖의 모든 코드 (모르는 코드 포함)                | `goldenWindowStatus.name` (`body-1` 강조) + `goldenWindowStatus.description`                 |
| `goldenWindowStatus === null` (옛 서버)             | 창이 있으면 창만, 없으면 `추천할 산책 구간이 없어요`                                         |
| 곡선 조회 성공                                      | `WalkTimesCurve` — `hourly` + 브리핑의 `goldenStart`/`goldenEnd`                             |
| 곡선 조회 실패 (5xx·무응답)                         | `시간대별 예보를 불러오지 못했어요` + `다시 시도`                                            |
| 곡선 `hourly` 가 빈 배열                            | 곡선 자리를 **비운다**. 위 상태 문구가 이미 이유를 말한다                                    |

- **`walkTimes === null` 의 꼬리는 `walkTimesUnavailableReasonCode` 가 가른다** (#716 · D12).
  `LOOKUP_FAILED` → `다시 시도`(브리핑 응답 재조회) + 좌표가 있으면 곡선. `NO_PLACE_ITEM`
  → 재시도 대신 `이 날에 장소 담기`(`/plans/{planId}/days/{day}/add`). `NOT_TODAY` ·
  `NO_PLACE_POINT` · **모르는 코드** → 문장 한 줄로 끝. 눌러도 같은 응답인 것에 버튼을
  달지 않는다.
- **곡선을 감싸는 컨테이너에 `items-start` 를 쓰지 않는다.** 자식이 max-content 로 서서
  곡선의 `min-w-0`·`overflow-x-auto` 가 무력해지고, 375 에서 문서 전체가 가로로 구른다
  (`DESIGN.md` — _"375px 에서 가로 스크롤이 생기면 버그다"_). 같은 곡선을 쓰는 홈 카드에는
  `items-start` 가 없다.
- **판정이 없는 날의 곡선에는 창을 넘기지 않는다.** `goldenStart`/`goldenEnd` 는 `null` 로
  둔다 — 창·상태의 정본은 브리핑 응답이고 그 응답이 판정을 내지 못한 날이다 (D3-3).
- **상태 문구를 FE 가 짓지 않는다.** `goldenWindowStatus` 는 `{code, name, description}`
  metadata 이고 서버가 한국어를 채워 보낸다 — 예: `특보로 추천 보류` / _"기상특보 경보가
  발효 중이라 시간대가 좋아도 추천하지 않습니다. 시간대 곡선은 근거로 그대로 제공됩니다."_
  (tour-service `GoldenWindowStatus.java:31~36` 실측). **한국어 매핑 테이블을 만들지 않는다.**
  홈은 `#270` 당시 자기 문구를 갖고 있는데, 이 화면은 서버 metadata 를 그대로 쓴다.
- **`goldenStart` 가 null 이라는 이유만으로 "남은 시간이 모두 위험" 이라고 쓰지 않는다.**
  그 문장은 `ALL_HOURS_RISKY` 일 때만 참이다 (서버 DTO 가 굵게 못박는다).
- `forecastCoverage.code === 'UNAVAILABLE'` 이면 **곡선 조회 `다시 시도`** 를 함께 낸다 —
  이것만 일시 장애다. `DAY_ENDED` 는 정상이라 버튼을 달지 않는다 (홈과 같은 규칙).
- 기준 줄(캡션): `{representativePlaceTitle} 기준 · 노면(아스팔트) 온도는 추정치예요`.
  대표 장소명이 없으면 앞을 빼고 뒤만 쓴다. **"현재 위치 기준" 이라고 쓰지 않는다** — 이
  판정은 그날 대표 장소 좌표 기준이다.
- `petConditionApplied === false` 면 `반려견 특성을 불러오지 못해 일반 조건으로 판정했어요`.
  응답의 두 자리(최상위 · `walkTimes`) 중 **최상위 값 하나만** 화면 아래 한 줄로 말한다 —
  같은 사실을 카드마다 반복하지 않는다.

### D5-5. 부분 데이터가 없을 때

- `basisPetId === null` → 기준 반려견 줄을 **숨긴다.** `petIds.length < 2` 일 때도 숨긴다
  (`basisPetNameOf` 가 이미 그 판정을 갖는다).
- `representativePlaceId === null` → 기준 장소 줄과 링크를 숨긴다.
- `firstItem === null` → 항목 0개 갈래로 간다.
- **없는 값을 "없음"/"미정" 으로 채우지 않는다.** 단, 특보만은 D5-3 표의 `null + null`
  조합에서 명시적으로 "없어요" 라고 말한다 — 그것이 서버가 보장하는 사실이기 때문이다.

## D6. 접근성

- 페이지 머리 `h1` = `여행 브리핑`. 카드 제목은 `h2` 넷 (`그날 일정` · `날씨와 적합도` ·
  `기상특보` · `산책하기 좋은 시간`). **`h1` 은 로딩·오류·기간 밖 갈래에도 있다** — 없으면
  문서 최상위 제목이 상태 문구의 `h2` 가 된다 (ai-plan 작업 상태 #451 과 같은 판단).
- `Surface aria-label` 은 각 카드 제목과 같은 문자열을 쓴다.
- `BackLink` 는 `variant="titleRow"`, 라벨 `일정으로 돌아가기` (`messages.plan.briefingBack`).
- 특보 배지는 **색만으로 말하지 않는다** — `{type.name} {level.name}` 이 배지 안에 낱말로 있다.
- 곡선 셀의 `sr-only` 라벨(기온 · 추정 노면 온도 · 등급 이름)은 이동해도 그대로 유지된다.
- `다시 시도` 버튼은 높이 44px (`h-11`).
- 시각 범위 `–` 는 en dash 고, 스크린리더가 "에서" 로 읽지 못하므로 `sr-only` 로
  `{from}부터 {to}까지` 를 함께 둔다.

## D11. 전날 갈래 (#733)

브리핑은 두 날에 열린다 — 출발 전날(`EVE`)과 여행 기간 중(`TODAY`). 그런데 **전날에 열면
카드 넷 중 둘이 안내 한 줄만 담았다.** 서버가 특보·골든타임을 당일에만 채우기 때문이다
(`today === false` 면 두 필드가 null 이고 이유 문장이 채워진다). 별도 라우트까지 만들어
들어온 대가가 빈 카드 둘이었다.

### D11-1. 값이 없는 카드를 그리지 않는다

전날에는 특보·골든타임 카드를 렌더하지 않고, 카드 스택 아래 **각주 한 줄**로 내린다 —
`기상특보와 산책 골든타임은 내일 아침에 열려요.` `TODAY` 는 카드 넷 그대로다.

- **각주는 카드가 아니다** (DESIGN.md §0 의 카드 판정 3문 — 자기 제목이 없다). `Surface`
  로 감싸면 접은 카드 둘이 카드 하나로 바뀔 뿐이다.
- **문구는 예고형이다.** `확인하지 못했어요`(실패)가 아니라 `열려요`(대기)다 — 실제 상태는
  장애가 아니라 "아직 때가 아님" 이고, 실패 톤으로 말하면 고칠 수 없는 것을 고치려 든다.
  굵기도 본문(400)이다.
- 같은 이유로 `TODAY` 의 `기상특보를 확인하지 못했어요` 줄도 `body-1`(16/600)에서
  `body-2`(14/600)로 내렸다. 제목 크기·굵기에 보조 텍스트 색을 얹어 위계가 어긋나 있었다.

### D11-2. 갈래는 `kind` 하나다 — 다만 값이 비었을 때만 접는다

판정은 `pickBriefingDate` 가 이미 돌려주는 `kind` 를 쓴다(새 판정 축을 만들지 않는다).
**그러나 `kind === 'EVE'` 만으로 접지 않는다.** `kind` 는 FE 시계로 고른 값이고 서버는 자기
`Clock` 을 보므로 자정 전후에 둘이 갈릴 수 있다(D3-1) — 그때 응답에 **발효 중인 태풍경보**가
실려 오는데 카드째 접으면 이 화면이 가장 크게 지키는 규칙(D5-3)을 뒤에서 깨게 된다.
그래서 `kind === 'EVE' && weatherWarning === null && walkTimes === null` 일 때만 접는다.

진입 배너(일정 상세)의 설명도 같은 축으로 갈린다 — 전날 `내일 볼 것 미리 보기`, 당일
`그날 일정 · 날씨 · 특보 · 산책 시간을 한 번에 봐요`.

### D11-3. 그날 일정은 동선으로 그린다

`처음` · `마지막` 라벨을 걷고 점·선으로 순서를 세운다. 라벨과 값이 **한 노드에 같은 굵기·
크기·색**으로 들어가 `처음 함덕 서우봉 해변` 이 한 문장처럼 읽혔다. 순서는 `ol` 과 점·선이
말하므로 글자로 다시 말하지 않는다.

- **이동 거리를 넣지 못했다.** `schedule` 에 좌표가 없어(D9-3) 거리를 낼 수 없다 — 대신
  응답이 아는 값인 **사이에 낀 항목 수**(`사이 2곳`)를 센다.
- **기준 장소는 해당 마디에 태그로 붙인다.** 별도 줄을 없애 동선 아래에 같은 장소 이름이
  한 번 더 서는 것을 막는다. 항목(`planItemId`)과 기준(**장소** id)을 잇는 열쇠가 응답에
  없어 **제목으로 맞추고**, 어느 쪽과도 맞지 않으면(가운데 항목이 기준인 날) 예전처럼 줄로
  남는다.

### D11-4. 날씨 카드에 시간축을 세우지 못했다

이슈는 하루를 아침·낮·저녁으로 갈라 시간축을 세우기를 요구했으나 **브리핑 응답에 시간대별
값이 없다.** `PlanDailyWeatherItem` 은 전부 하루치 집계고, 시각별 곡선은 `walkTimes` 안의
좌표로 tour 를 따로 불러야 나오는데 **전날 갈래는 `walkTimes` 자체가 null** 이라 부를
좌표조차 없다. 최저기온을 `아침`, 최고기온을 `낮` 으로 옮겨 적으면 구간 셋짜리 화면은
만들 수 있지만, 그 시각은 응답이 말한 적 없는 값이라 **화면이 사실을 지어내는 것**이 된다.

대신 한 것 둘.

1. **제목이 갈래를 말한다** — `내일 날씨와 적합도` / `오늘 날씨와 적합도`.
2. **하루 지표 줄** — 응답에 실려 오는데 카드가 버리고 있던 값을 세운다: 하늘상태 ·
   최고기온 · 최저기온 · 강수확률. 온도 두 값을 고르는 규칙은 `supportingTemperatures`
   (#352)가 그대로 갖는다 — 큰 숫자가 이미 최고기온인 날에 같은 값이 두 번 서지 않는다.
   판단은 `src/lib/plan/briefing-day-facts.ts` 가 소유한다.

`precipitationTypeName`(비 없는 날 서버가 `없음` 을 준다)과 풍속·습도는 넣지 않는다 —
앞은 아무 말도 하지 않는 칸이 되고, 뒤는 375px 한 줄이 표가 된다.

### D12-1. 사유 코드가 재시도를 가른다

`weatherWarningUnavailableReasonCode`(`NOT_TODAY` · `LOOKUP_FAILED`) ·
`walkTimesUnavailableReasonCode`(`NOT_TODAY` · `NO_PLACE_ITEM` · `NO_PLACE_POINT` ·
`LOOKUP_FAILED`) 가 왔다. **일시 장애는 `LOOKUP_FAILED` 하나뿐이라 재시도도 거기에만
단다** — 판정은 D5-3 · D5-4 에 적었다.

**`NO_PLACE_ITEM` 은 재시도가 아니라 할 일을 낸다.** 서버 enum 이 이 문제를 직접 적어
뒀다 — _"장소를 담지 않은 날에 '잠시 후 다시 시도' 가 서고, 정작 사용자가 할 일(장소
담기)은 화면 어디에도 드러나지 않는다."_ 그래서 이 갈래만 `이 날에 장소 담기` 로 보낸다.

**재시도가 부르는 것은 브리핑 응답이다** (`curve.onRetry` 가 아니다). `LOOKUP_FAILED` 는
브리핑이 원격 조회에 실패한 것이라 곡선만 다시 불러도 특보·골든타임은 비어 있다.

### D12-2. 좌표 폴백의 실익은 한 갈래뿐이다

`schedule.representativeLat/Lng` 가 `walkTimes` 와 무관하게 온다. 그런데 **네 사유에
대보면 곡선을 새로 부를 수 있는 날은 하나다**:

| 사유             | 좌표 | 곡선                                                  |
| ---------------- | ---- | ----------------------------------------------------- |
| `NOT_TODAY`      | 있음 | **못 부른다** — tour 곡선이 "오늘 남은 시간" 전용이다 |
| `NO_PLACE_ITEM`  | null | 대표 장소 자체가 없다                                 |
| `NO_PLACE_POINT` | null | 좌표 없음이 그 사유의 정의다                          |
| `LOOKUP_FAILED`  | 있음 | **여기 하나뿐이다**                                   |

그래서 `plan-briefing-view.tsx` 는 `walkTimes` 가 null 이면 **`LOOKUP_FAILED` 일 때만**
`schedule` 좌표로 곡선을 부른다. 아무 날에나 부르면 빈 응답을 받는 호출이 늘 뿐이다.

**"오늘 전용" 은 주석이 아니라 구조다** — `walkTimesPath`(`src/lib/api/insight.ts`)에
**`date` 파라미터가 아예 없다.** 날짜를 표현할 수단이 없는 엔드포인트라 `NOT_TODAY` 에
부르면 구조적으로 틀린 답이 온다. 이 한 줄이 "혹시 부를 수 있지 않나" 를 다시 논쟁하지
않게 한다.

**좌표는 반드시 `toLatLng()` 을 거친다.** 백엔드는 좌표를 못 구한 장소에 `0` 을 내릴 수
있고(`lib/geo/coord.ts`), `!= null` 로만 거르면 `lat=0&lng=0` 으로 **기니 만 앞바다 예보**를
곡선으로 그린다. 같은 좌표를 받는 지도는 이 관문을 통과하므로, 건너뛰면 **지도는 사라지고
곡선만 서는 모순**이 한 화면에 생긴다 — 둘이 같은 관문을 본다.

**곡선 조회 실패는 곡선 재시도로 푼다.** 이 갈래의 `다시 시도`(브리핑 재조회)로 대신할 수
없다 — 재조회가 같은 `LOOKUP_FAILED` 를 내면 좌표가 같아 `queryKey` 가 같고, 에러 상태의
곡선 쿼리는 다시 돌지 않는다. 눌러도 곡선이 영원히 오지 않는 자리가 된다.

D8-1 의 결정(_"상세의 `item.place.lat/lng` 로 메우지 않는다"_)은 **그대로다** — 여기서
쓰는 좌표는 서버가 그날 판정 기준으로 고른 그 좌표다. 화면이 판정을 만들지 않는다.

### D12-3. 지도를 그날 일정 카드에 둔다

좌표가 `schedule` 에 오면서 열린 자리다. **`PlaceMiniMap` 을 그대로 쓴다** — 같은
질문("여기가 어디쯤이냐")에 답하는 지도를 이 화면만 다시 만들면 두 화면의 축척·SDK
실패 폴백이 갈린다. 좌표나 장소 id·제목이 없으면 그 컴포넌트가 통째로 사라지므로
여기서 빈 자리를 만들지 않는다.

**동선(D11-3)을 지도로 바꾼 것이 아니다.** 항목별 좌표는 여전히 응답에 없어 선을 그을
수 없다 — 대표 장소 한 점을 찍는 것이고, 동선은 항목 수를 세는 그대로다.

**그래서 지도 위에 기준을 적는다** (`{장소명} 기준`). 항목이 여럿인 날에도 핀은 하나라,
말이 없으면 "이 날의 경로" 로 읽혀 나머지 항목이 빠진 지도가 된다. 기존 `basisLine` 은
기준 장소가 첫/마지막 마디와 제목이 같으면 사라지므로 그것에 기대지 않는다.

**좌표 확인을 `PlaceMiniMap` 에 맡기지 않는다.** 그쪽이 좌표 없을 때 `null` 을 반환하는
것은 구현 세부이지 공개 계약이 아니다. 호출부가 직접 `toLatLng()` 으로 가른다 — 그러지
않으면 (a) 감싼 요소가 남아 `gap-3` 이 두 번 먹는 여백이 생기고 (b) 그쪽이 "좌표 없음"
안내를 그리도록 바뀌는 날 이 화면에 예고 없이 빈 박스가 선다.

**카드의 주 액션을 `primary`·`md`(44px) 로 올렸다.** `PlaceMiniMap` 이 전폭 `길찾기`
(343×44)를 함께 들고 오는데 기존 `이 날 일정 보기` 는 `secondary`·`sm`(109×32) 이라,
외형 언어가 같은 채로 **보조 자료의 액션이 주 액션보다 9.7배 컸다.** 44px 은 모바일 최소
터치 영역이기도 하다.

**`NO_PLACE_ITEM` 의 `이 날에 장소 담기` 는 항목이 있는 날에만 낸다.** 항목 0개인 날은
그날 일정 카드의 `EmptyState` 가 이미 **같은 주소로** 보내고 있어, 라벨만 다른 버튼 둘이
한 화면에 선다.

### D12-4. `itemType` 유형 라벨

metadata 가 되면서 v1 이 라벨을 포기한 이유(FE 한국어 매핑 테이블이 필요하다)가 사라졌다.
**`name` 을 그대로 배지로 그린다.** 제목 줄에 이어 붙이지 않은 것은 #733 과 같은 이유다 —
`숙박 동문재래시장` 이 한 문장처럼 읽힌다. 기준 장소 태그와 같은 줄에 서는 별개 조각이다.

**두 배지에 계급을 준다.** 유형은 마디마다 **항상** 붙는 분류 라벨이고, `기준 장소` 는 그날
판정이 어느 항목에 걸렸는지 말하는 유일한 단서다. 톤·크기가 같으면 뜻이 무거운 쪽이 상시
라벨에 묻히므로 `기준 장소` 만 `strong` 으로 올린다. 유형 배지에는 `sr-only` 로 `유형` 을
앞에 둬, 스크린리더가 `… 김창열미술관 장소 기준 장소` 로 붙여 읽지 않게 한다.

### D12-5. `date` 파라미터 오류 코드

서버는 누락(`PLAN_125`)과 형식 오류(`PLAN_124`)를 가른다. mock 이 둘을 `PLAN_100` 하나로
묶고 있었다. **화면은 언제나 날짜를 보내므로 렌더에 영향이 없다** — 목이 서버와 같은
모양을 내야 계약 테스트가 진짜 계약을 지킨다.

같이 고친 드리프트 하나: 목의 `NOT_TODAY` 문장이 `…당일에만 **확인**합니다.` 였는데 서버
enum 은 `…당일에만 **제공**됩니다.` 다.
