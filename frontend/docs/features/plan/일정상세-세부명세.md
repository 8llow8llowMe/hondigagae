## D0. 화면 정의

- **경로**: `/plans/[planId]` — route group `(main)`
- **인증**: **필요**. `proxy.ts` `PROTECTED_PATHS` 에 `'/plans'` 가 이미 있고 매칭이

## D1. 레이아웃

### 모바일 (390 — 아트보드 01)

단일 칼럼. 위에서 아래로:

```text
제목 · 상태 배지 · 기간 · 총 일수
반려견 카드 (이니셜 · 이름 · 품종 · 특성)  ·  D-day
─────────── 8px 밴드 ───────────
1일차  9/12 (토)          [순서 편집] [이 날 산책]
  일자 판정 (등급 배지 · 최고 체감온도 · reasons)
  ─ 1px ─
  항목 1 · 2 · 3
  [장소 추가]
─────────── 8px 밴드 ───────────
2일차 …
  (비 예보일 때) 비가 오면 갈 만한 실내
─────────── 8px 밴드 ───────────
[일정 확정하기]   ← DRAFT. CONFIRMED 면 [여행 완료하기] + [초안으로 되돌리기]. COMPLETED 면 [확정으로 되돌리기]
위험 영역 — [일정 삭제]
```

- **8px 밴드는 일자 경계에만 쓴다.** 일자 안(판정 → 항목 → 실내 대안)은 1px 선으로 잇는다.
  밴드가 일자를 나누는 유일한 신호다 (아트보드 01 주석).
- **순번은 썸네일 좌상단 칩이다.** 순번 원 + 썸네일 + 텍스트로 3열을 만들면 390 에서 제목이
  눌린다. 2열(썸네일 · 텍스트)로 유지한다 (아트보드 01 주석).

### 데스크톱 (1024+ — 아트보드 02)

기존 `.rail-layout` 을 그대로 쓴다 — `--rail-context`(400) + 1fr, sticky 좌열, `dvh` 열 구분선.

**`.rail-layout-detail` 변형은 쓰지 않는다.** 그 변형은 장소 상세용이고 **DOM 순서와 데스크톱
배치가 다른 경우**를 위한 것이다. 일정 상세는 모바일에서도 개요·반려견이 맨 위라 **DOM 순서
그대로(aside 먼저)** 두면 두 레이아웃이 같이 성립한다.

| 열              | 내용                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------ |
| 좌 400 (sticky) | 개요(제목 · 상태 · 기간 · D-day · 반려견 · **일자별 판정 목차**) · 준비물 · 병원·약국 배너 |
| 우 가변         | 일자 섹션 (제목 `28/800`) · 확정 버튼 · 위험 영역                                          |

**고정은 `aside` 한 겹이 맡는다 — 개요 패널에 걸지 않는다.** 레일에 블록이 셋(개요 ·
준비물 · 배너)인데 첫 블록만 `lg:sticky` 였던 탓에 개요가 제자리에 못 박히고 **뒤 두 블록이
그 위로 올라와 글자가 겹쳤다** (실측 scrollY=700: 개요 top 64~519 고정, 준비물 top −181,
배너 top −18). `aside` 에 `lg:sticky lg:top-16 lg:self-start` 를 걸면 레일이 한 덩어리로
붙는다 — `lg:self-start` 가 없으면 grid stretch 로 레일 높이가 행 높이(1948px)까지 늘어나
고정이 성립하지 않는다 (DESIGN.md §7-1).

레일 콘텐츠는 개요 455 + 준비물 163 + 배너 74 = **692px** 로 가용 높이(1000 − 64 = 936px)
안에 들어온다. 블록을 더해 넘기기 시작하면 `.rail-sticky`(자기 스크롤)로 바꿔야 한다 —
고정 레일이 뷰포트보다 길면 아래쪽에 손이 닿지 않는다.

- **좌측 "일자별 판정" 세 줄은 앵커 링크다** (`#day1` …). 요약을 읽다가 그 날로 뛴다.
  각 줄 44px, 판정 색을 유지해 **목차이면서 요약**이다 (아트보드 02 주석).
- 폭 상한을 두지 않고 전폭을 쓴다 — 홈·목록·장소 상세와 같은 레일 문법이다.
- 1024 미만에서는 `.rail-layout` 이 grid 가 아니라 DOM 순서대로 쌓인다.

### 긴 한국어 실데이터로 확인할 항목

- 제목 60자(서버 상한) — 좌측 400 에서 `word-break: keep-all` 로 2~3줄

  제공돼 이 날은 아직 판단할 수 없습니다.")
- 항목 제목 100자(서버 상한)

### 공통 컴포넌트 `Modal` — **이미 있다** (#79 완료)

이름·기간·예산 수정은 **입력이 있는 다이얼로그**라 `ConfirmModal` 로는 안 된다. 다이얼로그 계약
(focus trap · Esc · 스크롤 잠금 · 포커스 복귀 · `role="dialog" aria-modal="true"`)은
[#79](https://github.com/8llow8llowMe/hondigagae/issues/79) 에서 `components/modal.tsx` 로
추출했고 `ConfirmModal` 도 그것을 쓴다. **`PlanEditModal` 은 새로 만들지 말고 이 `Modal` 을 쓴다.**

```tsx
<Modal
  open={open}
  onClose={close}
  title="일정 수정"
  size="md" // 입력 폼은 md. 확인 다이얼로그가 sm 이다
  footer={<>…취소 · 저장…</>}
>
  …필드…
</Modal>
```

- `role` 기본값이 `dialog` 다. **`alertdialog` 는 되돌릴 수 없는 확인에만** 쓴다 (그쪽은
  `ConfirmModal` 이 이미 처리한다).
- 제목·설명 id 는 `Modal` 이 `useId()` 로 만들어 `aria-labelledby`/`aria-describedby` 에 묶는다.
  **호출부가 id 를 만들지 않는다.**
- 계약 테스트는 `src/components/modal.test.ts` 다.

**`ConfirmModal` 의 공개 API 는 바꾸지 않는다** — 호출부(`pet-delete-section.tsx`)를 건드리지
않아야 이 리팩터가 A 이슈 diff 를 키우지 않는다.

## D3. 데이터 흐름

```text
서버                       클라이언트
────────────────────────   ──────────────────────────────────────────
readSession()
GET /plans/{planId}   ────▶ (프리페치 완료 상태로 hydrate)
  fetchQuery + try/catch    ├─ GET /plans/{planId}/weather   (판정)
  404 → notFound()          ├─ GET /members/me/pets          (반려견)
                            └─ GET /places/{placeId} × N     (실내 대안 보강)
today = new Date()
```

| 항목                   | 내용                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| API                    | `GET /plans/{planId}` (서버) · `/weather` · `/members/me/pets` · `/places/{placeId}` × N (클라이언트, **실내 대안만**)                         |
| React Query key        | `planKeys.detail(planId)` (기존) · `planKeys.weather(planId)` (신규) · `petKeys.list()` (기존) · **`placeKeys.detail(placeId)` (기존 재사용)** |
| staleTime / retry      | 일정·판정 = `PLAN_QUERY_OPTIONS`(30s / 10m). 서버 `fetchQuery` 는 **`retry: false`**                                                           |
| mutation 후 invalidate | `PUT`/`DELETE` 응답이 `PlanDetailResponse` 라 **`setQueryData` 로 갈아끼우고** `planKeys.list()` 만 invalidate                                 |
| 폴링 여부              | 없음                                                                                                                                           |

### 서버 — `fetchQuery` + try/catch, `loading.tsx` 없음

장소 상세(`app/(main)/places/[placeId]/page.tsx`)와 **같은 골격**이다.

- `prefetchQuery` 는 에러를 삼켜서 404(그런 일정이 없음)와 5xx(일시 장애)를 못 가른다.
  `fetchQuery` 는 던지므로 잡아서 판정한다.
- `retry: false` — 전역 기본값(5xx 2회)을 상속하면 백엔드가 죽었을 때 서버 렌더가 재시도
  백오프만큼 통째로 블로킹된다 (`architecture-guide.md` §9).
- **이 세그먼트에 `loading.tsx` 를 두지 않는다.** 경계가 있으면 응답이 먼저 스트리밍되기
  시작해 뒤따르는 `notFound()` 가 HTTP 상태를 못 바꾼다 (soft 404, `architecture-guide.md` §7).
  `app/(main)/plans/` 에도 `loading.tsx` 가 없어 그룹 분리는 필요 없다 — **생기면 그때
  `(list)` 그룹으로 옮긴다.**
- `not-found.tsx` · `error.tsx` 를 세그먼트에 둔다.
- **`today` 를 서버에서 만들어 내려보낸다.** 클라이언트가 따로 `new Date()` 를 부르면 자정
  근처에서 서버 렌더와 하이드레이션의 D-day 가 하루 갈린다 (목록과 같은 결정).

`generateMetadata` 는 두지 않는다 — 보호 화면이라 크롤러가 못 들어오고, 제목을 위해 백엔드를
한 번 더 부를 이유가 없다. `layout` 의 기본 제목을 쓴다.

### 항목의 장소 요약 — **상세 응답이 함께 준다** (`item.place`)

[#86](https://github.com/8llow8llowMe/hondigagae/issues/86) 으로 백엔드가 항목마다
`place`(`addr1` · `indoor` · `firstImage` · `lat` · `lng`)를 실어 준다.
[#115](https://github.com/8llow8llowMe/hondigagae/issues/115) 에서 **항목당
`GET /places/{placeId}` 를 걷어냈다** — 3일·6항목이면 왕복 6번이던 것이 0번이다.

**`place` 는 객체 통째로 `null` 이 될 수 있고, 세 갈래가 같은 모양이다.**

| 갈래              | 왜 null 인가                                       | 화면          |
| ----------------- | -------------------------------------------------- | ------------- |
| `WALK` · `MOVE`   | 장소를 가리키지 않는다 (`targetId` 가 walk_course) | 결손이 아니다 |
| delisted 장소     | 원천에서 사라졌다 — 항목은 우리 DB 에 남아 있다    | 제목만 남긴다 |
| tour-service 장애 | 백엔드가 요약을 비운 채 응답한다                   | 제목만 남긴다 |

- **행을 지우지 않는다.** 일정 자료는 우리 DB, 장소는 다른 서비스다 (공통명세 S8).
- **응답은 뒤의 둘을 구분하지 않는다.** 그래서 화면도 원인을 단정하지 않는다 — 편집모드의
  안내 문구가 "이 곳은 더 이상 조회되지 않아요" 까지만 말하는 이유다 (일자편집 E1).
- 결손 판정은 `hasUnresolvedPlace()` 하나다: `isPlaceTarget(item) && item.place === null`.
  **`place === null` 만으로는 판정할 수 없다** — `WALK`·`MOVE` 도 `null` 이다.

> **실내 여부는 #80 에서 못 붙였다가 [#112](https://github.com/8llow8llowMe/hondigagae/issues/112)
> 에서 붙였다.** #16 으로 장소 응답에 `indoor` 가 들어왔고 #86 이 항목 요약에도 실었다 —
> 목록 캐시를 꺼내 쓰는 우회는 끝까지 쓰지 않았다. **행 메타 줄은 `주소 · 실내` 다**
> (조립은 `lib/place/meta.ts`). `indoor` 가 `null` 이면 낱말이 빠진다 — 여기에는 실내 필터가
> 없어 "미확인" 배지를 둘 자리가 없고, `false`(야외)로 단정하지도 않는다.

### 남은 보강 — **실내 대안뿐이다**

`indoorAlternatives` 는 `{placeId, title, lat, lng, distanceMeters}` 뿐이라 주소·실내 여부를
말하려면 여전히 `GET /places/{id}` 가 필요하다 (`usePlaceEnrichment`).

- `useQueries` 로 병렬 조회한다. **key 는 `placeKeys.detail(placeId)` 재사용** — 장소 상세
  화면과 캐시를 공유해서, 상세를 보고 온 장소는 요청이 아예 나가지 않고 여기서 본 장소는
  장소 상세로 이동할 때 즉시 뜬다.
- 대상 id 는 `alternativePlaceIds(alternatives)` 가 **중복을 제거해** 만든다 — 같은 장소가
  두 일자의 대안일 수 있다.
- **실패한 장소는 제목만 남기고 행은 살린다** (항목과 같은 태도).

### 거리 — FE 하버사인, **직선거리임을 문구로 밝힌다**

서버에 거리 필드가 없다. **항목이 `place.lat`/`place.lng` 를 들고 오므로**(#86) 화면이
계산한다 — 예전에는 호출부가 보강 결과 맵을 `coordOf` 로 주입했는데, 이제 주입할 것이 없어
`toItemRows(items, lodgingBasis)` 가 항목에서 직접 꺼낸다.

- `src/lib/geo/distance.ts` 에 하버사인을 추가하고 **기존 `formatDistance()`(미터 입력)를
  그대로 쓴다** — 긴급 시설과 같은 표기여야 한다.
- 좌표가 유효하지 않은 장소가 있다 → 기존 `toLatLng()` 가 null 을 돌려준다. **한쪽이라도
  null 이면 그 행의 거리 문구를 렌더하지 않는다.** 0km 로 쓰지 않는다.
- **`직선 4.1km` 처럼 "직선" 을 붙인다.** 제주 산간·해안도로에서 직선거리와 주행거리는 크게
  다르다. 아트보드의 `4.1km` 를 그대로 쓰면 주행거리로 읽힌다.
- 기준점:
  - **숙소 기준** — **앞선 날**의 마지막 `LODGING` 항목. 있으면 그날 첫 항목에
    `숙소에서 직선 N km`
    > **구현하며 "그날" 을 뺐다.** 그날의 숙소를 기준으로 쓰면 아직 가지 않은 곳에서
    > 출발한 것이 된다 — 실렌더에서 1일차 첫 항목에 `숙소에서 직선 14.8km` 가 붙었고
    > 그 숙소는 그날 **저녁에** 체크인할 곳이었다. "그날" 을 넣어도 얻는 것이 없다:
    > 숙소가 그날 첫 항목이면 자기와의 거리(0km)라 잡음이고, 둘째 항목부터는
    > **직전 항목 규칙이 이미 그 숙소를 기준으로 잡는다.**
  - **순번 간** — 2번째 항목부터 직전 항목까지 `직선 N km 이동`
  - 숙소가 없으면 첫 항목에는 아무것도 붙이지 않는다
- **긴 이동 경고 임계값은 30km.** 넘으면 그 행만 경고 tint + `직선 41.2km 이동 — 하루 이동이
깁니다.` 별도 경고 배지를 만들지 않는다. **이게 편집 동기를 만든다** (아트보드 01 주석).

### 판정 — `GET /plans/{planId}/weather`

- `petConditionApplied === false` 면 반려견 특성 조회에 실패해 일반 조건으로 판정한 것이다 →
  판정 옆에 그 사실을 한 줄로 알린다.

### 확정에는 확인 대화상자가 없다 ([#565](https://github.com/8llow8llowMe/hondigagae/issues/565))

**되돌릴 수 있기 때문이다.** 백엔드에 상태 전이 가드가 없다 —
`PlanCommandProcessor.updatePlan` 이 `command.status()` 를 그대로 쓰므로
`{ status: 'DRAFT' }` 를 보내면 초안으로 돌아간다. 되돌릴 수 있는 동작에 확인을 붙이면
**되돌릴 수 없다는 거짓말**이 된다.

삭제는 반대다 — `담은 장소와 일자별 판정이 함께 사라져요. 되돌릴 수 없어요.` 로
`ConfirmModal` 을 세운다. **두 액션의 무게 차이는 의도된 것이다.**

- **되돌리기는 상태 배지 아래, 확정과 같은 자리다.** `초안 ↔ 확정` 은 그 배지가 말하는
  값을 바꾸는 일이라 같은 축이다. 관리 메뉴가 다루는 것은 일정의 **신원**(이름 · 예산 ·
  존재 여부)이지 상태가 아니다.
- **무게는 `variant` 로 가른다.** 확정은 그 화면의 주 행동이라 `primary`, 되돌리기는 거의
  누르지 않는 액션이라 `secondary` 다. 폭은 둘 다 전폭이다 — 자리가 같은데 폭까지 바뀌면
  버튼이 옮겨 다니는 것처럼 보인다.
- **실패 문구는 방향마다 다르다.** `확정하지 못했어요` 가 되돌리기 실패에 뜨면 사용자가
  무엇이 실패했는지 거꾸로 읽는다.
- **완료에서는 초안으로 되돌리지 않는다 (#613).** 다녀온 기록을 작성 중으로 되돌리는
  것은 다른 판단이다. 잘못 닫았으면 확정으로만 되돌린다. 초안에서는 완료를 열지 않는다.

### `PUT` 은 부분 수정이다 — 보내지 않은 필드는 유지된다

`PlanUpdateRequest` 는 `title` · `startDate` · `endDate` · `budget` · `status` 를 받고
**null 인 필드는 기존 값을 유지**한다 (`PlanCommandProcessor.updatePlan`).

- 상태 버튼은 `{ status }` 만 보낸다. 다음 값은 `planStatusActions` 가 정한다 (`lib/plan/status-action.ts`)
- 이름·기간·예산 수정은 `{ title, startDate, endDate, budget }` 를 보낸다 (#585). **날짜는 바꾸지 않았어도 둘 다 보낸다** — 생략은 "유지" 라, 한쪽만 보내면 서버가 새 시작일과 옛 종료일로 기간을 다시 계산한다
- **예산을 비우는 방법이 없다.** `budget: null` 은 "유지" 로 읽힌다. 폼에서 예산을 지우면
  `0` 으로 보낸다 — `@PositiveOrZero` 라 0 은 유효하다. 문구로 그렇게 안내한다.

### 기간 수정 — 열었다 (#585)

**예전에는 닫아 뒀다.** `PlanCommandProcessor.updatePlan` 이 기간을 줄여도 항목을 정리하지
않아, 3일 일정을 2일로 줄이면 `day: 3` 항목이 그대로 남고 상세 응답에 `totalDays` 를 넘는
항목이 섞여 왔다 — 프론트가 고아 항목을 만드는 경로를 열지 않는다는 판단이었다.

**그 근거는 더 이상 사실이 아니다.** BE 가 `99c6a41f` 로 **저장 앞**에 검사를 넣어, 줄어든
기간 밖에 항목이 남으면 `PLAN_008`(_"줄어든 여행 기간 밖에 일정 항목이 남아 있습니다. 해당
일차의 항목을 먼저 정리해 주세요."_)로 거부한다. 시작일을 미뤄 일수가 줄어드는 경우도 같이
본다 (`backend/docs/services/plan-service.md`). 고아가 생기지 않으므로 화면이 경로를 닫아 둘
이유가 없어졌다.

화면이 지는 것과 지지 않는 것:

- **거부 판정을 복제하지 않는다.** 어느 일차에 항목이 있는지는 상세 응답에 있지만, 그
  판정을 화면이 다시 세면 서버 규칙이 바뀔 때 두 곳이 갈린다. `PLAN_008` 은 검증이 아니라
  도메인 예외라 `fieldErrors` 가 없고, `apiErrorToFormErrors` 가 **폼 배너**로 올린다.
  서버 문구가 이미 할 일까지 말하므로 FE 가 자기 말투로 옮기지 않는다.
- **막힐 수 있다는 것은 미리 말한다** — `editPeriodHint`(_"기간을 줄이면 새 기간 밖에 남는
  항목을 먼저 정리해야 저장돼요."_). 기간 줄 아래 한 번만 둔다.
- **역전(`PLAN_003`)과 상한 30일(`PLAN_009`)은 화면이 먼저 본다.** 판정은
  `lib/plan/period.ts` 의 `planPeriodIssue` 하나이고 **만들기 폼도 같은 함수를 쓴다** —
  두 폼이 같은 기간에 다른 답을 내면 어느 쪽이 맞는지 알 수 없다.
- **시작일에 `max` 를, 두 날짜에 `min={today}` 를 걸지 않는다.** 기간을 통째로 뒤로 옮기는
  조작을 막게 되고, 수정에는 서버도 "오늘 이후" 제약을 두지 않는다.
- **저장 성공 시 `planKeys.weather` 를 함께 버린다.** 기간이 바뀌면 일차 수와 날짜가 통째로
  달라지는데 캐시는 옛 기간으로 만든 것이다.

다만 **다른 경로로 이미 생긴 고아 항목은 이 화면이 만날 수 있다.** `totalDays` 만큼 일자
섹션을 그리고, 범위를 벗어난 항목은 맨 아래 **"여행 기간 밖 항목"** 으로 모아 보여준다.
**숨기지 않는다** — 숨기면 사용자가 자료가 사라진 것을 모른다.

## D9. 항목 방문 체크 — '다녀옴' (이슈 [#124](https://github.com/8llow8llowMe/hondigagae/issues/124))

> **계약 확인 근거**: backend plan-service **소스 실측** — `PlanWebController.markItemVisited` ·
> `PlanItemVisitedRequest` · `PlanItemDetailItem.visited` · `PlanWebFacade.markItemVisited` ·
> `PlanCommandProcessor.markItemVisited` · `PlanErrorCode` (백엔드 PR #105).
> 게이트웨이 미기동이라 Swagger 실호출은 하지 못했다 — [#67](https://github.com/8llow8llowMe/hondigagae/issues/67) 에서 대조한다.

### D9-1. 계약

| 항목       | 값                                                                |
| ---------- | ----------------------------------------------------------------- |
| 엔드포인트 | `PUT /api/v1/plans/{planId}/items/{planItemId}/visited`           |
| 인증       | 필요 (`@PreAuthorize("isAuthenticated()")`)                       |
| 요청       | `{ "visited": boolean }` — `@NotNull`                             |
| 응답       | `Response<Void>` — **`dataBody` 가 `null`**                       |
| 조회 확장  | `PlanItemDetailItem.visited` — **primitive `boolean`, 항상 온다** |

- **해제도 같은 API 다.** `visited: false` 를 보낸다. 별도 DELETE 가 없다.
- **`clientFetchVoid` 를 써야 한다.** `clientFetch` 로 부르면 `unwrap()` 이
  `dataBody === null` 을 실패로 보고 **서버는 저장했는데 화면만 실패라고 말한다** —
  `deletePlan` 에서 브라우저 실측으로 잡았던 것과 같은 함정이다.
- **소유권을 두 번 본다.** 백엔드가 일정으로 소유권을 확인한 뒤
  `findById(planItemId).filter(found -> found.planId() == plan.id())` 로 항목이 그
  일정의 것인지 다시 본다. 남의 일정 항목을 내 `planId` 로 체크할 수 없다.

**오류**

| 코드       | 상태 | 뜻                                | 화면                                        |
| ---------- | ---- | --------------------------------- | ------------------------------------------- |
| `PLAN_001` | 404  | 없는 일정 / 남의 일정             | 재시도 없음                                 |
| `PLAN_005` | 404  | 없는 항목 / 그 일정의 항목이 아님 | 재시도 없음                                 |
| `PLAN_114` | 400  | 경로 형식 (`@PathVariable long`)  | 재시도 없음                                 |
| `PLAN_100` | 400  | `visited` 누락                    | 화면이 항상 boolean 을 보내 발생하지 않는다 |
| `PLAN_900` | 503  | 내부 연동 실패                    | 재시도                                      |

### D9-2. 일괄 교체가 체크를 초기화한다 — 이 절의 핵심

**일차 항목을 교체하면 그 날의 방문 체크가 전부 초기화된다.** 백엔드가 항목을 삭제 후
재삽입해 새 `planItemId` 를 발급하므로 `visited` 가 기본값 `false` 로 돌아간다
(컨트롤러 설명 · `PlanItemEntity.visited`).

**일괄 교체 모델과 정면으로 부딪히는 지점이라 화면이 먼저 말한다.** 순서 편집(E~)과
장소 담기(F~)가 모두 그 교체를 쓴다.

- 경고는 **일자 헤더 액션 바로 아래**에 한 줄로 둔다. 두 진입점(`순서 편집` · `장소 추가`)이
  모두 그 줄 위의 버튼에서 시작하므로 한 번만 두면 양쪽을 덮는다.
- **그 일자에 체크된 항목이 있을 때만 낸다.** 잃을 것이 없는 날에도 띄우면 경고가
  배경음이 되어 정작 잃을 날에 읽히지 않는다.
- 편집 중에는 감춘다 — 그때는 편집기가 저장 지점을 들고 있다.

부수 효과로, **교체 뒤 낡은 `planItemId` 로 체크하면 `PLAN_005` 404 다.** 재시도로
풀리지 않는 실패라 그 분기에 `다시 시도` 를 주지 않는다.

### D9-3. 배치 — 후행 44px 열

**행 전체가 `<Link>` 라 그 안에 버튼을 넣을 수 없다.** 중첩 상호작용은 시맨틱이 깨지고
키보드로 어느 쪽이 잡히는지 알 수 없다. 링크를 `flex-1` 로 두고 **토글을 링크의 형제**로
후행 열에 뺀다.

아트보드 01 이 금지한 것은 순번 원 + 썸네일 + 텍스트의 **선행** 3열(390 에서 제목이
눌린다)이다. 후행 아이콘 열은 제목이 쓰는 폭을 44px 만큼만 줄인다.

- **`aria-pressed` 토글이다.** `Checkbox` 는 라벨이 요소 옆에 붙는 폼 입력이라 행 후행
  액션에 맞지 않는다. 저장소는 이런 토글을 `aria-pressed` 로 쓴다 (`chip.tsx`).
- **이름은 상태가 아니라 누르면 일어날 일을 말한다** — `aria-pressed` 가 이미 상태를
  읽어 준다.
- **상태를 `variant` 로 그린다** (`secondary` ↔ `ghost`). `className` 으로 색을 덮지
  않는다 (component-guide.md §3).
- **기간 밖 고아 항목 섹션에는 토글이 없다.** `visit` prop 을 넘기지 않으면 렌더되지
  않는다 — 어느 일자에도 속하지 않는 항목에 '다녀옴' 을 두면 무엇을 다녀왔다는 것인지
  말할 수 없다.

**모든 일자에 노출한다.** 이슈 제목은 "여행 중" 이지만 미래 일자를 잠글 계약상 근거가
없고(서버가 언제든 받는다), 날짜로 가리면 여행 전에 일정을 훑는 사용자에게 토글이 아예
보이지 않아 기능의 존재를 알 수 없다.

### D9-4. 상태 · 문구

| 상태              | 화면                                              | 문구                                                                |
| ----------------- | ------------------------------------------------- | ------------------------------------------------------------------- |
| 꺼짐              | `ghost` 아이콘 버튼, `aria-pressed="false"`       | `다녀옴으로 표시` (`aria-label`)                                    |
| 켜짐              | `secondary` + `다녀옴` 배지 + 제목·썸네일 톤 약화 | `다녀옴 표시 해제` (`aria-label`)                                   |
| 저장 중           | **그 행의 토글만** `disabled` + `aria-busy`       | —                                                                   |
| 실패 (5xx·무응답) | 그 행 아래 `FormAlert` (`role="alert"`)           | `체크를 저장하지 못했어요. 잠시 후 다시 시도해 주세요.`             |
| 실패 (4xx)        | 같은 자리, 재시도 없음                            | `이 일정이 바뀌었어요. 새로고침한 뒤 다시 시도해 주세요.`           |
| 교체 경고         | 일자 헤더 아래 한 줄 (조건부)                     | `순서를 바꾸거나 장소를 담으면 이 날의 ‘다녀옴’ 표시가 초기화돼요.` |

- **성공에 토스트를 내지 않는다.** `aria-pressed` 상태 변화 자체가 피드백이고, 토글마다
  토스트를 내면 여러 곳을 연달아 체크할 때 화면이 토스트로 덮인다.
- **실패는 토스트가 아니라 그 행에 남는다** — 사라지는 UI 에 복구 수단을 두지 않는다
  (`components/toast.tsx`).
- **별도 `다시 시도` 버튼을 두지 않는다.** 실패해도 서버 상태가 그대로라 토글이 아직 같은
  방향을 가리키고, **그것을 다시 누르는 것이 재시도다** — 실내 대안 담기(F~)와 같은 판단이다.
- **색·투명도만으로 전달하지 않는다** (DESIGN.md §7). `다녀옴` 배지가 같은 사실을 낱말로
  말한다.

### D9-5. 데이터 흐름

- **낙관적 업데이트를 하지 않는다** (`api-integration-guide.md` §7). 응답이 `Void` 라
  갈아끼울 상세가 없고, `PLAN_005` 처럼 재시도로 풀리지 않는 실패가 있어 롤백이 잦다.
- **invalidate 대상은 `planKeys.detail(planId)` 하나다.** 응답이 `Void` 라 무효화가
  유일한 갱신 경로다.
- **판정(`planKeys.weather`)은 무효화하지 않는다.** 그날 판정은 **첫 장소 항목** 기준인데
  방문 체크는 항목 구성·순서를 바꾸지 않는다. 담기·순서편집이 판정을 다시 받는 것과
  갈리는 지점이다.
- **항목별로 동시 진행을 허용한다.** 일괄 교체와 달리 항목 한 행만 바꾸므로 두 요청이
  겹쳐도 한쪽이 사라지지 않는다. 그래서 전역 잠금이 아니라 `planItemId` 집합으로 진행·
  실패를 든다 (`useRef` 로 같은 tick 의 연속 클릭도 막는다 — form-guide.md §6).

- **일괄 교체 후 그 날 항목의 `visited` 가 `false` 로 초기화된다** (계약의 핵심)
- 교체 뒤 낡은 `planItemId` 로 체크 → 404 `PLAN_005`

### D9-7. 범위 밖

- **방문 진행률 요약** (좌 레일의 `다녀온 곳 3/8`) — 개요 패널 정보 구조를 다시 잡아야 한다
- **방문 시각 기록** — 계약에 없다 (`visited` boolean 뿐)
- **방문 기반 통계** — 후기 v1 은 일정당 후기 하나다. 성향 분석·집계는 범위 밖 (공통명세 S2 밴드와 같음)
- **편집모드 행의 토글** — 저장하면 항목이 새로 발급돼 체크가 사라진다. 그 자리에서
  체크하는 것은 곧 지워질 값을 만드는 일이다

### D10-1. 계약

| 항목       | 값                                                    |
| ---------- | ----------------------------------------------------- |
| 엔드포인트 | `GET` · `POST` · `PUT /api/v1/plans/{planId}/reviews` |
| 인증       | JWT `memberId`                                        |
| 개수       | 일정당 **하나**. 경로에 reviewId 없음                 |
| 작성 조건  | 본인 일정 + `status=COMPLETED`. 아니면 `PLAN_016`     |
| GET 없음   | `PLAN_015` 404                                        |
| POST 중복  | `PLAN_017` 409                                        |

요청: `{ overallRating: 1~5, body?: string(≤2000), items: [{ planItemId, rating: 1~5, comment?: ≤200 }] }`.
`items` 는 필수 배열이고 빈 목록이면 전체 만족도만 남긴다. PUT 은 **전량 교체**.
`planItemId` 는 Snowflake 라 **문자열로 보낸다**.

장소 항목 = `PLACE` / `MEAL` / `LODGING` 이고 `visited=true`. WALK·MOVE·미방문은 `PLAN_018`.
제목·placeId 는 요청에 받지 않고 **현재 항목에서 스냅샷**한다. PUT 에서 항목이 없어도
이미 후기에 같은 `planItemId` 가 있으면 제목·placeId 를 유지한다.

### D10-2. 화면

- **완료 일정 상세 좌측 레일**, 준비물 아래. 초안·확정에는 절 자체를 그리지 않는다.
- 초기 조회는 **클라이언트 RQ**. key 는 `planKeys.review(planId)`, 표준은 일정 30초/10분.
- `PLAN_015` → 빈 상태 + `후기 쓰기`. **재시도 없음.**
- 5xx → `ErrorState` + 재시도. `PLAN_016` 이 새면 서버 `resultMessage` 그대로.
- 작성 폼: 전체 만족도(필수, 1~5 숫자 버튼) + 선택 본문 + 다녀온 장소별 선택 평점·한 줄.
- 보기/수정: **후기 스냅샷**이 먼저다. 지금 일정에만 있는 방문 장소는 뒤에 붙인다.
- 목록 "후기 미작성" 밴드는 **만들지 않는다** — `hasReview` 가 없다 (공통명세 S2).
