## D0. 화면 정의

- **경로**: `/plans/[planId]` — route group `(main)`
- **인증**: **필요**. `proxy.ts` `PROTECTED_PATHS` 에 `'/plans'` 가 이미 있고 매칭이
  `pathname === base || pathname.startsWith(base + '/')` 라 **`/plans/{planId}` 도 이미 걸린다.
  추가 등록이 필요 없다.** 미로그인은 `/login?returnTo=/plans/123` 으로 보내진다.
- **진입 경로**: 목록 행(`plan-row.tsx`) · 홈 `upcoming-plan-row.tsx` · 만들기 성공 후
- **이탈 경로**: 목록(`/plans`) · 장소 상세(`/places/{placeId}`) · 삭제 성공 → `/plans`

> **만들기 성공 후 이동을 이 이슈에서 바꾼다.** 공통명세 S9 가 "상세가 생기면
> `/plans/{planId}` 로 바꾼다" 고 예고해 뒀다. 지금은 `/plans` 로 돌아간다.

## D1. 레이아웃

### 모바일 (390 — 아트보드 01)

단일 칼럼. 위에서 아래로:

```text
제목 · 상태 배지 · 기간 · 총 일수
반려견 카드 (이니셜 · 이름 · 품종 · 특성)  ·  D-day
─────────── 8px 밴드 ───────────
1일차  9/12 (토)          [순서 편집] [이 날 산책]
  일자 판정 (등급 배지 · 최고 체감온도 · reasons)
  ─ 1px ─
  항목 1 · 2 · 3
  [장소 추가]
─────────── 8px 밴드 ───────────
2일차 …
  (비 예보일 때) 비가 오면 갈 만한 실내
─────────── 8px 밴드 ───────────
[일정 확정하기]   ← DRAFT. CONFIRMED 면 [여행 완료하기] + [초안으로 되돌리기]. COMPLETED 면 [확정으로 되돌리기]
위험 영역 — [일정 삭제]
```

- **8px 밴드는 일자 경계에만 쓴다.** 일자 안(판정 → 항목 → 실내 대안)은 1px 선으로 잇는다.
  밴드가 일자를 나누는 유일한 신호다 (아트보드 01 주석).
- **순번은 썸네일 좌상단 칩이다.** 순번 원 + 썸네일 + 텍스트로 3열을 만들면 390 에서 제목이
  눌린다. 2열(썸네일 · 텍스트)로 유지한다 (아트보드 01 주석).

### 데스크톱 (1024+ — 아트보드 02)

기존 `.rail-layout` 을 그대로 쓴다 — `--rail-context`(400) + 1fr, sticky 좌열, `dvh` 열 구분선.

**`.rail-layout-detail` 변형은 쓰지 않는다.** 그 변형은 장소 상세용이고 **DOM 순서와 데스크톱
배치가 다른 경우**를 위한 것이다. 일정 상세는 모바일에서도 개요·반려견이 맨 위라 **DOM 순서
그대로(aside 먼저)** 두면 두 레이아웃이 같이 성립한다.

> **이 전제는 [#653](https://github.com/8llow8llowMe/hondigagae/issues/653) 에서 깨졌다.**
> 준비물·후기·배너가 모바일에서는 일자 **뒤**, 데스크톱에서는 레일 **안**이 되면서 레일을
> 본문 앞뒤 둘로 갈랐다. 지금 정본은 **D11-3** 이다. 아래 표와 sticky 설명도 그때 이후의
> 화면과 다르다 — 확정 버튼은 우측 열이 아니라 개요 아래이고(#553), 레일 고정은 걷었다.

| 열              | 내용                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------ |
| 좌 400 (sticky) | 개요(제목 · 상태 · 기간 · D-day · 반려견 · **일자별 판정 목차**) · 준비물 · 병원·약국 배너 |
| 우 가변         | 일자 섹션 (제목 `28/800`) · 확정 버튼 · 위험 영역                                          |

**고정은 `aside` 한 겹이 맡는다 — 개요 패널에 걸지 않는다.** 레일에 블록이 셋(개요 ·
준비물 · 배너)인데 첫 블록만 `lg:sticky` 였던 탓에 개요가 제자리에 못 박히고 **뒤 두 블록이
그 위로 올라와 글자가 겹쳤다** (실측 scrollY=700: 개요 top 64~519 고정, 준비물 top −181,
배너 top −18). `aside` 에 `lg:sticky lg:top-16 lg:self-start` 를 걸면 레일이 한 덩어리로
붙는다 — `lg:self-start` 가 없으면 grid stretch 로 레일 높이가 행 높이(1948px)까지 늘어나
고정이 성립하지 않는다 (DESIGN.md §7-1).

레일 콘텐츠는 개요 455 + 준비물 163 + 배너 74 = **692px** 로 가용 높이(1000 − 64 = 936px)
안에 들어온다. 블록을 더해 넘기기 시작하면 `.rail-sticky`(자기 스크롤)로 바꿔야 한다 —
고정 레일이 뷰포트보다 길면 아래쪽에 손이 닿지 않는다.

- **좌측 "일자별 판정" 세 줄은 앵커 링크다** (`#day1` …). 요약을 읽다가 그 날로 뛴다.
  각 줄 44px, 판정 색을 유지해 **목차이면서 요약**이다 (아트보드 02 주석).
- 폭 상한을 두지 않고 전폭을 쓴다 — 홈·목록·장소 상세와 같은 레일 문법이다.
- 1024 미만에서는 `.rail-layout` 이 grid 가 아니라 DOM 순서대로 쌓인다.

### 공통 컴포넌트 `Modal` — **이미 있다** (#79 완료)

이름·기간·예산 수정은 **입력이 있는 다이얼로그**라 `ConfirmModal` 로는 안 된다. 다이얼로그 계약
(focus trap · Esc · 스크롤 잠금 · 포커스 복귀 · `role="dialog" aria-modal="true"`)은
[#79](https://github.com/8llow8llowMe/hondigagae/issues/79) 에서 `components/modal.tsx` 로
추출했고 `ConfirmModal` 도 그것을 쓴다. **`PlanEditModal` 은 새로 만들지 말고 이 `Modal` 을 쓴다.**

```tsx
<Modal
  open={open}
  onClose={close}
  title="일정 수정"
  size="md" // 입력 폼은 md. 확인 다이얼로그가 sm 이다
  footer={<>…취소 · 저장…</>}
>
  …필드…
</Modal>
```

- `role` 기본값이 `dialog` 다. **`alertdialog` 는 되돌릴 수 없는 확인에만** 쓴다 (그쪽은
  `ConfirmModal` 이 이미 처리한다).
- 제목·설명 id 는 `Modal` 이 `useId()` 로 만들어 `aria-labelledby`/`aria-describedby` 에 묶는다.
  **호출부가 id 를 만들지 않는다.**
- 계약 테스트는 `src/components/modal.test.ts` 다.

**`ConfirmModal` 의 공개 API 는 바꾸지 않는다** — 호출부(`pet-delete-section.tsx`)를 건드리지
않아야 이 리팩터가 A 이슈 diff 를 키우지 않는다.

## D3. 데이터 흐름

```text
서버                       클라이언트
────────────────────────   ──────────────────────────────────────────
readSession()
GET /plans/{planId}   ────▶ (프리페치 완료 상태로 hydrate)
  fetchQuery + try/catch    ├─ GET /plans/{planId}/weather   (판정)
  404 → notFound()          ├─ GET /members/me/pets          (반려견)
                            └─ GET /places/{placeId} × N     (실내 대안 보강)
today = new Date()
```

| 항목                   | 내용                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| API                    | `GET /plans/{planId}` (서버) · `/weather` · `/members/me/pets` · `/places/{placeId}` × N (클라이언트, **실내 대안만**)                         |
| React Query key        | `planKeys.detail(planId)` (기존) · `planKeys.weather(planId)` (신규) · `petKeys.list()` (기존) · **`placeKeys.detail(placeId)` (기존 재사용)** |
| staleTime / retry      | 일정·판정 = `PLAN_QUERY_OPTIONS`(30s / 10m). 서버 `fetchQuery` 는 **`retry: false`**                                                           |
| mutation 후 invalidate | `PUT`/`DELETE` 응답이 `PlanDetailResponse` 라 **`setQueryData` 로 갈아끼우고** `planKeys.list()` 만 invalidate                                 |
| 폴링 여부              | 없음                                                                                                                                           |

### 서버 — `fetchQuery` + try/catch, `loading.tsx` 없음

장소 상세(`app/(main)/places/[placeId]/page.tsx`)와 **같은 골격**이다.

- `prefetchQuery` 는 에러를 삼켜서 404(그런 일정이 없음)와 5xx(일시 장애)를 못 가른다.
  `fetchQuery` 는 던지므로 잡아서 판정한다.
- `retry: false` — 전역 기본값(5xx 2회)을 상속하면 백엔드가 죽었을 때 서버 렌더가 재시도
  백오프만큼 통째로 블로킹된다 (`architecture-guide.md` §9).
- **이 세그먼트에 `loading.tsx` 를 두지 않는다.** 경계가 있으면 응답이 먼저 스트리밍되기
  시작해 뒤따르는 `notFound()` 가 HTTP 상태를 못 바꾼다 (soft 404, `architecture-guide.md` §7).
  `app/(main)/plans/` 에도 `loading.tsx` 가 없어 그룹 분리는 필요 없다 — **생기면 그때
  `(list)` 그룹으로 옮긴다.**
- `not-found.tsx` · `error.tsx` 를 세그먼트에 둔다.
- **`today` 를 서버에서 만들어 내려보낸다.** 클라이언트가 따로 `new Date()` 를 부르면 자정
  근처에서 서버 렌더와 하이드레이션의 D-day 가 하루 갈린다 (목록과 같은 결정).

`generateMetadata` 는 두지 않는다 — 보호 화면이라 크롤러가 못 들어오고, 제목을 위해 백엔드를
한 번 더 부를 이유가 없다. `layout` 의 기본 제목을 쓴다.

### 항목의 장소 요약 — **상세 응답이 함께 준다** (`item.place`)

[#86](https://github.com/8llow8llowMe/hondigagae/issues/86) 으로 백엔드가 항목마다
`place`(`addr1` · `indoor` · `firstImage` · `lat` · `lng`)를 실어 준다.
[#115](https://github.com/8llow8llowMe/hondigagae/issues/115) 에서 **항목당
`GET /places/{placeId}` 를 걷어냈다** — 3일·6항목이면 왕복 6번이던 것이 0번이다.

**`place` 는 객체 통째로 `null` 이 될 수 있고, 세 갈래가 같은 모양이다.**

| 갈래              | 왜 null 인가                                       | 화면          |
| ----------------- | -------------------------------------------------- | ------------- |
| `WALK` · `MOVE`   | 장소를 가리키지 않는다 (`targetId` 가 walk_course) | 결손이 아니다 |
| delisted 장소     | 원천에서 사라졌다 — 항목은 우리 DB 에 남아 있다    | 제목만 남긴다 |
| tour-service 장애 | 백엔드가 요약을 비운 채 응답한다                   | 제목만 남긴다 |

- **행을 지우지 않는다.** 일정 자료는 우리 DB, 장소는 다른 서비스다 (공통명세 S8).
- **응답은 뒤의 둘을 구분하지 않는다.** 그래서 화면도 원인을 단정하지 않는다 — 편집모드의
  안내 문구가 "이 곳은 더 이상 조회되지 않아요" 까지만 말하는 이유다 (일자편집 E1).
- 결손 판정은 `hasUnresolvedPlace()` 하나다: `isPlaceTarget(item) && item.place === null`.
  **`place === null` 만으로는 판정할 수 없다** — `WALK`·`MOVE` 도 `null` 이다.

> **실내 여부는 #80 에서 못 붙였다가 [#112](https://github.com/8llow8llowMe/hondigagae/issues/112)
> 에서 붙였다.** #16 으로 장소 응답에 `indoor` 가 들어왔고 #86 이 항목 요약에도 실었다 —
> 목록 캐시를 꺼내 쓰는 우회는 끝까지 쓰지 않았다. **행 메타 줄은 `주소 · 실내` 다**

### 남은 보강 — **실내 대안뿐이다**

`indoorAlternatives` 는 `{placeId, title, lat, lng, distanceMeters}` 뿐이라 주소·실내 여부를
말하려면 여전히 `GET /places/{id}` 가 필요하다 (`usePlaceEnrichment`).

- `useQueries` 로 병렬 조회한다. **key 는 `placeKeys.detail(placeId)` 재사용** — 장소 상세
  화면과 캐시를 공유해서, 상세를 보고 온 장소는 요청이 아예 나가지 않고 여기서 본 장소는
  장소 상세로 이동할 때 즉시 뜬다.
- 대상 id 는 `alternativePlaceIds(alternatives)` 가 **중복을 제거해** 만든다 — 같은 장소가
  두 일자의 대안일 수 있다.
- **실패한 장소는 제목만 남기고 행은 살린다** (항목과 같은 태도).

### 거리 — FE 하버사인, **직선거리임을 문구로 밝힌다**

서버에 거리 필드가 없다. **항목이 `place.lat`/`place.lng` 를 들고 오므로**(#86) 화면이
계산한다 — 예전에는 호출부가 보강 결과 맵을 `coordOf` 로 주입했는데, 이제 주입할 것이 없어
`toItemRows(items, lodgingBasis)` 가 항목에서 직접 꺼낸다.

- `src/lib/geo/distance.ts` 에 하버사인을 추가하고 **기존 `formatDistance()`(미터 입력)를
  그대로 쓴다** — 긴급 시설과 같은 표기여야 한다.
- 좌표가 유효하지 않은 장소가 있다 → 기존 `toLatLng()` 가 null 을 돌려준다. **한쪽이라도
  null 이면 그 행의 거리 문구를 렌더하지 않는다.** 0km 로 쓰지 않는다.
- **`직선 4.1km` 처럼 "직선" 을 붙인다.** 제주 산간·해안도로에서 직선거리와 주행거리는 크게
  다르다. 아트보드의 `4.1km` 를 그대로 쓰면 주행거리로 읽힌다.
- 기준점:
  - **숙소 기준** — **앞선 날**의 마지막 `LODGING` 항목. 있으면 그날 첫 항목에
    `숙소에서 직선 N km`
    > **구현하며 "그날" 을 뺐다.** 그날의 숙소를 기준으로 쓰면 아직 가지 않은 곳에서
    > 출발한 것이 된다 — 실렌더에서 1일차 첫 항목에 `숙소에서 직선 14.8km` 가 붙었고
    > 그 숙소는 그날 **저녁에** 체크인할 곳이었다. "그날" 을 넣어도 얻는 것이 없다:
    > 숙소가 그날 첫 항목이면 자기와의 거리(0km)라 잡음이고, 둘째 항목부터는
    > **직전 항목 규칙이 이미 그 숙소를 기준으로 잡는다.**
  - **순번 간** — 2번째 항목부터 직전 항목까지 `직선 N km 이동`
  - 숙소가 없으면 첫 항목에는 아무것도 붙이지 않는다
- **긴 이동 경고 임계값은 30km.** 넘으면 그 행만 경고 tint + `직선 41.2km 이동 — 하루 이동이
깁니다.` 별도 경고 배지를 만들지 않는다. **이게 편집 동기를 만든다** (아트보드 01 주석).

### 확정에는 확인 대화상자가 없다 ([#565](https://github.com/8llow8llowMe/hondigagae/issues/565))

**되돌릴 수 있기 때문이다.** 백엔드에 상태 전이 가드가 없다 —
`PlanCommandProcessor.updatePlan` 이 `command.status()` 를 그대로 쓰므로
`{ status: 'DRAFT' }` 를 보내면 초안으로 돌아간다. 되돌릴 수 있는 동작에 확인을 붙이면
**되돌릴 수 없다는 거짓말**이 된다.

삭제는 반대다 — `담은 장소와 일자별 판정이 함께 사라져요. 되돌릴 수 없어요.` 로
`ConfirmModal` 을 세운다. **두 액션의 무게 차이는 의도된 것이다.**

- **되돌리기는 상태 배지 아래, 확정과 같은 자리다.** `초안 ↔ 확정` 은 그 배지가 말하는
  값을 바꾸는 일이라 같은 축이다. 관리 메뉴가 다루는 것은 일정의 **신원**(이름 · 예산 ·
  존재 여부)이지 상태가 아니다.
- **무게는 `variant` 로 가른다.** 확정은 그 화면의 주 행동이라 `primary`, 되돌리기는 거의
  누르지 않는 액션이라 `secondary` 다. 폭은 둘 다 전폭이다 — 자리가 같은데 폭까지 바뀌면
  버튼이 옮겨 다니는 것처럼 보인다.
- **실패 문구는 방향마다 다르다.** `확정하지 못했어요` 가 되돌리기 실패에 뜨면 사용자가
  무엇이 실패했는지 거꾸로 읽는다.
- **완료에서는 초안으로 되돌리지 않는다 (#613).** 다녀온 기록을 작성 중으로 되돌리는
  것은 다른 판단이다. 잘못 닫았으면 확정으로만 되돌린다. 초안에서는 완료를 열지 않는다.

### `PUT` 은 부분 수정이다 — 보내지 않은 필드는 유지된다

`PlanUpdateRequest` 는 `title` · `startDate` · `endDate` · `budget` · `status` 를 받고
**null 인 필드는 기존 값을 유지**한다 (`PlanCommandProcessor.updatePlan`).

- 상태 버튼은 `{ status }` 만 보낸다. 다음 값은 `planStatusActions` 가 정한다 (`lib/plan/status-action.ts`)
- 이름·기간·예산 수정은 `{ title, startDate, endDate, budget }` 를 보낸다 (#585). **날짜는 바꾸지 않았어도 둘 다 보낸다** — 생략은 "유지" 라, 한쪽만 보내면 서버가 새 시작일과 옛 종료일로 기간을 다시 계산한다
- **예산을 비우는 방법이 없다.** `budget: null` 은 "유지" 로 읽힌다. 폼에서 예산을 지우면
  `0` 으로 보낸다 — `@PositiveOrZero` 라 0 은 유효하다. 문구로 그렇게 안내한다.

### 기간 수정 — 열었다 (#585)

**예전에는 닫아 뒀다.** `PlanCommandProcessor.updatePlan` 이 기간을 줄여도 항목을 정리하지
않아, 3일 일정을 2일로 줄이면 `day: 3` 항목이 그대로 남고 상세 응답에 `totalDays` 를 넘는
항목이 섞여 왔다 — 프론트가 고아 항목을 만드는 경로를 열지 않는다는 판단이었다.

**그 근거는 더 이상 사실이 아니다.** BE 가 `99c6a41f` 로 **저장 앞**에 검사를 넣어, 줄어든
기간 밖에 항목이 남으면 `PLAN_008`(_"줄어든 여행 기간 밖에 일정 항목이 남아 있습니다. 해당
일차의 항목을 먼저 정리해 주세요."_)로 거부한다. 시작일을 미뤄 일수가 줄어드는 경우도 같이
본다 (`backend/docs/services/plan-service.md`). 고아가 생기지 않으므로 화면이 경로를 닫아 둘
이유가 없어졌다.

화면이 지는 것과 지지 않는 것:

- **거부 판정을 복제하지 않는다.** 어느 일차에 항목이 있는지는 상세 응답에 있지만, 그
  판정을 화면이 다시 세면 서버 규칙이 바뀔 때 두 곳이 갈린다. `PLAN_008` 은 검증이 아니라
  도메인 예외라 `fieldErrors` 가 없고, `apiErrorToFormErrors` 가 **폼 배너**로 올린다.
  서버 문구가 이미 할 일까지 말하므로 FE 가 자기 말투로 옮기지 않는다.
- **막힐 수 있다는 것은 미리 말한다** — `editPeriodHint`(_"기간을 줄이면 새 기간 밖에 남는
  항목을 먼저 정리해야 저장돼요."_). 기간 줄 아래 한 번만 둔다.
- **역전(`PLAN_003`)과 상한 30일(`PLAN_009`)은 화면이 먼저 본다.** 판정은
  `lib/plan/period.ts` 의 `planPeriodIssue` 하나이고 **만들기 폼도 같은 함수를 쓴다** —
  두 폼이 같은 기간에 다른 답을 내면 어느 쪽이 맞는지 알 수 없다.
- **시작일에 `max` 를, 두 날짜에 `min={today}` 를 걸지 않는다.** 기간을 통째로 뒤로 옮기는
  조작을 막게 되고, 수정에는 서버도 "오늘 이후" 제약을 두지 않는다.
- **저장 성공 시 `planKeys.weather` 를 함께 버린다.** 기간이 바뀌면 일차 수와 날짜가 통째로
  달라지는데 캐시는 옛 기간으로 만든 것이다.

다만 **다른 경로로 이미 생긴 고아 항목은 이 화면이 만날 수 있다.** `totalDays` 만큼 일자
섹션을 그리고, 범위를 벗어난 항목은 맨 아래 **"여행 기간 밖 항목"** 으로 모아 보여준다.
**숨기지 않는다** — 숨기면 사용자가 자료가 사라진 것을 모른다.

### D5-1. 경로변수 형식 오류의 모양 (dev 실측 · 2026-09-21 · #803)

**일정 API 전체에 걸린 규칙이라 여기 한 번만 적고 다른 절은 이 절을 가리킨다.**

```text
GET /api/v1/plans/abc/briefing → 400
{"dataHeader":{"success":false,"resultCode":"PLAN_124",
 "resultMessage":"planId 파라미터 형식이 올바르지 않습니다.",
 "fieldErrors":[{"code":"PLAN_124","field":"planId",
   "message":"planId 파라미터 형식이 올바르지 않습니다."}]},"dataBody":null}
```

Swagger `paths` 17개로 실제 경로를 확인한 뒤 **15개 route/method 조합을 전부** 인증 없이
찔렀고 모두 같은 모양이었다. 만드는 곳은 한 줄이다 —
`ValidationErrorSupport.toResponse(MethodArgumentTypeMismatchException, defaultCode)` 가
`"%s 파라미터 형식이 올바르지 않습니다.".formatted(exception.getName())` 로 **필드명을 끼워
문구를 다시 만들고**, 같은 코드·필드·문구를 `fieldErrors` 한 건에 싣는다.

**문구가 실패한 경로변수 이름을 그대로 쓴다.** 목의 세 자리를 `planId` 로 맞추면 안 된다.

| 요청                                | `field`         |
| ----------------------------------- | --------------- |
| `PUT /plans/1/days/xyz/items`       | `day`           |
| `PUT /plans/1/items/xyz/visited`    | `planItemId`    |
| `DELETE /plans/1/packing-items/xyz` | `packingItemId` |
| `PUT /plans/abc/days/xyz/items`     | `planId`        |

마지막 줄이 요점이다 — **둘 다 틀리면 첫 인자가 이긴다.** 그리고 **경로변수 판정이 본문
검증보다 앞이다**: 본문 없는 `PUT /plans/1/packing-items/xyz/checked` 는 `PLAN_100` 이
아니라 `PLAN_124` 다.

**`PLAN_114` 가 아니다.** 예전 목이 쓰던 그 코드는 백엔드에서
`PlanValidationMessage.VISITED_REQUIRED`(`방문 여부는 필수입니다.`) — 방문 체크 **본문**
검증 코드라, 경로 오류에 쓰면 서버가 내지 않는 조합이 된다. 화면 영향은 없었다
(`toVisitToggleError` · `toPlanDaySaveError` 가 4xx 를 한 덩어리로 묶는다).

**같은 규칙이 모든 도메인에 걸린다** — #813 에서 판정을 공용 모듈
`src/lib/api/mock/path-variable.ts` 하나로 모았다. 서버도 도메인마다 같은 한 자리에서
만들기 때문이다. 문법의 정본은 D5-2 이고, **일정만 코드가 `PLAN_124`** 다
(`PLAN_1xx` 대역이 먼저 차서 공통 2종이 대역 끝으로 밀렸다 —
`backend/docs/coding-conventions.md` §8-2). 다른 도메인은 `PLACE_113` · `INSIGHT_113` ·
`WALKCOURSE_113` · `FAVORITE_113` · `PET_113` 이다.

### D5-2. 무엇이 형식 오류인가 — 바인딩 문법 (dev 실측 · #809)

D5-1 이 **오류의 모양**이라면 이쪽은 **무엇이 오류인가** 다. 목이 `/^\d+$/` 로 걸러
서버보다 엄격했다. 실제 문법은 스프링의 `NumberUtils.parseNumber` 다.

```java
String trimmed = StringUtils.trimAllWhitespace(text);            // 안쪽 공백까지 지운다
return (isHexNumber(trimmed) ? Long.decode(trimmed) : Long.valueOf(trimmed));

private static boolean isHexNumber(String value) {
    int index = (value.startsWith("-") ? 1 : 0);                 // + 는 보지 않는다
    return (value.startsWith("0x", index) || value.startsWith("0X", index)
         || value.startsWith("#", index));
}
```

| 입력                              | 바인딩  | 비고                          |
| --------------------------------- | ------- | ----------------------------- |
| `-1` · `+1` · `0` · `-0`          | 통과    | 부호를 받는다                 |
| `007` · `08` · `09`               | 통과    | **8진수가 아니다**            |
| `0x10` · `0X1F` · `#10` · `-#10`  | 통과    | 16진수 접두사 → `Long.decode` |
| `' 1'` · `'1 '` · `'1 2'`         | 통과    | 공백을 **전부** 지운다 → `12` |
| `9223372036854775807` (long MAX)  | 통과    | 경계값                        |
| `9223372036854775808`             | **400** | 범위 초과                     |
| `1.5` · `1e3` · `0b101` · `1,000` | **400** | —                             |
| `+0x10` · `#-10` · `--1` · `++1`  | **400** | `isHexNumber` 는 `-` 만 본다  |
| 공백만                            | **400** | —                             |

**8진수가 아니라는 것이 문법을 확정한 증거다.** `Long.decode` 였다면 `08`·`09` 가 무효여야
하는데 dev 는 둘 다 통과시킨다 — 16진수 접두사가 없어 `Long.valueOf` 로 가기 때문이다.

**`day` 는 `int` 라 경계가 다르다.** `2147483648` 은 `planId` 에서는 통과하고 `day` 에서는
400 이다. `long` 범위로 검사하면 이 자리가 틀린다.

**정규화한 값으로 조회한다.** 서버는 `' 1'` 을 `1` 로 풀어 **1번 일정을 찾는다** — 목이
원문으로 조회하면 같은 주소가 404 로 갈린다. `앞자리 0` 도 같다.

### D9-1. 계약

| 항목       | 값                                                                |
| ---------- | ----------------------------------------------------------------- |
| 엔드포인트 | `PUT /api/v1/plans/{planId}/items/{planItemId}/visited`           |
| 인증       | 필요 (`@PreAuthorize("isAuthenticated()")`)                       |
| 요청       | `{ "visited": boolean }` — `@NotNull`                             |
| 응답       | `Response<Void>` — **`dataBody` 가 `null`**                       |
| 조회 확장  | `PlanItemDetailItem.visited` — **primitive `boolean`, 항상 온다** |

- **해제도 같은 API 다.** `visited: false` 를 보낸다. 별도 DELETE 가 없다.
- **`clientFetchVoid` 를 써야 한다.** `clientFetch` 로 부르면 `unwrap()` 이
  `dataBody === null` 을 실패로 보고 **서버는 저장했는데 화면만 실패라고 말한다** —
  `deletePlan` 에서 브라우저 실측으로 잡았던 것과 같은 함정이다.
- **소유권을 두 번 본다.** 백엔드가 일정으로 소유권을 확인한 뒤
  `findById(planItemId).filter(found -> found.planId() == plan.id())` 로 항목이 그
  일정의 것인지 다시 본다. 남의 일정 항목을 내 `planId` 로 체크할 수 없다.

**오류**

| 코드       | 상태 | 뜻                                | 화면                                        |
| ---------- | ---- | --------------------------------- | ------------------------------------------- |
| `PLAN_001` | 404  | 없는 일정 / 남의 일정             | 재시도 없음                                 |
| `PLAN_005` | 404  | 없는 항목 / 그 일정의 항목이 아님 | 재시도 없음                                 |
| `PLAN_124` | 400  | 경로변수 형식 (`@PathVariable`)   | 재시도 없음                                 |
| `PLAN_100` | 400  | `visited` 누락                    | 화면이 항상 boolean 을 보내 발생하지 않는다 |
| `PLAN_900` | 503  | 내부 연동 실패                    | 재시도                                      |

### D9-2. 일괄 교체가 체크를 초기화한다 — 이 절의 핵심

**일차 항목을 교체하면 그 날의 방문 체크가 전부 초기화된다.** 백엔드가 항목을 삭제 후
재삽입해 새 `planItemId` 를 발급하므로 `visited` 가 기본값 `false` 로 돌아간다
(컨트롤러 설명 · `PlanItemEntity.visited`).

**일괄 교체 모델과 정면으로 부딪히는 지점이라 화면이 먼저 말한다.** 순서 편집(E~)과
장소 담기(F~)가 모두 그 교체를 쓴다.

- 경고는 **일자 헤더 액션 바로 아래**에 한 줄로 둔다. 두 진입점(`순서 편집` · `장소 추가`)이
  모두 그 줄 위의 버튼에서 시작하므로 한 번만 두면 양쪽을 덮는다.
- **그 일자에 체크된 항목이 있을 때만 낸다.** 잃을 것이 없는 날에도 띄우면 경고가
  배경음이 되어 정작 잃을 날에 읽히지 않는다.
- 편집 중에는 감춘다 — 그때는 편집기가 저장 지점을 들고 있다.

부수 효과로, **교체 뒤 낡은 `planItemId` 로 체크하면 `PLAN_005` 404 다.** 재시도로
풀리지 않는 실패라 그 분기에 `다시 시도` 를 주지 않는다.

### D9-3. 배치 — 후행 44px 열

**행 전체가 `<Link>` 라 그 안에 버튼을 넣을 수 없다.** 중첩 상호작용은 시맨틱이 깨지고
키보드로 어느 쪽이 잡히는지 알 수 없다. 링크를 `flex-1` 로 두고 **토글을 링크의 형제**로
후행 열에 뺀다.

아트보드 01 이 금지한 것은 순번 원 + 썸네일 + 텍스트의 **선행** 3열(390 에서 제목이
눌린다)이다. 후행 아이콘 열은 제목이 쓰는 폭을 44px 만큼만 줄인다.

- **`aria-pressed` 토글이다.** `Checkbox` 는 라벨이 요소 옆에 붙는 폼 입력이라 행 후행
  액션에 맞지 않는다. 저장소는 이런 토글을 `aria-pressed` 로 쓴다 (`chip.tsx`).
- **이름은 상태가 아니라 누르면 일어날 일을 말한다** — `aria-pressed` 가 이미 상태를
  읽어 준다.
- **상태를 `variant` 로 그린다** (`secondary` ↔ `ghost`). `className` 으로 색을 덮지
  않는다 (component-guide.md §3).
- **기간 밖 고아 항목 섹션에는 토글이 없다.** `visit` prop 을 넘기지 않으면 렌더되지
  않는다 — 어느 일자에도 속하지 않는 항목에 '다녀옴' 을 두면 무엇을 다녀왔다는 것인지
  말할 수 없다.

**모든 일자에 노출한다.** 이슈 제목은 "여행 중" 이지만 미래 일자를 잠글 계약상 근거가
없고(서버가 언제든 받는다), 날짜로 가리면 여행 전에 일정을 훑는 사용자에게 토글이 아예
보이지 않아 기능의 존재를 알 수 없다.

### D9-4. 상태 · 문구

| 상태              | 화면                                              | 문구                                                                |
| ----------------- | ------------------------------------------------- | ------------------------------------------------------------------- |
| 꺼짐              | `ghost` 아이콘 버튼, `aria-pressed="false"`       | `다녀옴으로 표시` (`aria-label`)                                    |
| 켜짐              | `secondary` + `다녀옴` 배지 + 제목·썸네일 톤 약화 | `다녀옴 표시 해제` (`aria-label`)                                   |
| 저장 중           | **그 행의 토글만** `disabled` + `aria-busy`       | —                                                                   |
| 실패 (5xx·무응답) | 그 행 아래 `FormAlert` (`role="alert"`)           | `체크를 저장하지 못했어요. 잠시 후 다시 시도해 주세요.`             |
| 실패 (4xx)        | 같은 자리, 재시도 없음                            | `이 일정이 바뀌었어요. 새로고침한 뒤 다시 시도해 주세요.`           |
| 교체 경고         | 일자 헤더 아래 한 줄 (조건부)                     | `순서를 바꾸거나 장소를 담으면 이 날의 ‘다녀옴’ 표시가 초기화돼요.` |

- **성공에 토스트를 내지 않는다.** `aria-pressed` 상태 변화 자체가 피드백이고, 토글마다
  토스트를 내면 여러 곳을 연달아 체크할 때 화면이 토스트로 덮인다.
- **실패는 토스트가 아니라 그 행에 남는다** — 사라지는 UI 에 복구 수단을 두지 않는다
  (`components/toast.tsx`).
- **별도 `다시 시도` 버튼을 두지 않는다.** 실패해도 서버 상태가 그대로라 토글이 아직 같은
  방향을 가리키고, **그것을 다시 누르는 것이 재시도다** — 실내 대안 담기(F~)와 같은 판단이다.
- **색·투명도만으로 전달하지 않는다** (DESIGN.md §7). `다녀옴` 배지가 같은 사실을 낱말로
  말한다.

### D9-5. 데이터 흐름

- **낙관적 업데이트를 하지 않는다** (`api-integration-guide.md` §7). 응답이 `Void` 라
  갈아끼울 상세가 없고, `PLAN_005` 처럼 재시도로 풀리지 않는 실패가 있어 롤백이 잦다.
- **invalidate 대상은 `planKeys.detail(planId)` 하나다.** 응답이 `Void` 라 무효화가
  유일한 갱신 경로다.
- **판정(`planKeys.weather`)은 무효화하지 않는다.** 그날 판정은 **첫 장소 항목** 기준인데
  방문 체크는 항목 구성·순서를 바꾸지 않는다. 담기·순서편집이 판정을 다시 받는 것과
  갈리는 지점이다.
- **항목별로 동시 진행을 허용한다.** 일괄 교체와 달리 항목 한 행만 바꾸므로 두 요청이
  겹쳐도 한쪽이 사라지지 않는다. 그래서 전역 잠금이 아니라 `planItemId` 집합으로 진행·

### D11-1. 바꾸는 것

**목표 순서 (모바일)**: `개요(+정방향 상태 액션)` → `일자 카드들` → `준비물` → `후기` → `배너`

1. **역방향 상태 변경을 `⋯` 메뉴로 내린다** (PL-2).
2. **준비물·후기·배너를 일자 아래로 내린다** (PL-3).
3. **일자 카드 안을 `제목 → 판정 → 항목 → 액션` 으로 바꾸고 `다시 만들기` 를 오버플로로**
   내린다 (PL-4).
4. **`✓` 에 눈으로 보이는 뜻을 준다** (PL-5).

### D11-2. 상태 변경 — 정방향은 남고 역방향만 메뉴로

| 상태 | 전폭 버튼 (개요 아래) | `⋯` 메뉴                            |
| ---- | --------------------- | ----------------------------------- |
| 초안 | `일정 확정하기`       | 수정 · 삭제                         |
| 확정 | `여행 완료하기`       | 수정 · **초안으로 되돌리기** · 삭제 |
| 완료 | (없음)                | 수정 · **확정으로 되돌리기** · 삭제 |

**정방향을 함께 내리지 않는 이유.** PL-2 가 지목한 해악은 _"드물고 되돌리기 어려운 상태
변경이 가장 강한 자리를 차지한다"_ 인데, `확정하기`·`완료하기` 는 **그 상태에서 사용자가 할
다음 일**이고 드물지도 않다. 또 **되돌리기 어렵지도 않다** — `plan-status-action.tsx` 가
확인 대화상자를 붙이지 않는 근거가 바로 _"되돌릴 수 있기 때문"_ 이다(#565·#613). 전부 내리면
`#553` 이 확정 버튼을 마지막 일자 끝에서 개요 아래로 끌어올린 결정까지 되돌린다.

**역방향만 내리면 완료 상태의 전폭 버튼이 0개가 된다** — 다녀온 일정에서 화면이 가장 강하게
미는 것이 아무것도 없는 것이 맞다. 그 화면의 할 일은 **읽는 것**이다.

`⋯` 는 **이미 있는 `PlanManageMenu`** 다 (개요 카드 우측 상단, `aria-label="일정 관리"`).
새 메뉴를 만들지 않는다.

**파괴적 항목 규칙은 그대로다** — `삭제` 가 마지막이고 그 위에 선을 긋는다. 역방향 상태
변경은 **파괴적이 아니다**(되돌릴 수 있다) → `수정` 과 `삭제` 사이, 선 위에 둔다.

**오류 자리.** 상태 변경은 실패할 수 있고 지금은 버튼 아래 `FormAlert` 가 말한다. 메뉴는
닫히므로 **메뉴 밖, 개요 카드 아래 액션 자리**에 그대로 낸다 — 실패는 메뉴가 아니라 화면이
말해야 한다.

### D11-3. 레이아웃 — 레일을 위·아래 둘로 가른다

모바일 DOM 순서와 데스크톱 2열을 **동시에** 만족해야 한다. D1 이 _"DOM 순서 그대로 두면 두
레이아웃이 같이 성립한다"_ 고 적은 전제가 이 변경으로 깨진다 — 준비물이 모바일에서는 일자
**뒤**, 데스크톱에서는 레일 **안**이다.

**`.rail-layout-detail`(장소 상세용)을 그대로 쓰지 않는다.** 그쪽은 aside 가 **한 덩어리**로
두 행에 걸치는 모양(`grid-row: 1 / span 2`)인데, 여기는 레일이 본문 **앞뒤로 갈린다.**

```text
DOM 순서            데스크톱 grid 배치
─────────────────   ────────────────────────────
① 개요 + 액션 + 목차  → col 1, row 1
② 일자 카드들        → col 2, row 1 / span 2
③ 준비물 · 후기 · 배너 → col 1, row 2
```

`lg` 미만에서는 `.rail-layout` 이 grid 가 아니므로 ①②③ 이 DOM 순서대로 쌓인다 — **그것이
목표 순서다.** 데스크톱 레일의 보이는 순서는 **지금과 같다**(개요 → 액션 → 목차 → 준비물 →
배너).

**행 크기를 명시해야 한다.** `.rail-layout` 의 행은 기본이 `auto` 인데, CSS Grid 는 **여러
트랙에 걸친 아이템의 초과분을 걸친 트랙에 균등 분배**한다 — ② 가 ① 보다 길면 그 절반이
row 1 에 얹혀 ① 과 ③ 사이가 벌어진다(실측 325~523px, 일수에 비례해 커진다).
`grid-template-rows: max-content minmax(0, 1fr)` 을 주면 걸친 아이템이 초과분을 **row 2 로
넘기므로** row 1 이 ① 의 높이에 딱 맞는다. `.rail-layout-filter` 가 같은 이유로 이미
`grid-template-rows` 를 쓴다.

**③ 에 위 여백을 주지 않는다** (`pt-2 md:pt-0`). ② 와 달리 ③ 은 데스크톱에서 자기 열의 첫
요소가 아니라 ① 다음이고, `SurfaceStack` 의 `md:p-6` 이 ① 아래쪽에 이미 24 를 낸다 — 주면
24 가 둘 겹쳐 48 이 된다(실측).

### D11-4. 일자 카드 — 판정 → 항목 → 액션

```text
제목 줄:  1일차   10-03 (토)                          ⋯
판정:     적합도 여행 적합 · 최고 체감온도 27.5℃ · 근거
항목:     1 함덕 서우봉 해변 / 2 동문재래시장
액션:     [장소 추가]  [순서 편집]
```

- **`장소 추가` · `순서 편집` 은 항목 아래로.** 지금 헤더에 있는 셋 중 둘이다.
- **`다시 만들기` 는 `⋯` 오버플로로.** 하루를 통째로 갈아엎는 것이라 나머지 둘과 무게가
  다르다. `regenerateHref === null` 이면 지금처럼 **항목 자체를 내지 않는다** — 메뉴가 비면
  `⋯` 도 내지 않는다.
- **빈 일자에도 `장소 추가` 는 남는다** (기존 규칙). `순서 편집` 은 지금처럼 항목이 있을 때만.
- **편집 중에는 액션 줄을 감춘다** (기존 규칙 그대로).

### D11-5. `✓` — 글자를 준다

체크 전 상태의 아이콘만으로는 뜻이 서지 않는다. **`aria-label` 은 이미 옳으므로 눈에 보이는
쪽만 고친다.**

- 버튼이 `iconOnly` 를 벗는다.
- **보이는 글자가 상태에 따라 갈린다** — 체크 전 `다녀옴 표시`, 체크 뒤 `다녀옴`.
  **양쪽 다 `다녀옴` 으로 두지 않는다**: 아직 안 간 행에 그 낱말이 있으면 훑는 사람에게 그
  행이 **이미 다녀온 것으로 읽힌다** — `✓` 가 무엇인지 모르는 것보다 틀리게 아는 것이 나쁘다.
- `aria-label` 은 지금처럼 양쪽 다 **행동**을 말한다(`다녀옴으로 표시` / `다녀옴 표시 해제`).
  보이는 글자와 갈리지만 둘 다 성립한다 — 눈은 상태를 보고, 귀는 `aria-pressed` 로 상태를 듣는다.
- 체크된 뒤에는 행의 `다녀옴` 배지와 같은 낱말이 두 번 선다 → **배지를 걷는다.** 낱말로도
  말한다는 #124 의 요구는 그대로이고, 그 일을 하는 요소만 버튼으로 옮겨 간다. 버튼 쪽이
  **체크 전에도** 보이므로 더 낫다.
- **44px 터치 영역을 잃지 않는다** (D9-3 의 후행 열 규칙) — 실측 `h=44` 유지.

**치르는 값 — 제목 폭 30px** (390 실측). 토글이 아이콘만일 때 44px 이던 것이 체크 전
**133px** · 체크 뒤 **103px** 이 되고 제목 열이 그만큼 줄어, **10자 안팎 제목이 두 줄로
접힌다** (`오설록 티뮤지엄 카페`: 제목 폭 133 → 2줄). 받아들이는 근거는 **이 행에서 잃는
것보다 화면에서 얻는 것이 크다**는 것이다 — 같은 변경 묶음이 `1일차` 를 초안 700→362 ·
확정 694→304 · 완료 954→252 로 끌어올렸다. 가로 넘침은 없다(`scrollWidth === 390`).

### D11-6. 접근성

- `⋯` 메뉴의 키보드 순회는 `Menu` 가 보장한다 (기존). 역방향 상태 변경이 메뉴로 들어가도
  **Tab → Enter → 방향키**로 닿는다.
- 상태 변경 실패 `FormAlert` 는 메뉴 밖에 있어 메뉴가 닫혀도 읽힌다.
- 일자 카드 액션이 항목 **뒤로** 가면 탭 순서도 그렇게 바뀐다 — 읽는 순서와 같아진다.
- `✓` 버튼에 글자가 생겨도 `aria-label` 을 지우지 않는다. 이름은 **누르면 일어날 일**을
  말하고(`다녀옴으로 표시` / `다녀옴 표시 해제`) 보이는 글자는 **상태 쪽**으로 기운다 —
  둘이 갈리는 것이 의도다. 현재 상태는 `aria-pressed` 가 읽어 준다.

### D11-7. 테스트 케이스

섹션 순서는 **렌더 문자열의 `indexOf` 로** 잠근다 — 클래스 단언은 순서를 못 본다.

| #   | 대상                  | 단언                                                                                              |
| --- | --------------------- | ------------------------------------------------------------------------------------------------- |
| 1   | 모바일 DOM 순서       | `indexOf(1일차) < indexOf(여행 준비물)` — 세 상태 모두                                            |
| 2   | 준비물·후기·배너 묶음 | 셋이 **일자 뒤**에 있고 서로의 순서도 준비물 → 후기 → 배너다                                      |
| 3   | 초안                  | `일정 확정하기` 가 전폭 버튼으로 남는다. 메뉴에 역방향 항목이 **없다**                            |
| 4   | 확정                  | `여행 완료하기` 는 버튼, `초안으로 되돌리기` 는 **메뉴 안**이다                                   |
| 5   | 완료                  | 전폭 상태 버튼이 **없다**. `확정으로 되돌리기` 가 메뉴 안이다                                     |
| 6   | 메뉴 항목 순서        | `삭제` 가 마지막이고 역방향 항목은 그 **위**다                                                    |
| 7   | 일자 카드 순서        | `indexOf(판정 등급어) < indexOf(첫 항목 제목) < indexOf(장소 추가)`                               |
| 8   | `다시 만들기`         | 일자 `⋯` 메뉴 안이다. `regenerateHref === null` 이면 메뉴에 그 항목이 없다                        |
| 9   | 빈 일자               | `장소 추가` 는 남고 `순서 편집` 은 없다 (기존 규칙 회귀)                                          |
| 10  | 편집 중               | 액션 줄이 통째로 없다 (기존 규칙 회귀)                                                            |
| 11  | `✓` 버튼              | 체크 전 `다녀옴 표시`, 체크 뒤 `다녀옴`. 체크 전 마크업에 `>다녀옴</button>` 이 **없다**          |
| 12  | `다녀옴` 배지 제거    | 체크된 행에 `다녀옴` 이 **한 번만** 나온다 (배지 + 버튼 중복 회귀)                                |
| 13  | 메뉴 항목             | 닫힌 `Menu` 는 `null` 이라 정적 마크업으로 못 본다 — 트리거의 존재/부재만 재고 항목은 e2e 가 본다 |

**새 단언마다 뮤테이션을 넣어 빨간불을 확인한다.**

**메뉴 안은 e2e 가 본다.** `menu.tsx:81` 이 닫혔을 때 `null` 을 렌더하므로
`renderToStaticMarkup` 으로는 항목도 링크도 볼 수 없다 — 기존 `PlanManageMenu` 의
`수정`·`삭제` 도 같은 이유로 단위 테스트가 없었다. `e2e/plan-status.spec.ts` 가 두 메뉴를
열어 항목과 `href` 를 확인한다.

### D11-8. 범위 밖

- **준비물의 `D-1 이하 승격`** (진단 PL-3 후반). 화면이 D-day 에 따라 달라지는 **새 동작**이라
  검증 표면이 따로 생기고, 이 절의 축(위계)과 다르다. **별도 이슈로 판다.**
- **PL-6** (`예산(선택)` 통화 접미) — 일정 만들기 화면이라 이 문서 범위 밖이다.
- 데스크톱 레일의 보이는 순서는 **바꾸지 않는다.** 이 변경은 모바일 순서 문제다.

### D11-9. 준비물 시간 승격 — 출발이 가까우면 일자 위로 (이슈 [#665](https://github.com/8llow8llowMe/hondigagae/issues/665))

D11-8 이 범위 밖으로 밀어 둔 **`D-1 이하 승격`** 을 여기서 연다. 진단 **PL-3** 후반이다.

#653 이 준비물을 일자 뒤로 내린 근거는 _"준비물은 출발 전날 과업"_ 이었다. **바로 그 출발
전날에는 근거가 뒤집힌다** — 그날 이 화면을 연 사람이 찾는 것은 짐 목록이다.

```text
D-2 이상:  개요 → 일자 카드들 → 준비물 → 후기 → 배너   ← #653 (기본)
D-1 · D-0: 개요 → 준비물 → 일자 카드들 → 후기 → 배너   ← 이 절
```

> **순서만 바꾼다.** 준비물 카드의 내용·AI 생성 흐름·계약은 건드리지 않는다 (D11-9-7).

### D11-9-1. 경계 — 승격 창은 `D-1` 과 `D-0` 둘뿐

갈래는 **`planPhaseOf`(`lib/plan/date.ts`)가 이미 나눠 둔 셋**을 그대로 쓴다. 날짜 축의
판정을 새로 만들지 않는다.

| 갈래                       | `planPhaseOf`           | 예 (오늘 `2026-09-18`) | 준비물 자리        |
| -------------------------- | ----------------------- | ---------------------- | ------------------ |
| `D-2` 이상                 | `upcoming` `days >= 2`  | 시작 `09-20`           | 일자 **뒤** (기본) |
| **`D-1`**                  | `upcoming` `days === 1` | 시작 `09-19`           | **일자 위**        |
| **`D-0` (출발 당일)**      | `upcoming` `days === 0` | 시작 `09-18`           | **일자 위**        |
| 여행 중 (2일차~마지막날)   | `ongoing` `day >= 2`    | `09-16` ~ `09-20`      | 일자 **뒤**        |
| 지난 일정                  | `past`                  | ~ `09-17`              | 일자 **뒤**        |
| 날짜를 못 읽음 · 기간 역전 | `null` · `past`         | —                      | 일자 **뒤**        |

- **승격의 기준은 "준비물이 아직 할 일인가" 다.** 짐은 떠나기 전에 싼다 — 출발한 뒤의
  준비물 카드는 과업이 아니라 기록이다.
- **2일차부터 내려간다.** 여행 중인 사람이 이 화면에 묻는 것은 _"오늘 어디 가지"_ 이고, 그
  답은 일자 카드에 있다. 준비물을 위에 두면 매일 아침 답을 한 번씩 밀어낸다.
- **지난 일정에 올리는 것은 뜻이 없다.** 다녀온 여행에서 짐 목록을 맨 위로 올릴 이유가
  없고, 그 화면이 찾는 것(후기)은 이미 아래 레일에 있다 (D10).
- **판정할 근거가 없으면 기본 순서를 지킨다.** 날짜를 못 읽거나 기간이 역전된 데이터에서
  화면 배치를 바꾸지 않는다 — 기본(비승격)이 #653 이 실측으로 고른 순서다.

> **`1일차`는 `ongoing` 이 아니다.** 이슈 본문은 여행 중을 _"1일차~마지막날"_ 이라고 적었지만
> `planPhaseOf` 는 **출발 당일을 `upcoming`(`days === 0`, `D-DAY`)에 남긴다** — `ongoing.day`
> 는 항상 2 이상이다(그 함수의 머리주석). **코드의 갈래가 정본이고**, 그래서 위 표의 `D-0`
> 과 `여행 중` 은 겹치지 않는다. 하루짜리 일정은 `ongoing` 을 아예 거치지 않으므로 `D-0`
> 하루만 승격됐다가 다음 날 `past` 로 떨어진다.

### D11-9-2. 판정 — 순수 함수 하나. 시간 의존을 컴포넌트에 두지 않는다

새 파일 **`src/lib/plan/packing-promotion.ts`** (짝 테스트 `packing-promotion.test.ts`).

```ts
/** 승격이 열리는 최대 남은 일수. `D-1` 까지가 창이다 (D11-9-1) */
export const PACKING_PROMOTION_MAX_DAYS = 1

/**
 * 준비물 카드를 일자 위로 올릴 것인가 (D11-9-1).
 *
 * @returns 출발 전날·당일이면 `true`. 그 밖(여행 중 · 지난 일정 · 읽을 수 없는 날짜)은 `false`
 */
export function isPackingPromoted(
  plan: Pick<PlanDetail, 'startDate' | 'endDate'>,
  today: Date,
): boolean {
  const phase = planPhaseOf(plan.startDate, plan.endDate, today)
  return phase?.kind === 'upcoming' && phase.days <= PACKING_PROMOTION_MAX_DAYS
}
```

**`planPhaseOf` 에 얹는다.** 산술만 보면 `startDate` 하나로도 같은 답이 난다 — `days < 0`
이면 `ongoing` 이든 `past` 든 비승격이라 둘을 가릴 필요가 없다. 그런데도 `endDate` 를 받아
`planPhaseOf` 를 부르는 이유는 둘이다.

1. **`lib/plan/date.ts` 가 _"날짜 축의 판정은 여기 하나뿐이다"_ 를 머리주석에 못박았다.**
   같은 화면에서 개요 배지(`D-1`)와 준비물 자리를 **다른 셈**으로 정하면, 배지는 `D-1` 인데
   준비물이 안 올라오는 날이 생길 수 있다. 같은 `days` 를 쓰면 그럴 수 없다.
2. **기간 역전(`endDate < startDate`) 깨진 데이터가 `past` 로 떨어져 비승격이 된다.**
   `startDate` 산술만 보면 역전 데이터도 승격한다.

**`today` 는 주입받는다.** 모듈 안에서 `new Date()` 를 부르지 않는다 — `dayRegenerateBlock`
과 같은 분담이다. `plan-detail-section.tsx` 는 **이미 `today: Date` 를 prop 으로 받고**,
그 값은 서버(`app/(main)/plans/[planId]/page.tsx`)가 만들어 `PlanDetailView` 를 거쳐 온다.
클라이언트가 스스로 시각을 읽으면 SSR 과 하이드레이션이 자정을 걸쳐 갈린다.

**반환값은 `boolean` 이다.** 갈래가 둘(위/아래)뿐이고 **화면이 이유를 말하지 않으므로**
`DayRegenerateBlock` 같은 이유 union 이 필요 없다. 이유를 말하게 되는 날 union 으로 넓힌다.

**호출은 한 줄이다.** `plan-detail-section.tsx` 의 `regenerateBlocked` 바로 아래에 둔다.

```ts
const packingPromoted = isPackingPromoted(plan, today)
```

**이 화면의 시간 의존은 이 한 줄이 전부다** — 아래 JSX 는 `boolean` 만 본다.

### D11-9-3. 배치 — CSS 를 새로 쓰지 않는다

승격 갈래에서 바뀌는 것은 **준비물 `Surface` 가 `rail-split-bottom` 스택에서
`rail-split-top` 스택의 마지막 카드로 옮겨 가는 것** 하나다. `.rail-layout-split` 규칙도,
새 클래스도 필요 없다.

```text
비승격 (기본, #653)                       승격 (D-1 · D-0)
────────────────────────────────          ────────────────────────────────
rail-split-top     개요·액션·목차          rail-split-top     개요·액션·목차
                                                             준비물
rail-split-main    일자 카드들             rail-split-main    일자 카드들
rail-split-bottom  준비물                  rail-split-bottom  (후기)
                   (후기)                                     배너
                   배너
```

**모바일 (`lg` 미만).** `.rail-layout` 이 grid 가 아니라 DOM 순서대로 쌓인다.

| 갈래   | 읽는 순서                              |
| ------ | -------------------------------------- |
| 비승격 | 개요 → 일자 → 준비물 → 후기 → 배너     |
| 승격   | 개요 → **준비물** → 일자 → 후기 → 배너 |

**데스크톱 (`lg` 이상).** 좌측 열(col 1)이 보이는 순서는 `row 1` 내용 → `row 2` 내용이다.

| 갈래   | 좌측 레일의 보이는 순서       |
| ------ | ----------------------------- |
| 비승격 | 개요 → 준비물 → (후기) → 배너 |
| 승격   | 개요 → 준비물 → (후기) → 배너 |

**둘이 같다 — 이것이 D11-8 의 _"데스크톱 레일의 보이는 순서는 바꾸지 않는다"_ 를 지키는
방법이다.** 준비물이 `row 1` 의 끝에 붙든 `row 2` 의 머리에 오든, 두 행이 세로로 이어 붙어
있어 **좌측 열에서 읽는 자리가 같다.** 옮겨야 하는 카드가 하필 그 이음매에 있어서
**CSS 없이 DOM 이동만으로** 모바일 순서와 데스크톱 순서를 동시에 만족한다.

**행 크기 처방은 그대로 살아 있다.** `grid-template-rows: max-content minmax(0, 1fr)` 을
건드리지 않는다 — `row 1` 이 `max-content` 라 `개요 + 준비물` 높이에 딱 맞고, 두 행에 걸친
일자 열의 초과분은 여전히 `row 2`(`minmax(0, 1fr)`)로 넘어간다. **행 크기를 `auto` 로
되돌리면 승격 갈래에서도 325~523px 틈이 다시 벌어진다** (D11-0-1 · `globals.css` 주석).

**승격해도 준비물은 정방향 상태 버튼보다 아래다.** 확정·완료 액션은 `PlanOverviewPanel` 이
`action` 으로 받아 개요 카드 바로 아래에 내고(#553), 준비물은 그 패널 **뒤**에 붙는 형제
카드다. 상태 배지와 그 배지를 바꾸는 버튼 사이에 다른 카드가 끼지 않는다.

**쓰지 않는 수단.**

| 수단                                              | 왜 안 쓰는가                                                                                                                                                                                          |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 모바일에서 CSS `order` 로 재배치                  | `.rail-layout` 은 `lg` 미만에서 grid 도 flex 도 아니라 컨테이너를 새로 만들어야 하고, 무엇보다 **보이는 순서와 DOM 순서가 갈린다** — 탭 순서·스크린리더가 시각 순서를 따라오지 않는다 (D11-6 을 깬다) |
| `.rail-layout-split-promoted` 변형을 하나 더 둔다 | 필요가 없다. DOM 이동으로 같은 결과가 나는데 grid 규칙이 둘로 갈리면 **행 크기 처방을 두 군데서 지켜야 한다**                                                                                         |
| 두 자리에 렌더하고 한쪽을 `hidden`                | 같은 카드가 두 번 선다 — 스크린리더가 두 번 읽고, `PlanPackingList` 가 `useQuery` 를 들어 **마운트가 둘**이 된다. `.rail-layout-detail` 주석이 트리를 둘로 나누지 않는 이유로 적은 것과 같다          |

### D11-9-4. 간격 — 새 여백을 만들지 않는다

- **승격된 준비물은 `rail-split-top` 의 `SurfaceStack` 안에서 개요 패널의 형제**가 된다.
  카드 사이 간격은 스택이 낸다(모바일 8 · `md` 24). 준비물 카드에 자기 여백을 붙이지 않는다.
- **`rail-split-bottom` 의 `pt-2 md:pt-0` 은 그대로 둔다.** 승격 갈래에서도 이 스택은 여전히
  일자 뒤(모바일) · 위 레일 뒤(데스크톱)라 D11-3 의 근거가 그대로 성립한다. `lg:pt-6` 을
  주면 `SurfaceStack` 의 `md:p-6` 과 겹쳐 48 이 된다.
- **`row 1` 이 준비물 높이만큼 길어진다.** 위·아래 레일 사이 간격이 24 로 남는지 **1280 에서
  다시 잰다** — D11-0-1 의 교훈("걸친 트랙이 있는 grid 는 순서만 보고 회귀 없음이라 적지
  않는다")이 이 절에도 그대로 걸린다.

#### 실측 (구현 후, 10일 초안 · `MOCK_API=true`, 문서 최상단 좌표는 스크롤 보정값)

| 값                            | 390 비승격  | 390 승격    | 1280 비승격 | 1280 승격 |
| ----------------------------- | ----------- | ----------- | ----------- | --------- |
| 위 레일 카드 사이             | 8           | 8 · 8       | 24          | 24 · 24   |
| 위 레일 → 일자 열             | 8           | 8           | —(2열)      | —(2열)    |
| 일자 열 → 아래 레일           | 8           | 8           | —(2열)      | —(2열)    |
| **위 레일 → 아래 레일**       | (일자 사이) | (일자 사이) | **24**      | **24**    |
| 준비물 카드 `top`             | 2394        | 304         | **380**     | **380**   |
| `1일차` `top`                 | 334         | 526         | 118         | 118       |
| `documentElement.scrollWidth` | 390         | 390         | 1280        | 1280      |

- **1280 에서 두 갈래가 픽셀까지 같다.** 준비물 카드가 `row 1` 끝에 붙든 `row 2` 머리에
  오든 `top` 이 **380 으로 동일**하고 `1일차` 도 118 그대로다 — D11-9-3 이 _"좌측 열에서
  읽는 자리가 같다"_ 고 적은 것이 계산된 좌표로 확인된 자리다. 위·아래 레일 간격도 두
  갈래 모두 **24**(위 스택 `md:p-6` 의 아래 24 + 아래 스택 `md:pt-0`)라 새 여백이 없다.
- **행 크기 처방이 살아 있다는 것도 값으로 확인했다.** `grid-template-rows` 를 `auto auto`
  로 되돌리면 같은 간격이 **24 → 543** 으로 벌어진다(두 갈래 모두). D11-0-1 이 적은
  325~523px 구간의 재현이고, e2e #14 가 이 뮤테이션에서 빨개진다.
  단, **일자 열이 좌측 레일보다 길 때만 나타난다** — 3일 일정으로는 `auto` 로 되돌려도
  간격이 24 그대로라 처방이 검증되지 않아, e2e 는 10일 일정으로 잰다.
- **390 에서 승격이 치르는 값은 `1일차` 192px** (334 → 526). 준비물 카드 184 + 스택 간격
  8 이다. 받아들이는 근거는 D11-9 그대로다 — `D-1`·`D-0` 에 이 화면을 연 사람이 찾는 것이
  짐 목록이라, 그 이틀만 일자가 한 카드만큼 내려간다. **가로 넘침은 없다**(`scrollWidth === 390`).

**자리가 화면 안에서 옮겨 다니지 않는다.** `today` 는 서버가 정해 prop 으로 내려오므로 한
번 그려진 화면에서 갈래가 뒤집히지 않는다 — `PlanPackingList` 가 언마운트·재마운트될 일이
없다. 자정을 넘겨 열어 둔 화면은 다음 내비게이션에서 새 `today` 를 받는데, 그때 재마운트가
나도 목록은 서버에 저장돼 있어(#586) 잃는 것이 없다.

### D11-9-5. 문구 · 접근성

- **새 문구가 없다.** 승격을 알리는 배지·설명을 붙이지 않는다 — **순서 자체가 신호다.**
  배지를 붙이면 `D-1` 을 말하는 자리가 개요 배지와 준비물 카드 둘이 되고, 진입점을 하나로
  모아 온 D11-2 와 반대로 간다. 카드 제목은 `여행 준비물`(`messages.plan.packingHeading`)
  그대로다.
- **DOM 순서 = 읽는 순서를 지킨다.** 승격 갈래에서도 탭 순서와 스크린리더 순서가 눈에 보이는
  순서와 같다 (D11-6 과 같은 원칙).
- **개요의 `일자별 판정` 목차와 일자 카드 사이에 준비물이 끼어든다.** 목차는 앵커라 거리와
  무관하게 닿으므로 끼어드는 것이 문제가 되지 않는다.
- 승격 여부로 **포커스를 옮기지 않는다.** 화면을 열었을 때 자리가 다를 뿐이고, 자동으로
  준비물로 스크롤하거나 포커스를 주면 사용자가 요청하지 않은 이동이 된다.

### D11-9-7. 범위 밖

- **준비물 카드의 내용·AI 생성 흐름·계약.** 생성 버튼, 체크, 직접 추가·삭제,
  `GET /plans/{planId}/packing-items` 는 손대지 않는다. **순서만 바꾼다.**
- **후기·배너는 승격 대상이 아니다.** 후기는 다녀온 뒤의 것이고 배너는 상시 진입점이라 둘 다
  D-day 와 무관하다 (테스트 #12 가 잠근다).
- **데스크톱 레일의 보이는 순서** — D11-8 그대로 바꾸지 않는다.
- **홈·일정 목록의 순서.** 이 승격은 일정 상세 한 화면의 규칙이다.
- **출발 당일 오전/오후 구분** — D11-9-8 미결 1.

### D14-1. 계약 — 이미 오고 있고, 이미 저장된다

| 항목      | 값                                                                         |
| --------- | -------------------------------------------------------------------------- |
| 조회      | `PlanItemDetailItem.startTime` — `LocalTime`, **nullable**                 |

  - 받는 쪽을 넓힌 것은 임시 조치가 아니라 **계약이 응답 형식을 약속하지 않았기 때문**이다.

### D15-2. 등급 코드 — 적합도와 **다른 체계**다

| 축          | 코드                                     |
| ----------- | ---------------------------------------- |
| 여행 적합도 | `HIGH` `MEDIUM` `LOW` **`INSUFFICIENT`** |

`_index.md` 하단 "명세와 실제 계약이 갈린 곳" 이 기록한 그대로다 — **한 매퍼로 묶지 않는다.**
`lib/insight/tone.ts` 의 **`walkSafetyTone()` 을 그대로 쓴다** (새로 만들지 않는다).

- **`DANGER` 가 `critical` 을 쓰는 유일한 축이다.** 적합도가 낮은 것은 오류가 아니지만

### D15-3. 배지를 붙일 행의 조건 — **서버가 이미 갈랐다**

**FE 가 조건을 다시 만들지 않는다.** 서버가 네 단계로 가른 결과가 `unavailableReasonCode` 로
내려온다 (`PlanWalkSafetyProcessor.java:105-124`). 화면이 `startTime !== null && place !== null`
같은 자기 조건을 세우면 **서버 판정과 두 갈래가 생기고**, 순서까지 다르면(서버는 `PAST_DATE`
를 장소 여부보다 **먼저** 본다) 같은 항목을 두 화면이 다르게 설명한다.

```text
배지를 세운다  ⟺  walkSafetyLevel !== null  그리고  code !== 'UNKNOWN'
````

서버가 실제로 가르는 순서 (바꾸지 않는다):

| 순서 | 조건                                 | 코드                    |
| ---- | ------------------------------------ | ----------------------- |
| 1    | 그 일차 날짜 < 오늘                  | `PAST_DATE`             |
| 2    | 장소 항목이 아니거나 `targetId` 없음 | `NOT_PLACE_TARGET`      |
| 3    | `startTime === null`                 | `NO_START_TIME`         |
| 4    | 날짜 > 오늘+4                        | `BEYOND_FORECAST_RANGE` |
| —    | 물어봤는데 실패                      | `LOOKUP_FAILED`         |

- **지난 날짜가 가장 먼저다.** 무엇을 고쳐도 풀리지 않는 사유라 "시각을 넣어 보세요" 를 먼저
  말하면 지켜지지 않을 안내가 된다 (enum 주석).
- **시각별 예보 지평은 `오늘 ~ 오늘+4`(5일)** 이고 **일자 날씨의 11일과 다르다**
  (`HOURLY_FORECAST_HORIZON_DAYS = 4`). 노면온도를 `기온 + 일사(날짜·시각·위도)` 로 추정해야
  해서 시각별 데이터가 있는 단기예보만 쓰기 때문이다. **같은 일정에서 `/weather` 에는 판정이
  있는데 여기는 비어 있는 날이 정상이다** — 화면이 둘을 나란히 두므로 반드시 알고 그린다.
- **5일 · 11일 숫자를 화면에 베껴 쓰지 않는다.** 서버 상수다. 그 값이 들어간 문장은
  `unavailableReason` 으로 온다 (D15-4).

### D15-4. 사유별 갈래 — 숨김 / 서버 문장 / 재시도

있으면 서버 문장을 그대로 쓴다.

| ----------------------- | -------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `NO_START_TIME`         | **숨김**                                           | —              | 시각이 없으면 **시각 줄 자체가 없다** (D14-3). 위험도가 설 자리가 함께 사라진다                                        |
| `NOT_PLACE_TARGET`      | **숨김**                                           | —              | `WALK`·`MOVE` 는 화면이 이미 안다. 이동 행마다 같은 문장이 서면 배경음이 된다                                          |
| `PAST_DATE`             | **숨김**                                           | —              | 일자 판정이 `verdictPastDate` 를 **일자 단위로 한 번** 이미 말한다. 항목마다 되풀이하면 완료 일정이 그 문장으로 덮인다 |
| `BEYOND_FORECAST_RANGE` | **서버 문장 그대로**, 일자 카드에 **한 줄**        | 일자 판정 아래 | 문장에 서버 상수(5일)가 들어 있어 화면이 베끼면 갈린다. `byDate` 가 **날짜만으로** 가르므로 그 일자 전부가 같은 사유다 |
| `LOOKUP_FAILED`         | **서버 문장 그대로 + `다시 시도`**                 | **그 행 아래** | 다섯 중 **유일한 일시 장애**다. 감추면 아무도 못 알아챈다                                                              |
| `UNKNOWN` 등급          | **배지 없이 `walkSafetyLevel.description` 그대로** | 시각 줄        | D15-5                                                                                                                  |
| 모르는 코드             | **서버 문장 그대로**, 그 행 아래                   | 그 행 아래     | 서버가 사유를 늘려도 이 갈래가 받는다 (#497 의 `default` 와 같다)                                                      |

- **숨김 셋에는 문구를 만들지 않는다.** "정보 없음" 배지도 두지 않는다 — 이슈가 요구한
  _"없는 판정을 위험으로 말하지 않는다"_ 는 **회색 배지를 세우지 않는다**는 뜻이기도 하다.
  회색이라도 배지는 판정한 자리에 선다.
- **`BEYOND_FORECAST_RANGE` 를 일자 단위로 접는 것이 이 절의 계산이다.** 항목마다 내면 5일 뒤
  여행의 모든 행에 같은 문장이 붙는다. 서버 판정이 **날짜만의 함수**라 접어도 잃는 것이 없다.
  **그 일자에 항목이 하나라도 있을 때만 낸다.**
- **`LOOKUP_FAILED` 의 재시도는 `planKeys.walkSafety(planId)` 재조회다.** 항목 단건 API 가
  없다. `placeId` 가 남아 있어 `GET /places/{placeId}/walk-safety` 를 직접 부를 수도 있지만
  **응답 모양이 달라** 그 행만 다른 타입으로 그리게 된다 — 범위 밖 (D15-9).
- 사유 코드는 **`string` 으로 타이핑한다.** union 으로 좁히면 서버가 사유를 늘렸을 때
  타입 오류가 되고, 화면이 서버 문장으로 물러설 수 없다 (`unavailableReasonCode` 선례).

### D15-5. 표시 — D14 의 시각 줄에 붙는다

```text
[썸네일]  10:30 · [산책 주의] · 체감온도 33.5℃      ← D14 의 시각 줄
 ①       천지연폭포  [식사]
          제주 서귀포시 … · 실내
          이전 장소에서 직선 4.1km
```

- **제목 위 캡션 한 줄**이다(`text-caption` · `text-fg-muted` · `tabular-nums`).
- **제목 줄에 넣지 않는다.** D11-5 가 `✓` 버튼에 글자를 주면서 제목 폭을 390 에서 **30px**
  깎았고(`오설록 티뮤지엄 카페` 가 2줄로 접힌다), 같은 줄에 시각을 또 얹으면 그 손실이 겹친다.
- **메타 줄(`주소 · 실내`)에 합치지 않는다.** 그 줄은 `line-clamp-1` 이라 시각을 앞에 붙이면
  **주소가 먼저 잘린다.** "언제" 와 "어디" 는 축이 다르기도 하다.
- **`sequence` 정렬을 시각으로 다시 하지 않는다.** 순서의 정본은 `sequence` 이고 서버도 그것으로
  내려 준다. 화면이 시각으로 재정렬하면 **저장된 순서와 보이는 순서가 갈리고**, 그 상태에서
  `순서 편집` 을 열면 사용자가 본 적 없는 배열이 나온다.
- **시각이 순서와 어긋나도 경고하지 않는다** (D14-8 미결 2). 서버가 막지 않는 값이고,
  경유·되돌아오기가 실제로 있는 일정이다.

**형식** — `HH:mm` 24시간제. 초는 버린다.

- **`오후 2시` 로 쓰지 않는다.** 일정표는 세로로 여러 줄이 겹치는 자리라 `tabular-nums` 로
  자릿수가 맞아야 훑을 수 있고, 오전/오후 접두는 그 정렬을 깬다.
- **정규화는 순수 함수 하나가 한다** — `lib/plan/start-time.ts` 의 `formatStartTime()`.
  `^(\d{2}):(\d{2})` 로 앞 두 칸만 읽고 나머지는 버린다. **`slice(0, 5)` 를 쓰지 않는다** —
  모양이 어긋난 값(`"오전 10시"` · `""`)을 조용히 잘라 **없는 시각을 지어낸다.**
- 정규화에 실패하면 **`null` 이고, 줄은 렌더되지 않는다.** 에러도 배지도 내지 않는다 —
  "시각 미상" 같은 자리를 만들면 시각이 없는 대다수 항목이 전부 그 문구를 이고 선다.

**접근성** — 숫자만 읽히면 무슨 숫자인지 알 수 없다.

```html
<p><span class="sr-only">시작 시각 </span><time datetime="10:30">10:30</time></p>
```

- `<time datetime>` 에는 **정규화된 `HH:mm`** 을 넣는다(서버 원문이 아니다).
- 이 줄은 링크 안에 있다 — 새 상호작용을 만들지 않으므로 D6 의 "링크 안에 링크 없음" 이
  그대로 유지된다.

### D14-4. 이 줄이 #625 의 자리다

[#625](https://github.com/8llow8llowMe/hondigagae/issues/625) 의 항목 산책 위험도 배지는 **이 시각 줄에 붙는다** (D15). 그래서 배지가
설 조건 중 하나(`시각 있음`)가 줄의 존재 여부와 **같은 값**이 되고, 시각이 없는 항목에서는
위험도 자리도 함께 사라진다 — 없는 판정을 빈 배지로 말하지 않는 가장 싼 방법이다.

**이 이슈에서는 배지를 넣지 않는다.** 줄의 자리와 정규화 함수만 세운다.

### D14-5. 일괄 교체가 시각을 지운다 — 되싣기 테스트를 유지하는 이유

`PUT …/days/{day}/items` 는 **부분 수정이 아니다**(E1). 요청 항목에 `startTime` 키가 없으면
서버는 "유지" 가 아니라 **`null` 로 새로 저장**한다 (`PlanCommandProcessor.java:295`→`:407`).
그래서 `lib/plan/day-items.ts:110` 의 되싣기가 지금 시각을 지키고 있다.

```ts
...(item.startTime === null ? {} : { startTime: item.startTime }),
```

**이 이슈에서 다음 테스트를 지우거나 느슨하게 고치지 않는다.**

| 파일                                        | 테스트                                                 |
| ------------------------------------------- | ------------------------------------------------------ |
| `lib/plan/day-items.test.ts:123`            | `memo · startTime · itemType 을 그대로 되돌려 싣는다`  |
| `lib/plan/day-items.test.ts:146`            | `memo · startTime 이 null 이면 키를 넣지 않는다`       |
| `lib/plan/day-items.test.ts:231`            | 담기 경로에서도 되싣는 항목의 `startTime` 이 살아 있다 |
| `lib/api/mock/plan-detail-mock.test.ts:341` | `memo · startTime 이 보존된다`                         |

**유지하는 이유가 이 이슈에서 한 단계 세졌다.** 예전에는 "화면에 안 보이는 값이 조용히
지워진다" 였고, 그것만으로도 회귀는 조용했다. 이제는 **보이던 줄이 사라진다** — 순서만 바꿨는데
시각이 통째로 없어지는 것을 사용자가 즉시 본다. 게다가 편집이 시각을 쓰기 시작하면
`toPayloadItem` 이 **저장된 값이 아니라 편집값**을 싣게 바뀌므로(G3), 되싣기 경로가 손을 타는
바로 그 이슈에서 안전망을 걷는 셈이 된다.

**`null` 이면 키를 뺀다는 규칙도 그대로다.** 일괄 교체에서는 키 생략이 곧 "비운다" 라서,
시각 지우기가 이 규칙 위에서 성립한다 (G3) — `PUT /plans/{planId}`(부분 수정, 키 생략 = 유지)와
**반대**다. 같은 화면에 두 규칙이 있으므로 문서와 테스트로 못박는다.

### D14-6. 시각을 지우는 다른 경로 둘 — 화면이 먼저 말한다

| 경로               | 무슨 일이 일어나나                                                                               |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| **하루 재생성**    | 초안에 시각이 없어(`AiPlanScheduleItem` 에 시각 필드 자체가 없다) **그 날 시각이 전부 사라진다** |
| **일괄 교체 일반** | 되싣기가 지킨다. 다만 D9-2 대로 **방문 체크는 초기화된다**                                       |

**하루 재생성 경고 문구를 D9-2 경고에 합친다.** `lib/ai-plan/regenerate.ts` 의
`toRegeneratedDayItems` 는 `toDraftItems` 를 거치므로 재생성된 일자에는 시각이 하나도 실리지
않는다. 지금 재생성 확인 대화상자는 방문 체크만 말한다.

| 조건                                     | 문구 (확정)                                              |
| ---------------------------------------- | -------------------------------------------------------- |
| 그 일자에 시각 있는 항목이 **있을 때만** | `다시 만들면 이 날에 적어 둔 시작 시각도 함께 사라져요.` |

- **잃을 것이 없는 날에는 내지 않는다** — D9-2 가 방문 체크 경고에 세운 것과 같은 규칙이다.
  늘 뜨는 경고는 배경음이 되어 정작 잃을 날에 읽히지 않는다.
- **순서 편집·장소 담기에는 이 경고를 달지 않는다.** 그쪽은 되싣기가 시각을 지킨다 — 지키는
  경로에 경고를 달면 사용자가 안전한 조작을 피하게 된다.

### D13-1. `petIds` 의 세 가지 의미 — 이 기능의 함정

`PUT` 은 부분 수정이다(D4). `petIds` 도 같은 규칙을 따르지만 **"비운다"가 없다.**

| 보낸 값               | 서버 해석                                          | 근거                                |
| --------------------- | -------------------------------------------------- | ----------------------------------- |
| **키 자체를 안 보냄** | 기존 동행견 **유지**. 소유 검증도 부르지 않는다    | `PlanWebFacade.java:111-112`        |
| `petIds: null`        | 위와 같다 — `null` 이 곧 "유지"다                  | `PlanUpdateRequest.java:65`         |
| `petIds: [a, b]`      | **목록 전체 교체.** 첫 번째가 대표(`plan.pet_id`)  | `PlanCommandProcessor.java:225,244` |
| `petIds: []`          | **400 `PLAN_010`.** 생성과 달리 대표견 폴백이 없다 | `PlanCommandProcessor.java:188-190` |

- **생성과 다른 지점이 하나다.** `PlanCreateRequest.effectivePetIds()` 는 빈 목록을 대표 반려견으로
  대신하지만(`PlanCreateRequest.java:88-93`), 수정에서 그렇게 하면 _사용자가 지우려던 아이가 말없이
  돌아온다._ 그래서 거절이다 (`PlanUpdateRequest.java:18-21`).
- **중복은 서버가 접는다** — 순서를 지키며 `distinct`. 화면이 중복을 만들 경로는 없다(체크박스).
- **한 마리여도 배열이다.** 생성·AI 와 같은 규칙이고(`다견선택-세부명세.md` D2-2), 여기서만 단건
  필드를 쓰면 "1마리는 `petId`, 2마리는 `petIds`" 분기가 또 생긴다. `petId` 는 **수정 요청에 아예 없다.**
- **`Number()` 를 거치지 않는다.** 요청 스키마는 `int64` 지만 FE 는 응답이 준 **문자열 그대로** 싣는다
  — Snowflake 라 숫자로 바꾸면 정밀도를 잃는다 (`lib/ai-plan/submit.ts:22-23` 과 같은 규칙, Jackson 이
  문자열을 `Long` 으로 받는다). 상한 5는 요청 배열 길이이고, **응답** `petIds` 는 문자열 배열이다.

**오류 표**

| 코드       | HTTP | 언제                            | 화면 처리                                                                                                                                |
| ---------- | ---- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `PLAN_010` | 400  | 빈 배열                         | **화면이 먼저 막는다** — 빈 배열은 실리지 않는다. 있던 동행견을 전부 해제하면 검증이 막고, 0마리로 열린 폼은 키 자체를 안 싣는다 (D13-5) |
| `PLAN_011` | 400  | 내 소유가 아닌/없는 아이가 섞임 | 폼 배너 + `petKeys.list()` 무효화 (목록이 낡았다는 신호)                                                                                 |
| `PLAN_019` | 400  | 이미 완료된 일정                | 폼 배너 + `planKeys.detail` 무효화 (다른 탭에서 완료됐다)                                                                                |
| `PLAN_115` | 400  | 6마리 이상                      | 화면이 만들 수 없다 — 2차 방어 (`fieldErrors.petIds` 로 온다)                                                                            |
| `PLAN_101` | 400  | 원소가 `null`·음수              | 화면이 만들 수 없다 — 2차 방어                                                                                                           |

`PLAN_115` 는 **필드 검증**이라 `fieldErrors[].field === 'petIds'` 로 오고
`apiErrorToFormErrors` 가 그룹 오류로 붙인다 (`ValidationErrorSupport.java:87` — `FieldError.getField()`).
**원소 검증(`PLAN_101`)은 `petIds[0]` 처럼 인덱스가 붙을 수 있어** 그룹에 매칭되지 않고 배너로
떨어질 수 있다 — 화면이 만들 수 없는 값이라 그대로 둔다. `PLAN_010`·`PLAN_011`·`PLAN_019` 는 **도메인 예외**라
`fieldErrors` 가 없고 같은 함수가 **폼 배너**로 올린다 — `PLAN_008` 과 같은 갈래다(D4 기간 수정).
**서버 문구를 FE 말투로 옮기지 않는다.**

### D13-2. 자리 — 이름·기간·예산과 같은 모달

`PlanEditModal` 안이다. 새 모달·새 화면을 만들지 않는다.

| 항목      | 규칙                                                                                            |
| --------- | ----------------------------------------------------------------------------------------------- |
| 진입      | 개요 카드 `⋯` → 수정 (`PlanManageMenu`). **메뉴 항목을 늘리지 않는다**                          |
| 필드 순서 | 제목 → **기간** → 기간 힌트 → **동행 반려견** → 예산                                            |
| 컨트롤    | 체크박스 그룹 (`RadioGroup` 아님)                                                               |
| 옵션      | `usePetList` 결과 전체. 정렬은 목록 응답 순서 그대로 — 화면이 다시 정렬하지 않는다              |
| 초기 선택 | `plan.petIds` 중 **옵션에 있는 것만**, `plan.petIds` 순서 유지 (`companionPetsOf` 와 같은 규칙) |
| 옵션 라벨 | 반려견 이름 / 보조 설명 `describePet(pet)` (`말티즈 · 4살`) — AI 조건 폼과 같은 조합            |
| 상한 안내 | **말하지 않는다.** 회원당 반려견이 5마리 상한(`messages.pet.limitReached`)이라 전부 골라도 5다  |

- **기간 바로 아래다.** 만들기 폼이 `기간 → 반려견` 순서로 묻도록 #400 이 맞춰 뒀다
  (`features/plan/form-order.test.ts`). 수정 모달만 반려견을 예산 뒤로 보내면 같은 서비스가 두 순서를
  갖는다. 모달은 세로로 스크롤되므로 그룹이 길어져도 예산이 잘리지 않는다.
- **반려견 목록은 prop 으로 받는다.** `PlanDetailView` 가 이미 `usePetList(true)` 로 읽어
  `PlanDetailSection` 에 `pets` 로 내려주고 있다 — 모달이 훅을 또 붙이면 그 화면이 `authed` 를
  알아야 하고(`use-pet-list.ts` 가 필수 인자로 강제한다) 렌더 테스트도 무거워진다.
  경로는 `PlanDetailSection` → `PlanManageMenu` → `PlanEditModal` 이다.
- **옵션이 0개면 그룹 자체를 렌더하지 않는다.** 반려견이 없는 회원과 **목록 조회가 실패한 경우**가
  같은 모양이 된다 — 둘 다 "고를 수 없다" 이고, D5 의 _반려견 조회 실패 → 카드만 빠진다_ 와 같은
  태도다. 이때 나머지 필드(이름·기간·예산)는 **그대로 저장된다.**

### D13-3. 완료된 일정에서는 컨트롤을 숨긴다

| 상태                  | 동행견 그룹 | 메뉴 항목 문구               |
| --------------------- | ----------- | ---------------------------- |
| `DRAFT` · `CONFIRMED` | 보인다      | `이름·기간·예산·동행견 수정` |
| `COMPLETED`           | **없다**    | `이름·기간·예산 수정`        |

- 서버가 `PLAN_019` 로 거절한다(`PlanCommandProcessor.java:218-220`). 누를 수 있는 컨트롤을 두고
  저장에서 되돌려 보내는 것은 화면이 거짓말을 한 것이다.
- **메뉴 문구를 상태로 가른다.** #585 가 기간을 열면서 문구에 `기간` 을 넣은 근거가
  _"메뉴 항목은 안에서 무엇을 고칠 수 있는지로 읽힌다"_ 였다. 완료 일정에서 `동행견` 이 적힌 항목을
  열었는데 그 컨트롤이 없으면 같은 근거가 반대로 깨진다. 메시지 키를 둘로 둔다.
- **완료에서 "왜 없는지" 를 말하지 않는다.** 그 화면은 확정/완료 버튼·순서 편집까지 이미 걷힌
  상태다. 여기서만 부재를 설명하면 어긋난다. 바꿔야 하면 `확정으로 되돌리기` 가 경로다(D11-2).
- **같은 요청으로 완료하면서 바꾸는 것은 서버가 막지 않는다**(`completesNow` 전이). 그 경로는
  이 화면에 없다 — 수정 모달은 `status` 를 **보내지 않는다**(`lib/plan/edit.ts` `toPlanUpdatePayload`).

### D13-4. 무엇을 보내는가 — 바뀌지 않았으면 `petIds` 를 넣지 않는다

```ts
// lib/plan/edit.ts — 변환은 여기 한 곳에서만 한다 (form-guide.md §5)
type PlanEditValues = {
  title: string
  startDate: string
  endDate: string
  budget: string
  /** 체크 순서. **첫 번째가 대표**다 */
  petIds: string[]
}

toPlanUpdatePayload(values, { petsEditable: boolean; initialPetIds: readonly string[] })
```

| 조건                                       | payload 의 `petIds` |
| ------------------------------------------ | ------------------- |
| `petsEditable === false` (완료 · 옵션 0개) | **키 없음**         |
| 초기 선택과 **순서까지** 같다              | **키 없음**         |
| 그 외                                      | `string[]` 그대로   |

- **기간과 반대 규칙이다.** 기간은 _생략이 "유지"_ 라 **바뀌지 않았어도 둘 다 보낸다**(D4) — 한쪽만
  보내면 서버가 옛 값과 섞어 다시 계산하기 때문이다. `petIds` 는 섞일 값이 없고, 같은 목록을 다시
  보내면 서버가 `plan_pet` 을 **지웠다 다시 넣는다**(`PlanCommandProcessor.java:246-247`). 얻는 것이
  없는 쓰기다.
- **순서만 바뀌어도 보낸다.** 첫 번째가 대표라 순서가 값이다.
- **완료 일정에서 키가 새면 `PLAN_019` 다.** 제목만 고치려던 저장이 400 으로 죽는다. 그래서
  "컨트롤을 숨긴다" 를 화면이 아니라 **페이로드 변환에서도 한 번 더** 잠근다.
- **삭제된 아이의 잔여 id 는 정리하지 않는다.** 초기 선택을 _옵션에 있는 것만_ 으로 거르므로,
  `plan.petIds` 에 삭제된 아이가 남아 있어도 "변경 없음" 이면 키가 실리지 않는다. 화면 어디에서도
  그 id 는 보이지 않고(`companionPetsOf` 가 뺀다), 조용히 지우는 저장은 사용자가 요청한 적 없는
  변경이다. → D13-10 미결 2.

### D13-5. 검증 — 0마리는 화면이 먼저 막는다, **단 "빼는 것" 일 때만** (#752 에서 갱신)

`validatePlanEdit` 에 한 갈래를 더한다. **`petsEditable` 일 때만 본다.**

| 판정       | 메시지                                                                      |
| ---------- | --------------------------------------------------------------------------- |
| 0마리      | `messages.plan.errorPetRequired` (`반려견을 골라 주세요.` — 기존 키 재사용) |
| 6마리 이상 | 만들 수 없다 (옵션이 최대 5개). 서버 `PLAN_115` 가 2차 방어                 |

오류는 **그룹(`fieldset`)에 붙는다** — `fieldErrorId('planEditPetIds')` 를 `aria-describedby` 로,
`aria-invalid` 는 `fieldset` 에만 (`component-guide.md` §7, `RadioGroup` 과 같은 배선).

#### 0마리를 언제 막는가 — **시작 상태와 조작을 가른다**

처음 규칙은 "0마리면 무조건 막는다" 였는데, 그러면 **동행견이 전부 삭제된 일정은 제목조차 고칠 수
없다.** 초기 선택은 옵션에 있는 것만 남으므로(D13-4) 그런 일정은 **0마리로 열리고**, 회원에게 다른
반려견이 남아 있으면 `petsEditable` 이 `true` 라 이 검증에 걸린다.

그래서 조건에 `initialPetIds` 를 더한다 — **0마리가 사용자의 조작인가, 폼이 열린 상태인가**.

| 초기 선택 | 지금 선택  | 판정                                                               |
| --------- | ---------- | ------------------------------------------------------------------ |
| 있음      | 0마리      | **막는다.** "동행견을 모두 빼겠다" 는 조작이고 서버가 `PLAN_010`   |
| 0마리     | 0마리      | **막지 않는다.** 조작이 아니라 시작 상태다 — 막으면 영영 못 고친다 |
| 0마리     | 1마리 이상 | 통과. 사용자가 스스로 고치는 경로다                                |

**서버는 이미 정상이다.** `petIds` 키가 없으면 소유 검증조차 부르지 않고(`PlanWebFacade.java:111-112`),
`toPlanUpdatePayload` 의 0마리 갈래가 이미 키를 만들지 않는다. **FE 검증 한 갈래만 고치면 닫힌다 —
서버 계약은 그대로다.**

> 이 경계를 처음 열어 둘 때는 서버 `PLAN_010` 이 원인이라고 적었는데, #720 조사에서 **실제 차단
> 지점이 이 검증**임이 확인됐다. 서버에서 빈 배열을 허용해도 증상은 고쳐지지 않는다.

#### 문구 — 막지 않는다는 사실을 같은 자리에서 말한다

0마리로 열린 폼에 `editPetsHint`(`먼저 고른 아이가 대표예요.`)만 서 있으면 _"골라야 저장되나"_ 로
읽힌다. 검증은 막지 않는데 화면이 반대로 말하는 셈이다.

| 조건                             | 문구                                |
| -------------------------------- | ----------------------------------- |
| 초기 0마리 **그리고** 지금 0마리 | `messages.plan.editPetsClearedHint` |
| 그 외                            | `messages.plan.editPetsHint` (기존) |

하나라도 고르면 대표가 생기므로 곧바로 기존 힌트로 돌아온다. 분기는 `planEditPetsHint` 가 진다 —
모달은 `useQueryClient` 때문에 node 환경에서 렌더되지 않아(`testing-guide.md` §1), 분기를 순수
함수로 내려야 테스트로 잠글 수 있다.

**`required`(별)도 같은 조건에 건다.** 검증이 더 이상 필수를 요구하지 않는데 별만 서 있으면 화면이
없는 제약을 있다고 말한다. `CheckboxGroup` 의 `required` 가 렌더하는 것은 `legend` 의 별뿐이고
`aria-invalid`·`aria-describedby` 는 `error` 가 배선하므로(`component-guide.md` §7) 접근성 배선은
이 분기에 영향받지 않는다.

### D13-6. 저장 뒤 — 화면이 판정을 다시 계산하지 않는다

**서버도 다시 계산하지 않는다.** `updatePlan` 은 `plan_pet` 만 맞추고 판정·준비물에 손대지 않으며,
_"다음 조회가 새 `petIds` 를 읽는다"_ 가 그 결정이다 (`PlanCommandProcessor.java:199-201`).
그래서 화면이 할 일은 **다시 읽는 것**뿐이다.

| 캐시 키                      | 처리                      | 이유                                                                                     |
| ---------------------------- | ------------------------- | ---------------------------------------------------------------------------------------- |
| `planKeys.detail(planId)`    | `setQueryData` (PUT 응답) | `PUT` 이 `PlanDetailResponse` 를 돌려준다 — 새 `petId`·`petIds` 가 그 안에 있다          |
| `planKeys.list()`            | invalidate                | 목록 행의 동행 요약과 반려견 필터 건수가 `petIds` 로 만들어진다 (`lib/plan/list.ts:109`) |
| `planKeys.weather(planId)`   | invalidate                | `basisPetId`·`petSuitabilities`·`indoorAlternatives` 가 **전부 동행견 기준**이다         |
| `planKeys.packing(planId)`   | **버리지 않는다**         | 서버가 저장된 준비물을 지우지도 다시 만들지도 않는다 — 같은 응답이 다시 올 뿐이다        |
| `planKeys.review(planId)`    | 건드리지 않는다           | 완료 전용인데 완료에서는 동행견을 못 바꾼다                                              |
| `planKeys.emergency(planId)` | 건드리지 않는다           | 위치 기반이다 — `PlanEmergencyProcessor` 에 반려견 참조가 없다                           |
| `petKeys.*`                  | 건드리지 않는다           | 반려견 자체는 바뀌지 않았다 (예외: `PLAN_011` 실패 시 목록 무효화, D13-1)                |

`weather` 무효화는 **지금도 무조건** 일어난다(`plan-edit-modal.tsx:97`, #585). 동행견 수정이 그
근거를 하나 더 얹는 것이라 코드가 늘지 않는다.

**말하는 것은 한 줄이다.** 모달은 성공하면 닫히므로 폼 안에 적으면 읽히지 않는다 — 토스트로 알린다
(`components/toast.tsx`: _끝난 일을 알린다_).

## D17. 관리 메뉴에 일정 복사 진입점 (이슈 [#617](https://github.com/8llow8llowMe/hondigagae/issues/617))

> **정본은 `docs/features/plan/일정복사-세부명세.md` 다.** 이 절은 **상세 화면이 지는 몫**
> — 메뉴 항목 하나와 그 노출 조건 — 만 적는다.
>
> **계약 확인 근거**: dev Swagger 실호출 `GET https://api-dev.hondigagae.com/plan-service/v3/api-docs`
> (2026-09-18, `POST /api/v1/plans/{planId}/copy` 존재 확인) + backend 소스 실측
> `PlanWebController.java:82-93` · `PlanCopyRequest.java:11-26` · `PlanCommandProcessor.java:97-137`
> (`origin/develop` `2b0b62a4`, 복제 구현 `064c28e4`). 로컬 게이트웨이는 미기동이라 실호출
> 대조는 못 했다.

### D17-1. 메뉴 항목 — `이 일정 복사하기`

`PlanManageMenu` 의 `items` 에 한 줄을 더한다. **새 트리거를 만들지 않는다** — 이 화면에
관리 진입점은 개요 패널 우측 상단의 `⋯` 하나다 (D11-2).

```text
이름·기간·예산 수정
이 일정 복사하기      ← 신규 (조건부)
(초안으로 되돌리기 / 확정으로 되돌리기)
───────────────────
일정 삭제
```

- **`수정` 다음, 역방향 상태 항목보다 위.** 복사는 *이 일정*을 바꾸지 않고 새 일정을
  만든다. 아래 두 묶음(상태를 바꾼다 / 이 일정을 지운다)은 모두 이 일정에 손대는 항목이라,
  손대지 않는 항목을 그 위에 둔다.
- **선 아래로 내리지 않는다.** 선 아래 `danger-900` 자리는 파괴적 항목 전용이고
  (`DESIGN.md` §2-6) 복사는 파괴적이지 않다.
- `status.saving` 으로 잠그지 않는다 — 상태 저장 중에도 복사는 별개의 API 다.

### D17-2. 보이는 조건 — 지난 **또는** 완료

| 일정                                              | 항목       | 근거                                                            |
| ------------------------------------------------- | ---------- | --------------------------------------------------------------- |
| 종료일 < 오늘 (`isPastPlan(plan.endDate, today)`) | **보인다** | 이슈 대상이 "지난 일정" 이다                                    |
| `plan.status.code === 'COMPLETED'`                | **보인다** | 다녀온 여행이다. 날짜가 아직 안 지났어도 뜻이 같다              |
| 여행 중 · 다가오는 초안/확정                      | **숨는다** | 아직 다녀오지 않은 일정을 복사하면 같은 기간 중복 초안이 생긴다 |
| 날짜를 못 읽는 데이터 (`planPhaseOf === null`)    | **숨는다** | 지난 쪽으로 밀지 않는다 (`lib/plan/date.ts:86` 과 같은 판단)    |

- 판정은 순수 함수 하나(`lib/plan/copy.ts` 의 `canCopyPlan(plan, today)`)가 갖는다.
- **`today` 는 이미 이 컴포넌트가 받고 있다** (`plan-manage-menu.tsx:62`, `PlanEditModal`
  에 넘기는 값과 같다). 클라이언트에서 `new Date()` 를 새로 부르지 않는다 — 자정 근처에서
  SSR 과 갈린다.
- **서버는 상태를 가리지 않는다** (`copyPlan` 에 `status` 검사가 없다). 이 제한은 화면의
  판단이고, 넓히자는 결정이 나면 `canCopyPlan` 한 곳만 고친다.

### D17-3. 이 절이 지지 않는 것

- **항목 행에는 그 제목이 없다.** 시각과 장소 이름 사이에 낀 `주의` 는 무엇이 주의인지 말하지
  않고, 스크린리더는 `10:30 주의 천지연폭포` 로 읽는다.
- 그래서 `messages.common.metricAxisWalkSafety = '산책'` 을 **더한다.** 기존 두 호출부는
  건드리지 않는다 — 같은 축이라도 자리마다 축이 서 있는지가 다르다.
- `적합도`·`혼잡도` 와 달리 `-도` 형이 아닌 이유: `산책도 주의` 는 말이 되지 않는다.
  `산책 안전` · `산책 주의` · `산책 위험` 세 값 모두 문장이 선다.

**체감온도** — `장소 상세와 라벨 규칙을 맞춘다`

| 라벨            | 값                        | 기준                        |
| --------------- | ------------------------- | --------------------------- |
| `체감온도`      | `feelsLikeCelsius`        | **시각** (`targetDateTime`) |
| `최고 체감온도` | `maxFeelsLikeTemperature` | 하루 최대                   |
| `최고기온`      | `maxTemperature`          | 하루 최대 (폴백)            |

- **이 자리는 `체감온도`(시각 기준)다.** `screen-inventory.md` §3-1 의 표 그대로이고,
  `lib/insight/temperature.test.ts` 가 네 문구를 한자리에서 고정한다.
- **같은 일자 카드에 기준이 다른 체감온도 둘이 선다** — 일자 판정의 `최고 체감온도 27.5℃`
  (하루 최대)와 항목 행의 `체감온도 33.5℃`(14:00). **그것이 정상이고, 라벨의 `최고` 유무가
  기준을 가른다.** 이 구분이 무너지면 사용자는 서로 다른 값으로 읽는다.
- **`displayTemperature()` 를 쓰지 않는다.** 그 함수는 `maxFeelsLikeTemperature` →
  `maxTemperature` 폴백을 고르는 **하루 단위** 규칙이다. 여기서는 `feelsLikeCelsius` 하나뿐이고
  **폴백이 없다** — `null` 이면 그 조각을 뺀다.
- **단위 `℃` 를 반드시 붙인다** (`formatCelsius`).

**행에 두지 않는 것 셋**

| 값                         | 이유                                                                                                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `estimatedPavementCelsius` | 서버 스키마가 _"'노면(아스팔트)' 를 밝히고 `temperature` 와 나란히 보여 주세요"_ 를 요구한다 — 행에 온도 셋을 세울 폭이 없고, 노면온도만 내면 **사용자가 기온으로 읽는다** (스키마가 직접 경고한 오독) |
| `temperature`              | 위와 짝이다. 둘은 함께 서거나 함께 빠진다                                                                                                                                                              |
| `saferWindowStart/End`     | 줄이 하나 더 늘고, 같은 값이 장소 상세에 완전한 형태로 있다 (#197)                                                                                                                                     |

**셋 다 장소 상세로 보낸다** — 행 전체가 이미 `/places/{placeId}` 링크이고, 그쪽에는 체감온도
hero · 근거 서랍 · 참고 열지수가 이미 있다.

**폭** — 390 에서 시각 줄은 썸네일(80) + gap(12)을 뺀 나머지다. `10:30 · 산책 주의 · 체감온도
33.5℃` 가 넘치면 **체감온도부터 뺀다** (배지가 먼저다, D15-8 미결 3).

### D15-6. 데이터 흐름

```text
상세 렌더 → [client] GET /plans/{planId}/walk-safety → planItemId 로 행에 붙임
```

| 항목                   | 내용                                                           |
| ---------------------- | -------------------------------------------------------------- |
| API                    | `GET /api/v1/plans/{planId}/walk-safety` (BFF `/api/bff` 경유) |
| React Query key        | **`planKeys.walkSafety(planId)`** — 상세·판정과 또 나눈다      |
| staleTime / gcTime     | **5분 / 30분**, `retry: 1`                                     |
| 서버 프리페치          | **하지 않는다**                                                |
| mutation 후 invalidate | **일괄 교체 · 방문 체크 제외한 모든 일정 mutation**            |
| 폴링                   | 없음                                                           |

- **key 를 `planKeys.weather` 와 합치지 않는다.** 한쪽이 5xx 로 죽어도 다른 쪽은 살아 있어야
  하고(D5), 무효화 대상도 다르다.
- **`staleTime` 5분은 "일정 목록·상세 30초" 가 아니라 "장소 인사이트 5분" 을 따른다**
  (`api-integration-guide.md` §7). 값의 출처가 tour-service 인사이트이고 **기상 예보 갱신
  단위가 1시간**이라 그보다 잦은 재조회가 낭비다. 표에서 벗어난 것이 아니라 **다른 행을
  고른 것**이고, 근거를 `queries.ts` 주석에 남긴다.
- **서버 프리페치를 하지 않는 이유**: 서버가 `(장소, 시각, 기준견)` 조합마다 tour-service 를
  한 번씩 부른다(`answered` 맵으로 중복만 접는다). 항목이 많은 일정이면 첫 페인트가 그만큼
  붙잡힌다. `/weather` 도 같은 이유로 클라이언트 조회다(`app/(main)/plans/[planId]/page.tsx`
  는 `planKeys.detail` 만 프리페치한다). 로딩 중에는 **배지 자리에 아무것도 그리지 않는다** —
  스켈레톤을 두면 시각 줄이 늘었다 줄었다 한다.
- **일괄 교체 후 반드시 무효화한다.** 교체는 `planItemId` 를 **전부 새로 발급**하므로
  (E1 규칙 3) 낡은 위험도는 **어느 행에도 붙지 않고 조용히 사라진다.** 게다가 시각을 고쳤으면
  판정 자체가 달라진다 — 순서 편집(E) · 장소 담기(F) · 하루 재생성 · **시각 수정(G)** 모두
  `planKeys.walkSafety(planId)` 를 함께 무효화한다.
- **방문 체크는 무효화하지 않는다.** 항목 구성·시각을 바꾸지 않는다 (D9-5 와 같은 판정).
- **행을 잇는 키는 `planItemId` 다.** `day`+`sequence` 로 이으면 교체 직후 한 프레임 동안
  **다른 항목의 판정이 붙는다.** 없는 `planItemId` 는 **그냥 배지가 없는 것**이지 오류가 아니다.
- **응답의 `title`·`placeTitle`·`startTime` 을 행에 그리지 않는다.** 행의 정본은 상세 응답이다
  — 두 응답 사이에 시차가 있으면 한 행에 두 이름이 섞인다.

### D15-7. 상태별 화면 · 문구 (확정)

| 상태                                           | 표시                                           | 문구 (확정)                                   |
| ---------------------------------------------- | ---------------------------------------------- | --------------------------------------------- |
| 조회 중                                        | **아무것도 그리지 않는다**                     | —                                             |
| 정상 (`SAFE`/`CAUTION`/`DANGER`)               | 시각 줄에 배지 + 체감온도                      | 서버 `walkSafetyLevel.name` **그대로**        |
| 등급 `UNKNOWN` (사유 코드 없음)                | **배지 없이** 캡션 문장                        | 서버 `walkSafetyLevel.description` **그대로** |
| `NO_START_TIME`·`NOT_PLACE_TARGET`·`PAST_DATE` | **숨김**                                       | —                                             |
| `BEYOND_FORECAST_RANGE`                        | 일자 카드에 한 줄 (그 일자에 항목이 있을 때만) | 서버 `unavailableReason` **그대로**           |
| `LOOKUP_FAILED` · 모르는 코드                  | 그 행 아래 캡션                                | 서버 `unavailableReason` **그대로**           |
| `LOOKUP_FAILED` 재시도 버튼                    | 일자 카드에 **하나**                           | `산책 위험도 다시 불러오기`                   |
| 전체 5xx · 무응답                              | 일자 카드 안 인라인 + 재시도                   | `산책 위험도를 불러오지 못했어요.`            |
| 전체 404 (`PLAN_001`) · 400 (`PLAN_124`)       | **자리를 통째로 숨긴다**                       | —                                             |

- **문장을 FE 가 짓지 않는다.** 이슈가 못박은 요구다. 서버 문장은 데이터 근거(예보 지평 5일 ·
  시각)를 담은 완성형이고, 화면이 옮겨 적으면 서버 상수가 바뀔 때 갈린다. FE 가 확정하는 문구는
  **버튼 이름과 전체 실패 문구 둘뿐**이고 그 둘에는 서버 값이 들어가지 않는다.
- **`PAST_DATE` 만 예외가 아닌가?** 일자 판정(#497)은 `PAST_DATE` 를 화면 말투로 옮겼다
  (`verdictPastDate`). 여기서는 **옮기지도 않고 아예 감춘다** — 같은 일자 카드에서 그 문장을
  이미 한 번 말했기 때문이다. 두 곳이 같은 사실을 다른 말투로 두 번 말하는 것이 더 나쁘다.
- **404 에 재시도를 달지 않고 문구도 내지 않는다.** 일정 본문은 상세가 이미 들고 있으므로
  이 자리는 **부분 데이터**다. D5 의 `반려견 조회 실패 → 숨김` 과 같은 취급이고,
  `api-integration-guide.md` 의 "404 는 `resultMessage` 노출" 은 **그 자원이 화면의 주인공일
  때**의 규칙이다 (주인공은 `GET /plans/{planId}` 쪽이 이미 처리한다).
- **전체 5xx 재시도 버튼은 일자마다가 아니라 한 번**이다 — 요청이 일정 단위 하나다.
- **성공에 토스트를 내지 않는다.**

### D15-8. 접근성

- **색으로만 전달하지 않는다** (DESIGN.md §7). 배지가 `산책 위험` 이라는 낱말을 함께 낸다 —
  `DANGER` 의 `critical` 톤이 유일하게 빨간 자리라 더 그렇다.
- 배지는 `<span>` 하나라 스크린리더가 `산책 주의` 를 한 덩어리로 읽는다. **`aria-label` 을
  따로 두지 않는다** (보이는 글자와 갈릴 자리를 만들지 않는다 — #652 D6).
- 시각 줄의 읽히는 순서: `시작 시각 10:30` → `산책 주의` → `체감온도 33.5℃`.
- **`체감온도` 라벨은 sr-only 가 아니라 보이는 글자다.** 맨 `33.5℃` 는 눈으로도 기온으로 읽힌다
  (#259 가 장소 상세에서 같은 결론을 냈다).
- `다시 시도` 버튼은 44px 이고 이름이 `산책 위험도 다시 불러오기` 다 — 한 화면에 다른 `다시
시도`(일자 판정)가 있어 이름이 갈려야 한다.
- 새 상호작용이 링크 안에 들어가지 않는다. 배지는 `<span>`, 재시도 버튼은 **일자 카드 액션
  줄**에 있어 행 링크 밖이다 (D6 의 "링크 안에 링크 없음" 유지).

| #   | 어떻게 왔나                                                                                                                                  |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `petConditionApplied: boolean \| null` 이 **항목마다** 온다. `null`(묻지 않았다)과 `false`(물어봤지만 반려견 특성 없이 판정)가 다른 사실이다 |
| 2   | 여섯째 사유 `NO_FORECAST_AT_TIME` 이 생겼다. 지평 **안**인데 그 시각 예보를 쓸 수 없는 줄이 이제 사유를 든다                                 |

**1 을 받는 방식은 요청할 때 생각한 것과 다르다.** 요청은 _"화면이 기준 반려견을 밝힐 수
있게"_ 였는데, 일자 판정 자리(`PlanDayVerdict`)가 **이미 기준을 말하고 있다**. 그래서 행마다
`{name} 기준` 을 붙이면 항목 수만큼 줄이 늘면서 새 정보는 0 이다(D15-5 가 노면온도·기온을
행에서 뺀 것과 같은 규율). **행은 일자와 어긋날 때만 말한다** — 일자는 반영했다는데 이
항목만 `false` 인 경우다. 어긋남이 실제로 생기는 이유는 두 값의 **출처가 다르기** 때문이다
(일자는 auth 특성 조회, 항목은 tour 의 `petCondition().isSpecified()`).

**2 는 화면 코드를 고치지 않고도 맞게 돌고 있었다.** `itemWalkSafetyView` 의 "모르는 코드 →
서버 문장" 갈래가 받아 냈다 — `unavailableReasonCode` 를 union 이 아니라 `string` 으로 둔
결정이 값을 한 것이다. 다만 **의도였음을 테스트로 고정**했다: 항목마다 갈리는 사유라
일자 단위로 접거나(`dayBeyondForecastReason`) 숨기면(`HIDDEN_REASON_CODES`) 거짓이 된다.

**`NO_FORECAST_AT_TIME` 은 재시도 버튼을 세우지 않는다.** 그 사유에 기상 원천 장애가 섞여
들어오지만 BE 가 이 경계에서 "지금 예보가 없다" 와 "원천이 잠깐 죽었다" 를 가르지 못한다 —
눌러도 같은 답이 오는 버튼은 차이를 말해 주지 못한다. 재시도는 `LOOKUP_FAILED` 에만 둔다.

**곁들여 `walkSafetyLevel.scoreDescription` 도 채워지기 시작했다.** 예전 주석은 _"언제나
null"_ 이라고 적었는데 쓸 일이 없어서가 아니라 BE 가 Feign 경계에서 버리고 있었다.
**행에서는 여전히 쓰지 않는다** — 등급당 고정 문장이라 배지가 이미 말하는 것 위에 줄만
늘린다. 값이 온다는 사실만 타입 주석에 남겼다.

- `WALK` 행은 **링크가 아닌 `div`** 갈래를 탄다 (`href === null`). 그 갈래는 이미 구현돼 있다.
- **유형 배지는 이미 뜬다.** `item.itemType.code !== 'PLACE'` 일 때 `<Badge>{item.itemType.name}</Badge>` 라
  서버가 준 `산책` 이 그대로 나간다 — **FE 에 한국어 매핑 테이블을 만들지 않는다.**

### D12-4. 요약이 올 때와 안 올 때 — 렌더 갈래

**`walkCourse` 가 `null` 인 경로가 셋이고, 셋 다 화면은 같게 군다** (`PlanQueryProcessor.java:183-198` 실측):

| 왜 비나                       | 근거                                                                      |
| ----------------------------- | ------------------------------------------------------------------------- |
| ① 코스 목록에 없는 `targetId` | `WALK` 는 저장 시 검증되지 않는다 (`PlanCommandProcessor.java:351`)       |
| ② **tour-service 장애**       | `catch (PlanException)` → `Map.of()` 로 삼키고 **일정은 그대로 응답한다** |
| ③ 수기로 정리된 행            | 같은 자리                                                                 |

서버 주석이 태도를 못박았다 — _"일정은 우리 DB 의 자료이고 코스 요약은 장식이다. 요약을 못 받았다고 사용자가
자기 일정을 못 보게 되면 안 된다."_ **화면도 같다: 행을 지우지 않는다.**

| 상태                        | 썸네일                                  | 제목         | 배지   | 메타 줄 (확정)                             | 비고                                 |

| 요약 있음 · 값이 다 있음    | `walkCourse.firstImage` (없으면 아이콘) | `item.title` | `산책` | `{name} · {distanceKm}km · {durationText}` | 예: `시흥-광치기 · 15.1km · 4~5시간` |

- **조립은 `lib/plan/walk-course-meta.ts` 순수 함수 하나가 갖는다.** `placeMetaLine`(주소 · 실내)과 **같은 모양**이고

## D18. 출발 전날의 무게 — 시선의 순서를 옮긴다 (이슈 [#732](https://github.com/8llow8llowMe/hondigagae/issues/732))

> **절 번호를 기존 것 위에 얹었다.** D11-9·D12~D17 은 다른 이슈에 배정돼 있어 기존 절을
> 재번호매김하지 않는다 (D12 머리주석과 같은 처리).
>
> **#665 위에 얹는 이슈다.** 그쪽은 준비물을 일자 위로 **올렸고**, 이쪽은 **강조 채널**을
> 함께 옮긴다 — 자리만 바꾸면 시선의 순서는 그대로다.

### D18-1. 상태 전이 액션 — 시점 축을 하나 더 둔다

`direction`(정/역, D11-2)이 첫 번째 축이고 **시점**이 두 번째다. 390 실측에서 D-1 화면의
유일한 filled 버튼이자 가장 큰 색면이 `여행 완료하기` 였다 — 그날 누를 일이 전혀 없다.

판정은 `planStatusActionLayout(statusCode, phase)` 하나이고 **버튼·메뉴 두 진입점이 그
결과를 나눠 받는다.** 각자 셈하면 같은 액션이 둘 다에 서거나 어느 쪽에도 없는 날이 생긴다.

| 상태      | `upcoming`               | `ongoing` · `past` |
| --------- | ------------------------ | ------------------ |
| DRAFT     | `확정하기` 버튼          | 같다               |
| CONFIRMED | `여행 완료하기` 메뉴     | 버튼               |
| COMPLETED | 버튼 없음 (D11-2 그대로) | 같다               |

**정방향 전부를 내리지 않았다.** 가르는 것은 "정방향이냐" 가 아니라 **"아직 이를 수 없는
일이냐"** 다 — 출발 전날의 초안은 확정할 수 있고 그것이 그날 할 일이다. 전부 내리면 #553 이
확정 버튼을 마지막 일자 끝에서 개요 아래로 끌어올린 결정까지 되돌아간다.

**날짜를 못 읽으면(`phase === null`) 버튼이다** — 있던 진입점을 근거 없이 감추지 않는다.

### D18-2. `D-N` + 일자별 판정 스트립 — 데스크톱 전용 목차를 대신한다

`일자별 판정` 목차는 **`hidden lg:block` 카드**였다. 모바일이 1순위인 제품에서 전체 판정
요약이 데스크톱 전용이라, 모바일 사용자는 일자 카드를 하나씩 열어야 했다.

세로 목록(줄당 44px)을 **개요 카드 안의 가로 한 줄**로 접는다. `D-N` 기둥이 `총 N일 · 예산`
줄에서 이 줄로 내려와 함께 서고(같은 말을 한 카드에 두 번 두지 않는다), 각 칸은 여전히 그
일자로 뛰는 앵커다. 44px 터치 영역은 줄에서 칸으로 옮긴다.

- **두 자리에 두지 않는다** — 카드를 남기고 스트립을 더하면 데스크톱에서 같은 자료가 두 번
  서고 앵커 링크도 일자마다 둘이 된다.
- **넷을 넘는 일자는 `외 N일` 로 센다** (`PLAN_VERDICT_STRIP_MAX_DAYS`). 여행은 최대 30일
  (`PLAN_PERIOD_MAX_DAYS`)이라 전부 세우면 요약이 아니라 목록이 된다. 상한이 넷인 근거는
  "두 줄" 이다 — 한 칸이 약 132px(`1일차` + `적합도 보통` 배지)이고 첫 줄은 `D-N` 이 한
  자리를 먹는다.
- **축 라벨(`적합도`)은 그대로 둔다** — 짧게 만들자고 떼면 `보통` 이 혼잡도의 `보통` 과
  구분되지 않는다 (#652 · `공통/등급배지-축라벨-세부명세.md` D5).

### D18-3. 브리핑 진입점 — 날짜가 맞는 동안만 brand

좌 레일에서 `내일 출발 · 브리핑 보기` 와 `가는 곳 주변 병원·약국` 이 같은 chevron 진입
행이었다. 하나는 지금 눌러야 할 것이고 하나는 사고가 났을 때 찾을 것이다.

`Surface tone="brand"`(`--brand-500` 테두리 + `--row-selected` 면, `DESIGN.md` §0-3)를
브리핑 카드에만 준다. **강조 조건을 새로 만들지 않는다** — 이 배너는 `pickBriefingDate` 가
날짜를 고른 이틀에만 렌더되므로 **서 있는 동안이 곧 강조할 동안**이다 (D16-2 그대로).

병원·약국 배너는 중립을 지킨다. 상시 진입점이 늘 강조돼 있으면 그 강조는 아무 말도 하지
않게 된다.

### D18-4. 준비물 — 내용이 있을 때만 승격한다 (D11-9 의 갈래를 셋으로)

D11-9 는 **시간만** 보고 올렸다. 그래서 출발 전날 화면 맨 위에 선 것이 설명 두 문단과
`AI로 준비물 챙기기` 버튼뿐인 **빈 카드**였다 — 승격의 보상이 "빈 상태를 더 잘 보이는
자리로 옮긴 것" 이 됐다.

`packingPlacement(plan, today, list)` 가 시간과 내용을 함께 본다.

| 값         | 조건                             | 화면                                            |
| ---------- | -------------------------------- | ----------------------------------------------- |
| `promoted` | 창이 열렸고 목록이 비지 않았다   | 위 레일, **요약 모드**                          |
| `strip`    | 창은 열렸는데 목록이 비었다      | 기본 자리 + 개요 아래 한 줄(`PlanPackingStrip`) |
| `default`  | 창이 닫혔거나 **아직 못 읽었다** | 기본 자리(일자 뒤)                              |

- **시간 축 함수는 `isPackingPromotionWindow` 로 이름이 바뀌었다** (D11-9-2 의
  `isPackingPromoted`). 경계·자정 규칙은 그대로다.
- **`null`(아직 못 읽음)은 "비었다" 가 아니다.** 조회가 끝나기도 전에 스트립을 띄웠다가
  목록이 도착해 걷어내면 화면만 한 번 더 흔들린다.
- **요약 모드**는 진행률 한 줄(`12개 중 3개 챙김`) + 항목 `PACKING_PREVIEW_MAX_ITEMS`(5)개 +
  `전체 보기` 다. 체크는 요약에서도 된다 — 읽기 전용이면 짐을 싸면서 체크하려고 매번 펴야
  한다. `전체 보기` 는 항목이 다섯 이하여도 남는다: 그 뒤에 재생성·직접 추가가 있어서,
  없애면 승격된 동안 준비물을 더할 방법이 사라진다.
- **자리를 정하려면 내용을 알아야 해서 화면이 목록을 구독한다** (`usePlanPackingList`).
  **카드가 아니라 `useQuery` 가 둘이고 query key 가 같아 요청은 하나다** — D11-9-3 이 막은
  것은 카드를 두 자리에 렌더하고 한쪽을 `hidden` 으로 두는 것이다.

### D18-5. 지표 라벨 고정 · `다녀옴 표시` · 날짜 표기

- **지표 라벨은 `최고 체감온도` 로 고정한다.** 나란한 두 일자가 다른 라벨(`최고 체감온도`
  27.5℃ / `최고기온` 24.0℃)을 쓰는데 설명이 없어 값의 차이가 아니라 화면의 오류로 읽혔다.
  예보 종류가 다른 날에만 **큰 숫자 옆**에 중립 배지로 `중기예보 최고기온` 이 선다 —
  `{source} 기준이라 대략적인 값이에요.` 는 근거 문단 맨 아래에서 사라진다.
  **최고기온을 체감온도라고 부르지는 않는다** (#253): 라벨은 축의 이름이고 단서는 그 날
  실제로 온 값의 이름이다. 예보 출처를 몰라도 `최고기온` 하나는 말한다.
- **`upcoming` 에서 `다녀옴 표시` 는 체크 아이콘만이다.** D-1 화면에서 가장 많이 반복되는
  문자열이었다 — 아무도 다녀오지 않은 일정의 모든 항목에 붙어 있었다. `aria-label` ·
  `aria-pressed` 는 그대로이고, 보이는 글자가 없어지면 #653 이 글자를 붙이며 새로 생긴
  WCAG 2.5.3(Label in Name) 제약도 함께 사라진다. **체크된 행은 `다녀옴` 을 지킨다** —
  상태를 말하는 유일한 낱말이라 접으면 색과 아이콘만 남는다 (DESIGN.md §7).
- **날짜 표기는 `formatPlanDay('2026-09-19') → '9월 19일 (토)'` 하나다** (`lib/plan/date.ts`).
  개요가 `2026-09-19 (토)`, 일자 카드가 `09-19 (토)` 로 갈려 있었다. 여행 브리핑
  ([#733](https://github.com/8llow8llowMe/hondigagae/issues/733))이 같은 함수를 쓴다.
  **연도를 통째로 버리지 않는다** — 기간 줄(`formatPlanDateRange`)은 지난 해 일정까지
  가리키므로 `formatPlanDayWithYear` 로 시작일에 연도를 남긴다.
