# 장소 담기 — 지도 보기 세부 명세

> 상위 공통명세: `docs/features/plan/공통명세.md`
> 앞선 문서: `docs/features/plan/일자편집-세부명세.md` (이슈 C — F0~F5 가 담기 화면의 정본)
> 이 문서는 **그 화면에 지도 보기를 더한다.** F2 가 정한 "라우트로 둔다"는 뒤집지 않는다.
> **화면 정본**: `혼디가개 장소 찾기.dc.html` 05(데스크톱 지도) · 06(모바일 시트) — 담기
> 화면 전용 아트보드는 없다. 그래서 `/places` 지도의 구조를 그대로 따르고, 다른 것은
> 이 문서가 명시한 네 가지(행 액션 · 핀 톤 · 토글 목적지 · 헤더)뿐이다.
> 작성일: 2026-09-09
> 이슈: [#370](https://github.com/8llow8llowMe/hondigagae/issues/370)
> 보강: [#1177](https://github.com/8llow8llowMe/hondigagae/issues/1177) — 지도를 그날 직전 장소에서 연다 ([D10](#d10-기준점에서-연다-1177))
> **새 API 가 없다.** `/places` 가 쓰는 `GET /places` · `GET /places/nearby` 와 담기의
> `PUT /plans/{planId}/days/{day}/items` 를 그대로 쓴다 — 계약 정본은 일자편집 명세 E1.

## 이 문서가 바꾸는 앞선 결정

| 문서                                        | 기존                                      | 이 문서                          | 이유                                                                                              |
| ------------------------------------------- | ----------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------- |
| 일자편집 F5 표 (`일자편집-세부명세.md:396`) | 담기 성공 후 **그 일자로 `replace` 이동** | **화면에 남는다** (두 보기 모두) | 지도에서 하루 동선을 짜려면 여러 곳을 연달아 담아야 한다. 담자마자 나가면 지도로 바꾼 의미가 없다 |
| `place-map-panel.tsx` 행 구조               | 행 `<button>` **안**에 제목 `<a>`         | 제목 링크를 **액션 열로 분리**   | `<button>` 안의 링크는 HTML 명세 위반이다. 담기 버튼까지 더하면 button 안에 a + button 이 된다    |

두 번째는 `/places` 지도에도 그대로 적용된다 — 같은 컴포넌트다.

## D0. 화면 정의

- **경로**: `/plans/[planId]/days/[day]/add` — **같은 라우트**다. 보기는 `?view=` 가 갖는다
- **인증**: 필요 (`proxy.ts` `PROTECTED_PATHS` 의 `/plans` 가 이미 덮는다)
- **기본 보기**: **지도**. `PLAN_ADD_DEFAULT_VIEW: ViewMode = 'map'`
  - 값은 `PLACES_DEFAULT_VIEW` 와 같지만 **상수를 따로 둔다.** `view-mode.ts` 가 이미
    _"화면이 자기 기본값을 갖는다"_ 를 규약으로 적어 뒀고, 긴급 시설이 목록으로 남은
    선례가 그 규약의 존재 이유다
  - 그래서 `/plans/1/days/1/add` 가 지도이고 목록이 `?view=list` 로 붙는다
- **진입 경로**: 일정 상세의 일자 섹션 `장소 추가`
- **이탈 경로**: 헤더의 `일정으로 돌아가기` (담기 성공으로는 **이탈하지 않는다**)

## D1. 레이아웃

`/places` 지도(아트보드 05·06)와 같되, **위에 컨텍스트 바가 한 줄 붙는다.**

- **모바일 (375)**: 컨텍스트 바 → 지도 → 하단 시트 3단(`min` 0.2 / `mid` 0.45 / `max` 0.85)
- **태블릿 (768)**: 같다. 시트는 `lg:hidden` 이라 1024 미만에서 계속 시트다
- **데스크톱 (1024+)**: 컨텍스트 바 → 지도 + 좌측 400 패널(`absolute top-6 bottom-8 left-4`)
- **필터 레일을 쓰지 않는다.** 지도 보기에서 280 레일을 함께 두면 지도가 세 번 접힌다
  (`/places` 지도와 같은 판단). 필터는 패널·시트 머리의 `PlaceMapFilterBar` 가 맡고,
  URL 에 남아 있으므로 목록으로 돌아가면 레일에 다시 보인다

### 높이 — `map-canvas-height` 를 캔버스에서 컨테이너로 올린다

`map-canvas-height` 는 `calc(100dvh - --header-h - --tabbar-h)` 로 **뷰포트를 정확히 다
쓴다.** 컨텍스트 바를 지도 위에 그냥 얹으면 그 높이만큼 넘쳐 지도 화면에 세로 스크롤이 난다.

```text
PlanAddPlaceView (plan)
<div class="map-canvas-height flex flex-col">   ← 높이를 여기서 잡는다
  <PlanAddPlaceHeader />                         ← 정상 흐름. 지도를 가리지 않는다
  <div class="min-h-0 flex-1">
    <PlaceMapView fill />                        ← place. 높이는 부모가 준 것을 채운다
      <div class="relative h-full">              ← PlaceMapView 의 루트
        <MapCanvas class="h-full w-full" />
        …우상단 컨트롤 · 좌측 패널 · 하단 시트
```

- **헤더는 `relative` 밖이다.** 안에 들어가면 좌측 패널의 `top-6` 이 헤더와 겹친다.
  헤더가 `PlaceMapView` 바깥에 있으므로 구조적으로 그럴 수 없다
- `/places` 는 `header` 를 주지 않으므로 **오늘과 픽셀이 같다** — 클래스가 캔버스에서
  부모로 올라가고 캔버스가 `h-full` 이 될 뿐이다
- `map-canvas-height` 의 사용처는 `place-map-view.tsx` **한 줄뿐**이라(grep 확인) 다른
  화면에 번지지 않는다
- `MapSheet` 는 `fixed inset-x-0` 이라 지도 높이와 무관하다 — **손대지 않는다**

### 검색 — 머리 아래와 패널 맨 위 (#1012)

`/places` 지도와 같은 `searchable` 을 켠다. 목록 보기에도 같은 검색이 서므로(일자편집 명세
F2) 두 보기가 같은 도구를 갖는다. **자리는 폭이 가른다:**

- **1024 미만 — 떠 있는 머리 카드 바로 아래**(사이 8, `compact`). `/places` 는 보기 토글
  왼쪽에 두지만 이 화면은 그 자리가 머리 카드(`end-32`) 밑이라, 거기 그리면 **보이지 않는
  입력이 포커스를 받는다.** 폭은 머리 카드와 같게 둔다(`max-w-md` 없음) — 한 기둥에 선 두
  표면의 오른쪽 끝이 어긋나면 따로 떠 있는 것으로 읽힌다
- **1024 이상 — 좌측 패널 맨 위.** `/places` 와 같다. 머리 기둥의 검색은 `lg:hidden`
- **SDK 실패 폴백 — 안내 줄 아래.** `/places` 와 같다

그래서 **떠 있는 머리의 자리를 `PlaceMapView` 가 갖는다** (`head` 슬롯). 머리가 이 화면의
`absolute` 였을 때는 검색을 그 아래에 세울 길이 없었고, **SDK 실패 폴백에서 머리가 안내 줄과
첫 행을 덮고 있었다**(375 에서 첫 행 사진 위, 1440 에서 안내 줄 전체 — #1012 착수 전 실측).
폴백은 이제 머리를 정상 흐름으로 맨 위에 세운다. 내용(뒤로가기 · 제목 카드)은 여전히 이
화면이 그린다 — place 는 plan 을 모른다.

모바일 시트 상한 `SHEET_MAX_TOP_INSET` 은 **140 → 248** 이다. 머리 기둥 바닥이 375 에서 182,
768 에서 240(뒤로가기가 제목 위로 올라가 카드가 104)이고, px 하나로 1024 미만 전체를 덮어야
해서 높은 쪽 + 8 이다.

**머리 기둥은 문서에서 우상단 컨트롤·시트보다 앞이다** (#1012 검토). 예전에는 같은 `z-30` 인
시트를 끝까지 올려도 머리가 위에 남도록 맨 뒤에 뒀는데, 검색이 머리 아래로 오자 모바일
키보드 순서가 토글 → 내 위치 → 시트 행 수십 개 → 검색이 됐다 (WCAG 2.4.3). 위 상한으로 시트가
머리에 닿지 않으므로 순서가 쌓임을 정하지 않는다 — 앞에 둬도 가려지지 않는다.

### `PlaceMapView` 의 새 인터페이스

**전부 place 어휘다.** plan 을 모른다 — `PlaceListSection.renderRow` 주석이 경고한
place → plan 역참조를 그대로 피한다.

**헤더를 slot 으로 받지 않는다.** 설계 검토에서 `header?: ReactNode` 판별 유니온을
쓰려 했으나 **`ReactNode` 자체가 `undefined` 를 포함해서** `{ header?: undefined }` 와
`{ header: ReactNode }` 가 서로 갈리지 않는다 — 타입이 아무것도 강제하지 못한다.
대신 **높이 소유권만 boolean 으로 넘기고 헤더는 호출부가 자기 트리에서 그린다.**
plan 의 헤더가 place 컴포넌트를 통과하지 않아 경계도 더 깨끗해진다.

> **#1012 가 떠 있는 머리를 `head?: ReactNode` 슬롯으로 올렸다.** 위 근거는 판별 유니온이
> 갈리지 않는다는 것이었고, 이 슬롯은 유니온이 아니라 **있으면 그리는 선택 슬롯**이라 그
> 근거가 닿지 않는다. place 가 plan 을 import 하지 않는 것은 `renderRowAction` 과 같다.
> 올린 이유는 D1 [검색](#검색--머리-아래와-패널-맨-위-1012) — 모바일 검색 자리와 폴백의 겹침.

```ts
type PlaceMapViewProps = {
  filters: PlaceFilters
  authed: boolean
  /**
   * `true` 면 **부모가 높이를 정한다** — 위에 헤더가 붙는 화면이 쓴다.
   * `false`(기본)면 스스로 `map-canvas-height` 로 뷰포트를 채운다.
   */
  fill?: boolean
  /**
   * 지도 우상단에 떠 있는 보기 전환의 목적지. **둘 다 주면 토글을 그린다.**
   * 헤더가 토글을 갖는 화면은 주지 않는다 — 같은 컨트롤이 두 개 뜨면 안 된다.
   */
  listHref?: string
  mapHref?: string
  /** 패널·시트 행의 오른쪽 고정폭(w-24) 열. 담기 버튼이 여기 온다 */
  renderRowAction?: (place: PlaceSummary) => ReactNode
  /** 행 아래 전폭 줄. 실패 알림이 여기 온다 — 액션 열은 w-24 라 FormAlert 가 못 들어간다 */
  renderRowNotice?: (place: PlaceSummary) => ReactNode
  /** 핀 톤을 낮출 장소들. 담기 화면은 "이미 담은 곳" 을 넘긴다 */
  mutedPlaceIds?: ReadonlySet<string>
  /** SDK 실패 폴백의 `PlaceListSection` 행 */
  renderListRow?: PlaceListSectionProps['renderRow']
}
```

- **`filterQuery` prop 을 삭제한다.** 오직 `viewModeHref('/places', …)` 를 만들려고
  있었다. hrefs 를 밖에서 받으므로 필요 없어지고, 하드코딩된 `'/places'` 가 함께 사라진다
- `/places` 는 `filters` · `authed` · `listHref` · `mapHref` 만 넘긴다 — 나머지는 안 준다
- 담기 화면은 `fill` 을 주고 `listHref`/`mapHref` 는 주지 않는다. 높이 컨테이너와 헤더는
  `PlanAddPlaceView` 가 자기 트리에서 그린다

### `PlaceMapPanel` 행 구조

```text
<li>
  <div class="flex items-stretch" (선택이면 bg-row-selected)>
    <button aria-pressed …>          ← 핀 고르기. PlaceRowContent (titleHref 없음)
    <div class="w-24 …">             ← 액션 열: 상세 링크 + renderRowAction
  </div>
  {좌표 없음 안내}
  {renderRowNotice}                  ← 행 아래 전폭
</li>
```

- **선택 버튼 안에 링크가 없다.** 제목 링크가 액션 열의 `상세` 링크로 나온다
- 액션 열이 **선택 버튼의 형제**라 담기 버튼도 중첩되지 않는다
- 선택 배경은 행 전체(`div`)로 옮긴다 — 액션 열까지 함께 칠해져야 한 행으로 읽힌다
- **액션 열은 `w-24` 를 유지하고 컨트롤을 세로로 쌓는다.** 96px 에 `상세`(44) 와
  `담기`(44) 를 나란히 두면 둘 다 44 터치 영역을 못 지킨다. 세로면 88px 이고 행 높이는
  `py-3 + size-20` = 104px 라 들어간다. `PlanAddPlaceRow`(목록)의 `w-24` 와 같은 폭이라
  두 보기의 행이 같은 축에서 끝난다
- **`/places` 지도 패널도 함께 바뀐다.** 제목이 더 이상 링크가 아니고 액션 열에 `상세`
  링크가 생긴다 — `renderRowAction` 이 없어도 상세 링크는 항상 있다

## D3. 데이터 흐름

```text
진입(server) → planKeys.detail fetchQuery(404 → notFound) + placeKeys.list prefetchInfinite
            → view === 'map' ? PlanAddPlaceHeader + PlaceMapView(fill) : 기존 목록
(client) 지도 이동 → useNearbyPlaces 로 출처 전환
        담기 → PUT …/days/{day}/items → 응답으로 planKeys.detail 교체 → 화면 유지
```

| 항목                   | 내용                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| API                    | `GET /places` (목록·지도 첫 화면) · `GET /places/nearby` (지도 이동 후) · `PUT /plans/{planId}/days/{day}/items` (담기)             |
| React Query key        | `placeKeys.list(filters)` · nearby 는 `useNearbyPlaces` 내부 · `planKeys.detail(planId)`                                            |
| staleTime / retry      | 서버 프리페치는 `retry: false` (재시도 백오프가 서버 렌더를 붙잡는다). 나머지는 전역 기본값                                         |
| mutation 후 invalidate | 응답으로 `planKeys.detail` **setQueryData**, `planKeys.weather` invalidate — `usePlanAddPlace` 가 이미 한다. **훅은 손대지 않는다** |
| 폴링                   | 없음                                                                                                                                |

- **지도 첫 화면은 별도 조회를 하지 않는다** (`architecture-guide.md` §9). 목록 캐시를
  재사용하므로 서버 프리페치가 지도 보기에서도 그대로 쓸모 있다 — 지도 갈래에서도
  `prefetchInfiniteQuery` 를 유지한다
  - **예외 — 기준점이 있는 날 (#1177).** 지도 첫 화면을 `/places/nearby` 로 시작한다. 프리페치한
    첫 장은 `placeId` 순이라 그날과 무관한 곳(한경면)부터 나온다. 기준점이 없는 날과 목록 보기는
    위 규칙 그대로다 — [D10](#d10-기준점에서-연다-1177)
- **"이 지역에서 재검색" 버튼을 누르면** `/places/nearby` 로 갈아탄다 (#396). 지도를 옮기기만
  해서는 조회하지 않고 버튼을 띄울 뿐이다. 첫 `idle` 은 재검색 권유의 기준 영역만 놓고 목록을
  거르지 않는다 (#1143 · `lib/map/place-map-area.ts`)

## D4. 상호작용

| 트리거                    | 동작                                                      | 결과                                                                                                                                              |
| ------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 헤더 `ViewToggle`         | `?view=` 만 바꾼 링크로 이동 (`push`)                     | 필터가 유지된 채 보기가 바뀐다. 뒤로가기로 되돌아온다                                                                                             |
| 핀 · 패널 행 클릭         | `selectedId` 설정                                         | 그 핀으로 이동 + `SELECTED_PLACE_MAP_LEVEL` 까지 확대, 행 배경 강조                                                                               |
| 액션 열 `담기`            | `addPlace.add({day, dayItems: group.items, place})`       | 성공 → 토스트 + 그 행이 `이미 담았어요` + 핀 톤 다운. **화면에 남는다**                                                                           |
| 액션 열 `상세` 링크       | `/places/{placeId}` 로 이동                               | 뒤로가기로 돌아온다. **이 화면은 지도가 기본**이라 `viewModeHref` 가 `view` 를 생략한다 — `/plans/{planId}/days/{day}/add` 만으로 지도로 복귀한다 |
| 지도 이동                 | `bounds` 만 갱신 — 조회 없음, 충분히 벗어나면 재검색 버튼 | 목록은 그대로다. **재검색을 누르면** 그 영역으로 nearby 조회하고 목록이 그 영역으로 바뀐다 (#396 · #1143)                                         |
| 필터 변경                 | URL 쿼리 갱신                                             | 두 보기가 같은 필터를 공유한다                                                                                                                    |
| 필터 초기화(`EmptyState`) | **`viewModeHref` 로 만든 경로**로 `replace`               | **보기를 유지한다** — `viewModeHref(…, PLAN_ADD_DEFAULT_VIEW)` 라 목록에서 눌러도 `?view=list` 가 남고 지도로 튀지 않는다                         |
| `일정으로 돌아가기`       | `/plans/{planId}#day-{day}`                               | 담기 결과가 이미 캐시에 있어 재조회하지 않는다                                                                                                    |

### 담기 후 화면에 남는다 — 무엇이 어떻게 바뀌는가

`usePlanAddPlace` 의 `onAdded` 콜백을 **넘기지 않는다.** 훅 내부는 그대로다.

응답이 `planKeys.detail` 을 갈아끼우므로 같은 렌더에서:

1. `addedPlaceIds`(`placeIdsOf(group.items)`)에 그 장소가 들어간다 → 행이 `이미 담았어요`
2. `mutedPlaceIds` 가 같은 집합이므로 → 핀이 톤 다운
3. 토스트 `{title}을(를) N일차에 담았어요` 가 뜬다 (`usePlanAddPlace` 가 이미 띄운다)

**목록 보기도 같이 남는다.** 두 보기가 다르게 행동하면 이 이슈가 고치려는 바로 그 불일치를
새로 만든다.

## D5. 상태별 화면

**`detail` 이 준비되지 않으면 보기와 무관하게 목록 껍데기로 떨어뜨린다.** 담기 버튼은 그
일자의 현재 항목 전부(`dayItems`)를 되실어야 하므로, detail 없이 그린 지도는 **담을 수 없는
지도**다. 서버가 `fetchQuery` 로 await 하니 첫 진입에는 이미 캐시에 있다 — 이 갈래는
클라이언트 이동에서만 잠깐 보인다.

| 상태                 | 표시                                                                | 문구 (확정)                                                |
| -------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------- |
| `detail` loading     | 목록 껍데기 + `PlaceRowSkeleton` ×6                                 | —                                                          |
| `detail` 400         | 목록 껍데기 + `EmptyState`                                          | 기존 `plan.detailBadRequest*`                              |
| `detail` 5xx         | 목록 껍데기 + `ErrorState` + 재시도                                 | 기존 `plan.detailErrorTitle`                               |
| 기간 밖 일자         | 목록 껍데기 + `EmptyState` + 돌아가기                               | 기존 `plan.addPlaceDayMissing*`                            |
| 지도 성공            | 지도 + 패널/시트                                                    | `지도에 보이는 {n}곳` (기존 `map.visibleCount`)            |
| 영역 안에 결과 0     | 패널/시트에 `EmptyState`                                            | 기존 `map.emptyInView*`                                    |
| 장소 목록 404 / 5xx  | **`영역 안에 결과 0` 과 같은 화면** — 패널·시트에 `map.emptyInView` | 기존 `map.emptyInView*`                                    |
| **지도 SDK 실패**    | 안내 한 줄 + `PlaceListSection`(**`PlanAddPlaceRow` 로**)           | 기존 `map.errorNoKey` / `errorUnsupported` / `errorScript` |
| 이미 담긴 장소       | 액션 열 `이미 담았어요` + 핀 `muted`                                | 기존 `plan.addPlaceAlready`                                |
| 담기 실패 (5xx)      | **그 행 아래** `FormAlert`                                          | 기존 `plan.addPlaceError*`                                 |
| 담기 실패 `PLAN_004` | **그 행 아래** `FormAlert`, 재시도 없음                             | 기존 `plan.addPlaceMissingPlaceError`                      |
| 좌표 없는 장소       | 패널에 남기고 안내 + **담기 버튼은 붙인다**                         | 기존 `map.noCoordinate`                                    |

**장소 목록 장애가 "결과 없음" 으로 보인다 — 알고 두는 것이다.** 패널·시트는
`visible.length === 0` 하나로만 갈리고 `listQuery.error` 는 SDK 실패 폴백 안에서만 읽힌다.
그래서 목록이 500 이어도 지도는 `이 지역에는 표시할 곳이 없어요` 를 띄운다 — 사용자는
장애를 조건이 좁아서 나온 결과로 오인한다.

**이 화면이 새로 만든 문제가 아니다.** `/places` 지도 보기가 이미 같은 동작이고, 고치려면
`PlaceMapView` 의 패널·시트 분기에 오류 상태를 넣어야 해서 #370 범위를 넘긴다. 여기에는
사실만 적어 둔다.

**새 문구가 없다.** 액션 열의 상세 링크 하나만 `aria-label` 이 필요하다 (D6).

**SDK 실패 폴백에 `renderListRow` 가 없으면 담기가 사라진다.** 지도가 안 뜨는 사용자에게
담기 화면이 열람 전용이 되는 것이라, 이 prop 은 선택이 아니라 이 화면의 필수다.

## D6. 접근성

- **링크 이름**: `ViewToggle` 은 보이는 글자(`목록 보기`/`지도 보기`)가 곧 이름이다 (#1125 — 예전 icon-only `aria-label` 을 걷었다).
  액션 열 상세 링크는 `{title} 상세 보기` — 한 화면에 여러 개라 보이는 글자만으로는
  전부 "상세" 로 읽힌다 (`담기` 버튼이 `{title} 담기` 인 것과 같은 이유)
- **키보드 순회**: 머리(뒤로 → 1024 미만 검색) → 토글 → 지도 핀 → 패널 필터 → 패널 행(선택 버튼 → 상세
  링크 → 담기 버튼). 행 안에서 **선택 → 상세 → 담기** 순서가 시각 순서와 같다
- **`<button>` 안에 링크·버튼을 넣지 않는다.** 이 문서가 고치는 결함이다. 중첩 대화형
  요소는 스크린리더가 무엇을 읽어야 할지 정하지 못한다
- **터치 44px**: 담기 버튼은 `size="md"`(44) 유지. 상세 링크도 같은 열에서 44 를 확보한다
- **색 외 전달**: 선택은 배경 + `aria-pressed`. 담긴 상태는 **핀 톤(muted) + 낱말**
  (`이미 담았어요`) 두 채널이다 — `MapCanvas` 는 마커에 판정 색을 쓰지 않는다는 규약이 있어
  색으로만 말하지 않는다
- **`h1` 은 두 보기 모두 보인다.** 컨텍스트 바에 있으므로 `/places` 지도처럼 `sr-only` 로
  숨기지 않는다

### D8-1. 1번 — 낱말을 지키되 터치 영역을 고쳤다

탈출 조건이 _"실화면에서 폭이 모자라면 ②로"_ 였다. **폭은 모자라지 않았다** — `w-24`(96px)
열에 낱말 `상세`와 `담기` 버튼이 세로로 들어가고, 데스크톱 1440·모바일 375 양쪽에서 서로
겹치지 않는다. 아이콘으로 바꿀 이유가 없다.

**대신 다른 것이 걸렸다.** `상세` 링크의 실측 크기가 데스크톱·모바일 모두 **28.8 × 44** 였다.
`h-11` 로 세로만 잡고 가로를 비워 둔 탓이다 — **44 를 주기로 한 이상 두 축 모두**다.
`min-w-11` 을 더해 44×44 를 채웠다 (`place-map-panel.tsx`). (§7 의 44 하한 자체는 #883 으로
지도 타깃만 남았지만, 이 판정은 그것과 무관하다 — 한 축만 지키면 지킨 것이 아니라는 말이다.)

`담기` 버튼(61.7 × 44)과 `이미 담았어요` 텍스트는 문제가 없었다.

### D8-2. 2번 — 부제를 남긴다

375 실측: 화면 헤더 **144px**(전역 nav 56 포함 200px), 그중 **부제는 18px 한 줄**이다.
빼면 지도가 612 → 634px 로 **2.7%** 넓어진다. _"지도가 세로를 다 쓴다"_ 는 걱정이 실제
숫자로는 서지 않는다.

반대편은 무겁다. `h1` 은 `1일차에 담을 장소` 라 **며칠차만 말하고 어느 일정인지는 말하지
않는다.** 부제가 유일하게 `몽실이와 제주 2박 3일` 을 낸다 — 일정이 여러 개인 사용자가
잘못된 일정에 담는 것을 막는 마지막 표식이다. 뒷문장(`고른 장소가 1일차 맨 뒤에 담겨요`)은
일괄 교체 모델의 결과를 미리 말해 주는 유일한 자리이기도 하다.

## D10. 기준점에서 연다 (#1177)

2026-10-06 dev 실데이터 사용성 점검에서 발견했다. 기본 보기인 지도가 그날 장소(중문·서귀포)와
무관하게 **제주시(`JEJU_MAP_ANCHOR`) 중심**으로 열렸고 패널 첫 항목이 한경면이었다 — `GET
/places` 는 좌표·정렬이 없어 `placeId` 순이다. 이 화면은 "다음에 갈 곳" 을 고르는 화면이라
직전에 들른 곳 근처부터 보여야 한다.

### 기준점 규칙 — `addPlaceFocus(day, days)` (`lib/plan/add-place-focus.ts`)

| 순서 | 어디서                                                   | 비고                                                |
| ---- | -------------------------------------------------------- | --------------------------------------------------- |
| 1    | 들어갈 자리(`itemInsertIndex`, #1175) 바로 앞부터 거꾸로 | 이동·좌표 없는 항목은 건너뛴다. 올레는 코스 시작점  |
| 2    | 자리 뒤 — 그날 끝의 숙소 — 의 첫 좌표                    | 숙박만 있는 날도 여기다                             |
| 3    | 전날까지의 마지막 숙소 (`lodgingBasisFor`)               | 그날 아침의 출발점. 전날의 숙박 아닌 장소는 안 본다 |
| 4    | 없음 (`null`)                                            | 지금과 같다 — 제주 기본 중심 · 목록 캐시 재사용     |

좌표는 `planItemMapCoord` 로 읽는다 — 지도와 같은 판단(#743)이다. 기간 밖 일자는 `null` 이다.

### 지도 보기

- **`PlaceMapView` 의 선택 prop `initialFocus`** 로 넘긴다. 없으면 `/places` 와 한 글자도 다르지
  않다. **마운트 때 값만 쓴다** — 담기 응답으로 기준점이 방금 담은 곳으로 바뀌는데, 그때마다
  카메라가 옮겨지면 연달아 담는 흐름(#370 · D4)이 끊긴다
- **카메라** — `MapCanvas` 의 `camera`. 기준점 · 폭 10km(반경의 지름) · `anchorRatio` 기본
  (0.35). 0.5 가 아닌 이유는 모바일 시트 `mid`(45dvh)가 지도 아래 절반을 덮어서다 — 375×812
  계산으로 기준점이 보이는 띠가 지도 높이의 약 18~47% 다. `refitOnResize` 는 켜지 않는다
  (시트·패널은 컨테이너 크기를 바꾸지 않는다)
- **첫 목록은 "이 지역에서 재검색" 을 누른 상태로 시작한다.** 기준점 둘레 사각형(네 변까지
  `PLACE_MAP_FOCUS_RADIUS_METERS` = 5km, 차로 10분 안팎)을 `areaAfterResearch` 로 초기 영역에
  두고 `researched` 를 켠다 — 들어오자마자 `/places/nearby`(서버 거리순, 반경은 모서리까지
  약 7.1km)가 나간다. 그 너머는 사용자가 지도를 옮겨 재검색한다
- **프리페치한 `/places` 첫 장(좌표 없는 key)은 그대로 둔다** — `PlaceMapView` 의 목록이 쓴다. 목록 보기는
  #1217 부터 거리순 key 를 따로 프리페치한다 (D11)
- **SDK 실패 폴백도 주변 조회 결과를 그린다** (지도 검토). 카카오 키 도메인이 등록되지 않은 환경은
  늘 폴백이라, 첫 장만 그리면 기준점이 통째로 무시됐다. 폴백 목록은 `places`(기준점이면 주변 조회,
  아니면 첫 장)다 — `/places` 는 폴백에서 재검색할 수 없어 예전과 같다
- **주변 조회가 오기 전에는 행 골격이다.** 목록 캐시가 이미 있어 기존 `listPending` 은 거짓인데,
  그대로면 첫 장을 기준점 영역으로 거른 결과(대개 0곳)가 빈 상태로 먼저 깜빡인다. 같은 이유로
  개수 캡션은 `p` 가 아니라 `div` 다 — 골격(`div`)을 품는 이 갈래가 처음 서버에서 그려지며
  하이드레이션이 깨졌다(실측)
- **주변 조회가 일시 장애(5xx · 무응답)로 실패하면 재시도다** (지도 검토). 목록 캐시로 떨어지면
  "이 지역에는 표시할 곳이 없어요" 로 장애를 데이터 부재처럼 말한다. 패널 · 시트 두 곳 모두
  `장소를 불러오지 못했어요` + `다시 시도`(`nearbyFailed`). 404 등에는 재시도를 달지 않는다
- **알고 남긴 것** — 1024~1279 데스크톱에서는 열린 패널이 기준점 서쪽 띠를 덮는다(`anchorRatio`
  는 세로만 다룬다, 계산값). 기준점 자체를 표시하는 핀은 없다 — 기준이 올레 시작점이거나 필터에
  걸리면 그 자리에 핀이 없다. 둘 다 후속 판단

**첫 `idle` 함정.** 지도는 먼저 제주 기본 위치로 만들어지고 카메라가 한 번 옮긴다. 첫
`idle`(`userMoved=false`)을 `/places` 처럼 `areaAfterIdle` 로 받으면 권유 기준이 제주 기본 시야로
덮여, 카메라가 옮기자마자 재검색 버튼이 뜬다. 카메라의 `idle` 은 `settledRef` 가 켜진 뒤라
`userMoved=true` 로 와서 그 값으로는 못 가른다. 그래서 기준점 지도는 따로 받는다
(`framingAfterIdle` · `lib/map/place-map-area.ts`).

| 단계      | 언제                         | `idle` 을                                                   |
| --------- | ---------------------------- | ----------------------------------------------------------- |
| `pending` | 지도 생성 ~ 카메라 적용 전   | **보지 않는다** — 보이는 영역도 안 옮긴다(버튼 깜빡임 방지) |
| `applied` | `onCameraApplied` 를 받은 뒤 | 권유 기준으로 삼는다 (`areaAfterFramedIdle`) → `settled`    |
| `settled` | 그 뒤                        | 보이는 영역만 옮긴다 — `/places` 와 같다(#396)              |

권유 기준을 기준점 사각형으로 두지 않는 이유: 카메라 단계가 정수라 실제 화면이 사각형보다
넓고(375 폭 레벨 8 ≈ 12km) 기준점이 화면 위쪽이라 중심도 다르다 — 그 차이가 그대로 확대·이동으로
읽힌다. 목록 영역(`searched`)은 사각형 그대로 둔다 — 옮기면 주변 조회 키가 바뀌어 한 번 더
조회한다. 대가는 캡션이 `목록 N곳` 인 것뿐이다.

### 목록 보기는 바꾸지 않는다 (→ #1217 에서 바꿨다, D11)

`/places` 가 좌표·정렬을 받지 않아, 클라이언트 정렬은 로드된 페이지만 정렬하는 거짓이 된다.

## D11. 목록 보기도 기준점에서 가까운 순이다 (#1217)

> 상태: **구현 완료** (#1217) — BE 계약은 #1202 · PR #1214 (`backend/docs/services/tour-service.md` "장소 목록 거리순 결정")

D10 의 지도와 같은 문제가 목록 보기(`?view=list`)에 남아 있었다 — 중문 일정이어도 첫 항목이 한경면이었다.
BE 가 `GET /places` 에 선택 `lat` · `lng` 를 열어(둘 다 있으면 (반올림 m, `placeId`) 거리순, 행마다
`distanceMeters`), 클라이언트 정렬의 거짓 없이 서버 거리순을 붙인다.

### 기준점과 조회

- **기준점은 지도와 같은 `addPlaceFocus`** 다. 목록용 진입은 `addPlaceListOrigin(detail, day)` —
  상세가 없으면 `undefined`(조회를 미룬다), 기준점이 없으면 `null`(좌표 없이 `placeId` 순 — 예전 그대로).
- **처음 값으로 얼린다.** 지도의 `initialFocus` 와 같은 이유다 — 담기에 성공하면(#370, 화면에 남는다)
  기준점이 방금 담은 곳으로 바뀌는데, 따라가면 key 가 바뀌어 목록이 처음부터 다시 받아지고 보던 자리가
  사라진다. 다시 들어오면(보기 전환 포함 — 두 보기는 다른 트리라 다시 마운트된다) 새 기준점이다.
- **상세가 오기 전에는 조회하지 않는다.** 좌표 없이 먼저 받으면 상세가 온 뒤 목록이 한 번 뒤집힌다.
  서버가 상세를 프리페치하므로 보통 첫 렌더부터 있다. 그동안은 행 골격이다(`isPending`).
- **목록 보기에서만 조회한다.** 지도 보기는 `PlaceMapView` 가 자기 목록(좌표 없는 key)을 든다 — 켜 두면
  지도에서 쓰지 않을 거리순 요청이 한 번 더 나간다.
- **키** — `placeKeys.list(filters, origin)`. `origin` 이 `null` 이면 예전 키 그대로라 `/places` · 지도 패널과
  캐시를 나눠 쓰고, 있으면 `{ lat, lng }` 가 붙어 갈린다(같은 필터라도 순서와 `distanceMeters` 가 다르다).
- **서버 프리페치도 같은 함수다** — 페이지가 받은 상세로 `addPlaceListOrigin` 을 불러 같은 key 로 첫 장을
  받는다. 어긋나면 하이드레이션이 빗나가 첫 화면에서 목록을 한 번 더 받는다(실측: 로드 뒤 클라이언트의
  `/api/bff/places?…lat=` 요청 없음). 상세를 못 받았으면 목록도 프리페치하지 않는다. 지도 보기의 프리페치는
  좌표 없는 key 그대로다.
- **커서는 그대로 `lastPlaceId`** — 서버가 그 장소의 (거리, id) 키를 되살린다(`PLACE_110` 이면 되살릴 수 없음).
- 기준점은 URL 에 싣지 않는다 — 사용자가 고르는 조건이 아니라 화면이 정하는 것이다(`toPlaceFilterQuery` 밖).

### 화면 (사용자 결정 2026-10-07 — 행 거리 + 목록 위 한 줄)

  쟀는데 "직전" 이면 거짓이다. "이날 동선" 은 셋 다 덮는다(전날 숙소는 그날의 출발점이다).

- **좌표 없는 장소는 거리순에서 빠진다**(BE 판단, 주변 조회와 같다). 같은 필터로 `/places` 에는 있던 곳이
  여기서는 0건일 수 있어, 0건 설명 뒤에 그 사실을 덧붙인다(`PlaceListSection.emptyNote`).
- **검색어 0건이면 검색어를 되돌려 준다** (#1220). 목록 보기가 `keyword={filters.keyword}` 를 넘긴다 —
  `/places` 목록 · 지도 SDK 폴백과 같다. 처음(#1217)에는 0건 설명을 통째로 바꾸는 prop 이라 검색어 문구가
  좌표 안내를 덮었다. 두 사실이 함께 참이라 **바꾸지 않고 덧붙인다**: `‘카페’ 로 찾은 장소가 없어요` ·
  `다른 말로 찾거나 필터를 바꿔 보세요. 위치 정보가 없는 곳은 가까운 순 목록에 나오지 않아요.`
