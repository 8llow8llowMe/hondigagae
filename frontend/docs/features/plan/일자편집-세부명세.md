# E. 일자 편집모드 (이슈 B)

## E0. 화면 정의

- **경로**: `/plans/[planId]` **안의 모드**다. 새 라우트를 만들지 않는다.
- **인증**: 필요 (상세와 동일 — `proxy.ts` 가 `/plans` 로 이미 덮는다)
- **진입**: 일자 섹션의 `순서 편집` 버튼
- **이탈**: `저장` 성공 · `취소` · 이탈 경고 후 페이지 이동

**편집은 한 번에 한 일자만 연다.** 일괄 교체 단위가 일자이기 때문이다 (아트보드 03 주석).
다른 일자의 `순서 편집` 을 누르면 열려 있던 편집을 어떻게 할지 먼저 묻는다(E4).

## E1. 계약 — `PUT /api/v1/plans/{planId}/days/{day}/items`

**해당 일차의 항목을 요청 본문 목록으로 통째로 교체한다.** 부분 수정이 아니다.
빈 목록을 보내면 그 일차 항목이 모두 삭제된다.

```ts
type PlanDayItemsReplacePayload = {
  items: {
    day: number // **1 이상이어야 한다** — 아래 규칙 5
    sequence: number // 0부터
    itemType: PlanItemTypeCode // NotNull
    targetId?: string // Long. PLACE/MEAL/LODGING = place.id, WALK = walk_course.id
    title: string // NotBlank, 100자 이하
    memo?: string // 500자 이하
    startTime?: string // 'HH:mm:ss'
  }[]
}
```

응답은 **`PlanDetailResponse` 통째로** 온다 (그 일자만이 아니다).

| 오류                    | 코드       | HTTP | 언제                                              |
| ----------------------- | ---------- | ---- | ------------------------------------------------- |
| `PLAN_DAY_OUT_OF_RANGE` | `PLAN_002` | 400  | `day < 1` 또는 `day > totalDays`                  |
| `NOT_FOUND_PLAN_PLACE`  | `PLAN_004` | 400  | 장소 항목의 `targetId` 를 tour-service 가 못 찾음 |
| `INVALID_REQUEST`       | `PLAN_100` | 400  | Bean Validation (`title` 빈 값 · 100자 초과 등)   |
| `NOT_FOUND_PLAN`        | `PLAN_001` | 404  | 없는 일정 · **남의 일정**                         |

### 반드시 지킬 것 다섯

1. **`targetId` 를 JSON 숫자로 만들지 않는다.** 요청은 `Long` 인데 `placeId` 는 Snowflake 라
   `Number()` 로 바꾸면 정밀도를 잃는다(예: `212481712381923328` > `Number.MAX_SAFE_INTEGER`).
   **문자열 그대로 실어 보내고 Jackson 이 `Long` 으로 읽게 한다** — 생성 요청의 `petId` 와
   같은 처리다 (공통명세 S1).

2. **`memo` 와 `startTime` 을 반드시 되돌려 보낸다.** 일괄 교체라 빼먹으면 **순서만 바꿨는데
   메모와 시각이 지워진다.** 상세 화면이 `startTime` 을 표시하지 않는다는 것과 무관하다 —
   표시하지 않을 뿐 보존해야 한다.

3. **`planItemId` 는 요청에 없고, 저장하면 전부 바뀐다.** 서버가 삭제 후 재삽입한다
   (`PlanCommandProcessor.replaceDayItems`). React key 와 편집 로컬 상태를 `planItemId` 로
   잡으면 저장 직후 전부 새 id 로 갈리므로, **저장 성공 시 편집 상태를 통째로 버린다.**

4. **`sequence` 는 저장 직전에 0부터 다시 매긴다.** 화면의 배열 순서가 정본이다.

5. **`day` 는 1 이상으로 보낸다.** 서버가 경로 변수 값으로 덮어쓰지만 **덮어쓰기는 `toCommand()` 안에서 일어나고 Bean Validation 은 그보다 먼저 돈다.** `PlanItemRequest.day` 에 `@Min(1)` 이 걸려 있어 `0` 이나 음수를 보내면 덮어쓰기에 닿기 전에 `PLAN_100` 으로 막힌다. **경로의 `day` 를 그대로 실어 보낸다.**

### `PLAN_004` 는 재시도로 풀리지 않는다

`verifyPlaceTargets` 는 **delisting 된 장소도 걸러낸다** (`PlaceVerifyQueryPort`). 즉
**원천에서 사라진 장소가 이미 담겨 있는 일자는, 아무것도 추가하지 않고 순서만 바꿔도
저장이 400 으로 막힌다.**

서버는 어느 항목인지 알려주지 않는다. 화면이 **상세에서 이미 알고 있는 정보로 짚는다** —
항목 보강(`GET /places/{placeId}`, 세부명세 A D3)이 **404 를 낸 항목이 원인 후보**다.

- 편집모드에 들어갈 때 그런 항목이 있으면 **미리** 그 행에 표시한다
- 저장 실패 `PLAN_004` 면 그 행을 가리키며 "이 곳은 더 이상 조회되지 않아 함께 저장할 수
  없어요. 목록에서 빼면 저장할 수 있어요." 로 안내한다
- **`다시 시도` 를 주지 않는다** — 같은 본문을 다시 보내면 같은 400 이다

## E2. 컴포넌트 구성

| 컴포넌트              | 신규/기존 | 위치                                       | 비고                                   |
| --------------------- | --------- | ------------------------------------------ | -------------------------------------- |
| `PlanDayEditor`       | 신규      | `features/plan/plan-day-editor.tsx`        | 편집 중인 일자 전체 (표시 + 컨트롤)    |
| `PlanEditableItemRow` | 신규      | `features/plan/plan-editable-item-row.tsx` | 썸네일 없는 낮은 행 · 이동 · 삭제/복구 |
| `usePlanDayEdit`      | 신규      | `features/plan/use-plan-day-edit.ts`       | 편집 로컬 상태 + 저장 mutation         |
| `planDayItemsPayload` | 신규      | `src/lib/plan/day-items.ts`                | 순수 함수 — 편집 상태 → 요청 본문      |

**재사용**: `Button` · `ConfirmModal` · `FormAlert` · `Surface` ·
기존 이탈 경고 훅 — 실제 파일명은 **`src/lib/form/use-unsaved-warning.ts`** 다
(`useUnsavedWarning`). `beforeunload` 만 다루고 App Router 내 라우트 이동은 경고하지
않는다는 한계도 그대로 물려받는다.

**드래그 라이브러리를 새로 넣지 않는다.** 의존성 추가 없이 `Alt+↑/↓` 와 이동 버튼으로
재정렬하고, 포인터 드래그는 HTML5 draggable 로만 얹는다. 접근성 경로가 **주**고 드래그가
보조다 (아트보드 03 주석이 `Alt+↑/↓` 를 "드래그 대안" 이라 부르지만, 순서를 뒤집는다).

## E3. 데이터 흐름

```text
순서 편집 클릭
  → 그 일자 항목을 로컬 배열로 복사 (서버 상태를 건드리지 않는다)
  → 순서 바꾸기 / 삭제 표시  (전부 로컬)
  → 저장  → PUT /plans/{planId}/days/{day}/items
             성공: 응답(PlanDetailResponse)으로 setQueryData + 편집 상태 폐기
             실패: 편집 상태 유지 + 오류 표시
```

| 항목            | 내용                                                               |
| --------------- | ------------------------------------------------------------------ |
| API             | `PUT /plans/{planId}/days/{day}/items`                             |
| mutation 후     | 응답으로 `planKeys.detail(planId)` 를 **`setQueryData`**           |
| invalidate      | `planKeys.weather(planId)` — 항목이 바뀌면 그날 기준 장소가 바뀐다 |
| 낙관적 업데이트 | **하지 않는다**                                                    |

- **낙관적 업데이트를 하지 않는 이유**: `planItemId` 가 서버에서 새로 발급되고, `PLAN_004`
  처럼 재시도로 풀리지 않는 실패가 있다. 아트보드가 "저장하기 전까지는 아무것도 바뀌지
  않아요" 를 화면에 써 둔 것과 같은 태도다.
- **판정을 invalidate 하는 이유**: `PlanDayWeatherItem` 은 그날 **첫 장소 항목**을 기준으로
  판정한다(컨트롤러 설명). 순서를 바꾸면 기준 장소가 바뀐다.

## E4. 상호작용

| 트리거                  | 동작                                       | 결과                                                       |
| ----------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| `순서 편집`             | 그 일자를 편집모드로                       | 썸네일이 사라지고 행이 낮아진다                            |
| `Alt+↑` / `Alt+↓`       | 항목을 한 칸 이동                          | 포커스가 따라간다                                          |
| 위/아래 이동 버튼       | 같음                                       | 맨 위/맨 아래에서는 `disabled`                             |
| 드래그                  | 같음                                       | 포인터 전용 보조 경로                                      |
| 항목 `삭제`             | **취소선 + `복구`** — 목록에서 빼지 않는다 | 저장 시점에 반영                                           |
| `복구`                  | 취소선 해제                                |                                                            |
| `저장`                  | `PUT …/days/{day}/items`                   | 성공 → 편집 종료. 실패 → 편집 유지 + 오류                  |
| `취소`                  | 변경이 있으면 확인 후 폐기                 | `ConfirmModal`                                             |
| 다른 일자의 `순서 편집` | 변경이 있으면 확인 후 전환                 | 같은 모달                                                  |
| 편집 중 페이지 이탈     | 이탈 경고                                  | 기존 이탈 경고 훅 재사용                                   |
| 전부 삭제 후 `저장`     | `items: []` 로 보낸다                      | 그 일자가 빈다. **막지 않는다** — 서버가 허용하는 동작이다 |

### 편집 중에는 두 가지를 하지 않는다

- **이동 거리를 다시 계산하지 않는다.** 순서를 옮길 때마다 숫자가 흔들리면 신뢰가 깨진다.
  대신 `이동 거리는 저장 후 다시 계산돼요` 를 그 자리에 둔다 (아트보드 03).
- **썸네일을 감춘다.** 드래그 대상은 순서지 사진이 아니다. 행이 낮아져 재정렬이 쉬워진다.

## E6. 접근성

- 편집 목록은 `<ol>`. 각 행의 이동 버튼에 `aria-label="위로 이동"` / `"아래로 이동"`.
- **키보드만으로 완결된다** — `Alt+↑/↓` 가 주 경로다. 드래그는 보조다.
- 이동 후 **포커스가 옮겨진 항목을 따라간다.** 안 그러면 연속 이동이 불가능하다.
  > **구현: 행이 아니라 이동 버튼에 포커스를 둔다.** 행에 `tabIndex` + `onKeyDown` 을
  > 얹으면 역할 없는 요소가 상호작용을 갖게 되어(`jsx-a11y/no-static-element-interactions`)
  > 스크린리더가 무엇을 눌러야 하는지 말하지 못한다. 조작하는 것은 이미 네이티브
  > `button` 인 이동 버튼이므로 거기에 포커스를 옮기고 `Alt+↑/↓` 도 거기서 받는다.
  > **경계에서 같은 방향 버튼이 `disabled` 가 되면 반대쪽 버튼으로 옮긴다** — disabled
  > 요소는 포커스를 받지 못해 그대로 두면 포커스가 사라진다.
- 순서 변경·삭제 표시를 `aria-live="polite"` 로 알린다 (`3번째로 이동했어요` / `삭제 예정이에요`).
- 삭제는 **취소선(시각) + 문구(`저장하면 삭제돼요`)** 로 이중 전달한다. 색·선만으로 알리지 않는다.
- 저장 버튼은 변경이 없으면 `disabled` — 그 이유를 `aria-describedby` 로 준다.
- 터치 영역 44px.

## E7. 테스트 케이스

**순수 로직 (`src/lib/plan/day-items.ts`)**

- `planDayItemsPayload()` — 삭제 표시 항목이 빠지고 `sequence` 가 0부터 다시 매겨진다
- **`memo` · `startTime` · `itemType` · `targetId` 가 그대로 실린다** (회귀 방지 핵심)
- **`targetId` 가 문자열로 실린다** — `212481712381923328` 이 정밀도를 잃지 않는다
- `targetId` 가 null 인 항목(`MOVE`)은 키 자체를 넣지 않는다
- 전부 삭제 → `items: []`
- **`day` 가 경로값 그대로 실린다** — `0` 을 보내면 `@Min(1)` 에 걸린다 (규칙 5)
- 이동 로직 — 맨 위에서 위로 / 맨 아래에서 아래로 는 배열이 그대로

**렌더 분기**

- 편집 중에는 썸네일이 없고 거리 문구가 안내 문장으로 바뀐다
- 삭제 표시 행에 취소선 + `복구` + `저장하면 삭제돼요`
- 저장 실패 5xx → `다시 시도` **있음**
- 저장 실패 `PLAN_004` → `다시 시도` **없음** + 해당 안내
- 편집 상태가 실패 후에도 남아 있다
- 조회 404 항목이 있으면 편집 진입 시 미리 표시된다

**접근성 계약**

- 이동 버튼 `aria-label`, 경계에서 `disabled`
- `aria-live` 영역 존재

**mock**

`plan-data.ts` 에 일괄 교체를 추가한다. `day` 범위 밖 → `PLAN_002`, 존재하지 않는
`targetId` → `PLAN_004`, `title` 빈 값/100자 초과 → `PLAN_100`.
**저장하면 `planItemId` 를 새로 발급한다** — 서버와 같아야 3번 규칙을 테스트할 수 있다.

| 4   | 저장 성공 후 판정 재조회 타이밍 | ① 즉시 invalidate ② 사용자가 요청할 때 | **①.** 기준 장소가 바뀌면 판정도 바뀐다                               |

# F. 장소 추가 · 실내 대안 담기 (이슈 C)

## F0. 화면 정의

- **장소 추가**: 일자 섹션의 `장소 추가` 버튼
- **실내 대안 담기**: 일자 판정 아래 `비가 오면 갈 만한 실내` 블록의 `담기` 버튼

둘 다 **그 일자의 항목 배열 끝에 하나를 붙여 E1 의 일괄 교체로 저장**한다. 새 API 는 없다.

## F1. 실내 대안 담기 — 가벼운 쪽

`PlanDayWeatherItem.indoorAlternatives` 는 `{ placeId, title }` 뿐이다. 이것만으로 항목을
만들 수 있다.

```ts
{ itemType: 'PLACE', targetId: placeId, title, sequence: <끝>, day: <경로값> }
```

- **아트보드의 `서귀포시 안덕면 · 실내 · 12.4km` 는 계약에 없다.** `placeId`·`title` 뿐이다.
  → `GET /places/{placeId}` 로 보강한다 (상세 항목 보강과 같은 방식·같은 캐시).
- **비 예보가 없는 일자에는 `indoorAlternatives` 가 비어 온다** — 그때는 블록을 렌더하지
  않는다. 빈 배열을 "대안 없음" 으로 쓰지 않는다.
- `담기` 성공 → 그 항목이 일자 맨 아래에 붙는다. 판정 invalidate 는 E3 과 동일.
- **이미 담긴 장소를 또 담을 수 있다.** 서버가 중복을 막지 않는다. 화면이 먼저 막는다 —
  그 일자에 같은 `targetId` 가 있으면 `담기` 대신 `이미 담았어요` 를 보여준다.

## F2. 장소 추가 — 무거운 쪽

`장소 추가` 는 **장소를 고르는 화면**이 필요하다. 아트보드에 그 화면이 없다.

**추천: 새 라우트 `/plans/[planId]/days/[day]/add`.**

- 상태를 URL 이 갖는다 → 뒤로가기가 자연스럽고 새로고침에서 살아남는다
  (`architecture-guide.md` §10 — URL 이 기본)
- 기존 장소 목록(`features/place/`)의 조회 훅·행 컴포넌트를 재사용한다
- 고르면 그 일자로 돌아가 **바로 일괄 교체를 저장**한다 (별도 확인 없음 — 되돌리기가 쉽다)
- **모달/시트로 하지 않는 이유**: 장소 목록은 필터 + 무한 스크롤이라 모달에 담기 무겁고,
  모달 안에서 무한 스크롤을 돌리면 배경 스크롤 잠금과 충돌한다

## F3. 계약 주의

- 추가하는 항목의 `itemType` 은 **`PLACE` 고정**이다. `MEAL`/`LODGING` 구분은 이 이슈에서
  하지 않는다 — 아트보드에 유형 선택 UI 가 없다. **`WALK` 는 만들 수 없다** (`walk_course`
  조회 API 가 없다, 백엔드 `PLACE_TARGET_TYPES` 주석의 TODO).
- `title` 은 **장소의 `title` 을 복사**한다. 서버가 100자로 자르지 않고 400 을 낸다 →
  **100자를 넘으면 잘라서 보낸다.**
- `targetId` 는 **문자열로** 보낸다 (E1 규칙 1).
- **delisting 된 장소는 목록에 나오지 않는다** → 목록에서 고른 장소는 `PLAN_004` 가 나지
  않는다. 단 **같은 일자에 이미 있던 다른 항목** 때문에 실패할 수 있다 (E1 참고).

## F4. 상태별 화면

| 상태                           | 표시                 | 문구 (확정)                                         |
| ------------------------------ | -------------------- | --------------------------------------------------- |
| 대안 없음 (`[]`)               | **블록 자체를 숨김** | —                                                   |
| 이미 담긴 대안                 | 버튼 비활성          | `이미 담았어요`                                     |
| 담기/추가 성공                 | 토스트               | `{title}을(를) N일차에 담았어요` (조사 처리 재사용) |
| 담기/추가 실패 (5xx)           | 토스트 + 재시도      | `담지 못했어요. 잠시 후 다시 시도해 주세요.`        |
| 담기/추가 실패 `PLAN_004`      | 토스트, 재시도 없음  | E5 와 같은 문구                                     |
| 고를 장소가 없음 (필터 결과 0) | `EmptyState`         | 장소 목록 화면의 기존 문구 재사용                   |

조사(`을/를`)는 기존 `withObjectParticle()`(`src/lib/text/korean.ts`) 을 쓴다.
