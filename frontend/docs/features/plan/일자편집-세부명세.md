# E. 일자 편집모드 (이슈 B)

## E0. 화면 정의

- **경로**: `/plans/[planId]` **안의 모드**다. 새 라우트를 만들지 않는다.
- **인증**: 필요 (상세와 동일 — `proxy.ts` 가 `/plans` 로 이미 덮는다)
- **진입**: 일자 섹션의 `순서 편집` 버튼
- **이탈**: `저장` 성공 · `취소` · 이탈 경고 후 페이지 이동

**편집은 한 번에 한 일자만 연다.** 일괄 교체 단위가 일자이기 때문이다 (아트보드 03 주석).
다른 일자의 `순서 편집` 을 누르면 열려 있던 편집을 어떻게 할지 먼저 묻는다(E4).

## E1. 계약 — `PUT /api/v1/plans/{planId}/days/{day}/items`

**해당 일차의 항목을 요청 본문 목록으로 통째로 교체한다.** 부분 수정이 아니다.
빈 목록을 보내면 그 일차 항목이 모두 삭제된다.

```ts
type PlanDayItemsReplacePayload = {
  items: {
    day: number // **1 이상이어야 한다** — 아래 규칙 5
    sequence: number // 0부터
    itemType: PlanItemTypeCode // NotNull
    targetId?: string // Long. PLACE/MEAL/LODGING = place.id, WALK = walk_course.id
    title: string // NotBlank, 100자 이하
    memo?: string // 500자 이하
    startTime?: string // 'HH:mm:ss'
  }[]
}
```

응답은 **`PlanDetailResponse` 통째로** 온다 (그 일자만이 아니다).

| 오류                    | 코드       | HTTP | 언제                                              |
| ----------------------- | ---------- | ---- | ------------------------------------------------- |
| `PLAN_DAY_OUT_OF_RANGE` | `PLAN_002` | 400  | `day < 1` 또는 `day > totalDays`                  |
| `NOT_FOUND_PLAN_PLACE`  | `PLAN_004` | 400  | 장소 항목의 `targetId` 를 tour-service 가 못 찾음 |
| `INVALID_REQUEST`       | `PLAN_100` | 400  | Bean Validation (`title` 빈 값 · 100자 초과 등)   |
| `NOT_FOUND_PLAN`        | `PLAN_001` | 404  | 없는 일정 · **남의 일정**                         |

### 반드시 지킬 것 다섯

1. **`targetId` 를 JSON 숫자로 만들지 않는다.** 요청은 `Long` 인데 `placeId` 는 Snowflake 라
   `Number()` 로 바꾸면 정밀도를 잃는다(예: `212481712381923328` > `Number.MAX_SAFE_INTEGER`).
   **문자열 그대로 실어 보내고 Jackson 이 `Long` 으로 읽게 한다** — 생성 요청의 `petId` 와
   같은 처리다 (공통명세 S1).

2. **`memo` 와 `startTime` 을 반드시 되돌려 보낸다.** 일괄 교체라 빼먹으면 **순서만 바꿨는데
   메모와 시각이 지워진다.** 상세 화면이 `startTime` 을 표시하지 않는다는 것과 무관하다 —
   표시하지 않을 뿐 보존해야 한다.

3. **`planItemId` 는 요청에 없고, 저장하면 전부 바뀐다.** 서버가 삭제 후 재삽입한다
   (`PlanCommandProcessor.replaceDayItems`). React key 와 편집 로컬 상태를 `planItemId` 로
   잡으면 저장 직후 전부 새 id 로 갈리므로, **저장 성공 시 편집 상태를 통째로 버린다.**

4. **`sequence` 는 저장 직전에 0부터 다시 매긴다.** 화면의 배열 순서가 정본이다.

5. **`day` 는 1 이상으로 보낸다.** 서버가 경로 변수 값으로 덮어쓰지만 **덮어쓰기는 `toCommand()` 안에서 일어나고 Bean Validation 은 그보다 먼저 돈다.** `PlanItemRequest.day` 에 `@Min(1)` 이 걸려 있어 `0` 이나 음수를 보내면 덮어쓰기에 닿기 전에 `PLAN_100` 으로 막힌다. **경로의 `day` 를 그대로 실어 보낸다.**

### `PLAN_004` 는 재시도로 풀리지 않는다

`verifyPlaceTargets` 는 **delisting 된 장소도 걸러낸다** (`PlaceVerifyQueryPort`). 즉
**원천에서 사라진 장소가 이미 담겨 있는 일자는, 아무것도 추가하지 않고 순서만 바꿔도
저장이 400 으로 막힌다.**

서버는 어느 항목인지 알려주지 않는다. 화면이 **상세에서 이미 알고 있는 정보로 짚는다** —
**장소를 가리키는데 `item.place` 가 비어 온 항목이 원인 후보**다
(`hasUnresolvedPlace()`, 세부명세 A D3).

> **#115 이전에는 항목당 `GET /places/{placeId}` 가 404 를 낸 id 집합으로 짚었다.**
> #86 이 요약을 상세 응답에 실으면서 그 조회가 사라졌고, 판정 근거도 `place === null` 로
> 옮겼다. **대신 원인이 하나 더 섞인다** — 404(delisting)만이 아니라 tour-service 일시
> 장애도 같은 모양이다. 그래서 **문구가 원인을 단정하지 않는다**: "이 곳은 더 이상
> 조회되지 않아요" 는 둘 다에 맞는 서술이고, 사용자가 취할 행동(목록에서 빼면 저장된다)도
> 둘 다 같다.

- 편집모드에 들어갈 때 그런 항목이 있으면 **미리** 그 행에 표시한다
- 저장 실패 `PLAN_004` 면 그 행을 가리키며 "이 곳은 더 이상 조회되지 않아 함께 저장할 수
  없어요. 목록에서 빼면 저장할 수 있어요." 로 안내한다
- **`다시 시도` 를 주지 않는다** — 같은 본문을 다시 보내면 같은 400 이다

## E2. 컴포넌트 구성

| 컴포넌트              | 신규/기존 | 위치                                       | 비고                                   |
| --------------------- | --------- | ------------------------------------------ | -------------------------------------- |
| `PlanDayEditor`       | 신규      | `features/plan/plan-day-editor.tsx`        | 편집 중인 일자 전체 (표시 + 컨트롤)    |
| `PlanEditableItemRow` | 신규      | `features/plan/plan-editable-item-row.tsx` | 썸네일 없는 낮은 행 · 이동 · 삭제/복구 |
| `usePlanDayEdit`      | 신규      | `features/plan/use-plan-day-edit.ts`       | 편집 로컬 상태 + 저장 mutation         |
| `planDayItemsPayload` | 신규      | `src/lib/plan/day-items.ts`                | 순수 함수 — 편집 상태 → 요청 본문      |

**재사용**: `Button` · `ConfirmModal` · `FormAlert` · `Surface` ·
기존 이탈 경고 훅 — 실제 파일명은 **`src/lib/form/use-unsaved-warning.ts`** 다
(`useUnsavedWarning`). `beforeunload` 만 다루고 App Router 내 라우트 이동은 경고하지
않는다는 한계도 그대로 물려받는다.

**드래그 라이브러리를 새로 넣지 않는다.** 의존성 추가 없이 `Alt+↑/↓` 와 이동 버튼으로
재정렬한다. 접근성 경로가 **주**고 드래그가 보조다 (아트보드 03 주석이 `Alt+↑/↓` 를
"드래그 대안" 이라 부르지만, 순서를 뒤집는다).

**HTML5 draggable 이 아니라 Pointer Events 다** (#159 · `use-drag-reorder.ts`).
`dragstart` 계열은 터치에서 아예 발생하지 않아 모바일에서 기능이 사라진다 — 이 앱은
모바일이 먼저다. 이 문단의 "HTML5 draggable 로 얹는다" 는 착수 전 판단이었고 구현에서
뒤집혔다.

**가장자리에서 화면이 따라 스크롤한다** (#161). 목록이 화면보다 길면 1번을 8번 자리로
옮기려다 손이 화면 밖으로 나가, 놓고 스크롤하고 다시 잡아야 했다. 판정은
`lib/plan/auto-scroll.ts` 의 순수 함수이고 규칙은 셋이다.

- 뷰포트 위·아래 **60px** 안에 들어오면 그 방향으로 스크롤한다. 밖이면 **아무 일도 하지
  않는다** — 짧은 목록에서 드래그해도 화면이 움직이지 않는 근거다
- 속도는 **깊이 비례**다(최대 14px/프레임). 일정 속도면 조금 걸쳤을 때 너무 빠르고 끝까지
  밀었을 때 너무 느리다. 화면 밖으로 나가도 최대치를 넘지 않는다
- **스크롤한 프레임마다 중간선 판정을 다시 부른다.** 손이 멈춰 있어도 화면이 흐르면 행이
  움직이므로, `pointermove` 만 보면 스크롤만 되고 순서는 안 바뀐다

## E3. 데이터 흐름

```text
순서 편집 클릭
  → 그 일자 항목을 로컬 배열로 복사 (서버 상태를 건드리지 않는다)
  → 순서 바꾸기 / 삭제 표시  (전부 로컬)
  → 저장  → PUT /plans/{planId}/days/{day}/items
             성공: 응답(PlanDetailResponse)으로 setQueryData + 편집 상태 폐기
             실패: 편집 상태 유지 + 오류 표시
```

| 항목            | 내용                                                               |
| --------------- | ------------------------------------------------------------------ |
| API             | `PUT /plans/{planId}/days/{day}/items`                             |
| mutation 후     | 응답으로 `planKeys.detail(planId)` 를 **`setQueryData`**           |
| invalidate      | `planKeys.weather(planId)` — 항목이 바뀌면 그날 기준 장소가 바뀐다 |
| 낙관적 업데이트 | **하지 않는다**                                                    |

- **낙관적 업데이트를 하지 않는 이유**: `planItemId` 가 서버에서 새로 발급되고, `PLAN_004`
  처럼 재시도로 풀리지 않는 실패가 있다. 아트보드가 "저장하기 전까지는 아무것도 바뀌지
  않아요" 를 화면에 써 둔 것과 같은 태도다.
- **판정을 invalidate 하는 이유**: `PlanDayWeatherItem` 은 그날 **첫 장소 항목**을 기준으로
  판정한다(컨트롤러 설명). 순서를 바꾸면 기준 장소가 바뀐다.

## E4. 상호작용

| 트리거                  | 동작                                       | 결과                                                       |
| ----------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| `순서 편집`             | 그 일자를 편집모드로                       | 썸네일이 사라지고 행이 낮아진다                            |
| `Alt+↑` / `Alt+↓`       | 항목을 한 칸 이동                          | 포커스가 따라간다                                          |
| 위/아래 이동 버튼       | 같음                                       | 맨 위/맨 아래에서는 `disabled`                             |
| 드래그                  | 같음                                       | 포인터 전용 보조 경로                                      |
| 항목 `삭제`             | **취소선 + `복구`** — 목록에서 빼지 않는다 | 저장 시점에 반영                                           |
| `복구`                  | 취소선 해제                                |                                                            |
| `저장`                  | `PUT …/days/{day}/items`                   | 성공 → 편집 종료. 실패 → 편집 유지 + 오류                  |
| `취소`                  | 변경이 있으면 확인 후 폐기                 | `ConfirmModal`                                             |
| 다른 일자의 `순서 편집` | 변경이 있으면 확인 후 전환                 | 같은 모달                                                  |
| 편집 중 페이지 이탈     | 이탈 경고                                  | 기존 이탈 경고 훅 재사용                                   |
| 전부 삭제 후 `저장`     | `items: []` 로 보낸다                      | 그 일자가 빈다. **막지 않는다** — 서버가 허용하는 동작이다 |

### 편집 중에는 두 가지를 하지 않는다

- **이동 거리를 다시 계산하지 않는다.** 순서를 옮길 때마다 숫자가 흔들리면 신뢰가 깨진다.
  대신 `이동 거리는 저장 후 다시 계산돼요` 를 그 자리에 둔다 (아트보드 03).
- **썸네일을 감춘다.** 드래그 대상은 순서지 사진이 아니다. 행이 낮아져 재정렬이 쉬워진다.

## E6. 접근성

- 편집 목록은 `<ol>`. 각 행의 이동 버튼에 `aria-label="위로 이동"` / `"아래로 이동"`.
- **키보드만으로 완결된다** — `Alt+↑/↓` 가 주 경로다. 드래그는 보조다.
- 이동 후 **포커스가 옮겨진 항목을 따라간다.** 안 그러면 연속 이동이 불가능하다.
  > **구현: 행이 아니라 이동 버튼에 포커스를 둔다.** 행에 `tabIndex` + `onKeyDown` 을
  > 얹으면 역할 없는 요소가 상호작용을 갖게 되어(`jsx-a11y/no-static-element-interactions`)
  > 스크린리더가 무엇을 눌러야 하는지 말하지 못한다. 조작하는 것은 이미 네이티브
  > `button` 인 이동 버튼이므로 거기에 포커스를 옮기고 `Alt+↑/↓` 도 거기서 받는다.
  > **경계에서 같은 방향 버튼이 `disabled` 가 되면 반대쪽 버튼으로 옮긴다** — disabled
  > 요소는 포커스를 받지 못해 그대로 두면 포커스가 사라진다.
- 순서 변경·삭제 표시를 `aria-live="polite"` 로 알린다 (`3번째로 이동했어요` / `삭제 예정이에요`).
- 삭제는 **취소선(시각) + 문구(`저장하면 삭제돼요`)** 로 이중 전달한다. 색·선만으로 알리지 않는다.
- 저장 버튼은 변경이 없으면 `disabled` — 그 이유를 `aria-describedby` 로 준다.
- 터치 영역 44px.

## E7. 테스트 케이스

**순수 로직 (`src/lib/plan/day-items.ts`)**

- `planDayItemsPayload()` — 삭제 표시 항목이 빠지고 `sequence` 가 0부터 다시 매겨진다
- **`memo` · `startTime` · `itemType` · `targetId` 가 그대로 실린다** (회귀 방지 핵심)
- **`targetId` 가 문자열로 실린다** — `212481712381923328` 이 정밀도를 잃지 않는다
- `targetId` 가 null 인 항목(`MOVE`)은 키 자체를 넣지 않는다
- 전부 삭제 → `items: []`
- **`day` 가 경로값 그대로 실린다** — `0` 을 보내면 `@Min(1)` 에 걸린다 (규칙 5)
- 이동 로직 — 맨 위에서 위로 / 맨 아래에서 아래로 는 배열이 그대로

**렌더 분기**

- 편집 중에는 썸네일이 없고 거리 문구가 안내 문장으로 바뀐다
- 삭제 표시 행에 취소선 + `복구` + `저장하면 삭제돼요`
- 저장 실패 5xx → `다시 시도` **있음**
- 저장 실패 `PLAN_004` → `다시 시도` **없음** + 해당 안내
- 편집 상태가 실패 후에도 남아 있다
- `place` 가 비어 온 장소 항목이 있으면 편집 진입 시 미리 표시된다
- **`WALK` 은 `place` 가 비어도 표시하지 않는다** — 애초에 물어볼 장소가 없다

**접근성 계약**

- 이동 버튼 `aria-label`, 경계에서 `disabled`
- `aria-live` 영역 존재

**mock**

`plan-data.ts` 에 일괄 교체를 추가한다. `day` 범위 밖 → `PLAN_002`, 존재하지 않는
`targetId` → `PLAN_004`, `title` 빈 값/100자 초과 → `PLAN_100`.
**저장하면 `planItemId` 를 새로 발급한다** — 서버와 같아야 3번 규칙을 테스트할 수 있다.

# F. 장소 추가 · 실내 대안 담기 (이슈 C)

## F0. 화면 정의

- **장소 추가**: 일자 섹션의 `장소 추가` 버튼
- **실내 대안 담기**: 일자 판정 아래 `비가 오면 갈 만한 실내` 블록의 `담기` 버튼

둘 다 **그 일자의 항목 배열 끝에 하나를 붙여 E1 의 일괄 교체로 저장**한다. 새 API 는 없다.

## F1. 실내 대안 담기 — 가벼운 쪽

`PlanDayWeatherItem.indoorAlternatives` 는 `{ placeId, title }` 뿐이다. 이것만으로 항목을
만들 수 있다.

```ts
{ itemType: 'PLACE', targetId: placeId, title, sequence: <끝>, day: <경로값> }
```

- **아트보드의 `서귀포시 안덕면 · 실내 · 12.4km` 는 계약에 없다.** `placeId`·`title` 뿐이다.
  → `GET /places/{placeId}` 로 보강한다 (`placeKeys.detail` 캐시를 장소 상세와 공유한다).
  > **정정 (구현 중 소스 실측):** 위 문장의 "계약에 없다" 는 **`placeId`·`title` 에만
  > 해당한다.** `PlanAlternativePlaceItem` 은 실제로 **5필드**이고
  > (`placeId` · `title` · `lat` · `lng` · **`distanceMeters`**), 아트보드의 `12.4km` 는
  > 그중 `distanceMeters` 다. FE 타입이 두 필드만 선언하고 있어 없는 줄 알았던 것이다.
  >
  > - 기준점은 **그날 대표 장소**(`representativePlaceId`)다 — 스키마 설명
  >   "그날 기준 장소로부터의 거리(m)" · `PlanWeatherPresenter#toAlternativeItems`
  > - 계산은 `GeoDistance.meters()` **하버사인**이라 **직선거리**다 →
  >   표기에 **`직선` 을 반드시 붙인다** (D3 과 같은 규칙). `직선 12.4km`
  > - **화면이 재지 않는다.** `haversineMeters` 를 부르지 않고 서버 값을 그대로 쓴다
  >
  > 보강(`GET /places/{id}`)에서 오는 것은 **주소와 실내 여부뿐**이고, 거리는 보강을
  > 기다리지 않는다.
  >
  > **#115 이후 보강은 실내 대안뿐이다.** 항목은 상세 응답이 `place` 를 함께 주므로
  > 목록에서 빠졌고, 대상 id 는 `alternativePlaceIds(alternatives)` 가 중복만 제거해
  > 만든다 — 같은 장소가 두 일자의 대안일 수 있다.
- **비 예보가 없는 일자에는 `indoorAlternatives` 가 비어 온다** — 그때는 블록을 렌더하지
  않는다. 빈 배열을 "대안 없음" 으로 쓰지 않는다.
- `담기` 성공 → 그 항목이 일자 맨 아래에 붙는다. 판정 invalidate 는 E3 과 동일.
- **이미 담긴 장소를 또 담을 수 있다.** 서버가 중복을 막지 않는다. 화면이 먼저 막는다 —
  그 일자에 같은 `targetId` 가 있으면 `담기` 대신 `이미 담았어요` 를 보여준다.

## F2. 장소 추가 — 무거운 쪽

`장소 추가` 는 **장소를 고르는 화면**이 필요하다. 아트보드에 그 화면이 없다.

**추천: 새 라우트 `/plans/[planId]/days/[day]/add`.**

- 상태를 URL 이 갖는다 → 뒤로가기가 자연스럽고 새로고침에서 살아남는다
  (`architecture-guide.md` §10 — URL 이 기본)
- 기존 장소 목록(`features/place/`)의 조회 훅·행 컴포넌트를 재사용한다
- 고르면 그 일자로 돌아가 **바로 일괄 교체를 저장**한다 (별도 확인 없음 — 되돌리기가 쉽다)
- **모달/시트로 하지 않는 이유**: 장소 목록은 필터 + 무한 스크롤이라 모달에 담기 무겁고,
  모달 안에서 무한 스크롤을 돌리면 배경 스크롤 잠금과 충돌한다

> **지도 보기가 붙었다** (#370). 같은 라우트이고 보기는 `?view=` 가 갖는다 — 기본은
> 지도다. 세부는 `docs/features/plan/담기지도-세부명세.md`.

## F3. 계약 주의

- 추가하는 항목의 `itemType` 은 **`PLACE` 고정**이다. `MEAL`/`LODGING` 구분은 이 이슈에서
  하지 않는다 — 아트보드에 유형 선택 UI 가 없다. **`WALK` 는 만들 수 없다** (`walk_course`
  조회 API 가 없다, 백엔드 `PLACE_TARGET_TYPES` 주석의 TODO).
- `title` 은 **장소의 `title` 을 복사**한다. 서버가 100자로 자르지 않고 400 을 낸다 →
  **100자를 넘으면 잘라서 보낸다.**
- `targetId` 는 **문자열로** 보낸다 (E1 규칙 1).
- **delisting 된 장소는 목록에 나오지 않는다** → 목록에서 고른 장소는 `PLAN_004` 가 나지
  않는다. 단 **같은 일자에 이미 있던 다른 항목** 때문에 실패할 수 있다 (E1 참고).

## F4. 상태별 화면

| 상태                           | 표시                    | 문구 (확정)                                         |
| ------------------------------ | ----------------------- | --------------------------------------------------- |
| 대안 없음 (`[]`)               | **블록 자체를 숨김**    | —                                                   |
| 이미 담긴 대안                 | 버튼 비활성             | `이미 담았어요`                                     |
| 담기/추가 성공                 | 토스트                  | `{title}을(를) N일차에 담았어요` (조사 처리 재사용) |
| 담기/추가 실패 (5xx)           | **인라인** `FormAlert`  | `담지 못했어요 잠시 후 다시 시도해 주세요.`         |
| 담기/추가 실패 `PLAN_004`      | **인라인**, 재시도 없음 | 아래 — E5 와 **다른 문구**다                        |
| 고를 장소가 없음 (필터 결과 0) | `EmptyState`            | 장소 목록 화면의 기존 문구 재사용                   |

조사(`을/를`)는 기존 `withObjectParticle()`(`src/lib/text/korean.ts`) 을 쓴다.

### 실패는 **누른 그 자리**에 남는다

"인라인" 만으로는 부족하다. 실측에서 두 번 어긋났다.

- **일자 상세**: 실패 알림이 실내 대안 블록이 있는 **모든 일자**에 떴다. 훅이 화면 전체에
  하나뿐인데 실패에 일자 정보가 없었기 때문이다. → `{ day, placeId }` 로 들고 호출부가
  `failure.target.day === group.day` 로 좁힌다. **진행 표시도 같다** — 같은 장소가 두 일자의
  대안일 수 있어(연속 우천일에 겹친다) `placeId` 만 비교하면 두 행이 함께 스피너를 낸다.
- **장소 추가 화면**: 알림을 헤더에 뒀더니 무한 스크롤 30번째 행에서 실패했을 때 **화면 밖**
  이라 아무 일도 안 일어난 것처럼 보였다. → 실패한 **행 안에** 렌더한다.

### 실패를 토스트로 말하지 않는다 (구현에서 정정)

위 표는 처음에 실패도 토스트로 적었지만, **`src/components/toast.tsx` 가 "오류를 토스트로
말하지 않는다 — 오류는 섹션 안에 남아야 다시 시도할 수 있다" 를 못박고 있다.** 4초 뒤에
사라지는 UI 에 유일한 복구 경로를 두면 안 된다. **성공만 토스트고 실패는 그 자리에
`FormAlert`(`role="alert"`) 로 남는다.** 재시도는 같은 `담기` 버튼을 다시 누르는 것이라
별도 버튼을 두지 않는다.

### `PLAN_004` 문구를 편집모드와 나눈다

분류는 `toPlanDaySaveError`(`src/lib/plan/save-error.ts`)가 **편집모드와 공유한다** — 같은
`PUT …/days/{day}/items` 라 분류가 두 벌이 되면 갈린다. 하지만 **문구는 나눈다**:

| 화면     | `PLAN_004` 문구                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------ |
| 편집모드 | `… 목록에서 빼면 저장할 수 있어요.`                                                              |
| 담기     | `이 일자에 더 이상 조회되지 않는 장소가 있어 담을 수 없어요. 일정에서 그 항목을 먼저 빼 주세요.` |

**담기 화면에는 뺄 목록이 없다.** 원인은 그 일자에 **이미 있던** 항목이고(일괄 교체가 그것까지
되싣는다) 일정으로 돌아가 편집모드에서 빼야 풀린다. 문구까지 공유하면 할 수 없는 일을
지시하게 된다. `PLAN_002` 는 나누지 않는다 — 어느 화면에서든 할 일이 새로고침으로 같다.

### 기간 밖 일자로 직접 들어왔을 때

주소를 손으로 고치면 `/days/9/add` 로 들어올 수 있다. **`totalDays` 를 알아야 판단할 수 있어
라우트가 아니라 화면이 막는다** — 고르고 나서 `PLAN_002` 로 실패하는 것보다 먼저 말한다.

- 경로의 `day` 가 **숫자가 아니거나 `1` 미만**이면 `notFound()` (`@PathVariable int` · `@Min(1)`)
- `day > totalDays` 면 `{day}일차는 이 여행에 없어요` + `이 여행은 총 {totalDays}일이에요.`
  **저장 실패 문구를 재사용하지 않는다** — 그쪽은 "새로고침한 뒤 다시 시도" 인데 새로고침해도
  없는 일자다.

## G0. 어디서 고치나 — 편집모드 안이다

**상세 행에서 바로 고치지 않는다.** 항목 단건 수정 API 가 없고 쓰기 경로가 일괄 교체
하나뿐이라(E1), 행에서 고치게 하면 **행마다 저장 지점이 생기고 그때마다 그 일자 항목이
전부 새 `planItemId` 로 재발급된다** — 옆 행의 방문 체크까지 초기화된다 (D9-2).

그래서 시각은 **`순서 편집` 모드 안**에서 순서·삭제와 같은 한 번의 저장에 실린다.
편집 단위가 일자인 이유(E0)와 같은 이유다.

## G1. 계약 — 키를 빼는 것이 곧 "지운다"

```ts
type PlanItemPayload = {
  // …
  /** `HH:mm:ss`. **키를 빼면 지워진다** — 일괄 교체라 "유지" 가 아니다 */
  startTime?: string
}
```

| 사실                        | 근거                                                                 |
| --------------------------- | -------------------------------------------------------------------- |
| 선택 필드다                 | `PlanItemRequest.startTime` 에 검증 애노테이션이 **없다**            |
| 키 생략 = `null` 저장       | `PlanCommandProcessor` 가 삭제 후 재삽입하며 커맨드 값을 그대로 쓴다 |
| 형식 오류 = `PLAN_100` 400  | 파싱 실패가 `HttpMessageNotReadableException` 으로 잡힌다            |
| 서버가 뜻을 검증하지 않는다 | 순서 역전·중복·`00:00` 전부 통과한다                                 |

**`PUT /plans/{planId}`(부분 수정) 와 반대다.** 저쪽은 키를 빼면 **유지**이고(D3-1 · 예산을
비울 수 없는 이유가 그것이다), 이쪽은 키를 빼면 **삭제**다. 같은 화면 안에 두 규칙이 있으므로
`day-items.ts` 주석과 테스트로 못박는다 (D14-5).

## G2. 화면 — 편집 행 안의 시각 입력

```text
[①]  [ 10:30  ⊗ ]  천지연폭포                    [↑] [↓] [삭제]
```

- 순번 배지(드래그 손잡이) **바로 뒤**, 제목 **앞**이다. 상세 행의 시각 줄(D14-3)과 읽는
  순서가 같다 — 편집에 들어갔다 나올 때 값이 자리를 옮기지 않는다.
- 편집 행은 썸네일이 없어 낮다(E2). 시각 입력이 `h-11`(44px)이라 **행 높이를 입력이 정한다** —
  터치 영역을 줄이려고 높이를 깎지 않는다 (DESIGN.md §7).

### 네이티브 `<input type="time">` 을 쓴다 — `DateField` 와 갈리는 지점

`date-field.tsx` 가 네이티브 날짜 입력을 거부한 근거 넷 중 **둘이 시각에는 해당하지 않는다.**

| `DateField` 의 근거                      | 시각에서는                                      |
| ---------------------------------------- | ----------------------------------------------- |
| `min` 을 넘겨도 왜 못 고르는지 안 보인다 | **막을 범위가 없다.** 과거 시각도 유효한 값이다 |
| 두 날짜의 **관계**를 보여줄 자리가 없다  | **관계가 없다.** 한 항목에 값 하나다            |
| 브라우저마다 조작이 다르다               | 그대로 남는다                                   |
| 빈 값 서식이 플레이스홀더처럼 읽힌다     | 그대로 남는다 (`--:--`)                         |

남은 둘의 값보다 **시간 피커를 새로 만드는 비용**(포털·오버레이·키보드 순회·`useOverlay`
배선)이 크다. 게다가 모바일에서 네이티브 시간 입력은 OS 휠 피커라 손으로 치는 것보다 낫고,
`00:00~23:59` 범위 검증을 브라우저가 이미 한다 — 손으로 치게 하면 `25:00` · `10시 30분` 을
전부 되돌려 줘야 한다.

**`Input` 컴포넌트를 그대로 쓴다.** `type` 은 native prop 으로 통과하고
(`components/input.tsx` `NativeProps`), `className` 에는 **폭 유틸리티만** 준다
(`component-guide.md` §3 — 색·radius·padding 을 덮지 않는다). 새 공통 컴포넌트를 만들지 않는다.

### 지우기 — 값이 있을 때만 선다

네이티브 시간 입력의 "비우기" UI 는 브라우저마다 있고 없다(크롬은 `⊗`, 데스크톱 사파리
스테퍼에는 없다). **값이 있을 때만** `Input` 의 `action` 슬롯에 `iconOnly` 지우기 버튼을 둔다.

- `action` 은 입력란 안 오른쪽의 **누를 수 있는** 자리다(`suffix` 와 반대). 자리·여백은
  컴포넌트가 잡으므로 호출부가 `pr-*` 를 뚫지 않는다.
- 아이콘은 `CloseIcon`, `size="md"`(44px).
- 값이 비면 버튼도 사라진다 — 누를 것이 없는 버튼을 세우지 않는다.

## G3. 순수 로직 — `lib/plan/day-items.ts` 가 세 군데 바뀐다

1. **`PlanDayEditItem` 에 편집 중인 시각을 든다.**

```ts
export type PlanDayEditItem = {
  item: PlanItemDetail
  removed: boolean
  /** 편집 중인 시각. **`HH:mm` 또는 `''`** — `<input type="time">` 의 값 그대로다 */
  startTime: string
}
```

- **`item.startTime` 을 직접 고치지 않는다.** `item` 은 서버가 준 것이고, 그것을 덮어쓰면
  "바뀐 것이 있나"(`hasEditChanges`)를 잴 기준이 사라진다.
- 초기값은 `toInputStartTime(item.startTime)` — `'10:30:00' → '10:30'`, `null → ''`.

2. **`hasEditChanges` 가 시각도 본다.** 지금은 순서와 삭제 표시만 본다
   (`lib/plan/day-items.ts` 의 `hasEditChanges`). 시각만 고친 편집에서 저장 버튼이 잠겨
   있으면 **고친 값을 저장할 방법이 없다.**

   비교는 **정규화된 값끼리** 한다 — 서버 `'10:30:00'` 과 입력 `'10:30'` 은 같은 값이다.
   원문으로 비교하면 아무것도 안 고쳐도 저장 버튼이 열린다.

3. **`toPayloadItem` 이 편집값을 싣는다.**

```ts
...(entry.startTime === '' ? {} : { startTime: `${entry.startTime}:00` }),
```

- **`:00` 을 붙여 `HH:mm:ss` 로 보낸다.** 추측이 아니라 **계약이 못 박은 모양**이다 —
  `PlanItemRequest.startTime` 의 설명이 _"생략 가능. 시작 시각 (HH:mm:ss). 생략하면 비워
  둡니다."_ 다 (2026-09-18 실호출, `GET https://api-dev.hondigagae.com/plan-service/v3/api-docs`).
- **`''` 는 키를 뺀다 = 지운다** (G1).
- **담기 경로(`appendPlaceItemPayload`)는 편집 상태를 모른다.** 거기서는 기존 항목을
  `PlanItemDetail` 에서 그대로 되싣고(`item.startTime`), **새로 담는 항목은 시각 없이**
  들어간다 — 담을 때 시각을 묻지 않는다(F5-3 의 "순서는 편집모드가 소유한다" 와 같은 분담).

## G4. 상호작용 · 문구 (확정)

| 트리거         | 동작                                       | 결과                                                 |
| -------------- | ------------------------------------------ | ---------------------------------------------------- |
| 시각 입력 변경 | 로컬 상태만 바뀐다                         | 저장 버튼이 열린다                                   |
| `시각 지우기`  | 값이 `''` 가 된다                          | 저장하면 그 항목의 시각이 지워진다                   |
| `저장`         | 일괄 교체 1회 (순서 + 삭제 + 시각 한 번에) | 성공 시 편집 상태를 통째로 버린다 (E1 규칙 3)        |
| `취소` / 이탈  | 고친 시각도 함께 버린다                    | 기존 이탈 경고가 그대로 덮는다 (`useUnsavedWarning`) |

| 자리                     | 문구 (확정)                                                      |
| ------------------------ | ---------------------------------------------------------------- |
| 편집기 머리 안내 한 줄   | `시작 시각은 선택이에요. 비우면 상세에 표시하지 않아요.`         |
| 시각 입력 접근 가능 이름 | `{title} 시작 시각` (`aria-label`)                               |
| 지우기 버튼              | `{title} 시작 시각 지우기` (`aria-label`)                        |
| 형식 오류 (`PLAN_100`)   | `시각 형식이 올바르지 않아요. 다시 입력해 주세요.` — 재시도 없음 |

- **행마다 보이는 라벨을 달지 않는다.** 한 일자에 항목이 여럿이라 `시작 시각` 이 6번 선다.
  이름은 `aria-label` 이 지고, 무엇을 넣는 칸인지는 `--:--` 서식과 머리 안내가 말한다.
- **`{title}` 을 이름에 넣는다.** 한 화면에 같은 컨트롤이 여러 개라 보이는 것만으로는 전부
  "시작 시각" 으로 읽힌다 — 담기 버튼(`{title} 담기`, F6)과 같은 규칙이다.
- **형식 오류에 `다시 시도` 를 주지 않는다.** 같은 본문을 다시 보내면 같은 400 이다
  (`PLAN_004` 와 같은 판정, E1).
- **저장 실패 문구는 기존 것을 그대로 쓴다** (`lib/plan/save-error.ts`). 시각 때문에 새 실패
  종류가 생기지 않는다.

## G5. AI 초안은 여전히 `startTime` 을 보내지 않는다 — 결정 유지

`lib/ai-plan/draft-to-plan.ts` 의 `draftToPlanPayload` 매핑표(`startTime` → **보내지 않는다**)와
`draft-to-plan.test.ts` 의 `startTime 을 보내지 않는다 — 초안에 없다` 를 **그대로 둔다.**

- **초안에 시각 필드가 아예 없다.** 백엔드 `AiPlanScheduleItem` 은 `itemType` · `placeId` ·
  `title` · `note` 넷뿐이다 (실측).
- **지어내면 [#625](https://github.com/8llow8llowMe/hondigagae/issues/625) 가 그 지어낸 시각으로 판정한다.** "09시부터 두 시간 간격" 같은
  규칙을 FE 가 만들면, 항목 산책 위험도가 **사용자가 정한 적 없는 시간의 답**을 내놓는다.
  백엔드가 `NO_START_TIME` 에서 _"정오를 넣어 판정하지 않는다"_ 고 못박은 것과 같은 논리다
  (`PlanItemWalkSafetyUnavailableReason`).
- **담은 뒤 사람이 넣는다.** 그 경로가 이 G 절이다.
- **하루 재생성도 같다** — 그래서 재생성은 그 날 시각을 지운다. 경고 문구는 D14-6.

## G6. 접근성

- 시각 입력은 네이티브 `<input type="time">` 이라 **키보드 순회·값 조작이 기본 제공**된다.
  `Alt+↑/↓` 이동은 **이동 버튼에 포커스가 있을 때만** 동작하므로(E6) 시각 입력 안에서
  방향키를 눌러도 행이 움직이지 않는다 — 충돌하지 않는다.
- 탭 순서는 읽는 순서와 같다: **시각 → 제목(비대화형) → ↑ → ↓ → 삭제**.
- 드래그 손잡이는 `aria-hidden` 인 순번 배지 그대로다. 손잡이와 시각 입력이 붙어 있으므로
  손잡이에만 `touch-none` 이 걸려 있는지 확인한다 — 입력까지 덮으면 모바일에서 값을 못 고른다.
- 지우기 버튼은 44px `iconOnly` 이고 이름이 `{title} 시작 시각 지우기` 다.
