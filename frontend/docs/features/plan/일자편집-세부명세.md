# E. 일자 편집모드 (이슈 B)

## E0. 화면 정의

- **경로**: `/plans/[planId]` **안의 모드**다. 새 라우트를 만들지 않는다.
- **인증**: 필요 (상세와 동일 — `proxy.ts` 가 `/plans` 로 이미 덮는다)
- **진입**: 일자 섹션의 `순서 편집` 버튼
- **이탈**: `저장` 성공 · `취소` · 이탈 경고 후 페이지 이동

**편집은 한 번에 한 일자만 연다.** 일괄 교체 단위가 일자이기 때문이다 (아트보드 03 주석).
다른 일자의 `순서 편집` 을 누르면 열려 있던 편집을 어떻게 할지 먼저 묻는다(E4).

## E1. 계약 — `PUT /api/v1/plans/{planId}/days/{day}/items`

**해당 일차의 항목을 요청 본문 목록으로 통째로 교체한다.** 부분 수정이 아니다.
빈 목록을 보내면 그 일차 항목이 모두 삭제된다.

```ts
type PlanDayItemsReplacePayload = {
  items: {
    day: number // **1 이상이어야 한다** — 아래 규칙 5
    sequence: number // 0부터
    itemType: PlanItemTypeCode // NotNull
    targetId?: string // Long. PLACE/MEAL/LODGING = place.id, WALK = walk_course.id
    title: string // NotBlank, 100자 이하
    memo?: string // 500자 이하
    startTime?: string // 'HH:mm:ss'
  }[]
}
```

응답은 **`PlanDetailResponse` 통째로** 온다 (그 일자만이 아니다).

| 오류                    | 코드       | HTTP | 언제                                              |
| ----------------------- | ---------- | ---- | ------------------------------------------------- |
| `PLAN_DAY_OUT_OF_RANGE` | `PLAN_002` | 400  | `day < 1` 또는 `day > totalDays`                  |
| `NOT_FOUND_PLAN_PLACE`  | `PLAN_004` | 400  | 장소 항목의 `targetId` 를 tour-service 가 못 찾음 |
| `INVALID_REQUEST`       | `PLAN_100` | 400  | Bean Validation (`title` 빈 값 · 100자 초과 등)   |
| `NOT_FOUND_PLAN`        | `PLAN_001` | 404  | 없는 일정 · **남의 일정**                         |

### 반드시 지킬 것 다섯

1. **`targetId` 를 JSON 숫자로 만들지 않는다.** 요청은 `Long` 인데 `placeId` 는 Snowflake 라
   `Number()` 로 바꾸면 정밀도를 잃는다(예: `212481712381923328` > `Number.MAX_SAFE_INTEGER`).
   **문자열 그대로 실어 보내고 Jackson 이 `Long` 으로 읽게 한다** — 생성 요청의 `petId` 와
   같은 처리다 (공통명세 S1).

2. **`memo` 와 `startTime` 을 반드시 되돌려 보낸다.** 일괄 교체라 빼먹으면 **순서만 바꿨는데
   메모와 시각이 지워진다.** 상세 화면이 `startTime` 을 표시하지 않는다는 것과 무관하다 —
   표시하지 않을 뿐 보존해야 한다.

3. **`planItemId` 는 요청에 없고, 저장하면 전부 바뀐다.** 서버가 삭제 후 재삽입한다
   (`PlanCommandProcessor.replaceDayItems`). React key 와 편집 로컬 상태를 `planItemId` 로
   잡으면 저장 직후 전부 새 id 로 갈리므로, **저장 성공 시 편집 상태를 통째로 버린다.**

4. **`sequence` 는 저장 직전에 0부터 다시 매긴다.** 화면의 배열 순서가 정본이다.

5. **`day` 는 1 이상으로 보낸다.** 서버가 경로 변수 값으로 덮어쓰지만 **덮어쓰기는 `toCommand()` 안에서 일어나고 Bean Validation 은 그보다 먼저 돈다.** `PlanItemRequest.day` 에 `@Min(1)` 이 걸려 있어 `0` 이나 음수를 보내면 덮어쓰기에 닿기 전에 `PLAN_100` 으로 막힌다. **경로의 `day` 를 그대로 실어 보낸다.**

### `PLAN_004` 는 재시도로 풀리지 않는다

`verifyPlaceTargets` 는 **delisting 된 장소도 걸러낸다** (`PlaceVerifyQueryPort`). 즉
**원천에서 사라진 장소가 이미 담겨 있는 일자는, 아무것도 추가하지 않고 순서만 바꿔도
저장이 400 으로 막힌다.**

서버는 어느 항목인지 알려주지 않는다. 화면이 **상세에서 이미 알고 있는 정보로 짚는다** —
**장소를 가리키는데 `item.place` 가 비어 온 항목이 원인 후보**다
(`hasUnresolvedPlace()`, 세부명세 A D3).

> **#115 이전에는 항목당 `GET /places/{placeId}` 가 404 를 낸 id 집합으로 짚었다.**
> #86 이 요약을 상세 응답에 실으면서 그 조회가 사라졌고, 판정 근거도 `place === null` 로
> 옮겼다. **대신 원인이 하나 더 섞인다** — 404(delisting)만이 아니라 tour-service 일시
> 장애도 같은 모양이다. 그래서 **문구가 원인을 단정하지 않는다**: "이 곳은 더 이상
> 조회되지 않아요" 는 둘 다에 맞는 서술이고, 사용자가 취할 행동(목록에서 빼면 저장된다)도
> 둘 다 같다.

- 편집모드에 들어갈 때 그런 항목이 있으면 **미리** 그 행에 표시한다
- 저장 실패 `PLAN_004` 면 그 행을 가리키며 "이 곳은 더 이상 조회되지 않아 함께 저장할 수
  없어요. 목록에서 빼면 저장할 수 있어요." 로 안내한다
- **`다시 시도` 를 주지 않는다** — 같은 본문을 다시 보내면 같은 400 이다

## E2. 컴포넌트 구성

| 컴포넌트              | 신규/기존 | 위치                                       | 비고                                   |
| --------------------- | --------- | ------------------------------------------ | -------------------------------------- |
| `PlanDayEditor`       | 신규      | `features/plan/plan-day-editor.tsx`        | 편집 중인 일자 전체 (표시 + 컨트롤)    |
| `PlanEditableItemRow` | 신규      | `features/plan/plan-editable-item-row.tsx` | 썸네일 없는 낮은 행 · 이동 · 삭제/복구 |
| `usePlanDayEdit`      | 신규      | `features/plan/use-plan-day-edit.ts`       | 편집 로컬 상태 + 저장 mutation         |
| `planDayItemsPayload` | 신규      | `src/lib/plan/day-items.ts`                | 순수 함수 — 편집 상태 → 요청 본문      |

**재사용**: `Button` · `ConfirmModal` · `FormAlert` · `Surface` ·
기존 이탈 경고 훅 — 실제 파일명은 **`src/lib/form/use-unsaved-warning.ts`** 다
(`useUnsavedWarning`). `beforeunload` 만 다루고 App Router 내 라우트 이동은 경고하지
않는다는 한계도 그대로 물려받는다.

**드래그 라이브러리를 새로 넣지 않는다.** 의존성 추가 없이 `Alt+↑/↓` 와 이동 버튼으로
재정렬한다. 접근성 경로가 **주**고 드래그가 보조다 (아트보드 03 주석이 `Alt+↑/↓` 를
"드래그 대안" 이라 부르지만, 순서를 뒤집는다).

**HTML5 draggable 이 아니라 Pointer Events 다** (#159 · `use-drag-reorder.ts`).
`dragstart` 계열은 터치에서 아예 발생하지 않아 모바일에서 기능이 사라진다 — 이 앱은
모바일이 먼저다. 이 문단의 "HTML5 draggable 로 얹는다" 는 착수 전 판단이었고 구현에서
뒤집혔다.

**가장자리에서 화면이 따라 스크롤한다** (#161). 목록이 화면보다 길면 1번을 8번 자리로
옮기려다 손이 화면 밖으로 나가, 놓고 스크롤하고 다시 잡아야 했다. 판정은
`lib/plan/auto-scroll.ts` 의 순수 함수이고 규칙은 셋이다.

- 뷰포트 위·아래 **60px** 안에 들어오면 그 방향으로 스크롤한다. 밖이면 **아무 일도 하지
  않는다** — 짧은 목록에서 드래그해도 화면이 움직이지 않는 근거다
- 속도는 **깊이 비례**다(최대 14px/프레임). 일정 속도면 조금 걸쳤을 때 너무 빠르고 끝까지
  밀었을 때 너무 느리다. 화면 밖으로 나가도 최대치를 넘지 않는다
- **스크롤한 프레임마다 중간선 판정을 다시 부른다.** 손이 멈춰 있어도 화면이 흐르면 행이
  움직이므로, `pointermove` 만 보면 스크롤만 되고 순서는 안 바뀐다

## E3. 데이터 흐름

```text
순서 편집 클릭
  → 그 일자 항목을 로컬 배열로 복사 (서버 상태를 건드리지 않는다)
  → 순서 바꾸기 / 삭제 표시  (전부 로컬)
  → 저장  → PUT /plans/{planId}/days/{day}/items
             성공: 응답(PlanDetailResponse)으로 setQueryData + 편집 상태 폐기
             실패: 편집 상태 유지 + 오류 표시
```

| 항목            | 내용                                                               |
| --------------- | ------------------------------------------------------------------ |
| API             | `PUT /plans/{planId}/days/{day}/items`                             |
| mutation 후     | 응답으로 `planKeys.detail(planId)` 를 **`setQueryData`**           |
| invalidate      | `planKeys.weather(planId)` — 항목이 바뀌면 그날 기준 장소가 바뀐다 |
| 낙관적 업데이트 | **하지 않는다**                                                    |

- **낙관적 업데이트를 하지 않는 이유**: `planItemId` 가 서버에서 새로 발급되고, `PLAN_004`
  처럼 재시도로 풀리지 않는 실패가 있다. 아트보드가 "저장하기 전까지는 아무것도 바뀌지
  않아요" 를 화면에 써 둔 것과 같은 태도다.
- **판정을 invalidate 하는 이유**: `PlanDayWeatherItem` 은 그날 **첫 장소 항목**을 기준으로
  판정한다(컨트롤러 설명). 순서를 바꾸면 기준 장소가 바뀐다.

## E4. 상호작용

| 트리거                  | 동작                                       | 결과                                                       |
| ----------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| `순서 편집`             | 그 일자를 편집모드로                       | 썸네일이 사라지고 행이 낮아진다                            |
| `Alt+↑` / `Alt+↓`       | 항목을 한 칸 이동                          | 포커스가 따라간다                                          |
| 위/아래 이동 버튼       | 같음                                       | 맨 위/맨 아래에서는 `disabled`                             |
| 카드 끌기 (#1029)       | 같음                                       | 포인터 전용 보조 경로 — 아래 `카드 끌기`                   |
| 항목 `삭제`             | **취소선 + `복구`** — 목록에서 빼지 않는다 | 저장 시점에 반영                                           |
| `복구`                  | 취소선 해제                                |                                                            |
| `저장`                  | `PUT …/days/{day}/items`                   | 성공 → 편집 종료. 실패 → 편집 유지 + 오류                  |
| `취소`                  | 변경이 있으면 확인 후 폐기                 | `ConfirmModal`                                             |
| 다른 일자의 `순서 편집` | 변경이 있으면 확인 후 전환                 | 같은 모달                                                  |
| 편집 중 페이지 이탈     | 이탈 경고                                  | 기존 이탈 경고 훅 재사용                                   |
| 전부 삭제 후 `저장`     | `items: []` 로 보낸다                      | 그 일자가 빈다. **막지 않는다** — 서버가 허용하는 동작이다 |

### 카드 끌기 — 번호가 아니라 카드 전체를 잡는다 (#1029)

**전에는 순번 배지(폭 24px)만 잡을 수 있었다.** 번호를 정확히 짚어야 해서 모바일에서는 끌 수
있다는 것을 찾지도, 잡지도 못했다. 이제 **카드 어디든** 잡는다. ▲▼ · `Alt+↑/↓` 는 그대로다.

카드를 잡게 하면 같은 누름이 **클릭 · 화면 스크롤 · 끌기** 중 무엇인지 가려야 한다. 입력마다
문턱을 둔다 — 판정은 `src/lib/plan/drag-gesture.ts` 의 순수 함수다.

| 입력        | 끌기가 되는 조건         | 그 전에                                                 |
| ----------- | ------------------------ | ------------------------------------------------------- |
| 마우스      | 누른 채 **5px** 움직인다 | 떼면 클릭이다. 가만히 눌러 두어도 끌기가 아니다         |
| 터치 · 펜   | **0.3초** 길게 누른다    | **8px** 이상 움직이면 스크롤로 보고 끝낸다              |
| 대화형 요소 | **끌지 않는다**          | `삭제` · ▲▼(잠긴 것도) · 링크 · 입력 위에서 시작한 누름 |

- **마우스 5px** — 클릭 중 손 떨림(1~2px)보다 크고, 끌려는 사람이 기다림을 느끼지 않을 만큼 작다.
- **터치 8px** — 손가락은 대고만 있어도 흔들려 마우스 문턱이면 길게 누르기가 성립하지 않는다.
  브라우저가 스크롤을 시작하는 거리(Chrome 약 15px)보다는 작아, 브라우저보다 먼저 손을 뗀다.
- **펜은 터치로 다룬다** — 태블릿의 펜도 화면을 끌어 스크롤한다.
- **잠긴 ▲ 도 제외한다** — 맨 위의 ▲ 를 눌렀는데 카드가 들리면 놀란다.
- **mac 의 Ctrl+클릭은 받지 않는다** (검토 반영) — `button=0` 인 오른쪽 클릭이라, 받으면 누름 중이
  되어 컨텍스트 메뉴를 막는다.

**놓기를 놓치는 경우** (검토 반영). 끄는 도중 앱 전환 · OS 알림으로 `pointerup` · `pointercancel`
이 오지 않으면 세션이 남아, 돌아와서 버튼 없이 움직이기만 해도 카드가 따라왔다. 둘로 막는다.

- 마우스가 **`buttons === 0` 으로 움직이면 끝이다** (`advanceDragGesture`). 터치는 닿아 있는 동안의
  `buttons` 값이 기기마다 달라 보지 않는다.
- 화면이 **가려지면(`visibilitychange` → `hidden`) 끝낸다.** 터치 대기 중이었다면 0.3초 타이머가
  보이지 않는 화면에서 끌기를 시작하던 경로도 이것이 닫는다.

**스크롤을 누가 가져가는가** — 이 절에서 가장 틀리기 쉬운 곳이다.

- 카드는 끌기 전 `touch-action: pan-y pinch-zoom` 이다. 카드가 화면 대부분을 덮어 `none` 이면
  목록 위에서 화면을 올릴 수 없다. **`pinch-zoom` 을 함께 두는 것은 두 손가락 확대 때문이다**
  (검토 반영) — `pan-y` 만이면 목록 위에서 확대가 막혀 저시력 사용자에게 회귀다. 두 번째
  손가락은 `onPointerDown` 이 받지 않아 끌기와 부딪히지 않는다.
- **`touch-action` 만으로는 끌기 중 스크롤을 막지 못한다.** 브라우저는 그 값을 손가락이 닿는
  순간에만 읽는다. 그래서 끌기가 시작된 뒤에는 목록에 **늘 걸어 둔 non-passive `touchmove`**
  리스너가 `preventDefault` 한다. React 의 `onTouchMove` 는 passive 라 무시되고, 끌기가
  시작될 때 붙이면 늦다 — Chrome 은 닿는 순간 막을 수 있는 리스너가 없으면 그 터치 전체를
  스크롤 스레드가 혼자 처리한다. e2e 에서 이 리스너를 빼면 끌기 대신 화면이 흐른다(확인함).
- 이동·놓기는 **창에서 받는다.** 카드에 걸면 한 칸 옮길 때 React 가 노드를 옮기며 포인터 캡처가
  풀릴 수 있고, 그러면 목록 밖에서 놓은 `pointerup` 을 놓친다.
- 길게 누르는 동안 **글자 선택 · iOS 콜아웃 · 컨텍스트 메뉴**를 막는다(`select-none` ·
  `-webkit-touch-callout: none` · 누름 진행 중의 `contextmenu`). 누름이 없을 때의 오른쪽 클릭은
  브라우저 메뉴를 그대로 연다.

**끄는 카드는 들린 모양이다** — `--shadow-md`(DESIGN.md §6 "드래그 중인 항목") · `z-10`(§7 z 스케일
"드래그 중인 일정 행") · 1% 확대. **확대는 `motion-safe` 에서만** 한다. 1% 인 이유는 390 에서
가로 스크롤을 만들지 않는 크기이기 때문이다(e2e 가 잰다).

안내 문구(확정): `카드를 끌거나 화살표로 순서를 바꿀 수 있어요. 저장하기 전까지는 아무것도 바뀌지 않아요.`

### 편집 중에는 두 가지를 하지 않는다

- **이동 거리를 다시 계산하지 않는다.** 순서를 옮길 때마다 숫자가 흔들리면 신뢰가 깨진다.
  대신 `이동 거리는 저장 후 다시 계산돼요` 를 그 자리에 둔다 (아트보드 03).
- **썸네일을 감춘다.** 드래그 대상은 순서지 사진이 아니다. 행이 낮아져 재정렬이 쉬워진다.

## E6. 접근성

- 편집 목록은 `<ol>`. 각 행의 이동 버튼에 `aria-label="위로 이동"` / `"아래로 이동"`.
- **키보드만으로 완결된다** — `Alt+↑/↓` 가 주 경로다. 드래그는 보조다.
- **카드에 역할 · `tabIndex` · `aria-*` 를 더하지 않는다** (#1029). 끌기는 포인터 전용 보조 경로라,
  카드를 포커스 가능하게 만들면 이동 버튼과 같은 일을 하는 탭 정지가 행마다 는다. 번호 손잡이의
  `title`(`끌어서 순서 바꾸기`)은 카드 전체가 손잡이가 되면서 걷었다 — 스크린리더 안내는 원래
  `<ol>` · 이동 버튼 이름 · `aria-live` 가 맡았고 그대로다. 순번 배지는 계속 `aria-hidden`.
- 이동 후 **포커스가 옮겨진 항목을 따라간다.** 안 그러면 연속 이동이 불가능하다.
  > **구현: 행이 아니라 이동 버튼에 포커스를 둔다.** 행에 `tabIndex` + `onKeyDown` 을
  > 얹으면 역할 없는 요소가 상호작용을 갖게 되어(`jsx-a11y/no-static-element-interactions`)
  > 스크린리더가 무엇을 눌러야 하는지 말하지 못한다. 조작하는 것은 이미 네이티브
  > `button` 인 이동 버튼이므로 거기에 포커스를 옮기고 `Alt+↑/↓` 도 거기서 받는다.
  > **경계에서 같은 방향 버튼이 `disabled` 가 되면 반대쪽 버튼으로 옮긴다** — disabled
  > 요소는 포커스를 받지 못해 그대로 두면 포커스가 사라진다.
- 순서 변경·삭제 표시를 `aria-live="polite"` 로 알린다 (`3번째로 이동했어요` / `삭제 예정이에요`).
- 삭제는 **취소선(시각) + 문구(`저장하면 삭제돼요`)** 로 이중 전달한다. 색·선만으로 알리지 않는다.
- 저장 버튼은 변경이 없으면 `disabled` — 그 이유를 `aria-describedby` 로 준다.
- 터치 영역 44px.

# F. 장소 추가 · 실내 대안 담기 (이슈 C)

## F0. 화면 정의

- **장소 추가**: 일자 섹션의 `장소 추가` 버튼
- **실내 대안 담기**: 일자 판정 아래 `비가 오면 갈 만한 실내` 블록의 `담기` 버튼

둘 다 **그 일자의 항목 배열 끝에 하나를 붙여 E1 의 일괄 교체로 저장**한다. 새 API 는 없다.

## F1. 실내 대안 담기 — 가벼운 쪽

`PlanDayWeatherItem.indoorAlternatives` 는 `{ placeId, title }` 뿐이다. 이것만으로 항목을
만들 수 있다.

```ts
{ itemType: 'PLACE', targetId: placeId, title, sequence: <끝>, day: <경로값> }
```

- **아트보드의 `서귀포시 안덕면 · 실내 · 12.4km` 는 계약에 없다.** `placeId`·`title` 뿐이다.
  → `GET /places/{placeId}` 로 보강한다 (`placeKeys.detail` 캐시를 장소 상세와 공유한다).
  > **정정 (구현 중 소스 실측):** 위 문장의 "계약에 없다" 는 **`placeId`·`title` 에만
  > 해당한다.** `PlanAlternativePlaceItem` 은 실제로 **5필드**이고
  > (`placeId` · `title` · `lat` · `lng` · **`distanceMeters`**), 아트보드의 `12.4km` 는
  > 그중 `distanceMeters` 다. FE 타입이 두 필드만 선언하고 있어 없는 줄 알았던 것이다.
  >
  > - 기준점은 **그날 대표 장소**(`representativePlaceId`)다 — 스키마 설명
  >   "그날 기준 장소로부터의 거리(m)" · `PlanWeatherPresenter#toAlternativeItems`
  > - 계산은 `GeoDistance.meters()` **하버사인**이라 **직선거리**다 →
  >   표기에 **`직선` 을 반드시 붙인다** (D3 과 같은 규칙). `직선 12.4km`
  > - **화면이 재지 않는다.** `haversineMeters` 를 부르지 않고 서버 값을 그대로 쓴다
  >
  > 보강(`GET /places/{id}`)에서 오는 것은 **주소와 실내 여부뿐**이고, 거리는 보강을
  > 기다리지 않는다.
  >
  > **#115 이후 보강은 실내 대안뿐이다.** 항목은 상세 응답이 `place` 를 함께 주므로
  > 목록에서 빠졌고, 대상 id 는 `alternativePlaceIds(alternatives)` 가 중복만 제거해
  > 만든다 — 같은 장소가 두 일자의 대안일 수 있다.
- **비 예보가 없는 일자에는 `indoorAlternatives` 가 비어 온다** — 그때는 블록을 렌더하지
  않는다. 빈 배열을 "대안 없음" 으로 쓰지 않는다.
- `담기` 성공 → 그 항목이 일자 맨 아래에 붙는다. 판정 invalidate 는 E3 과 동일.
- **이미 담긴 장소를 또 담을 수 있다.** 서버가 중복을 막지 않는다. 화면이 먼저 막는다 —
  그 일자에 같은 `targetId` 가 있으면 `담기` 대신 `이미 담았어요` 를 보여준다.

## F2. 장소 추가 — 무거운 쪽

`장소 추가` 는 **장소를 고르는 화면**이 필요하다. 아트보드에 그 화면이 없다.

**추천: 새 라우트 `/plans/[planId]/days/[day]/add`.**

- 상태를 URL 이 갖는다 → 뒤로가기가 자연스럽고 새로고침에서 살아남는다
  (`architecture-guide.md` §10 — URL 이 기본)
- 기존 장소 목록(`features/place/`)의 조회 훅·행 컴포넌트를 재사용한다
- 고르면 그 일자로 돌아가 **바로 일괄 교체를 저장**한다 (별도 확인 없음 — 되돌리기가 쉽다)
- **모달/시트로 하지 않는 이유**: 장소 목록은 필터 + 무한 스크롤이라 모달에 담기 무겁고,
  모달 안에서 무한 스크롤을 돌리면 배경 스크롤 잠금과 충돌한다

> **지도 보기가 붙었다** (#370). 같은 라우트이고 보기는 `?view=` 가 갖는다 — 기본은
> 지도다. 세부는 `docs/features/plan/담기지도-세부명세.md`.

### 검색 — `/places` 와 같은 자리 (#1012)

이름·주소 검색(`PlaceSearchField`, URL `?keyword=`)을 **두 보기에 함께** 둔다. 처음에는
빠져 있었는데 뺀 근거가 명세에 없어 누락으로 본다 — 필터·목록·지도가 이미 `/places`
컴포넌트를 그대로 쓰는데 검색만 없으면, 이름을 아는 곳 하나를 담으려고 필터를 뒤져야 한다.

- **목록 보기** — 카드 머리 `tools` 에 **검색 → 모바일 필터 칩** 순서로 선다. `/places` 목록
  머리와 같은 순서·같은 모양이다. 검색은 모든 폭에서 이 자리이고 칩만 `lg:hidden` 이다
- **지도 보기** — `PlaceMapView` 의 `searchable` 을 켠다. 자리는 담기지도 명세
  [D1 검색](담기지도-세부명세.md#검색--머리-아래와-패널-맨-위-1012) 이 정한다
  (1024 미만은 떠 있는 머리 바로 아래, 이상은 좌측 패널 맨 위, SDK 실패 폴백은 안내 줄 아래)
- **경로가 유지된다.** 제출·지우기는 `usePlaceFilterNav` 가 **현재 경로**(`usePathname`)에
  조건을 얹어 `replace` 하므로 `/plans/{planId}/days/{day}/add` 에 남는다 — `/places` 로
  튀지 않고, 목록 보기의 `?view=list` 도 남는다
- **보기 기본값이 `/places` 와 같아서 맞게 돈다.** 훅은 경로와 무관하게 `PLACES_DEFAULT_VIEW`
  로 `view` 를 읽는다. `PLAN_ADD_DEFAULT_VIEW` 가 갈리면 훅이 기본 보기를 받아야 한다
  (`use-place-filter-nav.test.ts` 가 두 값의 같음을 잠근다)

- `targetId` 는 **문자열로** 보낸다 (E1 규칙 1).
- **delisting 된 장소는 목록에 나오지 않는다** → 목록에서 고른 장소는 `PLAN_004` 가 나지

## F4. 상태별 화면

| ------------------------------ | ----------------------- | --------------------------------------------------- |
| 대안 없음 (`[]`)               | **블록 자체를 숨김**    | —                                                   |

조사(`을/를`)는 기존 `withObjectParticle()`(`src/lib/text/korean.ts`) 을 쓴다.

### 실패는 **누른 그 자리**에 남는다

"인라인" 만으로는 부족하다. 실측에서 두 번 어긋났다.

- **일자 상세**: 실패 알림이 실내 대안 블록이 있는 **모든 일자**에 떴다. 훅이 화면 전체에
  하나뿐인데 실패에 일자 정보가 없었기 때문이다. → `{ day, placeId }` 로 들고 호출부가
  `failure.target.day === group.day` 로 좁힌다. **진행 표시도 같다** — 같은 장소가 두 일자의
  대안일 수 있어(연속 우천일에 겹친다) `placeId` 만 비교하면 두 행이 함께 스피너를 낸다.
- **장소 추가 화면**: 알림을 헤더에 뒀더니 무한 스크롤 30번째 행에서 실패했을 때 **화면 밖**
  이라 아무 일도 안 일어난 것처럼 보였다. → 실패한 **행 안에** 렌더한다.

### 실패를 토스트로 말하지 않는다 (구현에서 정정)

위 표는 처음에 실패도 토스트로 적었지만, **`src/components/toast.tsx` 가 "오류를 토스트로
말하지 않는다 — 오류는 섹션 안에 남아야 다시 시도할 수 있다" 를 못박고 있다.** 4초 뒤에
사라지는 UI 에 유일한 복구 경로를 두면 안 된다. **성공만 토스트고 실패는 그 자리에
`FormAlert`(`role="alert"`) 로 남는다.** 재시도는 같은 `담기` 버튼을 다시 누르는 것이라
별도 버튼을 두지 않는다.

### `PLAN_004` 문구를 편집모드와 나눈다

분류는 `toPlanDaySaveError`(`src/lib/plan/save-error.ts`)가 **편집모드와 공유한다** — 같은
`PUT …/days/{day}/items` 라 분류가 두 벌이 되면 갈린다. 하지만 **문구는 나눈다**:

| 화면     | `PLAN_004` 문구                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------ |
| 편집모드 | `… 목록에서 빼면 저장할 수 있어요.`                                                              |
| 담기     | `이 일자에 더 이상 조회되지 않는 장소가 있어 담을 수 없어요. 일정에서 그 항목을 먼저 빼 주세요.` |

**담기 화면에는 뺄 목록이 없다.** 원인은 그 일자에 **이미 있던** 항목이고(일괄 교체가 그것까지
되싣는다) 일정으로 돌아가 편집모드에서 빼야 풀린다. 문구까지 공유하면 할 수 없는 일을
지시하게 된다. `PLAN_002` 는 나누지 않는다 — 어느 화면에서든 할 일이 새로고침으로 같다.

### 기간 밖 일자로 직접 들어왔을 때

주소를 손으로 고치면 `/days/9/add` 로 들어올 수 있다. **`totalDays` 를 알아야 판단할 수 있어
라우트가 아니라 화면이 막는다** — 고르고 나서 `PLAN_002` 로 실패하는 것보다 먼저 말한다.

- 경로의 `day` 가 **숫자가 아니거나 `1` 미만**이면 `notFound()` (`@PathVariable int` · `@Min(1)`)
- `day > totalDays` 면 `{day}일차는 이 여행에 없어요` + `이 여행은 총 {totalDays}일이에요.`
  **저장 실패 문구를 재사용하지 않는다** — 그쪽은 "새로고침한 뒤 다시 시도" 인데 새로고침해도
  없는 일자다.

## G0. 어디서 고치나 — 일정 목록의 시간 칩이다 (#1028 에서 뒤집음)

**원안 (#623)**: 상세 행에서 바로 고치지 않고 `순서 편집` 모드 안에서 순서·삭제와 같은 한 번의
저장에 싣는다. 근거는 항목 단건 수정 API 가 없어 행마다 저장 지점이 생기면 그때마다 그 일자
항목이 전부 새 `planItemId` 로 재발급되고, **옆 행의 방문 체크까지 초기화된다**는 것이었다 (D9-2).

**#1028 이 뒤집는다.** 시각은 **일정 목록의 각 항목 줄에 있는 칩**에서 넣고 고친다. 근거 셋.

1. **사용자 요청이다.** 시각은 계획적인 사람만 넣는 선택 값인데, 넣으려면 `순서 편집` 을 열어야
   한다는 것이 화면에서 보이지 않았다. 반대로 순서를 바꾸러 들어온 사람에게는 행마다 44px 시각
   입력과 안내 문구가 서서 편집 행이 두 배로 무거웠다.
2. **D9-2 의 비용을 다시 쟀다 — 잃는 날이 드물다.** 초기화로 잃는 것은 **그 일자에 이미 체크된
   `다녀옴`** 뿐이다. 체크는 시작일 전에는 서버가 받지 않고(#983 · `PLAN_027`), 시각은 대개 여행
   전에 넣는다 — 대부분의 저장에서 잃을 것이 없다. 잃을 것이 있는 날에만 모달 안에 한 줄로
   알리고(G4), **확인창을 한 번 더 두지 않는다** — 늘 뜨는 확인은 배경음이 된다.
3. **원안의 이점("한 번의 저장")은 시각에 약하다.** 시각은 항목 하나의 값이고, 한 번에 여러
   항목을 고칠 때도 항목마다 모달 한 번이면 된다. 순서·삭제처럼 서로 얽힌 변경이 아니다.

**치르는 값**: 시각 하나를 고칠 때마다 일괄 교체 1회다 — `planItemId` 전부 재발급 · 판정 무효화
(E3 · D15-6). 순서 편집의 저장과 같은 비용이라 새로 생긴 종류의 비용은 아니다.

**BE 후속 [#1030](https://github.com/8llow8llowMe/hondigagae/issues/1030)** — 항목 하나의 시작
시각을 방문 체크를 잃지 않고 고치는 단건 수정 API. 생기면 G4 의 초기화 경고와 일괄 교체 경로를
걷고 그 API 로 옮긴다.

## G1. 계약 — 키를 빼는 것이 곧 "지운다"

```ts
type PlanItemPayload = {
  // …
  /** `HH:mm:ss`. **키를 빼면 지워진다** — 일괄 교체라 "유지" 가 아니다 */
  startTime?: string
}
```

| 사실                        | 근거                                                                 |
| --------------------------- | -------------------------------------------------------------------- |
| 선택 필드다                 | `PlanItemRequest.startTime` 에 검증 애노테이션이 **없다**            |
| 키 생략 = `null` 저장       | `PlanCommandProcessor` 가 삭제 후 재삽입하며 커맨드 값을 그대로 쓴다 |
| 형식 오류 = `PLAN_100` 400  | 파싱 실패가 `HttpMessageNotReadableException` 으로 잡힌다            |
| 서버가 뜻을 검증하지 않는다 | 순서 역전·중복·`00:00` 전부 통과한다                                 |

**`PUT /plans/{planId}`(부분 수정) 와 반대다.** 저쪽은 키를 빼면 **유지**이고(D3-1 · 예산을
비울 수 없는 이유가 그것이다), 이쪽은 키를 빼면 **삭제**다. 같은 화면 안에 두 규칙이 있으므로
`day-items.ts` 주석과 테스트로 못박는다 (D14-5).

## G2. 화면 — 시간 칩 + 전자시계 모달

### 칩 — D14-3 의 시각 줄이 곧 칩이다

```text
[썸네일]  [🕒 10:30] · [산책 주의] · 체감온도 33.5℃   ← 시각 있음: secondary sm, 누르면 고친다
 ①       천지연폭포  [식사]
          제주 서귀포시 … · 실내

[썸네일]  🕒 시간 등록하기                             ← 시각 없음: ghost sm
 ②       카페 델문도
```

- **칩을 따로 두지 않고 D14-3 시각 줄 자리를 칩으로 바꿨다.** 캡션과 칩을 나란히 두면 한 행에
  `10:30` 이 두 번 서고, #625 산책 위험도 배지가 어느 쪽에 붙는지 갈린다. 배지·체감온도는 칩
  오른쪽에 그대로 붙는다 (D15-5).
- **시각이 없으면 `ghost`, 있으면 `secondary`.** `시간 등록하기` 는 계획적인 사람만 쓰는 선택
  행동이라 모든 행에 테두리 버튼으로 세우면 제목보다 먼저 읽힌다 — `fg-muted` 글자로 캡션 톤에
  머문다. 값이 들어 있는 칩은 테두리가 "값이 있고 누르면 고친다" 를 말한다. `ghost` 는 좌우
  여백(12)만큼 `-ml-3` 으로 당겨 시계 아이콘을 제목 첫 글자에 맞춘다 (배치 유틸리티).
- **모든 항목에 선다** — `MOVE`(이동·휴식) · `WALK` 포함. 시각은 항목 자체의 값이다.
- **없는 곳**: 공유 보기(`SharedPlanItemRow` — 다른 컴포넌트다) · `순서 편집` 중(행이 편집기로
  바뀐다) · 기간 밖 항목 섹션(저장할 일자가 없다 — 예전 캡션만 선다).
- **누르는 자리는 `Button` `sm` 이다** — 보이는 32, `::before` 띠로 46~48 (DESIGN.md §7 "시각은
  작아도 누르는 자리는 44 언저리로"). 줄 아래 `mb-2` 는 그 띠(위아래 8px)가 제목과 겹치지 않게
  떼는 몫이다 — 붙어 있으면 제목 윗부분을 누를 때 링크 대신 칩이 받는다.

**행 링크가 "늘린 링크" 로 바뀐다.** 예전에는 행 전체가 `<a>` 였고, 그 안에 버튼을 넣을 수 없다
(D6 · 중첩 상호작용). 이제 `<a>` 는 **제목을 감싸고** `::after` 가 행 면(`relative`)을 통째로
덮는다 — 썸네일·메타·거리 어디를 눌러도 링크라 **누르는 자리는 예전과 같다.** 칩만 `z-10`
(DESIGN.md z 스케일 "형제 요소 위로 띄우는 로컬 레이어")으로 그 위에 선다. 초점 링은 `::after`
에 그려 예전처럼 행 면을 두른다. 덤으로 링크 이름이 행 전체 글(시각·주소·거리)이 아니라
**제목**이 된다. 방문 토글(후행 열)은 이 면의 형제라 덮이지 않는다.

### 모달 — 전자시계

```text
┌─────────────────────────────────────────┐
│ 천지연폭포 시작 시각                     │
│ ▲▼나 방향키로 바꾸거나 숫자를 바로 입력해요. │
│ 저장하면 이 날의 ‘다녀옴’ 표시가 초기화돼요. │ ← 그 일자에 체크가 있을 때만
│            ︿          ︿               │
│          [ 10 ]  :  [ 30 ]              │
│            ﹀          ﹀               │
│ 시간 지우기             [취소] [저장]    │ ← 지우기는 시각이 있을 때만
└─────────────────────────────────────────┘
```

- 공통 `Modal`(`size="sm"`)이다. 칸은 `text-display` · `font-black`(DESIGN.md §3-1 "큰 지표 숫자").
- **칸은 `role="spinbutton"` 인 `<input inputMode="numeric">` 이다.** `div` 에 `tabIndex` 를 주면
  모바일에서 숫자 키패드가 뜨지 않는다 — 직접 입력이 요구라 입력 요소여야 한다. 값의 뜻은
  `aria-valuenow/min/max` · `aria-valuetext`(`10시` · `30분`) · `aria-label`(`시` · `분`)이 말한다.
- **▲▼ 는 탭 정지가 아니다** (`tabIndex={-1}`). 키보드는 칸 안의 ↑↓ 로 같은 일을 한다.
- **증감**: 시 1 · 분 5, 끝에서 순환(`23 ↑ → 00`). 분은 5 의 배수에 붙는다(`07 ↑ → 10`).
  `Home`/`End` 는 최솟값·최댓값(APG spinbutton).
- **숫자 직접 입력**: 두 자리 규칙(네이티브 시간 입력과 같다) — 십의 자리가 될 수 있는 첫
  자리(시 0~~2 · 분 0~~5)는 두 번째를 기다리고, 아니면 바로 `0X`. 범위를 넘는 두 자리는 방금 친
  자리로 다시 시작한다. 분은 여기서 1 단위다. **시 두 자리가 끝나면 분 칸으로 넘어간다.**
- **숫자는 `keydown` 이 아니라 `onChange` 의 `InputEvent.inputType` 으로 읽는다.** 모바일 가상
  키보드는 `key` 를 `Unidentified` 로 보내는 일이 있고, 칸은 포커스 때 전체 선택이라 길이로는
  백스페이스와 덮어쓰기를 가를 수 없다(`10` 위에 `1` → 원문 `1`).
- **열 때의 값**: 그 항목의 시각 → 없으면 **같은 날 가장 가까운 앞 항목의 시각** → 그것도
  없으면 `10:00`. 하루는 순서대로 흘러가 다음 항목은 대개 앞 항목 뒤다. 뒤 항목은 보지 않는다
  (거꾸로 내려와야 하고, 역전 일정에서 엉뚱하다). 앞 시각에 간격을 더해 지어내지 않는다 —
  머무는 시간은 장소마다 다르다. `10:00` 은 여행 첫 일정이 대개 오전에 시작하고 둥근 값이라
  어느 쪽으로 고치든 누르는 횟수가 적다. **어느 값이든 저장 전까지는 출발점일 뿐이다.**
- **저장 중에는 닫히지 않는다** (#1014 `guardClose` 와 같은 규칙) — Esc · 바깥 · 취소 전부.
  칸은 `disabled` 가 아니라 `readOnly` 다 — 초점을 든 칸이 `disabled` 가 되면 초점이 `body` 로
  떨어져 실패로 돌아왔을 때 고치던 자리를 잃는다.
- **`Modal` 에 넘기는 닫기 함수를 렌더마다 새로 만들지 않는다.** `useOverlay` 가 그 함수를
  effect 의존성으로 들어, 바뀌면 초점을 모달 밖으로 돌렸다 다시 넣는다 — 이 모달은 숫자 한
  자리마다 다시 렌더되므로 치는 족족 초점이 튄다. 저장 중 여부는 ref 로 읽고 호출부 닫기는
  `useCallback` 이다 (`useOverlay` 쪽 수정은 #1026 · PR #1027).

### 네이티브 `<input type="time">` 을 걷은 이유 (#623 과 갈리는 지점)

#623 은 "시간 피커를 새로 만드는 비용(포털·오버레이·키보드 순회·`useOverlay` 배선)이 크다" 며

## G6. 접근성

- 칩은 네이티브 `button` + `aria-haspopup="dialog"`, 이름에 제목이 든다. 늘린 링크 위에서도
  탭 순서는 DOM 순서대로 **칩 → 제목 링크 → 방문 토글**이다.
- 모달 칸: `role="spinbutton"` · `aria-valuenow/min/max` · `aria-valuetext` · `aria-label`.
  열면 **시 칸**이 초점을 받는다(`initialFocusRef`) — 첫 초점 가능 요소(▲ 버튼)가 아니다.
- ↑↓ 는 `preventDefault` 로 페이지 스크롤·커서 이동과 부딪히지 않는다. 모르는 키(Tab · Enter ·
  Esc)는 막지 않는다 — Enter 는 저장, Esc 는 닫기로 그대로 산다.
- **입력 중 초점이 빠지지 않는다** — 닫기 함수의 정체성을 지키는 이유다 (G2). 390·1280 목 서버
  실측: 숫자·방향키 7번 동안 `focusout` 0건(시 → 분 자동 이동 1건 제외, 2026-09-29).
- 초기화 경고는 설명 자리에 있어 열 때 읽힌다. 실패는 `FormAlert`(`role="alert"`).
- **저장 뒤 초점은 같은 자리의 새 칩으로 돌아온다** (#1028 검토). 일괄 교체가 `planItemId` 를
  새로 발급해 모달을 연 칩이 언마운트되므로 `useOverlay` 의 복귀 초점이 떨어진 노드를 가리켜
  `body` 로 빠졌다 — 키보드·스크린리더 사용자가 목록 맨 위로 튕겨 나갔다. 칩에 **일자 · 순서**
  표식(`data-plan-time-chip`, `timeChipFocusKey`)을 달고, 저장을 보낼 때 적어 둔 표식의 칩을 닫은
  다음 프레임에 잡는다. 순서는 시각 저장으로 바뀌지 않는다. 저장하지 않고 닫으면 칩이 그대로라
  기존 복귀가 맞는다.
- **붙여넣기는 글 전체를 읽는다** (`parsePastedClock`). `10:30` · `14시 20분` · `1030` 은 칸과
  무관하게 시·분을 함께 채우고, 숫자 한두 자리는 그 칸의 값이다. 범위를 넘거나 못 읽으면
  **아무것도 바꾸지 않는다** — 처음 구현은 마지막 숫자만 읽어 `14` 가 `04` 가 됐다.

# H. 이동·휴식 직접 추가 (이슈 [#1014](https://github.com/8llow8llowMe/hondigagae/issues/1014))

> **계약 확인 근거**: backend plan-service **소스 실측** (`origin/develop` `748795ba`, 2026-09-29) —
> `adapter/in/web/dto/request/PlanItemRequest.java:28-35`(`targetId` · `title`) ·
> `application/service/processor/PlanCommandProcessor.java:385-419`(`verifyItemTargets`) ·
> `PlanValidationMessage.java:15-16`(`PLAN_109` · `PLAN_110`).
> 백엔드 변경은 없다 — 계약이 이미 `MOVE` 를 받는다.

## H0. 화면 정의

AI 일정은 `MOVE` 항목(예: `이동 및 휴식`)을 만들지만 **사용자가 직접 넣을 방법이 없었다.**
FE 에는 `appendPlaceItemPayload`(`PLACE`)·`appendWalkCourseItemPayload`(`WALK`)만 있었다.

- 일자 카드 액션 줄의 **`순서 편집` 오른쪽**에 `이동·휴식 추가` 를 둔다
- 누르면 **공통 `Modal`** 이 제목 하나를 받는다
- 제출하면 그 일자 **맨 끝**에 `MOVE` 항목으로 붙여 E1 의 일괄 교체로 저장한다. 새 API 는 없다

## H1. 계약 — 대상 없는 항목

```ts
{ itemType: 'MOVE', title, sequence: <끝>, day: <경로값> } // targetId 키 없음
```

| 사실                           | 근거                                                                    |
| ------------------------------ | ----------------------------------------------------------------------- |
| `targetId` 는 비운다           | `PlanItemRequest.targetId` 설명 "MOVE 는 비워 둡니다"                   |
| 장소 검증을 타지 않는다        | `verifyPlaceTargets` 가 `targetId` 가 `null` 인 항목을 묻지 않는다      |
| `title` 필수 · 공백만이면 거절 | `@NotBlank` → `PLAN_109`                                                |
| `title` 100자 초과면 거절      | `@Size(max = 100)` → `PLAN_110`. **자르지 않는다**                      |
| 배지 `이동` 은 서버가 준다     | 응답 `itemType` metadata(`{code, name, description}`)를 그대로 렌더한다 |

- **`targetId` 는 `null` 을 싣지 않고 키를 뺀다.** 뜻은 같지만 되싣는 쪽(`toPayloadItem`)이 이미
  키를 빼므로 한 본문 안에서 두 모양을 섞지 않는다 (`PlanItemPayload.targetId?: string`).
- **`PLAN_004` 는 여전히 날 수 있다.** 새 `MOVE` 때문이 아니라 **그 일자에 이미 있던 장소**가
  원천에서 사라진 경우다 — 일괄 교체가 그것까지 되싣는다 (E1 · F3 과 같다).

조립은 `lib/plan/day-items.ts` 의 **`appendMoveItemPayload(items, day, { title })`** 다.
`appendPlaceItemPayload` 의 자매이고, 기존 항목을 전부 되싣고 `sequence` 를 0부터 다시 매긴 뒤
끝에 하나를 붙인다. `title` 은 앞뒤 공백을 걷고 100자로 자른다 — 자르기는 검증을 거치지 않은
호출에 대한 2차 방어다(아래 H2).

## H2. 배치 · 모달

```text
[장소 추가] [순서 편집] [이동·휴식 추가]        [이 날 산책 위험도]
```

- **`순서 편집` 오른쪽**, 같은 `variant="secondary"` · `size="sm"` 다. 이 일자를 **고치는**
  도구라 왼쪽 무리에 선다
- **빈 일자에도 남는다** — `장소 추가` 와 같다. 장소가 없어도 이동·휴식은 넣을 수 있다
- **편집 중에는 감춘다** — 액션 줄 전체가 그렇다 (F6)
- **숨김 조건이 따로 없다.** 공유 보기는 다른 컴포넌트(`SharedPlanSection`)라 이 줄이 없고,
  상세 화면의 `장소 추가` 도 권한으로 숨지 않는다 — 같은 조건을 따른다
- 버튼에 `aria-haspopup="dialog"` 를 단다
- **라우트가 아니라 모달이다.** `장소 추가` 가 라우트인 이유(F2 — 필터 + 무한 스크롤)가 여기엔
  없다. 고를 목록이 없고 제목 하나만 받는다

모달(`PlanDayMoveAddView` · `size="md"`, `PlanEditModal` · `PlanCopyView` 와 같은 골격):

| 자리   | 내용                                                                          |
| ------ | ----------------------------------------------------------------------------- |
| 제목   | `{day}일차에 이동·휴식 추가` — 같은 버튼이 일자마다 있어 어느 날인지 밝힌다   |
| 설명   | `이 날 맨 뒤에 추가돼요. 순서는 순서 편집에서 바꿀 수 있어요.`                |
| 필드   | 라벨 `이름` · **빈 값으로 연다** · placeholder `예: 차로 이동, 카페에서 쉬기` |
| 제한   | `maxLength={100}` — 붙여넣기도 여기서 잘린다                                  |
| 조작부 | `취소` · `추가하기`(submit)                                                   |

- **placeholder 는 예시지 기본값이 아니다.** 열 때마다(일자가 바뀌어도) 입력을 비운다
- **비운 채 추가하면 `이동 및 휴식` 이다** (#1026). 예전에는 필수 오류로 막았는데, 이 모달의 목적이
  "여기서 쉰다" 는 자리 표시라 이름을 짓게 할 이유가 약했다. AI 일정이 같은 자리에 쓰는 제목과
  맞춘다. 필수 표시(`*`)는 걷고 필드 아래 안내(`addMoveFieldHint`)가 비웠을 때 무엇이 되는지
  말한다. 채우는 곳은 `appendMoveItemPayload` 하나다 — 서버 `@NotBlank` 에 빈 값이 닿지 않는다
- **`<form>` 으로 감싼다** — 입력이 하나라 Enter 로 바로 보낸다. 제출 버튼은 `footer`(폼 밖)라
  `form` 속성으로 잇는다
- **검증은 제출 시 `validateMoveTitle()`** 이다 (`form-guide.md` §5). 이제 **길이만** 본다 — 걸리면
  요청을 보내지 않고 필드에 문구를 붙인 뒤 입력으로 초점을 돌린다. 길이는 **걷어낸 값**으로
  잰다(보내는 값이 그것이라)
- **자르지 않고 막는다.** 장소 담기(F3)는 복사해 온 이름이라 잘라도 잃는 것이 없지만, 이것은
  사용자가 쓴 글이다

## H3. 저장 · 캐시

`features/plan/use-plan-add-move.ts` 의 `usePlanAddMove`. **`usePlanAddPlace` 와 후처리가 같다**:

1. `setQueryData(planKeys.detail(planId), 응답)` — 응답으로 상세를 갈아끼운다
2. `invalidateQueries(planKeys.weather(planId))` — 판정 (E3). `MOVE` 가 기준 장소가 될 수 없어도
   버린다: "이 교체는 판정과 무관하다" 를 화면이 가려내면 서버 규칙을 복제하게 된다
3. `invalidateQueries(planKeys.walkSafety(planId))` — 교체가 `planItemId` 를 전부 새로 발급한다 (D15-6)
4. 성공 토스트 → 모달을 닫는다

- **낙관적 업데이트를 하지 않는다** — `planItemId` 를 서버가 발급하고 재시도로 풀리지 않는 실패가 있다
- **훅을 합치지 않았다.** 진행·실패를 드는 열쇠가 다르다 — 장소 담기는 `{day, placeId}` 로 행
  하나를 가리키고, 이쪽은 모달 하나라 `day` 만 든다
- **잠금은 하나로 묶는다.** 실내 대안 `담기` 와 이 추가가 동시에 나가면 나중 응답이 앞선 것을
  덮는다(F6). 이 추가가 도는 동안 실내 대안 `담기` 가 잠기고(`PlanDayAdd.busy`), 담기가 도는
  동안 모달의 `추가하기` 가 잠긴다(`blocked`). 버튼으로 **모달을 여는 것**은 잠그지 않는다 —
  여는 것은 아무것도 보내지 않는다
- 재진입 가드는 `ref` 다 — `disabled` 반영 전 Enter 두 번 (`form-guide.md` §6)
