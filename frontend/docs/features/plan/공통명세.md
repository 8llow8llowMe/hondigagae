> 게이트웨이 미기동이라 Swagger 실호출은 하지 못했다 — [#67](https://github.com/8llow8llowMe/hondigagae/issues/67) 에서 대조한다.

## S0. 화면 정의

| 화면        | 경로         | 인증     | 초기 데이터                                       |
| ----------- | ------------ | -------- | ------------------------------------------------- |
| 일정 목록   | `/plans`     | **필수** | 서버 프리페치 1페이지 + client `useInfiniteQuery` |
| 직접 만들기 | `/plans/new` | **필수** | 없음 (폼). 반려견 목록만 client 조회              |

두 화면 모두 route group `(main)`. `GET /plans` 는 `@PreAuthorize("isAuthenticated()")` 라
**미로그인은 화면이 성립하지 않는다** — 장소·긴급 시설과 다르다.

### 왜 두 화면을 한 이슈로 묶었나

아트보드의 만들기 진입점이 **세 곳**이고 전부 `/plans/new` 로 간다 — 모바일 헤더 `+`
시트, 데스크톱 헤더 버튼, 빈 상태 버튼. 목록만 먼저 머지하면 **404 진입점**이 생긴다.
[#13](https://github.com/8llow8llowMe/hondigagae/issues/13) 이전의 `/emergency` 가 그랬다.

**`/plans/[planId]` 상세는 이 범위가 아니다.** 목록 행의 링크는 별도 이슈가 해소한다.
그 404 는 이 PR 이 만드는 것이 아니라 **이미 있다** — 홈의 `upcoming-plan-row.tsx` 가
같은 경로로 링크하고 있고 홈은 [#51](https://github.com/8llow8llowMe/hondigagae/issues/51) 에서 이미 머지됐다.

## S1. 계약

### `GET /api/v1/plans` — 내 일정 목록

| 파라미터     | 제약                   | 화면이 보내는 값 |
| ------------ | ---------------------- | ---------------- |
| `lastPlanId` | 선택. 첫 페이지는 생략 | 마지막 `planId`  |
| `size`       | 1~50, 기본 10          | **50**(상한)     |

응답은 `SliceResponse<PlanSummaryItem>` — `contents` + `hasNext` 뿐이다.
**`totalCount` 가 없다.**

```ts
type PlanSummaryItem = {
  planId: string // Snowflake. number 로 타이핑하면 정밀도가 손상된다
  petId: string
  areaCode: string
  title: string
  startDate: string // 'YYYY-MM-DD'
  endDate: string
  status: CodeNameMetadata // DRAFT | CONFIRMED | COMPLETED
}
```

### `POST /api/v1/plans` — 일정 생성

| 필드          | 필수 | 제약                            | 오류 코드               |
| ------------- | ---- | ------------------------------- | ----------------------- |
| `petId`       | ✅   | `Long`                          | `PLAN_101`              |
| `areaCode`    | ✅   | 문자열 (제주 = 39)              | `PLAN_102`              |
| `sigunguCode` | —    | 문자열                          | —                       |
| `title`       | ✅   | 60자 이하                       | `PLAN_103` / `PLAN_104` |
| `startDate`   | ✅   | `YYYY-MM-DD`                    | `PLAN_105`              |
| `endDate`     | ✅   | `YYYY-MM-DD`                    | `PLAN_106`              |
| `budget`      | —    | 0 이상 정수                     | `PLAN_107`              |
| `items`       | —    | 생략 = 빈 일정 · **최대 100개** | `PLAN_136` (아래 S1-1)  |

**`petId` 만 요청에서 숫자다.** 응답의 `petId`·`planId` 는 문자열인데 생성 요청 본문의
`petId` 는 `Long` 이다 — `Number(petId)` 변환이 필요하고, Snowflake 라 그 변환이
**정밀도를 잃는다.** 반려견 id 는 실제로 안전 정수 범위 밖이므로 **문자열을 그대로 실어
보내고 Jackson 이 `Long` 으로 읽게 한다** (JSON 숫자 리터럴로 만들지 않는다).

**시작일 > 종료일은 서버가 `PLAN_003`(400)** 으로 막는다. 화면도 같은 검증을 먼저 한다 —
왕복 없이 그 자리에서 말해 주는 편이 낫다.

### S1-1. 일정 항목 수 상한 — `PLAN_136` · `PLAN_028` ([#1251](https://github.com/8llow8llowMe/hondigagae/issues/1251))

BE [#1243](https://github.com/8llow8llowMe/hondigagae/issues/1243) 으로 일정 하나의 항목이 **최대 100개**가 됐다.
계약 정본은 `backend/docs/services/plan-service.md` "일정 항목 수 상한" 절, 모양은 `PlanErrorCode.java` ·
`PlanValidationMessage.java` · `ValidationErrorSupport.java` 소스 실측이다.

| 코드       | HTTP | `fieldErrors`                    | 오는 곳                                                | 뜻                                              |
| ---------- | ---- | -------------------------------- | ------------------------------------------------------ | ----------------------------------------------- |
| `PLAN_136` | 400  | `[{ field: 'items' }]` (`@Size`) | `POST /plans` · `PUT /plans/{planId}/days/{day}/items` | 요청 한 번의 목록(`items`)이 100개를 넘음       |
| `PLAN_028` | 400  | 없음 (도메인 예외)               | `PUT /plans/{planId}/days/{day}/items` **만**          | 교체 뒤 다른 날과 합친 일정 전체가 100개를 넘음 |

FE 처리:

| 경로                                                                                | 판정                                                                                                                         | 문구 (확정)                                                                              | 재시도 |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------ |
| 하루 교체 — 편집모드 · 장소/산책 코스 담기 시트 · 장소/이동 추가 · 하루 재생성 반영 | `toPlanDaySaveError`(`lib/plan/save-error.ts`)                                                                               | `일정에는 항목을 최대 100개까지 담을 수 있어요. 담긴 항목을 줄인 뒤 다시 시도해 주세요.` | 없음   |
| AI 초안 담기 (`POST /plans`, `ai-plan-job-view`)                                    | `toAiPlanCommitErrors`(`lib/ai-plan/commit-error.ts`) → 폼 전체 오류                                                         | `일정에는 항목을 최대 100개까지 담을 수 있어요. 여행 기간을 줄여 다시 만들어 주세요.`    | 없음   |
| 직접 만들기 · 담기 시트의 새 일정 갈래 (`POST /plans`)                              | 해당 없음 — **`items` 를 보내지 않는다** (`lib/plan/form.ts`). 새 일정의 첫 장소는 이어지는 하루 교체로 담겨 위 첫 줄을 탄다 | —                                                                                        | —      |

- **새로고침 안내로 보내지 않는다.** 예전에는 두 코드가 `toPlanDaySaveError` 의 "나머지 4xx" 로 떨어져
  `saveStaleError`(`화면이 최신이 아니에요. 새로고침한 뒤 다시 시도해 주세요.`)를 보였다 — 새로고침해도
  같은 400 이고, 사용자는 상한 때문인 줄 모른다. 두 코드 모두 같은 본문을 다시 보내면 같은 실패라
  **`다시 시도` 를 주지 않는다** (`api-integration-guide.md` §3 의 400 = 입력 수정 유도).
- **판정은 `isPlanItemLimitError`(`lib/plan/item-limit.ts`) 하나다.** `resultCode` 와 함께 `fieldErrors[].code`
  도 본다 — 검증 오류가 여럿이면 대표 코드는 정렬된 첫 오류(`items` 보다 앞선 `title` 등)라 `PLAN_136` 이
  대표 자리에 없을 수 있다.
- **문구는 FE 것이다 — 서버 `resultMessage` 를 그대로 쓰지 않는다.** 근거:
  1. 하루 교체 저장 실패는 이미 FE 문구로 말한다(`PLAN_004` · `PLAN_002` · `PLAN_100`) — 분류가 "다음에 할 일"
     을 정해야 하는 자리이고, 서버 문구는 사실만 말한다.
  2. 두 코드의 서버 문구가 다르다(`일정에는 항목을…` / `일정 항목은…`). 같은 상황에 화면마다 다른 말이 나간다.
  3. `form-guide.md` §4.2-4 "서버 문구를 그대로 쓴다" 는 **입력 칸 옆에 붙는 필드 오류**의 규칙이다. AI 담기
     폼에는 `items` 칸이 없고, 이 화면에서 할 일(기간을 줄여 다시 만들기)은 서버가 알 수 없다 —
     `PLAN_004` 를 FE 블록으로 말하는 것(`commitDelisted*`)과 같은 판단이다.
- **숫자 100 은 `PLAN_MAX_ITEMS` 한 곳**(`lib/plan/item-limit.ts`, 서버 `Plan.MAX_ITEMS` 복제본)이다. 문구에
  싣기 위해서만 쓰고 사전 차단은 하지 않는다 — 판정은 서버가 교체 뒤 일정 전체 수로 한다. 서버 값이 바뀌면
  이 상수와 `item-limit.test.ts` 를 함께 고친다.
- **하루 교체는 화면마다 문구를 나누지 않는다** (`PlanDaySaveCopy` 에 넣지 않았다). `PLAN_004` 와 달리 할 일이
  "담긴 항목을 줄인다" 로 같고, 어디서 줄이는지(편집모드는 그 자리, 나머지는 일정 상세)는 화면이 자명하다.
  AI 담기만 다른 이유: 초안의 항목을 줄일 수단이 없다(빼기는 조회되지 않는 곳만) — 할 수 없는 일을
  지시하지 않는다.
- **AI 담기의 `PLAN_136` 은 폼 전체 오류로 올린다.** 공용 매핑(`apiErrorToFormErrors`)은 그 오류를
  `fields.items` 에 넣고 `form` 을 비우는데, 담기 폼에는 `items` 칸이 없어 **문구가 아무 데도 안 보였다**
  (`ai-plan-commit-panel.test.ts` 의 "전제" 케이스). `useForm` 에 생략 가능한 `toErrors` 를 더해 이 폼만
  `toAiPlanCommitErrors` 를 준다 — 기존 호출부는 생략해 동작이 그대로다. "폼에 없는 필드의 오류는 form
  으로" 같은 공용 규칙으로 넓히지 않은 이유: 폼마다 칸 목록을 알려 줘야 해 모든 `useForm` 호출부가 바뀌고,
  이 문제를 겪는 코드가 상한 하나뿐이다. 함께 온 다른 필드 오류(`title`)는 제자리에 둔다.
- 검증: `save-error.test.ts` · `item-limit.test.ts` · `commit-error.test.ts` · `ai-plan-commit-panel.test.ts`,
  담기 시트 한 바퀴는 `e2e/plan-item-limit.spec.ts`(교체를 `page.route` 로 400 `PLAN_028` 에 묶는다).

## S2. 아트보드에 있으나 **구현하지 않는 것**

| 아트보드                     | 빼는 이유                                                                                                                                                                               |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "후기 미작성" 밴드           | 목록 `PlanSummaryItem` 에 `hasReview` 가 없다. 완료 일정마다 GET 하면 N+1 이다. **상세에서만** `GET /plans/{id}/reviews` 로 가른다 (#615). 목록에 진입점만 만들지 않는다                |
| `항목 6개 · 총 이동 96.3km`  | `PlanSummaryItem` 에 항목 수·거리 필드가 없다. **아트보드 05 주석 스스로가** "총 이동 거리 합계 같은 요약 통계는 넣지 않는다" 고 적어 두었다 — 행과 주석이 어긋난 곳이라 주석 편을 든다 |
| `제주시` / `서귀포시` 지역명 | 목록은 `areaCode`(`'39'`) 만 준다. 코드→이름 매핑이 FE 에 없고 지어내지 않는다                                                                                                          |
| `AI 로 만들기` 진입점        | AI 일정 생성 화면이 아직 없다. **그 화면이 생길 때 켠다** — 지금 켜면 만들기 시트의 두 항목 중 하나가 404 다                                                                            |

만들기 시트에 AI 항목이 빠지면 남는 선택지가 하나뿐이다. **선택지가 하나면 시트를 열지
않는다** — 헤더 `+` 를 누르면 곧바로 `/plans/new` 로 간다. 시트는 AI 가 붙을 때 만든다.

## S3. 셀 수 없는 것을 숫자로 적지 않는다

`GET /plans` 에는 **`status` 파라미터가 없고 `totalCount` 도 없다.**
좁히기는 화면에서 한다 ([#13](https://github.com/8llow8llowMe/hondigagae/issues/13) 긴급 시설과 같은 결정).

**`petId` 는 있다** — `PlanWebController#getMyPlans` 의 `@RequestParam(required = false) Long petId`
("반려견별 여행 히스토리", 커밋 `8a63485`). 앞서 "없다" 고 적었던 것은 **틀렸다**
([#148](https://github.com/8llow8llowMe/hondigagae/issues/148) 에서 정정).
그래도 **쓰지 않는다**: 화면의 반려견 필터는 **다중 선택**(`PlanFilters.petIds`)인데 서버는
단일이라 표현할 수 없고, 한 마리만 골랐을 때만 서버로 넘기면 같은 필터가 선택 개수에 따라
다른 경로로 동작한다. 아래 개수 규칙도 `hasNext` 때문에 그대로다.

- 첫 페이지 `size=50` → `hasNext` 면 "더 보기" 로 이어 받는다
- **일정이 한 건도 없으면 모바일 상태 탭 · 반려견 칩 줄을 세우지 않는다** ([#913](https://github.com/8llow8llowMe/hondigagae/issues/913)).
  빈 계정 390 에서 `전체 0 · 초안 0 · 확정 0 · 완료 0` 이 빈 상태 위에 섰다 — 좁힐 것이 없는 화면에서
  가장 먼저 읽히는 것이 0 네 개였다. 판정은 목록을 다 받은 뒤(`countable`)에만 한다. 데스크톱 레일은
  2단 grid 의 열 자리라 그대로 둔다.
- **`hasNext` 가 참인 동안 필터 개수를 전부 숨긴다** — 상태 탭의 `3 · 1 · 0 · 2`,
  레일의 반려견별 개수, 헤더의 `일정 4개 · 다가오는 일정 2개` 가 모두 해당한다.
  아직 안 받아 온 것을 0 이라고 말할 수 없다
- 필터 결과가 비면 **"지우면 몇 개가 있는지"** 를 문장에 넣는다 (아트보드 05).
  이 숫자도 전량을 받았을 때만 말한다

긴급 시설의 `countsAreComplete` 와 같은 규칙이고, 근거만 다르다 — 저쪽은
`facilities.length < totalCount`, 이쪽은 `hasNext` 다.

## S4. 여행 중 / 다가오는 / 지난은 **날짜**로 나눈다 — 상태가 아니다

아트보드는 "다가오는 일정"에 초안을, "지난 일정"에 완료 2건을 둔다. 상태로 나눈 것처럼
보이지만 **그렇게 구현하면 지난 일정이 영원히 비어 있는다.**

`PlanStatus.COMPLETED` 는 **사람이 닫는다.** 서버 자동 전이는 없다. 일정 상세의
`여행 완료하기` 가 `PUT /plans/{planId}` `{ status: 'COMPLETED' }` 를 보낸다 (#613).
초안에서는 완료를 열지 않고, 완료에서는 초안으로 되돌리지 않는다. 시작일 전에는 서버가
완료를 `PLAN_026` 400 으로 거절하고(시작일 당일부터 허용, #971), 화면도 그 전에는 진입점을
두지 않는다 (일정상세 세부명세 D18-1). 같은 선에서 항목의 `다녀옴` 표시도 시작일 전에는
`PLAN_027` 400 으로 거절된다(해제는 언제나 허용, #983) — 화면은 D-1 이전 미체크 행에 토글을
두지 않는다 (일정상세 세부명세 D9-3-1).

→ **`endDate` 가 오늘보다 이전이면 지난 일정이다.** 상태 배지는 서버가 준 `status.name`
을 그대로 보여준다. **둘은 다른 축이다** — 완료 배지가 없어도 지난 일정에 들어가고,
확정 배지를 단 채 지난 일정에 있을 수 있다.

### S4-1. 칸은 셋이다 — 가운데가 비어 있었다 (#561)

처음에는 "지난 게 아니면 전부 다가오는" 이었다. 그래서 **오늘 여행 중인 일정**이
`다가오는 일정` 제목 아래 D-day 도 없이 섰다 — dev 실측으로 `2026-09-11 ~ 09-14` 일정을
09-14 에 보니 배지 자리가 빈 채였고, 바로 아래 `D-11` 과 나란히 놓여 더 눈에 띄었다.

두 규칙(`isPastPlan` · 남은 일수)은 각자 맞았다. **없던 것은 그 사이의 상태**다.

| 칸              | 조건                   | 기둥            | 날짜 줄          |
| --------------- | ---------------------- | --------------- | ---------------- |
| `여행 중`       | 시작일 < 오늘 ≤ 종료일 | `여행 중`       | `… · 오늘 N일차` |
| `다가오는 일정` | 오늘 ≤ 시작일          | `D-N` / `D-DAY` | 기간만           |
| `지난 일정`     | 종료일 < 오늘          | 없음            | 기간만           |

- **출발 당일은 `다가오는 일정` 에 남는다.** 그날 할 말은 `D-DAY` 이고 그게 `여행 중`
  보다 강하다. 그래서 `오늘 N일차` 의 `N` 은 항상 2 이상이고, 하루짜리 일정은 `여행 중`
  을 거치지 않는다.
- **판정은 `lib/plan/date.ts` 의 `planPhaseOf` 하나가 한다.** 목록 · 홈 행 · 상세 개요가
  같은 함수를 쓴다 — 두 화면이 같은 일정에 다른 말을 하면 어느 쪽이 맞는지 알 수 없다.
  문구로 옮기는 것도 `lib/plan/phase-text.ts` 한 군데에서만 한다.
- **홈은 제목이 바뀐다.** 한 건만 세우므로(`UPCOMING_PLAN_COUNT === 1`) 그 일정이 여행
  중이면 섹션 제목이 `진행 중인 일정` 이 된다. 여러 건을 세우게 되면 이 규칙은 다시
  봐야 한다 — 섞이면 어느 쪽도 제목이 될 수 없다.
- 날짜를 못 읽으면 `다가오는 일정` 에 두고 기둥을 비운다. 지난 쪽으로 미는 편이 더
  위험하다.
- 기간이 역전된(`endDate < startDate`) 깨진 데이터는 `지난 일정` 으로 떨어진다.

**같은 말이 겹치는 것을 감수한다.** 여행 중이면 묶음 제목(`여행 중`) · 기둥(`여행 중`) ·
날짜 줄(`오늘 N일차`)이 함께 선다. 겹쳐도 기둥을 비우지 않는 이유는 **기둥이 목록의
세로 기준선**이기 때문이다 — 이 이슈의 출발점이 "`D-11` 옆 배지 자리가 빈 채였다" 였고,
묶음을 갈랐다고 그 자리를 다시 비우면 같은 인상이 돌아온다. 제목은 스크롤로 밀려 사라지지만
기둥은 행마다 남는다. `오늘 N일차` 만 행마다 값이 다르므로, 값이 겹치는 것은 제목과
기둥 둘뿐이다.

## S5. 정렬 — 서버 순서를 이 화면에서는 재정렬한다

`PlanRepository.findByMemberIdAndDeletedFalseAndIdLessThanOrderByIdDesc` — 서버 정렬은
**`id DESC`(생성 역순)** 다. 날짜순이 아니다.

긴급 시설은 "서버 순서를 재정렬하지 않는다" 였다. **여기서는 재정렬한다** — 저쪽의 서버
순서는 *거리순*이라 사용자에게 의미가 있었지만, 이쪽의 `id DESC` 는 *만든 순서*라 여행
목록에서 아무 의미가 없다. 아트보드가 D-day 를 기둥으로 세운 것이 그 근거다.

- 여행 중: `startDate` **오름차순** (먼저 떠난 여행이 위 — 보통 한 건이다)
- 다가오는 일정: `startDate` **오름차순** (가까운 여행이 위)
- 지난 일정: `endDate` **내림차순** (최근 여행이 위)

**부분 정렬이라는 점을 감추지 않는다.** `hasNext` 인 동안에는 받아 온 것 안에서만
정렬된 것이고, "더 보기" 로 받은 일정이 위쪽에 끼어들 수 있다. 이건 커서 페이지네이션의
본질이라 화면이 고칠 수 없다 — 개수를 숨기는 것과 같은 이유로 **개수는 숨기되 순서는
그대로 둔다.** 순서는 숨길 수가 없다.

## S6. 상태 = 배타 / 반려견 = 다중 — 컨트롤로 구분한다

아트보드 04 주석이 못 박은 규칙이다.

| 축     | 모바일                     | 데스크톱 (좌 280 레일) |
| ------ | -------------------------- | ---------------------- |
| 상태   | 전폭 균등 4열 밑줄 탭 48px | **라디오** (배타)      |
| 반려견 | 칩 (`aria-pressed`)        | **체크박스** (다중)    |

- 같은 세로 목록을 전부 `aria-pressed` 토글로 두면 **상태도 다중 선택으로 읽힌다**
- 상태 탭은 `role="tablist"` 가 아니라 **`radiogroup`** 이다 — 탭은 패널을 바꾸는 것이고
  여기서는 같은 목록을 거르는 것이다. 모바일의 밑줄은 시각 표현일 뿐이다
- **"적용된 필터" 칩 줄은 만들지 않는다** — 같은 정보를 세 곳에 두지 않는다
- 기간·지역 필터는 넣지 않는다 (아트보드 주석: 일정이 20개를 넘을 때)

**좌측 레일은 280 이다.** 홈·상세의 400 은 프로필·판정을 담는 "맥락 패널" 이고 목록의
좌측은 "필터 레일" 이라 역할이 달라 폭도 다르다.

어느 것도 아니면 초안과 같은 점선으로 그리고 `name` 을 그대로 쓴다.

## S8. 반려견 정보는 별도 조회로 합친다

목록은 `petId` 만 준다. 이름·사진·품종·나이는 `GET /members/me/pets` 에 있다.
**최대 5마리라 항상 전량이 오고 `SliceResponse` 가 아니다** — 합류 비용이 없다.

- 반려견 조회가 **실패해도 목록은 보인다.** 필터 레일과 행의 반려견 칩만 빠진다 —
  일정 자료는 우리 DB, 반려견은 다른 서비스다 (아트보드 06 ③ 과 같은 태도)
- 목록에 있는 `petId` 가 반려견 목록에 없으면(삭제된 반려견) **그 일정을 숨기지 않는다.**
  무엇을 보여 줄지는 아래 S8-1 이 정한다

### S8-1. 반려견을 지운 뒤의 동행 표시 ([#1042](https://github.com/8llow8llowMe/hondigagae/issues/1042))

반려견을 지우면 plan-service 가 삭제 응답 전에 동행 목록을 정리한다 (#972, `backend/docs/services/plan-service.md`
"반려견이 삭제되면"). 다견 미완료 일정에서는 그 아이가 빠지지만 **두 경우는 지운 petId 가 `petIds` 에 남는다** —
그 아이만 동행하던 미완료 일정(`PLAN_010` "최소 한 마리" 때문에 자리 표시자로 남는다)과 완료 일정(기록이라 불가침).
화면은 `petIds ∩ 내 반려견 목록` 으로 읽는다 — `planCompanionsOf` (`src/lib/plan/companion-pets.ts`).

| 반려견 목록        | 일정 상태   | 교집합     | 목록 행 · 상세 카드                                       |
| ------------------ | ----------- | ---------- | --------------------------------------------------------- |
| 받기 전 · **실패** | 무관        | —          | 자리만 빠진다 — **"동행 반려견 없음" 을 단정하지 않는다** |
| 받음               | 초안 · 확정 | 비었다     | **동행 반려견 없음** (아바타 없음)                        |
| 받음               | 초안 · 확정 | 있다       | 찾은 아이만 — 못 찾은 id 는 조용히 뺀다                   |
| 받음               | 완료        | 못 찾은 id | **삭제된 반려견** — 행은 수에 넣고, 상세는 수로 한 줄     |

- **조회 실패와 "비었다" 를 가른다.** 반려견 목록을 `null` 로 넘기면 "모른다" 다. 빈 배열로 넘기면 반려견
  서비스의 일시 장애가 모든 일정의 "동행 반려견 없음" 으로 읽힌다
- **미완료 일정의 못 찾은 id 는 세지 않는다.** 다견 일정이면 삭제 트리거가 이미 뗐어야 하고, 남아 있다면
  트리거가 실패해 새벽 배치가 곧 뗄 값이다
- **완료 일정은 지운 아이도 센다** — "몽실이 외 1마리" 로 다녀온 일정이 "몽실이" 혼자 다녀온 것처럼 읽히지 않게
- **편집 폼은 이 규칙을 따라가지 않는다.** 초기 체크는 여전히 옵션에 있는 아이만이다(`planEditPetIds`) —
  자리 표시자 id 를 체크된 채로 열면 저장이 `PLAN_011` 로 죽는다. 0마리로 열린 폼의 저장은 #752 가 열어 두었다

## S9. 만들기 폼 (`/plans/new`)

**묻는 순서는 `/ai-plans/new` 와 같다** (#400). 두 화면은 같은 일을 하는 두 갈래인데
순서가 어긋나면 한쪽을 써 본 사람이 다른 쪽에서 다시 헤맨다. 회귀는
`src/features/plan/form-order.test.ts` 가 **두 폼을 함께 읽어** 잡는다.

| 순서 | 필드   | 컨트롤          | 비고                                                     |
| ---- | ------ | --------------- | -------------------------------------------------------- |
| 1    | 시작일 | `date`          |                                                          |
| 2    | 종료일 | `date`          | 시작일보다 이르면 그 자리에서 막는다 (`PLAN_003` 선반영) |
| 3    | 반려견 | 라디오 목록     | **반려견이 0마리면 폼 대신 등록 유도**를 보여준다        |
| 4    | 제목   | `text` (60자)   | 서버 제한과 같은 값                                      |
| 5    | 예산   | 금액 입력(선택) | 0 이상. `AmountInput` — 아래 「예산 입력」               |

- **기간이 먼저다.** 여행 계획은 "언제 가지" → "누구랑" 순서이고, **시작일을 고르면 종료일
  달력이 이어서 열리는** 흐름이 기간이 첫 블록일 때 가장 자연스럽다 — 중간에 있으면 위
  필드를 지나쳐 온 뒤에 달력이 두 번 튀어나온다
- **`예산` 을 접기 안에 넣지 않는다.** `/ai-plans/new` 는 선택 입력이 넷이라 접기가 값을
  하지만(#354) 이 화면은 하나뿐이다 — 하나를 위해 접기를 두면 여는 동작이 그 하나보다
  비싸다. **필수 뒤 맨 끝**이라는 자리로 같은 것을 말한다

- `areaCode` 는 **입력받지 않는다.** 제주 전용 서비스라 `DEFAULT_AREA_CODE`(`'39'`) 고정.
  선택지가 하나뿐인 필드를 폼에 두지 않는다
- `items` 는 보내지 않는다 — 빈 일정을 만들고 장소는 일자 편집 화면에서 담는다
  (아트보드 만들기 시트: "빈 일정을 만들고 장소를 담아요")
- **생성 후 `/plans` 로 돌아간다.** 상세 화면이 아직 없다. 상세가 생기면
  `/plans/{planId}` 로 바꾼다
- 검증 문구는 `PlanValidationMessage` 복제본이라 **어미를 해요체로 바꾸지 않는다**
  (`// PLAN_NNN` 주석을 단다). 바꾸면 같은 폼에서 클라이언트·서버 말투가 갈린다

### 날짜 정책 — 지난 여행도 기록으로 만든다 (#973)

**직접 만들기 · 수정 · 복사는 지난 날짜를 막지 않는다. AI 생성만 오늘 이후다.** 두 폼의
정책이 다른 것은 의도다 — 막는 이유가 AI 에만 있다.

| 진입점                   | 시작일 `min` | 서버                                          | 근거                                               |
| ------------------------ | ------------ | --------------------------------------------- | -------------------------------------------------- |
| `/plans/new` 직접 만들기 | 없음         | `POST /plans` 과거 허용 (`validateDateRange`) | 다녀온 여행을 기록으로 남긴다                      |
| 일정 수정 모달           | 없음         | `PUT /plans/{id}` 과거 허용                   | 이미 시작한 · 지난 일정을 고친다                   |
| 일정 복사                | 없음         | `POST /plans/{id}/copy` 과거 허용             | 지난 일정을 옮겨 적는다                            |
| `/ai-plans/new` AI 생성  | `today`      | `AIPLAN_017` — 오늘 이후만                    | **예보가 있어야 짠다.** 지난 날은 날씨 근거가 없다 |

- **지난 시작일을 고르면 시작일 아래에 한 줄을 세운다** — `pastStartDateHint`
  ("지난 날짜예요. 다녀온 여행의 기록으로 만들어져 날씨·적합도는 볼 수 없어요."). 막지 않고
  **무엇이 비는지**만 말한다. 상세는 그 날의 날씨·적합도 자리를 "지난 날이라 확인할 수
  없어요" 로 채우는데, 만든 뒤에 처음 알게 하지 않는다.
- 기록용 일정은 이미 시작일이 지났으므로 **완료(#971) · 다녀옴 표시(#983) 가드에 걸리지 않는다** —
  두 가드는 "오늘 < 시작일" 인 여행만 막는다.
- 회귀: BE `PlanCommandProcessorTest` "지난 날짜로도 만든다", FE `plan-create-form.test.ts`
  "지난 시작일을 고르면 …".

### 예산 입력 — 천 단위 쉼표 (#986)

만들기 폼 · 수정 모달(`plan-edit-budget`) · `/ai-plans/new` 의 `budgetManwon` 이 **같은
`AmountInput`**(`src/components/amount-input.tsx`)을 쓴다. 규칙과 커서 계산의 정본은
`src/lib/form/grouped-digits.ts` 다.

- **입력란에는 `300,000`, 폼 값은 `'300000'`** 이다. 쉼표는 표기라 폼 값 · 전송 값에 들어가지
  않는다 — 그래서 스키마(`/^\d+$/` · `PLAN_BUDGET_MAX` 상한)와 전송 변환(`Number(...)`)은 그대로다
- **숫자 외 글자는 버린다.** 붙여넣기 `300,000원` · `₩ 300000` · 전각 `３００` 도 숫자로 읽는다
- **정수만 받는다 — 붙여넣기의 소수부는 버린다.** `300,000.00` → `300,000`, AI 폼 `1.5` → `1`.
  `.` 을 여느 글자처럼 지우면 `30,000,000` · `15` 가 되어 값이 조용히 100배 · 10배가 된다
  (#986 리뷰). 직접 친 `.` 은 반영하지 않는다(값 · 커서 유지). 천 단위 구분이 `.` 인 로케일
  표기(`300.000`)는 이 서비스 대상이 아니라 **소수로 읽는다**
- **전부 지우면 빈 값이다** (`0` 이 아니다). 빈 값의 뜻은 폼마다 그대로 — 만들기는 키 생략,
  수정은 `0` 전송(`일정상세-세부명세.md` 의 `PUT` 절), AI 는 "상관없음"
- **앞자리 0 은 치는 편집에서만 뗀다.** 지우기로 생긴 앞자리 0 은 남긴다 — `300,000` 에서
  첫 자리 3 을 지우면 `00,000` 이고, 이어서 5 를 치면 `500,000` 이다. 떼면 `0` → `50` 이
  되어 사용자가 지우지 않은 자릿수가 사라진다(#986 리뷰). 남은 앞자리 0 은 **포커스를 떠날 때**
  정리한다(`00,000` → `0`). `Number()` 로 읽은 값은 같아 스키마 · 전송 값이 달라지지 않는다.
  `0` 하나만은 값("예산 0원")이라 남긴다
- **커서는 방금 친 숫자 바로 뒤에 남는다.** 쉼표가 생기거나 사라져도 "앞에 숫자가 몇 개
  있었나" 로 옮기기 때문이다. 쉼표 바로 뒤 백스페이스는 **그 앞 숫자**를, 쉼표 앞 Delete 는
  **그 뒤 숫자**를 지운다 — 쉼표만 지우면 다시 그릴 때 되살아나 "눌러도 안 지워진다" 가 된다.
  단어 단위 지우기(`deleteWordBackward` 등)도 쉼표만 지웠으면 같은 규칙이다
- `type="number"` 가 아니라 `text` + `inputMode="numeric"` 이다 (휠 스크롤로 값이 바뀌지 않고
  모바일에서 숫자 키패드가 열린다). `maxLength` 는 쉼표까지 세므로 받지 않는다
- 회귀: 순수 로직은 `grouped-digits.test.ts`, 세 사용처는 `amount-input.test.ts`(소스) ·
  각 폼 렌더 테스트, 실제 커서 · 붙여넣기 · 전송 값은 `e2e/amount-input.spec.ts`
- **알려진 한계 — 고치지 않는다** (#986 리뷰):
  - 쉼표 **하나만 선택**해 지우면 쉼표만 지운 백스페이스와 구분되지 않아 그 앞 숫자가 지워진다
  - IME **조합 중** 되쓰기 — 일본어 · 중국어 전각 조합, 일부 Android 키보드에서 조합이 끊길 수
    있다. 숫자 키패드(`inputMode="numeric"`)에서는 조합이 거의 생기지 않는다
  - **음수 부호**는 글자로 보고 버린다 — `-300` 을 붙여 넣으면 `300` 이다. 예산은 0 이상이라
    음수가 들어올 자리가 없지만, 부호가 사라졌다고 따로 알리지는 않는다
