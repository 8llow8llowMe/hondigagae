## D0. 화면 정의

- **경로**: **새 라우트를 만들지 않는다.** 일정 상세(`/plans/[planId]`) 안의 **모달**이다
  (`PlanCopyModal`). 근거 셋:
  - 입력이 기간 한 쌍뿐이다. `PlanEditModal`(이름·기간·예산)보다 작은 폼에 세그먼트를
    새로 열 이유가 없다.
  - 라우트를 만들면 그 세그먼트에 `not-found.tsx` · `error.tsx` 를 또 세워야 한다
    (`일정상세-세부명세.md` D3 의 soft 404 규칙).
  - 실패했을 때 **돌아갈 자리가 원본 상세**다. 모달이면 그 자리를 떠나지 않는다.
- **인증**: **필요**. `proxy.ts` `PROTECTED_PATHS` 의 `'/plans'` 가 `/plans/{planId}` 를 이미
  덮는다 — 추가 등록이 없다 (`일정상세-세부명세.md` D0 과 같은 근거).
- **진입 경로**: 일정 상세 좌 레일 관리 메뉴(`PlanManageMenu`) → `이 일정 복사하기`.
  **보이는 조건은 D4-1 에 있다.**
- **이탈 경로**:
  - 성공 → `router.push('/plans/{새 planId}')` — **새 일정 상세**
  - 취소·닫기 → 원본 상세 그대로 (아무것도 바뀌지 않는다)

## D1. 레이아웃

`PlanEditModal` 과 **같은 골격**이다 — 같은 메뉴에서 열리는 같은 성격의 폼이 서로 다른
모양이면 사용자가 두 화면을 다른 기능으로 읽는다.

  → 기간 힌트 한 줄 → 승계 힌트 한 줄 → `FormAlert`(실패 시) → 푸터(`취소` · `복사하기`).
  두 날짜는 **세로로 쌓인다**.
- **태블릿 (768)**: 두 날짜가 한 줄(`flex-col sm:flex-row`, 각 `flex-1`) — `PlanEditModal`
  의 기간 줄과 같은 클래스다.
- **데스크톱**: 같음. `Modal size="md"` 가 폭을 잡는다.

긴 한국어 실데이터로 확인할 항목:

- 제목 60자 일정에서 설명 문단(제목을 인용하지 않는다 — D5 확정 문구 참고)이 두 줄을 넘지 않는지
- 기간 힌트의 치환값이 **`30일`** 까지 들어갔을 때 (상한, D3-2)
- 서버 거절 문구 중 가장 긴 `PLAN_010`(_"동행할 반려견을 지정하거나 대표 반려견을 등록해
  주세요."_) + 뒤따르는 링크가 한 줄에 눌리지 않는지

## D3. 데이터 흐름

```text
상세 화면(이미 hydrate 됨)
  └ 관리 메뉴 → 이 일정 복사하기 → PlanCopyModal
        └ [client] POST /plans/{planId}/copy  { startDate, endDate }
              ├ 200 → setQueryData(planKeys.detail(새 planId), 응답)
              │        invalidate planKeys.list()
              │        router.push(`/plans/${새 planId}`)
              └ 4xx/5xx → 모달 안 FormAlert (D5)
```

| 항목                   | 내용                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| API                    | `POST /api/v1/plans/{planId}/copy` (클라이언트. 서버 프리페치 대상이 아니다 — 사용자 동작으로만 일어난다)          |
| React Query key        | 읽기 key 없음(**mutation**). 성공 응답을 `planKeys.detail(새 planId)` 에 심고 `planKeys.list()` 를 invalidate 한다 |
| staleTime / retry      | mutation 이라 `staleTime` 없음. **재시도 없음** — 같은 본문을 자동 재전송하면 일정이 두 개 생긴다                  |
| mutation 후 invalidate | `planKeys.list()` 만. **원본의 `detail`·`weather`·`packing`·`review` 는 건드리지 않는다** (D3-4)                   |
| 폴링 여부 / 종료 조건  | 없음. **동기 API 다** — AI 일정 생성(202 + 폴링)과 다르다                                                          |

### D3-1. 계약 — `POST /api/v1/plans/{planId}/copy`

경로·메서드 근거: `PlanWebController.java:82-93` (`@PostMapping("/{planId}/copy")`,
`@PreAuthorize("isAuthenticated()")`, 응답 `Response<PlanDetailResponse>`).

**요청 본문** (`PlanCopyRequest.java:11-26`, dev Swagger `PlanCopyRequest` 와 일치)

```json
{
  "title": "몽실이와 제주 2박 3일 (복사)",
  "startDate": "2027-09-12",
  "endDate": "2027-09-14"
}
```

| 필드        | 타입                    | 필수     | 실측 근거                                                                                    |
| ----------- | ----------------------- | -------- | -------------------------------------------------------------------------------------------- |
| `title`     | `string`                | **선택** | `PlanCopyRequest.java:13-15` `@Size(max = 60)` → 위반 시 `PLAN_104`. Swagger `maxLength: 60` |
| `startDate` | `string` (`YYYY-MM-DD`) | **필수** | `PlanCopyRequest.java:17-20` `@NotNull` → `PLAN_105`. Swagger `required` 에 포함             |
| `endDate`   | `string` (`YYYY-MM-DD`) | **필수** | `PlanCopyRequest.java:22-25` `@NotNull` → `PLAN_106`. Swagger `required` 에 포함             |

- **경로 `planId` 는 `long` 이다** (`PlanWebController.java:86`, Swagger `type: integer, format: int64`).
  FE 는 **문자열로 들고 다닌다** — 기존 `paths.plans.detail(planId: string)` 과 같다.
  숫자가 아닌 값은 서버가 **400 `PLAN_124`** 로 답하고(모양은 일정상세 명세 D5-1), 화면은
  그 경로로 들어올 수 없다(메뉴에서만 연다).
- **이 화면은 `title` 을 보내지 않는다** (D0-1 · D8 #2). 서버가 원본 제목 뒤에 ` (복사)` 를
  붙이고 60자를 넘으면 앞을 잘라 맞춘다 (`PlanCommandProcessor.java:376-384`).

**응답 `dataBody`** — `PlanDetailResponse`, 즉 **일정 상세와 완전히 같은 타입**이다
(Swagger `ResponsePlanDetailResponse`, 필드 `planId·petId·petIds·areaCode·sigunguCode·title·
startDate·endDate·budget·status·totalDays·items`). FE 타입 `PlanDetail`(`types/plan.ts`)
을 그대로 쓴다 — **새 타입을 만들지 않는다.**

- `status` 는 `{code,name,description}` metadata 이고 **복사본은 항상 `DRAFT`** 다
  (`PlanCommandProcessor.java:114`). 화면은 서버가 준 `name` 을 그대로 렌더한다 —
  한국어 매핑 테이블을 만들지 않는다.
- 래퍼(`dataHeader.success`) 판별은 `docs/api-integration-guide.md` §2 를 따른다.

### D3-2. 서버가 거절하는 경우 — **화면이 문장을 짓지 않는다**

검사 순서가 소스에 그대로 있다 (`PlanCommandProcessor.java:98-102`):
`validateDateRange(start, end)` → **그다음** 일수 비교.

| HTTP | `resultCode`   | 서버 `resultMessage` (그대로 노출)                      | 실측 근거                                                         | 화면 처리                                    |
| ---- | -------------- | ------------------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------- |
| 400  | `PLAN_021`     | 복사할 여행 기간의 일수는 원본과 같아야 합니다.         | `PlanErrorCode.java:31` · `PlanCommandProcessor.java:100-102`     | **폼 배너**. 재시도 버튼 없음                |
| 400  | `PLAN_003`     | 여행 시작일은 종료일보다 늦을 수 없습니다.              | `PlanErrorCode.java:13` · `PlanCommandProcessor.java:305-307`     | 화면이 **먼저 막는다**(D4-2). 뚫리면 폼 배너 |
| 400  | `PLAN_009`     | 여행 기간은 최대 30일까지 만들 수 있습니다.             | `PlanErrorCode.java:18` · `PlanCommandProcessor.java:309-311`     | 화면이 **먼저 막는다**(D4-2)                 |
| 400  | `PLAN_010`     | 동행할 반려견을 지정하거나 대표 반려견을 등록해 주세요. | `PlanErrorCode.java:20` · `PlanCommandProcessor.java:144-156`     | 폼 배너 + `반려견 관리로 가기` 링크 (D5)     |
| 400  | `PLAN_105/106` | 여행 시작일은 필수입니다. / 여행 종료일은 필수입니다.   | `PlanValidationMessage.java:11-12`                                | `fieldErrors` → 각 필드. 화면이 먼저 막는다  |
| 404  | `PLAN_001`     | 존재하지 않는 여행 일정입니다.                          | `PlanErrorCode.java:11` · `PlanWebFacade.java:67`(`getOwnedPlan`) | 폼 배너 + `목록으로` 링크. **재시도 금지**   |
| 5xx  | —              | —                                                       | `docs/api-integration-guide.md` §3                                | 폼 배너 + 같은 버튼으로 다시 제출 가능       |

- **`PLAN_010` 은 "원본의 동행 반려견을 지금은 한 마리도 소유하지 않는다" 는 뜻이다.**
  서버는 원본 구성에서 **지금 내 소유인 아이만** 남기고, 남는 아이가 없으면 대표 반려견
  폴백 없이 거절한다 (`PlanCommandProcessor.java:144-156`). **이 화면은 미리 판정하지
  않는다** — 반려견 목록을 또 불러 소유를 대조하는 것은 서버 규칙의 복제다.
- **404 는 "남의 일정"과 "없는 일정"을 구분하지 않는다** (`getOwnedPlan` 이 둘 다
  `PLAN_001`). 화면도 존재 여부를 흘리지 않는다 — 상세와 같은 규칙이다.
- **`PLAN_022`(공유 가능 상태) 같은 상태 제약은 이 API 에 없다.** 소스·Swagger 어디에도
  `status` 검사가 없다 — `copyPlan` 은 `DRAFT`·`CONFIRMED`·`COMPLETED` 를 가리지 않는다.
  **진입점을 좁히는 것은 FE 의 판단이다** (D4-1 · D8 #1).

### D3-3. 무엇이 복사되고 무엇이 복사되지 않는가

복사 결과는 **새 일정 하나**이고 (`PlanCommandProcessor.java:104-137`), 원본은 어떤 필드도
바뀌지 않는다 — 소스의 `copyPlan` 은 `source` 를 **읽기만** 한다.

| 대상                                                                     | 승계 | 실측 근거                                                                                   |
| ------------------------------------------------------------------------ | ---- | ------------------------------------------------------------------------------------------- |
| 지역(`areaCode`·`sigunguCode`) · `budget`                                | O    | `PlanCommandProcessor.java:108-113`                                                         |
| 항목의 `day`·`sequence`·`itemType`·`targetId`·`title`·`memo`·`startTime` | O    | `PlanCommandProcessor.java:121-135`                                                         |
| 동행 반려견                                                              | △    | 원본 구성에서 **지금 소유한 아이만** (`:144-156`). 첫 번째가 대표                           |
| 상태                                                                     | ✗    | 항상 `DRAFT` (`:114`)                                                                       |
| 방문 체크(`visited`)                                                     | ✗    | `toItems`(`:396-410`)가 `visited` 를 옮기지 않는다 — 새 항목은 미방문                       |
| 준비물 · 후기                                                            | ✗    | 복제 코드가 두 저장소를 부르지 않는다. 컨트롤러 설명도 명시(`PlanWebController.java:72-75`) |
| 반려견 컨디션 스냅샷                                                     | ✗    | `planPetConditionRepositoryPort` 를 `copyPlan` 이 부르지 않는다                             |
| 일자별 날씨 판정                                                         | ✗    | 날짜가 달라 새로 조회된다 (새 일정 상세 진입 시 `planKeys.weather`)                         |

**이 표는 화면 문구가 된다** (D5 의 `copyDescription` · `copyCarryHint`). 사용자가 복사 뒤
"준비물이 왜 없지" 를 묻게 두지 않는다.

### D3-4. 캐시 — 원본을 건드리지 않는다

- **원본 `planKeys.detail(원본)`·`weather`·`packing`·`review` 를 invalidate 하지 않는다.**
  서버가 원본을 수정하지 않으므로 버릴 이유가 없고, 버리면 모달을 닫자마자 원본 상세가
  불필요하게 다시 조회된다.
- **`planKeys.list()` 는 invalidate 한다.** 목록에 일정이 하나 늘었다.
- **새 일정은 `setQueryData(planKeys.detail(새 planId), 응답)`** 로 심는다. 응답이 상세와
  같은 타입이라 이동 직후 화면이 조회 없이 그려진다 — `PlanEditModal` 이 `PUT` 응답을
  심는 것과 같은 판단(`plan-edit-modal.tsx`).
- **새 일정의 `weather` 는 심지 않는다.** 복사 응답에 판정이 없고 날짜가 바뀌었다.

## D4. 상호작용

| 트리거                       | 동작                                                                 | 결과                                                                    |
| ---------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 관리 메뉴 `이 일정 복사하기` | 메뉴 닫고 `PlanCopyModal` 열기                                       | 시작일·종료일이 **비어 있다** (D4-3)                                    |
| 시작일 선택                  | 종료일을 `copyEndDateFor(시작일, plan.totalDays)` 로 **자동 채운다** | 사용자는 그대로 고칠 수 있다. **검증이 아니라 기본값이다** (D4-2)       |
| 종료일 선택                  | 값만 바꾼다                                                          | 자동 채움을 덮어쓴다                                                    |
| `복사하기`                   | `validatePlanCopy` 통과 시 `POST …/copy`                             | 진행 중 버튼 `loading`, 중복 제출 차단(`savingRef`, `form-guide.md` §6) |
| 성공                         | `setQueryData` + `invalidate` + `router.push('/plans/{새 id}')`      | **새 일정 상세.** 원본은 그대로 남는다                                  |
| 실패                         | `toPlanCopyError(cause)` → `FormAlert`                               | 모달을 **닫지 않는다** — 닫으면 무엇이 실패했는지 사라진다              |
| `취소` · 백드롭 · `Esc`      | 모달 닫기                                                            | 아무것도 저장되지 않는다                                                |

### D4-1. 진입점 — **일정 상세 관리 메뉴 하나다**

**목록에는 두지 않는다.** `plan-row.tsx` 의 `PlanRow` 가 행 전체를 `<Link>` 로 감싸고 있고, 이
저장소는 **링크 안에 링크·버튼을 넣지 않는다**(`일정상세-세부명세.md` D6, `pet-row.tsx`
와 같은 규칙). 목록에 복사를 붙이려면 행 구조를 통째로 바꿔야 하는데, 그것은 이 이슈의
범위가 아니다 (D8 #3).

**메뉴 안 위치**: `이름·기간·예산 수정` **바로 다음**, 역방향 상태 항목보다 **위**.
선 아래 `danger-900` 자리는 `일정 삭제` 혼자 남는다 (`DESIGN.md` §2-6).

```text
이름·기간·예산 수정
이 일정 복사하기      ← 신규
(초안으로 되돌리기 / 확정으로 되돌리기)   ← 상태에 따라
───────────────────
일정 삭제
```

근거: 복사는 **이 일정을 바꾸지 않고 새 일정을 만든다.** 아래 두 묶음(상태를 바꾼다 /
이 일정을 지운다)은 모두 *이 일정*에 손대는 항목이라, 손대지 않는 항목을 그 위에 둔다.
**파괴적이지 않으므로 선 아래로 내리지 않는다.**

**보이는 조건 / 숨는 조건** — 두 축을 `OR` 로 본다.

| 일정                                                | `이 일정 복사하기` | 근거                                                              |
| --------------------------------------------------- | ------------------ | ----------------------------------------------------------------- |
| 종료일 < 오늘 (`isPastPlan`)                        | **보인다**         | "지난 일정" 이 이 이슈의 대상이다                                 |
| `status.code === 'COMPLETED'`                       | **보인다**         | 다녀온 여행이다. 날짜가 아직 안 지났어도 같은 의미다              |
| 여행 중(`ongoing`) · 다가오는(`upcoming`) 초안·확정 | **숨는다**         | 아직 다녀오지 않은 일정을 복사하면 같은 기간의 중복 초안이 생긴다 |
| 날짜를 못 읽는 깨진 데이터 (`planPhaseOf === null`) | **숨는다**         | 지난 쪽으로 밀지 않는다 (`lib/plan/date.ts` 의 기존 판단과 같다)  |

- 판정은 **순수 함수 하나**(`canCopyPlan(plan, today)`)가 갖는다. `today` 는 **서버가 내려준
  값**을 쓴다 — 상세 화면이 이미 `today` 를 내려받아 `PlanManageMenu` 에 넘기고 있다
  (`plan-manage-menu.tsx` 의 `today` prop). 클라이언트가 `new Date()` 를 또 부르면 자정
  근처에서 SSR 과 갈린다.
- **`isPastPlan` 과 `COMPLETED` 는 다른 축이다** (`lib/plan/date.ts` 의 `isPastPlan` 주석이
  그렇게 못박는다). 둘 중 하나만 보면 "9월에 다녀와 완료 처리한 10월 일정" 또는 "완료 처리를
  안 한 지난 일정" 한쪽이 복사 진입을 잃는다.
- **서버는 상태를 가리지 않는다** (D3-2). 이 제한은 화면 쪽 판단이므로, 넓히자는 요구가
  오면 `canCopyPlan` 한 곳만 고치면 된다.

### D4-2. 클라이언트 선차단 — **상한은 막고, 일수 일치는 막지 않는다**

| 규칙                       | 화면이 먼저 막나 | 근거                                                                               |
| -------------------------- | ---------------- | ---------------------------------------------------------------------------------- |
| 날짜 서식 · 빈 값          | **막는다**       | `PLAN_105/106`. 기존 `validatePlanEdit`(`lib/plan/edit.ts`)과 같은 서식 검사       |
| 역전 (`PLAN_003`)          | **막는다**       | `planPeriodIssue` 의 `'reversed'`                                                  |
| 30일 상한 (`PLAN_009`)     | **막는다**       | `planPeriodIssue` 의 `'too-long'` · `lib/plan/period.ts` 의 `PLAN_PERIOD_MAX_DAYS` |
| **일수 일치 (`PLAN_021`)** | **막지 않는다**  | 서버 판정을 복제하지 않는다 — `PLAN_008`(#585)에서 내린 결정과 같다                |

**`lib/plan/period.ts` 의 `planPeriodIssue` 를 그대로 재사용한다** (이슈 지시이자, 이미 만들기
폼·수정 모달이 쓰는 함수다). 새 판정 함수를 만들지 않는다 — 세 폼이 같은 기간에 다른 답을
내면 어느 쪽이 맞는지 알 수 없다 (`period.ts` 머리 주석이 그 이유를 적어 둔 그대로다).

**순서까지 서버와 같다.** 서버는 `validateDateRange`(역전 → 상한)를 **먼저** 보고 일수
비교를 나중에 본다 (`PlanCommandProcessor.java:98-102`). 화면도 `planPeriodIssue` 를 먼저
보고, 통과하면 그대로 제출한다. 순서가 뒤집히면 역전된 기간에 "일수가 원본과 다릅니다" 가
붙어 **틀린 진단**이 나간다.

**상한이 실제로 걸리는 경우는 드물다** — 일수가 원본과 같아야 하고 원본은 이미 30일
이하이기 때문이다. 그래도 **함수에서 `'too-long'` 만 예외 처리하지 않는다.** 예외를 파면
"어떤 폼은 상한을 안 본다" 는 규칙이 하나 더 생기고, 30일을 넘긴 옛 데이터가 있으면 그때만
서버 왕복으로 막힌다. **재사용이 싸고 예외가 비싸다.**

**일수 일치는 서버가 판정한다.** 화면이 `totalDaysBetween(new) === plan.totalDays` 를 세어
막으면 서버 규칙(`PLAN_021`)의 복제본이 생긴다 — `PLAN_008` 을 화면이 다시 세지 않기로 한
#585 의 결정과 같은 이유다. 거절 문구는 **서버 것을 그대로** 배너에 띄운다.

### D4-3. 종료일 자동 채움은 **기본값이지 검증이 아니다**

시작일을 고르면 `copyEndDateFor(시작일, plan.totalDays)`(= `addPlanDays(시작일, totalDays - 1)`,
`lib/plan/date.ts`)로 종료일을 채운다.

- **사용자는 그 값을 고칠 수 있다.** 고쳐서 일수가 달라지면 제출은 그대로 나가고 서버가
  `PLAN_021` 로 답한다 — 화면은 그 문장을 짓지 않는다.
- 이것은 `plan-create-form.tsx`·`PlanEditModal` 이 **시작일이 종료일을 넘으면 종료일을
  비우는** 것과 같은 성격의 도움이다(값을 다루는 편의, 규칙의 복제가 아니다).
- **모달을 열 때 두 날짜는 비어 있다.** 원본 날짜를 미리 채우면 그대로 제출했을 때
  같은 기간의 일정이 하나 더 생긴다 — 복사를 누른 사람이 원한 것은 **다른 기간**이다.
  (원본 날짜를 채우는 대안은 D8 #4.)

## D5. 상태별 화면

**확정 문구** (전부 `src/lib/messages/plan.ts` 에 둔다. 구현자가 즉흥으로 짓지 않는다.)

| 키                      | 문구                                                                     |
| ----------------------- | ------------------------------------------------------------------------ |
| `copyAction`            | `이 일정 복사하기`                                                       |
| `copyTitle`             | `일정 복사`                                                              |
| `copyDescription`       | `담은 장소를 그대로 옮겨 새 초안을 만들어요. 원본 일정은 그대로 남아요.` |
| `copyCarryHint`         | `방문 체크 · 준비물 · 후기는 복사되지 않아요.`                           |
| `copyPeriodHint`        | `원본과 같은 {days}일로 복사돼요. 일수가 다르면 저장되지 않아요.`        |
| `copyTitleHint`         | `제목 뒤에 (복사) 가 붙어요. 복사한 뒤 바꿀 수 있어요.`                  |
| `copySubmit`            | `복사하기`                                                               |
| `copyCancel`            | `취소`                                                                   |
| `copyError`             | `복사하지 못했어요. 잠시 후 다시 시도해 주세요.`                         |
| `copyMissingPlanAction` | `목록으로`                                                               |
| `copyPetAction`         | `반려견 관리로 가기`                                                     |

- `copyPeriodHint` 의 `{days}` 는 `plan.totalDays` 를 치환한다. **`3일` 로 적고 `2박 3일`
  로 적지 않는다** — 서버가 세는 단위가 일수(`totalDays`)이고, 거절 문구도 "일수" 라고
  말한다. 두 단위를 섞으면 사용자가 무엇을 맞춰야 하는지 흐려진다.
- `copyPeriodHint` 를 두는 근거는 `editPeriodHint`(#585)와 같다 — **막힐 수 있다는 사실은
  미리 말하고, 막혔을 때의 문장은 서버 것을 쓴다.**

**상태 표**

| 상태                         | 표시                                         | 문구 (확정)                                                                    |
| ---------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------ |
| loading (모달 열기)          | 없음 — 추가 조회가 없다                      | —                                                                              |
| 기본                         | 설명 + 기간 2필드 + 힌트 2줄                 | `copyDescription` · `copyPeriodHint` · `copyCarryHint` · `copyTitleHint`       |
| 제출 중                      | `복사하기` `loading`, 두 필드 `disabled`     | —                                                                              |
| 입력 오류 (서식·역전·상한)   | 해당 필드 `error` (종료일에 붙인다)          | 기존 `errorStartDateRequired` · `errorDateRange` · `errorPeriodTooLong` 재사용 |
| 일수 불일치 (400 `PLAN_021`) | `FormAlert` **폼 배너**, 재시도 버튼 없음    | **서버 `resultMessage` 그대로**                                                |
| 반려견 없음 (400 `PLAN_010`) | `FormAlert` + `/pets` 링크                   | **서버 `resultMessage` 그대로** + `copyPetAction`                              |
| 원본 사라짐 (404 `PLAN_001`) | `FormAlert` + `/plans` 링크, **제출 비활성** | **서버 `resultMessage` 그대로** + `copyMissingPlanAction`                      |
| 그 밖의 400                  | `FormAlert`                                  | 서버 `resultMessage`. 없으면 `copyError`                                       |
| 일시 장애 (5xx · 무응답)     | `FormAlert`. 같은 버튼으로 다시 제출         | `copyError`                                                                    |
| 401                          | 공통 처리 (재발급 1회 → 로그인)              | `docs/auth-guide.md` §3                                                        |
| 성공                         | 모달 닫고 새 상세로 이동                     | — (별도 토스트를 띄우지 않는다. 화면이 바뀐 것이 곧 결과다)                    |

- **404 에 재시도 버튼을 달지 않는다.** 같은 원본을 다시 불러도 같은 404 다
  (`api-integration-guide.md` §3). 제출 버튼을 비활성으로 두고 `목록으로` 만 남긴다.
- **성공 토스트를 만들지 않는다.** 이동 자체가 결과이고, 이 저장소에 일정 생성 성공 토스트
  전례가 없다(만들기도 상세로 보낼 뿐이다).

## D6. 접근성

- 메뉴 항목은 `Menu` 가 `role="menuitem"` 과 키보드 순회를 이미 보장한다
  (`PlanManageMenu` 주석의 기존 근거). **새 트리거를 만들지 않으므로 icon-only 이슈가
  없다.**
- 모달은 `Modal`(`role="dialog"`) 을 쓴다 — **`ConfirmModal`(`alertdialog`)이 아니다.**
  입력이 있는 폼이고 되돌릴 수 없는 확인이 아니다 (`PlanEditModal` 과 같은 근거).
- 두 날짜 필드는 `Field` 의 `label` 과 `id` 로 묶는다. `DateField` 에 `label` 을 함께 넘긴다
  (달력 버튼의 접근 가능한 이름).
- 힌트 세 줄은 **필드 아래 텍스트**다. 오류(`error`)와 시각적으로 구분되어야 하고, 색만으로
  구분하지 않는다 — 오류에는 필드 `invalid` 와 문구가 함께 간다.
- `FormAlert` 는 실패가 생긴 **그 자리(모달 안)** 에 남는다. 모달을 닫고 뒤에서 알리지
  않는다 (`plan-manage-menu.tsx` 의 삭제 `FormAlert` 와 같은 규칙).
- 터치 영역 44px: 메뉴 항목·날짜 필드·푸터 버튼 모두 기존 컴포넌트가 만족한다.

**메뉴 항목은 e2e 가 본다.** `menu.tsx` 의 `Menu` 가 닫힌 메뉴를 `null` 로 렌더해 정적 마크업에
항목이 없다 — 기존 `수정`·`삭제` 와 같은 한계다(`일정상세-세부명세.md` D11-7).
`e2e/plan-status.spec.ts` 가 이미 두 메뉴를 여는 골격을 갖고 있으므로 거기에 붙인다:

- 지난 일정 메뉴에 `이 일정 복사하기` 가 **있다**
- 다가오는 초안 메뉴에 **없다**
- 항목을 눌러 모달이 열리고 `일정 복사` 제목이 보인다

**mock** — `src/lib/api/mock/plan-data.ts` 에 `POST /plans/{planId}/copy` 를 추가한다.
**백엔드보다 느슨하거나 엄격해서는 안 된다** (`pet-data.ts` 와 같은 규칙):

- 숫자가 아닌 `planId` → 400 `PLAN_124` / 없는·남의 `planId` → 404 `PLAN_001` (기존 헬퍼 재사용)
- `startDate`/`endDate` 누락 → 400 `PLAN_100` + `fieldErrors`(`PLAN_105`/`PLAN_106`)
- 역전 → `PLAN_003`, 31일 → `PLAN_009`, **일수 불일치 → `PLAN_021`** (순서도 서버와 같게)
- 성공 시 **새 `planId`** 로 `DRAFT` 일정을 만들고 항목을 `visited: false` 로 복제한다.
  준비물·후기는 만들지 않는다. **원본 레코드를 수정하지 않는다** (회귀 방지)
- 원본 동행견이 mock 회원 소유에 없으면 400 `PLAN_010`
