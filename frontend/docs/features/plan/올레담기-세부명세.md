## D0. 화면 정의

- **경로**: `/olle/[walkCourseId]` **안의 시트**다. 새 라우트를 만들지 않는다
- **인증**: **코스 상세는 공개**이고 **담기만 보호 동작**이다. `PROTECTED_PATHS` 를 건드리지 않는다 (D4-1)
- **진입**: 코스 상세 하단의 `일정에 담기` 버튼
- **이탈**: 담기 성공 토스트 · 시트 닫기 · 새 일정 만들기 후 담기

### D0-1. 방향이 둘 중 어느 쪽인가

| 방향                 | 기존 화면                                                        | 이 이슈      |
| -------------------- | ---------------------------------------------------------------- | ------------ |
| 일정 → 대상을 고른다 | `/plans/{planId}/days/{day}/add` (#82 · `use-plan-add-place.ts`) | **아니다**   |
| 대상 → 일정을 고른다 | 장소 상세의 `PlaceAddToPlanSheet` (#118)                         | **이쪽이다** |

**`PlaceAddToPlanSheet` 와 같은 모양을 쓴다.** 1단계 `기존 일정 선택` · 2단계 `새 일정 만들어서 담기` 이고,
2단계는 화면을 옮기지 않고 **같은 시트를 한 단계 밀어 넣는다**(좌상단 뒤로) — 담으려던 맥락을 잃지 않기 위해서다.
그 파일 머리주석이 근거를 갖고 있고, 여기서 다시 정하지 않는다.

**`usePlanAddPlace` 를 재사용하지 않는다.** 그 훅은 `planId` 를 마운트 시점에 고정하는데, 이 시트 안에서는
일정을 바꿀 수 있고 새로 만든 일정의 `planId` 는 제출 뒤에야 나온다
(`place-add-to-plan-sheet.tsx` 의 `PlaceAddToPlanSheet` 머리주석).

## D1. 레이아웃

`PlaceAddToPlanSheet` 와 **같은 `BottomSheet`** 다. 폭·단계 전환·뒤로 버튼 자리를 그대로 쓴다.

| 폭           | 모양                                                                    |
| ------------ | ----------------------------------------------------------------------- |
| 모바일 (390) | 바텀시트. 머리 = 코스 이름표 + 시트 제목 / 본문 = 일정 목록 → 일자 선택 |
| 데스크톱     | 같은 컴포넌트. `BottomSheet` 가 폭을 제한한다                           |

**담기 대상 요약 줄을 시트 머리에 둔다** — `1코스 시흥-광치기 · 15.1km`. 일정 목록을 스크롤하는 동안 **무엇을
담는 중인지** 사라지면, 여러 코스를 보다 들어온 사용자가 다른 코스를 담는다.

### 긴 한국어 실데이터로 확인할 항목

- `15코스 (B) 한림-고내(B)` — 괄호가 둘. 시트 머리 한 줄에서 줄바꿈 처리
- `제주올레여행자센터-월평` — 공백 없는 긴 고유명사
- 일정 제목이 긴 경우 (`엄마랑 몽실이랑 가는 제주 3박 4일 여행`) — 일정 행 말줄임

### D2-1. 시트를 `features/plan` 에 두는 이유

바뀌는 자료가 **일정**이다. `PlaceAddToPlanSheet` 도 장소 상세에서 쓰지만 `features/plan` 에 있고, 실패 분류·
`planKeys` 무효화·일괄 교체 규칙이 전부 그쪽 지식이다. `features/walk-course` 에 두면 plan 의 계약이 두 곳에 흩어진다.

**`appendWalkCourseItemPayload` 를 `lib/walk-course/` 가 아니라 `lib/plan/day-items.ts` 에 둔다.** 같은 파일의
`toPayloadItem`(기존 항목 되싣기)을 **반드시** 써야 하기 때문이다 — 그것을 새로 쓰면 `memo`·`startTime` 보존
규칙(E1 규칙 2)이 두 벌이 되고, 한쪽만 고쳐졌을 때 **순서만 바꿨는데 메모가 지워진다.**

## D3. 계약 — `WALK` 이라서 달라지는 것

```ts
// 보내는 항목 하나. 나머지 규칙은 일자편집-세부명세 E1
{
  day,                       // 경로값 그대로. @Min(1)
  sequence: existing.length, // 맨 끝
  itemType: 'WALK',          // ← 고정
  targetId: walkCourseId,    // ← walk_course.id. **문자열 그대로**
  title,                     // @NotBlank · 100자 이하
}
```

| 항목              | `PLACE` 담기 (#82·#118)                    | **`WALK` 담기 (이 이슈)**                                 |
| ----------------- | ------------------------------------------ | --------------------------------------------------------- |
| `itemType`        | `'PLACE'` 고정                             | **`'WALK'` 고정**                                         |
| `targetId` 의 뜻  | `place.id`                                 | **`walk_course.id` — 다른 표다. 값이 겹쳐도 뜻이 다르다** |
| 저장 시 서버 검증 | tour-service 로 **존재 검증** → `PLAN_004` | **검증하지 않는다** (D3-3)                                |
| 응답의 요약       | `item.place`                               | **`item.walkCourse`** — 서로 다른 필드다                  |
| 화면의 링크       | `/places/{targetId}`                       | **만들지 않는다** (D12 · `일정상세-세부명세.md`)          |

- **`targetId` 를 JSON 숫자로 만들지 않는다.** 서버는 `Long` 으로 읽지만 `walkCourseId` 는 Snowflake 다 —
  실측값 `6911167100216303304` 은 `Number.MAX_SAFE_INTEGER` 밖이다. 문자열 그대로 실어 Jackson 이 읽게 한다
  (E1 규칙 1과 **같은 이유·같은 처리**).
- **`title` 은 무엇을 넣나**: **`courseLabel`** 이다 (`1코스` · `3코스 (A)`). `name`(`시흥-광치기`)만 넣으면
  사용자가 아는 번호가 사라지고, 둘을 이어 붙이면(`1코스 시흥-광치기`) 100자 상한에는 여유가 있지만 일정 항목
  행에서 요약 줄과 중복된다 — **요약이 오면 구간명은 `item.walkCourse.name` 이 말한다**(D12).
  **요약이 안 올 때를 대비해 `title` 하나로 코스를 특정할 수 있어야 한다** → `{courseLabel} {name}` 을 넣고
  `ITEM_TITLE_MAX`(100)로 자른다. 결정 근거는 D8-2.
- **`memo`·`startTime` 을 새 항목에 넣지 않는다.** 담기는 항목을 만드는 자리이고 메모는 사용자가 쓰는 것이다.
  **기존 항목들의 `memo`·`startTime` 은 그대로 되싣는다** (E1 규칙 2).

### D3-1. 새 API 가 없다 — 기존 항목을 전부 되싣고 하나를 더한다

`appendPlaceItemPayload` 와 **같은 모양**이다. 되싣지 않으면 그 일자가 새 항목 하나만 남기고 비워진다.

```ts
export function appendWalkCourseItemPayload(
  items: PlanItemDetail[],
  day: number,
  course: { walkCourseId: string; title: string },
): PlanDayItemsReplacePayload
```

- 기존 항목은 `toPayloadItem(item, day, index)` 로 **그대로** 되싣는다 — 그 안에 이미 담겨 있던 `WALK` 항목도
  `itemType: 'WALK'` + `targetId` 가 보존된다.
- 새 항목은 **맨 끝**이다. 위치를 고르는 UI 를 두지 않는다 — 순서는 편집모드가 소유한다 (F5-3).
- **`appendPlaceItemPayload` 에 `itemType` 인자를 붙여 하나로 합치지 않는다.** 두 함수가 다른 것은 타입 문자열
  하나가 아니라 **중복 판정(`placeIdsOf` vs `walkCourseIdsOf`)과 `title` 조립 규칙**이다. 인자로 합치면 호출부가
  두 축을 맞춰 넘겨야 하고, 잘못 넘긴 조합이 컴파일을 통과한다.
  > **`appendPlaceItemPayload` 의 주석 한 줄이 낡았다.** _"`WALK` 는 이 이슈 밖이다 (F3 — `walk_course` 조회 API 가
  > 없다)"_ — 그 전제는 [#382](https://github.com/8llow8llowMe/hondigagae/issues/382) 로 **더 이상 참이 아니다.**
  > 구현 시 그 문장을 고치고 이 문서를 가리킨다.

### D3-2. 중복은 **다른 네임스페이스**로 센다

```ts
/** 그 일자에 이미 담긴 **산책 코스** id. `placeIdsOf` 의 자매다 */
export function walkCourseIdsOf(items: PlanItemDetail[]): Set<string>
```

- **`placeIdsOf` 를 재사용하면 안 된다.** 그 함수는 `isPlaceTarget` 으로 `WALK` 를 **일부러 걸러낸다**
  (`day-items.ts` 의 `placeIdsOf`, 테스트 `day-items.test.ts` 의
  `it('WALK 의 targetId 는 walk_course.id 라 장소로 세지 않는다')`). 코스를 장소 id 집합으로 재면 **영원히 중복이 잡히지
  않는다.**
- 반대로 **코스 판정에 `placeIdsOf` 의 결과를 섞어도 안 된다.** 우연히 값이 겹치는 장소가 담겨 있으면 담을 수
  있는 코스가 `이미 담았어요` 로 잠긴다 — 버튼이 사라져 우회로가 없다. #82 가 겪은 결함의 **거울상**이다.
- 판정은 `item.itemType.code === 'WALK' && item.targetId !== null` 이다. **`isPlaceTarget` 의 부정이 아니다** —
  `MOVE` 가 그 사이에 있다.
- **서버는 중복을 막지 않는다.** 화면이 먼저 막지 않으면 같은 코스가 두 번 담긴 일정이 조용히 만들어진다.
  다만 **왕복 산책처럼 같은 코스를 하루에 두 번 담는 일정이 실제로 있다**(`PlanQueryProcessor:171` 주석이 그 경우를
  전제로 중복 제거를 한다) → **막지 말고 알리기만 할지**는 D8-3 에 남긴다.

### D3-3. `PLAN_004` 가 `WALK` 에는 오지 않는다 — 틀린 id 가 조용히 저장된다

`verifyPlaceTargets` 는 `command.itemType().isPlaceTarget()` 인 항목만 검증한다
(`PlanCommandProcessor.java:351`). 그리고 **`PLACE_TARGETS` 에 `WALK` 는 없다** (`PlanItemType.java:52`).
tour-service 쪽도 같은 사실을 적어 뒀다 — _"plan-service 의 `WALK` `targetId` 는 저장 시 검증되지 않는다"_
(`WalkCourseQueryProcessor.java:52-60`).

**결과**

| 상황                             | 저장     | 그 뒤                                                 |
| -------------------------------- | -------- | ----------------------------------------------------- |
| 존재하는 `walkCourseId`          | 성공     | 상세에 `item.walkCourse` 요약이 붙는다                |
| **존재하지 않는 `walkCourseId`** | **성공** | **요약이 `null`.** 제목만 남는다 — 오류가 뜨지 않는다 |

**그래서 화면이 id 를 지어내지 않는다.** `targetId` 는 **코스 상세 응답의 `walkCourseId` 를 그대로** 실어야 하고,
문자열 가공(자르기·`Number()` 왕복)을 어디서도 하지 않는다. 틀려도 서버가 막아 주지 않으므로 **테스트가 그
자리를 지킨다** (D7).

## D4. 상호작용

| ----------------------- | ----------------------------------------------- | ------------------------------------------------------- |

| 일정 선택 → 일자 선택   | `PUT /plans/{planId}/days/{day}/items`          | 성공 → 토스트 + 시트 닫기                               |

| 이미 담긴 일자          | 그 일자 옵션이 **`이미 담았어요`** 로 잠긴다    | `walkCourseIdsOf` 로 판정 (D3-2)                        |
| 담기 성공 후            | 하단 버튼 라벨이 `다른 일정에도 담기` 로 바뀐다 | `PlaceAddToPlanSheet` 의 `onAdded` 와 같은 규칙         |

| 저장 실패 4xx           | 시트 안 `FormAlert`, **재시도 없음**            | 문구는 D5                                               |

### D4-1. 코스 상세는 공개인데 담기는 보호 동작이다

`/olle/**` 를 `PROTECTED_PATHS` 에 넣지 않는다 (`walk-course/공통명세.md` S1). 대신 **장소 상세 하단
바와 같은 규칙**을 쓴다 (`screen-inventory.md` §3):

- **미로그인에는 조회조차 보내지 않는다.** 시트가 닫혀 있으면 `GET /plans` 를 부르지 않는다 —
  `PlaceAddToPlanSheet:74` 가 `if (!open) return null` 로 **훅 자체를 마운트하지 않는** 이유가 그것이다.
  `BottomSheet` 의 `open` 만으로 막으면 아래 단계의 훅이 그대로 돌아 **401 이 나가고 전역 재발급이 헛돈다**(실측).
- 버튼은 **보인다.** 누르면 `toLoginHref` 로 `returnTo` 를 달아 보낸다 — 기능의 존재를 숨기지 않는다 (#116 과 같은 판단).

### D4-2. 담은 뒤 어디로 보내지 않는다

토스트에 `일정 보기` 링크를 두되 **자동 이동하지 않는다.** 코스를 여러 개 담는 사용자가 매번 목록으로 튕기면
다시 들어와야 한다. 문구는 D5.

## D6. 접근성

- 시트는 기존 `BottomSheet` 의 포커스 트랩·`aria-modal`·ESC 를 그대로 쓴다.
- 대상 요약 줄은 시트의 접근 이름에 포함한다 — `1코스 시흥-광치기 일정에 담기`.
- 비활성 일자 옵션은 `disabled` + **보조 문구(`이미 담았어요`)** 로 이중 전달한다. 색·흐림만으로 알리지 않는다.
- 담기 결과 토스트는 `aria-live="polite"`. 기존 `useToast` 가 갖고 있다.
- 하단 `일정에 담기` 버튼 터치 영역 44px.
