# 콘텐츠 최대폭 — 1440 컨테이너 설계

> 대상: `.rail-layout` 을 쓰는 6개 화면 + `GlobalHeader`
> 이슈: #376
> 작성: 2026-09-09
> 상태: 설계 확정 · 계획 `docs/superpowers/plans/2026-09-09-content-max-width.md` — 구현 진행 상황은 [#376](https://github.com/8llow8llowMe/hondigagae/issues/376)

**Goal:** 넓은 화면에서 **화면마다 다른 폭 규칙**을 하나로 모은다. 레일 레이아웃과 헤더
안쪽 내용을 `--content-max: 1440px` 로 캡하고 중앙 정렬한다.

**Non-goal:** 512 / 672 / 768 캡 화면의 폭 변경. 지도 화면의 전폭 해제. #370 의 담기 지도 (머지되면 자동으로 전폭이다). 레일 폭(400/280)
재설계. 헤더 높이·sticky·border 계약 변경. 새 컴포넌트.

---

## 1. 진단

### 1-1. 폭 갈래가 넷이다

| 폭 | 화면 |
| --- | --- |
| `max-w-lg` 512 | 반려견 등록 · 수정 |
| `max-w-2xl` 672 | 일정 생성 |
| `max-w-screen-md` 768 | 마이페이지(3) · 응급 · 즐겨찾기 · AI일정(2) · 반려견 목록 · 일정 응급 |
| 무제한 (`.rail-layout`) | 홈 · 장소찾기 목록 · 장소상세 · 일정 목록 · 일정상세 · 담기 목록 |
| 전폭 | 장소찾기 지도 |

1920 에서 마이페이지는 정중앙 768 컬럼이고, 홈은 왼쪽 끝에 붙은 레일 + 1440px 우측 본문이다.
**두 화면이 같은 제품으로 보이지 않는다.**

### 1-2. 무제한으로 자라는 것은 우측 열 하나뿐이다

`.rail-layout` 은 `grid-template-columns: var(--rail-context) minmax(0, 1fr)` 이고 레일은
고정이다. 뷰포트가 커지면 **우측 열만** 자란다. 1920 에서 우측 본문은 1440px 이고,
목록은 카드가 아니라 전폭 행이라(`DESIGN.md` §0) 행 하나가 그 폭을 그대로 쓴다.

### 1-3. 전폭은 이미 "가입하지 않음"으로 구현돼 있다

지도 화면은 `.rail-layout` 을 붙이지 않고 `<main id="main-content">` 만 낸다.
예외 처리가 아니라 **그 규칙에 가입하지 않는 방식**이다.

- `app/(main)/places/(list)/page.tsx` — `view === 'map'` 분기

**develop 기준으로 지도 화면은 이 하나다.** 담기 지도(`plans/[planId]/days/[day]/add`)는
#370 에서 오는 미머지 작업이고, 그쪽 분기도 같은 모양(`.rail-layout` 없는 bare `<main>`)이라
머지되면 **아무 작업 없이 전폭을 물려받는다.**

이 구조가 캡을 어디에 걸지를 결정한다 (§3).

---

## 2. 폭 값 — 1440

레일 400 은 고정이므로 캡이 깎는 것은 전부 우측이다.

| 컨테이너 | 우측 열 | 인셋(`px-10` ×2) 뺀 본문 |
| --- | --- | --- |
| 1280 | 880 | **800** |
| **1440** | 1040 | **960** |
| 1584 (레일 480 유지 시) | 1104 | 1024 |
| (오늘) 1440 뷰포트 | 1040 | 960 |

**1440 은 1440 노트북에서 오늘과 픽셀이 같다.** 그 아래는 무변화, 그 위에서만 멈춘다.

1280 을 쓰지 않는 이유:

| # | 이유 |
| --- | --- |
| 1 | **1440 노트북에서 본문이 960 → 800 으로 오늘보다 좁아진다.** 지도·목록이 본체인 제품에서 본체를 깎는 방향이다 |
| 2 | 참조한 당근알바의 1280 은 **4열 카드 그리드**에서 나온 값이다(280×4 + gap). 우리는 레일 + 전폭 행이라 최적폭 계산식이 다르다 |

## 3. 기각 — 캡을 `(main)/layout.tsx` 의 `#main` 래퍼에 거는 안

한 줄로 전 화면에 적용되지만 **지도 두 개가 부모 `max-width` 를 뚫고 나와야 한다.**
negative margin + `100vw` 계열이 필요하고, 스크롤바 폭 때문에 §7 의
_"375 에서 가로 스크롤이 생기면 버그다"_ 를 건드릴 위험이 있다.

전폭을 얻기 쉬운 구조(§1-3)를 어렵게 바꾸는 방향이라 채택하지 않는다.
`.app-container` 유틸을 만들어 화면마다 붙이는 안도 같은 이유로 기각한다 — 파일 20개+ 를
고치고 새 화면마다 부착을 잊을 수 있다.

## 4. 설계

### 4-1. 토큰 — `src/styles/tokens.css`

```css
--content-max: 1440px;   /* 신규 */
--rail-context: 400px;   /* 유지 */
```

`@media (width >= 99rem)` 의 `--rail-context: 480px` **블록을 삭제한다.**
컨테이너가 1440 에서 멈추므로 1584 에서 레일만 넓히는 규칙은 **발동할 수 없다.**
남겨두면 죽은 코드다.

### 4-2. 레이아웃 — `app/globals.css`

**Tailwind arbitrary 를 쓰지 않는다.** `max-w-[var(--content-max)]` 는 대괄호 안에 함수
호출이 있어 eslint `noComplexArbitrary` 에 걸린다(`eslint.config.mjs`). 그 규칙의 안내대로
`globals.css` 에 **이름 있는 클래스**로 둔다.

캡이 필요한 곳이 레일 레이아웃과 헤더 안쪽 둘이므로 한 규칙에 두 셀렉터로 적는다 —
값이 두 군데로 갈라지면 헤더와 본문의 좌우 경계가 어긋난다.

```css
/* 최상위. @media 밖 */
.content-container,
.rail-layout {
  max-inline-size: var(--content-max);
  margin-inline: auto;
}
```

- `.rail-layout` 의 grid 선언은 지금처럼 `@media (width >= 64rem)` 안에 남는다. 캡만 밖으로
  나온다 — 1440 미만에서는 `max-inline-size` 가 걸리지 않고 `margin-inline: auto` 도
  폭이 `auto` 인 블록에서 무효라 **모바일·태블릿은 무변화**다.
- `.rail-layout-filter` · `.rail-layout-detail` 은 `grid-template-columns` 만 덮으므로
  캡을 자동으로 상속한다.

### 4-3. 헤더 — `src/features/nav/global-header.tsx`

바(`<header>`)는 전폭을 유지하고 **안쪽 div 에만** `content-container` 를 붙인다.
`px-4 md:px-10` 은 그대로 둔다.

sticky · `border-b` · `--header-h`(56/64) 계약은 그대로다. 바를 캡하면 구분선이 화면
가운데서 끊긴다 — 참조한 당근알바도 바는 전폭이고 안쪽만 캡이다.

주석의 _"`max-width` 를 두지 않는다 — 헤더는 화면 폭을 쓴다"_ 는 바를 가리키는 문장이므로
**안쪽/바깥쪽을 구분하는 문장으로 고쳐 쓴다.** 지우지 않는다 — 바를 캡하지 않는 이유가
그 자리에 남아야 한다.

### 4-4. 손대지 않는 것

| 대상 | 이유 |
| --- | --- |
| 512 / 672 / 768 화면 | 폼과 읽기 measure 는 그 폭이 맞다. 1440 보다 항상 작아 무영향 |
| 응급 지도 (`emergency-map`) | 768 안에 박힌 **컴포넌트**지 지도 화면이 아니다 |
| `INSET_BLEED_*` | margin 기반이라 뷰포트가 아니라 컨테이너 기준으로 접힌다 |
| `.scroll-rail` | `contain: layout` 이라 캡과 무관하다 |

### 4-5. 문서 — `DESIGN.md`

- §7 표의 `max`(1584~) 행을 **컨테이너 규칙**으로 교체
- 레이아웃 토큰 표에 `--content-max: 1440px` 추가, `--rail-context` 를 `400` 고정으로
- §7-1 의 _"1584+ 에서 맥락 패널만 480 으로 넓어지는 것과 달리"_ 서술 정정
- `app/globals.css` 의 `.rail-layout` · `.rail-layout-filter` 머리 주석에 있는
  "1584+ 에서 480" 서술도 함께 정정 (줄 번호는 이 변경으로 밀린다)

---

## 5. 알려진 어긋남 (범위 밖)

헤더 콘텐츠는 왼쪽에서 40(`px-10`), 레일 콘텐츠는 24(`lg:px-6`)라 **16px 어긋난다.**
오늘도 같은 값이지만, 화면 끝이 아니라 컨테이너 경계에 서게 되면 더 눈에 띌 수 있다.
이번 범위 밖으로 두고 §6 실측에서 거슬리면 **별도 이슈**로 올린다.

## 6. 검증

| 항목 | 방법 |
| --- | --- |
| lint · typecheck · test | `pnpm verify` — `noComplexArbitrary` 위반이 없어야 한다 (§4-2) |
| 1440 에서 오늘과 동일 | 변경 전후 스크린샷 대조 |
| 1920 중앙 정렬 | 홈 · 장소찾기 목록 · 일정 상세 |
| 지도 화면 전폭 | `/places?view=map` (develop 의 유일한 지도 화면) |
| 375 가로 스크롤 0 | `document.scrollingElement.scrollWidth === clientWidth` |
| 브레이크포인트 | 1920 / 1440 / 1280 / 1024 / 768 / 375 |

dev 서버는 `pnpm dev:alt`(**5174**)로 띄운다 — 3000 은 카카오 지도 키 도메인이 등록돼 있지
않아 지도가 항상 폴백으로 뜬다.

색 토큰만 `token-sync.test.ts` 대상이라 **§7 표는 기계 검증이 없다.** 수동 대조로 처리한다.
