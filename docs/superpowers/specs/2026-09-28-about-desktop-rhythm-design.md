**Goal:** 1024 이상에서 `/about` 의 스크롤 흐름이 **처음 보는 화면마다 완성돼 보이고**, 끝(데이터 절 · 마무리)까지 **덜 지루하게 닿게** 한다.

**Non-goal:** 1024 미만 레이아웃(실측상 문제 없음). 문구 · 절 구성 · 캐릭터. 무대 구조(sticky 틀 · 기준선 · 맥락 줄). 질문 3 트랙(35vh). 새 색 · 그림자 · duration 토큰.

---

## 1. 진단

2026-09-28 에 헤드리스 Chromium(Playwright)으로 1440×900 · 1280×800 · 1024×768 · 768×1024 · 375×812 를 천천히 스크롤하며 캡처하고 좌표를 쟀다. 브라우저 패널은 숨겨져 rAF 가 멈춰 있어 계측에 쓰지 않았다.

**1024 미만은 좋다.** 375(5,813px · 화면 7.2개) · 768(6,098px · 6.0개) 모두 질문 → 항목 → 예시가 한 흐름으로 읽히고 가로 스크롤이 0 이다. 아래 넷은 전부 1024 이상의 문제다.

| # | 증상 | 실측 | 원인 |
| --- | --- | --- | --- |
| D1 | 질문 1 · 위급에 들어서면 예시 카드가 **로딩 중처럼** 보인다 | 1440×900 에서 절 제목이 보이는 동안 카드 윗부분 약 60px 이 비고 행 셋이 흐리다 | 단계 0. `globals.css` 가 `:not(.is-step-1)` 에서 칩을 `visibility: hidden` 으로, 행을 `opacity: .35` 로 둔다. 단계 1 은 첫 항목 **중심**이 기준선(헤더 아래 화면 가운데)을 지나야 켜지는데, 그 전까지 제목 · 카드가 이미 화면에 있다 |
| D2 | 페이지가 길다 | 1440×900 11,022px(12.2개) · 1024×768 9,638px(12.5개) — **모바일의 1.7배**. 절 제목 → 첫 항목 문장 287px | 무대 항목 열 개가 한 칸 58vh. 문장은 칸 가운데에 서므로 제목 아래 반 칸(29vh)이 빈다 |
| D3 | 질문 4 뒤, 데이터 절 앞에 빈 띠가 크다 | 카드 아래 → 다음 절 표지어: 질문 1→2 **331** · 질문 2→3 **349** · 질문 4→데이터 **435** (1440). 1024: 265 · 217 · **326** | 데이터 절만 `.about-screen-fill`(헤더 아래 한 화면 · `justify-content: center`)이라 내용이 가운데로 내려간다. 절 윗변 → 표지어가 다른 절 64 · 데이터 **158** |
| D4 | 지금 어디쯤인지 알 수 없는 폭이 있다 | 1024–1279: 절 내비 **없음** · 진행선 **없음**. 1280–1535: 절 내비가 **라벨 없는 점 여섯** | 진행선은 `lg:hidden`(1024 미만만), 절 내비는 1280 부터, 라벨은 1536 부터 보인다 |

> 1024×768 은 가로 태블릿 · 작은 노트북 폭이다. 1024–1279 는 D2 가 가장 긴 폭(12.5화면)인데, 위치 표시가 하나도 없다.

## 2. 결정

| # | 결정 | 기대 효과 (1440×900) |
| --- | --- | --- |
| S1 | **단계 1 을 앞당긴다.** 첫 항목 **윗변**이 화면 바닥 위 20% 선(진입선)을 넘으면 단계는 최소 1 이다. 2 단계부터는 지금처럼 중심 · 기준선 | 무대가 화면에 들어올 때 카드가 처음부터 채워진 모양이다. 칩이 드러나는 전환은 카드가 화면 아래에서 올라오는 순간에 재생된다 |
| S2 | **칸을 58vh → 44vh 로 줄인다.** 꼬리 여백은 같은 식으로 `calc(50dvh − 22vh − 헤더/2)` | 문서 −1,260px(칸 10개 × 14vh) · 제목 → 첫 문장 287 → 약 224 |
| S3 | **데이터 절의 한 화면 채움을 푼다.** `.about-screen-fill` 을 데이터 절에서 뗀다(클래스와 CSS 규칙도 지운다 — 쓰는 곳이 데이터 절 하나다) | 질문 4 → 데이터 띠 435 → 약 341(다른 전환 331 · 349 와 같은 폭). 문서 추가 −약 90px |
| S4 | **진행선을 1280 미만까지 보인다.** `lg:hidden` → `xl:hidden` — 절 내비가 서는 폭에서 바통을 넘긴다 | 1024–1279 에 위치 표시가 생긴다 |
| S5 | **1280–1535 절 내비 점에 이름을 띄운다.** 가리키거나(hover) 키보드 초점(`focus-visible`)이 오면 점 오른쪽에 라벨 칩 | 점만 보고 절을 고르지 않아도 된다 |

S2 · S3 합산: 1440×900 11,022 → **약 9,670px(10.7화면)**, 1024×768 9,638 → **약 8,470px(11.0화면)**. 실측으로 확인한다(§5).

### 2-1. S1 — 단계 1 앞당기기

- **식.** `stepAt` 은 그대로 두고, 진입 조건을 더하는 순수 함수를 하나 둔다.

  ```ts
  /** 첫 항목 윗변이 진입선을 넘었으면 최소 1 — 단계 0 은 무대가 아직 화면 아래일 때만이다 */
  export function stageStep(
    centers: readonly (number | null)[],
    firstTop: number | null,
    line: number,
    entryLine: number,
  ): number
  ```

  `entryLine = innerHeight × 0.8`. `firstTop` 이 `null`(첫 항목이 등록 안 됨)이면 `stepAt` 과 같다.
- **왜 윗변 · 80% 인가.** 첫 항목 윗변이 진입선에 오면 카드 윗변은 1440×900 에서 848–875 · 1024×768 에서 677–703 이다(질문 1 · 2 · 4 실측) — 카드가 화면 바닥으로 막 들어오는 때다. 칩이 드러나는 전환(200)이 **보이는 자리에서** 한 번 재생되고, 카드가 흐린 채로 화면 가운데까지 올라오는 일은 없다. 더 일찍(100%) 켜면 전환이 화면 밖에서 끝나고, 더 늦게(60%) 켜면 D1 이 되살아난다.
- **되감기.** 뒤로 스크롤해 윗변이 진입선 아래로 내려가면 0 으로 돌아간다 — 무대는 스크롤 위치의 함수라는 선행 명세 §3-4 규칙 그대로다. 그때 카드는 이미 화면 바닥 근처라 흐린 모양이 눈에 머물지 않는다.
- **번호 칸 · 문장 흐림.** 단계 1 이 켜진 순간 항목 1 의 문장은 기준선보다 아래에 있다. 항목 1 을 켜진 모양(채움 · 본문색)으로 두는 것이 맞다 — 절에 들어온 사람이 읽을 첫 문장이다.
- **1024 미만.** 같은 식을 쓴다. 쌓기 흐름에서는 카드가 항목 아래라 카드가 보일 때는 이미 단계 1 이상이다 — 보이는 변화가 없다.
- **감속 모션.** 그대로 재지 않고 마지막 단계에 고정한다.
- **질문 2.** 단계 0 에서 곡선 카드가 무엇을 숨기는지와 무관하게 같은 식이 적용된다. 캐릭터 첫 자세(목줄 산책)는 단계 0 · 1 이 같아 바뀌지 않는다.

### 2-2. S2 — 칸 44vh

- `.about-stage-point { min-block-size: 44vh }`, 꼬리 `calc(50dvh − 22vh − var(--header-h) / 2)`. **칸과 꼬리는 짝이다** — 꼬리의 `22vh` 는 칸의 절반이다. 둘 중 하나만 바꾸면 "마지막 항목이 켜지는 순간 무대 끝이 화면 바닥" 이 깨진다.
- **꼬리는 모든 창 높이에서 양수다.** 900 에서 450 − 198 − 32 = 220 · 700 에서 350 − 154 − 32 = 164.
- **항목 문장이 칸 안에 든다.** `lg:text-title-2` 세 줄이 가장 긴 항목이고, 44vh 는 768 에서 338px 이다.
- **왜 44 인가.** 한 단계가 휠 서너 칸(1440×900 에서 396px)이다. 58vh(522px)는 단계 사이 카드가 멈춰 있는 시간이 길어 지루했고, 그렇다고 칸이 너무 작으면 단계가 한 번의 휠에 두 개씩 지나간다. **44vh 가 급하게 느껴지면 50vh 로 올린다**(문서 −720px) — 구현 뒤 실제 화면에서 사용자와 함께 정한다(§6).
- 질문 3 트랙(`--about-tour-step: 35vh`)은 건드리지 않는다. 무대와 방식이 달라(한 화면에 붙인 채 목록을 넘긴다) 칸 크기가 다른 뜻을 갖는다.

### 2-3. S3 — 데이터 절 한 화면 채움 풀기

- 선행 명세 §3-5 2차 검토가 **"1280×800 기준 한 화면"** 으로 정한 것을 뒤집는다. 근거: 내용이 가운데로 내려가며 앞 절 무대 끝과 겹쳐 **이 절 앞에만** 약 90px 이 더 빈다(D3). 한 화면을 채워서 얻던 것은 "절 내비로 `데이터` 에 가면 화면 전체가 데이터" 인데, 채움을 풀면 그 자리 아래로 **마무리 CTA 가 비친다** — 그것이 다음 할 일이라 손해가 아니다.
- 안쪽 7 : 5 두 열의 `lg:items-center` 는 둔다 — 열끼리의 정렬이지 절 높이의 문제가 아니다.
- **안 한 안.** 채움은 두고 내용만 위로 붙이는 것(`justify-content: start`). 빈 공간이 절 아래 · 마무리 밴드 앞으로 옮겨 갈 뿐이다(1440×900 에서 약 250px).

### 2-4. S4 — 진행선 1280 미만까지

- `ScrollProgressBar` 의 `lg:hidden` → `xl:hidden`. 자리 · 모양은 그대로다(헤더 아래 2px, `aria-hidden` 장식).
- 1280 이상은 절 내비가 지금 절을 알려 주므로 진행선을 두지 않는다 — **두 표시가 한 화면에 동시에 서지 않는다.**

### 2-5. S5 — 절 내비 라벨 띄우기 (1280–1535)

- 지금 라벨 `span` 은 `sr-only 2xl:not-sr-only` 다. **같은 `span` 하나를 쓴다** — 보이는 칩을 따로 복제하면 스크린리더가 이름을 두 번 읽는다.
- 1280–1535 에서 그 `span` 을 점 오른쪽에 `absolute` 로 두고, 평소에는 보이지 않게(`opacity: 0`, 접근 가능한 이름은 남는다), 링크가 `:hover` · `:focus-visible` 이면 드러낸다. 1536 이상은 지금처럼 늘 보인다.
- 모양: 기존 표면 토큰 — `bg-bg` · `border-border` · `rounded-md` · `text-caption` · 600. 그림자 없음. 전환은 기존 150.
- 층: 절 내비 자신의 쌓임 맥락 안에서 뜬다. 절 내비가 본문 위에 서 있으므로 새 z 값이 필요 없다 — 필요해지면 DESIGN.md z 스케일 5단 안에서 고른다(`z-40` · 흐름 내 컨트롤에 붙은 팝오버).
- **라벨은 본문 왼쪽 끝(1280 에서 104px)을 넘어 본문 위로 잠깐 겹친다.** 가리키는 동안만이라 받아들인다.

## 3. 접근성

- S1 · S2 는 보이는 모양의 타이밍만 바꾼다. 정적 렌더 · JS 실패 · 감속 모션은 지금처럼 **마지막 단계(전부 보임)** 다.
- 단계 0 의 칩은 지금처럼 누를 수도 초점을 받을 수도 없다(#916 검토) — S1 은 단계 0 이 **보이는 시간**만 줄인다.
- S5 의 라벨은 이미 링크의 이름이다. 보이게 할 뿐 이름은 바뀌지 않는다. 키보드 사용자도 `focus-visible` 로 같은 칩을 본다.

## 6. 후속 · 미결

- **칸 44 ↔ 50vh** — 구현 뒤 1440×900 · 1024×768 실제 화면을 보고 사용자와 정한다. 50 으로 가면 §2 기대 효과와 §5 목표 높이를 다시 적는다.
- 1024–1279 에 절 내비를 두는 안은 보류다. 1024 에서 본문 왼쪽 여백이 40px 이라 점 레일(44)이 본문과 겹친다. 진행선(S4)으로 먼저 보고, 부족하면 따로 연다.
