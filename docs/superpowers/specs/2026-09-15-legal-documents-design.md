# 이용약관·개인정보 처리방침 설계

> 작성일 2026-09-15 · 대상 워크스페이스 `frontend/`

## 0. 이 문서의 한계

**여기 실린 약관·처리방침 초안은 법률 자문이 아니다.** 개인정보보호위원회 표준
처리방침 양식과 이 저장소에서 실측한 데이터 흐름에 맞춰 작성하지만, 실이용자를
받는 서비스라면 **공개 전에 사람이 검토해야 한다.** 이 단계를 S8-1 배포 게이트에
항목으로 남긴다.

## 1. 배경

서비스가 `www.hondigagae.com` 에 공개되고 **불특정 이용자가 실제로 가입한다**는
전제다. 개인정보 보호법이 전면 적용된다.

코드에는 이미 "대상 문서가 없어서 미룬다"는 지연 표식이 세 군데 박혀 있다.

| 위치 | 현재 상태 |
| --- | --- |
| `frontend/src/lib/messages/footer.ts:13` | "없는 링크를 만들지 않는다" — 푸터에 링크 없음 |
| `frontend/src/features/member/account-section.tsx:41` | 마이페이지에 약관 링크 미렌더 |
| `frontend/docs/features/auth/회원가입-세부명세.md:187` | 동의 체크박스 미도입 — "요청 DTO 에 자리가 없다" |

앞의 둘은 이 작업이 해소한다. 셋째는 백엔드 선행이 필요해 **범위 밖**이다 (S9).

## 2. 범위

### 하는 것

- 이용약관·개인정보 처리방침 **본문 정본**을 구조화 상수로 작성
- `/terms` · `/privacy` 정적 라우트
- 푸터·마이페이지 **진입점 연결**
- 문서 버전·시행일·개정 이력 관리 구조
- 법정 기재사항 누락을 잡는 자동 검증

### 하지 않는 것

- 회원가입 동의 체크박스 (백엔드 DTO 에 필드 없음 — S9-B)
- 만 14세 미만 가입 차단 (연령 정보를 받지 않음 — S9-C)
- 탈퇴 회원 식별자 보관 방식 변경 (백엔드 구현 — S9-D)

### 성공 기준

1. 로그아웃 상태에서 `/terms` · `/privacy` 가 열린다
2. 처리방침이 보호법 제30조 **표준 양식 12개 절**을 모두 담는다
3. 본문의 사실 기술이 **코드 실측과 일치**한다 (수집 항목·위탁·국외 이전)
4. 푸터·마이페이지에서 두 문서에 도달한다
5. `pnpm verify` 통과

### 판단 셋

**반려견 정보를 회원 정보와 같은 급으로 다룬다.** 견종·건강 성향 자체는 개인정보가
아니지만 회원 계정에 묶이는 순간 "식별된 개인에 관한 정보"가 된다. 이 서비스의
정체성이 거기 있으므로 처리방침에서 축소하지 않는다.

**위치정보는 "저장하지 않는다"를 명시한다.** 코드가 실제로 그렇다 — 좌표는 조회
파라미터로만 흐르고 DB 에 남지 않는다. 사실이므로 쓸 수 있고, 쓰면 위치정보법상
개인위치정보 보유 논점을 상당 부분 비껴간다. **이 사실이 바뀌면 문서도 바뀌어야
한다** — 좌표를 저장하는 기능이 생기면 이 절을 먼저 고친다.

**국외 이전은 Gmail SMTP 하나뿐이다.** 인증코드 발송용이며 수탁자는 Google LLC 다.
그 외 MySQL·Redis·MinIO 는 자체 인프라이고, **AI 언어모델도 Ollama 자체 호스팅**이라
이용자 입력이 외부 AI 사업자로 나가지 않는다. 처리방침에 이 문장을 명시적으로 넣는다:

> AI 제안 생성에 사용하는 언어모델은 자체 인프라에서 구동되며, 이용자가 입력한
> 정보는 외부 AI 사업자에게 전송되지 않습니다.

제3자 제공은 **없다.** 다만 카카오맵 SDK 는 이용자 브라우저가 카카오에 직접 요청하므로
IP 등이 전달된다는 사실을 고지한다 — 우리가 제공하는 것은 아니지만 숨길 것도 아니다.

### 5-1. 타입

```ts
type Block =
  | { kind: 'text'; text: string }
  | { kind: 'list'; items: readonly string[] }
  | { kind: 'table'; headers: readonly string[]; rows: readonly (readonly string[])[] }

type Article = {
  /** 조 번호. 1부터 연속이어야 한다 (테스트가 감시한다) */
  no: number
  title: string
  blocks: readonly Block[]
}

type Revision = { version: string; effectiveDate: string; summary: string }

type LegalDocument = {
  id: 'terms' | 'privacy'
  title: string
  version: string
  /** YYYY-MM-DD */
  effectiveDate: string
  articles: readonly Article[]
  /** 최신이 앞. 최초 제정도 한 줄로 남긴다 */
  history: readonly Revision[]
}
```

`table` 블록이 있어야 처리방침의 수집항목 표·보유기간 표가 들어간다. 마크다운
파서를 썼다면 이 표에 스타일을 따로 먹여야 했을 자리다.

### 5-2. 문구 배치 — 본문과 화면 문구를 가른다

**이 저장소는 화면 문구를 해요체로 고정하고 테스트로 감시한다.**
`src/lib/messages/message-tone.test.ts` 가 `src/lib/messages/` **디렉터리의 `.ts`
파일만** 훑으며 `~습니다` · `~입니다` 를 잡는다.

그런데 **약관 본문은 해요체가 아니다.** 법률문서는 합니다체다. 그래서 가른다.

| | 위치 | 어미 | 톤 테스트 |
| --- | --- | --- | --- |
| 약관·처리방침 **본문** | `src/lib/legal/*` | 합니다체 | 대상 밖 |
| 페이지 **화면 문구** (제목·"시행일"·목차 레이블) | `src/lib/messages/legal.ts` | 해요체 | 대상 |

이 분리를 안 하면 톤 테스트가 약관 전문에 걸린다. 반대로 `legal.ts` 에 본문을
흘려 넣어도 걸린다 — 경계가 테스트로 강제된다.

### 5-3. 렌더러

`LegalDocumentView` 는 서버 컴포넌트다. 상태도 세션 분기도 없다.

- 목차: `articles` 순회 → `#article-N` 앵커 링크
- 조문: `<h2 id="article-N">제N조(제목)</h2>` + 블록별 렌더
- 개정 이력: 문서 하단 `<dl>`. 조작할 수 없는 정보라 목록 항목이 아니다
  (`account-section.tsx` 의 버전 표기와 같은 판단)
- 레이아웃: `content-container` + `INSET_CLASS.main` — 기존 본문 열 규약을 따른다

## 7. 개정 관리

`version` + `effectiveDate` + `history` 를 문서 구조체가 직접 든다.

- 페이지 상단에 시행일, 하단에 개정 이력을 렌더한다
- 개정할 때 `history` 에 한 줄 추가하는 것이 규약이고, git diff 가 개정 기록이다
- 약관 제3조의 사전 공지 기간(불리한 변경 30일 / 그 외 7일)을 지키려면 **시행일을
  미래로 둔 채 먼저 배포**할 수 있어야 한다. 구조가 이를 허용한다

### 8-1. 배포 게이트 (코드로 잡을 수 없는 것)

`/terms` · `/privacy` 를 공개하기 **전에** 사람이 확인한다.

- [ ] 개인정보 보호책임자 **실명**과 연락처가 확정되어 들어갔는가
      (연락처는 개인 메일이 아니라 **서비스 도메인 주소**를 쓴다. 공개 페이지라
      크롤러가 그대로 수집한다. 전화번호는 넣지 않는다 — 법정 기재사항은 "연락처"
      이지 전화번호가 아니다)
- [ ] 시행일이 실제 공개일 이후인가
- [ ] S9-D 확인 결과가 "파기" 절에 반영되었는가
- [ ] 사람이 전문을 한 번 읽었는가 (S0)

## 9. 범위 밖 — 백엔드 이슈로 발의

실운영 전제에서 FE 만으로는 닫히지 않는 구멍이 셋이다. 이슈만 올리고 구현은
백엔드 담당이다.

| # | 사안 | 근거 |
| --- | --- | --- |
| B | **회원가입 동의 획득·이력 저장** | 보호법 제15조·제22조. `SignupRequest` 에 동의 필드 + 동의 시각 + **동의한 문서 버전**을 남겨야 한다. 없으면 "처리방침은 있는데 동의는 안 받는" 상태다 — 스스로 공표한 기준을 안 지키는 셈이라 문서가 없는 것보다 불리하다 |
| C | **만 14세 미만 가입 차단** | 현재 연령 정보를 **아예 받지 않는다**. 제22조의2 상 만 14세 미만은 법정대리인 동의가 필요한데, 확인 수단이 없으면 약관에 "만 14세 이상"을 쓰고도 지킬 방법이 없다 |
| D | **탈퇴 회원 식별자 보관 방식** | `src/lib/api/mock/member-data.ts:306` 이 "마스킹 + 같은 이메일 재가입 불가"로 적고 있다. 재가입 차단을 위해 **원문 이메일을 남기고 있다면 목적 외 보관**이다 — 단방향 해시여야 한다. 실제 백엔드 구현 확인이 선행된다 |

**D 는 이 작업의 "파기" 절과 직결된다.** 실제 동작을 확인하기 전에는 그 절을
확정해서 쓸 수 없다 — 문서가 거짓이 되면 안 된다. 확인 전까지 보수적으로 적고,
확인 후 조정한다.

## 10. 작업 순서

```text
이슈 A [FE] 이용약관·개인정보 처리방침 문서와 페이지   ← 이 명세의 대상
이슈 B [BE] 회원가입 동의 획득·이력 저장               ← 발의만
이슈 C [BE] 만 14세 미만 가입 차단 수단                ← 발의만
이슈 D [BE] 탈퇴 회원 식별자 보관 방식 점검            ← 발의만 (A 의 파기 절에 영향)
```

브랜치 `feature/fe/<A번호>-legal-documents`. 파일 약 12개로 PR 30파일 기준 안쪽이다.
