# Development Orchestrator

메인 실행자가 작업 유형과 복잡도를 정한 뒤, 필요한 역할만 실행한다. 모델 ID와 모드 선택은 호스트 어댑터에 있다. 이 파일에는 공통 절차만 둔다.

작업을 시작하기 전에 현재 호스트의 어댑터를 읽는다.

- Codex — [adapters/codex.md](adapters/codex.md). 역할 파일은 `.codex/agents/*.toml`, 운영 정본은 [docs/codex-agents.md](../../../docs/codex-agents.md)
- Cursor — [adapters/cursor.md](adapters/cursor.md). 전용 역할 파일은 없다
- Claude Code — [docs/claude-agents.md](../../../docs/claude-agents.md). 역할 파일은 `.claude/agents/*.md`

호스트를 구분할 수 없으면 메인 실행자가 같은 역할을 순서대로 수행하고, 다른 호스트의 모델 ID를 복사하지 않는다.

## 절차

매 작업은 아래 순서로 진행한다. 유형과 복잡도에 따라 건너뛰는 단계는 각 절에 적는다. 역할을 부르기 전에 `TYPE`과 `COMPLEXITY`를 명시한다.

### 1. CLASSIFY

| 유형 | 대상 |
|------|------|
| `SIMPLE` | 위치와 계약이 분명한 CRUD, DTO, 매핑, 단순 검증·설정, 작은 테스트, 문구 |
| `FEATURE` | 일반적인 단일 서비스·화면 기능 |
| `BUG` | 원인 분석이 필요한 버그. 재현·상태·트랜잭션·동시성이 얽히면 여기에 둔다 |
| `REFACTOR` | 동작을 보존하면서 구조를 바꾸는 변경 |
| `ARCHITECTURE` | MSA·보안·트랜잭션·메시징·동시성·대형 교차 모듈 설계 |
| `LARGE_FEATURE` | 발견 역할이 둘 이상 필요하고 백엔드·프론트 멀티 에이전트 스킬이 같이 쓰이는 작업 |

명확하고 국소적인 버그는 `BUG`로 두되 조사 역할을 둘 다 부르지 않는다. 설계 판단이 없으면 `ARCHITECTURE`로 올리지 않는다.

### 2. COMPLEXITY

| 등급 | 의미 | 기본 깊이 |
|------|------|-----------|
| `T0` | 위치·계약·검증이 이미 확정된 국소 변경 | 가장 싼 역할. 탐색·설계·별도 검토를 생략할 수 있다 |
| `T1` | 한 모듈 안의 일반 구현·수정 | 역할의 기본 강도 |
| `T2` | 여러 계층, 공개 API, 쿼리·인덱스, 경계 검토가 함께 있는 작업 | 분석·검토 역할을 한 단계 올린다 |
| `T3` | 실수 비용이 큰 작업 | 해당 역할의 최상위 승격 칸. 아래 신호로만 판정한다 |

`T3`는 아래 신호 중 **2개 이상**이 작업 범위에 실제로 있을 때다. 하나뿐이면 `T2`다.

- 인증·인가
- 개인정보
- 결제
- 재고·예약처럼 선점과 만료가 있는 상태
- 분산락
- 멱등성
- RabbitMQ·Kafka 재처리
- 멀티 인스턴스 race
- DB 스키마 변경
- 대규모 마이그레이션
- API 하위 호환
- Gateway·Auth 공통 변경
- 장애 원인 미상

xHigh(Codex)와 별도 Plan·보안 검토(Cursor)는 `T3` 칸에서만 쓴다. 탐색 역할은 어떤 등급에서도 최상위 추론으로 올리지 않는다. 빠르게 파일을 찾고 호출 관계를 추적하는 일이기 때문이다.

### 3. EXPLORE

- `T0`이거나 수정 위치가 이미 특정되면 생략한다.
- 위치나 호출 흐름이 불명확할 때만 탐색 역할을 실행한다.
- `BUG`에서 독립적인 증거 수집이 유효하면 탐색과 원인 분석을 함께 실행할 수 있다. 둘 다 읽기 전용일 때만 병렬이다.

### 4. PLAN

- `T0`·`T1`은 메인 실행자가 범위와 순서를 짧게 고정하고 별도 설계 역할을 부르지 않는다.
- `T2` 이상은 구현 전에 범위, 보존할 동작, 검증 방법을 고정한다.
- `ARCHITECTURE`와 `T3`는 설계 또는 원인 분석 결과가 저장소 증거와 맞을 때만 구현으로 넘긴다.
- `LARGE_FEATURE`의 읽기 전용 발견은 최대 2~3개다. 백엔드는 `backend-multi-agent`, 프론트엔드는 `fe-multi-agent`를 함께 적용하고, 발견 결과를 하나의 계획으로 합친 뒤 구현한다.

### 5. IMPLEMENT

유형별 구현 역할:

| 유형 | 구현 |
|------|------|
| `SIMPLE` | 단순 구현 역할. 문구·한 줄 메타데이터는 메인 실행자가 직접 처리할 수 있다 |
| `FEATURE` | 구현 역할. 워크스페이스 전용 역할이 있으면 그쪽을 쓴다 (BE `be-executor`, FE `fe-implementer`) |
| `BUG` | 원인이 확정된 뒤에만 구현 역할이 최소 수정한다 |
| `REFACTOR` | 리팩토링 역할 한 명이 순차 수정한다. 계층·모듈 경계를 넘으면 그 전에 설계 역할을 둔다 |
| `ARCHITECTURE` | 구현 요청이 있을 때만 확정된 계획을 구현 역할 또는 리팩토링 역할 한 명에게 넘긴다 |

공유 파일, 공개 계약, DB 스키마, 도메인 객체를 수정하는 쓰기 역할은 한 번에 하나만 실행한다. 하위 에이전트는 다시 에이전트를 만들지 않는다.

### 6. VERIFY

대상 범위의 컴파일과 관련 테스트를 실행한다. 하위 에이전트의 "통과했다"를 완료 근거로 쓰지 않는다. 메인 실행자가 검증 명령을 한 번 더 돌린 결과로 보고한다.

### 7. REVIEW

- `T0`은 대상 테스트로 끝내고 별도 검토를 생략할 수 있다.
- 공개 API, 보안, 트랜잭션, 복수 계층, 변경량이 큰 `T1`·`T2`는 검토 역할을 둔다.
- `T3`는 검토 역할을 최상위 칸으로 두고, 보안·인증·결제·개인정보가 범위에 있으면 해당 보안 검토를 추가한다.
- HIGH 이상 지적만 구현 역할이 수정한 뒤 다시 검증한다.

## 기본 원칙

- 먼저 루트 `AGENTS.md`(Claude Code는 `CLAUDE.md`)와 대상 워크스페이스의 엔트리 문서를 읽는다.
- 에이전트 수보다 작업 경계와 증거를 우선한다. 명확한 작업에 조사 역할을 형식적으로 더하지 않는다.
- 병렬 실행은 서로 독립적인 읽기 전용 조사·검토에만 쓴다.
- 사용자가 명시적으로 병렬화·특정 역할·특정 모델을 요청하면 그 호스트에서 가능한 범위에서 우선한다.
- 워크스페이스 전용 역할은 Claude Code에만 파일이 있다. BE는 `be-executor` / `be-hexagonal-reviewer` / `be-db-reviewer` / `be-security-reviewer`, FE는 `fe-*` 7종이다. 다른 호스트에서는 해당 역할의 절차를 메인 실행자가 순서대로 적용한다.

## 완료 조건

1. 요청한 동작이 구현되었다.
2. 영향 범위가 컴파일되고 관련 테스트가 통과했다.
3. 필요한 수준의 최종 검토가 끝났다.
4. CRITICAL/HIGH 지적이 해결되었다.
5. 불필요한 변경과 겹치는 동시 편집이 없다.
6. 보고에 `TYPE`, `COMPLEXITY`, 실제 사용한 역할과 호스트별 실행 수단(Codex는 모델·추론 강도, Cursor는 모드), 실행한 검증, 남은 위험이 있다.
